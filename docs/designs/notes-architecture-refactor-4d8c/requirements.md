# apps/notes 아키텍처 리팩토링 요구사항

이 문서는 `apps/notes`의 모듈 구조와 상태 관리를 재정비할 때 지켜야 할 요구사항을 정한다. 이후 구현자는 사용자가 현재 수행할 수 있는 작업과 저장 자료를 유지하면서 각 모듈의 책임, 상태를 관리하는 위치와 의존성 연결을 명확하게 해야 한다.

## 목표 상태

- `apps/notes`의 각 모듈은 한 가지 사용자 동작 또는 함께 바뀌는 책임을 맡고, 다른 모듈은 slice의 `public API`를 통해 사용한다.
- 화면 상태, 편집 중인 값, 저장 자료와 브라우저 API마다 관리 위치를 정해 같은 값을 여러 곳에서 관리하지 않는다.
- UI 표현, 도메인 규칙, 사용자 동작 처리, 저장소와 브라우저 의존성을 각각 바꾸어도 무관한 모듈은 수정할 필요가 없어야 한다.
- 리팩토링 뒤에도 사용자가 현재 수행할 수 있는 작업은 기존 요구사항의 동작을 그대로 유지해야 한다.

## 지켜야 할 조건

### 현재 사용 동작과 저장 자료를 유지한다

- [개인 메모 애플리케이션 요구사항](../personal-notes-app-8fd/requirements.md)과 [`apps/notes` 디자인 체계](../../../apps/notes/DESIGN.md)의 조건과 완료 증거를 계속 충족한다. 이 문서들은 사용자가 할 수 있는 일, 입력, 화면과 문구의 기준으로 남는다.
- 현재 서비스가 제공하는 메모 작성과 편집, 자동 저장 및 복구, 메모 배치와 속성, 복사와 삭제 취소, 일괄 복사, 템플릿, 텍스트 분석, 사용 횟수와 설정을 제거하거나 약화하지 않는다.
- 메모 이동과 네 가장자리 및 네 꼭짓점의 크기 조절에서 입력한 거리와 방향을 저장 좌표에 반영한다. 캔버스를 확대하거나 축소한 뒤에도 같은 규칙을 적용하고, 입력이 끝나기 전에 취소되면 변경을 저장하지 않는다. 저장한 메모의 원문과 본문 revision은 도형 조작만으로 바뀌지 않아야 한다.
- 화면 폭별 레이아웃, 주소, 탐색, 키보드와 포인터 조작, 접근성 이름, 진행 상태, 오류 안내와 재시도 동작을 유지한다. 화면 디자인은 기존 디자인 체계를 따른다.
- 기존 URL(`/`, `/notes/[noteId]`, `/batch-copy`, `/usage`, `/analysis`, `/templates`, `/settings`)을 유지한다.
- 브라우저의 IndexedDB에 기록한 메모, 메모 초안, 일괄 복사 자료, 템플릿, 설정과 사용 기록을 계속 읽을 수 있어야 한다. 저장 형식이나 IndexedDB 버전을 바꿀 필요가 생기면 기존 자료를 보존하고 새 버전으로 옮기는 과정을 제공한다.
- 저장 또는 복구가 실패하거나, 업그레이드를 기다리거나, 저장소 연결이 끝나도 기존의 오류 안내, 재시도와 복구 동작을 유지한다.
- 기존 요구사항과 실제 서비스 동작이 다르게 확인되면 영향을 받는 변경을 멈추고, 어느 쪽을 기준으로 할지 결정하기 전까지 기존 동작을 제거하거나 요구사항을 고치지 않는다.

### 모듈 책임과 의존 방향을 분명히 한다

- FSD 구조와 계층 의존 방향을 준수하고 slice의 `public API`를 유지한다. Next.js의 `app/` 라우트와 소스의 FSD 페이지 계층은 구별한다. ESLint import 검사가 계층 위반을 계속 찾아내야 한다.
- 같은 계층에 있는 다른 slice의 내부 모듈을 직접 import하지 않는다. 필요한 교차 참조는 기존 `public API`에 명시하고, 순환 import를 만들지 않는다.
- 모듈은 한 가지 사용자 동작 또는 함께 바뀌는 책임을 맡는다. 서로 독립적으로 바뀌는 책임을 범용 service, manager, helper 또는 utility에 합치지 않는다.
- 하나의 Hook에서 서로 다른 이유로 바뀌는 상태나 외부 시스템 연결을 함께 관리하는 경우 그 책임을 나눈다. 같은 사용자 동작의 상태 전이, 저장 순서와 오류 처리는 파일 길이나 함수 수만을 이유로 분리하지 않는다.
- UI는 필요한 값과 이벤트를 입력으로 받아 표현한다. 저장소나 브라우저 구현을 UI에서 직접 생성하지 않는다. 도메인 규칙, 사용자 동작 처리와 화면 표현은 각각 독립적으로 바꿀 수 있게 둔다.
- 실행 환경에 따라 구현이 바뀌는 IndexedDB, 클립보드, 시계, 식별자 생성과 분석 Worker는 필요한 동작만 드러내는 타입으로 연결한다. 구체 구현 선택과 조립은 애플리케이션의 명시적인 조립 지점에서 맡긴다.
- 모든 저장소와 브라우저 의존성을 하나의 애플리케이션 객체나 범용 Context에 모아 관리하지 않는다. 설정, 메모, 분석 등은 자신이 쓰는 capability만 전달받고, 함께 써야 하는 자원은 그 자원의 수명에 맞춰 공유한다.
- 기존 `public API`, 조립 방식과 의존성 타입이 같은 책임을 이미 맡으면 먼저 재사용한다. 실제 변경 가능성이나 중복이 드러나지 않은 범용 추상화, 빈 구조, 전역 의존성 조회기 또는 새 의존성은 추가하지 않는다.
- React와 Next.js 실행 환경을 구분한다. 브라우저 API를 쓰는 코드는 필요한 Client Component 경계 안에 두고, 서버에서 클라이언트로 전달하는 값은 직렬화 가능한 자료로 제한한다.

### 상태마다 기준이 되는 위치를 하나 둔다

- IndexedDB와 각 repository가 저장 자료의 기준이다. 저장 전 입력, 화면 선택, 제스처 진행, 알림과 경고는 필요한 수명에 맞춰 각각 관리한다.
- IndexedDB를 사용하는 비동기 조회와 변경에도 TanStack Query가 적합한지 검토한다. IndexedDB를 저장 원본으로 유지하면서 각 작업의 cache 수명, 저장 뒤 cache 일관성, 실패 처리와 현재 provider의 책임을 비교하고, 적용 여부와 근거를 기록한다. 이 검토만으로 의존성 추가나 저장 자료 변경을 승인하지 않는다.
- 폼 입력값, dirty와 validation 상태는 React Hook Form 사용 지침에 따라 폼 단위로 관리한다. 같은 입력값을 React state, Context 또는 도메인 초안에 매번 복제하지 않는다.
- 화면에서 함께 바뀌어야 하는 상태는 그 상태를 실제로 공유하는 가장 가까운 조립 지점에서 관리한다. 화면 전체에 무관한 상태를 모으거나 단순한 파생값을 별도 상태로 저장하지 않는다.
- Context는 깊은 하위 구성요소들이 함께 써야 하는 상태나 동작을, 필요한 하위 구성요소를 감싼 곳에서 제공할 때만 사용한다. 인프라 조회를 위한 전역 container로 사용하지 않는다. 컴포넌트를 정의하는 값과 이벤트는 Props로 전달하고, UI 합성은 `children`을 우선한다.
- 저장, 복사와 탐색은 이를 시작한 사용자 입력 처리 안에서 실행한다. 렌더링 중 부수 효과를 일으키거나 외부 시스템 동기화 목적이 아닌 Effect로 내부 상태를 맞추지 않는다.
- 선택, 포커스, 속성 대상, drag, 편집 초안, 저장 진행과 저장 성공은 기존 동작에서 정한 수명과 의미를 유지한다. 하나의 값으로 합쳐 서로 다른 사용 동작을 바꾸지 않는다.

### 반응성과 유지보수성을 해치지 않는다

- 기존 요구사항의 반응성과 전체 메모 접근을 유지한다. 모바일 목록은 메모 수가 늘어도 모든 메모를 탐색하고 일괄 복사에 쓸 수 있어야 한다. 목록 성능은 [기존 완료 증거](../personal-notes-app-8fd/requirements.md#완료를-확인할-증거)의 대표 자료량, IndexedDB 조회, 초안 복구, 첫 화면, JavaScript heap, DOM 수와 스크롤 반응을 변경 전후 같은 조건에서 비교한다.
- 한 메모를 편집할 때 무관한 메모와 화면 전체의 렌더링을 불필요하게 늘리지 않는다. 상태를 옮기거나 구독을 바꿀 때 대표 작업에서 기존 렌더링 비용을 악화시키지 않는다.
- 상태 처리 Hook의 구현은 `.ts` 모듈에 두고, 컴포넌트는 필요한 Hook을 최상위에서 정적으로 호출한다. 컴포넌트 렌더링은 순수하게 유지한다.
- 기존 의존성과 브라우저 자체 동작을 우선 사용한다. 전역 상태 관리 라이브러리, DI container 또는 UI framework 도입은 이 요구사항의 일부가 아니며, 필요한 이유와 영향을 별도로 결정하기 전까지 추가하지 않는다.

## 이번 문서에서 정하지 않는 사항

- 사용자 동작, 화면, 문구와 디자인을 바꾸는 작업
- 계정, 서버 저장, 기기 간 동기화, 새 백엔드와 DB
- 라이브러리 패키지 제공이나 포트폴리오 애플리케이션과의 연결
- 요구사항 검토 없이 하는 IndexedDB 자료 삭제, 의미 변경 또는 재초기화

## 완료를 확인할 증거

- 모든 기존 unit, browser와 E2E 검사가 변경 뒤에도 통과한다. 현재 명령은 `pnpm notes:test`, `pnpm --filter notes-app test:browser`, `pnpm notes:test:e2e`다. 회귀를 피하려고 테스트를 삭제하거나 검증을 약화하지 않는다.
- 메모 이동과 여덟 방향의 크기 조절을 기본 배율과 확대 상태에서 마친 뒤 화면, IndexedDB 저장값과 재방문 결과를 대조한다. 조작 직후와 저장 완료 뒤의 차이를 구분하고, 기존 메모 조작 검사에서 확인된 실패의 원인과 해결 결과를 남긴다.
- `pnpm notes:lint`와 `pnpm notes:typecheck`가 통과하고, ESLint가 FSD 계층 의존 방향과 slice `public API` 우회 import를 계속 차단한다.
- 실제 브라우저에서 주요 화면과 넓은 화면 및 320 CSS px 화면의 사용자 과업을 확인한다. 메모 편집과 재방문, 모바일 초안 복구, 일괄 복사 순서 및 저장, 템플릿 편집, 분석과 설정 저장이 변경 전 동작을 유지해야 한다.
- 기존 IndexedDB 자료를 가진 상태에서 이전 자료를 읽고 필요한 업그레이드를 마친 뒤에도 메모 원문, 순서, 템플릿, 설정, 사용 기록과 복구 초안을 확인할 수 있어야 한다.
- 구현 계획에서 리팩토링 대상인 IndexedDB 읽기와 변경 작업마다 TanStack Query 적용 또는 미적용 판단, cache와 IndexedDB 사이의 일관성, 저장 실패 처리와 판단 근거를 확인할 수 있어야 한다. 도입을 제안한다면 패키지 버전, 의존성 그래프와 연결 위치를 별도로 조사한다.
- 코드 검토에서 각 상태를 관리하는 위치, 각 모듈의 책임, slice 간 import 방향과 외부 의존성을 조립하는 위치를 확인할 수 있어야 한다. 검증은 사용자가 확인하는 동작과 저장 자료를 기준으로 하며 파일 배치나 Hook 호출 형태만으로 완료를 판정하지 않는다.
- 의존성 연결을 확인할 때 모든 구현체를 나열하거나 조회하는 단일 객체가 없는지, 각 repository와 `storageMonitor`가 같은 `PersonalNotesDatabase` 인스턴스를 사용하는지, 분석 Worker가 화면 수명에 맞춰 종료되는지 확인한다.
- 책임을 나눈 Hook마다 상태 수명, 호출 위치와 외부에서 사용하는 반환값을 이전과 비교한다. 분리 때문에 독립된 Hook 호출 사이에 동일한 상태를 복제하거나 새 구독과 불필요한 렌더링을 만들지 않아야 한다.

## 조사 근거

[현재 앱 구조와 공식 자료 조사](references/architecture-baseline.md)는 현재 구현에서 확인한 구조, 설치된 기술과 공식 자료가 밝히는 실행 환경의 차이를 기록한다. [메모 조작과 Hook 책임 조사](references/geometry-and-hook-responsibility.md)는 기존 조작 검사와 Hook의 책임을 비교한다. 두 문서의 분석은 이 요구사항을 넓히거나 새 사용자 과업을 승인하지 않는다.
