# 단일 페이지 개발자 소개 웹사이트 제작 플랜

한국어 소개와 근거를 `/` 한 페이지에 구성하고, 실제 콘텐츠로 화면과 조작 반응을 다듬은 다음 영어 버전을 추가한다. 프로젝트 상세, 사례 상세, 전체 목록과 웹 이력서는 만들지 않는다. 긴 해결 과정은 기존 블로그에서 관리하며 이 사이트의 소개만 읽어도 개발자의 정체성과 역량을 이해할 수 있게 한다.

이 플랜은 콘텐츠, 화면 설계와 이후 구현을 위한 절차다. 현재는 문서와 문구 초안이 있고 애플리케이션은 구현하지 않았다. 코드와 설정 변경은 구현에 착수하기로 한 뒤 진행한다. 조사에서 제안한 시각 표현을 승인된 디자인으로 취급하지 않는다.

## 기준 문서와 적용 지침

[요구사항](requirements.md) 전체를 기준으로 하며 작업별 적용 절은 아래에 적는다. 이 플랜을 마지막으로 변경한 커밋에 함께 있는 요구사항과 개발 지침이 기준 버전이다.

- [소개 방향](decisions/developer-positioning.md): 사용자 이해와 화면 설계를 먼저 설명하고 기술적 문제 해결로 뒷받침한다.
- [프로젝트 소개](decisions/project-availability.md): 개인 메모 앱과 Issnuta를 함께 소개한다. 소스와 서비스 URL은 준비된 경우에만 제공한다.
- [대표 경험](decisions/featured-cases.md): 작업별 이력, 문서 생성, 화면 정지와 대시보드의 네 경험을 짧게 소개한다.
- [문구 저장](decisions/terms-storage.md): `src/shared/terms/ko.json`으로 시작하고 한국어 제작 후 `en.json`을 추가한다.
- [단일 페이지 UI, UX 조사](references/single-page-ui-ux.md): 원자료와 2025~2026 사례의 확인 범위, 권장 배치와 미결정 시각 표현을 구분한다.
- [개발 지침](../../dev/README.md): 구현 환경, 기술과 의존성, 수정할 파일과 검사 방법을 정할 때 적용한다. 현재 기술별 지침과 실행 명령은 없다.

## 요구사항 변경의 영향

기존 플랜의 다중 페이지 제작 절차는 단일 페이지 구성으로 대체한다. 프로젝트 및 사례 상세 주소, 웹 이력서 본문, 페이지 간 전환, 상세 글의 Markdown/MDX 저장 방식은 더 이상 구현할 대상이 아니다. 이 브랜치의 추적 파일에는 애플리케이션 소스와 의존성 명세가 없으므로 현재 제거할 라우트나 코드도 없다.

소개 방향, 확정된 첫 문장, 두 프로젝트, 네 경험, 두 오픈소스 기여와 한국어 우선 제작은 유지한다. [경험의 상세 근거](references/featured-case-copy.md)와 프로젝트 조사 자료는 편집 자료로 남긴다. 긴 본문을 홈페이지에 모두 펼치거나 접이식 상세로 옮기지 않는다.

## 작업 상태와 중단 조건

상태는 시작 전, 진행 중, 대기, 완료로 구분한다. 시작하거나 멈출 때 실제 진척에 맞춰 갱신하고, 완료할 때에는 해당 절의 결과와 확인 근거를 남긴다. 문서 완료와 화면 구현 완료를 구분한다.

작업 단위마다 마지막에 필요한 확인을 한 번 수행한다. 실패하거나 수정한 부분만 다시 확인한다. 다음 조건에서는 영향을 받는 작업을 멈추고 필요한 선택을 확인한다.

- 미결정 디자인이나 문구를 최종 결과로 구현해야 하는 경우.
- 새 프레임워크, 의존성, 배포 조건 또는 언어별 주소가 필요한 경우.
- 실제 자료와 초안의 기능, 성과나 링크가 다르거나 이미지 사용 가능 여부가 불명확한 경우.
- 단일 페이지 소개를 넘어 새 앱, 블로그 기능이나 연락 양식이 필요해지는 경우.
- 요구사항과 적용 지침이 충돌하거나 기존 구현에서 유지할 동작이 불명확한 경우.

이와 무관한 자료 정리와 조사까지 중단하지 않는다. 새로운 요구사항이 생기면 영향을 받는 문서와 플랜을 갱신해 커밋한 뒤 해당 작업을 재개한다.

## 작업 순서

### 소개 방향과 단일 페이지 구성의 조사

상태: 완료.

적용 요구사항: 「사이트의 역할과 자료 활용」, 「개발자 소개와 문구 작성」, 「주소와 콘텐츠 구분」, 「시각적 방향」.

[기존 채용 수요 조사](references/frontend-hiring-and-positioning.md)와 승인된 소개 방향을 유지하고, 세 입력 자료 및 실제 사이트를 비교한 [단일 페이지 조사](references/single-page-ui-ux.md)에 콘텐츠와 화면의 역할을 정리했다. 출처, 관찰 범위, 수치의 조건과 제안을 구분한 문서가 산출물이다. 이는 조사 완료이며 제안한 색, 글꼴과 화면의 확정 또는 구현 완료가 아니다.

### 한국어 콘텐츠와 연결 대상 확정

상태: 진행 중.

적용 요구사항: 「개발자 소개와 문구 작성」, 「Project」, 「Case」, 「홈페이지」, 「완료를 확인할 결과」.

[홈페이지 문구](references/homepage-copy.md)에는 확정된 첫 문장, 두 프로젝트, 네 경험, 오픈소스, 글 후보와 연락 안내가 있다. 회사 경험은 최신 이력서와 포트폴리오의 조건을 대조했다. 선정 항목은 확정되어 있으나 보조 문구, 배치와 글 선정은 초안이다.

- 실제 게재 본문은 `references/homepage-copy.md`에서 다듬는다. 첫 소개는 확정된 문장을 유지하며 보조 문장을 줄인다. 소개의 강점이 프로젝트와 경험의 근거로 이어지는지 확인한다.
- 프로젝트의 목적, 제작 내용과 현재 활동을 짧게 정리한다. 메모 앱의 소스 URL은 없어도 진행하고 Issnuta의 소스는 유지한다. 이용 주소가 생겼다면 실제 서비스와 소스 링크를 구분한다.
- 네 경험은 판단과 확인된 변화만 남긴다. 수치의 대상과 조건을 생략하지 않으며 상세 절차와 도식은 편집 자료에 둔다. 해당 경험의 블로그 글이 없는 경우 링크를 만들어 넣지 않는다.
- [글 후보](references/homepage-content.md#확인이-필요한-질문)에서 게재 목록을 정한다. React 글 한 편과 블로그 링크가 추천안이며 기존 두 글은 자동 확정하지 않는다. 발행 시점과 현재 기술 설명을 구분하고 향후 글 추가 기준도 유지한다.
- PR 및 릴리스, 이메일과 GitHub 및 LinkedIn, 최신 이력서의 이용 가능한 주소를 준비한다. 원본에 연락처가 있다는 이유로 개인정보가 포함된 PDF 전체를 추적 파일에 추가하지 않는다.
- 프로젝트 미리보기의 실제 자료와 사용 가능 여부를 확인한다. 현재 기능을 벗어난 가짜 화면으로 대체하지 않는다.

산출물은 게재할 한국어 문구, 링크와 시각 자료의 선택이다. 완료 조건은 페이지 이동 없이 어떤 개발자이며 무엇을 맡길 수 있는지 설명할 수 있고, 주장에 실제 근거가 있으며 링크 목적과 제공 여부가 정해져 있는 것이다. 게재 문구와 글 선정이 미정이면 완료로 표시하지 않는다.

### 구현 환경과 기존 자료 확인

상태: 시작 전.

적용 요구사항: 「디자인 체계의 구성과 제작 순서」, 「모호한 상황의 확인」.

콘텐츠 확정과 독립적으로 진행할 수 있다. 화면 설계 전에 소스, 의존성 명세와 잠금 파일, 스타일, 글꼴, 이미지, 실행 및 검사 설정을 다시 확인한다. 기존 블로그와 이력서에서 연결하거나 재사용할 자료와 유지할 동작도 확인한다. 없는 항목과 접근할 수 없는 항목을 구별한다.

현재 확인된 구성은 설계 문서와 저장소 지침뿐이다. 미리 고른 프레임워크의 관례를 기존 구조로 기록하지 않는다. 산출물은 재사용할 자료와 새로 정할 기술의 목록이다. 완료 조건은 유지할 동작과 화면 설계에 사용할 자료를 특정할 수 있는 것이다.

### 실제 한국어로 화면 구성과 시각 규칙 선택

상태: 시작 전.

적용 요구사항: 「홈페이지」, 「공통 화면」, 「시각적 방향」, 「조작과 상태」, 「접근성과 반응형 동작」.

시작 조건은 실제 문구, 기존 자료와 미리보기 제공 조건을 아는 것이다. [조사의 UI 제안](references/single-page-ui-ux.md#ui-제안-작업의-목적과-결과를-나란히-읽는-화면)을 비교 출발점으로 사용한다.

- 첫 소개에서 프로젝트의 시작까지 이어지는 화면과 페이지 전체를 함께 설계한다. 헤더의 내부 탐색과 외부 링크를 구분한다. 데스크톱의 섹션 제목 열 및 내용 열은 모바일에서 같은 순서의 한 열로 바꾼다.
- 두 프로젝트의 설명과 실제 UI 또는 재구성한 설명 그림을 비교한다. 경험 네 개는 접지 않은 요약으로 두고 긴 기술 설명을 추가하지 않는다.
- 텍스트만 있는 배치와 실제 프로젝트 화면을 보탠 배치를 같은 문구로 비교한다. 후자를 추천하되 이미지의 존재만으로 개성이 충분하다고 판단하지 않는다. 선택 표시와 결과를 잇는 2D 표현이 이해를 돕는지 살핀다.
- 1440×900과 390×844에서 첫 화면의 정보 밀도, 한글 줄바꿈, 제목과 본문 대비 및 프로젝트와 경험의 구분을 확인한다. 320px 폭과 200% 글자 확대에서도 내용이 잘리지 않아야 한다.
- 기본, hover, focus, active와 필요한 현재 위치 표시를 정한다. reduced-motion에서 제거할 움직임과 터치에서 유지할 정보도 함께 정한다.
- 밝은 테마 추천안, 글꼴, 강조색, 폭과 여백을 비교해 최종 선택을 확인한다. 3D나 조작형 시연이 필요해지면 별도 선택과 성능 및 접근성 조건을 먼저 정한다.

산출물은 승인된 페이지 구성과 실제 문구가 들어간 데스크톱 및 모바일 화면, 조작 상태의 표현이다. 선택 전에는 토큰의 확정값으로 옮기지 않는다. 완료 조건은 소개가 경험의 근거로 이어지고, 다른 사이트의 배치를 복제하지 않으면서 실제 작업과 연결된 시각적 특징을 설명할 수 있는 것이다.

### 기술 구성과 콘텐츠 형식 결정

상태: 시작 전.

적용 요구사항: 「문구 관리와 언어」, 「주소와 콘텐츠 구분」, 「디자인 체계의 구성과 제작 순서」.

구현 환경과 필요한 화면 및 동작이 정해진 뒤 진행한다. 기본 HTML 링크로 탐색하고 소개를 정적으로 제공하는 방식을 우선 비교한다. 프레임워크는 아직 선택하지 않았으며, `/`가 하나라는 이유만으로 클라이언트 렌더링 SPA를 요구하지 않는다.

- 프레임워크와 정확한 버전, 배포 방식, 한글 글꼴, CSS 및 이미지 처리 방식을 정한다. 의존성 선택 전에 [개발 지침](../../dev/README.md)의 공식 통합 방식, 패턴, 직접 및 전이 의존성 조사와 기존 기능 비교를 수행한다.
- 프로젝트 식별자, 선택적인 서비스 및 소스 URL, 경험의 근거 링크와 글의 날짜를 문구와 구분해 관리할 형식을 정한다. 소개, 제목, 설명과 안내는 `src/shared/terms/ko.json`에서 수정할 수 있어야 한다.
- FSD의 필요한 레이어만 사용한다. 홈 조합의 후보 위치는 `src/pages/home`이며 프레임워크의 파일 기반 라우터와 충돌하면 같은 책임을 갖는 폴더명을 먼저 정한다. 상세 주소 체계와 긴 본문 엔진은 추가하지 않는다.
- 실제로 추가할 파일, 적용할 기존 검사 명령과 최소 확인 방법을 정한다. 새 테스트 코드나 검사 스크립트를 이 플랜만으로 작성하지 않는다.

산출물은 승인된 기술 및 콘텐츠 구성과 파일 및 검사 목록이다. 기술이 미정이거나 필수 확인을 수행할 수 없으면 다음 구현 작업을 시작하지 않는다.

### 디자인 체계와 한국어 문구 데이터 구성

상태: 시작 전.

적용 요구사항: 「디자인 체계의 구성과 제작 순서」, 「문구 관리와 언어」, 「시각적 방향」.

승인된 시각 규칙과 기술 결정을 사용한다. 저장소 최상위 `DESIGN.md`에 필요한 요소, 색과 글자 및 간격, 상태, 반응형과 움직임 규칙을 작성한다. 의미 있게 반복하는 값만 토큰으로 만든다. 테마, 그림자와 겹친 영역은 실제 필요한 범위만 정의한다.

한국어 문구는 `src/shared/terms/ko.json`에 추가한다. 링크, 섹션 제목, 프로젝트 설명과 외부 링크 묶음, 경험의 결과 및 조건, 오픈소스와 글의 반복 항목만 재사용 대상으로 판단한다. 요소 이름마다 파일을 만들거나 사용하지 않는 입력창, 모달과 선택 UI를 추가하지 않는다.

코드 추가 대상은 앞 작업에서 정한 기본 스타일과 재사용 UI다. 제거할 기존 코드는 현재 없으며 착수 시 생긴 코드가 있다면 유지할 동작부터 확인한다. 완료 조건은 `DESIGN.md`의 규칙을 실제 샘플에 적용할 수 있고 한국어 문구를 데이터 수정만으로 바꿀 수 있는 것이다.

### 한국어 단일 페이지와 외부 연결 구현

상태: 시작 전.

적용 요구사항: 「주소와 콘텐츠 구분」, 「Project」, 「Case」, 「홈페이지」, 「공통 화면」, 「조작과 상태」.

승인된 홈 조합과 콘텐츠 형식에 따라 소개, 프로젝트, 경험, 오픈소스, 글과 연락을 구현한다. 본문 바로가기와 섹션 앵커, 헤더 및 푸터를 연결한다. 별도 `/projects`, `/cases`, `/resume`, `/writing`, `/open-source`와 항목별 상세 페이지는 만들지 않는다. 이후 언어별 주소 선택은 별개다.

- 처음 내려받는 HTML에서 소개와 링크를 읽을 수 있도록 선택한 정적 제공 방식을 적용한다. 시각 효과가 늦거나 실패해도 본문을 유지한다.
- URL이 없는 프로젝트에는 링크와 빈 공간을 만들지 않는다. 서비스와 소스 및 블로그 링크를 중첩하지 않는다. 메모 앱의 소스 URL을 콘텐츠에 추가하고 제거했을 때 UI 수정 없이 링크가 바뀌는지 확인한다.
- 경험 요약만으로 역할과 변화가 이해되게 하고 수치의 조건을 같은 항목에 유지한다. 이력서는 문서 링크로 제공하며 내부에 전체 내용을 복제하지 않는다.
- 승인된 링크 반응과 2D 표현만 적용한다. 소개 정보를 hover 안에 숨기거나 자동 등장, 강제 스크롤과 로딩 전용 화면을 추가하지 않는다.
- React를 선택했다면 Hook 구현은 `.tsx` UI와 분리한다. 읽기 전용 화면을 위해 불필요한 전역 상태, Context와 장식용 렌더 루프를 도입하지 않는다.

완료 조건은 한국어 본문과 링크가 실제 화면에 있고, 내부 탐색이 같은 페이지에서 이루어지며 서비스 준비 여부가 정확히 반영되는 것이다. 다른 브랜치의 프로젝트 개발, 블로그 글 게시와 외부 서비스 배포는 포함하지 않는다.

### 한국어 화면의 동작과 전달력 확인

상태: 시작 전.

적용 요구사항: 「조작과 상태」, 「접근성과 반응형 동작」, 「기본 구성에서 제외하는 표현」, 「완료를 확인할 결과」.

한국어 구현이 준비되면 정한 검사를 실행하고 브라우저에서 한 번의 종합 확인을 한다. 문서나 스크린샷만으로 구현 완료를 판단하지 않는다.

- 첫 방문에서 직무와 개발 기준을 읽고 프로젝트 및 경험에서 근거를 찾을 수 있는지 확인한다. 상세 페이지나 외부 글을 읽어야 자기소개를 이해하게 만들지 않는다.
- 내부 링크, 직접 해시 진입, 새로고침과 뒤로 가기, 키보드 순서 및 포커스를 확인한다. 스크롤 중 포커스를 강제로 바꾸지 않고 고정 요소가 포커스를 가리지 않아야 한다.
- 320px, 390px와 1440px 폭, 200% 글자 확대, 터치와 reduced-motion에서 정보, 링크와 읽는 순서를 유지하는지 확인한다. 적용되는 WCAG 2.2 A 및 AA 항목, 명암비, 대상 크기와 이미지 대체 설명을 함께 점검한다.
- 이미지가 늦거나 없을 때의 본문과 배치, 글꼴 로딩, 링크 누락을 확인한다. PR, 릴리스, 블로그, 이력서와 연락 링크는 각각의 목적지에 맞게 연결되어야 한다.
- 선택한 환경에서 초기 표시, 조작 지연과 배치 변화를 기록한다. [성능 조사 기준](references/single-page-ui-ux.md#접근성과-성능의-확인-기준)을 참고하되 로컬 결과를 실제 방문의 75백분위나 측정하지 않은 INP로 보고하지 않는다.
- `ko.json` 문구만 바꾸어 UI에 반영되는지 확인하고 실제 화면과 `DESIGN.md`를 대조한다.

산출물은 확인 환경과 결과, 수정할 문제 및 미측정 항목이다. 완료 조건은 요구사항에 해당하는 확인을 통과하고 해결하지 못한 필수 문제가 없는 것이다. 성능 수치를 맞추려고 소개 내용을 없애거나 기본 링크를 약화하지 않는다.

### 영어 문구와 같은 구성의 영어 버전 제공

상태: 시작 전.

적용 요구사항: 「문구 관리와 언어」, 「아직 정하지 않은 사항」, 「완료를 확인할 결과」.

한국어 웹사이트의 확인을 마친 뒤 기본 언어, 언어별 주소와 언어 선택 및 번역 누락 처리를 정한다. 언어별 주소를 선택하더라도 각 언어의 소개는 한 페이지에서 완결된다.

`src/shared/terms/en.json`을 추가하고 확정된 한국어의 뜻과 수치 조건을 보존해 작성한다. 기존 홈 조합과 콘텐츠를 재사용하고 영어용 프로젝트 및 사례 상세는 만들지 않는다. 영어 문구로 메뉴 폭, 제목 줄바꿈과 링크 이름, 모바일 및 확대 화면을 확인한다. 언어 변경 시 현재 읽던 섹션의 유지 방식도 선택한 주소 구성에 맞춰 확인한다.

완료 조건은 두 언어의 소개 내용과 링크가 일치하며 각 JSON의 수정만으로 각 언어 문구가 바뀌는 것이다. 영어 단어를 끼워 넣은 한국어 초안이나 빈 영어 파일을 완료 산출물로 취급하지 않는다.
