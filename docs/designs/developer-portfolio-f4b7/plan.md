# 편집형 단일 페이지 개발자 소개 웹사이트 제작 플랜

한국어 소개와 확인 가능한 기여를 `/` 한 페이지에 편집형 기술 프로필로 구성한다. 회사별 Engineering Contribution, 오픈소스, 독립 작업과 연락 정보를 먼저 구현하고 실제 한국어 화면에서 글자, 색상, 여백과 반응형 배치를 확인한 다음 영어 버전을 추가한다.

현재는 요구사항, 조사, 결정과 문구 초안이 있으며 애플리케이션 소스와 의존성 명세는 없다. 코드와 설정 변경은 구현 환경을 정한 뒤 진행한다.

## 기준 문서와 적용 지침

[요구사항](requirements.md) 전체를 기준으로 한다. 이 플랜을 마지막으로 변경한 커밋에 함께 있는 요구사항과 개발 지침이 기준 버전이다.

- [개발자 소개](decisions/developer-positioning.md): 서비스 문제의 원인, 데이터 흐름과 비동기 상태 개선, 배포 후 실제 동작 확인을 앞세운다.
- [Engineering Contribution](decisions/featured-cases.md): 인공지능팩토리의 네 기여와 이전 회사의 압축된 기여를 Experience에 구성한다.
- [독립 작업](decisions/project-availability.md): AI Agent Workflow와 Offline Translation Web App을 소개한다.
- [편집형 시각 방향](decisions/editorial-direction.md): 밝은 바탕, Pretendard, 제한된 분홍색 강조와 비대칭 편집 배치를 사용한다.
- [문구 저장](decisions/terms-storage.md): `src/shared/terms/ko.json`으로 시작하고 한국어 확인 뒤 `en.json`을 추가한다.
- [편집형 디자인 조사](references/editorial-design-system.md): 글꼴, 색상 대비, 반응형 구성과 접근성 근거 및 구현에서 확인할 항목을 구분한다.
- [개발 지침](../../dev/README.md): 기술과 의존성, 수정할 파일과 검사 방법을 정할 때 적용한다. 현재 기술별 지침과 실행 명령은 없다.

## 요구사항 변경의 영향

기존의 개인 프로젝트 우선 화면은 회사별 Engineering Contribution을 먼저 읽는 편집형 기술 프로필로 바뀐다. 개인 메모 앱, 글 목록과 `Selected Work`는 첫 버전의 필수 영역이 아니다. 작업별 이력 구성 경험은 대표 기여에서 제외하고 Reliability & Delivery를 추가한다.

유지하는 내용은 다음과 같다.

- `/` 한 페이지에서 소개가 완결된다.
- 상세한 해결 과정은 블로그가 맡는다.
- React Router와 Outline 기여를 실제 PR 및 공식 릴리스로 연결한다.
- 한국어를 먼저 제작하고 화면 문구를 JSON으로 관리한다.
- 회사 화면을 추정하지 않고 기술 도식은 설명에 필요한 경우에만 사용한다.
- WCAG 2.2 AA, 키보드 사용, 320px 재배치와 200% 글자 확대를 확인한다.

이전 [단일 페이지 UI, UX 조사](references/single-page-ui-ux.md)의 사례 분석은 참고 자료로 유지한다. 이전 조사에서 제안한 프로젝트 중심 정보 순서, 1120px 폭, 17~18px 본문과 미결정 색상 및 글꼴은 구현 기준으로 사용하지 않는다.

## 작업 상태와 중단 조건

상태는 시작 전, 진행 중, 대기와 완료로 구분한다. 문서가 정리된 상태와 실제 화면이 작동하는 상태를 구분한다. 각 작업은 필요한 확인을 마지막에 한 번 수행하고 실패하거나 수정한 부분만 다시 확인한다.

다음 조건에서는 영향을 받는 작업을 멈춘다.

- 문구의 수치와 자료의 조건이 다르거나 역할을 확인할 수 없는 경우.
- 회사 내부 정보, 기관명이나 화면을 추정해야만 내용을 만들 수 있는 경우.
- 새 프레임워크, 의존성, 배포 방식 또는 영어 주소 구성이 필요하지만 비교 근거가 없는 경우.
- Pretendard 제공 방식과 지원 브라우저가 맞지 않거나 컨테이너 쿼리 대안이 필요한 경우.
- 단일 페이지 소개를 넘어 새 앱, 블로그 기능, 연락 양식이나 별도 상세 페이지가 필요한 경우.
- 요구사항과 개발 지침이 충돌하거나 구현에서 유지할 동작이 불명확한 경우.

새로운 요구사항이 생기면 영향을 받는 문서와 플랜을 갱신해 커밋한 뒤 작업을 재개한다.

## 작업 순서

### 편집형 방향과 외부 기준 조사

상태: 완료.

적용 요구사항: 「개발자 소개와 편집 기준」, 「편집형 시각 규칙」, 「글꼴과 글자 체계」, 「색상」, 「여백과 반응형 배치」, 「조작과 움직임」, 「접근성」.

`UI Design System Proposal v1`의 선택을 [편집형 디자인 조사](references/editorial-design-system.md)에서 실제 사이트와 공식 자료에 대조했다. Pretendard 가변 글꼴, 컨테이너 쿼리, 움직임 감소 설정과 WCAG 2.2 기준을 확인했고 브랜드 색상과 흰색의 명암비를 다시 계산했다.

완료 근거는 외부 자료가 설명하는 규칙과 이 사이트가 선택한 수치를 구분하고, 구현에서 다시 확인할 내용을 남긴 것이다. 조사 완료가 실제 화면의 완성을 뜻하지 않는다.

### 한국어 콘텐츠와 링크 확정

상태: 진행 중.

적용 요구사항: 「Identity」, 「Experience」, 「Open Source」, 「Independent Work」, 「Background와 Contact」, 「글과 언어 관리」.

[홈페이지 문구](references/homepage-copy.md)에 실제 화면에서 사용할 한국어 초안을 준비했다. 다음 내용을 확인한 뒤 문구를 확정한다.

- Identity는 기준 문장을 방문자가 한 번에 이해할 수 있는 한두 문장으로 다듬는다.
- 인공지능팩토리의 네 기여는 수치의 대상과 조건을 같은 항목에 유지한다.
- 이전 회사의 경험은 확인된 변화만 남기고 없는 수치를 만들지 않는다.
- React Router와 Outline의 PR 및 릴리스 링크가 실제 기여와 일치하는지 확인한다.
- AI Agent Workflow와 Offline Translation Web App의 이름, 설명, 이용 및 소스 링크를 정한다.
- `30초 이내 배포`의 비교 조건을 확인하지 못하면 게재하지 않는다.
- Email, GitHub, Blog, LinkedIn과 Résumé의 실제 주소를 준비한다.

산출물은 게재할 한국어 문구와 외부 링크다. 완료 조건은 페이지 밖의 설명을 읽지 않아도 어떤 문제를 해결해 온 개발자인지 파악할 수 있고 모든 수치와 링크를 확인할 수 있는 것이다.

### 구현 환경과 기존 자료 확인

상태: 시작 전.

적용 요구사항: 「디자인 체계와 제작 순서」, 「구현 전에 정할 사항」.

현재 브랜치에는 설계 문서와 저장소 지침만 있다. 애플리케이션을 만들기 전에 다음을 조사하고 결정한다.

- 프레임워크, 정적 HTML 제공 방식, 배포 방식과 지원 브라우저
- 스타일 작성 방식, CSS 변수와 테마 구성
- Pretendard를 로컬 파일, 패키지 또는 CDN으로 제공하는 방식과 fallback
- 아이콘과 이미지 처리 방식
- 같은 페이지 안의 이동, 직접 해시 진입과 새로고침 처리
- lint, 타입 검사, 빌드와 브라우저 확인 방법

외부 의존성을 선택하기 전에 [개발 지침](../../dev/README.md)에 따라 공식 통합 방식, 버전, 기능, 잠재적 문제와 대안을 조사한다. 한 페이지라는 이유만으로 클라이언트 렌더링 SPA를 전제하지 않는다.

산출물은 기술 선택과 실제로 추가할 파일 및 검사 목록이다. 기술과 검사 방법이 정해지지 않으면 구현을 시작하지 않는다.

### 디자인 체계와 한국어 문구 데이터 구성

상태: 시작 전.

적용 요구사항: 「글과 언어 관리」, 「편집형 시각 규칙」, 「글꼴과 글자 체계」, 「색상」, 「여백과 반응형 배치」.

저장소 최상위 `DESIGN.md`에 구현과 일치하는 시각 규칙을 기록하고 한국어 문구를 `src/shared/terms/ko.json`에 둔다.

- Proposal의 색상 역할을 실제 토큰 이름에 연결한다. `#EE5166`은 일반 본문에 사용하지 않는다.
- Pretendard 제공 방식, fallback과 400, 500, 600 및 700 굵기를 기록한다.
- 글자 크기, 줄 높이, 본문 폭, 1200px 내용 폭과 유동적인 좌우 여백을 실제 한국어 문구로 확인한다.
- 여백 정보, 문맥 안의 수치, 빠르게 읽는 근거 행과 제한된 구분선을 반복 규칙으로 정의한다.
- PageHeader, IdentityBlock, SectionHeader, CompanyHeader, ContributionBlock, MetricStatement, MetadataLine, SystemFigure, EvidenceRow, IndependentWorkEntry, ExternalTextLink와 ContactDirectory 중 실제로 반복되는 단위만 구성 요소로 만든다.
- 사용하지 않는 modal, drawer, toast, table, tab, search, carousel, tooltip과 form 상태를 미리 만들지 않는다.

완료 조건은 `DESIGN.md`와 한국어 데이터만으로 각 영역의 표현, 상태와 사용 조건을 설명할 수 있고 문구를 바꿀 때 UI 코드를 수정하지 않아도 되는 것이다.

### 한국어 단일 페이지 구현

상태: 시작 전.

적용 요구사항: 「한 페이지의 정보 순서」, 「Identity」, 「Experience」, 「Open Source」, 「Independent Work」, 「Background와 Contact」, 「조작과 움직임」.

`/`에 Header, Identity, Experience, Open Source, Independent Work, Background, Contact와 Footer를 순서대로 구현한다. 별도 프로젝트, 경험, 이력서와 글 페이지를 만들지 않는다.

- 처음 전달되는 HTML에서 소개와 주요 링크를 읽을 수 있게 한다.
- Identity에 화면 전체 높이를 강제하지 않고 첫 Experience로 자연스럽게 이어지게 한다.
- Experience는 회사를 최상위 단위로 두고 기여의 성격에 맞춰 수치 중심, 구조 중심과 근거 중심의 다른 밀도를 사용한다.
- 오픈소스와 Background는 큰 카드 대신 읽기 쉬운 행으로 제공한다.
- 링크가 없는 항목에는 빈 버튼과 비활성 버튼을 만들지 않는다.
- 기술 정보는 pill 태그 모음이 아니라 기술을 사용한 경험 옆의 MetadataLine으로 제공한다.
- 설명이 더 분명해지는 경우에만 SystemFigure를 추가하고 본문 또는 `figcaption`으로 같은 의미를 제공한다.
- 링크와 현재 위치의 반응만 제한적으로 움직이며 콘텐츠를 애니메이션 완료 뒤에 표시하지 않는다.

완료 조건은 한국어 본문과 링크가 실제 화면에 있고 같은 페이지 안에서 각 영역으로 이동할 수 있으며 외부 링크의 목적을 이름만으로 알 수 있는 것이다.

### 반응형 배치와 접근성 확인

상태: 시작 전.

적용 요구사항: 「여백과 반응형 배치」, 「조작과 움직임」, 「접근성」, 「완료 기준」.

한국어 화면에서 페이지 전체 구성과 구성 요소 내부 배치를 나누어 확인한다.

- 320px와 390px에서는 보조 정보를 본문 앞 또는 안에 두고 한 열의 DOM 읽는 순서를 유지한다.
- 약 48rem과 70rem에서는 실제 내용이 자연스럽게 분리될 때만 편집 그리드를 적용한다.
- Contribution, Evidence Row와 System Figure는 필요한 경우 각각의 가용 폭에 반응하는 컨테이너 쿼리를 적용한다.
- 1440px에서 1200px 최대 폭과 바깥 여백이 본문 및 수치를 지나치게 흩어 놓지 않는지 확인한다.
- 200% 글자 확대에서 내용과 조작 수단이 사라지거나 페이지 전체에 가로 스크롤이 생기지 않아야 한다.
- 키보드 순서, 포커스 표시, 직접 해시 진입, 새로고침과 뒤로 가기를 확인한다.
- Header를 고정한다면 포커스와 영역 제목을 가리지 않도록 `scroll-margin`과 실제 이동을 확인한다.
- 일반 텍스트 4.5:1, 큰 텍스트 및 의미 있는 비텍스트 표시 3:1과 포인터 대상 조건을 확인한다.
- `prefers-reduced-motion: reduce`에서 비필수 움직임을 없애고 모든 내용을 즉시 읽을 수 있게 한다.
- 글꼴이 늦게 불러와지거나 도식이 표시되지 않아도 본문과 링크를 사용할 수 있어야 한다.

산출물은 확인한 화면 크기, 조작 방식, 결과와 조정한 디자인 값이다. 값이 바뀌면 `DESIGN.md`와 구현을 함께 갱신한다.

### 영어 문구와 같은 구성의 영어 버전 제공

상태: 시작 전.

적용 요구사항: 「글과 언어 관리」, 「구현 전에 정할 사항」, 「완료 기준」.

한국어 화면 확인을 마친 뒤 기본 언어, 언어별 주소와 언어 선택 방식을 정한다. `src/shared/terms/en.json`에 확정된 한국어의 뜻과 수치 조건을 보존한 영어 문구를 추가한다.

기존 한 페이지 구성과 콘텐츠 데이터를 재사용한다. 영어 문구로 Header 폭, 제목 줄바꿈, MetadataLine과 모바일 화면을 다시 확인한다. 영어 전용 상세 페이지와 별도의 프로젝트 구성을 만들지 않는다.

완료 조건은 두 언어의 정보와 링크가 일치하며 각 JSON의 수정만으로 선택한 언어 화면이 바뀌는 것이다.
