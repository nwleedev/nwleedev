# 개발자 소개 웹사이트 제작 플랜과 작업 상태

한국어 콘텐츠를 정리한 뒤 디자인과 페이지 제작을 진행하고, 한국어 웹사이트의 페이지와 탐색 동작을 확인한 다음 영어 문구와 영어 버전을 구성한다. 각 절차의 상태와 남은 작업은 이 문서에서 추적한다.

이 플랜은 문구, 디자인과 개발 작업을 이어가는 데 사용한다. 아직 정하지 않은 기술과 디자인은 아래 결정 절차에서 구체화한다. 구현 절차에 적힌 내용은 예정된 작업이며, 코드 구현을 진행하기로 한 뒤 실행한다.

## 기준 문서와 적용 지침

기준은 [요구사항](requirements.md) 전체다. 절차별로 적용할 절 제목을 명시하고, 다음 결정과 조사 자료를 함께 사용한다.

- [개발자 소개 방향](decisions/developer-positioning.md): 사용자 이해와 화면 설계를 앞세우고, 기술적 문제 해결 경험으로 뒷받침한다.
- [대표 사례 구성](decisions/featured-cases.md): 작업별 이력 구성, 장시간 문서 생성, 화면 정지 해결, 대시보드 개선의 네 사례를 홈페이지에 소개한다.
- [첫 버전의 프로젝트 소개](decisions/project-availability.md): 개인 메모 앱과 Issnuta를 함께 소개한다. 메모 앱은 소개부터 제공하고 소스 주소를 나중에 추가할 수 있게 하며, 실제 서비스가 준비되면 이용 링크를 추가한다.
- [FSD 구조와 문구 저장 위치](decisions/terms-storage.md): 한국어 제작 단계부터 `src/shared/terms/ko.json`을 사용하고, 영어 문구를 구성할 때 같은 폴더에 `en.json`을 추가한다.
- [UI 디자인 제안서 반영 위치](references/proposal-coverage.md): 제안서의 각 내용이 요구사항과 조사 자료의 어느 부분에 반영되었는지 확인한다.
- [개발 지침](../../dev/README.md): 기술 조사, 의존성 선택, 실제 수정할 파일과 확인 방법을 정할 때 적용한다. 현재 기술별 지침과 실행 명령은 없으므로 기술을 선택하는 절차에서 적용할 지침과 명령을 구체화한다.

기준 문서의 버전은 이 플랜을 마지막으로 변경한 커밋에 함께 있는 버전으로 확인한다. 플랜을 처음 커밋하기 전에는 작성 시 읽은 문서를 기준으로 삼는다.

## 상태를 기록하고 갱신하는 방법

각 절차의 `상태`가 진행 여부를 나타내는 유일한 기록이다. 별도 현황표나 작업 번호를 만들지 않고, 다른 절차를 가리킬 때에는 그 절차의 제목을 사용한다.

- **시작 전**: 아직 착수하지 않았다. 시작 조건이 충족되지 않은 후속 절차도 이 상태로 둔다.
- **진행 중**: 실제 작업에 착수했으며 완료 조건을 아직 충족하지 않았다. 일부 산출물이 있어도 남은 작업이 있으면 유지한다.
- **대기**: 착수한 작업을 답변, 자료 또는 선행 작업 때문에 멈췄다. 대기 이유와 재개 조건을 같은 절에 적는다.
- **완료**: 필요한 산출물이 있고, 명시된 완료 조건을 확인했다. 확인한 파일이나 화면, 확인 방법과 결과를 같은 절에 남긴다.

**각 절차를 시작할 때 먼저 상태를 `진행 중`으로 바꾸고 저장한다. 작업을 진행할 때마다 같은 절의 진행 내용과 남은 작업을 갱신한다.** 다음 절차로 이동하거나 작업을 멈추기 전에 실제 진척과 기록이 일치하도록 수정한다. 전체 작업이 끝날 때 한꺼번에 상태를 바꾸지 않는다.

중단할 때에는 `대기`로 바꾸고 필요한 답변이나 자료를 구체적으로 적는다. 재개 조건이 충족되면 새로 확인한 사실이나 결정을 문서와 플랜에 반영하고, 실제 재개 시 `진행 중`으로 바꾼다. 완료 조건을 충족하면 근거를 기록한 뒤 `완료`로 바꾼다. 변경 사항을 커밋할 때 작업한 절차의 상태 변경도 함께 포함한다.

모호한 상황에서는 가능한 선택지, 선택에 따라 달라지는 점, 추천안과 이유를 제시한다. 답변이 필요한 작업은 멈추고, 답변과 무관한 작업만 계속한다. 기존에 확정된 선택은 다시 질문하지 않는다.

완료한 작업에 수정이 필요하면 수정할 절차를 다시 `진행 중`으로 바꾸고 수정 이유를 적는다. 결정이 필요해 바로 수정할 수 없으면 `대기`로 바꾼다. 요구사항이 변경되면 영향을 받는 후속 작업을 멈추고, 변경된 요구사항을 반영해야 하는 문서와 플랜을 갱신해 커밋한 뒤 재개한다.

각 절차의 마지막에 필요한 확인을 한 번 수행한다. 통과한 확인을 관행적으로 반복하지 않는다. 수정이나 실패 때문에 다시 확인해야 할 때에는 바뀐 부분과 아직 해결되지 않은 문제를 대상으로 삼는다. 문서만 작성한 상태를 화면 구현 완료로 표시하지 않는다.

## 절차별 작업

### 요구사항과 개발자 소개 방향 정리

**상태: 완료**

적용 요구사항: 「사이트의 역할과 자료 활용」, 「개발자 소개와 문구 작성」, 「문구 관리와 언어」, 「디자인 체계의 구성과 제작 순서」.

완료한 내용과 근거:

- [채용공고 조사](references/frontend-hiring-and-positioning.md)와 [개발자 사이트 조사](references/developer-websites.md)를 바탕으로 [문구 작성 방향](references/developer-introduction.md)을 정리했다. 조사 시점과 확인하지 못한 내용은 각 조사 문서에 남아 있다.
- 소개 방향, 문구 저장 위치와 홈페이지의 대표 사례 네 개를 결정 문서에 기록했다.
- 첫 소개 문장을 확정했고, 후속 소개와 사례 요약은 초안으로 구분했다. 한국어 제작 후 영어 문구를 구성하는 순서와 UI 제안서의 요구사항 반영 위치도 문서에 기록했다.

완료 조건은 요구사항, 승인된 결정과 제안을 구분해 다음 작업의 입력으로 사용할 수 있는 것이다. 위 문서가 그 근거이며, 전체 문구나 화면이 완성되었다는 뜻은 아니다.

### 한국어 문구와 게재 콘텐츠 구성

**상태: 진행 중**

적용 요구사항: 「사이트의 역할과 자료 활용」, 「개발자 소개와 문구 작성」, 「페이지별 내용」, 「완료를 확인할 결과」.

현재 진행 내용: [개발 기준과 사례 요약](references/developer-introduction.md), [네 사례의 상세 본문](references/featured-case-copy.md)과 [프로젝트 및 글 후보](references/homepage-content.md)의 사실 근거를 정리했다. 소개에서는 사용자의 목적을 화면 구성과 처리 기준으로 구체화하고, 실제 사용 과정에서 그 기준을 확인하는 강점을 설명하는 초안을 작성했다. 첫 소개 문장과 네 사례의 선정은 확정되어 있으며, 강점의 해석과 새 문구 및 게재 후보는 아직 초안이다.

상세 소개는 여러 종류의 정보 사이의 관계를 구성하고, 화면의 안내와 실제 처리 결과가 일치하도록 설계하는 능력을 설명한다. 정보의 종류를 중심으로 표현해 화면 수나 화면 사이의 이동을 전제하지 않는다. 사례 요약은 정보의 구성 기준, 대기 중의 선택, 응답 처리 방식과 지표의 의미를 판단한 근거로 연결했다. 문구는 실제 화면을 구성하면서 계속 다듬을 수 있다.

[홈페이지 한국어 초안](references/homepage-copy.md)은 확정된 첫 소개에 이어 개발자의 역량, 개인 프로젝트, 대표 사례 네 개, 오픈소스 기여, 글과 연락 안내를 구성한다. 사용자가 정보를 직접 대조하거나 처리 결과를 추측해야 하는 부담에 주목하는 소개를 작성하고, 정보 구성과 상태 판단의 경험을 근거로 연결했다. 사용자 이해와 화면 설계를 앞세우는 결정과 확정된 첫 소개는 유지했다.

방문자용 본문과 문구별 근거를 구분했다. 첫 버전에 개인 메모 앱과 Issnuta를 함께 소개하는 것은 확정했고, 글 두 편의 선정과 첫 소개 이외의 문구 및 배치는 초안으로 유지한다. 현재 홈페이지 문구는 전체 초안에서 수정하고, 기존 개별 문구 및 게재 후보 문서는 비교 근거로 사용한다.

대표 사례 네 개는 정보 구성, 사용자의 선택을 고려한 기능 설계, 필요한 정보를 유지하는 성능 개선, 지표의 정확성을 보여주는 소개로 작성했다. 각 항목에서 기대할 수 있는 능력을 먼저 설명하고 실제 경험을 근거로 연결했다. [홈페이지 초안의 편집 근거](references/homepage-copy.md#프로젝트와-사례가-보태는-의미)에 채용 수요와 경험의 연결, 수치의 의미를 기록했다. [사례 상세](references/featured-case-copy.md)는 근거를 더 살펴보려는 독자를 위한 설명으로 구분했다.

개인 프로젝트의 홈페이지 및 상세 소개를 목적과 개발 기준이 이어지도록 작성했다. 개인 메모 앱은 문장의 재사용과 내용 보존을, Issnuta는 인터넷 연결이 없는 사용 조건을 중심으로 설명한다. 메모 앱의 테스트 경험은 입력값과 실제 저장을 구분하는 판단의 근거로 반영했다. 문구와 출처는 [개인 메모 앱 소개](references/personal-notes-project.md#웹사이트에-사용할-문구-초안)와 [프로젝트 후보 자료](references/homepage-content.md)에 있다.

두 프로젝트의 게재와 소개 방식은 [프로젝트 소개 결정](decisions/project-availability.md)에 반영했다. Issnuta는 문제가 생길 수 있는 조건을 살피고 원인과 영향을 바탕으로 개선할 내용을 정하는 관점이 드러나도록 홈페이지와 상세 소개를 작성했다. 메모 앱은 첫 버전에 소개만 제공하며, 소스 URL을 나중에 콘텐츠에 추가할 수 있어야 한다. 이 세 항목은 미결정 질문에서 제외했다.

프로젝트 링크의 표시 조건은 요구사항과 아래 구현 절차에 기록했다. 현재는 문서에 반영한 상태이며 JSON이나 화면을 구현한 것은 아니다. 문구 확정과 글 선정 및 웹 이력서 준비가 남아 있으므로 한국어 콘텐츠 구성은 `진행 중`으로 유지한다.

기존 블로그의 최신 목록과 글 후보를 다시 확인하고, 오래된 글의 방법을 현재도 사용하는 방식으로 단정하지 않는 요구사항을 반영했다. React 상태 초기화 글의 중심 원리는 현재 React 공식 자료와 일치하지만, AI 작업 맥락 글의 세부 구성은 현재 작업 방식과 같다고 볼 근거가 없다. 첫 버전에는 React 글 한 편과 블로그 링크를 제공하는 구성을 추천안으로 바꾸고, [글 선정 질문](references/homepage-content.md#확인이-필요한-질문)에 개별 글 없이 시작하는 안과 두 후보를 작성 당시 경험으로 함께 소개하는 안을 구분했다. 앞으로 작성할 글도 개발자 소개에 보태는 의미와 소개할 기술 설명이 최신 공식 자료와 일치하는지를 확인한 뒤 선별 목록을 갱신한다.

개인 메모 앱의 [테스트 경험 조사](references/personal-notes-testing.md)는 사용자가 작성한 내용을 중요하게 여기는 기준을 뒷받침하는 자료다. 검사 방법은 프로젝트 소개에 자동 채택하지 않는다. 모델 기반 탐색 전체의 완료와 CI 재현은 확인되지 않아 성과로 사용하지 않는다.

회사 사례는 글과 새 기술 도식으로 구성한다. 현재 서비스가 없는 프로젝트도 목적과 제작 내용을 먼저 소개하고, 실제 이용 링크는 서비스 준비 후 추가한다. 이 결정에 맞춰 아래 프로젝트 구현과 사이트 완료 조건을 갱신했다.

남은 작업:

- 홈페이지 전체 초안을 기준으로 게재 문구를 다듬는다. 첫 소개의 역량과 기대할 기여가 본문에서도 이어지는지, 각 경험을 읽을 이유가 드러나는지 확인하고 문구를 확정한다. 확정된 두 프로젝트를 유지하면서 글의 선정과 전체 배치를 정한다.
- 상세 소개와 요약을 읽고 이 개발자에게 어떤 판단을 맡길 수 있는지, 왜 그렇게 기대할 수 있는지 설명할 수 있도록 문구를 확정한다. 작업명이나 기술 이름을 제외해도 강점이 남는지 확인하고, 추상적인 자기평가가 되지 않도록 실제 경험을 연결한다. 원자료와 대조한 사실 및 수치 조건은 편집 근거에 둔다.
- [글 선정 질문](references/homepage-content.md#확인이-필요한-질문)의 답변을 반영해 첫 버전에 연결할 글과 설명 문구를 확정한다. 기존 글에서 소개할 기술 설명을 최신 공식 자료와 대조하고 작성 시점을 확인한 뒤, 지금도 사용하는 방법으로 오해하게 만드는 문구를 제외한다. 두 프로젝트와 선택한 글을 읽을 순서를 정하고, 비슷한 의미가 반복되지 않는지 확인한다.
- 선택한 두 프로젝트의 상세 문구를 다듬는다. Issnuta는 문제의 발생 조건과 영향을 살피는 판단을 설명하고, 개인 메모 앱은 기록을 다시 사용하는 목적과 내용 보존의 기준을 설명한다. 현재 활동을 상태 이름으로만 표시하거나 완료하지 않은 개선을 성과로 표현하지 않는다. 메모 앱의 실제 소스 주소는 나중에 추가할 수 있으므로 첫 버전 콘텐츠 확정의 선행 조건으로 두지 않는다.
- [개인 메모 앱 소개](references/personal-notes-project.md#웹사이트에-사용할-문구-초안)는 서비스의 목적과 개발자의 관심을 먼저 전달하도록 다듬는다. 테스트 자료는 이 의미를 뒷받침하는 데 필요한 경우에 사용한다. 모델 기반 탐색 전체를 별도 성과로 추가하려면 메모 앱 브랜치의 후속 완료 근거를 먼저 확인한다. 이 절차에서 다른 브랜치의 테스트를 수정하거나 재실행하지 않는다.
- 오픈소스 기여의 PR 및 릴리스 링크는 전체 초안에 연결했다. 웹 이력서의 본문과 PDF 연결, 실제 이메일 및 LinkedIn 주소를 준비하고 프로젝트 및 사례별 상세 주소를 정한다. 이름과 GitHub 프로필은 본인 계정에서 확인했다.
- [도식 구성안](references/featured-case-copy.md#기술-도식에-담을-관계)에 따라 각 사례에서 설명할 관계와 읽는 순서를 확정한다. 실제 그림은 화면 설계에서 본문 폭과 모바일 배치에 맞춰 새로 작성하고, 기술 관계와 설명이 일치하는지 확인한다.
- 방문자용 문구와 사실 확인용 메모를 구분하고, 초안과 확정 문구의 표시를 갱신한다. 문구의 길이는 이후 실제 화면에서도 조정할 수 있게 한다.

산출물: 기존 문구 문서의 보완과 실제 게재할 프로젝트, 사례, 글, 링크 및 도식의 구성 자료. 새 내용은 그 주제를 설명하는 이름으로 `references/`에 기록한다.

완료 조건: 한국어 페이지마다 사용할 내용과 연결 대상이 정해져 있다. 소개와 선별한 콘텐츠를 읽고 개발자의 역량과 기대할 기여를 설명할 수 있으며, 그 설명을 이력서, 포트폴리오와 프로젝트의 근거로 확인할 수 있다. 작업명과 수정 내역을 나열한 글은 이 조건을 충족하지 않는다. 사실이나 게재 가능 여부가 해결되지 않은 항목은 완료 근거로 사용하지 않는다.

### 기존 사이트 자료와 구현 환경 파악

**상태: 시작 전**

적용 요구사항: 「웹 이력서」, 「디자인 체계의 구성과 제작 순서」.

시작 조건: 요구사항과 승인된 결정을 읽는다. 한국어 콘텐츠 구성과 독립적으로 진행할 수 있으며, 화면 디자인을 시작하기 전에 마친다.

- 현재 작업 브랜치의 파일과 설정을 확인한다. 현재 추적 파일에는 애플리케이션 소스, 의존성 명세와 잠금 파일, 실행 및 검사 설정이 없다. 새 파일이 생겼다면 그 내용을 반영한다.
- 기존 사이트나 블로그에서 이어서 사용할 이력서, 글, 이미지, 글꼴, 아이콘과 화면 구성이 있는지 확인한다. 확인 가능한 자료만 기록하고, 별도 구현물이 필요하면 위치를 질문한다.
- 요구사항의 기존 구현 조사 항목에 따라 라우팅, 콘텐츠 저장 방식, 스타일, 공통 UI, 테마와 반응형 구성을 조사한다. 존재하지 않는 항목과 접근하지 못해 확인할 수 없는 항목을 구분한다.
- 기존 사이트에서 계속 제공할 기능과 자료, 다시 설계할 부분을 정리한다. 기존 구현을 변경해야 한다면 예상 영향을 먼저 설명한다.

산출물: 기존 자료와 구현 환경에 관한 조사 문서. 완료 조건: 사용할 입력 자료와 보존할 기능을 알고, 새로 정해야 할 기술 및 디자인 항목을 특정할 수 있다.

### 기술 구성과 콘텐츠 저장 방식 결정

**상태: 시작 전**

적용 요구사항: 「문구 관리와 언어」, 「주소와 콘텐츠 구분」, 「공통 화면」, 「완료를 확인할 결과」.

시작 조건: 기존 환경 조사가 끝나고, 한국어 콘텐츠의 종류와 페이지 구성을 알 수 있다.

- 프레임워크와 버전, 렌더링 및 라우팅 방식, 스타일 작성 방식, 개발 환경을 비교해 결정한다. 목록과 긴 상세 글, 한국어 우선 제작, 이후 영어 추가에 미치는 영향을 설명한다.
- 한국어 문구의 JSON 키와 분류, 긴 본문, 이미지와 링크를 저장하는 형식을 정한다. UI 코드와 문구를 분리하고, 한 곳의 `terms` 폴더에서 관리하는 결정을 유지한다. 선별한 글은 제목, 요약, URL, 발행 또는 수정 시점과 홈페이지 표시 여부를 콘텐츠 항목으로 관리해 앞으로 작성할 글을 UI 코드 수정 없이 추가하거나 교체할 수 있게 한다.
- 프로젝트의 상세 주소, 서비스 이용 URL과 소스 URL을 구분한다. 소스 URL은 선택 항목으로 두며, URL이 없으면 링크를 표시하지 않고 나중에 콘텐츠에 URL을 추가하면 표시되도록 정한다. 홈페이지, 목록과 상세에서 같은 프로젝트 주소를 사용한다.
- 선택할 버전의 공식 자료와 적용 가능한 오픈소스 사례를 조사한다. 의존성마다 직접 및 전이 의존성, 대안, 필요한 기능, 잠재적 문제와 통합 방식을 개발 지침에 따라 확인한다.
- 필요한 FSD 계층과 각 모듈의 역할, 의존 방향을 정한다. 실제 페이지와 재사용 목적을 확인한 뒤 폴더를 구성한다.
- 개발, 빌드와 확인에 사용할 명령을 정한다. 이후 각 구현 절차에 추가하거나 수정할 실제 파일, 유지할 기능, 사용할 명령과 예상 결과를 보완한다. 제거할 파일이 필요하면 대상과 이유를 별도로 명시한다.

산출물: 기술 조사, 승인된 기술 결정, 구체적인 파일과 확인 방법을 보완한 이 플랜. 완료 조건: 한국어 사이트 구현을 시작하는 데 필요한 기술적 질문이 해결되어 있다. 영어 버전의 기본 언어와 주소 방식은 영어 추가 절차에서 결정하되, 한국어 문구가 UI 코드에 직접 들어가지 않도록 준비한다.

### 필요한 UI 구성요소와 상태 정리

**상태: 시작 전**

적용 요구사항: 「페이지별 내용」, 「조작과 상태」, 「디자인 체계의 구성과 제작 순서」.

시작 조건: 기존 자료 조사와 한국어 콘텐츠 구성이 끝나 있다.

- 각 페이지에서 실제로 필요한 헤더, 탐색 링크, 소개, 목록 항목, 메타데이터, 본문, 이미지와 설명, 푸터 및 404 구성을 추린다.
- 프로젝트의 현재 활동을 설명하는 본문, 상세 설명 링크, 소스 링크와 서비스가 준비됐을 때 추가할 이용 링크를 구분한다. 소스 URL이 없는 항목에는 링크나 빈 자리를 두지 않는다. 각 구성요소에 필요한 기본, hover, focus, pressed, 현재 위치 상태를 정한다.
- 모바일과 키보드에서도 필요한 정보와 링크에 접근할 수 있게 구성한다. 사용하지 않는 로딩 상태, 비활성 상태, 입력창과 모달을 기본 목록에 추가하지 않는다.

산출물: 페이지별 구성요소와 필요한 상태를 정리한 디자인 자료. 완료 조건: 각 구성요소의 사용 페이지와 역할이 분명하고, 다음 시각 설계에서 표현할 상태를 알 수 있다.

### 한국어 화면과 디자인 기초 확정

**상태: 시작 전**

적용 요구사항: 「시각적 방향」, 「접근성과 반응형 동작」, 「기본 구성에서 제외하는 표현」, 「디자인 체계의 구성과 제작 순서」.

시작 조건: 한국어 콘텐츠와 구성요소 및 상태 목록이 준비되어 있다.

- 실제 한국어 문구를 사용해 홈페이지, 목록, 긴 상세 페이지와 웹 이력서의 정보 순서 및 배치를 설계한다. 넓은 화면과 좁은 화면에서 읽는 순서, 본문 폭, 이미지 폭, 메뉴 배치를 함께 정한다.
- 대표 사례의 기술 도식을 새로 작성하고, 정보 결합, 상태 조회, 응답 변환과 추가 조회의 관계를 각 사례의 본문과 대조한다. 화면 폭이 줄어도 순서와 설명을 읽을 수 있도록 배치한다.
- 기존 개발자 사이트 조사를 참고하되 이력서와 포트폴리오 PDF의 시각 표현은 복사하지 않는다. 추가 비교가 필요한 실제 화면은 Codex 앱 브라우저에서 확인한다.
- 한글을 표시할 수 있는 글꼴과 크기, 강조색, 밝거나 어두운 기본 화면, 레이아웃 폭과 전환 시점, 여백, 테두리, 모서리, 그림자와 모션 값을 비교한다. 선택이 필요한 항목은 실제 한국어 화면으로 차이를 보여준다.
- 대비, 글자 확대, 초점 표시와 조작 영역을 설계에 반영한다. 요구사항에서 제외한 과도한 장식이나 불필요한 화면 효과가 들어가지 않게 한다.

산출물: 한국어 화면 시안과 승인된 시각적 선택. 완료 조건: 주요 페이지의 내용과 조작이 화면에 드러나고, 구현한 화면과 비교할 수 있는 디자인 기준이 있다. 정하지 않은 글꼴이나 색을 임의로 확정한 상태로 다음 절차를 진행하지 않는다.

### 개발 환경과 한국어 JSON 연결

**상태: 시작 전**

적용 요구사항: 「문구 관리와 언어」, 「주소와 콘텐츠 구분」, 「완료를 확인할 결과」.

- 선택한 기술과 버전으로 개발 환경을 구성하고, 필요한 FSD 계층과 콘텐츠 읽기 구성을 만든다.
- 확정된 한국어 문구를 `src/shared/terms/ko.json`에 넣고 화면에서 읽도록 연결한다. 서비스 주소, 이미지 파일과 콘텐츠 간 연결 정보는 결정된 형식으로 저장한다.
- 디자인 토큰과 글꼴, 공통 스타일을 적용하고, 페이지별 제작에 필요한 기본 실행 상태를 마련한다.

산출물: 실행 가능한 한국어 사이트의 기본 구성. 완료 조건: 정해진 실행 및 빌드 명령이 통과하고, JSON 문구를 바꾸면 UI 구현 코드를 수정하지 않아도 화면의 문구가 바뀐다. 영어 문구 작성과 `en.json` 추가는 한국어 사이트 제작 후 진행한다.

### 공통 화면과 페이지 탐색 구현

**상태: 시작 전**

적용 요구사항: 「공통 화면」, 「조작과 상태」, 「접근성과 반응형 동작」.

시작 조건: 개발 환경과 한국어 JSON 연결을 완료했다.

- 이름을 통한 홈 이동, Projects, Cases, Blog, Resume 탐색, 본문 바로가기, 본문 영역과 푸터를 구현한다.
- 링크와 버튼의 목적 및 상태를 구분하고, 모바일 메뉴 배치와 키보드 초점 이동을 구현한다. 페이지 제목, 설명과 언어 정보를 표시한다.
- 잘못된 주소에 대한 404 화면과 홈 또는 목록으로 돌아가는 링크를 제공한다. 프로젝트와 사례의 없는 항목에도 같은 처리를 연결한다.

산출물: 공통 UI와 주소 처리. 완료 조건: 키보드로 본문과 탐색 링크에 접근할 수 있고, 현재 위치와 초점이 보이며, 존재하지 않는 주소에서 돌아갈 수 있다. 전체 페이지의 이동 연결은 한국어 사이트 완성 확인에서 함께 확인한다.

### 프로젝트 목록과 상세 페이지 구현

**상태: 시작 전**

적용 요구사항: 「Project」, 「프로젝트와 사례 목록」, 「상세 페이지」.

시작 조건: 공통 화면이 준비되고, 프로젝트의 목적과 개발 기준 및 현재 활동을 설명할 내용이 정해져 있다. 서비스 이용 주소는 첫 버전의 시작 조건이 아니다.

- `/projects`에 프로젝트의 목적과 제작 내용을 소개하고, 상세 설명이 필요한 프로젝트에 `/projects/[id]`를 제공한다.
- 개인 메모 앱과 Issnuta의 목적과 개발 기준을 설명한다. 현재 활동은 [프로젝트 소개 결정](decisions/project-availability.md)에 맞게 본문으로 설명하고, 실제 서비스가 준비된 항목에만 이용 링크를 추가한다. 개발 기간과 화면 이미지, 프로젝트의 문제 해결 사례는 소개를 뒷받침하는 내용만 연결한다.
- 개인 메모 앱은 처음에 소스 링크 없이 소개하고, Issnuta에는 확인된 소스 주소를 연결한다. 소스 URL이 없으면 링크를 표시하지 않으며, 나중에 콘텐츠에 URL을 추가하면 UI 코드를 고치지 않고 홈페이지와 목록 및 상세에 같은 소스 링크가 표시되도록 구현한다.
- 첫 버전에는 검색, 필터, 정렬과 페이지 나누기를 추가하지 않는다. 목록과 상세에서 디자인 토큰과 재사용 규칙을 적용한다.

산출물: 실제 프로젝트 내용으로 채운 목록과 상세 화면. 완료 조건: 방문자가 프로젝트 소개에서 개발자의 관심과 판단 기준을 읽고 상세 설명을 열 수 있다. 소스 URL이 없는 경우와 콘텐츠에 URL을 추가한 경우의 링크 표시를 확인한다. 서비스가 준비된 항목의 이용 링크는 실제로 작동하며, 없는 프로젝트 주소는 404로 처리된다.

### 사례 목록과 상세 페이지 구현

**상태: 시작 전**

적용 요구사항: 「Case」, 「프로젝트와 사례 목록」, 「상세 페이지」.

시작 조건: 프로젝트 페이지 제작을 마치고, 사례 본문과 사용할 근거 자료가 준비되어 있다.

- `/cases`와 `/cases/[id]`를 구현하고, 선정한 네 사례에서 개선한 점과 개발자의 판단이 드러나도록 내용을 배치한다.
- 긴 글의 제목 구조, 본문 폭, 새로 작성한 기술 도식과 설명, 필요한 코드 및 수치의 조건을 표현한다. 회사 사례는 글과 기술 도식으로 구성한다.
- 사례 목록으로 돌아가는 링크와 없는 사례의 404 처리를 연결한다. 홈페이지에서도 같은 사례 정보를 사용할 수 있도록 구성한다.

산출물: 사례 목록과 상세 화면. 완료 조건: 요약에서 주장한 역량을 본문의 판단과 근거로 확인할 수 있고, 모바일에서도 긴 글과 그림을 읽으며 목록으로 돌아갈 수 있다.

### 웹 이력서 구현

**상태: 시작 전**

적용 요구사항: 「웹 이력서」, 「사이트의 역할과 자료 활용」.

시작 조건: 사례 페이지 제작을 마치고, 현재 이력서 내용과 PDF 연결 대상이 정해져 있다.

- `/resume`에 최신 경력, 기술, 프로젝트, 기여와 연락 정보를 웹에서 읽을 수 있게 구성한다.
- 기존 웹 이력서가 확인되었다면 현재 자료와 차이를 반영하고, PDF를 열거나 내려받을 수 있도록 연결한다.
- PDF의 지면 구성을 복사하지 않고 사이트의 글자, 여백과 본문 규칙을 적용한다.

산출물: 웹 이력서와 PDF 연결. 완료 조건: 최신 이력을 웹에서 읽고 PDF에 접근할 수 있으며, 소개 및 사례 페이지와 사실관계가 일치한다.

### 홈페이지 구성과 콘텐츠 연결

**상태: 시작 전**

적용 요구사항: 「홈페이지」, 「개발자 소개와 문구 작성」, 「기본 구성에서 제외하는 표현」.

시작 조건: 프로젝트, 사례와 웹 이력서의 연결 대상이 준비되어 있다.

- `/`에 이름, Frontend Engineer, 한국어 소개, 선정한 프로젝트와 대표 사례 네 개를 배치한다. 사례 순서는 확정된 구성을 기준으로 정하고, 아직 선택이 필요하면 실제 화면과 함께 제시한다.
- 오픈소스 기여와 PR 및 릴리스 링크, 선정한 블로그 글, 프로필과 연락 링크를 연결한다.
- 첫 화면이 거대한 제목만으로 채워지지 않도록 하고, 작업 목록을 읽기 전에 개발자가 제공할 가치를 파악할 수 있도록 구성한다.
- 별도의 오픈소스 목록 페이지, 글 목록 페이지나 문의 양식을 임의로 추가하지 않는다.

산출물: 한국어 홈페이지. 완료 조건: 소개에서 프로젝트 설명, 사례 근거, 이력서 및 연락 수단으로 이어지는 연결이 실제로 작동한다. 서비스 이용 링크는 준비된 항목에서 확인한다.

### 한국어 웹사이트 완성 확인

**상태: 시작 전**

적용 요구사항: 「완료를 확인할 결과」와 모든 페이지, 문구, 조작 및 접근성 조건.

시작 조건: 한국어 홈페이지와 프로젝트, 사례, 이력서 및 공통 화면 제작을 마쳤다.

- Codex 앱 브라우저에서 소개를 읽고, 프로젝트의 목적과 제작 내용을 열고, 사례의 근거를 확인한 뒤 이력서와 PDF에 접근한다. 개발 상태와 제공하는 링크가 일치하는지 확인하고, 서비스가 준비된 항목은 실제로 열어 사용한다. 내부 및 외부 링크와 404에서 돌아오는 동작도 확인한다.
- 넓은 화면과 좁은 화면, 키보드 이동, 글자 200% 확대, 대비, 조작 영역, 초점 표시, 그림의 대체 설명과 모션 감소 설정을 확인한다. 적용되는 WCAG 2.2 AA 항목을 함께 확인하고, 위 항목만 통과한 것을 전체 준수로 판단하지 않는다.
- 제목과 본문이 잘리거나 페이지 전체에 불필요한 가로 스크롤이 생기는지 살핀다. 긴 코드와 그림은 요구사항에 맞는 별도 표시 영역을 사용한다.
- 한국어 JSON 문구를 수정해 화면에 반영되는지 확인하고, 첫 소개와 사례가 채용 수요 및 실제 경험과 연결되는지 최종 화면에서 확인한다.
- 정해진 빌드와 필요한 정적 검사의 성공 여부, 실제 브라우저에서 확인한 동작을 기록한다. `DESIGN.md`와 화면이 다르면 요구사항과 승인된 디자인을 기준으로 어느 쪽을 고칠지 판단하고 일치시킨다.

산출물: 사용할 수 있는 한국어 웹사이트와 이 절의 확인 결과. 완료 조건: 요구된 한국어 페이지와 탐색 동작에 미해결 문제가 없고, 확인 근거를 남겼다. 이 절이 완료되기 전에는 영어 문구 구성에 착수하지 않는다.

### 영어 문구와 언어별 제공 방식 결정

**상태: 시작 전**

적용 요구사항: 「문구 관리와 언어」, 「아직 정하지 않은 사항」.

시작 조건: 한국어 웹사이트 완성 확인이 완료되었다.

- 완성된 한국어 화면과 문구를 기준으로 소개, 프로젝트, 사례, 이력서와 공통 UI의 영어 문구를 작성한다. 직역하거나 한국어보다 넓은 성과 및 책임을 주장하지 않는다.
- 기본 언어, 언어별 주소, 언어 전환 시 이동 대상, 번역이 빠졌을 때의 처리를 선택지와 함께 결정한다. 기존 한국어 주소를 유지하거나 바꿀 때의 영향도 설명한다.
- `src/shared/terms/en.json`에 영어 문구를 구성하고, 한국어 콘텐츠에 맞는 영어 문구가 빠짐없이 있는지 확인한다. 기존 `terms` 폴더와 FSD 구성을 유지한다.

산출물: 영어 문구와 언어 제공 방식의 결정, 영어 적용 절차에 보완한 실제 수정 파일 및 확인 방법. 완료 조건: 한국어의 사실과 의미를 보존한 영어 문구가 준비되고, 언어 전환 및 누락 처리에 관한 미결정 사항이 없다.

### 영어 버전 적용과 전체 완료 확인

**상태: 시작 전**

적용 요구사항: 「문구 관리와 언어」, 「접근성과 반응형 동작」, 「완료를 확인할 결과」.

시작 조건: 영어 문구와 언어별 제공 방식의 결정이 완료되었다.

- 결정한 방식으로 문구 읽기, 언어별 주소와 전환 동작을 연결한다. 화면의 언어, 제목, 설명과 접근성 문구를 함께 적용한다.
- 영어 문장의 길이에 따라 줄바꿈과 배치를 조정하고, 한국어 화면도 유지되는지 확인한다.
- 같은 프로젝트, 사례와 이력서를 두 언어에서 확인하고, 언어 전환 및 번역 누락 시 화면과 주소가 결정한 방식으로 표시되는지 확인한다. 한국어 JSON을 고치면 한국어 화면에, 영어 JSON을 고치면 영어 화면에 반영되는지도 확인한다.

산출물: 한국어와 영어로 제공되는 웹사이트, 최신 디자인 문서와 완료 근거. 완료 조건: 두 언어에서 소개와 프로젝트 설명, 사례 및 이력서를 읽을 수 있다. 서비스가 준비된 항목에서는 이용 링크가 작동한다. 요구사항을 충족하지 못한 문제가 남아 있지 않고, 각 절차에 확인 근거와 완료 상태를 기록했다.
