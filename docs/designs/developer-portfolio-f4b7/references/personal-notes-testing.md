# 개인 메모 앱의 테스트 개선 경험과 문구 활용

테스트 경험에서 소개할 가치는 **사용자의 목적을 기준으로 무엇을 확인해야 완성됐다고 판단할 수 있는지 정하는 능력**이다. 메모 앱에서는 작성한 문장을 다시 사용할 수 있어야 한다는 목적이 그 기준이다. 입력값과 저장값을 구분한 검사, 실패 후 재시도는 이 판단의 근거로 활용할 수 있다.

이 문서는 [개발자 소개와 문구 작성](../requirements.md#개발자-소개와-문구-작성)에 활용할 테스트 경험을 판단하기 위한 조사다. 2026년 9월 15일 `feature/personal-notes-app`에서 테스트를 추가하거나 수정한 커밋, `94283e3`의 테스트 코드와 실행 기록을 확인했다. 아래에서 실제 앱 수정, 검사 방식의 변경, 아직 보완 중인 탐색을 구분한다. 테스트는 재실행하지 않았다. 검사별 기록은 문구의 사실 확인 자료이며, 이 문서의 절 구성을 웹사이트의 소개 항목으로 옮기지 않는다.

## 입력칸에 보이는 값을 직접 확인하도록 수정

`9754181`은 분석 화면에서 메모 화면으로 돌아온 뒤 원문이 남아 있는지 확인하는 대상을 바꿨다. 이전에는 메모를 감싼 요소의 텍스트에서 원문을 찾았지만, 변경 후에는 `메모 내용` 입력칸의 값을 `toHaveValue`로 비교한다. 수정한 파일은 `apps/notes/e2e/analysis.spec.ts`다.

입력칸의 현재 값과 상위 요소의 텍스트가 다를 수 있다는 점을 반영한 수정이다. 사용자에게 보이는 원문을 확인한다는 검사 목적에 맞게 관찰 대상을 고른 사례로 설명할 수 있다. 저장 완료까지 증명한 것으로 확대하지 않는다.

## 자동 저장과 화면을 떠날 때의 저장을 구분

새로고침 뒤 원문이 남아 있어도 타이머가 저장했는지, 페이지를 떠날 때 저장했는지는 구분할 수 없다. 같은 앱이 두 시점에 모두 저장하기 때문이다. `4e9c5ea`의 보완과 `94283e3`의 `apps/notes/e2e/notes-model.spec.ts`는 이 차이를 검사에 반영한다.

현재 검사는 원문을 입력한 뒤 700ms 시점에는 이전 저장값을 확인하고, 100ms를 더 진행한 뒤 새 원문이 IndexedDB에 저장되는지 기다려 비교한다. 그다음 입력칸에서 포커스를 옮기는 경우와 내부 화면으로 이동하는 경우를 따로 실행하고 저장된 원문을 확인한다. 최종 화면 하나만 확인하던 방식보다 어떤 저장 계기가 작동했는지 구분하는 근거가 된다.

앱에서는 저장 중에 추가로 입력한 내용이 저장되지 않는 문제도 수정했다. `266ec02`는 먼저 시작한 저장이 끝난 뒤 최신 입력을 이어서 저장하도록 변경했다. 같은 커밋의 `apps/notes/src/_pages/notes/model/notes-data-provider.browser.test.tsx`에는 첫 저장을 대기시킨 상태에서 다시 입력하고 두 저장을 차례로 완료하는 검사가 있다. 이 검사는 대기시킬 수 있는 저장 대역을 사용하므로 실제 IndexedDB에 대한 확인과 구분한다.

소개에는 **비동기 저장의 실행 순서와 저장값을 나누어 검사한 판단**을 사용할 수 있다. 실제 앱의 저장 누락 수정과 검사 중 의도적으로 만든 저장 실패를 같은 버그 발견 실적으로 합치지 않는다.

## 생성 실패와 재시도를 실제 화면 조작에 연결

`94283e3`은 메모 생성 검사를 내부의 테스트 전용 명령에서 사용자가 실행하는 버튼 클릭, 원문 입력과 새로고침으로 옮겼다. `apps/notes/e2e/notes.spec.ts`는 각 실행 후보마다 새 브라우저 환경을 만들고 생성 및 새로고침 순서를 조합해 편집기 개수와 원문 목록을 비교한다. 예상 원문은 실제 반환값을 복사하지 않고 입력한 내용으로 관리한다.

실패 후 재시도 검사에서는 첫 IndexedDB 메모 쓰기가 실패하도록 설정하고 `새 메모`를 누른다. 오류 알림, 늘지 않은 메모 개수와 다시 누를 수 있는 버튼을 확인하고, 다시 생성한 메모가 새로고침 뒤에도 남는지 비교한다. 실패 조건을 만든 뒤 사용자가 실제로 이어갈 수 있는 조작을 확인한 사례다.

같은 커밋의 실행 기록에는 앱의 오류 알림과 Next.js의 화면 이동 알림을 함께 찾는 선택자 때문에 실패한 뒤, 메모 작업 영역의 알림으로 대상을 한정한 내용이 있다. 최종 전체 실행에서는 WebKit의 선택 및 포커스 검사 한 개가 실패했고 단독 재실행에서는 통과했다고 기록되어 있다. 이 실행 기록만으로 모든 검사가 안정화됐다고 볼 수는 없다. 출처는 `docs/designs/personal-notes-app-8fd/model-based-testing-execution.md`의 「생성 기능 실행 결과」다.

## 병렬 실행 수와 시간 상한 조정

`e39e77e`는 로컬 운영 서버에서 정해진 탐색 횟수를 실행하도록 Playwright worker 수를 3으로 제한하고, 일부 탐색의 시간 상한을 늘렸다. `apps/notes/playwright.config.ts`, `apps/notes/e2e/notes-model.spec.ts`와 `notes-order-model.spec.ts`에서 확인했다. 시간 상한을 늘린 두 탐색의 `numRuns: 20`과 중단 시 실패로 처리하는 조건은 유지했다.

검사량을 줄여 통과시키기보다 실행 환경에 맞춰 동시 실행 수와 시간을 조정한 기록으로 설명할 수 있다. 다만 이후 실행에도 간헐적인 실패 기록이 있으므로, 실패를 모두 해결했다거나 실행 속도가 개선됐다는 성과로 사용하지 않는다. 홈페이지보다는 기술 설명에서 필요할 때 보충할 내용이다.

## 모델 기반 탐색은 보완 중인 경험으로 구분

현재 실행 문서의 첫 결론은 메모의 12개 기능 모두 새 완료 기준에서 보완이 필요하다는 것이다. 메모 생성은 행동 생성의 새 근거를 확보했지만 오류 탐지, 실패 순서 축소, 로그와 재현은 아직 진행하지 않았다고 기록한다. 아래에 남아 있는 이전 단계의 통과 기록을 현재 전체 완료로 읽으면 안 된다.

따라서 자동으로 생성한 행동 순서, 의도적인 결함 탐지, 실패 축소와 재현을 모두 완성한 것으로 소개하지 않는다. CI 재현도 같은 문서에서 미착수로 남아 있다. 근거는 `94283e3`의 `docs/designs/personal-notes-app-8fd/model-based-testing-execution.md`다.

프로젝트 상세에서는 이미 확인되는 입력값 검사, 저장 시점 구분과 실제 화면의 실패 후 재시도를 우선 사용한다. 탐색 전체의 성과를 별도 사례로 소개하려면 메모 앱 브랜치의 후속 완료 근거를 먼저 확인해야 한다. 이 조사를 이유로 메모 앱의 테스트나 구현을 수정하지 않는다.

## 공식 자료와 비교한 해석

2026년 9월 15일 Codex 앱 브라우저에서 다음 원문을 확인했다. 특정 도구를 사용했다는 사실보다, 무엇을 관찰해야 원하는 오류를 구별할 수 있는지 판단한 경험을 소개하는 근거로 사용한다.

- [Playwright Assertions](https://playwright.dev/docs/test-assertions)는 입력값, 요소 개수와 포커스를 각각 다른 검사로 제공한다. `toHaveValue`의 설명은 “Input has a value”다. 메모 원문과 저장값, 선택 및 포커스를 한 검사로 모두 입증했다고 해석하지 않는 판단에 연결된다.
- [Playwright Clock](https://playwright.dev/docs/clock)은 시간과 타이머를 제어하는 방식을 설명한다. 메모 앱의 시간 진행과 저장값 조회를 비교하면, 시간 진행과 실제 저장을 별도로 확인해야 한다는 해석이 가능하다.
- [fast-check 모델 기반 테스트](https://fast-check.dev/docs/advanced/model-based-testing/)는 모델을 단순하게 유지하고 실제 구현을 그대로 비교하지 말라고 설명한다. 짧은 원문은 “avoid testing the code by comparing it to itself”다. 같은 문서는 명령 순서의 재실행 정보를 별도로 설명하므로, 행동 생성만 확보한 상태와 실패 재현 완료를 구분해야 한다.

## 프로젝트 상세에 사용할 문구 초안

> 메모의 저장 여부는 나중에 다시 열었을 때 작성한 내용이 남아 있는지로 판단합니다. 화면에 입력값이 보이는 것과 저장이 끝난 것을 구분하는 이유입니다. 저장 시점과 실패 후 재시도를 나누어 확인한 것도 사용자가 모아 둔 문장을 다시 사용할 수 있는지 확인하기 위해서입니다.

이 문구는 [개인 메모 앱 소개](personal-notes-project.md#웹사이트에-사용할-문구-초안)의 내용 보존 기준을 뒷받침하는 초안이다. 채용과 협업에서 보여줄 의미는 검사 도구의 사용 경험보다, 사용자에게 필요한 상태를 정의하고 이를 확인할 방법을 고르는 판단에 있다. 저장 설명과 합쳐 편집하며 같은 뜻을 반복하면 줄인다. 테스트 체계 전체의 완성, 모든 브라우저의 안정성, 결함 탐지율이나 운영 장애 감소를 주장하지 않는다.

각 파일은 함께 적은 커밋의 저장소 루트 기준으로 찾을 수 있으며 `git show <커밋>:<파일>`로 확인할 수 있다. 미완료 조건과 검사 해석은 문구 편집용 근거로 남기며 방문자용 자기소개에 그대로 옮기지 않는다.
