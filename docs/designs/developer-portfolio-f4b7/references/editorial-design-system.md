# 편집형 단일 페이지 디자인 조사

`UI Design System Proposal v1`이 제시한 편집형 개발자 소개 방향, 글꼴, 색상, 반응형 구성과 접근성 기준을 2026년 9월 20일 다시 확인했다. 이 문서는 [편집형 단일 페이지 요구사항](../requirements.md)의 시각 규칙과 구현 플랜을 뒷받침하는 조사 자료다. 제안서에서 선택한 디자인 값과 외부 자료가 설명하는 일반 규칙을 구분한다.

## 결론

`Technical Publication / Career Index / Evidence-driven` 방향은 한 페이지에서 개발자의 주장과 근거를 이어 읽게 하려는 요구에 맞는다. 편집형이라는 말은 잡지 모양을 흉내 내는 뜻이 아니라, 회사별 기여, 수치, 기술 정보와 외부 링크의 위계를 글자, 여백, 정렬과 제한된 색으로 드러낸다는 뜻으로 적용한다.

Pretendard 가변 글꼴, 구성 요소별 컨테이너 쿼리, 움직임 감소 설정과 WCAG 2.2 AA 기준은 공식 자료로 확인했다. 제안서의 브랜드 색상 대비도 다시 계산했다. 반면 최대 폭, 반응형 전환값과 구성 요소별 임계값은 표준이 정한 값이 아니다. 실제 한국어 문구와 Pretendard 렌더링으로 확인하고 `DESIGN.md`에서 최종 구현값과 조정 이유를 기록해야 한다.

## 실제 사이트에서 확인한 편집 방식

### Rauno Freiberg의 제작 글

2026년 9월 20일 브라우저에서 [What will you ship?](https://rauno.me/craft/vercel)를 확인했다. 왼쪽에는 문서 목차가, 오른쪽에는 제목, 본문과 시각 자료가 이어졌다. 같은 페이지에서 제목 크기, 본문 폭, 목차, 이미지와 코드가 서로 다른 밀도로 배치되었으며 모든 내용을 동일한 카드에 넣지 않았다.

글은 Vercel 홈페이지의 기준으로 성능, 절제된 시각 표현, 읽기 쉬운 글자, 정보의 정직성, 배치 안정성, 빠른 훑어보기와 접근 가능한 포커스를 설명한다. 강한 색과 움직임을 반복하면 중요도가 약해진다는 제작자의 판단도 확인했다. 이 관찰은 장식보다 정보 위계와 기본 동작의 품질을 앞세우는 근거로 사용한다. 어두운 바탕, 고정 목차, 격자와 그래픽 자체는 이번 사이트에 가져오지 않는다.

### Tania Rascia의 개인 사이트

2026년 9월 20일 브라우저에서 [Tania Rascia의 개인 사이트](https://www.taniarascia.com/)를 확인했다. 왼쪽에는 소개와 주요 링크가 있고 오른쪽에는 연도, 경력 설명과 최근 글이 이어졌다. 연도는 본문보다 낮은 위계로 정렬되고, 분홍색은 링크와 선택적인 강조에 반복해서 사용되었다.

이 사례는 연도와 상태 같은 보조 정보를 본문 옆에 두는 방법과 하나의 강조색으로 링크 관계를 반복하는 방법을 보여준다. 다만 현재 사이트는 여러 주소, 어두운 테마, 그림과 개인적인 연표를 사용한다. 이번 한 페이지의 정보 순서, 밝은 바탕과 회사별 Engineering Contribution은 별도로 정한 요구사항을 따른다.

### 적용 결론

두 사이트는 서로 다른 색, 글꼴과 콘텐츠를 사용하지만 다음 점이 일치한다.

- 한 문서에서 주요 소개와 근거를 이어 읽게 한다.
- 연도, 목차와 기술 정보는 본문을 보조하는 위치에 둔다.
- 모든 항목을 같은 카드로 반복하지 않는다.
- 강조색과 그래픽은 사용할 이유가 있는 곳에만 둔다.

따라서 편집형 화면의 고유성은 잡지 효과나 입체 그래픽이 아니라, 이 개발자의 회사 기여와 외부에서 확인 가능한 작업에 맞춘 정보 밀도와 정렬에서 만들어야 한다.

## 글꼴 확인

[Pretendard 공식 저장소](https://github.com/orioncactus/pretendard)는 9가지 굵기와 가변 글꼴을 제공하며 웹에서 사용할 `Pretendard Variable` 이름과 CDN, 패키지 및 로컬 글꼴 방식을 안내한다. Next.js의 로컬 글꼴 예시에서는 `display: swap`과 가변 굵기 지정도 확인할 수 있다.

이에 따라 Pretendard를 기본 글꼴로 선택하는 것은 구현 가능한 결정이다. 다만 제공 방식은 아직 기술 구성이 없으므로 확정할 수 없다. 외부 CDN은 구현이 간단하지만 외부 연결에 의존하고, 로컬 파일은 배포 파일과 캐시를 직접 관리해야 한다. 프레임워크와 배포 방식을 정할 때 선택한다.

제안서의 400, 500, 600과 700 굵기 제한은 Pretendard가 요구하는 제한이 아니라 이 사이트의 글자 위계를 단순하게 유지하기 위한 디자인 결정이다. 실제 글자 크기와 줄 높이는 한국어 문구가 320px와 390px에서 자연스럽게 줄바꿈되는지 확인한다.

## 색상 대비 확인

WCAG 2.2의 [텍스트 최소 명암비](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)는 일반 텍스트에 4.5:1, 큰 텍스트에 3:1을 요구한다. [비텍스트 명암비](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)는 의미 있는 그래픽, 구성 요소와 직접 만든 상태 표시에 인접 색과 3:1 이상을 요구한다.

WCAG의 상대 휘도 계산식으로 흰색과의 명암비를 다시 계산한 결과는 다음과 같다.

- `#EE5166`: 3.498:1
- `#C62A44`: 5.503:1
- `#B4233C`: 6.469:1
- `#71717A`: 4.833:1

`#EE5166`은 일반 크기 본문에 필요한 4.5:1을 충족하지 않지만 큰 글자와 충분한 두께의 비텍스트 표시에는 사용할 수 있다. 일반 링크와 보조 정보에는 `#C62A44` 또는 더 높은 대비를 갖는 색을 사용한다. 포커스 외곽선은 계산값만 통과하는 얇은 선으로 만들지 않고 실제 배경과 두께를 함께 확인한다.

## 반응형 구성 확인

[MDN의 반응형 디자인 안내](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design)는 유연한 그리드, 상대 단위와 콘텐츠에 맞는 미디어 쿼리를 함께 사용하는 방식을 설명한다. 제안서가 기기 이름 대신 실제 콘텐츠가 다시 배치되어야 하는 폭을 기준으로 삼는 방향과 맞는다.

[MDN의 컨테이너 쿼리 안내](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries)는 미디어 쿼리가 뷰포트에 반응하는 반면 컨테이너 쿼리는 containment context의 크기에 따라 하위 요소의 스타일을 바꾼다고 설명한다. Contribution, Evidence Row와 System Figure처럼 여러 위치에서 쓸 수 있는 구성 요소에 컨테이너 쿼리를 검토하는 근거가 된다.

컨테이너 쿼리를 사용한다는 결정이 모든 구성 요소에 쿼리를 추가해야 한다는 뜻은 아니다. 한 열에서도 의미가 충분하면 기본 배치를 유지한다. 약 42rem, 36rem과 34rem은 실제 문구를 놓기 전의 비교값이며 전역 기준으로 사용하지 않는다.

최대 내용 폭 1200px, 약 48rem과 70rem의 페이지 구성 전환도 이 사이트를 위한 값이다. 구현에서는 다음 장면을 비교한다.

- 320px와 390px에서 보조 정보가 본문 앞에 자연스럽게 이어지는지
- 약 48rem에서 보조 정보와 본문을 분리했을 때 읽는 순서가 분명한지
- 약 70rem 이상에서 12열을 사용해도 본문이 불필요하게 넓어지지 않는지
- 1440px에서 바깥 여백과 최대 폭이 경력 정보를 지나치게 흩어 놓지 않는지

## 움직임과 접근성 확인

[MDN의 `prefers-reduced-motion` 안내](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)는 사용자가 기기에서 움직임 감소를 요청한 경우 `reduce`가 참으로 평가된다고 설명한다. 모든 내용을 애니메이션 뒤에 나타나게 만드는 대신 링크 반응과 필요한 상태 전환만 제공하고, 감소 설정에서는 비필수 변형을 없애는 요구가 타당하다.

WCAG 2.2의 [Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)는 키보드 포커스를 받은 요소가 작성자가 만든 콘텐츠에 완전히 가려지지 않아야 한다고 명시한다. [Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)는 원칙적으로 24×24 CSS px을 요구하며 문장 안의 링크와 충분한 간격 등 예외를 함께 정의한다.

따라서 헤더를 고정한다면 같은 페이지 안의 이동과 키보드 이동에서 제목과 포커스가 가려지지 않는지 확인해야 한다. 짧은 인라인 링크에 무조건 24px 높이를 강제하는 대신 WCAG 예외와 인접 링크 사이의 간격을 함께 판단한다.

## 제안서에서 요구사항으로 채택한 내용

- `Technical Publication / Career Index / Evidence-driven` 편집 방향
- Header, Identity, Experience, Open Source, Independent Work, Background, Contact 순서
- 회사별 Engineering Contribution과 문맥 안의 수치 강조
- Pretendard와 밝은 바탕, `#EE5166`을 시작점으로 한 색상 역할
- 카드 그림자를 사용하지 않는 하나의 페이지 바탕
- 최대 1200px 내용 폭과 유동적인 좌우 여백
- 페이지 구성에는 콘텐츠에 맞춘 미디어 쿼리, 재사용 구성 요소에는 필요한 경우 컨테이너 쿼리 사용
- 제한된 움직임과 WCAG 2.2 AA 목표
- 회사 화면을 추정한 이미지, 장식용 입체 그래픽과 반복 카드 배제

## 구현에서 확인해야 할 내용

- 현재 브랜치에는 애플리케이션 소스, 프레임워크와 스타일 설정이 없다. 실제 토큰 이름과 파일 구성은 기술을 정한 뒤 결정한다.
- Pretendard 제공 방식과 fallback은 배포 및 성능 조건을 확인한 뒤 정한다.
- Header 고정 여부는 전체 길이와 포커스 가림 확인 뒤 정한다.
- 반응형 전환값과 컨테이너 쿼리 임계값은 실제 한국어 줄바꿈을 보고 조정할 수 있다.
- `30초 이내 배포`는 현재 편집 자료만으로 비교 조건을 확정하지 못했다. 근거를 확인하기 전에는 홈페이지 수치로 사용하지 않는다.
- 제안서가 정하지 않은 어두운 테마, 보조 고정폭 글꼴, 삽화 체계와 복잡한 애니메이션은 첫 버전에 추가하지 않는다.
