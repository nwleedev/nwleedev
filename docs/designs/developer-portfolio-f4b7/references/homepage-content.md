# 개발자 소개를 뒷받침할 프로젝트와 글

프로젝트와 글은 **사용자의 목적을 이해하고, 실제로 사용할 수 있는 서비스로 구체화하는 개발자**라는 소개를 뒷받침할 때 선별한다. 방문자가 개발자의 관심과 함께 개발할 때 기대할 가치를 이해하는 것이 목적이다. 기술 분야별로 경험을 하나씩 채우거나 구현 방법을 많이 설명하는 것을 선정 기준으로 삼지 않는다.

첫 버전에는 개인 메모 앱과 Issnuta를 함께 소개한다. 아래 두 글은 게재 여부를 검토할 후보이며, 작성 당시의 방법을 현재도 사용하는 방법으로 전제하지 않는다. 프로젝트와 글을 자기소개에 연결한 구성은 [홈페이지 한국어 초안](homepage-copy.md)에서 읽을 수 있다. 현재 홈페이지 문구는 전체 초안에서 수정하며, 세부 표현과 배치 및 글의 선정은 이어서 정한다.

현재 방문자가 사용할 수 있는 서비스는 없으며, [제작 내용을 먼저 소개하는 결정](../decisions/project-availability.md)에 따라 서비스 준비 후 이용 링크를 추가한다.

이 문서는 [홈페이지 구성](../requirements.md#홈페이지)을 정하기 위한 자료다. 2026년 9월 15일 개인 메모 앱의 Git 기록과 구현, GitHub CLI로 [Issnuta 저장소](https://github.com/nwleedev/issnuta)의 설명과 README를 확인했다. 2026년 9월 19일 Codex 앱 브라우저에서 [기존 블로그](https://blog.nwlee.com/)의 글 목록을 다시 확인하고, 아래 두 글과 비교 후보의 본문을 읽었다. 같은 날 React와 OpenAI의 공식 자료를 대조해 후보 글의 어느 설명이 현재 자료와 일치하는지 확인했다. 전체 프로젝트와 글의 품질을 평가하지 않았으며, 현재 소개 방향을 뒷받침할 항목을 고르기 위해 비교했다.

## 개인 메모 앱

개인 메모 앱에서는 **사람들이 기록한 정보를 어떻게 다시 사용하는지에 관심을 두는 개발자**라는 면을 설명할 수 있다. 여러 메모의 문장을 골라 다시 사용하려는 목적은 이 관심을 구체적으로 보여준다. 화면 배치와 저장 처리의 변경 내역은 [개발 목적과 Git 근거](personal-notes-project.md)에서 확인할 자료다. 이 해석은 [사용자 이해와 화면 설계를 앞세우는 소개](developer-introduction.md)를 뒷받침하는 후보이며, 실제 사용자 조사를 수행했다는 뜻은 아니다.

홈페이지의 현재 설명은 [개인 메모 앱 소개](homepage-copy.md#개인-메모-앱)에서 관리한다. [목적과 개발 기준의 긴 설명](personal-notes-project.md#웹사이트에-사용할-문구-초안)은 문구 편집에 참고하며 별도 프로젝트 상세 페이지에 싣지 않는다. 문장을 다시 사용하려는 목적을 정보 구성과 내용 보존의 기준으로 구체화할 수 있다는 의미를 전달한다.

프로젝트 설명에서는 어떤 필요에 관심을 두고 어떤 서비스를 만들고 있는지 먼저 전달한다. [테스트 경험](personal-notes-testing.md)은 입력값과 실제 저장을 구분해야 한다는 개발 기준의 근거로 활용한다. 검사 도구나 실행 순서는 소개 본문에 넣지 않는다. 현재 제공하지 않는 계정 동기화나 의미 유사성 자동 판별은 소개에 넣지 않는다. 첫 버전에는 소개만 제공하고, 소스 URL은 [추후 추가하는 결정](../decisions/project-availability.md#소스-주소-추가와-링크-표시)을 따른다.

## Issnuta

Issnuta에서는 **사용자가 서비스를 필요로 하는 상황과 실제로 사용할 수 있는 조건을 함께 고려하는 개발자**라는 면을 설명할 수 있다. 인터넷 연결이 없는 상황에서도 번역하려는 목적이 그 근거다. 브라우저에서 모델을 실행했다는 사실은 이 목적을 뒷받침하는 기술 설명이며, 프로젝트를 소개하는 주된 이유는 사용자의 필요에 대한 관심이다.

2026년 9월 15일 확인한 [한국어 README](https://github.com/nwleedev/issnuta/blob/f9b75720ee22fb142d821438227ac4dac8e1e95b/README.ko.md)는 프로젝트를 “모바일 우선 오프라인 번역 PWA”로 소개한다. 먼저 선택한 언어의 모델을 내려받아 저장한 뒤, 인터넷 연결 없이 번역할 수 있다고 설명한다. 한국어와 영어, 한국어와 일본어 사이의 번역을 제공한다.

홈페이지의 현재 설명은 [Issnuta 소개](homepage-copy.md#issnuta)에서 관리한다.

문구 편집에 참고할 긴 설명이며 별도 상세 페이지의 게재 본문은 아니다:

> 인터넷 연결이 없는 환경에서도 필요한 문장을 번역할 수 있도록 만든 웹 애플리케이션입니다. 사용할 언어의 모델을 미리 저장하면 한국어와 영어, 한국어와 일본어 사이를 번역할 수 있습니다.
>
> 번역이 필요한 순간에 인터넷에 연결할 수 있는지도 설계의 기준으로 삼았습니다. 모델을 준비하는 과정과 오프라인에서 번역하는 과정을 구분해, 사용 조건에 맞는 서비스 제공 방식을 구체화했습니다.
>
> 현재는 프로젝트를 점검하며 문제가 생길 수 있는 조건을 살피고 있습니다. 발견한 문제는 원인과 영향을 확인하고, 개선할 내용과 우선순위를 정리합니다.

프로젝트 설명은 사용 환경의 제약에 맞춰 서비스 제공 방식을 정할 수 있다는 의미를 전달한다. 오프라인 번역이라는 목적과 모델의 사전 저장을 연결한 설명은 위 README의 동작 방식을 해석한 것이다. 현재 활동은 [프로젝트 소개 결정](../decisions/project-availability.md#첫-버전에-소개할-프로젝트)에 따라 문제를 살피고 개선할 내용을 구체화하는 판단으로 설명한다. 여행 경험, 실제 사용자의 요청이나 번역 정확도에 대한 성과는 추가하지 않는다.

소스 코드는 외부에서 열람할 수 있다. 2026년 9월 15일 GitHub CLI로 저장소 정보와 위 README를 다시 확인했다. 저장소의 홈페이지 주소 항목은 비어 있고 README에는 로컬 실행 방법이 있어, 이 자료만으로 배포된 서비스의 접속 주소나 현재 동작을 확인할 수는 없다. 현재 활동의 소개와 소스 연결은 위 결정을 따른다. 서비스 링크를 추정하거나 소스 코드 링크를 서비스 이용 링크로 대신하지 않는다.

AI 작업 문서 도구와 일기 관리 및 분석 서비스도 [이력서에서 확인한 후보](content-and-site-direction.md#첫-소개와-프로젝트)다. 개인 메모 앱과 일기 관리 팀 프로젝트는 서로 다른 프로젝트로 구분한다.

## 프로젝트 게재와 현재 활동

두 프로젝트의 게재, Issnuta의 현재 활동을 설명하는 방식과 메모 앱의 소스 링크 추가 조건은 [프로젝트 소개 결정](../decisions/project-availability.md)에 기록했다. 이 세 항목은 미결정 질문에서 제외한다. 홈페이지 문구는 그 결정을 바탕으로 계속 다듬는다.

개인 메모 앱을 먼저 설명하고 Issnuta로 이어지는 순서는 제안이다. 기록의 재사용과 사용 환경이라는 서로 다른 관심을 통해 서비스 설계에서 기대할 기여를 설명한다. 글의 선정과 세부 배치는 별도로 정한다.

## Key를 활용하여 컴포넌트 상태를 초기화하기

이 글에서는 **익숙한 방식도 목적에 맞는지 원리를 살펴 다시 판단하는 개발 태도**를 읽을 수 있다. 특정 API를 안다는 사실보다, 이전에 사용하던 방법을 돌아보고 대안을 비교한 이유가 소개에 보탤 의미다. 글 전체를 현재의 구현 지침으로 취급하지 않는다.

2025년 9월 21일 발행한 [글 원문](https://blog.nwlee.com/use-react-keys-to-reset-components)은 URL 검색 조건이 바뀌어도 자식 컴포넌트의 상태가 유지되는 상황을 설명한다. “동일한 위치에 있는 컴포넌트는 상태가 보존된다”는 원리에서 출발해, Effect에서 상태를 변경하는 방법과 `key`로 상태를 초기화하는 방법을 비교한다. 본문은 2026년 9월 19일 다시 확인했다.

홈페이지 설명 초안:

> 검색 조건이 바뀌어도 이전 상태가 남는 이유를 React의 상태 보존 방식으로 살펴보고, 당시 선택할 수 있던 초기화 방법을 비교했습니다.

이 글을 소개하면 대표 사례의 SharedWorker나 SSE 경험 외에도 프레임워크의 기본 원리를 이해하고 적용하는 관심을 보여줄 수 있다. 실제 제목과 링크를 사용하며, 사례에 없는 성능 수치나 라이브러리 전문성을 추가하지 않는다.

## AI 에이전트에서 작업 맥락을 관리하기 위해 사용한 방법

이 글에서는 **개발 과정에서 반복되는 불편을 발견하고 자신에게 필요한 방법을 찾아 개선하는 태도**를 읽을 수 있다. 목표와 결정 사항을 잃는 문제를 겪으며 기록 방식을 바꾼 경험이 그 근거다. AI 도구를 사용했다는 사실만으로 전문성을 주장하지 않으며, 글에 적힌 관리 방법을 현재도 그대로 사용한다고 설명하지 않는다.

2026년 3월 8일 수정한 [글 원문](https://blog.nwlee.com/codex-work-context-maintainance)은 긴 작업에서 목표와 결정 사항을 놓치는 문제를 설명한다. “이미 결정된 방식에 대해서 고민하거나 번복한다”는 문제를 제시하고, 데이터베이스와 파일을 사용한 방법을 비교한다. 계획, 결정, 진행 상황과 조사 기록을 나누어 작업별로 관리한 경험이 담겨 있다. 본문은 2026년 9월 19일 다시 확인했다.

홈페이지 설명 초안:

> 장시간 AI 개발에서 목표와 결정 사항을 놓치는 문제를 겪으며, 작성 당시 비교한 기록 방식과 개선 과정을 정리했습니다.

도구를 사용한다는 사실에 더해 반복되는 문제를 발견하고 기록 방식을 개선한 판단을 보여주는 후보다. 본문에 실린 당시의 스크립트와 파일 구성은 현재의 작업 방식으로 채택하거나 권장한다는 뜻이 아니다.

## 게재 결정과 문구 관리

개수와 순서보다 먼저, 자기소개와 후보를 함께 읽었을 때 개발자의 관심과 협업에서 기대할 가치가 이어지는지 확인한다. 프로젝트 설명은 어떤 서비스를 만드는지 알려주고, 글의 요약은 무엇을 읽을 수 있는지 알려주는 역할이다. 이 설명들을 모은 것만으로 개발자 소개가 완성되지는 않는다.

같은 관심을 반복해서 보여주는 항목은 줄일 수 있고, 개발자에 대한 이해를 넓혀 주는 항목은 함께 소개할 수 있다. 기술 종류를 더 많이 보여준다는 이유로 개수를 늘리지 않는다. 전체 소개 문구를 기준으로 추천 목록을 만든 뒤, 게재 의향이나 제공 가능 여부가 모호한 항목을 확인한다.

글의 제목과 Issnuta는 원문 및 저장소를 식별하는 이름으로 유지하고, 홈페이지 설명은 수정 가능한 한국어 초안으로 관리한다. 선별한 글의 제목, 요약, URL과 발행 또는 수정 시점은 콘텐츠에서 갱신할 수 있어야 한다. 프로젝트의 게재 방식과 목록은 결정 문서를 따르고, 글의 선정 및 배치는 한국어 콘텐츠 구성에서 정한 뒤 플랜에 반영한다.

서비스 준비 전에도 프로젝트의 목적과 현재 활동을 설명한다. 이용 링크가 없다는 이유로 프로젝트 영역을 생략하거나 실제 접속할 수 없는 주소를 넣지 않는다. 서비스 준비 후 이용 링크를 추가하는 절차는 [프로젝트 제공 결정](../decisions/project-availability.md#제작과-완료-확인에-미치는-영향)을 따른다.

## 블로그 글 후보 비교

첫 버전에는 현재 자료와 대조할 수 있는 React 상태 초기화 글 한 편을 소개하고 블로그로 연결하는 구성을 추천한다. 프론트엔드의 기본 원리를 구현 선택에 적용하는 판단을 보여주면서, 아직 확정하지 않은 현재 작업 방식을 과거 글로 대신 설명할 위험을 줄일 수 있다. 앞으로 새 글을 작성하면 최신성만으로 추가하지 않고, 이 사이트의 개발자 소개를 뒷받침하는지와 소개할 기술 설명이 최신 공식 자료와 일치하는지를 함께 확인한다.

[React 공식 문서](https://react.dev/learn/preserving-and-resetting-state)는 같은 위치의 컴포넌트 상태가 유지되며 `key`로 컴포넌트에 명시적인 식별값을 주면 상태를 초기화할 수 있다고 설명한다. React 글의 중심 설명은 이 원리와 일치한다. 이 확인은 글의 모든 코드와 판단이 현재 프로젝트에도 적합하다는 보증이 아니다. 홈페이지에서는 API 사용법보다 기존 방법을 React의 상태 보존 원리에 비추어 다시 판단한 점을 소개한다.

AI 작업 맥락 글은 ChromaDB, `PLANS.md`와 파일별 기록 방식을 직접 사용하고 비교한 뒤, 계획과 결정 및 진행 상황을 구분해 보관하는 방식으로 바꾼 경험을 담고 있다. [OpenAI의 실행 계획 문서](https://developers.openai.com/cookbook/articles/codex_exec_plans)는 긴 작업에서 계획 문서를 현재 상태와 다음 행동을 남기는 자료로 계속 갱신하는 방식을 설명한다. 두 자료는 장시간 작업에서 기록을 유지해야 한다는 문제 인식이 이어진다는 점을 보여주지만, 블로그의 세부 파일 구성과 현재 작업 방식이 같다는 근거는 아니다. 이 글을 연결하려면 당시의 비교와 개선 과정을 보여주는 글로 소개해야 한다.

다른 글은 다음 이유로 첫 추천 구성에서 제외한다.

- [지시사항을 분할하여 Codex로 효율적인 작업하기](https://blog.nwlee.com/codex-effective-prompts)와 [내가 AGENTS.md를 작성하는 방법](https://blog.nwlee.com/agents-md-guides-to-codex-cli)은 AI 작업 맥락 글과 관심이 겹친다. 두 글보다 작업 맥락 글이 여러 방법의 한계와 선택 과정을 더 구체적으로 보여준다.
- [React 웹 페이지에서 Quill 에디터 텍스트 수정 페이지 작업하기](https://blog.nwlee.com/react-app-quill-text-edit-issues)와 [NextJS에서 캘린더 컴포넌트 개발하기](https://blog.nwlee.com/nextjs-with-use-calendar)는 프론트엔드 구현 사례를 보탤 수 있다. 다만 현재 본문은 사용 목적이나 판단보다 라이브러리 적용 절차와 코드 예시의 비중이 높아, 이 사이트가 전달하려는 개발자의 가치와 직접 연결하기 어렵다.
- [타입스크립트 라이브러리 프로젝트 진행하면서 겪은 시행착오](https://blog.nwlee.com/library-project-setup-with-pnpm-workspace-tsup)는 라이브러리 구성 경험을 보여주지만, 사용자 이해와 화면 설계를 강조하는 첫 소개 및 대표 사례에 이어 놓기 어렵다.

이 비교에서는 글의 품질에 순위를 매기지 않았다. 첫 화면에서 개발자의 가치와 근거를 짧게 연결할 수 있는지, 소개할 기술 설명이 최신 공식 자료와 일치하는지, 작성 당시의 방법과 현재의 방법을 혼동하게 만들지 않는지를 기준으로 삼았다. 블로그에는 앞으로도 글을 작성하며, 새 글도 같은 기준으로 검토해 선별 목록에 추가하거나 기존 후보와 바꾼다.

## 확인이 필요한 질문

### 첫 버전 홈페이지에는 어떤 글을 연결할까?

- **React 상태 초기화 글 한 편과 블로그 링크를 제공한다.** React의 상태 보존과 `key` 동작에 대한 설명을 현재 공식 자료와 대조할 수 있고 프론트엔드 개발자의 판단을 먼저 보여줄 수 있어 추천한다. 앞으로 새 글을 작성하면 같은 기준으로 선별해 추가한다.
- **개별 글을 고르지 않고 블로그 링크만 제공한다.** 현재 글의 방법과 지금의 개발 방식을 혼동할 여지를 줄이고, 앞으로 작성할 글 가운데 소개 목적에 맞는 글이 생기면 선별 목록을 시작한다.
- **React 상태 초기화 글과 AI 작업 맥락 글을 함께 연결한다.** 서로 다른 판단을 보여줄 수 있다. AI 글은 현재의 권장 방법이 아니라 작성 당시 문제를 발견하고 방법을 조정한 경험으로 설명하며, 발행 또는 수정 시점을 함께 표시한다.

답변이 정해질 때까지 홈페이지 초안의 두 글은 게재 후보로 유지하며 확정된 목록으로 취급하지 않는다. 선택한 글의 제목과 링크는 원문을 그대로 사용하고, 설명 문구는 이 사이트의 소개 목적과 글의 작성 시점을 드러내도록 다듬는다.
