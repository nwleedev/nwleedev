# 대표 경험 요약을 위한 상세 근거

네 사례는 정보를 구성하는 판단, 대기 중 선택의 설계, 브라우저 처리에 대한 이해, 지표를 신뢰할 수 있게 만드는 개선을 각각 보여준다. 아래의 긴 설명과 도식 후보는 [선정한 네 경험](../decisions/featured-cases.md)의 사실 확인과 문구 편집에 사용한다. 단일 페이지에 게재할 상세 본문이나 별도 사례 페이지의 구현 입력이 아니다.

홈페이지에서 전달할 역량과 요약은 [홈페이지 Experience 문구](homepage-copy.md#experience)에서 관리한다. 자세한 해결 과정은 블로그가 맡지만 아래 글이 블로그 발행까지 확정된 것은 아니다. 회사 경험의 설명 방식은 [Engineering Contribution 결정](../decisions/featured-cases.md)을 따른다.

## 작업별 이력 구성

### 작업의 시작과 이후 기록을 함께 읽을 수 있도록

작업의 시작과 이후 진행 기록을 하나의 이력으로 확인할 수 있도록 화면을 구성했습니다. 화면과 내려받은 CSV에도 같은 상태 판정 기준을 적용했습니다.

도커 이미지 기반 워크플로우 실행 서비스에서 사용자는 한 작업이 어떻게 진행됐는지 확인해야 했습니다. 서버는 선행 작업과 후속 기록을 별도로 관리했지만, 화면에서는 이 기록들의 관계를 보여줄 필요가 있었습니다.

### 사용자가 확인할 단위에 맞춘 목록과 페이지 구성

PM과 API의 제약을 공유하고, 선행 작업을 기준으로 페이지를 나누기로 했습니다. 각 선행 작업 아래에는 그 작업의 후속 기록을 배치했습니다. 기록의 종류에 따라 나뉜 서버 정보를 사용자가 확인할 작업 단위로 다시 구성한 것입니다.

목록의 배치와 함께 상태를 구분하는 기준도 정했습니다. 기록을 불러오지 못한 경우를 기록이 없는 상태로 표시하지 않았고, 아직 진행 중인 작업과 후속 기록이 없는 작업을 구별했습니다. 사용자가 빈 목록을 보더라도 조회 실패인지, 아직 기록이 없는 것인지 알 수 있도록 했습니다.

화면과 CSV가 같은 작업을 서로 다르게 설명하지 않도록 판정 규칙을 함께 적용해 배포했습니다. 정보의 배치뿐 아니라 그 정보가 의미하는 상태까지 일치시키는 데 초점을 두었습니다.

## 장시간 문서 생성

### 기다리는 동안에도 진행 상태와 선택을 확인할 수 있도록

5~10분이 걸리는 문서 생성에서 현재 상태와 경과 시간을 확인하고, 필요하면 취소할 수 있도록 설계했습니다. 취소하지 않기로 선택한 뒤에도 진행 상태를 계속 확인할 수 있게 했습니다.

AI 연구지원 서비스에서 사용자가 문서를 업로드하면 초안을 생성하는 기능을 맡았습니다. 요구사항과 회의 내용을 설계 문서로 구체화하고, 기술 방식 결정과 구현, 배포를 진행했습니다. PM이 전달한 검토 의견을 바탕으로 대기 중 안내와 페이지 이동, 취소 후 화면을 정리했습니다.

### 선택을 바꿔도 진행 안내가 끊기지 않도록

문서를 기다리는 동안에는 현재 상태와 경과 시간을 표시하고, 페이지를 떠나려 할 때는 이동 의사를 확인했습니다. 취소를 진행하지 않기로 선택하면 문서 생성과 상태 확인을 유지했습니다. 취소가 성공했을 때처럼 처리 내용을 분명하게 확인할 수 있는 경우에만 상태 추적을 마치도록 했습니다.

취소 여부를 확인했다는 이유만으로 상태 추적을 끝내면, 문서가 계속 생성되고 있어도 사용자는 진행 상황을 알 수 없습니다. 사용자의 선택과 서버의 처리 상태를 함께 고려해 안내를 유지할 시점을 정했습니다.

### 서버가 확인한 상태를 화면에 반영

문서 생성의 단계 시작과 완료는 SSE 이벤트로 전달받았습니다. 이벤트를 받으면 서버 상태를 다시 조회하고, 그 응답을 기준으로 화면을 갱신했습니다.

상태를 조회하는 중에 새 이벤트가 도착하면 진행 중인 요청을 마친 뒤 한 번 더 조회했습니다. SSE 연결 오류가 생겨도 서버 상태를 다시 확인했습니다. 이벤트 수신 여부만으로 문서 생성이 성공하거나 실패했다고 판단하지 않도록 구성했습니다.

백엔드에 직접 접속하기 어려운 배포 환경에서는 두 서버의 Nginx를 거쳐 요청을 전달했습니다. 두 단계의 응답 버퍼링을 해제해 SSE 이벤트를 전달했고, 배포 후 문서 생성, 취소와 화면의 진행 표시가 실제 처리 상태와 일치하는지 확인했습니다.

## 화면 정지 해결

### 응답 형식을 유지하면서 3~4초 화면 정지를 해결

약 5 MB의 API 응답을 처리할 때 발생하던 3~4초 화면 정지를 해결했습니다. 응답 크기와 형식을 유지하면서 처리 위치를 바꿨고, 배포 후 정지가 해소된 것을 확인했습니다.

도커 이미지 기반 워크플로우 실행 서비스에서 응답 처리와 실시간 차트, 공통 UI를 담당했습니다. 대용량 응답을 호출하고 화면에 필요한 형태로 변환하는 과정에서 화면이 멈추는 문제가 있었습니다.

### 응답 변환과 화면 갱신을 분리

API 호출과 응답 변환은 SharedWorker에서 수행하고, 메인 스레드는 변환된 정보로 화면을 갱신하도록 구성했습니다. 응답을 줄이거나 형식을 바꾸는 대신, 화면을 갱신하는 메인 스레드에서 응답 변환을 분리했습니다.

이 구조를 실행 이력과 상세 화면 등 같은 API 처리가 필요한 페이지에 적용했습니다. 한 화면의 증상을 고치는 데서 끝내지 않고, 같은 처리로 발생하는 정지를 여러 화면에서 해결할 수 있도록 공통으로 사용할 호출 방식을 마련했습니다.

변경 후에도 응답의 크기와 형식은 유지했습니다. 배포된 화면에서 정지 문제가 해결된 것을 직접 확인했습니다.

## 대시보드 개선

### 지표의 의미를 바로잡고 필요한 값만 추가로 조회

자원 모니터링 대시보드에서 잘못 표시되거나 누락된 지표를 교정했습니다. 전체 구간을 반복해서 조회하던 방식을 바꿔, 10분 동안의 데이터 전송량을 96.5 MB에서 41 KB로 줄였습니다.

이 대시보드는 PC 자원의 현재 상태와 시간에 따른 변화를 보여줍니다. 운영 중 발견한 표시 오류의 원인을 분석하고, 조회와 변환 수정부터 확인 및 배포까지 담당했습니다.

### 같은 화면의 오류도 원인에 따라 구분

빈 값과 잘못된 사용 비율, 시계열 누락을 각각 나누어 살폈습니다. 지표의 정의와 실제 응답을 대조해 조회 조건, 계산과 변환 방식을 수정했습니다.

- 빈 값은 지표 이름과 라벨이 실제 응답과 맞지 않아 발생했습니다. 실제 응답에 맞춰 조회와 변환을 수정했습니다.
- 사용 비율은 활동 비율을 용량 비율로 해석하고 있었습니다. 표시할 지표의 의미에 맞춰 사용량을 전체 용량으로 나눈 백분율로 계산했습니다.
- 시계열 누락은 같은 라벨의 서로 다른 시계열이 합쳐지는 문제였습니다. 종류별 라벨로 구분해 시계열을 보존했습니다.

### 반복 조회를 줄이고 표시 내용을 대조

새 값을 가져올 때마다 전체 시간 구간을 요청하는 대신, 마지막 요청 시각 이후의 값만 추가로 조회하도록 설계했습니다. 이 변경으로 10분 동안 조회한 데이터의 전송량이 96.5 MB에서 41 KB로 줄어든 것을 확인했습니다.

기존 대시보드와 실제 응답을 대조해 지표가 정상적으로 표시되는지 확인했습니다. 표시 오류와 반복 전송을 각각 개선해, 화면에서 확인하는 값과 그 값을 가져오는 방식을 함께 정비했습니다.

## 기술 도식에 담을 관계

다음은 설명 그림의 후보이며 첫 버전에서 모두 제작하지 않는다. 홈페이지 요약에 꼭 필요한 관계만 선별할 수 있고, 상세한 도식은 향후 블로그 글을 준비할 때 참고한다. 이 목록 자체를 방문자용 본문으로 사용하지 않는다.

- 작업별 이력: 별도로 받은 선행 작업과 후속 기록을 작업 단위로 묶고, 같은 판정 기준을 화면과 CSV에 적용하는 관계를 보여준다.
- 문서 생성: SSE 이벤트 수신, 서버 상태 조회와 응답에 따른 화면 갱신을 순서대로 표시한다. 조회 중 새 이벤트가 도착하면 현재 요청 뒤 추가 조회하고, 연결 오류에서도 서버 상태를 다시 확인하는 경우를 구분한다. 취소 확인 중에도 진행 안내를 유지하는 조건은 본문과 연결한다.
- 화면 정지: SharedWorker의 API 호출 및 응답 변환과 메인 스레드의 화면 갱신을 구분한다. 약 5 MB의 응답 크기와 형식을 유지한 조건을 함께 표시한다.
- 대시보드: 전체 구간을 반복 조회한 방식과 마지막 요청 시각 이후만 추가 조회하는 방식을 비교한다. 전송량에는 10분이라는 조건을 붙이고, 지표 표시 오류를 교정한 내용과 구분한다.

## 편집 근거와 게재 전 확인

이 절은 문구 편집용 자료이며 웹사이트 본문에 포함하지 않는다. 2026년 9월 15일 제공된 포트폴리오 PDF의 5, 7, 11, 12, 13쪽을 이미지로 읽고 [기존 경험 분석](content-and-site-direction.md#자료에서-확인한-경험과-근거의-한계)과 대조했다. 본문의 회사 경험은 이 자료에 기록된 사실을 바탕으로 썼다.

### 채용 수요와 소개 방식의 반영

[카카오페이 공고](https://kakaopay.career.greetinghr.com/ko/o/233787)는 정보를 전달하는 UI 구성과 예외 상황의 예상, 직군 간 협업을 요구한다. 작업별 이력과 문서 생성 사례에서 정보의 단위와 상태 안내를 정한 이유를 앞세운 근거다. 짧은 원문은 “목표를 달성하기 위한 노력 또는 고민한 부분”이다.

[당근 공고](https://careers.daangn.com/jobs/role/7689088003/)는 사용자 문제를 판단한 경험, 직접 기여한 부분과 기술을 선택한 이유를 설명하도록 안내한다. 화면 정지에서는 처리 위치를 바꾼 판단을, 대시보드에서는 서로 다른 오류 원인과 조회 방식의 변경을 설명한다. 공고의 “특정 기술/아키텍처를 비판적으로 검토 후 적절히 도입한 사례”라는 안내를 참고했다.

[Brittany Chiang의 사이트](https://brittanychiang.com/)는 중요하게 여기는 UI 품질을 첫 소개에 밝히고 경험으로 뒷받침한다. 이 구성에 따라 [첫 소개](developer-introduction.md#홈페이지-첫-소개)에서 내세운 정보 구성과 기술적 문제 해결 능력을 각 사례의 판단과 연결했다. 카카오페이, 당근과 Brittany의 본문은 2026년 9월 15일 Codex 앱 브라우저에서 다시 확인했다.

### 사실과 해석의 구분

- 작업별 이력: 포트폴리오 7쪽의 목록 구성, PM과의 협의, 상태 구분과 CSV 판정 규칙을 사용했다. 사용자의 정보 확인 단위를 먼저 정했다는 의미로 설명하며 탐색 시간이나 만족도 수치를 추가하지 않았다.
- 문서 생성: 11~12쪽의 대기, 이동 확인, 취소와 서버 상태 재조회를 사용했다. 경과 시간은 남은 예상 시간이 아니다. 상태 API 조회 횟수 비교는 본문에 넣지 않았으며 생성 속도가 개선됐다고 표현하지 않았다.
- 화면 정지: 5쪽의 약 5 MB, 3~4초 정지, SharedWorker 적용과 배포 확인을 사용했다. 응답 시간, FPS나 INP 개선 수치로 바꾸지 않았다.
- 대시보드: 13쪽의 표시 오류별 원인, 추가 조회 방식과 실제 응답 대조를 사용했다. 전송량 수치에는 10분이라는 비교 구간을 함께 표시했다.

도식을 사용한다면 확인된 기술 관계를 설명하기 위해 재구성한 자료로 표시한다. 긴 본문과 도식을 한 페이지의 접이식 상세로 옮기는 방식도 현재 범위에서 제외한다.
