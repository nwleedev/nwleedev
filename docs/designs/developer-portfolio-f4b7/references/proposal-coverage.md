# UI 디자인 제안서의 요구사항 반영 위치

현재 사이트 구성은 [단일 페이지 요구사항](../requirements.md#주소와-콘텐츠-구분)을 따른다. 아래는 2026년 9월 15일 기존 UI 제안서를 다중 페이지 요구사항과 대조한 기록이다. 웹 이력서, 내부 상세와 전체 목록, 페이지 간 전환 및 긴 사례 제작에 관한 반영 설명은 더 이상 유효하지 않다.

시각 원칙, 접근성, 문구 분리와 디자인 체계의 필요한 항목은 유지한다. 새 디자인 리서치와 PDF를 바탕으로 한 현재 적용안은 [단일 페이지 UI, UX 조사](single-page-ui-ux.md)에 있으며, 제작 순서는 [플랜](../plan.md)을 따른다. 아래 기록 자체를 현재 요구사항의 충족 목록으로 사용하지 않는다.

이 문서는 한국어 웹사이트의 화면 설계와 제작을 준비할 때 제안서의 내용이 어느 문서에 있는지 확인하기 위한 대조 자료다. 2026년 9월 15일 저장소 최상위의 `temps/main-web-ui-design/proposal.md` 1~28장 전체와 [요구사항](../requirements.md), 소개 방향 및 대표 사례 결정을 대조했다. 제안서 원본은 임시 자료로 보관되어 있으며, 이후 작업의 기준은 요구사항과 승인된 결정 문서다.

## 사이트 목적과 페이지 구성

제안서 1, 5~7, 12~19, 23장의 사이트 역할과 콘텐츠 구분은 [사이트의 역할과 자료 활용](../requirements.md#사이트의-역할과-자료-활용), [주소와 콘텐츠 구분](../requirements.md#주소와-콘텐츠-구분), [페이지별 내용](../requirements.md#페이지별-내용)에 반영되어 있다.

PDF 복제 금지, 실제 사이드 프로젝트로의 이동, 프로젝트와 사례의 구별, 홈에서 선별한 콘텐츠를 보여주는 구성, 웹 이력서와 PDF 접근을 포함한다. 서비스 링크와 내부 상세 링크를 구별하고, 첫 버전에 검색과 필터 및 별도 글 목록 페이지를 만들지 않는 조건도 유지한다. 공통 화면과 404, 긴 사례의 그림 및 코드 표현은 페이지별 요구사항으로 정리되어 있다.

## 시각적 방향과 반복해서 사용할 표현

제안서 4, 8~11, 13, 22장의 방향은 [시각적 방향](../requirements.md#시각적-방향)과 [기본 구성에서 제외하는 표현](../requirements.md#기본-구성에서-제외하는-표현)에 반영되어 있다. `Quiet Engineering Editorial`이라는 제목 대신 내용, 글자, 여백과 조작 반응을 어떻게 구성할지 한국어로 설명한다.

중립색과 강조색 하나, 글자와 여백을 이용한 정보 구분, 읽기 적합한 본문 폭, 제한적인 테두리와 그림자, 필요한 아이콘과 움직임을 포함한다. 반복할 특징은 결과를 먼저 보여주는 사례, 서비스와 설명의 별도 링크, 실제 기술 정보의 일정한 배치, 링크와 조작 영역의 제한적인 반응으로 정리했다.

제안서 11.4장의 여백 우선 원칙과 20장의 강조색 명암비 확인 순서를 요구사항에 명시했다. 4장의 유행을 이유로 공상과학풍 화면이나 과도한 장식을 채택하지 않는 조건도 구체화했다. 거대한 소개 화면, 기술 로고 모음, 둥근 카드의 일괄 적용과 장식용 애니메이션을 피하는 기존 조건과 함께 적용한다.

## 조작, 접근성과 반응형 동작

제안서 19~21장은 [조작과 상태](../requirements.md#조작과-상태), [접근성과 반응형 동작](../requirements.md#접근성과-반응형-동작)에 반영되어 있다. 기본 링크와 버튼의 구분, 중첩 링크 금지, 터치에서도 정보 제공, 불필요한 로딩 및 비활성 상태 제외, 움직임 감소 설정을 포함한다.

WCAG 2.2 AA 목표와 명암비, 글자 확대, 포인터 대상 크기, 키보드, 포커스, HTML 의미, 대체 텍스트 조건을 유지한다. 화면 폭이 달라져도 읽는 순서와 필요한 동작을 유지하고, 공간이 부족하면 한 열로 바꾸며, 긴 코드 등에만 내부 가로 스크롤을 허용한다. 모바일 메뉴도 네 링크를 줄바꿈해 제공할 수 있는지 먼저 확인한다.

## 디자인 체계에 필요한 조사와 산출물

제안서 25~28장의 상세 조건은 [디자인 체계의 구성과 제작 순서](../requirements.md#디자인-체계의-구성과-제작-순서)와 [완료를 확인할 결과](../requirements.md#완료를-확인할-결과)에서 확인할 수 있다.

기존 요구사항의 마지막 문장은 기존 구현과 설정을 확인한 뒤 구성 요소 및 토큰을 정한다고만 설명했다. 제안서가 열거한 프레임워크와 페이지 구성, 스타일과 공통 요소, 글꼴 및 이미지, 블로그와 공유하는 시각적 특징, 반응형과 테마 확인 항목을 구체화했다. 제안서와 다르다는 이유로 기존 구현을 폐기하지 않는 조건도 명시했다.

구성 요소 목록, 기본 시각 규칙, 토큰, 개별 구성 요소와 반복 조합을 정리한 뒤 `DESIGN.md`를 작성하는 순서를 반영했다. 구성 요소의 용도, 내부 구성, 표현 종류, 상태, 토큰, 시각 규칙, 사용 조건과 잘못된 사용 예를 남기는 조건은 이전 요약만으로 확인하기 어려웠던 부분이다.

제안서 26장의 구성 요소 이름은 그대로 파일 목록으로 확정하지 않는다. 실제로 필요한 요소와 반복 조합만 정의하며, `DESIGN.md`와 재사용할 구현으로 새 페이지와 사례를 같은 규칙에 따라 추가할 수 있어야 한다. 문서를 작성했다는 사실만으로 구현까지 완료됐다고 판단하지 않는다.

## 조사 자료와 이후 결정으로 구분한 내용

제안서 2~3장의 경력 해석과 외부 사이트 설명은 요구사항에 그대로 옮기지 않았다. 경력 사실과 수치 조건은 [개발 경험 분석](content-and-site-direction.md#자료에서-확인한-경험과-근거의-한계), 사이트 관찰은 [개발자 개인 사이트 조사](developer-websites.md)에 기록되어 있다. 제안서 9장의 요청 횟수 예시는 비교 조건을 함께 설명해야 하므로 홈페이지에 사용할 필수 수치로 정하지 않았다.

개발자를 소개하는 방향은 [사용자 이해와 화면 설계](../decisions/developer-positioning.md)를 따른다. 첫 소개에서 실시간 데이터 처리 경험을 중심에 두는 대신, 실제 기술 경험은 이를 뒷받침하는 사례로 사용한다. 홈페이지에 보여줄 사례는 [대표 사례 네 개](../decisions/featured-cases.md)로 정했다.

제안서 24장에서 미결정이었던 영어 제공은 [문구 관리와 언어](../requirements.md#문구-관리와-언어)에서 한국어 제작 후 영어 추가로 구체화됐다. 회사 사례는 [글과 새 기술 도식으로 설명하는 방식](../decisions/featured-cases.md#사례의-설명-방식)을 정했다.

첫 버전에 소개할 개인 메모 앱과 Issnuta, 소스 링크의 제공 방식은 [프로젝트 소개 결정](../decisions/project-availability.md)에 반영됐다. 글의 선정과 상세 주소, 색과 글꼴, 테마 및 화면 폭은 [아직 정하지 않은 사항](../requirements.md#아직-정하지-않은-사항)에 남아 있다.

## 공식 자료에서 확인한 근거와 적용 한계

2026년 9월 15일 Codex 앱 브라우저에서 제안서가 참고한 공식 자료 세 개를 다시 읽었다. [Primer Layout](https://primer.style/product/getting-started/foundations/layout/)은 콘텐츠에 집중할 수 있는 배치와 화면 폭이 줄어도 같은 동작을 제공하는 반응형 구성을 설명한다. [Primer Motion and animation](https://primer.style/accessibility/design-guidance/motion-and-animation/)은 움직임의 필요성을 먼저 판단하고 사용자의 움직임 감소 설정을 존중하도록 안내한다. [Geist Typography](https://vercel.com/geist/typography)는 글자 크기, 줄 높이, 자간과 굵기의 조합으로 글자 스타일을 정의한다.

이 자료는 제안서의 배치, 움직임과 글자 구성 원칙을 뒷받침한다. Primer의 화면 폭이나 Geist의 글꼴 및 크기를 이 사이트의 확정값으로 채택했다는 뜻은 아니다. 이 대조는 제안서의 문서 반영 여부를 설명하며, 실제 화면의 디자인과 접근성 검증을 대신하지 않는다.

한국어 콘텐츠로 화면과 기본 시각 규칙을 구체화하는 것이 다음 제작 준비다. 영어 문구의 완성을 기다리지 않고 진행한다. 구현 기술, 실제 콘텐츠와 시각적 선택이 필요한 시점에는 [모호한 상황의 확인](../requirements.md#모호한-상황의-확인)에 따라 필요한 결정을 확인한다.
