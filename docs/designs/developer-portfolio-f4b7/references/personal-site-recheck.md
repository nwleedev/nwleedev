# 개인 사이트의 배치와 경력 서술 재조사

단일 칼럼 구성은 Emil의 세로 본문 배치를, 글자 위계는 Paco의 절제된 표현을, 경력 설명은 Brittany의 구체적인 담당 업무 서술을 참고한다. 세 사이트 모두가 네비게이션 없는 단일 칼럼은 아니다. 관찰한 구성을 그대로 복제하지 않고 [요구사항](../requirements.md)의 네비게이션 바 제외, 단일 칼럼과 구체적인 기여 설명에 맞춰 선택한다.

2026년 9월 20일 세 홈페이지를 Codex 브라우저에서 데스크톱 화면과 모바일 폭으로 직접 확인했다. 화면 이미지, 접근성 트리와 웹 본문을 함께 읽었다. 조사는 첫 소개, 경력 또는 현재 업무, 프로젝트 소개와 주요 링크에 한정한다. 정밀한 CSS 측정이나 전체 사이트 접근성 감사는 아니다.

## Brittany Chiang

[Brittany Chiang 홈페이지](https://brittanychiang.com/)의 데스크톱은 왼쪽 이름, 직무와 고정 탐색, 오른쪽 소개 및 경력의 두 영역이다. 어두운 바탕, 낮은 대비의 날짜, 청록색 링크와 기술 태그를 사용한다. 모바일 화면에서는 좌측 탐색이 사라지고 소개 다음 경력이 세로로 이어진다.

경력은 기간, 회사 및 직무, 담당 업무, 사용 기술과 작업 확인 링크 순서로 읽힌다. Apple 경력은 막연한 UI 개발 대신 웹 플레이어의 브라우저 인증과 곡 재생 UI를 특정한다. Klaviyo 경력은 공통 컴포넌트와 접근성, 협업 대상을 설명한다. 짧은 원문 “in-browser user authorization and full song playback”이 담당 기능의 범위를 보여준다.

우리 사이트에는 이처럼 무엇을 구현했는지 밝히는 문장과 확인 자료 연결을 적용한다. 좌우 분할, 고정 탐색, 큰 이름과 기술 pill은 가져오지 않는다. 프로젝트에는 설치 수와 GitHub 수치도 있으므로 이 사이트가 숫자를 전혀 사용하지 않는다고 해석하지 않는다.

## Paco Coursey

[Paco Coursey 홈페이지](https://paco.me/)는 이름과 소개를 본문에 가까운 크기로 두고 링크를 문장에 섞는다. 데스크톱의 Building, Projects와 Writing은 세 열이다. 모바일 폭에서도 이 목록은 옆으로 이어지고 가로 스크롤이 보였으므로 단일 칼럼 구현의 그대로 쓸 예시는 아니다.

현재 Linear에서 맡은 역할과 이전 Vercel의 디자인 시스템, 웹사이트, 대시보드 개발을 짧은 문장으로 소개한다. 프로젝트는 이름과 용도를 연결한다. Writer의 설명은 “Plain text editor with a focus on performance.”다. 회사 연표나 각 프로젝트의 상세 해결 과정은 첫 화면에 풀어 쓰지 않는다.

우리 사이트에는 과장되지 않은 이름 크기와 기능을 특정하는 설명 방식을 적용한다. 가로 목록과 홈페이지 글 목록은 채택하지 않는다. 이 정도 분량만으로 우리 경력의 변경 방법까지 충분히 설명할 수 있다는 뜻은 아니다.

## Emil Kowalski

[Emil Kowalski 홈페이지](https://emilkowal.ski/)는 밝은 바탕의 중앙 본문에서 이름과 Design Engineer, Today, Projects, Writing을 세로로 이어 놓는다. 제목과 본문의 크기 차이가 크지 않고 여백으로 영역을 구별한다. 모바일에서도 같은 세로 순서다. 상단 강좌 안내는 있지만 섹션 이동 메뉴는 없다.

현재 Linear의 Web 팀과 이전 Vercel의 디자인 팀을 밝힌다. Sonner는 React toast, Vaul은 React drawer처럼 결과물의 용도를 짧게 설명한다. “Today I work on the Web team at Linear.”는 현재 역할을 바로 알려주는 문장이다.

우리 사이트에는 위에서 아래로 이어지는 본문과 절제된 제목을 적용한다. 큰 영역 간 공백, 강좌 안내, 글 목록과 뉴스레터 입력 양식은 가져오지 않는다. 이 홈페이지는 상세 경력 목록이 아니므로 회사별 기여를 깊게 서술하는 직접 예시로 과장하지 않는다.

## 우리 사이트에 적용할 판단

배치는 한 칼럼으로 통일하되 정보까지 줄이지 않는다. 회사명, 기간과 역할, 맡은 일, 개별 기여를 같은 왼쪽 기준선에서 읽게 한다. 제목 크기보다 문단 사이의 간격과 서술 순서로 훑어보기를 돕는다. 언어 선택과 외부 자료 링크는 본문의 텍스트 링크로 남긴다.

각 기여는 문제가 발생한 기능과 조건, 직접 바꾼 방식, 확인한 변화가 드러나는 본문으로 쓴다. 모든 항목에 고정된 세 소제목을 반복하거나 기술명만 늘리지 않는다. 수치는 해당 작업의 설명 안에 두며 새로운 비율을 계산하거나 조건을 생략하지 않는다.

본문의 구체성은 외부 개발자의 경력을 빌려 만드는 것이 아니다. [기존 자료 분석](content-and-site-direction.md#자료에서-확인한-경험과-근거의-한계)과 [경험별 상세 근거](featured-case-copy.md)를 사용해 [한국어 문구](homepage-copy.md)를 보강한다. 3초 폴링 요청 수는 가정에 따른 비교라는 한계를 유지한다. 이전 회사의 WebSocket 경험은 정확한 원인과 수정 코드가 확인되지 않아 조사 도구와 해결한 현상까지만 적는다.

채택한 구성은 [시각 방향 결정](../decisions/editorial-direction.md)과 [기여 서술 결정](../decisions/featured-cases.md)에 반영한다. 최대 본문 폭과 글자 크기는 표준이나 위 사이트의 측정값이 아니라 `DESIGN.md`의 구현 시작값이다. 이 조사만으로 새 화면의 가독성이나 접근성이 검증된 것은 아니다.
