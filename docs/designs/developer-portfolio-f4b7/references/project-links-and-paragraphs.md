# Projects의 링크 배치와 문단 구성

각 프로젝트의 설명 아래에 저장소와 결과물 링크를 함께 두는 안을 제안한다. 프로젝트를 만든 이유와 개선한 점을 먼저 읽고, 관심이 생기면 바로 확인할 수 있기 때문이다. 제목 옆에 두거나 기술 정보와 함께 두는 배치도 비교했지만, 현재 사이트의 단일 칼럼과 여러 문단 설명에는 본문 아래가 더 잘 맞는다고 판단했다. 이 배치는 아직 선택되지 않았다.

이 조사는 [Projects 요구사항](../requirements.md#projects)의 링크 위치와 여러 문단 구성을 위한 참고 자료다. 실제 화면 관찰과 문서 확인 날짜는 2026년 10월 3일이다. 사례에서 확인한 배치와 이 사이트에 적용할 제안을 구분한다.

## 현재 사이트에서 바꿔야 할 부분

현재 프로젝트 항목은 설명 한 문단과 링크 하나를 제공한다. 두 프로젝트에 서로 다른 목적의 링크를 함께 제공하고 설명을 여러 문단으로 나누려면, 문구뿐 아니라 이를 표시하는 항목 구성도 바뀌어야 한다. 근거는 [프로젝트 표시 컴포넌트](../../../../apps/entry/src/_pages/home/ui/IndependentWorkSection.astro), [문구 타입](../../../../apps/entry/src/shared/terms/types.ts)과 [한국어 문구](../../../../apps/entry/src/shared/terms/ko.json)다.

회사 경력에는 이미 여러 문단을 표시하는 기여 본문이 있고, Open Source에는 여러 링크가 있다. [공통 링크 컴포넌트](../../../../apps/entry/src/shared/ui/ExternalTextLink.astro)는 링크 이름과 목적 설명을 제공한다. Projects에서도 같은 링크 표시와 접근성 처리를 재사용할 수 있는지 확인해야 한다. 비슷하게 보인다는 이유만으로 회사 경력과 프로젝트를 하나의 컴포넌트로 합치지는 않는다.

## 실제 화면에서 확인한 배치

### Docusaurus: 제목 옆에 소스 링크

[Docusaurus Showcase](https://docusaurus.io/showcase)의 Ionic, Jest와 React Native 항목에서는 사이트 이름과 `source` 링크가 같은 행에 있다. 사이트 이름은 이용 사이트로, `source`는 저장소로 연결되며 설명은 그 아래에 놓인다.

이 배치는 설명을 읽기 전에도 이용 사이트와 저장소를 찾을 수 있다. 다만 이 사이트의 `Personal Notes Workspace`처럼 제목이 길고 두 링크에 목적을 설명하는 텍스트가 필요하면 제목과 링크가 공간을 나눠 써야 한다. 제목 바로 아래에 링크 행을 따로 두는 안은 이 문제를 줄일 수 있지만, 본문보다 링크를 먼저 읽게 한다. 이는 관찰한 화면을 바탕으로 한 적용 판단이다.

Docusaurus의 카드 격자, 스크린샷, 분류 태그와 즐겨찾기 표시는 현재 사이트에 적용할 제안이 아니다. 비교 대상은 제목과 링크의 관계다.

### Radix: 소개 내용 아래에 문서와 데모 링크

[Radix 홈페이지](https://www.radix-ui.com/)에서는 제목, 소개 문장과 코드 예시 아래에 `Get started`와 `Playground` 링크가 나란히 있다. GitHub 링크는 상단 메뉴에 따로 있다.

소개 내용을 읽은 뒤 문서나 데모를 선택한다는 순서를 참고할 수 있다. Projects에서는 코드 예시 없이 여러 문단 아래에 두 링크를 모으면 같은 읽는 순서를 만들 수 있다. 현재 사이트의 단일 칼럼에 적용하기 쉽다는 판단이며, Radix가 포트폴리오에 이 배치를 권장한 것은 아니다.

큰 버튼, 배경 장식, 코드 예시와 옆에 놓인 데모 화면은 가져오지 않는다. Projects에서는 기존 본문 링크처럼 목적이 적힌 텍스트를 사용하는 안을 제안한다.

### Vercel: 결과물 링크와 저장소 정보를 분리

[Vercel의 Next.js Boilerplate](https://vercel.com/templates/next.js/nextjs-boilerplate)에서는 `Deploy`와 `View Demo`가 제목 오른쪽에 있고, 저장소 링크는 상세 설명 옆의 GitHub 정보에 들어 있다. GitHub 정보 다음에는 용도와 기술 정보가 이어진다.

결과물을 이용하는 사람과 저장소를 확인하는 사람에게 필요한 정보를 분리하는 구성이다. 현재 사이트에서는 별도 옆 칼럼을 만들 수 없으므로, 저장소를 기간 및 기술 정보와 함께 놓는 안으로 바꿔 비교할 수 있다. 다만 두 링크가 떨어져 있으면 채용담당자가 프로젝트별로 확인 가능한 자료를 한눈에 찾기는 어려울 수 있다. 이 영향은 화면 배치에 대한 판단이며 이용자 측정 결과는 아니다.

배포 버튼, 큰 미리보기와 두 칼럼 상세 화면은 적용 대상이 아니다. 비교 대상은 데스크톱 링크 배치이며, 서비스별 모바일 구성과 키보드 접근성 평가는 포함하지 않는다.

## 현재 사이트에 제안하는 배치

설명을 모두 읽은 뒤 두 링크를 함께 볼 수 있도록, 마지막 문단과 기간 및 기술 정보 사이에 링크 목록을 두는 안을 제안한다. 제목, 여러 문단, 링크 목록, 기간 및 기술 정보를 같은 왼쪽 기준선에 맞추면 기존 단일 칼럼을 유지할 수 있다.

두 링크는 목적을 적은 텍스트로 표시한다. GitHub 아이콘만 보이면 개발자가 아닌 방문자는 저장소라는 뜻을 알아야 하므로, 모바일에서도 링크 이름을 읽을 수 있게 하는 편이 이 사이트에 적합하다. 현재 프로필의 모바일 아이콘 목록과 Projects의 자료 링크는 목적이 다르다.

이름은 `GitHub 저장소`와 `문구 개선 사례 보기`, `GitHub 저장소`와 `메모 앱 열기`를 제안한다. 영어는 각각 `GitHub repository`, `View wording examples`, `Open notes app`으로 같은 목적을 전달할 수 있다. 기존 문구 개선 사례와 Notes 소스 링크를 유지하고, 각 프로젝트에 새 링크 하나를 더한다.

너비가 부족하면 링크 목록이 줄바꿈되도록 하고 프로젝트 본문을 옆 칼럼으로 나누지 않는 안을 제안한다. 문단 사이 간격과 마지막 문단에서 링크까지의 간격은 기존 글자 체계 및 여백 값을 활용하고, 실제 한국어와 영어 화면에서 구분되는지 확인해야 한다. 새 고정 높이와 문단 수는 정하지 않는다.

## 링크의 목적과 모바일 사용 기준

각 링크 이름으로 저장소와 결과물을 구분할 수 있어야 한다. `보기`만 반복하기보다 대상이 드러나는 이름을 쓴다. 보조 기술로 링크 목록만 읽을 때도 어느 프로젝트의 자료인지 알 수 있게 한다. W3C는 링크 텍스트 또는 프로그램이 확인할 수 있는 문맥으로 목적을 알 수 있어야 한다고 설명한다. 이 기준은 특정 위치가 가장 좋다는 근거가 아니라, 어느 배치를 선택해도 충족해야 하는 접근성 조건이다. [WCAG 링크 목적 설명](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html)

프로젝트 링크를 한곳에 모아도 각각 누르기 쉬워야 한다. WCAG 2.2 AA의 최소 기준은 24×24 CSS px 또는 정해진 간격 등의 예외다. 본문 밖에서 나란히 제공하는 링크 목록을 문장 속 링크라고 간주해 예외를 적용하지 않는다. 기존 프로필 아이콘의 44px 기준과 이 최소 기준은 구분한다. [WCAG에서 정한 링크를 누를 수 있는 최소 영역](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

320 CSS px에서도 설명과 두 링크가 잘리거나 페이지 전체에 가로 스크롤이 생기지 않아야 한다. 200% 글자 확대는 기존 사이트 요구사항으로 별도 확인한다. 200% 확인만으로 WCAG Reflow를 충족했다고 판단하지 않는다. W3C의 Reflow 기준은 세로 스크롤 콘텐츠를 320 CSS px 너비에서도 읽을 수 있어야 한다는 것이다. [WCAG Reflow 설명](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## 여러 문단으로 읽히게 하는 방법

문단은 기술 종류별로 나누기보다 읽는 사람이 이해해야 할 내용에 따라 나눈다. AI Agent Workflow는 작업을 이어갈 때 필요한 규칙과 기록을 첫 문단에, 한국어 문구 검사와 여러 저장소에 적용한 경험을 다음 문단에 둔다. Personal Notes Workspace는 반복 입력과 메모 증가를 해결하려던 목적, 문구와 명령어를 다시 쓰기 쉽게 만든 경험을 첫 문단에 둔다. 직접 발견한 이동 문제와 모바일 구성을 조사한 경험은 다음 문단에 둔다.

Offline Translation Web App도 같은 표시 방식을 사용하되, 문단을 늘리려고 사실을 보태지 않는다. 네트워크 연결 없이 번역하고 실행 중에도 입력을 이어갈 수 있는 사용 경험과, 필요한 파일 저장 및 배포 자동화 경험을 나눌 수 있다. 문구는 [홈페이지 한국어 문구의 Projects](homepage-copy.md#projects)에 있다.

현재 소개에서 확인되지 않은 이용자 수와 시간 절감 수치를 추가하지 않는다. 여러 문단으로 바꾸는 목적은 기존 목적과 기여를 읽기 편하게 구분하는 것이다.

## 연결할 자료와 남은 확인

AI Agent Workflow의 문구 개선 사례는 현재 사이트의 `/projects/use-better-terms`에 있다. 두 언어의 홈페이지에서 같은 [사례 페이지](../../../../apps/entry/src/pages/projects/use-better-terms.astro)로 연결되며, 사례 본문은 한국어다. 이번 링크 추가에 영어 사례 페이지 제작까지 포함하지 않는다.

AI Agent Workflow의 저장소는 아직 확정되지 않았다. `nwleedev/codex-agents-demo`는 GitHub에서 열람 가능한 저장소이며 README에 Codex CLI 지시사항 모음이라고 적혀 있다. 현재 지시사항은 AI 이미지 생성용이라고 설명하므로, 사이트에서 소개한 규칙과 문구 검사를 대표하는 자료인지는 추가 확인이 필요하다. [저장소 README](https://github.com/nwleedev/codex-agents-demo#readme)

Personal Notes Workspace는 현재 [평가 버전 소스](https://github.com/nwleedev/nwleedev/tree/a06bfc94c64232581742792a9834b82f5963f225/apps/notes)에 연결된다. 애플리케이션 주소는 [배포 설정](../../../../apps/notes/wrangler.jsonc)과 [README](../../../../apps/notes/README.md)에 없어 아직 확인하지 못했다. 배포 설정의 애플리케이션 이름만으로 이용 주소를 추정할 수는 없다.

남은 결정은 링크의 배치다. 남은 사실 확인은 AI Agent Workflow의 대표 저장소와 Personal Notes Workspace의 실제 이용 주소다. 이 항목들은 [후속 플랜](../plan.md#22-projects-요구사항과-배치-검토)에 구분해 기록한다.
