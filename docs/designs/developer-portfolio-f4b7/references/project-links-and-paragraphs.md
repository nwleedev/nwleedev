# Projects의 링크 배치와 문단 구성

실제 서비스는 제목에서 열고, 저장소와 문구 개선 사례는 설명 아래에 두는 구성이 현재 사이트에 적합하다. Personal Notes Workspace의 제목 끝에 외부 링크 아이콘을 붙이면 메모 앱으로 이동할 수 있다는 점을 드러낼 수 있다. 제목 옆에 여러 링크를 모으지 않아 긴 프로젝트 이름과 여러 문단 설명도 기존 단일 칼럼에서 읽을 수 있다.

이 조사는 [Projects 요구사항](../requirements.md#projects)의 링크 위치와 여러 문단 구성을 위한 참고 자료다. 실제 화면 관찰과 문서 확인 날짜는 2026년 10월 3일이다. 사례에서 확인한 배치와 이 사이트에 적용할 제안을 구분한다.

## 현재 사이트에서 바꿔야 할 부분

변경 전 프로젝트 항목은 설명 한 문단과 링크 하나를 제공했다. 두 프로젝트에 서로 다른 목적의 링크를 함께 제공하고 설명을 여러 문단으로 나누려면, 문구뿐 아니라 이를 표시하는 항목 구성도 바뀌어야 한다. 근거는 [프로젝트 표시 컴포넌트](../../../../apps/entry/src/_pages/home/ui/ProjectsSection.astro), [문구 타입](../../../../apps/entry/src/shared/terms/types.ts)과 [한국어 문구](../../../../apps/entry/src/shared/terms/ko.json)다.

회사 경력에는 이미 여러 문단을 표시하는 기여 본문이 있고, Open Source에는 여러 링크가 있다. [공통 링크 컴포넌트](../../../../apps/entry/src/shared/ui/ExternalTextLink.astro)는 링크 이름, 목적 설명과 대각선 화살표 표시를 제공한다. Projects에서도 같은 링크 표시와 접근성 처리를 재사용할 수 있는지 확인해야 한다. 비슷하게 보인다는 이유만으로 회사 경력과 프로젝트를 하나의 컴포넌트로 합치지는 않는다.

## 실제 화면에서 확인한 배치

### Docusaurus: 제목 옆에 소스 링크

[Docusaurus Showcase](https://docusaurus.io/showcase)의 Ionic, Jest와 React Native 항목에서는 사이트 이름과 `source` 링크가 같은 행에 있다. 사이트 이름은 이용 사이트로, `source`는 저장소로 연결되며 설명은 그 아래에 놓인다.

사이트 이름 자체를 이용 사이트 링크로 쓰는 방식을 참고할 수 있다. 다만 이 사이트의 `Personal Notes Workspace`처럼 제목이 길면 저장소 링크까지 같은 행에 놓았을 때 공간을 나눠 써야 한다. 서비스는 제목에서 열고 저장소는 설명 아래에 두면 제목 옆에는 외부 링크 아이콘만 추가하면 된다. 이는 관찰한 화면을 바탕으로 한 적용 판단이다.

Docusaurus의 카드 격자, 스크린샷, 분류 태그와 즐겨찾기 표시는 현재 사이트에 적용할 제안이 아니다. 비교 대상은 제목과 링크의 관계다.

### Radix: 소개 내용 아래에 문서와 데모 링크

[Radix 홈페이지](https://www.radix-ui.com/)에서는 제목, 소개 문장과 코드 예시 아래에 `Get started`와 `Playground` 링크가 나란히 있다. GitHub 링크는 상단 메뉴에 따로 있다.

소개 내용을 읽은 뒤 문서나 데모를 선택하는 순서를 참고할 수 있다. Projects에서는 AI Agent Workflow의 저장소와 문구 개선 사례를 여러 문단 아래에 모으면 같은 읽는 순서를 만들 수 있다. 현재 사이트의 단일 칼럼에 적용하기 쉽다는 판단이며, Radix가 포트폴리오에 이 배치를 권장한 것은 아니다.

큰 버튼, 배경 장식, 코드 예시와 옆에 놓인 데모 화면은 가져오지 않는다. Projects에서는 기존 본문 링크처럼 목적이 적힌 텍스트를 사용하는 안을 제안한다.

### Vercel: 결과물 링크와 저장소 정보를 분리

[Vercel의 Next.js Boilerplate](https://vercel.com/templates/next.js/nextjs-boilerplate)에서는 `Deploy`와 `View Demo`가 제목 오른쪽에 있고, 저장소 링크는 상세 설명 옆의 GitHub 정보에 들어 있다. GitHub 정보 다음에는 용도와 기술 정보가 이어진다.

서비스를 이용하는 사람과 저장소를 확인하는 사람에게 필요한 링크를 나누는 구성이다. 현재 사이트에서는 서비스 링크를 제목에, 저장소 링크를 같은 프로젝트의 설명 아래에 두는 데 참고할 수 있다. 별도 옆 칼럼 없이 제목부터 설명과 자료까지 한 방향으로 읽을 수 있다는 판단이며, 채용담당자의 이용 결과를 측정한 것은 아니다.

배포 버튼, 큰 미리보기와 두 칼럼 상세 화면은 적용 대상이 아니다. 비교 대상은 데스크톱 링크 배치이며, 서비스별 모바일 구성과 키보드 접근성 평가는 포함하지 않는다.

## 현재 사이트에 적용할 배치

Personal Notes Workspace는 제목을 누르면 메모 앱으로 이동한다. 제목 끝의 외부 링크 아이콘으로 일반 제목과 구별하고, 제목과 아이콘을 하나의 링크로 제공한다. 아이콘 모양은 기존 본문 링크의 대각선 화살표를 활용하는 안을 제안한다. 아이콘만 별도 링크로 만들거나 제목 오른쪽 끝에 떨어뜨려 놓지 않는다.

AI Agent Workflow의 저장소와 문구 개선 사례, Personal Notes Workspace의 저장소는 마지막 문단과 기간 및 기술 정보 사이에 둔다. 제목, 여러 문단, 자료 링크와 기술 정보를 같은 왼쪽 기준선에 맞춰 기존 단일 칼럼을 유지한다. 메모 앱 링크는 제목에서 제공하므로 설명 아래에 반복하지 않는다.

자료 링크는 목적을 적은 텍스트로 표시한다. GitHub 아이콘만 보이면 개발자가 아닌 방문자는 저장소라는 뜻을 알아야 하므로, 모바일에서도 링크 이름을 읽을 수 있게 한다. 이름은 `GitHub 저장소`와 `문구 개선 사례 보기`, 영어는 `GitHub repository`와 `View wording examples`를 제안한다. 서비스 주소가 없는 두 프로젝트의 제목은 일반 제목으로 유지한다.

너비가 부족하면 제목과 자료 링크가 줄바꿈되도록 한다. 외부 링크 아이콘만 다음 줄에 남지 않고 제목의 마지막 부분과 함께 보이는지 확인해야 한다. 문단 사이 간격과 마지막 문단에서 링크까지의 간격은 기존 글자 체계 및 여백 값을 활용한다. 새 고정 높이와 문단 수는 정하지 않는다.

## 링크의 목적과 모바일 사용 기준

각 링크 이름으로 저장소와 결과물을 구분할 수 있어야 한다. `보기`만 반복하기보다 대상이 드러나는 이름을 쓴다. 보조 기술로 링크 목록만 읽을 때도 어느 프로젝트의 자료인지 알 수 있게 한다. W3C는 링크 텍스트나 프로그램이 확인할 수 있는 문맥으로 목적을 설명하며, 웹 애플리케이션 이름도 링크 목적을 나타낼 수 있다고 명시한다. 따라서 Notes 제목을 링크로 쓰는 것은 이 기준에 부합하는 방식이다. [WCAG 링크 목적 설명](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html)

제목 링크에는 프로젝트 이름과 메모 앱으로 이동한다는 목적을 전달한다. 아이콘은 그 이름을 반복해서 읽히지 않게 보조 기술에서 제외하고 별도 키보드 이동 대상도 만들지 않는다. W3C도 같은 링크 안에 아이콘과 설명 텍스트가 있으면 아이콘 설명을 중복하지 않는 예를 제시한다. [아이콘과 텍스트를 함께 제공한 링크 사례](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html#examples)

제목 링크와 설명 아래 자료 링크는 키보드로 이동했을 때 포커스가 보여야 한다. 제목 색만 바꾸지 않고 외부 링크 아이콘과 마우스를 올리거나 키보드로 이동했을 때의 표시를 함께 확인한다. [WCAG 키보드 포커스 표시 설명](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)

프로젝트 링크를 한곳에 모아도 각각 누르기 쉬워야 한다. WCAG 2.2 AA의 최소 기준은 24×24 CSS px 또는 정해진 간격 등의 예외다. 본문 밖에서 나란히 제공하는 링크 목록을 문장 속 링크라고 간주해 예외를 적용하지 않는다. 기존 프로필 아이콘의 44px 기준과 이 최소 기준은 구분한다. [WCAG에서 정한 링크를 누를 수 있는 최소 영역](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

320 CSS px에서도 제목, 아이콘, 설명과 자료 링크가 잘리거나 페이지 전체에 가로 스크롤이 생기지 않아야 한다. 200% 글자 확대는 기존 사이트 요구사항으로 별도 확인한다. 200% 확인만으로 WCAG Reflow를 충족했다고 판단하지 않는다. W3C의 Reflow 기준은 세로 스크롤 콘텐츠를 320 CSS px 너비에서도 읽을 수 있어야 한다는 것이다. [WCAG Reflow 설명](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## 여러 문단으로 읽히게 하는 방법

문단은 기술 종류별로 나누기보다 읽는 사람이 이해해야 할 내용에 따라 나눈다. AI Agent Workflow는 작업을 이어갈 때 필요한 규칙과 기록을 첫 문단에, 한국어 문구 검사와 여러 저장소에 적용한 경험을 다음 문단에 둔다. Personal Notes Workspace는 반복 입력과 메모 증가를 해결하려던 목적, 문구와 명령어를 다시 쓰기 쉽게 만든 경험을 첫 문단에 둔다. 직접 발견한 이동 문제와 모바일 구성을 조사한 경험은 다음 문단에 둔다.

Offline Translation Web App도 같은 표시 방식을 사용하되, 문단을 늘리려고 사실을 보태지 않는다. 네트워크 연결 없이 번역하고 실행 중에도 입력을 이어갈 수 있는 사용 경험과, 필요한 파일 저장 및 배포 자동화 경험을 나눌 수 있다. 문구는 [홈페이지 한국어 문구의 Projects](homepage-copy.md#projects)에 있다.

현재 소개에서 확인되지 않은 이용자 수와 시간 절감 수치를 추가하지 않는다. 여러 문단으로 바꾸는 목적은 기존 목적과 기여를 읽기 편하게 구분하는 것이다.

## 연결할 자료

AI Agent Workflow의 문구 개선 사례는 현재 사이트의 `/projects/use-better-terms`에 있다. 두 언어의 홈페이지에서 같은 [사례 페이지](../../../../apps/entry/src/pages/projects/use-better-terms.astro)로 연결되며, 사례 본문은 한국어다. 이번 링크 추가에 영어 사례 페이지 제작까지 포함하지 않는다.

AI Agent Workflow의 저장소 링크는 [Docs System](https://github.com/nwleedev/docs-system)이다. 외부에서 열람할 수 있으며, README에는 에이전트 지침, 설계 문서와 개발 지침을 관리하는 스킬 및 `use-better-terms`가 소개되어 있다. 홈페이지에서 소개한 규칙과 문구 검사 도구를 살펴볼 수 있다. [Docs System README](https://github.com/nwleedev/docs-system#readme)

Personal Notes Workspace의 제목은 [메모 앱](https://notes.nwlee.com)으로 연결한다. 이용 주소에서 메모 화면이 표시됐다. 확인한 대상은 주소와 첫 화면이다.

설명 아래 저장소 링크는 [현재 Notes 소스](https://github.com/nwleedev/nwleedev/tree/main/apps/notes)로 연결한다. GitHub의 `main`에서 `apps/notes`와 애플리케이션 파일을 확인했다. 홈페이지의 저장소 링크는 이 주소로 연결하며, 과거 평가의 근거로 남긴 고정 버전 링크와 구분한다.

링크 배치와 주소는 후속 플랜에 반영할 수 있다. 한국어와 영어 화면에서 제목 및 아이콘의 줄바꿈, 키보드 포커스와 클릭 영역은 [화면 확인 단계](../plan.md#25-두-언어-화면과-링크-확인)에서 확인한다.
