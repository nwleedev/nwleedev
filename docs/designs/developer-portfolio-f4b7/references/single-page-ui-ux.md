# 단일 페이지의 UI, UX와 콘텐츠 구성 제안

이 문서의 사례 조사와 원자료 분석은 유지하지만, 개인 프로젝트를 먼저 보여주는 화면 제안과 미결정 시각 값은 현재 기준이 아니다. 승인된 편집형 방향, 글꼴, 색상과 정보 순서는 [편집형 디자인 조사](editorial-design-system.md), [편집형 시각 방향 결정](../decisions/editorial-direction.md)과 [요구사항](../requirements.md)을 따른다.

소개, 개인 프로젝트 두 개, 대표 경험 네 개, 오픈소스 기여, 글과 연락 수단을 위에서 아래로 이어 읽는 구성을 권한다. 개성은 기술을 설명하는 별도 시연이 아니라 실제 프로젝트의 화면, 한글 타이포그래피, 정보의 배치와 조작 반응에서 만든다. 상세한 해결 과정은 블로그가 맡고, 이 페이지는 어떤 개발자이며 무엇을 기대할 수 있는지 설명한다.

이 문서는 [단일 페이지 요구사항](../requirements.md)의 「사이트의 역할과 자료 활용」, 「홈페이지」, 「시각적 방향」을 구체화하기 위한 조사와 설계 제안이다. 콘텐츠 작성과 화면 설계에 사용한다. 확정된 첫 소개, 프로젝트 및 대표 경험 선정은 유지한다. 아래 섹션 순서, 화면 수치와 시각 표현은 아직 승인된 디자인이 아니다.

## 세 입력 자료에서 가져올 것

2026년 9월 19일 `2025-2026_2D_3D_web_design_research.md`, 이력서 PDF 2쪽과 포트폴리오 PDF 18쪽을 다시 읽었다. PDF는 텍스트와 주요 사례의 페이지 이미지를 대조했다. 이력서는 2026년 9월 19일, 포트폴리오는 2026년 9월 7일 생성본이다. 이전 조사에서 사용한 이력서와 생성 시점이 다르므로 성과 문구는 이번 자료와 대조한다. 원자료의 개인 연락처와 PDF 이미지는 조사 문서에 복제하지 않는다.

### 디자인 리서치: 독자적인 표현과 기술 전시를 구별

입력 리서치는 2D와 3D 사례를 비교하고, 컴포넌트 관계, 상태 변화, 렌더링과 네트워크 요청 순서를 조작하는 `Interactive Frontend System`을 제안한다. 이는 조사자의 설계 제안이며 실제 경력이나 승인된 사이트 구성은 아니다.

독자적인 시각 규칙을 정하고 모바일에 맞춰 표현을 달리하는 원리는 유효하다. 반면 Interface, State, Data, Runtime, Performance를 차례로 탐색하는 구성은 개발자 소개보다 기술 학습의 비중이 커진다. 블로그와 역할이 겹치므로 첫 버전의 정보 구조로 채택하지 않는 편을 권한다. 입력 자료의 FPS 비교 예시는 실제 측정 성과로 사용하지 않는다.

### 이력서: 직무와 기여의 근거

이력서 1쪽은 프론트엔드 개발에서 API 응답, 상태, 성능과 배포 후 동작까지 다룬 경험을 보여준다. 2쪽에는 작업 문서 도구, 오프라인 번역, 팀 프로젝트와 오픈소스 기여가 있다. 기술 이름이나 모든 경력을 별도 섹션으로 나열하기보다, 사용자에게 필요한 동작을 끝까지 구현하는 능력의 근거로 선별한다.

현재 회사와 이전 회사의 연혁, 학점, 도구 목록을 홈페이지 중심에 추가할 이유는 없다. 전체 경력은 최신 이력서 링크로 제공하고, 이미 선정한 두 프로젝트와 두 오픈소스 기여를 유지한다. 이력서의 프로젝트를 근거 없이 첫 버전 목록에 더하지 않는다.

### 포트폴리오: 화면에서 무엇을 판단했는가

대표 경험은 이미 선정한 네 개로 충분하다. 7쪽의 이력 구성은 함께 읽어야 할 정보와 PM 협의를, 11~12쪽의 문서 생성은 기다림과 취소 중 안내를 보여준다. 5쪽의 화면 정지와 13쪽의 대시보드는 그 화면을 실제로 사용할 수 있게 만든 기술적 판단이다.

수치는 반드시 대상과 조건을 함께 쓴다. `3~4초`는 개선 전 화면 정지이며 응답 시간이나 FPS가 아니다. `96.5 MB → 41 KB`는 10분 동안의 데이터 전송량이다. `5~10분`은 문서 생성 시간이며 단축 성과가 아니다. 9쪽의 배너 용량은 세 파일 합계이므로 방문자 한 명의 다운로드량으로 쓰지 않는다. 상세 근거와 확인 한계는 [경험 분석](content-and-site-direction.md#자료에서-확인한-경험과-근거의-한계)에 둔다.

## 2025~2026 사례에서 확인한 사실

제작 시점과 관찰 시점을 구별한다. 2025년에 발표된 제작 글은 당시의 설계 이유를 설명하고, 실제 사이트는 2026년 9월 19일의 표시를 확인한 자료다. 특정 스타일이 시장 전체를 대표한다거나 채용 성과를 높인다고 판단할 자료는 아니다.

### Brittany Chiang: 소개와 근거를 같은 문서에서 읽기

1440×900 화면에서는 이름과 직무가 왼쪽에 남고 오른쪽으로 경력과 프로젝트가 이어졌다. Projects를 누르면 같은 문서의 `#projects`로 이동했다. 390×844에서는 소개 다음에 본문이 이어지는 한 열로 바뀌었다. 이력서 PDF와 작업의 외부 링크는 본문과 구분되어 있다. [실제 사이트](https://brittanychiang.com/)

적용할 것은 한 페이지에서 소개와 근거를 연결하는 방식이다. 남색 배경, 고정된 왼쪽 소개, 경력 타임라인과 기술 배지의 조합은 가져오지 않는다. 이 사이트의 전체 프로젝트 아카이브도 현재 요구사항에는 필요하지 않다.

### Emil Kowalski: 짧은 설명만으로 작업의 성격 전달

1440×900과 390×844에서 이름과 직무, UI에 대한 관심, Projects와 Writing의 순서를 확인했다. 프로젝트마다 이름과 한 줄 설명이 있어 링크를 열기 전 용도를 알 수 있다. 한 열과 여백이 중심이지만 모바일에서도 상단 여백이 상당하므로 첫 화면 밀도까지 그대로 가져오지는 않는다. [실제 사이트](https://emilkowal.ski/)

제작 글의 짧은 원문은 “making sure your animations have a purpose”다. 기능이나 설명을 돕지 않는 움직임을 제한하는 [Primer의 모션 지침](https://primer.style/accessibility/design-guidance/motion-and-animation/)과 같은 방향이다. 이번 페이지에서는 프로젝트의 목적을 짧게 쓰고, 모션은 링크와 위치 및 상태 변화를 설명할 때 사용한다. [Emil의 모션 글](https://emilkowal.ski/ui/you-dont-need-animations)

### Stefan Vitasović: 하나의 시각적 발상을 반복하는 2025 포트폴리오

2025년 3월 5일 작성자의 제작 글은 스위스 인쇄물에서 얻은 비대칭 배치와 문자가 단어로 모이는 움직임을 설명한다. 모바일에서는 WebGL 대신 기본 비디오를 사용한다고 밝힌다. 2026년 9월 19일 데스크톱에서 큰 글자, 비대칭 배치와 프로젝트 미디어를 확인했고, 소개에서 아래로 스크롤하면 주소가 `/projects`로 바뀌었다. [작성자의 제작 설명](https://tympanus.net/codrops/2025/03/05/case-study-stefan-vitasovic-portfolio-2025/), [실제 사이트](https://stefanvitasovic.dev/)

적용할 것은 효과의 종류를 늘리는 대신 하나의 표현을 일관되게 다듬는 태도다. 화면 전체 크기의 제목, 별도 페이지 전환과 스크롤 제어는 이번 요구와 맞지 않는다. 모바일 대체 방식은 작성자의 설명이며 이번 조사에서 모든 기기의 실행을 확인한 것은 아니다.

### Vercel Ship 2025: 표현의 이유가 먼저인 그래픽

2025년 6월 11일 제작 글은 Fluid compute라는 주제에서 액체 금속 모티프를 발전시킨 과정을 설명한다. 시각 탐색에는 생성형 도구도 사용했고 최종 웹 표현에는 시뮬레이션과 ray marching을 사용했다. 브라우저에서 연결된 피라미드 실험의 금속성 도형과 조정 패널을 확인했다. 이는 행사 최종 화면 전체에 대한 검증이 아니다. [Vercel 제작 설명](https://vercel.com/blog/designing-and-building-the-vercel-ship-conference-platform), [그래픽 실험](https://ship-25-explorations.vercel.app/ferro-pyramid)

이 사례는 AI 도구를 썼는지보다 주제와 표현의 관계를 따져야 한다는 근거다. 액체 금속을 개발자 소개에 붙일 이유는 없다. 메모의 선택과 조합처럼 실제 작업에서 형태를 찾는 것이 이번 사이트에 더 적합하다.

### Maxime Heckel: 인터랙티브 설명은 블로그의 역할

모바일 첫 화면에서는 셰이더 이미지, 소개와 연도별 글 목록을 확인했다. 소개는 복잡한 주제를 playground와 시각화로 이해하도록 돕는다고 밝힌다. 2025년 TSL/WebGPU 글과 2026년 셰이더 글들이 나뉘어 있다. 글 안의 모든 예제를 실행한 것은 아니다. [블로그](https://blog.maximeheckel.com/), [2025년 TSL/WebGPU 글](https://blog.maximeheckel.com/posts/field-guide-to-tsl-and-webgpu/)

상세 설명을 맡는 기존 블로그가 있으므로 이 구성을 개인 홈페이지 안에 재구현하지 않는다. 홈페이지에는 글의 주제와 읽을 이유만 남기고 원문으로 연결한다.

### Bruno Simon: 3D 자체가 전문성을 보여주는 경우

작성자의 `folio-2025` 저장소는 입력, 차량, 물리, 카메라와 렌더링을 게임 루프로 구성한다. 2026년 9월 19일 확인한 커밋은 `41046b57eeed8d156d9c3fd7fa259900baef7816`이다. 단순히 3D 장식을 얹은 소개와는 제작 범위가 다르다. [작성자 저장소의 게임 루프](https://github.com/brunosimon/folio-2025/blob/41046b57eeed8d156d9c3fd7fa259900baef7816/readme.md#game-loop)

실제 사이트 접속에서는 이 조사 환경의 화면 캡처가 실패해 주행과 모바일 조작을 확인하지 못했다. 이를 사이트 자체의 장애나 접근성 실패로 판단하지 않는다. 현재 경력의 핵심은 3D 렌더링이 아니므로 같은 탐색 방식을 기본안으로 채택할 근거도 없다. [실제 사이트](https://bruno-simon.com/)

### 트렌드 글의 적용 한계

Webflow의 2026 전망은 “algorithmic sameness”에 대응하는 고유 표현, 짧은 문구와 요약 중심 탐색을 제안한다. 이는 해당 회사의 편집 관점이지 보편적인 디자인 규칙이나 조사 통계가 아니다. 위 제작자들의 서로 다른 표현을 함께 보면 공통으로 가져올 것은 특정 효과가 아니라 자신의 작업에 맞는 표현을 고르는 기준이다. [Webflow의 2026 전망](https://webflow.com/blog/web-design-trends-2026)

## 권장하는 읽기 순서와 콘텐츠 분량

아래 순서는 제안이다. 홈페이지용 본문은 [한국어 문구 초안](homepage-copy.md) 한 곳에서 관리하며, 이 문서는 화면에서 차지할 역할을 설명한다.

1. **소개:** 이름, Frontend Engineer와 확정된 첫 문장을 먼저 보여준다. 이어지는 보조 문장은 정보 구성과 실제 상태를 일치시키는 관심을 짧게 설명한다. 첫 화면에 프로젝트 영역의 시작도 보여 소개만으로 화면을 채우지 않는다.
2. **개인 프로젝트:** 메모 앱과 Issnuta의 목적, 제작 내용과 현재 활동을 보여준다. 각각 두세 문장 정도로 시작해 화면에서 조정한다. 준비된 서비스와 소스만 연결하고, 내부 상세 보기 링크는 만들지 않는다.
3. **경험으로 보여주는 역량:** 네 경험을 모두 펼쳐 놓는다. 제목, 직접 내린 판단과 확인된 변화로 두 문장 안팎을 구성한다. 기술 도식과 해결 절차를 네 세트로 반복하지 않는다. 해당 경험을 다룬 글이 실제로 있을 때만 별도 글 링크를 붙인다.
4. **오픈소스 기여:** React Router와 Outline을 두 줄의 작업 목록으로 소개한다. 각 수정의 의미와 PR 및 릴리스 링크를 분리해 제공한다. 별점, 기여 횟수나 실시간 GitHub 데이터를 붙이지 않는다.
5. **글:** 선정한 글의 제목, 한 줄 요약과 작성 시점, 블로그 링크를 제공한다. 첫 후보는 React 상태 초기화 글이며 최종 게재는 미결정이다. 글 본문, 검색과 분류 기능은 복제하지 않는다.
6. **연락:** 협업에서 기대할 기여를 한 문장으로 다시 연결하고 이메일, GitHub, LinkedIn과 최신 이력서를 제공한다. 연락 양식이나 전체 경력 연표는 추가하지 않는다.

채용담당자는 위 순서로 정체성과 근거를 읽을 수 있고, 개발자는 프로젝트 소스나 PR 및 블로그로 선택적으로 이동할 수 있다. 외부 이동을 하지 않아도 소개는 완결되어야 한다. 빠른 연락과 이력서 확인은 헤더에서도 가능하게 하는 안을 권한다.

## UI 제안: 작업의 목적과 결과를 나란히 읽는 화면

### 기본 배치와 글자

밝은 중립 배경, 짙은 본문과 한 가지 강조색으로 시작하는 안을 권한다. 실제 색과 글꼴은 선택 전이다. 한글 본문을 기준으로 글꼴을 비교하고, 큰 영문 이름만으로 시각적 차이를 만들지 않는다.

데스크톱에서는 좁은 섹션 제목 열과 넓은 내용 열을 같은 기준선에 맞춘다. 고정된 자기소개 사이드바나 모든 항목을 감싼 카드 대신, 제목의 크기 차이와 항목 사이의 간격으로 구분한다. 두 프로젝트는 각각 설명과 실제 UI 미리보기를 한 묶음으로 배치하고, 네 경험은 세로 목록으로 이어 읽게 한다. 수치가 있는 경험에서만 숫자를 한 단계 크게 쓰되 단위와 조건을 떨어뜨리지 않는다.

화면 초안의 시작값은 페이지 폭 1120px 이내, 본문 폭 36rem 안팎, 본문 17~18px와 줄 높이 1.65, 모바일 좌우 여백 20px를 제안한다. 소개 제목은 화면 높이가 아니라 내용 길이로 크기를 조절한다. 이 값은 디자인 토큰이나 승인된 기준이 아니며 1440×900, 390×844와 320px 폭에 실제 한국어를 놓고 바꾼다.

### 고유한 시각 요소

프로젝트마다 사용 목적을 보여주는 실제 UI 일부를 우선한다. 메모 앱은 원문에서 선택한 문장이 조합되는 관계, Issnuta는 모델을 준비한 뒤 오프라인 번역을 사용하는 관계가 후보이다. 이미지를 구할 수 없으면 확인된 기능의 관계를 간결한 선과 문장으로 새로 그리는 안을 비교한다. 재구성한 설명은 실제 앱 화면으로 표시하지 않는다.

반복할 표현은 선택한 문장과 그 결과를 같은 강조색으로 잇는 표시다. 링크의 밑줄, 키보드 포커스와 같은 페이지 내 현재 위치에도 같은 색의 역할을 일관되게 적용한다. 배경에 선을 계속 흐르게 하거나 모든 글자를 분해하는 효과는 사용하지 않는다. 이 규칙이 실제 콘텐츠와 연결되지 않으면 장식으로 유지하지 않는다.

회사 경험은 글을 기본으로 하고 설명에 꼭 필요한 경우만 정적 도식을 보탠다. 프로젝트 이미지 두 장을 채우기 위해 가짜 UI, 운영 화면이나 AI 생성 이미지를 만들지 않는다. 실제 미리보기의 제공 가능 여부는 화면 설계 전에 확인한다.

### 모바일과 첫 화면

모바일에서는 섹션 제목, 설명, 그림과 링크를 DOM의 읽는 순서 그대로 한 열로 배치한다. 데스크톱의 그림을 축소해 글자를 읽게 하지 않고, 모바일에 필요한 장면을 고르거나 이미지 아래 문장으로 같은 의미를 제공한다.

헤더에는 같은 페이지의 프로젝트, 경험, 연락 링크와 외부 블로그 및 이력서 링크를 목적별로 구분한다. 좁은 화면에서는 줄바꿈을 우선하고 고정 헤더는 기본안에서 제외한다. 정확한 링크 개수와 고정 여부는 실제 폭에서 판단한다. 메뉴 전체를 수평 스와이프해야 찾거나 조작 패널을 열어야 소개를 읽는 구조는 피한다.

첫 화면에서 직무, 소개와 다음에 읽을 작업의 단서를 함께 볼 수 있는지 확인한다. 200% 글자 확대에서 이를 한 화면에 억지로 압축하지는 않는다. 확대 시에는 내용 보존과 읽는 순서를 우선한다.

## UX와 조작 반응

페이지 내부 탐색은 기본 앵커 링크로 구성한다. 예시 이름은 `#projects`, `#experience`, `#contact`이며 구현 전에 제목과 맞춘다. 직접 해시 주소로 진입, 새로고침, 뒤로 가기와 키보드 이동에서도 해당 내용을 찾을 수 있어야 한다. 스크롤을 가로채거나 주소를 다른 소개 페이지로 바꾸지 않는다.

현재 위치 표시는 부가적인 안내다. 스크롤 중 포커스를 강제로 옮기지 않고, 메뉴 링크의 글자와 표시를 함께 바꾼다. 링크 밑줄과 포커스의 제한적인 전환은 가능하지만 본문은 등장 애니메이션이 끝나기를 기다리지 않고 읽을 수 있어야 한다. 움직임 감소 설정에서는 위치를 따라가는 긴 이동과 비필수 전환을 없앤다.

프로젝트 전체를 클릭 영역으로 만들지 않고 서비스, 소스와 관련 글을 독립 링크로 둔다. URL이 없으면 빈 버튼이나 비활성 버튼을 남기지 않는다. 블로그로 이동하는 링크와 이메일, 이력서의 목적을 이름에서 알 수 있게 한다. 새 탭을 사용할 경우 그 동작도 안내한다.

소개 본문은 HTML로 읽을 수 있게 제공하고, 선택적인 시각 효과의 로딩이나 실패가 소개와 링크를 가리지 않게 하는 구성을 권한다. 읽기 전용 소개를 위해 스켈레톤, 진행률과 비동기 대시보드를 추가할 필요는 없다.

## 2D와 3D를 적용할 범위

기본안은 **HTML/CSS 기반 배치와 목적이 있는 2D 반응**이다. 실제 앱의 기능을 이 페이지에서 다시 구현하지 않으면서도 한글 조판, 폭에 따라 달라지는 배치, 링크 상태와 선택 표시의 세부 동작을 보여줄 수 있다.

텍스트만 있는 이력서형 화면은 제작 범위가 적지만 시각적 구현 역량을 드러낼 재료가 부족하다. 반대로 전체 화면 3D 탐색이나 프론트엔드 원리 실험실은 소개를 읽기 전에 학습과 조작을 요구하며 블로그와 기능이 겹친다. 그래서 프로젝트의 실제 화면과 제한된 2D 표현을 결합하는 안을 우선 비교한다.

3D를 영구히 금지한다는 제안은 아니다. 실제 프로젝트의 공간 관계를 설명할 필요가 생기고 정적인 대안보다 이해가 쉬운 경우에만 별도 선택으로 검토한다. 그때에도 본문 밖의 선택적 표현, 키보드 및 터치 대안, 움직임 감소와 렌더링 실패 대안, 추가 용량과 모바일 성능을 함께 판단한다. 현재 플랜에는 WebGL/WebGPU, Three.js나 물리 엔진을 기본 의존성으로 넣지 않는다.

## 접근성과 성능의 확인 기준

요구사항의 WCAG 2.2 AA 목표를 유지한다. 한 페이지라는 이유로 긴 화면의 탐색과 포커스 이동을 생략하지 않는다. W3C는 세로 콘텐츠를 320 CSS px 상당 폭에서도 정보와 기능 손실 없이 읽도록 설명하고, 고정 콘텐츠가 포커스를 완전히 가리지 않아야 한다고 명시한다. 글자 200% 확대와 320px 재배치는 별도로 확인한다. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [W3C Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

프로젝트 이미지 크기를 미리 확보하고 첫 화면 아래의 미디어는 필요할 때 불러오는 안을 권한다. 성능 판단에는 초기 표시, 조작 반응과 배치 안정성을 함께 사용한다. web.dev가 설명하는 양호 기준은 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하이며 모바일과 데스크톱을 나눈 실제 방문의 75백분위 기준이다. 이 수치는 제안하는 점검 기준이지 이미 측정한 결과나 새로 승인된 요구사항이 아니다. 로컬 측정을 실제 방문 데이터나 WCAG 충족 증거로 대신하지 않는다. [Web Vitals](https://web.dev/articles/vitals)

## 결정과 플랜에 미치는 영향

단일 페이지와 블로그의 역할 분리는 유지한다. 프로젝트 및 사례 상세, 전체 목록과 웹 이력서 제작 절차는 사용하지 않는다. 기존 긴 설명과 도식 초안은 사실 확인용 자료로 보존하며 자동으로 홈페이지나 블로그에 게시하지 않는다.

후속 요구사항에서 밝은 편집형 화면, Pretendard, `#EE5166` 계열 강조색과 회사별 Engineering Contribution 중심의 정보 순서를 선택했다. 개인 프로젝트 미리보기와 글 목록은 첫 버전의 필수 영역에서 제외한다. 이 문서의 1120px 화면 폭, 17~18px 본문과 프로젝트 중심 배치는 이전 비교안으로만 보존한다.

구현은 [편집형 디자인 조사](editorial-design-system.md)의 공식 자료 확인과 [플랜](../plan.md)을 따른다. 실제 링크, Pretendard 제공 방식, Header 고정 여부와 한국어 문구에 맞춘 반응형 값은 구현 전에 확인한다.
