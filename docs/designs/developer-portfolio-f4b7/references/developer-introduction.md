# 개발자 소개 방향과 웹사이트 문구

홈페이지 첫 소개와 상세 소개는 개발자의 가치와 작업 방식을 먼저 드러내도록 다시 다듬을 필요가 있다. [채용 역량과 소개 방식의 비교](frontend-hiring-and-positioning.md#현재-소개-문구에-적용할-편집-판단)에서는 개별 작업을 나열하기 전에 경험을 관통하는 강점을 설명하는 방향을 제안한다. 아래 문구는 그 판단과 비교하며 수정할 초안이다.

이 문서는 [사이트의 역할과 자료 활용](../requirements.md#사이트의-역할과-자료-활용)에 맞는 웹사이트 문구를 다듬기 위한 편집 자료다. 홈페이지 첫 소개와 상세 소개, 대표 사례와 오픈소스 기여 문구를 담는다. 아래 인용 블록은 방문자에게 보여줄 한국어 초안이며, 표현과 길이는 계속 수정할 수 있다. 그 밖의 설명과 근거는 문구를 선택하는 데 쓰는 자료다.

## 소개에서 남길 인상

첫 소개에서는 어떤 웹을 만드는 프론트엔드 개발자인지 설명하고, 사례에서는 이를 어떻게 구현했는지 보여준다. 방문자가 기억할 중심은 화면을 설계하고 구현하면서 반응성과 동작의 정확성을 개선해 온 경험이다. 실시간 데이터는 그 경험을 보여주는 소재이며, 개발자의 직무를 한정하는 이름으로 사용하지 않는다.

프레임워크 중심의 소개도 가능하지만 React와 TypeScript라는 이름만으로는 이력의 특징을 설명하기 어렵다. 성능 최적화만 강조하면 상태 동기화, 데이터 정확성, 요구사항 조정 경험이 덜 드러난다. 이 경험들을 함께 설명하는 현재 방향이 자료에 더 잘 맞는다.

서버 API와 배포 설정을 다룬 경험은 프론트엔드 문제를 해결한 과정에서 보여준다. 별도의 직무 이름을 늘리기보다 어떤 문제 때문에 어디까지 작업했는지 설명한다. AI를 이용하는 서비스와 문구 검사 도구도 직접 만든 기능과 그때의 판단으로 소개한다.

## 방문자에게 보여줄 문구 초안

### 홈페이지 첫 소개

이름과 `Frontend Engineer`를 함께 표시한다. 첫 문장은 강조할 강점을, 뒤의 두 문장은 그 강점을 뒷받침하는 경험을 설명한다.

> 빠르게 반응하고, 정확하게 동작하는 웹을 만듭니다.

> 화면을 설계하고 구현하며, 성능과 동작의 정확성을 개선해 온 프론트엔드 개발자입니다. 페이지를 이동하거나 작업을 취소하는 상황까지 고려해, 사용자가 현재 상태를 확인하고 다음 행동을 선택할 수 있도록 설계해 왔습니다.

화면 설계와 구현, 성능 개선과 상태 처리를 프론트엔드의 강점으로 소개한다. 아래 대표 사례에서 화면 정지 해결과 대시보드 개선, 문서 생성 중의 사용자 행동, API 제약에 따른 목록 구성을 보여준다. 첫 문장은 여러 화면에 적용할 수 있는 역량을 설명하고, 어떤 화면을 어떤 기술로 만들었는지는 사례에서 설명한다.

장시간 작업 경험에서는 사용자의 행동에 따라 필요한 안내와 동작을 설계한 점을 보여준다. 페이지를 벗어나려는 사용자의 의사를 확인하고, 취소하지 않기로 한 경우에는 작업 상태를 계속 보여준 경험이 근거다. 연결 오류에 따른 상태 재확인은 사용자의 선택과 구분해 사례에서 설명한다.

### 상세 소개

> React와 TypeScript로 웹 서비스의 화면을 설계하고 구현해 왔습니다. 사용자가 기다리는 동안 무엇을 확인할 수 있어야 하는지, 다른 페이지로 이동하거나 작업을 취소하려 할 때 어떻게 안내해야 하는지까지 생각합니다. 화면의 반응 속도와 표시값의 정확성도 함께 살피며, 화면 정지와 잘못된 지표 표시의 원인을 찾아 개선했습니다.
>
> 화면에 필요한 정보와 API 응답이 맞지 않을 때는 PM과 제약을 공유하고 구현 방식을 조정했습니다. 서버 API를 구현하고 배포 설정을 조정해 문제를 해결했으며, 배포 후에도 화면이 의도대로 동작하는지 확인했습니다.

### 대표 사례 문구의 구성

다음 네 사례는 성능 개선, 사용자 행동에 따른 화면 설계, 표시값의 정확성과 협업 경험을 보여주기 위한 구성안이다. 각 인용 블록의 제목과 요약은 사례 목록에 사용할 초안이며, 최종 게재 사례와 순서는 아직 정하지 않았다. 구체적인 기술 설명은 어떤 문제를 해결하기 위한 선택이었는지 읽을 수 있을 만큼 남긴다.

### 사례: 화면 정지 해결

> 3~4초 멈추던 화면, 응답 처리 위치를 바꾸다

> 약 5 MB의 API 응답을 처리하는 동안 화면이 3~4초 멈추는 문제를 해결했습니다. API 호출과 응답 변환을 SharedWorker로 옮겨 화면을 갱신하는 메인 스레드의 처리 부담을 줄였습니다. 응답 크기와 형식은 유지했고, 배포 후 화면 정지가 해소된 것을 확인했습니다.

### 사례: 문서 생성의 상태와 취소

> 5~10분 걸리는 문서 생성, 기다리는 동안의 사용 경험 설계

> 문서를 기다리는 동안 현재 상태와 소요 시간을 확인할 수 있도록 했습니다. 페이지를 벗어나려 할 때는 이동 의사를 확인하고, 취소하지 않기로 선택하면 진행 상태를 계속 보여주도록 구현했습니다. SSE 이벤트나 연결 오류가 발생하면 서버 상태를 다시 조회해 작업 상태를 판단하고, 배포 후 실제 작업 상태와 화면 표시가 일치하는지 확인했습니다.

### 사례: 대시보드 개선

> 대시보드의 잘못된 표시값을 바로잡고, 반복 전송을 줄이다

> 지표가 잘못 표시되거나 빠지는 원인을 찾아 조회와 변환 로직을 수정하고, 실제 응답과 대조해 표시값을 확인했습니다. 전체 구간을 반복해서 요청하던 방식은 마지막 요청 이후의 값만 가져오도록 바꿔, 10분 동안의 데이터 전송량을 96.5 MB에서 41 KB로 줄였습니다.

### 사례: 요구사항 조정

> 나뉜 작업 기록을 하나의 이력으로 정리하다

> API에서는 선행 작업과 후속 기록을 따로 제공했지만, 화면에서는 작업별로 이어지는 이력이 필요했습니다. PM과 협의해 목록 구성과 페이지 나누기 기준을 조정하고, 작업 하나에 후속 기록이 함께 보이도록 구현했습니다. 화면과 CSV에는 같은 판정 규칙을 적용해 작업 상태를 일관되게 표시했습니다.

### 오픈소스 기여 소개

> React Router와 Outline에 기여한 수정 사항이 공식 릴리스에 반영됐습니다.
>
> React Router에서는 선택적 URL 파라미터의 매칭 오류를, Outline에서는 인라인 이미지 앞의 텍스트 삭제 오류를 재현하고 수정했습니다. 기존 동작을 유지하는 수정안을 기여했고, 각각 React Router v7.13.1과 Outline v1.2.0에 포함됐습니다.

이 문구에서 각 이름은 [React Router PR](https://github.com/remix-run/react-router/pull/14689)과 [Outline PR](https://github.com/outline/outline/pull/10759)로 연결한다. 릴리스 정보는 [기여 확인 자료](content-and-site-direction.md#외부에서-확인할-수-있는-오픈소스-기여)에 있는 공식 링크를 사용한다.

## 사실을 매력적인 설명으로 편집하는 기준

방문자가 개발자의 기여와 달라진 동작을 이해하도록 사실을 선택하고 순서를 바꾼다. 기술 이름은 선택의 이유를 설명할 때 사용한다. 사례 제목에는 해결한 문제나 결과를, 요약에는 직접 바꾼 부분을 담는다. 수치가 없어도 원인 분석, 제약 안에서의 판단, 배포한 기능을 명확하게 설명할 수 있다.

자료를 검토하는 사람이 측정 원본을 확보하지 못했다는 사실은 개발자가 측정하지 않았다는 뜻이 아니다. 자료에 기록된 성과를 설명할 때 검토자의 확인 범위를 개발자의 자기평가로 바꾸지 않는다. 근거를 더 확인할 사항은 [자료 분석](content-and-site-direction.md#자료에서-확인한-경험과-근거의-한계)에서 관리한다.

수치를 쓸 때는 의미를 결정하는 대상을 문장 안에 남긴다. 대시보드 사례는 데이터 전송량과 10분이라는 비교 구간을 함께 적는다. 문서 생성 사례는 상태 판정과 취소 처리만으로도 판단이 드러나므로, 요약에 폴링 환산 수치를 추가하지 않았다. 상세에서 수치를 사용한다면 비교 조건을 함께 설명한다.

측정 여부나 조건이 해결되지 않아 결과를 단정할 수 없는 경우에는 확인된 구현과 동작으로 문장을 다시 쓴다. 실험실 결과를 운영 성과로 바꾸거나 데이터 전송량을 사용자 유지율로 설명하지 않는다. 성과의 의미를 바꾸는 조건은 해당 결과와 함께 설명한다.

## 채용 관점에서 이 방향을 권하는 근거

2026년 9월 14일 확인한 다음 일차 자료는 문제 분석, 맡은 일, 구현의 품질을 구체적으로 설명할 근거를 제공한다. 서로 다른 회사의 기대를 비교한 편집 판단이며 특정 문구가 채용 결과를 개선한다는 실험 결과는 아니다.

### 토스증권 FE Platform Engineer

공고는 근본 원인 분석과 프론트엔드 개발 및 배포 환경의 개선 경험을 요구한다. 이력서에는 브라우저 동작 원리를 이해하고 성능을 개선한 경험을 쓰도록 안내하며, 짧은 원문은 “경험을 단순 나열하는 것이 아닌”이다. 화면 정지와 서버 설정 사례에서 사용 기술보다 문제와 판단을 먼저 설명할 근거다. [토스증권 공식 공고](https://toss.im/career/job-detail?job_id=7977718003)

### 당근 로컬 콘텐츠 Frontend

공고는 문제의 원인을 추적한 경험, PM 및 동료와 요구사항을 정한 경험, 출시 이후의 성능과 운영을 함께 다룬다. 이력서와 포트폴리오에는 기여한 부분, 직접 볼 수 있는 코드나 PR, 구조를 정리할 때의 판단을 쓰도록 안내한다. 짧은 원문은 “실제로 맡아온 역할과 해결해온 문제의 복잡도”다. 원인 분석, 요구사항 조정, 오픈소스 기여를 서로 다른 증거로 보여줄 근거다. [당근 공식 공고](https://careers.daangn.com/jobs/role/7990233003/)

### Linear의 채용 및 업무 원칙

Linear는 소프트웨어의 품질과 세부 동작에 대한 관심을 강조한다. 사용자 문제를 이해하고 오래 사용할 수 있는 기반을 만들며 불필요한 절차를 늘리지 않는 원칙도 제시한다. 짧은 원문은 “getting even the smallest details right”다. 취소, 상태 재조회, 텍스트 삭제처럼 구체적인 동작을 완성한 경험을 설명할 근거다. 이 자료는 특정 직무의 합격 기준이 아니라 회사가 설명하는 업무 원칙으로 사용했다. [Linear 공식 채용 페이지](https://linear.app/careers)

## 문구와 이력의 연결

2026년 9월 7일 생성된 이력서 2쪽과 포트폴리오 18쪽을 바탕으로 작성했다. 2026년 9월 14일 이력서 두 쪽과 아래 사례에 해당하는 PDF 화면을 대조했다. 자료의 사실 정리와 수치별 사용 조건은 [개발 경험 분석](content-and-site-direction.md)에 둔다.

- 첫 소개: 포트폴리오 5쪽의 화면 정지 해결, 7쪽의 목록 구성과 11~12쪽의 작업 상태, 취소 및 연결 오류 처리를 바탕으로 화면 설계와 구현, 반응성과 동작의 정확성을 강조했다.
- 상세 소개: 이력서 1쪽과 포트폴리오 5쪽, 7쪽, 11~14쪽을 바탕으로 사용자 행동을 고려한 안내와 동작, 화면 정지 해결, 표시값 교정과 PM 협의 경험을 연결했다. 서버 API 구현은 14쪽, Nginx 설정은 12쪽, 화면 정지의 배포 후 확인은 5쪽에 기록되어 있다.
- 화면 정지: 포트폴리오 5쪽의 처리 위치 변경, 응답 조건 유지와 배포 확인을 사용했다. 3~4초는 개선 전 화면 정지 시간이다.
- 문서 생성: 이력서 1쪽과 포트폴리오 11~12쪽의 상태 확인, 취소, 페이지 이탈과 연결 오류 처리를 사용했다. 5~10분은 문서 생성에 걸리는 시간이다.
- 대시보드: 이력서 1쪽과 포트폴리오 13쪽의 표시값 교정과 10분 전송량 비교를 사용했다.
- 요구사항 조정: 포트폴리오 7쪽의 PM 협의, 작업 단위 목록과 CSV 판정 규칙을 사용했다.
- 오픈소스: 이력서 2쪽과 [React Router PR #14689](https://github.com/remix-run/react-router/pull/14689), [Outline PR #10759](https://github.com/outline/outline/pull/10759)의 작성자와 병합 상태를 대조했다. 릴리스 반영은 [공식 릴리스 확인 기록](content-and-site-direction.md#외부에서-확인할-수-있는-오픈소스-기여)을 근거로 한다.
