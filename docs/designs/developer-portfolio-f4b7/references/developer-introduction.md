# 개발자 소개 방향과 웹사이트 문구

이 문서는 사용자 이해와 화면 설계를 먼저 설명하던 이전 소개 방향의 조사 기록이다. 현재 소개 기준과 Experience 순서는 [개발자 소개 결정](../decisions/developer-positioning.md), [Engineering Contribution 결정](../decisions/featured-cases.md)과 [홈페이지 문구](homepage-copy.md)를 따른다.

**첫 소개에서는 사용자 이해와 화면 설계를 앞세우고, 기술적 문제 해결을 그 근거로 연결한다.** 현재 경험의 특징은 사용자에게 필요한 화면 구성과 동작을 판단하면서 브라우저, API와 배포 설정의 문제까지 해결한 데 있다. [소개 방향 결정](../decisions/developer-positioning.md)을 기준으로 문구의 의미와 근거를 비교한다.

아래의 상세 소개와 사례 문구는 비교 및 편집용 후보이며 별도 상세 페이지를 뜻하지 않는다. 현재 게재 본문은 [홈페이지 한국어 초안](homepage-copy.md)에서 관리한다. 긴 해결 과정은 블로그가 맡으므로 이전 후보를 전부 한 페이지에 옮기지 않는다.

이 문서는 [개발자 소개와 편집 기준](../requirements.md#개발자-소개와-편집-기준)에 맞는 소개 방향과 개별 문구 후보의 편집 근거다. 홈페이지에서 이어 읽을 현재 문구는 [홈페이지 한국어 초안](homepage-copy.md)에서 관리한다. 아래 첫 소개의 첫 문장은 이전에 확정했던 표현이며, 그 밖의 인용 블록은 비교에 사용한 후보로 구분한다. 비교 설명과 조사 근거는 방문자에게 보여줄 문구에 포함하지 않는다.

## 채용 수요와 실제 경험을 대조한 판단

현재 자료에서 소개할 수 있는 강점은 사용 상황을 판단하는 능력과 기술적 원인을 이해하는 능력의 조합이다. React와 TypeScript 사용 경험은 이를 구현한 기술 배경으로 설명한다. 모든 채용 요건을 갖췄다고 주장하거나, 공고에 자주 등장한다는 이유로 경험에 없는 강점을 붙이지 않는다.

2026년 9월 15일 Codex 앱 브라우저에서 카카오페이와 당근의 공식 공고, Brittany Chiang과 Emil Kowalski의 자기소개를 읽었다. 다른 기업과 개발자의 비교에는 [2026년 9월 14일 조사](frontend-hiring-and-positioning.md)를 사용한다. 회사별 필수 및 우대 요건, 모집 상태와 직무 수준의 차이는 그 문서에서 구분한다.

- 사용자 이해와 화면 설계: 카카오페이는 복잡한 정보의 UI 구성과 예외 상황 예상을, 당근은 사용자 이해와 상황에 맞는 기술 판단을 요구한다. 작업별 이력 구성과 장시간 문서 생성의 안내 및 선택 설계는 이 역량을 설명할 근거다. 사용자가 겪을 상황을 예상하고 화면 구성과 동작을 구체화하는 일을 맡길 수 있다는 인상으로 연결한다. [카카오페이 공고](https://kakaopay.career.greetinghr.com/ko/o/233787), [당근 공고](https://careers.daangn.com/jobs/role/7689088003/), [경험 근거](content-and-site-direction.md#요구-조정과-ui의-정확성)
- 기술 이해와 문제 해결: LINE Pay의 기술 원리 이해와 당근의 원인 파악 요구는 화면 정지, 잘못된 지표와 이벤트 전달 문제의 분석 경험과 연결된다. 화면에 드러난 현상을 브라우저 처리, API 응답과 서버 설정까지 살펴 해결하는 일을 맡길 수 있다는 인상이다. [LINE Pay 조사](frontend-hiring-and-positioning.md#line-pay-기술의-원리를-이해하고-실험과-운영에-참여), [화면 정지 근거](content-and-site-direction.md#화면-반응성과-실시간-데이터), [이벤트 전달과 상태 판단 근거](content-and-site-direction.md#장시간-작업과-상태-동기화)
- 동료와 제약을 조정하는 능력: 카카오페이와 당근의 협업 요구에 연결되는 실제 근거는 PM과 목록 및 페이지 나누기 기준을 조정한 경험이다. 사용자에게 필요한 화면과 API가 제공하는 정보가 다를 때 구현 방식을 함께 정할 수 있다는 의미다. 이를 조직 전체의 기술 리더십이나 멘토링 경험으로 확대하지 않는다. [목록 구성과 협의 근거](content-and-site-direction.md#요구-조정과-ui의-정확성)

접근성, 디자인 시스템, 사용자 조사나 A/B 테스트 경험을 소개의 중심에 놓을 만큼의 근거는 현재 자료에서 확보하지 못했다. 이 점은 문구를 고르기 위한 판단이며, 홈페이지에 개발자의 약점으로 나열할 내용은 아니다.

## 차별화할 가치 후보

두 후보는 같은 경험 중 무엇을 먼저 이해시키느냐가 다르다. 차별화는 다른 개발자에게 없는 능력이라고 단정하는 것이 아니라, 이 개발자에게 기대할 수 있는 판단과 그 근거를 구체적으로 보여주는 데서 찾는다. 아래 제목과 설명은 소개 방향을 비교하기 위한 것이며 홈페이지의 최종 문구가 아니다.

### A. 사용자 이해와 화면 설계를 앞세우는 소개

전달할 가치는 **사용자의 목적에 맞게 정보를 구성하고, 사용자의 선택에 필요한 안내와 동작을 설계하며 기술적 제약을 해결하는 능력**이다. 요구사항을 정보 구성과 조작 방식으로 구체화할 수 있는 프론트엔드 개발자로 소개한다.

장시간 작업에서는 기다리는 사람의 상황과 선택에 따라 안내 및 동작을 정했다. 작업 이력에서는 API가 나눈 정보를 사용자의 작업 단위로 다시 구성했다. 두 경험은 무엇을 보여줄지와 어떻게 사용할지를 판단한 근거다. 화면 정지와 표시값 개선은 그렇게 만든 화면을 제대로 사용할 수 있게 뒷받침한 경험으로 연결한다. [장시간 작업](content-and-site-direction.md#장시간-작업과-상태-동기화), [정보 구성](content-and-site-direction.md#요구-조정과-ui의-정확성)

채용과 협업에서 기대할 역할은 사용자에게 필요한 동작을 구체화하고, 기획 의도와 기술적 제약을 함께 고려하며 화면을 구현하는 일이다. B보다 새 화면을 설계하고 동료와 구현 방식을 협의하는 역량을 먼저 보여준다. 기술적 깊이는 뒤의 사례에서 증명한다.

이 방향을 단순히 “사용자 중심 개발자”라고 줄이면 본인의 특징이 사라진다. 정보를 어떻게 구성하고 사용자의 선택에 따라 기능이 어떻게 실행되어야 하는지 함께 판단한다는 점을 상세 소개에 남겨야 한다. 사용성 테스트로 편의성을 입증했거나 기획과 디자인을 전부 주도했다는 뜻으로 확대하지 않는다.

### B. 기술 이해와 문제 해결을 앞세우는 소개

전달할 가치는 **화면에 드러난 문제의 원인을 이해하고, 필요한 변경을 선택해 웹의 반응성과 동작을 개선하는 능력**이다. 증상을 재현하고 기존 구조를 이해한 뒤 수정할 수 있는 프론트엔드 개발자로 소개한다.

화면 정지에서는 응답 크기를 유지하며 처리 위치를 바꿨고, 대시보드에서는 표시 오류의 원인과 반복 조회를 각각 수정했다. 이벤트 전달에서는 서버 설정을, 오픈소스 기여에서는 기존 동작과 호환되는 수정을 검토했다. 특정 라이브러리에 한정되지 않는 원인 분석과 변경 판단을 보여준다. [화면 정지](content-and-site-direction.md#화면-반응성과-실시간-데이터), [대시보드](content-and-site-direction.md#전송량-감소와-표시값-교정), [오픈소스 기여](content-and-site-direction.md#외부에서-확인할-수-있는-오픈소스-기여)

채용과 협업에서 기대할 역할은 기존 웹 서비스의 성능과 동작 문제를 분석하고 개선하는 일이다. A보다 기술적 깊이와 문제를 해결하는 방식을 먼저 보여주며, 외부에서 확인할 수 있는 PR도 직접적인 근거가 된다.

이 방향만 강조하면 오류 수정이나 성능 개선을 주로 맡는 개발자로 읽힐 수 있다. 새 화면 설계와 사용 상황의 판단을 상세 소개에 함께 담아야 한다. 일부 서버 작업을 근거로 대규모 시스템 설계나 서버 전반의 전문성을 주장하지 않는다.

## 선택한 방향을 문구에 적용하는 방법

[소개 방향 결정](../decisions/developer-positioning.md)에 따라 첫 소개에는 A를, 이를 뒷받침하는 경험에는 B를 반영한다. 정보 구성과 사용 중의 선택을 판단하는 능력을 먼저 설명하고, 성능과 오류를 분석한 사례로 기술적 깊이를 보여준다.

[Brittany](https://brittanychiang.com/)는 중요하게 여기는 UI 품질을 먼저 밝히고 경험으로 뒷받침한다. [Emil](https://emilkowal.ski/)은 UI의 모습과 느낌 및 동작에 대한 관심을 설명한 뒤 작업을 보여준다. 여기서는 **개발 기준을 먼저 제시하고, 작업을 그 기준의 근거로 읽게 하는 구성**을 참고한다. 접근성 전문성이나 시각적 취향 같은 타인의 소개 내용은 옮기지 않는다.

한국어 문구를 다시 쓸 때 첫 소개에서는 만들고자 하는 사용 경험을 짧게 설명한다. 상세 소개에서는 사용자의 목적과 기술적 제약을 어떻게 함께 판단하는지 보여준다. 대표 사례는 작업별 정보 구성, 문서 생성 중의 대기와 취소, 화면 정지와 표시값 개선을 연결하되 첫 소개에서 작업을 모두 열거하지 않는다.

경험을 소개로 해석할 때의 질문은 **이 개발자와 함께하면 어떤 판단을 맡길 수 있는가**다. 현재 자료에서는 사용자의 목적을 화면 구성과 처리 기준으로 구체화하고, 그 기준이 실제 사용 과정에서도 지켜지는지 확인하는 강점을 제안할 수 있다. API가 나눈 기록을 사용자가 확인할 단위로 구성한 경험과, 메모의 입력값과 저장값을 구분한 경험은 서로 다른 기술을 사용했지만 이 판단을 함께 뒷받침한다. 앞의 경험은 무엇을 보여줄지 정하는 능력을, 뒤의 경험은 무엇을 확인해야 완성됐다고 판단할 수 있는지 정하는 능력을 보여준다. [이력 구성 근거](content-and-site-direction.md#요구-조정과-ui의-정확성), [메모 앱 테스트 근거](personal-notes-testing.md)

홈페이지에서 먼저 전달할 것은 어떤 필요에 관심을 두는 개발자인지, 함께 서비스를 만들 때 무엇을 기대할 수 있는지다. 개발자의 가치는 소개에서 직접 설명하고, 구현 내용은 이를 뒷받침하는 근거로 연결한다. 프로젝트는 만들려는 서비스의 목적을, 글은 탐구하는 주제와 관점을 보여주며 이 소개를 뒷받침한다.

상세 사례에서는 관심을 가진 독자에게 문제 해결의 근거와 필요한 기술 설명을 제공한다. 구현 방법과 검사 절차를 설명할 수 있다는 사실만으로 홈페이지에 넣지 않는다. 실제 경험이더라도 소개하려는 강점과 연결되지 않으면 사실 확인 자료에 남긴다.

선택한 소개 방향과 개별 문구의 확정 여부는 구분한다. 사실의 해석이나 강조점에 모호한 부분이 생기면 [모호한 상황의 확인](../requirements.md#모호한-상황의-확인)에 따라 질문과 선택지를 제공한다.

## 방문자에게 보여줄 문구 초안

아래는 개별 문구의 후보와 그 의미를 설명하는 자료다. 현재 홈페이지 전체의 문구를 읽거나 수정할 때는 [홈페이지 본문](homepage-copy.md#방문자에게-보여줄-본문)을 사용한다.

### 홈페이지 첫 소개

이름과 `Frontend Engineer`를 함께 표시한다. 첫 소개에는 확정된 한 문장을 사용하고, 개발 기준과 이를 뒷받침하는 경험은 이어지는 내용에서 설명한다.

> 서비스 사용자의 목적에 맞춰 필요한 정보를 제공하고, 사용자가 원하는 기능을 사용할 수 있도록 웹 서비스를 설계합니다.

이 문장은 화면 설계의 기준을 설명한다. 직무는 함께 표시하는 `Frontend Engineer`에서 밝힌다. 후속 문장을 늘리기보다 상세 소개와 선별한 사례가 이 기준을 뒷받침하도록 구성한다.

### 상세 소개

다음은 사용자 이해와 화면 설계를 먼저 설명하는 추천 문구다. 기술적 판단과 협업을 언급하되, 개별 구현과 검사 항목은 사례에서 설명한다.

> 사용자가 무엇을 하려는지 이해하고, 필요한 정보와 기능을 중심으로 화면을 설계합니다. 기획 의도와 기술적 제약 사이에서 구현 방식을 조율하며, 사용자의 선택에 따라 화면이 어떻게 달라져야 하는지 구체화합니다.
>
> 기능을 실행한 뒤의 경험도 중요하게 생각합니다. 기다리거나 도중에 선택을 바꾸는 상황에서도 사용자가 진행 상태를 알 수 있도록, 화면의 안내와 실제 처리가 일치하는지 살핍니다.

첫 문단은 사용자에게 필요한 화면과 조작을 정할 수 있는 역량을 설명한다. 둘째 문단은 기능을 실행한 이후까지 설계한다는 관점을 보여준다. 이 조합은 정보를 표시하는 화면의 구현에 더해, 사용자의 선택과 처리 상태에 맞춰 화면이 어떻게 달라져야 하는지도 맡길 수 있다는 의미다. 실제 판단과 확인한 변화는 [대표 사례의 상세 문구](featured-case-copy.md)에서 뒷받침한다.

프로젝트와 글은 이 소개를 뒷받침하는 경험을 기준으로 선별한다. 화면의 구성과 실제 동작을 판단한 근거는 사례에서 설명하고, 상세 소개의 표현은 이후 실제 화면에서도 다듬을 수 있다.

### 대표 사례 문구의 구성

홈페이지에는 [대표 사례 선정](../decisions/featured-cases.md)에 따른 네 사례를 소개한다. 작업별 이력 구성, 장시간 문서 생성, 화면 정지 해결, 대시보드 개선 순서로 읽는 구성을 제안한다. 앞의 두 사례에서는 사용자에게 필요한 정보와 조작을 설계한 판단을, 뒤의 두 사례에서는 이를 뒷받침하는 기술적 문제 해결을 보여준다. 선정한 사례와 배치 제안, 문구 초안은 구분한다.

2026년 9월 15일 다시 읽은 [카카오페이 공고](https://kakaopay.career.greetinghr.com/ko/o/233787)는 목표 달성을 위해 고민한 부분을 설명하도록 안내한다. [당근 공고](https://careers.daangn.com/jobs/role/7689088003/)는 어떤 사용자 문제를 판단하고 무엇을 개선했는지, 기술을 선택한 이유는 무엇인지 설명하도록 안내한다. [Brittany의 소개와 경력](https://brittanychiang.com/#experience)은 첫 소개에서 강조한 UI 품질을 컴포넌트 개발과 접근성을 고려한 구현 경험에 연결한다. 이를 참고해 각 요약에서 사용자에게 달라진 점과 직접 내린 판단을 먼저 설명하고, 구현 세부 사항과 확인 방법은 상세에서 설명한다.

아래 인용 블록은 경험의 제목과 요약을 비교할 때 사용하는 후보이며 사례 목록 페이지는 만들지 않는다. 긴 설명은 [대표 경험의 상세 근거](featured-case-copy.md)에 보존한다. 각 사례 아래의 편집 설명은 방문자용 요약에 포함하지 않는다.

### 사례: 요구사항 조정

> 하나의 실행 과정을 함께 보여주는 이력 화면

> 사용자가 한 작업의 진행 과정을 함께 확인할 수 있도록, 별도로 제공되던 시작과 후속 기록을 구성했습니다. PM과 API의 제약을 공유하고 페이지를 나눌 기준을 정해, 기획 의도를 구현 가능한 화면으로 구체화했습니다.

이 사례에서는 사용자에게 필요한 정보 구성을 정하고 동료와 구현 기준을 협의한 경험을 보여준다. 상세에는 선행 작업을 기준으로 페이지를 나누고 후속 기록을 그 아래에 배치한 이유, 조회 오류와 빈 이력을 구별한 기준을 설명한다. [포트폴리오 7쪽의 근거](content-and-site-direction.md#요구-조정과-ui의-정확성)를 사용한다.

### 사례: 문서 생성의 상태와 취소

> 기다리는 동안의 선택까지 고려한 문서 생성 화면

> 5~10분이 걸리는 문서 생성에서는 기다리는 동안의 안내와 선택도 설계에 포함했습니다. 생성을 계속할지 취소할지 선택하는 과정에서도 실제 처리 상태를 확인해, 사용자가 진행 상황을 알 수 있도록 했습니다.

이 사례에서는 대기 중 사용자의 선택에 따라 안내와 처리를 정한 판단을 보여준다. 상세에는 SSE 이벤트를 최종 상태로 취급하지 않은 이유, 조회 중 새 이벤트가 오거나 연결 오류가 생겼을 때 서버 상태를 확인한 방법, 배포 후 실제 상태와 화면 표시를 대조한 내용을 설명한다. [포트폴리오 11~12쪽의 근거](content-and-site-direction.md#장시간-작업과-상태-동기화)를 사용한다. 경과 시간은 생성 완료까지 남은 예상 시간이 아니다.

### 사례: 화면 정지 해결

> 대용량 응답 처리로 발생한 3~4초 화면 정지 해결

> 화면에 필요한 정보를 유지하면서도 조작을 방해하지 않는 처리 방식을 선택했습니다. 약 5 MB의 응답을 변환하는 처리를 화면 갱신과 분리해, 응답 크기와 형식을 유지한 채 3~4초 정지를 해결했습니다.

이 사례에서는 브라우저의 처리 방식을 이해하고 제약 안에서 변경을 선택한 판단을 보여준다. 상세에는 약 5 MB의 응답 크기와 형식을 유지한 조건, SharedWorker와 메인 스레드의 역할을 설명한다. [포트폴리오 5쪽의 근거](content-and-site-direction.md#화면-반응성과-실시간-데이터)를 사용한다.

### 사례: 대시보드 개선

> 자원 상태를 판단할 지표를 바로잡은 대시보드

> 사용자가 자원 상태를 판단할 수 있도록 지표의 의미와 실제 표시값을 대조해 오류를 바로잡았습니다. 필요한 구간만 추가로 조회하는 방식으로 바꾸면서, 10분 동안의 데이터 전송량도 96.5 MB에서 41 KB로 줄였습니다.

이 사례에서는 표시값을 바로잡는 판단과 반복 전송을 줄이는 판단을 함께 보여준다. 상세에는 잘못된 지표와 누락의 원인을 구분하고, 마지막 요청 이후의 값을 조회하는 방식과 실제 응답을 대조한 확인 방법을 설명한다. [포트폴리오 13쪽의 근거](content-and-site-direction.md#전송량-감소와-표시값-교정)를 사용하며 전송량 수치에는 10분이라는 비교 구간을 함께 적는다.

### 오픈소스 기여 소개

> React Router와 Outline에 기여한 수정 사항이 공식 릴리스에 반영됐습니다.
>
> React Router에서는 선택적 URL 파라미터의 매칭 오류를, Outline에서는 인라인 이미지 앞의 텍스트 삭제 오류를 재현하고 수정했습니다. 기존 동작을 유지하는 수정안을 기여했고, 각각 React Router v7.13.1과 Outline v1.2.0에 포함됐습니다.

이 문구에서 각 이름은 [React Router PR](https://github.com/remix-run/react-router/pull/14689)과 [Outline PR](https://github.com/outline/outline/pull/10759)로 연결한다. 릴리스 정보는 [기여 확인 자료](content-and-site-direction.md#외부에서-확인할-수-있는-오픈소스-기여)에 있는 공식 링크를 사용한다.

## 사실을 매력적인 설명으로 편집하는 기준

방문자가 어떤 판단을 맡길 수 있는 개발자인지 이해하도록 사실을 해석하고 선별한다. 사례 제목에는 해결한 문제나 확인된 변화를, 요약에는 그 변화를 만들 때 중요하게 본 기준과 판단을 담는다. 구현 방법과 수치는 그 판단을 뒷받침할 때 사용한다. 사실을 정확히 옮겼다는 이유만으로 소개 문구가 완성되었다고 판단하지 않는다.

자료를 검토하는 사람이 측정 원본을 확보하지 못했다는 사실은 개발자가 측정하지 않았다는 뜻이 아니다. 자료에 기록된 성과를 설명할 때 검토자의 확인 범위를 개발자의 자기평가로 바꾸지 않는다. 근거를 더 확인할 사항은 [자료 분석](content-and-site-direction.md#자료에서-확인한-경험과-근거의-한계)에서 관리한다.

수치를 쓸 때는 의미를 결정하는 대상을 문장 안에 남긴다. 대시보드 사례는 데이터 전송량과 10분이라는 비교 구간을 함께 적는다. 문서 생성 사례는 상태 판정과 취소 처리만으로도 판단이 드러나므로, 요약에 폴링 환산 수치를 추가하지 않았다. 상세에서 수치를 사용한다면 비교 조건을 함께 설명한다.

측정 여부나 조건이 해결되지 않아 결과를 단정할 수 없는 경우에는 확인된 구현과 동작으로 문장을 다시 쓴다. 실험실 결과를 운영 성과로 바꾸거나 데이터 전송량을 사용자 유지율로 설명하지 않는다. 성과의 의미를 바꾸는 조건은 해당 결과와 함께 설명한다.

## 채용 관점에서 이 방향을 권하는 근거

2026년 9월 14일 확인한 다음 일차 자료는 문제 분석, 맡은 일, 구현의 품질을 구체적으로 설명할 근거를 제공한다. 서로 다른 회사의 기대를 비교한 편집 판단이며 특정 문구가 채용 결과를 개선한다는 실험 결과는 아니다.

### 당근 로컬 콘텐츠 Frontend

공고는 문제의 원인을 추적한 경험, PM 및 동료와 요구사항을 정한 경험, 출시 이후의 성능과 운영을 함께 다룬다. 이력서와 포트폴리오에는 기여한 부분, 직접 볼 수 있는 코드나 PR, 구조를 정리할 때의 판단을 쓰도록 안내한다. 짧은 원문은 “실제로 맡아온 역할과 해결해온 문제의 복잡도”다. 원인 분석, 요구사항 조정, 오픈소스 기여를 서로 다른 증거로 보여줄 근거다. [당근 공식 공고](https://careers.daangn.com/jobs/role/7990233003/)

## 문구와 이력의 연결

2026년 9월 7일 생성된 이력서 2쪽과 포트폴리오 18쪽을 바탕으로 작성했다. 2026년 9월 14일 이력서 두 쪽과 아래 사례에 해당하는 PDF 화면을 대조했다. 자료의 사실 정리와 수치별 사용 조건은 [개발 경험 분석](content-and-site-direction.md)에 둔다.

- 첫 소개: 포트폴리오 7쪽의 작업별 목록 구성과 11~12쪽의 사용 상황에 따른 안내 및 동작을 사용자 목적에 맞는 화면 설계로 해석했다. 5쪽의 화면 정지 해결은 화면 응답 속도 개선을 뒷받침한다. 11~13쪽의 상태 확인과 표시값 교정은 처리 상태를 판정하고 올바른 값을 화면에 표시한 근거다.
- 상세 소개: 포트폴리오 7쪽과 11쪽의 판단, 7쪽의 PM 협의를 사용자의 목적과 기술적 제약 사이에서 화면의 기준을 정하는 강점으로 해석했다. 12쪽의 실제 처리 상태 확인과 13쪽의 지표 교정은 사용자가 화면을 믿고 판단할 수 있게 만드는 관심을 뒷받침한다. 브라우저와 서버의 동작을 살핀 근거는 5쪽의 SharedWorker, 12쪽의 Nginx와 14쪽의 서버 API다. 사용자 조사나 서버 전반의 전문성을 새로 주장하지 않는다.
- 화면 정지: 포트폴리오 5쪽의 처리 위치 변경, 응답 조건 유지와 배포 확인을 사용했다. 3~4초는 개선 전 화면 정지 시간이다.
- 문서 생성: 이력서 1쪽과 포트폴리오 11~12쪽의 상태 확인, 취소, 페이지 이탈과 연결 오류 처리를 사용했다. 5~10분은 문서 생성에 걸리는 시간이다.
- 대시보드: 이력서 1쪽과 포트폴리오 13쪽의 표시값 교정과 10분 전송량 비교를 사용했다.
- 요구사항 조정: 포트폴리오 7쪽의 PM 협의, 작업 단위 목록과 CSV 판정 규칙을 사용했다.
- 오픈소스: 이력서 2쪽과 [React Router PR #14689](https://github.com/remix-run/react-router/pull/14689), [Outline PR #10759](https://github.com/outline/outline/pull/10759)의 작성자와 병합 상태를 대조했다. 릴리스 반영은 [공식 릴리스 확인 기록](content-and-site-direction.md#외부에서-확인할-수-있는-오픈소스-기여)을 근거로 한다.
