# 개발자 소개 방향과 웹사이트 문구

복잡한 데이터와 작업 흐름을 다루는 서비스에서 성능과 동작의 정확성을 개선하는 프론트엔드 개발자로 소개하는 방향을 권한다. 화면의 문제를 데이터 처리와 서버 설정까지 따라가 해결한 경험, 동료와 요구사항을 조정한 경험, 오픈소스 수정 이력을 함께 보여주면 어떤 일을 맡길 수 있는지 구체적으로 전달할 수 있다.

이 문서는 [사이트의 역할과 자료 활용](../requirements.md#사이트의-역할과-자료-활용)에 맞는 소개 방향을 선택하고 웹사이트 문구를 다듬기 위한 편집 제안이다. 아래 인용 블록은 방문자에게 보여줄 한국어 초안이다. 그 밖의 설명과 근거는 문구를 선택하는 데 쓰는 자료이며, 사이트에 함께 게재하는 내용이 아니다. 소개 방향과 최종 문구는 아직 확정하지 않았다.

## 소개에서 남길 인상

첫 소개에서는 다루는 문제의 성격을 보여주고, 사례에서는 그 문제를 맡았을 때 어떻게 해결하는지 보여준다. 방문자가 기억할 중심은 실시간 데이터와 오래 걸리는 작업을 다루는 개발 경험이다. 이를 원인 분석, 협업과 배포 확인으로 뒷받침한다.

프레임워크 중심의 소개도 가능하지만 React와 TypeScript라는 이름만으로는 이력의 특징을 설명하기 어렵다. 성능 최적화만 강조하면 상태 동기화, 데이터 정확성, 요구사항 조정 경험이 덜 드러난다. 이 경험들을 함께 설명하는 현재 방향이 자료에 더 잘 맞는다.

서버 API와 배포 설정을 다룬 경험은 프론트엔드 문제를 해결한 과정에서 보여준다. 별도의 직무 이름을 늘리기보다 어떤 문제 때문에 어디까지 작업했는지 설명한다. AI를 이용하는 서비스와 문구 검사 도구도 직접 만든 기능과 그때의 판단으로 소개한다.

## 방문자에게 보여줄 문구 초안

### 홈페이지 첫 소개

> 복잡한 데이터와 작업 흐름을, 믿고 사용할 수 있는 웹으로 만듭니다.

> 실시간 차트와 장시간 작업이 있는 서비스를 개발하며 화면 멈춤, 데이터 누락, 상태 불일치를 해결해 왔습니다. 필요한 경우 서버 API와 배포 설정까지 다루고, 배포 후 동작을 확인하는 프론트엔드 개발자입니다.

이름과 `Frontend Engineer`를 함께 표시한다. 첫 문장은 지향하는 작업의 성격을 설명하고, 이어지는 문장은 이를 뒷받침하는 경험을 제시한다.

### 상세 소개

> React와 TypeScript로 데이터와 상태 변화가 많은 웹 서비스를 개발해 왔습니다. 화면의 반응 속도와 데이터의 정확성을 함께 살핍니다. 대용량 응답을 처리할 때 멈추던 화면을 개선하고, 오래 걸리는 문서 생성의 진행 상태 표시와 취소 동작을 설계했습니다.
>
> API가 제공하는 데이터와 필요한 화면이 맞지 않을 때는 PM과 제약을 공유하고 구현 방식을 조정했습니다. 서버 API와 배포 설정을 직접 다뤄 화면에서 시작된 문제를 해결하고, 배포 후에도 의도한 동작이 유지되는지 확인했습니다.
>
> 오픈소스에서도 오류를 재현하고 수정하는 일을 이어왔습니다. React Router의 URL 매칭 오류와 Outline의 텍스트 삭제 오류를 수정했고, 두 기여 모두 공식 릴리스에 반영됐습니다.

### 사례: 화면 정지 해결

> 3~4초 멈추던 화면의 데이터 처리 방식을 바꾸다

> 약 5 MB의 API 응답을 처리할 때 발생하던 화면 정지를 해결했습니다. API 호출과 데이터 변환을 SharedWorker로 옮기고, 메인 스레드는 변환된 결과로 화면을 갱신하도록 구성했습니다. 응답 크기와 형식을 유지하면서 배포 후 화면 정지 문제가 해결된 것을 확인했습니다.

### 사례: 문서 생성의 상태와 취소

> 5~10분 걸리는 작업의 진행 상태 표시와 취소 동작 설계

> 문서가 생성되는 동안 진행 상태를 확인하고 취소를 선택할 수 있도록 화면을 설계했습니다. SSE 이벤트에 따라 서버 상태를 다시 조회하고, 연결 오류가 발생했을 때도 서버 응답을 확인해 작업 상태를 판단했습니다. 페이지 이탈 확인과 취소 이후의 동작까지 구현하고 배포했습니다.

### 사례: 대시보드 개선

> 대시보드의 표시값을 바로잡고 데이터 전송량 줄이기

> 지표가 잘못 표시되거나 빠지는 원인을 찾아 조회와 변환 로직을 수정했습니다. 전체 구간을 반복해서 요청하던 방식은 마지막 요청 이후의 데이터를 가져오도록 바꿨습니다. 10분 동안의 데이터 전송량을 96.5 MB에서 41 KB로 줄이고, 실제 응답과 대조해 표시값을 확인했습니다.

### 사례: 요구사항 조정

> 따로 제공되는 작업 기록을 하나의 이력으로 보여주기

> 선행 작업과 후속 기록을 별도로 제공하는 API에 맞춰, PM과 목록 구성과 페이지 나누기 방식을 조정했습니다. 사용자가 작업 단위로 이력을 확인할 수 있도록 화면을 구성하고, CSV에도 같은 판정 규칙을 적용했습니다.

### 오픈소스 기여 소개

> React Router와 Outline의 오류를 수정했습니다.
>
> URL 매칭과 텍스트 편집에서 발생하는 오류를 재현하고, 기존 동작을 유지하는 수정안을 기여했습니다. 변경 사항은 React Router v7.13.1과 Outline v1.2.0에 포함됐습니다.

이 문구에서 각 이름은 [React Router PR](https://github.com/remix-run/react-router/pull/14689)과 [Outline PR](https://github.com/outline/outline/pull/10759)로 연결한다. 릴리스 정보는 [기여 확인 자료](content-and-site-direction.md#외부에서-확인할-수-있는-오픈소스-기여)에 있는 공식 링크를 사용한다.

## 사실을 매력적인 설명으로 편집하는 기준

방문자가 개발자의 기여와 달라진 동작을 이해하도록 사실을 선택하고 순서를 바꾼다. 기술 이름은 선택의 이유를 설명할 때 사용한다. 사례 제목에는 해결한 문제나 결과를, 요약에는 직접 바꾼 부분을 담는다. 수치가 없어도 원인 분석, 제약 안에서의 판단, 배포한 기능을 명확하게 설명할 수 있다.

자료를 검토하는 사람이 측정 원본을 확보하지 못했다는 사실은 개발자가 측정하지 않았다는 뜻이 아니다. 자료에 기록된 성과를 설명할 때 검토자의 확인 범위를 개발자의 자기평가로 바꾸지 않는다. 근거를 더 확인할 사항은 [자료 분석](content-and-site-direction.md#자료에서-확인한-경험과-근거의-한계)에서 관리한다.

수치를 쓸 때는 의미를 결정하는 대상을 문장 안에 남긴다. 대시보드 사례는 데이터 전송량과 10분이라는 비교 구간을 함께 적는다. 문서 생성 사례는 상태 판정과 취소 처리만으로도 판단이 드러나므로, 요약에 폴링 환산 수치를 추가하지 않았다. 상세에서 수치를 사용한다면 비교 조건을 함께 설명한다.

측정 여부나 조건이 해결되지 않아 결과를 단정할 수 없는 경우에는 확인된 구현과 동작으로 문장을 다시 쓴다. 실험실 결과를 운영 성과로 바꾸거나 데이터 전송량을 사용자 유지율로 설명하지 않는다. 성과의 의미를 바꾸는 조건은 해당 결과와 함께 설명한다.

## 채용 관점에서 이 방향을 권하는 근거

2026년 9월 14일 확인한 다음 일차 자료는 문제 분석, 맡은 일, 구현의 품질을 구체적으로 설명할 근거를 제공한다. 서로 다른 회사의 기대를 비교한 편집 판단이며 특정 문구가 채용 결과를 개선한다는 실험 결과는 아니다.

### 당근 로컬 콘텐츠 Frontend

공고는 문제의 원인을 추적한 경험, PM 및 동료와 요구사항을 정한 경험, 출시 이후의 성능과 운영을 함께 다룬다. 이력서와 포트폴리오에는 기여한 부분, 직접 볼 수 있는 코드나 PR, 구조를 정리할 때의 판단을 쓰도록 안내한다. 짧은 원문은 “실제로 맡아온 역할과 해결해온 문제의 복잡도”다. 원인 분석, 요구사항 조정, 오픈소스 기여를 서로 다른 증거로 보여줄 근거다. [당근 공식 공고](https://careers.daangn.com/jobs/role/7990233003/)

### Linear의 채용 및 업무 원칙

Linear는 소프트웨어의 품질과 세부 동작에 대한 관심을 강조한다. 사용자 문제를 이해하고 오래 사용할 수 있는 기반을 만들며 불필요한 절차를 늘리지 않는 원칙도 제시한다. 짧은 원문은 “getting even the smallest details right”다. 취소, 상태 재조회, 텍스트 삭제처럼 구체적인 동작을 완성한 경험을 설명할 근거다. 이 자료는 특정 직무의 합격 기준이 아니라 회사가 설명하는 업무 원칙으로 사용했다. [Linear 공식 채용 페이지](https://linear.app/careers)

## 문구와 이력의 연결

2026년 9월 7일 생성된 이력서 2쪽과 포트폴리오 18쪽을 바탕으로 작성했다. 2026년 9월 14일 이력서 두 쪽과 아래 사례에 해당하는 PDF 화면을 대조했다. 자료의 사실 정리와 수치별 사용 조건은 [개발 경험 분석](content-and-site-direction.md)에 둔다.

- 첫 소개와 상세 소개: 이력서 1쪽의 실시간 UI, API 제약 조정, 서버 API 및 배포 경험과 포트폴리오 5쪽, 7쪽, 11~14쪽을 종합했다. 화면 반응성, 표시값의 정확성과 작업 상태 처리를 중심으로 개발 경험을 요약했다.
- 화면 정지: 포트폴리오 5쪽의 처리 위치 변경, 응답 조건 유지와 배포 확인을 사용했다. 3~4초는 개선 전 화면 정지 시간이다.
- 문서 생성: 이력서 1쪽과 포트폴리오 11~12쪽의 상태 확인, 취소, 페이지 이탈과 연결 오류 처리를 사용했다. 5~10분은 문서 생성에 걸리는 시간이다.
- 대시보드: 이력서 1쪽과 포트폴리오 13쪽의 표시값 교정과 10분 전송량 비교를 사용했다.
- 요구사항 조정: 포트폴리오 7쪽의 PM 협의, 작업 단위 목록과 CSV 판정 규칙을 사용했다.
- 오픈소스: 이력서 2쪽과 [React Router PR #14689](https://github.com/remix-run/react-router/pull/14689), [Outline PR #10759](https://github.com/outline/outline/pull/10759)의 작성자와 병합 상태를 대조했다. 릴리스 반영은 [공식 릴리스 확인 기록](content-and-site-direction.md#외부에서-확인할-수-있는-오픈소스-기여)을 근거로 한다.
