# 개발자 개인 웹사이트의 구성과 제작 방식

현재 구성에는 짧은 소개와 선별한 근거를 한 페이지에서 읽고, 상세한 해결 과정은 블로그로 연결하는 방식을 적용한다. 최신 적용안과 2025~2026 시각 사례 비교는 [단일 페이지 UI, UX 조사](single-page-ui-ux.md)에 있다.

아래는 2026년 9월 14일 다중 페이지 구성을 검토하던 시점의 관찰과 권고다. 개발자의 소개 방식과 콘텐츠 관리 근거는 참고할 수 있지만, 전체 목록과 사례 상세, 내부 설명 주소 및 Markdown/MDX 비교는 현재 구현 입력에서 제외한다. 아래의 ‘이번 사이트’와 ‘현재 요구사항’은 그 조사 시점의 해석이며 이후의 단일 페이지 요구사항을 대신하지 않는다.

이 문서는 [사이트의 역할과 자료 활용](../requirements.md#사이트의-역할과-자료-활용)을 바탕으로 콘텐츠와 화면 구성을 선택할 때 참고할 리서치다. 아래의 적용 의견은 조사에서 도출한 권고이며, 확정된 요구사항을 추가하거나 바꾸지 않는다. 현재 경력에 대한 구체적인 적용은 [콘텐츠와 제작 방향](content-and-site-direction.md)에 정리했다.

## 조사 범위와 판단 기준

2026년 9월 14일에 여섯 개발자의 실제 사이트, 작성자의 제작 설명, 본인이 관리하는 소스 저장소와 공식 기술 문서를 확인했다. 유명 사이트의 모양보다 소개에서 작업과 근거까지 이어지는 방식을 비교했다.

같은 날 Codex 앱 브라우저에서 여섯 사이트의 자기소개를 다시 읽고, 어떤 관심과 강점을 경력보다 먼저 설명하는지 확인했다. Josh는 별도 About 페이지까지 읽었다. 채용 역량과 현재 이력에 연결한 해석은 [프론트엔드 채용 역량과 개발자 소개](frontend-hiring-and-positioning.md)에 둔다.

Playwright MCP로 여섯 사이트를 1440×1000 CSS px에서 열어 실제 표시와 본문을 대조했다. Emil, Paco, Anthony, Rauno와 Brittany의 사이트는 390×844 CSS px에서도 살폈다. Emil의 Sonner 제작 글도 상세 화면과 본문을 함께 확인했다. 외부 사이트를 열자마자 촬영한 이미지는 등장 효과가 끝난 화면과 달라, 텍스트 추출만으로 화면 구성을 판단하지 않았다.

이 관찰은 특정 시점과 브라우저에서 확인한 사례다. 전체 사이트의 접근성 적합성, 성능 점수, 채용 전환율과 모든 기기에서의 동작을 검증한 결과는 아니다. 디자인 엔지니어와 오픈소스 개발자 비중이 높은 표본이므로 개발자 전체의 관행으로 일반화하지 않는다.

## 실제 사이트 비교

### Emil Kowalski: 소개 다음에 작업과 제작 글

자기소개는 Design Engineer라는 직무와 현재 일하는 팀을 밝힌 뒤, 디자이너와 개발자를 위한 도구를 만들고 UI를 깊이 생각하는 관심사를 설명한다. 짧은 원문은 “how it looks, feels, behaves”다. 방문자는 UI의 모습과 느낌, 동작을 중요하게 여기는 개발자로 이해한 뒤 Sonner와 Vaul을 읽게 된다. 이는 작업을 보기 전에 그 작업을 만든 사람이 무엇에 관심을 두는지 알려주는 방식이다. [Emil의 자기소개](https://emilkowal.ski/)

이름과 직무, 현재 하는 일에 이어 Projects와 Writing을 배치한다. 프로젝트에는 이름과 짧은 설명이 있고, 글은 별도 상세 페이지로 이동한다. 현재 목록에는 Sonner와 Vaul 외에 강의와 도구도 포함된다. 흰 배경의 한 열 구성에서 글자와 여백으로 항목을 구분하며, 모바일에서도 소개와 프로젝트 순서를 유지한다. [Emil Kowalski 홈](https://emilkowal.ski/)

기술 설명은 결과를 체험하거나 볼 수 있는 자료와 판단 이유를 연결한다. Sonner 제작 글은 이름, 알림의 겹침, 높이가 다른 항목과 스와이프 등을 각각 설명하고 비교용 동작 예시와 코드를 붙인다. 완성 화면 하나로 모든 역량을 설명하지 않는다는 점이 유용하다. [Building a toast component](https://emilkowal.ski/ui/building-a-toast-component)

적용 의견: 홈페이지에서 프로젝트의 용도를 짧게 보여주고, 사례 상세에서 동작이 달라진 이유를 설명하는 방식을 참고한다. 강의 판매, 뉴스레터, 넓은 상단 여백과 모션 자체는 이번 사이트에 필요한 기능으로 간주하지 않는다.

### Paco Coursey: 만들고 있는 것과 관심사를 함께 설명

첫 소개는 “Crafting interfaces”로 시작해 소프트웨어와 웹 경험을 세밀하게 다듬고 UI의 흥미로운 동작을 실험한다는 관심을 밝힌다. 현재 역할과 과거 Vercel에서 만든 디자인 시스템, 사이트와 대시보드는 그다음에 나온다. 화면을 만드는 사람의 취향과 작업 기준이 개별 프로젝트를 묶어 준다. [Paco의 자기소개](https://paco.me/)

소개 아래에 Building, Projects, Writing을 나란히 두고 Now와 Connect로 이어진다. 링크 아래의 짧은 설명만으로 각 작업의 목적을 구별할 수 있다. 모바일 폭에서는 일부 작업 영역을 가로로 탐색하는 표현이 관찰됐다. 이름과 관심사, 작업을 한 사이트에서 연결하는 방식은 참고할 수 있지만 그 열 구성을 그대로 가져올 근거는 없다. [Paco Coursey 홈](https://paco.me/)

작성자는 2021년 개편 글에서 자신과 생각, 만들고 있는 것을 설명하는 사이트를 원했다고 썼다. 짧은 원문은 “what I’m thinking about, and what I’m building”이다. 이 글은 현재 구현을 설명하는 문서가 아니라 개인 사이트의 목적에 관한 작성자 설명이다. [Redesign 2021, 2021-11-12](https://paco.me/writing/redesign-2021)

적용 의견: 회사 경력 밖의 사이드 프로젝트와 글도 개발자를 설명하는 자료로 사용한다. 관심사 영역을 채우기 위해 취미나 작업 철학을 만들어 넣지 않는다. 읽는 순서를 유지하는 반응형 요구사항에 맞춰 목록 구성은 별도로 설계한다.

### Anthony Fu: 작업이 많은 개발자의 장기 목록

홈에서는 자신을 “a fanatical open sourceror and design engineer”라고 소개한다. 이어서 Creator, Core team과 Maintaining을 구분해 프로젝트에 대한 실제 역할을 밝히고, 자신과 다른 사람의 생산성과 만드는 즐거움을 돕는 도구에 관심이 있다고 설명한다. 프로젝트 이름이 많지만 역할과 동기가 먼저 정해져 있어 오픈소스와 도구를 만드는 사람이라는 인상으로 연결된다. [Anthony의 자기소개](https://antfu.me/)

Projects는 Current Focus부터 여러 생태계와 도구 종류별 목록으로 이어진다. 각 항목에는 이름, 설명과 실제 저장소 또는 서비스 링크가 있다. 데스크톱의 여러 열은 모바일에서 세로 목록으로 정리된다. 현재 관심 대상과 전체 작업을 함께 탐색할 수 있는 구조다. [Anthony Fu Projects](https://antfu.me/projects)

본인 저장소의 `pages/projects.md`에는 분류별 `name`, `link`, `desc`, `icon` 데이터가 들어 있다. 목록의 내용을 화면 구성과 분리해 기록하는 실제 사례다. 확인한 소스는 `6953631cf290e084494293bdab716292c55049ac`이며, 본인 README가 이 저장소를 개인 사이트라고 명시한다. [프로젝트 데이터](https://github.com/antfu/antfu.me/blob/6953631cf290e084494293bdab716292c55049ac/pages/projects.md), [저장소 설명](https://github.com/antfu/antfu.me/blob/6953631cf290e084494293bdab716292c55049ac/README.md)

적용 의견: 홈에는 선별한 작업을 보여주고 전체 목록을 별도로 관리한다. 다수의 분류, 넓은 그리드, 배경 효과와 후원 기능은 현재 콘텐츠 규모의 근거가 되지 않는다. 첫 버전의 검색과 필터 제외를 유지한다.

### Brittany Chiang: 경력과 프로젝트를 읽고 이력서로 이동

첫 소개는 “I build accessible, pixel-perfect experiences for the web.”이다. About에서는 디자인과 엔지니어링을 함께 고려하며 접근성과 세부 UI를 중요하게 생각한다고 설명하고, 디자인 시스템과 프론트엔드 플랫폼을 개발한 경험으로 이를 뒷받침한다. 특정 수정 작업보다 어떤 품질을 중요하게 여기는 개발자인지 먼저 읽힌다. 접근성 개선을 담당하므로 그 전문성을 첫 문장에 사용할 수 있는 사례다. [Brittany의 자기소개](https://brittanychiang.com/)

데스크톱에서는 왼쪽에 이름, 직무, 소개와 섹션 이동을 두고 오른쪽에 About, Experience, Projects와 Writing을 이어 놓는다. 모바일에서는 이름과 소개 뒤에 본문을 세로로 배치한다. 별도의 전체 이력서와 프로젝트 아카이브 링크가 있다. [Brittany Chiang 홈](https://brittanychiang.com/)

사이트 푸터는 Figma에서 설계하고 Next.js와 Tailwind CSS로 구현했으며 Vercel에 배포하고 Inter를 사용한다고 설명한다. 이는 작성자가 밝힌 제작 도구이며, 현재 실행 버전이나 배포 커밋까지 확인한 것은 아니다. [Brittany Chiang 제작 정보](https://brittanychiang.com/)

적용 의견: 선별한 내용과 전체 이력서의 역할을 분리하고, 경력 설명에는 실제 맡은 일을 남긴다. 홈페이지 전체를 경력 중심으로 만드는 구성, 이 사이트의 남색 배경, 두 열 배치와 마우스에 반응하는 효과는 그대로 옮기지 않는다.

### Rauno Freiberg: 화면 경험 자체로 소개하는 방식

첫 문장은 자신을 “interaction designer”라고 소개하고 현재 함께하는 Vercel과 Devouring Details를 밝힌다. 장문의 역량 설명 대신 Craft와 Projects로 연결하고, 실제 화면의 표현과 동작으로 직무의 성격을 전달한다. 이 방식은 시각적 작업 자체가 강한 근거일 때 성립한다. 현재 이력에 같은 직무를 붙이거나 대형 소개 화면을 도입할 근거는 아니다. [Rauno의 자기소개](https://rauno.me/)

현재 화면은 큰 자기소개와 도형을 넓은 영역에 배치하고 옆의 작업 화면으로 이어지는 구성이다. 본문에는 Craft, Projects, Field Notes, 과거 연도 사이트와 외부 연결이 있다. 모바일 폭에서도 가로 방향으로 이어지는 화면을 확인했다. 텍스트만 읽으면 짧은 링크 모음처럼 보이지만 실제 화면의 점유 면적과 이동 방식은 훨씬 강하다. [Rauno Freiberg 홈](https://rauno.me/)

적용 의견: 개인 홈에서 별도 작업과 과거 사이트로 연결하는 역할만 참고한다. 큰 소개 화면과 가로 탐색을 이번 사이트의 기본 배치 참고로 삼으면 [시각적 방향](../requirements.md#시각적-방향)과 [접근성과 반응형 동작](../requirements.md#접근성과-반응형-동작)에 맞지 않는다. 제안서의 간결한 사이트라는 설명만으로 시각적 적합성을 판단할 수 없다.

### Josh W. Comeau: 설명하는 능력을 직접 보여주는 글

About에서는 웹 개발을 시작한 시점과 엔지니어 및 강의 경력을 짧게 설명한 뒤, 현재는 개발자를 돕는 독립 제작자로 활동한다고 밝힌다. 짧은 원문은 “empowering up-and-coming software developers”다. 이어지는 직접 조작할 수 있는 예시, 오픈소스와 교육 활동이 이 목적을 뒷받침한다. 다른 사례처럼 첫 문장을 전문 영역의 표어로만 쓰지 않고, 과거 경력에서 현재의 목적까지 이야기로 연결한다. [Josh의 자기소개](https://www.joshwcomeau.com/about-josh/)

홈페이지는 글과 튜토리얼을 중심으로 구성하고 주제별 탐색과 인기 글로 이어진다. 구름 형태의 장식, 색상과 글의 분위기가 강한 개성을 만든다. 이 구조는 글이 주된 작업인 개발자에게 맞는 사례다. [Josh W. Comeau 홈](https://www.joshwcomeau.com/)

제작 설명에서는 MDX로 본문에 React 예시를 넣고, 글과 메타데이터를 파일로 관리해 커밋한다고 밝힌다. 기존 강의 플랫폼과 기술을 맞추려는 이유도 설명한다. 글에 적힌 Next.js와 React의 베타 버전 목록은 해당 개편의 기록이며 현재 권장 버전으로 읽으면 안 된다. 본문은 2024-09-24 발행, 2026-05-05 갱신으로 표시되어 있다. [How I Built My Blog, 2024 App Router Edition](https://www.joshwcomeau.com/blog/how-i-built-my-blog-v2/)

적용 의견: 사례를 설명할 때 정적인 글로 부족한 부분에만 비교 도식이나 조작 가능한 예시를 고려한다. 이를 첫 버전의 필수 기능으로 추가하거나 기존 블로그를 개인 사이트로 이전하는 근거로 사용하지 않는다.

## 다른 개발자는 어떻게 제작하는가

내용의 성격에 따라 구현 방식이 달라진다. 비교 사례가 같은 프레임워크나 템플릿으로 수렴하지 않으므로, 겉모습을 이유로 기술을 선택할 수 없다.

### 반복 목록은 데이터로 관리

Anthony의 사이트는 프로젝트 정보를 Markdown 앞부분의 구조화된 데이터로 관리하고, `package.json`의 빌드 명령에서 `vite-ssg`로 페이지를 생성한다. Vue와 Markdown을 함께 사용하는 개인 사이트의 제작 사례다. 정확한 설치 버전은 잠금 파일로 결정되므로 선언 범위를 설치 버전으로 단정하지 않는다. [프로젝트 데이터](https://github.com/antfu/antfu.me/blob/6953631cf290e084494293bdab716292c55049ac/pages/projects.md), [빌드 명령](https://github.com/antfu/antfu.me/blob/6953631cf290e084494293bdab716292c55049ac/package.json)

이번 사이트에서는 이름과 요약, 외부 서비스 주소, 내부 설명 주소를 구분해 관리하는 데 적용할 수 있다. 구체적인 파일 형식과 라이브러리는 정하지 않았다.

### 긴 설명은 편집과 시연의 필요에 맞춰 관리

Josh는 글을 전부 React 컴포넌트로 작성할 때 문단 편집과 목록용 정보 추출이 불편했다고 설명한다. MDX로 옮기면서 본문 편집과 필요한 React 예시를 함께 사용한다. 글 안에 조작 가능한 예시를 넣기 위한 선택이며 단순한 소개 페이지에도 같은 도구 전체가 필요한 것은 아니다. [Josh의 콘텐츠 관리 설명](https://www.joshwcomeau.com/blog/how-i-built-my-blog-v2/#content-management)

이번 사이트에서는 일반 사례를 Markdown으로 편집할지, 실제로 조작 가능한 예시가 필요한 사례에 MDX를 사용할지 비교할 수 있다. CMS, 데이터베이스와 실시간 API가 필수라는 근거는 없다.

### 현재 사이트와 과거 소스를 구별

Paco의 `pacocoursey/paco` README는 “outdated personal site from 2020”이라고 명시한다. 확인한 소스는 `e011620d0fca28fb25d9877c1d739feaddd06b53`이며 Next.js와 CSS Modules 사용을 설명한다. 이 저장소로 현재 `paco.me`의 버전이나 구성 요소를 단정하면 안 된다. [Paco의 구버전 저장소 설명](https://github.com/pacocoursey/paco/blob/e011620d0fca28fb25d9877c1d739feaddd06b53/README.md)

Brittany의 현재 사이트는 본문에서 이전 Gatsby 포트폴리오를 별도 프로젝트로 소개한다. 현재 사이트의 푸터는 Next.js 사용을 설명하므로 과거 포트폴리오의 소스를 현재 구현과 혼동하지 않는다. [현재 사이트의 프로젝트와 제작 설명](https://brittanychiang.com/)

## 제안서의 시각적 원칙을 뒷받침하는 자료

여백과 글자로 내용을 구분하고 불필요한 움직임을 줄이는 방향은 실제 사례와 공식 지침이 함께 뒷받침한다. 특정 색, 글꼴이나 간격 값을 그대로 채택한다는 뜻은 아니다.

- Emil의 글은 움직임에 목적이 있어야 한다고 설명한다. 짧은 원문은 “making sure your animations have a purpose”다. Primer 역시 기능이나 설명을 더하지 않는 장식 움직임을 제한하고, 움직임 감소 설정을 존중하도록 안내한다. 두 자료는 움직임의 필요성을 먼저 판단해야 한다는 점에서 일치한다. [Emil의 모션 설명](https://emilkowal.ski/ui/you-dont-need-animations), [Primer의 모션 지침](https://primer.style/accessibility/design-guidance/motion-and-animation/)
- Primer는 읽는 순서를 존중하고 화면이 줄어도 기능을 유지하도록 안내한다. Paco의 모바일 가로 탐색이나 Rauno의 화면 구성을 그대로 도입하는 것보다 이번 콘텐츠에 맞게 세로 읽기 순서를 정할 근거다. [Primer Layout](https://primer.style/product/getting-started/foundations/layout/)
- Geist는 보조 배경을 필요한 구분에 제한하고, 글자 스타일을 크기, 줄 높이, 자간과 굵기의 조합으로 정의한다. 역할과 조합을 참고할 수 있지만 Geist 글꼴과 색상표 자체가 선택된 것은 아니다. [Geist Colors](https://vercel.com/geist/colors), [Geist Typography](https://vercel.com/geist/typography)

## 교차 확인에서 얻은 결론과 한계

Emil과 Paco는 자기소개에서 작업으로 곧바로 이어지고, Brittany는 선별한 작업과 전체 이력서를 구분한다. Anthony는 많은 작업을 구조화된 목록으로 관리한다. 이를 함께 보면 홈페이지는 선별한 작업을 고르는 곳으로 만들고, 목록과 상세에 다른 읽기 깊이를 주는 방향이 타당하다. 채용 성과를 높인다는 인과관계까지 입증한 자료는 아니다.

제안서에 적힌 외부 사이트 설명은 링크 연결과 콘텐츠 순서를 이해하는 데 도움이 되지만, 현재 화면을 대신하지 못한다. 특히 Rauno의 배치와 Paco의 오래된 소스는 무엇을 참고할 수 있는지 구분해야 한다. 최신 트렌드라는 이유만으로 장식이나 유료 도구를 선택할 근거도 없다.

현재 요구사항은 유지할 수 있다. 확정이 필요한 것은 다른 개발자의 스타일이 아니라 이 사이트의 첫 프로젝트, 사례에 사용할 근거와 화면, 언어, 실제 기본 표현과 구현 기술이다.
