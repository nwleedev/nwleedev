# 개발 경험을 소개 콘텐츠로 구성하는 방법

홈페이지는 개발자의 역량과 서비스 개발 및 협업에서 기대할 기여를 전달하는 곳으로 사용한다. 이 문서에서 확인한 화면 설계와 성능 및 동작 개선 경험은 그 설명을 뒷받침할 근거다. 실제 홈페이지의 문구 구성은 [한국어 전체 초안](homepage-copy.md)에서 확인하고, 아래의 구현 방식과 수치 조건은 사실 확인 및 상세 설명에 사용한다.

이 문서는 [사이트의 역할](../requirements.md#사이트의-역할과-자료-활용)에 맞는 콘텐츠와 제작 방향을 선택하기 위한 리서치다. 사실로 확인한 내용과 편집 제안, 추가 결정이 필요한 사항을 구분한다. [외부 사이트 비교](developer-websites.md)는 이 구성의 참고 근거다.

## 자료에서 확인한 경험과 근거의 한계

2026년 9월 14일에는 `proposal.md`와 9월 7일 생성 PDF를 확인했다. 9월 19일에는 새로 생성된 이력서 PDF 2쪽과 9월 7일 생성 포트폴리오 PDF 18쪽을 다시 읽고 주요 수치 및 도식을 화면과 대조했다. 아래 회사 업무와 성과는 제공된 PDF의 기록이며 운영 코드나 측정 원본을 독립적으로 확인한 결과가 아니다. 새 디자인 리서치의 분석과 단일 페이지 적용안은 [UI, UX 조사](single-page-ui-ux.md)에 있다.

### 화면 반응성과 실시간 데이터

포트폴리오 5쪽은 약 5 MB 응답을 호출하고 변환할 때 발생한 3~4초 화면 정지를 다룬다. API 호출과 변환을 SharedWorker로 옮기고 메인 스레드는 결과로 화면을 갱신한다. 응답 크기와 형식을 유지하면서 배포 후 정지 문제가 해결된 것을 확인했다고 기록되어 있다.

6쪽은 새로고침 이후 REST 이력과 스트림 수신값을 같은 캐시 큐에 합치고 시간 단위를 맞추는 작업이다. 분할된 JSON의 미완성 부분을 보관해 다음 청크와 합치는 처리도 나온다. 단순히 차트를 그린 경험보다 데이터가 끊기거나 누락되는 조건을 해결한 경험으로 설명할 수 있다.

편집 제안: 화면 정지 해결은 [첫 소개에서 설명한 화면 설계 역량](developer-introduction.md#홈페이지-첫-소개)을 뒷받침하는 기술적 경험으로 제시한다. 사례에서는 문제를 재현하는 조건, 처리 위치를 바꾼 이유와 배포 확인을 보여준다. 전후 처리 시간, FPS나 INP는 원자료에 없으므로 새 성과 수치로 만들지 않는다.

### 장시간 작업과 상태 동기화

포트폴리오 11~12쪽은 5~10분 걸리는 문서 생성, 페이지 이탈과 취소, SSE 단계 이벤트에 따른 상태 재조회를 설명한다. 이벤트를 최종 상태로 취급하지 않고 서버 응답으로 상태를 판단한다. 조회 중 추가 이벤트가 오면 진행 중인 요청 뒤에 다시 조회하고, 연결 오류에서도 서버 상태를 확인한다.

이력서 1쪽은 3초 폴링과 이벤트 기반 조회를 비교한다. 5~10분을 3초 간격으로 조회하면 100~200회에 해당하고, 자료에 기록된 이벤트 기반 상태 API 요청은 10회 이하다. 이 비교만으로 이전 운영 환경이 실제로 계속 폴링했다고 단정할 수는 없다.

편집 제안: 대기 중 페이지를 이동하거나 작업을 취소하려는 사용자의 선택에 따라 어떤 안내와 동작을 제공했는지 먼저 설명한다. 취소하지 않기로 선택하면 작업 상태를 계속 보여주는 처리가 그 예다. 연결 오류에 따른 서버 상태 재조회와 두 단계 Nginx의 버퍼링 해제는 이벤트 전달과 상태 판단을 설명할 때 사용한다.

조회 횟수를 비교할 때는 작업 시간, 비교 기준과 상태 판정 방식을 함께 보여준다. 문서 생성 시간 자체가 짧아졌다는 뜻으로 쓰지 않는다.

### 전송량 감소와 표시값 교정

포트폴리오 13쪽과 이력서 1쪽은 대시보드의 전체 구간 재요청을 마지막 요청 시각 이후 데이터 조회로 바꿔 10분 기준 `96.5 MB → 41 KB`로 줄였다고 기록한다. 포트폴리오에는 지표 이름과 라벨 불일치, 비율 계산 오류와 시계열 누락을 서로 다른 원인으로 교정한 내용도 있다.

14쪽은 브라우저에 Prometheus 접속 정보와 원본 PromQL을 전달하지 않는 서버 API를 설명한다. 화면에 필요한 정보로 응답을 변환하고 실제 연결과 브라우저에 전달되는 내용을 확인했다고 기록한다.

편집 제안: 사례의 첫 결과에는 반드시 10분이라는 비교 구간과 데이터 전송량이라는 대상을 함께 적는다. 포트폴리오 소개에 있는 약 90%라는 수치와 혼합하거나, 응답 한 건의 크기나 로딩 시간 개선으로 바꾸지 않는다. 측정 시작 조건, 초기 조회 포함 여부, 압축 여부와 반복 횟수는 추가 근거가 있어야 설명할 수 있다.

### 요구 조정과 UI의 정확성

포트폴리오 7쪽은 선행 작업과 후속 기록을 별도로 주는 API에 맞춰 목록과 페이지 나누기 방식을 조정하고 화면과 CSV에 같은 판정 규칙을 적용한 사례다. 8쪽은 선택 목록의 표시 위치, 전체화면 팝업과 키보드 조작을 다룬다. 10쪽은 요구사항과 회의 내용을 화면 후보로 구체화한 경험이다.

15쪽은 브라우저의 인증 정보와 만료된 서버 세션이 어긋난 문제를 재현하고, 보호 화면 표시 전 확인과 실행 중 인증 실패에 같은 복구 원칙을 적용한 사례다. 담당 범위는 원인 분석, 공통 복구 설계, 구현과 QA 환경 배포로 기록되어 있다.

편집 제안: 사용 기술의 개수를 늘리기보다 어떤 조건을 확인하고 어떤 동작을 유지했는지 설명한다. 사례별 담당 범위와 팀에서 조정한 일을 구분하면 직접 수행한 판단이 드러난다.

### 다른 수치의 사용 범위

포트폴리오 9쪽의 `4.87 MB → 약 0.55 MB`는 데스크톱, 태블릿과 모바일용 배너 파일 세 개의 합계다. 이력서에는 약 548 KB로 적혀 있다. 이를 방문자 한 명의 다운로드량이나 로딩 시간으로 소개하면 측정 대상이 달라진다.

이력서에 있는 E2E 시나리오 수와 배포 시간, QA 기간도 각각 검사 범위와 작업 조건을 설명할 때만 쓸 수 있다. 서로 다른 프로젝트의 숫자를 모아 하나의 성능 향상 지표처럼 제시하지 않는 구성을 권한다.

## 외부에서 확인할 수 있는 오픈소스 기여

두 기여는 PR 병합 여부와 릴리스 기록을 각각 확인할 수 있다. 홈페이지의 간결한 근거로 우선 사용하고, 필요하면 상세 사례에서 재현과 호환성 판단을 설명할 수 있다. 다음 날짜는 GitHub의 UTC 기록이다.

### React Router

PR #14689는 구분자 없이 이어지는 URL까지 선택적 매개변수로 잘못 매칭하는 문제를 수정하며 2026-01-21에 병합됐다. PR에는 기존 점 접미사 동작을 유지하기 위한 처리도 설명되어 있다. 릴리스 `react-router@7.13.1`은 2026-02-23 발행이고, 이 태그의 변경 기록에 #14689가 포함된다. 짧은 원문은 “optional params matching without a "/" separator”다. [PR #14689](https://github.com/remix-run/react-router/pull/14689), [v7.13.1 변경 기록](https://github.com/remix-run/react-router/blob/react-router%407.13.1/CHANGELOG.md), [공식 릴리스](https://github.com/remix-run/react-router/releases/tag/react-router%407.13.1)

편집 제안: 오류 재현, 기존 동작 유지와 릴리스 반영을 연결한다. 병합과 릴리스 날짜를 한 날짜로 합치거나 라이브러리 전체를 설계한 것으로 표현하지 않는다.

### Outline

PR #10759는 인라인 이미지 앞의 마지막 글자를 Delete 또는 Backspace로 지우지 못하는 문제를 수정하며 2025-12-03에 병합됐다. 표 안팎과 일반 텍스트 삭제를 확인하는 절차가 PR에 있다. 2026-01-06 발행된 v1.2.0 릴리스의 `New Contributors`에 이 PR이 명시되어 있다. [PR #10759](https://github.com/outline/outline/pull/10759), [Outline v1.2.0](https://github.com/outline/outline/releases/tag/v1.2.0)

편집 제안: 이미지 인접 위치에서의 삭제 문제와 기존 텍스트 편집 유지라는 구체적인 결과를 쓴다. 회사 사례의 수치와 달리 방문자가 원문에서 기여를 확인할 수 있다는 장점이 있다.

## 웹에서 설명하는 구성 제안

다음은 최종 게재 문구나 출시 목록이 아니라, 자료를 사이트의 읽기 순서에 맞게 편집하는 제안이다. [페이지별 내용](../requirements.md#페이지별-내용)의 구성을 전제로 한다.

### 첫 소개와 프로젝트

첫 소개와 상세 소개, 사례 제목 및 요약은 [개발자 소개 방향과 웹사이트 문구](developer-introduction.md)에서 비교한다. 방문자에게 보여줄 문구와 작성용 근거를 구분하며, 이 문서의 수치 사용 조건과 자료 확인 범위를 자기소개에 그대로 옮기지 않는다. 언어별 제작 순서는 [문구 관리와 언어](../requirements.md#문구-관리와-언어)를 따른다.

소개 아래에는 프로젝트의 이름, 해결하려는 문제와 제작 내용을 보여주는 구성을 권한다. 설명은 같은 페이지에서 읽게 하고, 서비스가 준비되면 이용 링크를 소스 링크와 구분해 추가한다. 내부 프로젝트 상세 페이지는 만들지 않는다.

이력서 2쪽에는 한국어 문구 검사 도구를 포함한 작업 문서 도구, 오프라인 번역 웹 서비스와 일기 관리 및 분석 팀 프로젝트가 있다. 이들은 프로젝트 후보를 찾는 자료이며, 첫 버전에 모두 싣는다는 결정은 아니다. 제공 자료만으로 각 서비스의 현재 접속 가능 여부와 실제 주소를 확정할 수 없다. 추가로 확인한 번역 서비스 저장소와 설명 초안은 [홈페이지 연결 콘텐츠](homepage-content.md#issnuta)에 있다.

오프라인 번역은 브라우저 추론과 작업 분리, 문구 검사 도구는 모호한 표현의 탐지와 문맥 판단, 일기 서비스는 팀 단위 출시 경험을 설명할 수 있다. 첫 버전에는 개인 메모 앱과 Issnuta를 함께 소개하기로 했으며, [홈페이지 연결 콘텐츠](homepage-content.md)에 개발자의 관심과 판단을 설명하는 초안이 있다. 현재 방문자가 사용할 수 있는 서비스는 없으므로 [프로젝트 소개 결정](../decisions/project-availability.md)에 따라 실제 서비스는 준비된 뒤 연결한다.

### 홈페이지의 대표 사례 후보

홈페이지에 소개할 네 사례는 [대표 사례 선정](../decisions/featured-cases.md)을 따른다. 작업별 이력 구성과 문서 생성은 사용자에게 필요한 정보와 조작을 설계한 근거로, 화면 정지와 대시보드 개선은 기술적 원인을 분석하고 개선한 근거로 연결한다. 제목과 요약, 상세에 남길 판단은 [사례 문구](developer-introduction.md#대표-사례-문구의-구성)에서 관리한다.

실시간 차트의 새로고침 복구, 만료 세션 복구와 키보드 조작은 향후 대표 경험을 교체하거나 블로그 글을 구성할 때 참고할 자료로 남긴다. 전체 사례 목록은 만들지 않는다. 오픈소스 기여는 요구사항에 따라 홈페이지의 별도 영역에서 소개한다.

### 상세 사례와 시각 자료

상세한 배경, 선택 이유, 구현과 검증은 홈페이지에 싣지 않는다. 다음 도식 후보는 긴 설명을 편집하거나 향후 블로그 글을 작성할 때 참고할 자료이며 제작이 확정된 산출물이 아니다. 홈페이지에는 결과와 그 조건, 맡은 역할만 간결하게 남긴다.

- 화면 정지 사례: API, SharedWorker와 메인 스레드가 각각 수행하는 작업을 웹에서 새로 그린 도식으로 설명한다.
- 문서 생성 사례: 이벤트 수신, 진행 중인 조회, 추가 조회와 서버의 최종 응답을 시간 순서로 표시한다.
- 실시간 차트 사례: REST 이력이 들어오는 시점과 스트림 값이 합쳐지는 지점을 구분한다.
- 오픈소스 사례: 필요한 최소 재현 입력과 기대 결과를 관련 PR에 연결한다.

회사 사례는 [글과 새 기술 도식으로 구성하는 결정](../decisions/featured-cases.md#사례의-설명-방식)을 따른다. 새로 만든 도식은 확인된 기술 관계를 설명하는 자료이며, 실제 운영 화면이나 측정 기록으로 제시하지 않는다.

### 이력서와 글의 역할

이력서는 최신 문서로 연결한다. 웹 이력서 페이지나 PDF의 경력을 복제한 영역은 만들지 않는다. 홈페이지의 소개와 선별한 경험은 개발자의 강점을 설명하고, 전체 경력 사실은 이력서에서 확인하게 한다.

글은 실제로 쓴 글 가운데 현재 전문 영역을 보충하는 글을 선별해 기존 블로그로 연결한다. 2026년 9월 15일에는 블로그 목록과 글 두 편의 본문을 확인해 [홈페이지에 연결할 글 후보](homepage-content.md)를 정리했다. 전체 글을 비교한 선정이나 최종 게재 결정은 아니다.

## 제작 방식에 대한 조사

소개와 선별한 경험은 한 페이지의 미리 생성한 콘텐츠로 제공하고, 실제 애플리케이션은 서브도메인에서 연결하는 구성을 권한다. 단일 페이지는 클라이언트 렌더링 SPA와 같은 뜻이 아니다. 구체적인 프레임워크 선택은 별도 결정이다.

### JSON 문구 관리와 FSD 구성

언어별 JSON을 한 곳에 모으는 방식은 [문구 관리와 언어 요구사항](../requirements.md#문구-관리와-언어)에 맞는다. FSD 적용과 실제 저장 위치는 [FSD 구조와 문구 저장 위치](../decisions/terms-storage.md)에서 정한다. 다음은 2026-09-14에 확인한 공식 문서 근거다.

- FSD의 Layers 문서는 Shared에 슬라이스를 두지 않고 세그먼트를 직접 둔다고 설명한다. `i18n`은 번역 설정과 전체 번역 문자열을 위한 세그먼트의 예시이며, 추가 세그먼트도 허용한다. [FSD Layers](https://feature-sliced.design/docs/reference/layers)
- Slices and segments 문서는 “You can also create custom segments.”라고 명시하고, 특히 Shared와 App에서 사용자 정의 세그먼트를 사용할 수 있다고 설명한다. 따라서 `shared/terms`는 FSD가 지정한 필수 이름이 아니라 이 사이트의 문구 관리 목적에 맞춘 이름이다. [FSD Slices and segments](https://feature-sliced.design/docs/reference/slices-segments)
- next-intl은 “agnostic to how you store messages”라고 설명하고, 설정에서 JSON을 불러오는 예를 제공한다. 예제의 `messages` 폴더명과 라이브러리에 전달하는 `messages` 설정 항목은 구별해야 한다. 이 사례는 저장 위치를 직접 지정할 수 있다는 근거이며, next-intl 채택 결정은 아니다. [next-intl Messages](https://next-intl.dev/docs/usage/configuration#messages)

세 자료를 비교하면 FSD의 레이어 구성과 문구 저장 폴더의 이름을 따로 결정할 수 있다. 번역 설정의 실제 위치와 API 사용법은 이후 선택할 기술에 맞춰 확인해야 한다.

### 현재 저장소에서 확인되는 범위

작업을 시작한 `main`의 `811f9f3`에는 `.gitignore`, `AGENTS.md`, `docs/designs/README.md`, `docs/dev/README.md`만 추적되어 있었다. 따라서 이 브랜치에서 재사용할 라우터, CSS 변수, 글꼴, 이미지 처리, 웹 이력서와 구성 요소 구현은 확인되지 않았다. 다른 작업 브랜치나 운영 사이트에도 구현이 없다는 뜻은 아니다.

제안서의 기존 구현 조사 항목은 이후 기술 선택과 구현 준비에서 확인해야 한다. 현재 브랜치에 설정이 없다는 이유로 프레임워크, 검사 도구와 디자인 값을 자동으로 추가할 수는 없다.

### 정적 제공 방식의 후보

- Next.js 공식 문서는 `output: 'export'`로 주소별 정적 파일을 생성하는 방식을 설명한다. React 기반 콘텐츠에 사용할 수 있지만 요청 시 서버 기능이 필요한 경우에는 제약을 확인해야 한다. [Next.js Static Exports](https://nextjs.org/docs/app/guides/static-exports)
- React Router 공식 문서는 URL 목록 또는 데이터로 정한 주소를 빌드 시 미리 렌더링하는 방식을 설명한다. 현재는 소개 페이지의 정적 제공 후보로만 비교하며 프로젝트와 사례 상세 주소를 만들 근거로 사용하지 않는다. [React Router Pre-Rendering](https://reactrouter.com/how-to/pre-rendering)
- Astro 공식 문서는 콘텐츠 컬렉션으로 Markdown 등의 내용을 불러오고 구조를 검사하는 방식을 설명한다. 읽는 콘텐츠가 중심인 사이트의 관리 방식 후보로 비교할 수 있다. [Astro Content Collections](https://docs.astro.build/en/guides/content-collections/)

세 자료는 2026-09-14에 확인한 공식 기능 설명이다. 특정 버전 설치나 의존성 추가를 결정한 것은 아니다. 작성 편의, 필요한 조작 예시, 기존 프로젝트와 공유할 기술, 배포 조건을 정한 다음 선택해야 한다. 외부 개발자의 사이트가 사용한다는 이유만으로 Next.js, MDX나 스타일 라이브러리를 고르지 않는다.

### 단일 페이지의 콘텐츠 관리

프로젝트의 이름, 요약, 현재 활동과 선택적인 서비스 및 소스 URL을 관리하고, 경험은 제목, 판단, 결과와 조건 및 근거 링크를 구별하는 안을 권한다. 항목별 내부 설명 주소나 긴 본문은 추가하지 않는다. 구조화된 목록을 문구 및 표시 코드와 분리하는 참고 사례는 [Anthony의 데이터 관리 방식](developer-websites.md#반복-목록은-데이터로-관리)에 있다.

짧은 소개 문구는 확정된 JSON 저장 방식을 사용한다. 긴 글을 위한 Markdown/MDX, CMS나 관리자 화면은 현재 범위에 필요하지 않다. 조작형 시연이 필요해지면 소개에 보태는 의미와 별도 블로그의 역할부터 확인한다.

## 현재 기준으로 다시 확인한 웹 원칙

확정된 접근성과 이동 원칙은 유지할 수 있다. 구체적인 값과 동작은 실제 화면으로 확인해야 한다.

- WCAG 2.2는 2024-12-12 W3C 권고본을 확인했다. 4.5:1 텍스트 대비, 200% 글자 확대, 키보드 조작, 보이는 포커스와 포커스 가림, 최소 대상 크기 외에도 적용되는 A와 AA 항목을 확인해야 한다. 24×24 CSS px에는 인라인 링크 등 명시된 예외가 있어 모든 링크에 같은 박스를 강제한다는 뜻은 아니다. [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- 다중 페이지를 전제했던 URL 구성과 페이지 전환 API 비교는 현재 구현 입력에서 제외한다. 기본 앵커 탐색과 움직임 감소 설정의 적용안은 [단일 페이지 UX](single-page-ui-ux.md#ux와-조작-반응)를 따른다.

## 아직 필요한 결정과 그 영향

문서화와 사례 후보 비교는 가능하지만, 실제 출시 콘텐츠와 디자인 값을 확정하려면 [아직 정하지 않은 사항](../requirements.md#아직-정하지-않은-사항)에 대한 판단이 필요하다.

- [언어별 제작 순서](../requirements.md#문구-관리와-언어)는 한국어 웹사이트 제작 후 영어 문구를 구성하는 것으로 정했다. 한국어 화면을 먼저 설계하고, 영어 버전을 추가할 때 영어 문구로 글꼴과 메뉴 폭을 다시 확인한다. 두 언어를 제공할 때의 기본 언어와 언어별 주소 구성은 아직 정하지 않았다.
- 첫 버전의 프로젝트와 소스 링크는 [프로젝트 소개 결정](../decisions/project-availability.md)을 따른다. 두 프로젝트를 함께 소개하고, 메모 앱은 추후 소스 URL을 추가할 수 있게 한다. 이용 링크는 서비스 준비 후 추가한다.
- 회사 사례의 글과 도식은 확인된 기술 관계를 기준으로 구성한다. 새로운 성과 수치를 추가하려면 그 수치의 조건과 근거를 확인해야 한다.
- 글꼴과 강조색, 테마, 본문 폭과 간격은 첫 소개, 프로젝트 항목과 네 경험 요약을 배치해 본 뒤 정해야 한다.
- 구현 기술과 배포 조건은 단일 페이지의 정적 제공, JSON 문구 연결과 이미지 제공 방법을 결정한다.

첫 소개부터 프로젝트의 시작까지의 화면과 전체 페이지를 실제 한국어로 비교하는 안을 권한다. 소개, 프로젝트 목적, 경험의 수치 조건과 외부 링크를 차례로 읽고 이해할 수 있는지 확인한다. 구체적인 비교안과 구현 순서는 [UI, UX 조사](single-page-ui-ux.md)와 [플랜](../plan.md)에 있다.
