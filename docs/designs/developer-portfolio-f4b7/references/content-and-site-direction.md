# 개발 경험을 소개 콘텐츠로 구성하는 방법

실시간 데이터와 오래 걸리는 작업을 다루면서 화면 문제의 원인을 찾고, API 제약을 조정하며, 배포 후 달라진 동작을 확인한 경험을 중심에 두는 것이 적합하다. 홈페이지에는 소개와 실제 작업을 선별하고, 기술적 판단은 사례 상세에서 설명하는 구성을 권한다.

이 문서는 [사이트의 역할](../requirements.md#사이트의-역할과-자료-활용)에 맞는 콘텐츠와 제작 방향을 선택하기 위한 리서치다. 사실로 확인한 내용과 편집 제안, 추가 결정이 필요한 사항을 구분한다. [외부 사이트 비교](developer-websites.md)는 이 구성의 참고 근거다.

## 자료에서 확인한 경험과 근거의 한계

2026년 9월 14일에 `proposal.md`, 2026년 9월 7일 생성된 이력서 PDF 2쪽과 포트폴리오 PDF 18쪽을 확인했다. 이력서 전체와 포트폴리오의 주요 수치 및 도식을 화면으로 대조했다. 다음의 회사 업무와 성과는 제공된 PDF의 기록이며 운영 코드나 측정 원본을 독립적으로 확인한 결과가 아니다.

### 화면 반응성과 실시간 데이터

포트폴리오 5쪽은 약 5 MB 응답을 호출하고 변환할 때 발생한 3~4초 화면 정지를 다룬다. API 호출과 변환을 SharedWorker로 옮기고 메인 스레드는 결과로 화면을 갱신한다. 응답 크기와 형식을 유지하면서 배포 후 정지 문제가 해결된 것을 확인했다고 기록되어 있다.

6쪽은 새로고침 이후 REST 이력과 스트림 수신값을 같은 캐시 큐에 합치고 시간 단위를 맞추는 작업이다. 분할된 JSON의 미완성 부분을 보관해 다음 청크와 합치는 처리도 나온다. 단순히 차트를 그린 경험보다 데이터가 끊기거나 누락되는 조건을 해결한 경험으로 설명할 수 있다.

편집 제안: 소개에서는 실시간 화면의 끊김과 상태 문제를 해결한 경험을 한 문장으로 요약한다. 사례에서는 문제를 재현하는 조건, 처리 위치를 바꾼 이유와 배포 확인을 보여준다. 전후 처리 시간, FPS나 INP는 원자료에 없으므로 새 성과 수치로 만들지 않는다.

### 장시간 작업과 상태 동기화

포트폴리오 11~12쪽은 5~10분 걸리는 문서 생성, 페이지 이탈과 취소, SSE 단계 이벤트에 따른 상태 재조회를 설명한다. 이벤트를 최종 상태로 취급하지 않고 서버 응답으로 상태를 판단한다. 조회 중 추가 이벤트가 오면 진행 중인 요청 뒤에 다시 조회하고, 연결 오류에서도 서버 상태를 확인한다.

이력서 1쪽은 3초 폴링과 이벤트 기반 조회를 비교한다. 5~10분을 3초 간격으로 조회하면 100~200회에 해당하고, 자료에 기록된 이벤트 기반 상태 API 요청은 10회 이하다. 이 비교만으로 이전 운영 환경이 실제로 계속 폴링했다고 단정할 수는 없다.

편집 제안: 조회 횟수와 함께 작업 시간, 비교 기준과 상태 판정 방식을 보여준다. 문서 생성 시간 자체가 짧아졌다는 뜻으로 쓰지 않는다. 화면 이탈 확인, 취소 거절 시 추적 유지와 두 단계 Nginx의 버퍼링 해제는 별도 판단을 설명할 재료다.

### 전송량 감소와 표시값 교정

포트폴리오 13쪽과 이력서 1쪽은 대시보드의 전체 구간 재요청을 마지막 요청 시각 이후 데이터 조회로 바꿔 10분 기준 `96.5 MB → 41 KB`로 줄였다고 기록한다. 포트폴리오에는 지표 이름과 라벨 불일치, 비율 계산 오류와 시계열 누락을 서로 다른 원인으로 교정한 내용도 있다.

14쪽은 브라우저에 Prometheus 접속 정보와 원본 PromQL을 전달하지 않는 서버 API를 설명한다. 화면에 필요한 정보로 응답을 변환하고 실제 연결과 브라우저에 전달되는 내용을 확인했다고 기록한다.

편집 제안: 사례의 첫 결과에는 반드시 10분이라는 비교 구간과 데이터 전송량이라는 대상을 함께 적는다. 포트폴리오 소개에 있는 약 90%라는 수치와 혼합하거나, 응답 한 건의 크기나 로딩 시간 개선으로 바꾸지 않는다. 측정 시작 조건, 초기 조회 포함 여부, 압축 여부와 반복 횟수는 추가 근거가 있어야 설명할 수 있다.

### 요구 조정과 UI의 정확성

포트폴리오 7쪽은 선행 작업과 후속 기록을 별도로 주는 API에 맞춰 목록과 페이지 나누기 방식을 조정하고 화면과 CSV에 같은 판정 규칙을 적용한 사례다. 8쪽은 선택 목록의 표시 위치, 전체화면 팝업과 키보드 조작을 다룬다. 10쪽은 요구사항과 회의 내용을 화면 후보로 구체화한 경험이다.

15쪽은 브라우저의 인증 정보와 만료된 서버 세션이 어긋난 문제를 재현하고, 보호 화면 표시 전 확인과 실행 중 인증 실패에 같은 복구 원칙을 적용한 사례다. 담당 범위는 원인 분석, 공통 복구 설계, 구현과 QA 환경 배포로 기록되어 있다.

편집 제안: 사용 기술의 개수를 늘리기보다 어떤 조건을 확인하고 어떤 동작을 유지했는지 설명한다. 사례별 담당 범위와 팀에서 조정한 일을 구분하면 직접 수행한 판단이 드러난다.

### 다른 수치의 사용 범위

포트폴리오 9쪽의 `4.87 MB → 약 0.55 MB`는 데스크톱, 태블릿과 모바일용 배너 파일 세 개의 합계다. 이력서에는 약 548 KB로 적혀 있다. 이를 방문자 한 명의 다운로드량이나 로딩 시간으로 소개하면 측정 대상이 달라진다.

이력서에 있는 E2E 시나리오 수와 배포 시간, QA 기간도 각각 검사 범위와 작업 조건을 설명할 때만 쓸 수 있다. 서로 다른 프로젝트의 숫자를 모아 하나의 성능 향상 지표처럼 제시하지 않는 구성을 권한다.

## 외부에서 확인할 수 있는 오픈소스 기여

두 기여는 PR 병합 여부와 릴리스 기록을 각각 확인할 수 있다. 홈페이지의 간결한 근거로 우선 사용하고, 필요하면 상세 사례에서 재현과 호환성 판단을 설명할 수 있다. 다음 날짜는 GitHub의 UTC 기록이다.

### React Router

PR #14689는 구분자 없이 이어지는 URL까지 선택적 매개변수로 잘못 매칭하는 문제를 수정하며 2026-01-21에 병합됐다. PR에는 기존 점 접미사 동작을 유지하기 위한 처리도 설명되어 있다. 릴리스 `react-router@7.13.1`은 2026-02-23 발행이고, 이 태그의 변경 기록에 #14689가 포함된다. 짧은 원문은 “optional params matching without a "/" separator”다. [PR #14689](https://github.com/remix-run/react-router/pull/14689), [v7.13.1 변경 기록](https://github.com/remix-run/react-router/blob/react-router%407.13.1/CHANGELOG.md), [공식 릴리스](https://github.com/remix-run/react-router/releases/tag/react-router%407.13.1)

편집 제안: 오류 재현, 기존 동작 유지와 릴리스 반영을 연결한다. 병합과 릴리스 날짜를 한 날짜로 합치거나 라이브러리 전체를 설계한 것으로 표현하지 않는다.

### Outline

PR #10759는 인라인 이미지 앞의 마지막 글자를 Delete 또는 Backspace로 지우지 못하는 문제를 수정하며 2025-12-03에 병합됐다. 표 안팎과 일반 텍스트 삭제를 확인하는 절차가 PR에 있다. 2026-01-06 발행된 v1.2.0 릴리스의 `New Contributors`에 이 PR이 명시되어 있다. [PR #10759](https://github.com/outline/outline/pull/10759), [Outline v1.2.0](https://github.com/outline/outline/releases/tag/v1.2.0)

편집 제안: 이미지 인접 위치에서의 삭제 문제와 기존 텍스트 편집 유지라는 구체적인 결과를 쓴다. 회사 사례의 수치와 달리 방문자가 원문에서 기여를 확인할 수 있다는 장점이 있다.

## 웹에서 설명하는 구성 제안

다음은 최종 게재 문구나 출시 목록이 아니라, 자료를 사이트의 읽기 순서에 맞게 편집하는 제안이다. [페이지별 내용](../requirements.md#페이지별-내용)의 구성을 전제로 한다.

### 첫 소개와 프로젝트

첫 소개와 상세 소개, 사례 제목 및 요약은 [개발자 소개 방향과 웹사이트 문구](developer-introduction.md)에서 비교한다. 방문자에게 보여줄 문구와 작성용 근거를 구분하며, 이 문서의 수치 사용 조건과 자료 확인 범위를 자기소개에 그대로 옮기지 않는다. 사이트의 기본 언어와 최종 표현은 아직 정하지 않았다.

소개 아래에는 실제로 사용할 수 있는 프로젝트의 이름, 누구의 어떤 문제를 해결하는지와 서비스 링크를 보여주는 구성을 권한다. “서비스 사용”과 “제작 내용”처럼 이동 목적을 드러내는 링크 이름을 비교할 수 있다. 설명 페이지가 없는 항목에 빈 상세 페이지를 만들 필요는 없다.

이력서 2쪽에는 한국어 문구 검사 도구를 포함한 작업 문서 도구, 오프라인 번역 웹 서비스와 일기 관리 및 분석 팀 프로젝트가 있다. 이들은 프로젝트 후보를 찾는 자료이며, 첫 버전에 모두 싣는다는 결정은 아니다. 제공 자료만으로 각 서비스의 현재 접속 가능 여부와 실제 주소를 확정할 수 없다.

오프라인 번역은 브라우저 추론과 작업 분리, 문구 검사 도구는 모호한 표현의 탐지와 문맥 판단, 일기 서비스는 팀 단위 출시 경험을 설명할 수 있다. 어떤 작업이 현재 체험 가능한지 확인한 뒤 선별해야 한다. 실제 서비스가 없을 때 해당 영역을 어떻게 제공할지는 별도 결정이며 임의로 생략하거나 가상의 서비스로 채우지 않는다.

### 홈페이지의 대표 사례 후보

서로 다른 판단을 보여주는 다음 네 사례를 후보로 권한다. 확정된 출시 목록은 아니다.

- 대용량 응답 처리 중 화면 정지: 응답 형식을 유지하면서 처리 위치를 바꾼 판단.
- 문서 생성 작업의 상태 동기화: 이벤트와 서버 상태를 구별하고 취소와 연결 오류를 처리한 판단.
- 대시보드의 표시값 교정과 전송량 감소: 데이터 정확성과 요청 방식을 함께 다룬 판단.
- 실시간 차트의 새로고침 복구: 이력과 새 수신값을 연결하고 분할 데이터를 처리한 판단.

오픈소스 기여는 별도 홈 영역에서 간결하게 제시할 수 있다. 만료 세션 복구, API 제약에 따른 목록 조정과 키보드 조작은 사례 목록을 확장할 후보로 남긴다. 모든 경력 항목을 독립 페이지로 나누기보다 설명할 판단과 근거가 있는지를 기준으로 고르는 편이 낫다.

### 상세 사례와 시각 자료

사례의 상단에는 결과와 그 조건을 함께 놓고, 이어서 배경과 담당한 일, 문제, 선택 이유, 구현과 검증을 읽게 하는 구성을 권한다. 이는 PDF의 페이지 순서를 옮기는 작업과 다르다. 예를 들어 전송량 결과 옆에 10분이라는 조건을 붙이고, 아래에서 추가 조회 방식과 표시값 검증을 설명한다.

- 화면 정지 사례: API, SharedWorker와 메인 스레드가 각각 수행하는 작업을 웹에서 새로 그린 도식으로 설명한다.
- 문서 생성 사례: 이벤트 수신, 진행 중인 조회, 추가 조회와 서버의 최종 응답을 시간 순서로 표시한다.
- 실시간 차트 사례: REST 이력이 들어오는 시점과 스트림 값이 합쳐지는 지점을 구분한다.
- 오픈소스 사례: 필요한 최소 재현 입력과 기대 결과를 관련 PR에 연결한다.

회사 화면을 사용할 수 있는 범위가 정해지기 전에는 실제 UI 이미지를 사용할 수 있다고 전제하지 않는다. 화면 없이도 설명 가능한 기술 관계부터 검토할 수 있다. 새로 만든 도식이나 예시가 실제 운영 화면과 같은 증거 수준을 가진다고 표현해서는 안 된다.

### 이력서와 글의 역할

웹 이력서는 경력 사실을 빠짐없이 확인하고 PDF로 이어지는 곳으로 사용한다. 홈페이지의 전문 영역 설명과 사례 상세의 기술적 판단을 다시 전부 반복하지 않는 편집을 권한다.

글은 실제로 쓴 글 가운데 현재 전문 영역을 보충하는 글을 선별해 기존 블로그로 연결한다. 이번 조사에서는 블로그의 전체 글 목록과 최신 상태를 대조하지 않았으므로 글 제목이나 선정 목록을 만들어 넣지 않는다.

## 제작 방식에 대한 조사

소개와 목록, 일반 사례는 미리 생성한 콘텐츠로 제공하고 실제 애플리케이션은 서브도메인에서 연결하는 구조가 요구사항에 맞는다. 구체적인 프레임워크 선택은 별도 결정이다.

### 현재 저장소에서 확인되는 범위

작업을 시작한 `main`의 `811f9f3`에는 `.gitignore`, `AGENTS.md`, `docs/designs/README.md`, `docs/dev/README.md`만 추적되어 있었다. 따라서 이 브랜치에서 재사용할 라우터, CSS 변수, 글꼴, 이미지 처리, 웹 이력서와 구성 요소 구현은 확인되지 않았다. 다른 작업 브랜치나 운영 사이트에도 구현이 없다는 뜻은 아니다.

제안서의 기존 구현 조사 항목은 이후 기술 선택과 구현 준비에서 확인해야 한다. 현재 브랜치에 설정이 없다는 이유로 프레임워크, 검사 도구와 디자인 값을 자동으로 추가할 수는 없다.

### 정적 제공 방식의 후보

- Next.js 공식 문서는 `output: 'export'`로 주소별 정적 파일을 생성하는 방식을 설명한다. React 기반 콘텐츠에 사용할 수 있지만 요청 시 서버 기능이 필요한 경우에는 제약을 확인해야 한다. [Next.js Static Exports](https://nextjs.org/docs/app/guides/static-exports)
- React Router 공식 문서는 URL 목록 또는 데이터로 정한 주소를 빌드 시 미리 렌더링하는 방식을 설명한다. 프로젝트와 사례 목록에서 상세 주소를 만드는 구조를 비교할 수 있다. [React Router Pre-Rendering](https://reactrouter.com/how-to/pre-rendering)
- Astro 공식 문서는 콘텐츠 컬렉션으로 Markdown 등의 내용을 불러오고 구조를 검사하는 방식을 설명한다. 읽는 콘텐츠가 중심인 사이트의 관리 방식 후보로 비교할 수 있다. [Astro Content Collections](https://docs.astro.build/en/guides/content-collections/)

세 자료는 2026-09-14에 확인한 공식 기능 설명이다. 특정 버전 설치나 의존성 추가를 결정한 것은 아니다. 작성 편의, 필요한 조작 예시, 기존 프로젝트와 공유할 기술, 배포 조건을 정한 다음 선택해야 한다. 외부 개발자의 사이트가 사용한다는 이유만으로 Next.js, MDX나 스타일 라이브러리를 고르지 않는다.

### 목록과 상세를 함께 유지하는 방식

제안은 프로젝트의 이름, 요약, 서비스 주소와 내부 설명 주소를 서로 다른 정보로 관리하고, 사례는 제목, 결과와 조건, 담당 범위, 본문과 근거 링크를 구별하는 것이다. 홈의 선별 항목과 전체 목록이 같은 콘텐츠를 참조하면 설명과 링크가 서로 달라지는 일을 줄일 수 있다. 구조화된 프로젝트 목록의 실제 사례는 [Anthony의 데이터 관리 방식](developer-websites.md#반복-목록은-데이터로-관리)에 있다.

일반 사례에 글과 도식만 필요하면 조작 가능한 본문 도구는 추가할 이유가 적다. 실제 시연이 설명에 필요해지면 Markdown과 MDX의 편집 및 실행 차이를 비교할 수 있다. 첫 버전에 관리자 화면이나 CMS를 도입해야 한다는 요구사항은 없다.

## 현재 기준으로 다시 확인한 웹 원칙

확정된 접근성과 이동 원칙은 유지할 수 있다. 구체적인 값과 동작은 실제 화면으로 확인해야 한다.

- WCAG 2.2는 2024-12-12 W3C 권고본을 확인했다. 4.5:1 텍스트 대비, 200% 글자 확대, 키보드 조작, 보이는 포커스와 포커스 가림, 최소 대상 크기 외에도 적용되는 A와 AA 항목을 확인해야 한다. 24×24 CSS px에는 인라인 링크 등 명시된 예외가 있어 모든 링크에 같은 박스를 강제한다는 뜻은 아니다. [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- Google은 설명 가능한 URL과 단어 사이의 하이픈을 권한다. 이는 사람이 읽을 수 있는 사례 주소를 뒷받침하지만 `/cases`라는 이름 자체를 요구하는 검색 규칙은 아니다. [Google URL 구조 지침](https://developers.google.com/search/docs/crawling-indexing/url-structure)
- MDN의 `ViewTransition` 인터페이스에는 2025년 10월부터 Baseline 2025라는 설명이 있다. 일부 기능의 지원은 다를 수 있다고 함께 명시하므로 모든 전환 기능과 구형 브라우저가 지원된다는 뜻으로 확대하면 안 된다. 기본 링크 이동을 유지한 상태에서 추가 표현으로만 적용한다는 요구사항이 적절하다. [MDN ViewTransition](https://developer.mozilla.org/en-US/docs/Web/API/ViewTransition)

## 아직 필요한 결정과 그 영향

문서화와 사례 후보 비교는 가능하지만, 실제 출시 콘텐츠와 디자인 값을 확정하려면 [아직 정하지 않은 사항](../requirements.md#아직-정하지-않은-사항)에 대한 판단이 필요하다.

- 기본 언어와 영어 제공 여부는 소개 문구의 길이, 한글 글꼴과 메뉴 폭에 영향을 준다.
- 실제 사용 가능한 프로젝트와 주소, 소스 제공 범위는 홈의 선별 목록과 상세 링크를 결정한다.
- 회사 UI 이미지의 사용 범위와 추가 성과 근거는 사례에 넣을 그림과 수치 설명의 깊이를 결정한다.
- 글꼴과 강조색, 테마, 본문 폭과 간격은 실제 프로젝트 항목과 긴 사례 본문을 배치해 본 뒤 정해야 한다.
- 구현 기술과 배포 조건은 정적 생성, 본문 편집 방식과 이미지 제공 방법을 결정한다.

추가 제안으로는 대표 프로젝트 항목 하나와 긴 사례 하나에 실제 내용을 넣어 데스크톱과 모바일에서 비교하는 작업이 유용하다. 최종 색상과 수치를 먼저 정하기보다 소개, 링크, 수치의 조건과 긴 설명이 함께 읽히는지를 확인할 수 있다. 이 제안은 구현 계획이나 확정된 디자인이 아니다.
