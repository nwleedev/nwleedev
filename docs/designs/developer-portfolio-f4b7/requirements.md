# 개발자 소개 웹사이트 요구사항

`nwlee.com`은 프론트엔드 개발자로서의 역량과 서비스 개발 및 협업에 기여할 수 있는 가치를 채용담당자와 개발자에게 소개하는 개인 웹사이트다. 이력서와 포트폴리오에 담긴 경력, 프로젝트에서 확인한 경험을 근거로 페이지 내용을 구성한다. 첫 버전에는 개발 중인 프로젝트를 소개하고, 서비스가 준비되면 실제로 사용할 수 있는 링크를 추가한다. 이력서나 포트폴리오 PDF를 웹페이지로 복제하지 않는다.

이 문서는 사이트의 콘텐츠와 화면을 설계하고 구현할 때 따를 요구사항이다. 조사에서 도출한 권고와 아직 정하지 않은 선택은 별도로 구분한다.

## 모호한 상황의 확인

작업 중 모호한 상황이 발생하면 임의로 해석하거나 선택을 확정하지 않고 질문과 선택지를 제공한다. 무엇이 모호한지, 각 선택이 작업의 내용과 진행 방식에 어떤 영향을 주는지 설명하고, 추천안이 있으면 그 이유를 함께 제시한다.

답변이 필요한 사항은 미결정으로 남기고, 답변에 따라 달라지는 작업은 기다린다. 영향을 받지 않는 작업은 계속 진행한다.

## 사이트의 역할과 자료 활용

방문자는 짧은 소개에서 어떤 프론트엔드 개발자인지 파악하고, 관심 있는 프로젝트나 문제 해결 사례를 선택해 자세히 살펴볼 수 있어야 한다. 사이트는 프로젝트와 활동이 늘어날 때 이를 연결하는 중심점으로 사용한다.

- 이력서, 포트폴리오와 프로젝트의 문제 정의, 제약, 해결 방식, 검증 결과와 기술 관계를 콘텐츠 자료로 사용한다.
- PDF의 문장을 나열하거나 전체 경력을 홈페이지의 중심에 배치하지 않는다.
- PDF의 상단 분홍색 선, 하단 어두운 띠, 슬라이드 번호, 고정된 두 열 구성과 화면 비율을 복제하지 않는다. PDF의 강조색을 검토 없이 사이트 색으로 채택하지 않는다.
- PDF 페이지를 이미지로 삽입해 본문을 대신하지 않는다. 도식은 설명하는 기술 관계를 유지하면서 웹에서 읽을 수 있게 구성한다.
- 실제 서비스 사용과 사이트 안의 설명 읽기를 서로 구분한다. 프로젝트와 사례에서는 기술 이름과 추상적인 자기평가보다 문제와 확인된 결과를 먼저 보여준다.

## 개발자 소개와 문구 작성

페이지 내용은 채용담당자와 개발자가 어떤 역량을 갖춘 사람인지, 서비스 개발과 협업에서 어떤 기여를 기대할 수 있는지 이해하도록 구성한다. 이력서, 포트폴리오와 프로젝트의 경험에서 드러나는 능력과 가치를 설명하고, 관심을 가진 방문자가 그 근거를 사례에서 확인할 수 있게 한다. 경험의 의미를 전달해 더 알아보고 함께 일하고 싶은 마음이 들도록 쓴다.

- 작업 사항을 그대로 옮기거나 요약한 목록으로 개발자 소개를 대신하지 않는다. 개별 경험에서 드러나는 판단과 강점을 해석해 어떤 개발자인지 설명한다.
- 프론트엔드 채용공고를 통해 기업이 개발자에게 요구하는 역량을 파악하고, 이를 바탕으로 소개에서 무엇을 강조하고 어떻게 표현할지 정한다. 기술 이름과 자격요건을 수집하는 데 그치지 않는다.
- 개발자 블로그와 개인 사이트에서 각 개발자가 자신을 어떻게 소개하는지 조사한다. 무엇을 중요하게 여기는지, 어떤 인상을 남기는지, 이를 어떤 경험과 작업으로 뒷받침하는지 살펴 문구 작성에 참고한다. 다른 사람의 소개 문장이나 강점을 그대로 가져오지 않는다.
- 실제 경험과 채용 수요를 연결해 이 개발자를 차별화할 수 있는 가치를 찾는다. 일반적인 프론트엔드 역량을 나열하는 데 그치지 않고, 본인의 경험에서 드러나는 판단과 강점의 조합이 왜 채용과 협업에서 의미가 있는지 설명한다. 실시간 데이터를 다루는 일에만 전문성이 있는 것처럼 소개하지 않는다.

확인되지 않은 경력이나 성과를 보태지 않는다. 구체적인 작업과 수치는 소개의 가치를 뒷받침하는 사례와 이력서에 필요한 깊이로 남긴다. 조사에서 제안한 소개 방향과 최종 문구는 구분한다.

## 문구 관리와 언어

우선 한국어 문구로 웹사이트를 설계하고 제작한다. 한국어 웹사이트를 제작한 다음 영어 문구를 구성해 영어 버전을 제공한다.

개발자 소개와 화면에 사용하는 메시지, 단어, 용어와 표현은 한국어 제작 단계부터 UI 코드와 분리해 JSON으로 관리한다. 문구 초안은 이후에도 UI 구현 코드를 바꾸지 않고 수정할 수 있어야 한다.

소스 구성에는 Feature-Sliced Design(FSD)을 적용한다. 문구를 한 곳에서 관리하기 위한 폴더명과 저장 위치는 [FSD 구조와 문구 저장 위치](decisions/terms-storage.md)를 따른다.

## 주소와 콘텐츠 구분

홈페이지와 프로젝트, 사례, 이력서를 다음 주소로 제공한다.

- `/`: 개발자 소개와 선별한 작업.
- `/projects`: 사이드 프로젝트 목록.
- `/projects/[id]`: 설명이 필요한 프로젝트의 상세 내용.
- `/cases`: 기술적 문제 해결 사례 목록.
- `/cases/[id]`: 개별 사례의 판단과 검증 근거.
- `/resume`: 웹 이력서와 PDF 이력서 접근.
- `blog.nwlee.com`: 기존 블로그.
- `<project>.nwlee.com`: 별도로 배포할 사이드 프로젝트.

`[id]`는 URL 매개변수 표기다. 실제 주소에는 사람이 읽을 수 있는 영어 소문자와 하이픈 조합을 사용한다. `work`를 메뉴 이름이나 페이지 주소로 사용하지 않는다.

### Project

Project는 무엇을 만들었는지 설명하는 독립적인 서비스나 사이드 프로젝트다. 가능하면 방문자가 실제 애플리케이션을 사용할 수 있어야 한다.

상세에는 이름, 짧은 설명, 목적과 제작 내용을 제공한다. 개발 중인 프로젝트는 현재 상태를 함께 표시하고, 서비스가 준비되면 실제 이용 링크를 추가한다. 외부에서 열람할 수 있는 소스 저장소가 있으면 연결한다. 개발 기간, 실제 UI 이미지와 관련 Case는 설명에 필요한 경우에 포함한다. 기술 스택은 보조 정보로 사용한다. 모든 실험에 상세 페이지를 만들 필요는 없다.

### Case

Case는 어떤 문제를 어떻게 해결했는지 설명한다. 결과나 검증 근거를 먼저 제시한 뒤 배경, 담당한 일, 문제, 제약, 판단, 구현과 검증 내용을 필요한 깊이로 제공한다.

회사 사례는 글과 새로 작성한 기술 도식으로 구성한다. 도식은 실제 기술 관계를 설명하며, 회사 UI 이미지나 PDF 페이지를 대신 복제하지 않는다.

모든 사례에 같은 항목을 강제로 채우지 않는다. 숫자로 확인할 수 있으면 결과를 먼저 보여주고, 숫자가 적합하지 않으면 오류 재현과 수정 확인, 수정안 병합과 릴리스 반영처럼 확인할 수 있는 사실을 사용한다.

## 페이지별 내용

### 홈페이지

자기소개, 선별한 Projects, 선별한 Cases, 오픈소스 기여, 글, 프로필과 연락 수단으로 구성한다. 이 순서를 기본 권장 순서로 삼고 전체 자료를 한 페이지에 펼치지 않는다.

- 소개에는 이름, `Frontend Engineer`, 전문 영역과 개발자로서의 가치를 설명하는 한두 문장과 필요한 최소 링크를 둔다. 소개만으로 첫 화면 전체를 채우지 않는다.
- Projects는 실제 접근할 수 있는 사이드 프로젝트를 우선한다. 첫 버전에는 개발 중인 프로젝트의 이름, 짧은 설명과 제작 내용을 소개하고 개발 상태를 표시한다. 상세 페이지가 있으면 연결하고, 실제 서비스가 준비된 항목에 이용 링크를 추가한다.
- Cases에는 대표 사례 3~4개를 제시한다. 제목과 결과로 사례를 선택할 수 있어야 한다.
- React Router와 Outline 기여는 관련 PR과 공식 릴리스를 연결해 간결하게 보여준다. 첫 버전에 별도 `/open-source` 페이지를 만들지 않는다.
- 글은 기존 블로그에서 일부만 골라 연결한다. 별도 `/writing` 페이지를 만들지 않는다.
- 프로필에는 이메일, GitHub, LinkedIn과 이력서로 접근할 수 있는 링크를 제공한다. 연락 양식은 포함하지 않는다.

### 프로젝트와 사례 목록

`/projects`에는 페이지 제목, 짧은 설명과 반복되는 프로젝트 항목을 둔다. 실제 서비스와 상세 설명 링크를 구분한다.

`/cases`에는 페이지 제목, 짧은 설명, 사례 항목, 검증 결과 요약과 상세 링크를 둔다. 두 목록 모두 먼저 훑어보고 관심 있는 항목을 고르는 용도로 만든다.

첫 버전에는 검색, 분류 필터와 페이지 나누기를 만들지 않는다. 프로젝트 정렬 UI와 사례 분류 탭도 기본 구성에 포함하지 않는다. 항목이 실제로 많아진 뒤 필요성을 판단한다.

### 상세 페이지

프로젝트 상세는 애플리케이션의 목적, 제작 내용과 현재 개발 상태를 설명한다. 준비된 서비스와 열람 가능한 소스만 연결한다. 실제 UI 이해에 도움이 될 때만 화면 이미지를 사용하고, 별도로 설명할 기술 문제가 있으면 그 문제를 설명한 사례로 연결한다.

사례 상세는 긴 기술 설명을 읽을 수 있어야 한다. 제목, 결과, 배경과 담당 업무, 문제와 제약, 판단, 구현, 검증과 결과를 표현할 수 있어야 한다. 그림, 화면 이미지, 도식과 코드 블록은 실제 설명에 필요한 경우에 지원한다.

사례 목록으로 돌아갈 수 있어야 한다. 상위 페이지를 나타내는 별도 계층 탐색, 이전 사례와 다음 사례 이동은 첫 버전의 필수 기능이 아니다.

### 웹 이력서

`/resume`은 최신 이력서의 정보 범위를 기준으로 이름과 연락 정보, 요약 소개, 경력, 오픈소스 기여, 프로젝트, 주요 기술과 학력을 제공한다. PDF 이력서에 접근할 수 있어야 한다. 기존 웹 이력서가 있다면 최신 자료와 대조한다.

### 공통 화면

헤더, 메뉴, 본문 바로가기, 푸터, 텍스트 링크, 외부 사이트와 서브도메인 링크, 포커스 표시, 페이지와 섹션 제목, 기술 정보, 그림과 설명, 404 화면을 제공한다.

메뉴의 기본 항목은 `Projects`, `Cases`, `Blog`, `Resume`이며 사이트 이름으로 홈에 돌아갈 수 있다. 헤더 고정은 필수가 아니다. 모바일에서도 네 링크를 줄바꿈해 표시할 수 있으면 접이식 메뉴를 만들지 않는다. 실제 폭에서 불가능할 때만 메뉴를 별도 영역에 여는 방식을 추가한다.

존재하지 않는 프로젝트와 사례 주소에서는 404 화면을 보여주고 홈, 프로젝트 목록 또는 사례 목록으로 돌아갈 방법을 제공한다.

## 시각적 방향

내용과 근거를 먼저 읽을 수 있고, 글자와 여백으로 정보의 중요도를 구분하며, 링크와 조작 반응을 세심하게 다듬는 방향을 따른다. 기술 설명의 편집 원칙을 사용하되 PDF나 잡지의 화면 구성을 복제하지 않는다.

- 하나의 명확한 콘텐츠 축을 기본으로 한다. 목록에 필요한 경우 그리드를 사용할 수 있지만 모든 정보를 카드로 감싸지 않는다.
- 글자 크기와 굵기, 줄 높이, 자간, 정렬과 여백으로 정보의 순서를 드러낸다. 구분선은 필요한 곳에 제한한다.
- 중립적인 색을 기본으로 하고 강조색 하나를 사용한다. 강조색을 정할 때는 사용할 위치별 명암비 충족 여부를 먼저 확인한다. 모든 제목이나 링크에 강조색을 일괄 적용하지 않는다.
- 색은 페이지 배경, 주요 본문, 보조 본문, 덜 중요한 정보, 구분용 배경, 구분선, 강조, 포커스, 성공, 경고와 오류의 의미를 구별할 수 있게 정의한다.
- 읽기 쉬운 산세리프 글꼴을 기본으로 한다. 고정폭 글꼴은 URL, PR 번호, 코드, 식별자와 수치 등 실제 기술 정보에 제한할 수 있다. 사이트 전체에 고정폭 글꼴을 적용하지 않는다.
- 본문에는 읽기 적합한 폭을 두고, 설명용 이미지와 도식은 필요하면 본문보다 넓게 표시할 수 있다.
- 여백으로 문장 안의 관계, 구성 요소 안의 관계, 항목, 섹션과 페이지를 구분한다. 섹션 사이를 구분할 때는 테두리보다 여백을 우선한다. 모든 임의의 수치를 디자인 토큰으로 만들지 않는다.
- 테두리는 내용 구분이 필요할 때 사용한다. 둥근 모서리와 그림자를 일반 콘텐츠의 기본 표현으로 사용하지 않는다. 겹쳐 표시하는 UI가 실제로 생길 때만 높낮이 표현을 정의한다.
- 아이콘은 외부 이동이나 저장소처럼 의미 전달에 도움이 될 때 사용한다. 기술 로고를 모아 역량을 표현하지 않는다.

반복되는 특징은 사례의 결과 우선 제시, 실제 서비스와 설명의 별도 링크, 실제 기술 정보의 일정한 배치, 링크와 조작 영역의 제한적인 반응이다. URL, PR 번호, 날짜, 수치와 상태는 실제 정보일 때만 표시한다.

## 조작과 상태

링크와 조작 요소는 기본, 마우스를 올린 상태, 키보드 포커스, 누르는 상태와 현재 위치를 표현한다. 실제 비활성화 기능이 없으면 비활성 상태를 미리 만들지 않는다.

- 주소 이동에는 기본 HTML 링크를 사용한다. 실행할 동작이 있는 경우에만 버튼을 사용한다.
- 서비스와 상세 설명 링크를 하나의 클릭 가능한 카드 안에 중첩하지 않는다. 두 링크에 각각 접근할 수 있어야 한다.
- 핵심 정보는 마우스를 올려야만 나타나게 만들지 않는다. 터치에서도 같은 정보와 기능을 제공한다.
- 툴팁을 기본 구성에 추가하지 않는다. 필요한 설명은 본문이나 보이는 이름으로 제공한다.
- 핵심 콘텐츠는 정적으로 제공할 수 있으므로 로딩용 윤곽 화면과 회전 표시를 기본 상태로 만들지 않는다. 실제 비동기 콘텐츠가 있을 때 해당 기능에만 정의한다.
- 움직임은 마우스와 포커스 상태 변화, 누르기 반응, 페이지 이동 관계와 상태 변화 설명에 사용한다. 비필수 움직임은 `prefers-reduced-motion`에서 제거하거나 단순화한다.
- View Transition API를 사용하더라도 이를 지원하지 않는 환경에서 기본 이동과 콘텐츠 이용이 가능해야 한다.

## 접근성과 반응형 동작

접근성 목표는 WCAG 2.2 AA다. 다음 항목만 확인하는 것으로 전체 기준 충족을 대신하지 않는다.

- 일반 텍스트의 명암비는 최소 4.5:1이다. 큰 텍스트는 WCAG의 해당 조건을 충족할 때 3:1을 적용할 수 있다.
- 글자 크기를 200%로 확대해도 콘텐츠와 기능이 사라지지 않는다.
- 포인터 대상은 원칙적으로 24×24 CSS px 이상이거나 WCAG가 명시한 예외를 충족한다.
- 주요 이동과 동작은 키보드로 사용할 수 있고 포커스가 보여야 한다. 고정되거나 겹친 UI가 포커스된 요소를 완전히 가리지 않아야 한다.
- HTML 요소가 제공하는 의미를 우선 사용한다. ARIA는 기본 의미로 해결할 수 없을 때 추가한다. 아이콘만 있는 조작 요소에는 접근 가능한 이름을 제공한다.
- 정보를 전달하는 이미지에는 대체 텍스트를 제공한다. 장식 이미지는 중복 정보를 읽지 않게 처리한다.
- 화면 폭이 달라져도 정보 우선순위와 사례의 읽는 순서를 유지한다. 여러 열을 유지할 공간이 없으면 한 열로 바꾼다.
- 페이지 전체에는 가로 스크롤이 생기지 않는다. 화면 이미지와 그림은 영역에 맞게 줄이고, 코드 블록처럼 본질적으로 긴 콘텐츠만 필요한 내부 스크롤을 허용한다.

## 기본 구성에서 제외하는 표현

전체 화면 크기의 제목, 기술 로고 모음, 역량 백분율과 진행 막대, 가짜 터미널, 장식 코드, 추천사, 전체 경력 타임라인, 연락 양식과 불필요한 캐러셀은 사용하지 않는다.

둥근 카드나 벤토 그리드를 모든 화면의 기본 구성으로 사용하지 않는다. 유리 효과, 강한 발광 효과, 장식용 그라디언트, 불필요한 3D 물체와 AI 생성 대표 이미지를 사이트의 기본 표현으로 사용하지 않는다.

계속 움직이는 배경, 반복 재생 장식, 모든 섹션의 자동 등장, 커서 대체, 강제 스크롤과 의미 없는 시차 효과를 사용하지 않는다. 유행한다는 이유만으로 공상과학풍 인터페이스나 과도한 장식과 시각적 효과를 추가하지 않는다.

## 디자인 체계의 구성과 제작 순서

기존 구현을 파악한 뒤 필요한 구성 요소와 상태, 기본 시각 규칙, 디자인 토큰, 개별 구성 요소, 반복 조합 순서로 디자인 체계를 구체화하고 `DESIGN.md`에 정리한다.

화면 설계 전에 다음 항목을 실제 저장소에서 확인한다.

- 프레임워크와 버전, 페이지 이동 방식, 기존 페이지와 콘텐츠 저장 방식, 웹 이력서, Markdown 또는 MDX 사용 여부, 프로젝트와 사례 목록을 관리하는 구조.
- 스타일 작성 방식과 구성 요소 라이브러리, CSS 변수와 테마, 헤더와 푸터 및 링크 구현, 포커스와 움직임 감소 설정 등 접근성을 위한 공통 스타일.
- 글꼴 파일과 불러오는 방식, 한글 표시 가능 여부와 가변 글꼴 사용 여부, 아이콘 라이브러리, 이미지 처리 방식, 기존 블로그와 공유하는 이미지 및 시각적 특징.
- 반응형 규칙, 어두운 테마와 시스템 테마 설정의 사용 여부, 반복되는 색, 글자, 여백, 테두리와 모서리 값.

제안서와 기존 구현이 다르면 유지할 기능, 재사용할 수 있는 구현과 수정이 필요한 부분을 구분한다. 제안서와 다르다는 이유만으로 기존 구현을 폐기하지 않는다.

구성 요소 목록에는 이 사이트에서 필요한 요소와 실제 상태만 포함한다. 예시로 열거한 요소마다 별도 파일을 만들 필요는 없으며, 같은 역할을 반복하는 단위만 재사용한다.

기본 시각 규칙은 색, 글자, 여백, 배치, 테두리, 모서리, 겹친 영역의 배경과 그림자, 아이콘과 움직임을 포함한다. 반복해서 사용하는 의미 있는 결정만 디자인 토큰으로 만든다.

개별 구성 요소에는 용도, 내부 구성, 필요한 표현 종류와 상태, 사용하는 토큰, 시각 규칙, 사용 조건과 잘못된 사용 예를 설명한다. 실제로 반복되는 조합이 있을 때만 별도 사용 규칙을 정의한다. 프로젝트의 서비스 및 상세 링크, 사례의 성과와 검증 근거 제시, 긴 기술 본문, 오픈소스의 외부 근거 연결은 이 기준으로 확인한다.

## 완료를 확인할 결과

첫 버전에서는 개발자 소개, 개발 중인 프로젝트의 목적과 제작 내용, 사례의 근거 탐색과 이력서 접근을 각각 확인할 수 있어야 한다. 서비스가 준비된 뒤에는 이용 링크를 추가하고 실제 프로젝트를 사용할 수 있는지 확인한다. 각 페이지의 필수 내용과 현재 제공하는 링크, 404 복귀, 키보드 조작, 축소 화면과 글자 확대 상태를 실제 화면에서 확인할 수 있어야 한다.

방문자는 소개와 선별된 콘텐츠를 읽고 개발자의 역량과 서비스 개발 및 협업에서 기대할 기여를 설명할 수 있어야 한다. 작업 목록이나 구현 절차만으로 역량과 가치를 추측하게 하는 구성은 이 조건을 충족하지 않는다.

문구 작성 자료에서 채용공고의 요구 역량과 다른 개발자의 소개 방식이 문구 선택에 어떻게 반영됐는지 확인할 수 있어야 한다. 설명할 역량과 가치, 이를 뒷받침하는 이력서, 포트폴리오 및 프로젝트의 경험을 소개 문구와 연결해 남긴다. 첫 소개에서는 개발자의 강점을 파악하고, 이어지는 사례에서는 그 강점의 근거를 확인할 수 있어야 한다.

먼저 한국어 웹사이트에서 각 페이지의 내용과 필수 동작을 확인할 수 있어야 한다. 이후 영어 문구를 구성해 같은 페이지의 내용을 영어로도 읽을 수 있게 한다. 각 언어를 제공하는 단계에서 UI 구현 코드를 수정하지 않고 JSON의 문구를 바꿔, 그 언어의 화면에 반영되는 것을 확인할 수 있어야 한다.

디자인 체계는 실제로 필요한 구성 요소와 상태, 기본 표현, 의미 있는 토큰, 반복 조합, 반응형과 접근성 규칙, 프로젝트와 사례의 사용 규칙을 포함한다. `DESIGN.md`와 재사용할 기본 스타일 및 구성 요소 구현을 통해 새 페이지와 사례를 같은 규칙으로 추가할 수 있어야 한다. 사용하지 않는 입력창, 모달과 선택 UI를 완성도를 이유로 추가하지 않는다.

리서치 문서는 다른 개발자의 사이트 구성과 제작 방식, 현재 자료에 대한 적용 근거, 한계와 미결정을 구분해 남긴다. 요구사항과 리서치 문서의 완성은 웹사이트나 디자인 체계의 구현 완료를 뜻하지 않는다.

## 아직 정하지 않은 사항

- 영어 버전 추가 후의 기본 사이트 언어와 언어별 주소 구성.
- 첫 버전에 보여줄 사이드 프로젝트 목록과 각 소스 저장소의 외부 제공 여부.
- 실제 글꼴, 글자 크기 체계, 강조색, 밝은 테마만 제공할지 어두운 테마도 제공할지 여부.
- 본문과 페이지의 최대 폭, 반응형 전환 지점과 그리드 열 수.
- 여백, 모서리, 테두리, 그림자, 움직임 시간과 속도 변화의 구체적인 값.
