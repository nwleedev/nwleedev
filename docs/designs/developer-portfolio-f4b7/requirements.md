# 편집형 단일 페이지 개발자 소개 웹사이트 요구사항

`nwlee.com`은 프론트엔드 개발자로서 해결해 온 문제와 확인된 기여를 채용담당자와 개발자에게 소개하는 단일 페이지 기술 프로필이다. 방문자는 다른 페이지로 이동하지 않고도 어떤 문제를 해결해 왔는지, 어떤 기술적 판단을 내리는지, 외부에서 확인할 수 있는 작업이 무엇인지 파악할 수 있어야 한다.

사이트는 `Technical Publication / Career Index / Evidence-driven` 방향을 유지하되, 네비게이션 바 없는 단일 칼럼으로 구성한다. 편집형이라는 이유로 화면을 여러 열로 나누거나 숫자와 문구를 과장되게 강조하지 않는다. 이력서와 포트폴리오의 내용을 그대로 옮기거나 일반적인 포트폴리오 카드 모음으로 재구성하지 않는다.

이 문서는 사이트의 콘텐츠, 시각 규칙과 구현 결과가 충족해야 할 요구사항이다. 외부 사이트 관찰과 적용 판단은 [개인 사이트 재조사](references/personal-site-recheck.md)에서 구분하며, 모바일 프로필 링크의 아이콘과 반응형 배치 근거는 [모바일 프로필 아이콘 조사](references/mobile-profile-icons.md)에 기록한다. [모바일 Drawer 조사](references/mobile-drawer.md)는 교체 전 판단을 남긴 기록으로만 보존한다.

## 모호한 상황의 확인

작업 중 요구사항의 의미가 분명하지 않으면 임의로 확정하지 않는다. 선택에 따라 방문자가 보게 될 내용이나 조작 방식이 달라지는 경우에는 질문과 선택지를 먼저 제시한다.

답변이 필요한 사항은 미결정으로 남기고 그 답변에 따라 달라지는 작업을 기다린다. 영향을 받지 않는 자료 확인과 준비는 계속할 수 있다.

## 사이트의 역할과 자료 활용

사이트는 다음 질문에 빠르게 답해야 한다.

- 어떤 프론트엔드 문제를 주로 해결해 왔는가?
- 그 설명을 뒷받침하는 실제 기여는 무엇인가?
- 외부에서 직접 확인할 수 있는 기여는 무엇인가?
- 자세한 이력과 기술 글은 어디에서 확인할 수 있는가?

이력서, 포트폴리오와 프로젝트에서 확인한 역할, 판단, 변화와 기술 관계를 소개 자료로 사용한다. PDF의 문장, 화면 비율, 분홍색 선과 어두운 하단 영역을 복제하지 않는다. 회사 내부 화면이나 시스템 구조를 추정해서 만들지 않으며, 확인되지 않은 기관명과 고객사 정보도 게재하지 않는다.

개인 웹사이트만 읽어도 각 경력에서 무엇을 맡아 어떻게 바꾸었고 무엇을 확인했는지 알 수 있어야 한다. 문제의 맥락과 구체적인 해결 방식을 설명하되, 코드, 시행착오와 재현 절차를 포함한 긴 해결 과정은 `blog.nwlee.com`에서 관리한다. 블로그, 이력서, GitHub와 LinkedIn은 목적이 드러나는 이름으로 연결한다.

## 개발자 소개와 편집 기준

소개에서 앞세울 기준은 다음 문장이다.

> 서비스에서 발생한 문제의 원인을 찾고, 서버 응답 처리와 비동기 작업 상태를 개선한 뒤 배포한 변경이 의도대로 작동하는지 확인하는 프론트엔드 엔지니어.

이 문장은 콘텐츠를 고르는 기준이며 첫 화면에 그대로 사용해야 하는 고정 문구는 아니다. 실제 소개 문구는 사실과 수치 조건을 유지하면서 자연스러운 한국어로 다듬는다.

- `React를 잘합니다`처럼 근거 없는 자기평가보다 실제 변화, 수치와 외부에서 확인 가능한 기여를 먼저 보여준다.
- 기술 이름은 독립적인 역량 목록이 아니라 그 기술을 사용한 경험 옆의 보조 정보로 둔다.
- 수치는 설명 문장의 일부로 둔다. 큰 숫자, 강조색과 별도 성과판으로 시선을 끌지 않는다.
- 수치는 대상과 비교 조건을 함께 쓴다. 새 비율이나 성과를 계산해 보태지 않는다.
- `설계`, `주도`, `담당`과 `검증`은 자료에서 확인되는 역할에만 사용한다.
- 회사 프로젝트를 장기간 운영한 독립 서비스처럼 표현하거나 짧은 수행 기간을 앞세워 강조하지 않는다.

## 한 페이지의 정보 순서

`/` 한 페이지를 다음 순서로 구성한다.

1. Identity
2. Experience
3. Open Source
4. Independent Work
5. Background
6. Contact와 Footer

별도의 `Selected Work`, `Skills`, `Projects` 영역과 내부 상세 페이지를 만들지 않는다. About은 Identity가 대신한다. 모든 화면 폭에서 같은 순서로 세로 스크롤하며 읽는다.

네비게이션 바, 고정 목차, 메뉴 버튼과 Drawer를 만들지 않는다. 데스크톱에서는 외부 자료 링크를 소개 본문에 유지하고 언어 선택은 화면 오른쪽 상단에 둔다. 모바일에서는 외부 자료 링크를 같은 본문 위치의 아이콘 목록으로 바꾸고 현재 화면과 다른 언어 하나만 이름 오른쪽에 표시한다. 키보드 사용을 위한 본문 바로가기와 기존 영역 id를 통한 직접 이동은 유지한다.

## Identity

첫 영역에는 이름, `Frontend Engineer`, 한두 문장의 소개와 GitHub, Blog, LinkedIn 및 Résumé 링크를 둔다. TypeScript와 React 기반 서비스에서 실시간 정보 표시, 오래 걸리는 비동기 작업, 운영 대시보드와 인증 문제를 해결해 온 경험을 보조 문장으로 설명할 수 있다.

데스크톱에서는 네 링크를 현재처럼 한 행에서 줄바꿈 가능한 텍스트 목록으로 표시한다. 모바일에서는 같은 순서와 목적지를 유지한 아이콘 목록을 한 행에 표시하며 텍스트 목록은 숨긴다. 아이콘 목록은 본문 왼쪽 기준선에서 시작하고 인접한 링크 사이에 같은 간격을 둔다. 남는 가로 너비를 링크 사이에 분배하지 않는다. 각 아이콘 링크는 44px 조작 영역을 유지하고 보이는 SVG는 화면 폭에 따라 24px에서 최소 18px까지 줄어들 수 있다. 목록은 줄바꿈하지 않으며 320px 이하에서도 페이지의 가로 오버플로우를 만들지 않아야 한다.

이름과 언어 링크는 하나의 가로 Flex 행에 두고 `align-items: center`로 세로축 중앙을 맞춘다. 데스크톱에서는 KO와 EN을 모두 표시하고 모바일에서는 한국어 화면에 EN, 영어 화면에 KO만 표시한다. 양쪽 요소를 배치할 때 `position: absolute`나 아이콘 전용 위치 보정을 사용하지 않는다.

프로필 사진, 기술 로고 모음, 숙련도 표시, 성과 대시보드, 3D 물체, 추정한 회사 화면과 터미널 모양을 넣지 않는다. Identity에 `100vh`를 강제하지 않고 다음 Experience의 시작이 자연스럽게 이어지게 한다.

## Experience

Experience의 최상위 단위는 회사다. 회사 안에서는 SI 프로젝트를 각각 전시하지 않고 확인된 `Engineering Contribution`으로 편집한다.

`Experience` 제목 아래에는 영역의 작성 방식이나 웹사이트 편집 방식을 설명하는 도입 문구를 두지 않는다. 제목 다음의 첫 회사 앞에 구분선을 넣지 않으며, 도입 문구와 구분선을 제거한 자리에 빈 여백을 남기지 않는다.

각 회사에는 회사명, 기간, 역할과 맡은 일을 적고 그 아래에 기여 설명을 이어 쓴다. 회사 정보와 기여를 좌우 열로 나누거나 독립적인 대형 카드로 만들지 않는다.

각 기여에는 어떤 기능이나 사용 상황의 문제였는지, 개발자가 무엇을 어떻게 변경했는지, 어떤 변화나 동작을 확인했는지가 드러나야 한다. 기술명과 결과만 나열하지 않는다. 항목의 분량을 억지로 맞추거나 모든 항목에 같은 소제목을 반복하지 않으며, 자료가 뒷받침하는 내용만 서술한다.

첫 버전에서 인공지능팩토리의 기여는 다음 네 항목으로 구성한다.

- **Data & Monitoring:** 실제 응답과 지표 정의를 대조해 지표 이름 및 라벨 불일치, 사용 비율 계산과 시계열 누락을 수정한 내용을 설명한다. 전체 구간을 다시 받지 않고 마지막 요청 시각 이후만 조회한 변경과 10분 기준 전송량이 96.5 MB에서 41 KB로 줄어든 결과를 문장으로 연결한다.
- **Async State & Realtime:** 5~10분 걸리는 문서 생성에서 SSE 이벤트를 계기로 서버 상태를 조회하고 그 응답으로 화면을 갱신한 방식을 설명한다. 조회 중 추가 이벤트나 연결 오류가 발생할 때의 처리와 취소하지 않기로 한 뒤에도 진행 안내를 유지한 동작을 포함한다. 상태 요청 10회 이하는 3초 폴링을 가정한 100~200회와 비교한 값이며 실제 운영 전후 측정이나 생성 시간 단축으로 쓰지 않는다.
- **Browser Runtime & Realtime Data:** 약 5 MB 응답 처리 중 발생한 3~4초 화면 정지에 대해, 응답 크기와 형식을 유지하면서 API 호출 및 변환을 SharedWorker로 옮기고 여러 화면에서 재사용한 방식을 설명한다. 배포 후 정지 해소를 확인한 사실과 REST 이력 및 실시간 차트 값의 병합 처리를 구분해 서술한다.
- **Reliability & Delivery:** 로그인한 사용자가 거치는 주요 절차를 확인하도록 70개 이상의 E2E 시나리오를 구성한 기여를 설명한다. 브라우저 인증 정보와 만료된 서버 세션의 불일치를 재현하고, 보호 화면 진입 전 확인과 실행 중 인증 실패에 같은 복구 원칙을 적용해 QA 환경에 배포한 담당 범위를 밝힌다.

크러스트유니버스 및 Quarkonix 경력도 결과만 압축하지 않는다. 주기적 refetch 환경의 optimistic update, Vite 설정과 React lazy loading 및 적용 절차 문서화, Chrome DevTools를 이용한 WebSocket 연결 중단 원인 확인을 각각 설명한다. 어느 회사의 일인지 추가 근거 없이 분리하거나 확인되지 않은 오류 원인, 수정 코드와 성과 수치를 만들지 않는다.

현재 기여는 본문만으로 이해할 수 있게 구성한다. 기존 기술 도식은 문장으로 대체하며, 자세한 구조도와 코드는 블로그에서 설명한다.

## Open Source

React Router와 Outline 기여를 회사 경력과 구분된 외부 확인 자료로 소개한다. 큰 프로젝트 카드나 GitHub 화면 이미지 대신 변경 내용, 병합 상태, 공식 릴리스와 PR 링크를 읽기 쉬운 행으로 제공한다.

영역의 작성 방식이나 웹사이트 편집 방식을 설명하는 도입 문구는 두지 않는다. 제목 다음의 첫 기여 앞에 구분선을 넣지 않고 불필요한 빈 여백도 만들지 않는다. 병합 상태와 공식 릴리스 포함 여부는 각 항목의 릴리스 및 PR 링크로 확인할 수 있게 한다.

- React Router PR #14689와 v7.13.1
- Outline PR #10759와 v1.2.0

실시간 별 수, 기여 횟수나 저장소 로고 모음을 추가하지 않는다.

## Independent Work

독립 작업은 별도 제목으로 회사 Experience와 구분하고 실제 작업 단위로 소개한다. `회사 프로젝트 밖에서 문제를 정의하고 구현한 작업입니다.`처럼 영역을 편집하거나 사이트를 구성한 방식을 설명하는 도입 문구는 두지 않는다. 제목 다음의 첫 작업 앞에는 구분선을 넣지 않고 32px 뒤에 내용을 시작한다. 두 작업을 옆으로 배치하거나 한쪽을 어긋나게 놓지 않는다.

- **AI Agent Workflow:** 요구사항, 조사, 결정과 구현이 섞이지 않도록 만든 저장소 규칙과 Skill을 소개한다. 한국어 문구를 저장하기 전에 검사하는 절차와 여러 저장소에 적용한 사실을 함께 설명하되 효과를 측정한 것처럼 표현하지 않는다.
- **Offline Translation Web App:** 사용할 언어의 모델을 미리 저장한 뒤 네트워크 연결 없이 한국어와 영어, 한국어와 일본어 사이를 번역하는 사용 방식을 먼저 설명한다. Web Worker, IndexedDB, 브라우저 캐시와 GitHub Actions 배포 자동화를 그 방식을 구현한 기술 정보로 제공한다. `30초 이내 배포`는 근거와 조건을 확인한 경우에만 사용한다.

일기 관리 및 분석 팀 프로젝트와 개인 메모 앱은 첫 버전의 필수 소개 항목이 아니다. 이후 새로운 독립 작업을 추가할 때에는 개발자의 판단과 확인 가능한 결과를 보태는지 먼저 확인한다.

## Background와 Contact

Background에는 학력, 정보처리기사와 TOEIC Speaking 정보를 압축해서 제공한다. 교육 과정과 단기 활동은 이력서에 남기고 첫 버전 홈페이지에는 넣지 않는다. 제목 다음의 첫 항목 앞에 구분선을 넣지 않고 32px 뒤에 내용을 시작한다. 삭제한 선의 padding과 빈 여백을 남기지 않으며 두 번째 이후 항목의 구분선은 유지한다.

Contact는 별도 안내 문구 없이 Email, GitHub, Blog, LinkedIn과 Résumé를 나열한다. 제목 다음의 첫 링크 앞에 구분선을 넣지 않고 32px 뒤에 내용을 시작한다. 삭제한 문구와 선의 여백은 남기지 않는다. 전화번호와 연락 양식은 넣지 않는다.

## 글과 언어 관리

한국어 화면을 먼저 제작하고 확인한 다음 영어 문구를 추가한다. 소개, 제목, 설명, 링크 이름과 상태 문구는 UI 코드와 분리한 JSON으로 관리한다. 한국어는 `src/shared/terms/ko.json`, 영어는 `src/shared/terms/en.json`에서 관리한다.

블로그 글 목록과 검색 기능은 홈페이지에 복제하지 않는다. Identity와 Contact에서 Blog로 이동할 수 있게 한다. 한국어 `/`와 영어 `/en/`는 같은 UI와 정보 순서를 사용한다. 언어 전환을 없애지 않는다. 데스크톱에서는 화면 오른쪽 상단에 KO와 EN을 가로 Flex 목록으로 표시하고 현재 언어는 글자와 `aria-current="page"`로 함께 구분한다. 모바일에서는 현재 언어를 반복하지 않고 한국어 화면에는 EN, 영어 화면에는 KO 링크 하나만 표시한다.

## 편집형 시각 규칙

화면은 개발자의 소개와 경력을 차례로 읽는 한 편의 글처럼 구성한다. 장식보다 내용을 먼저 읽게 하고, 주장보다 근거를 먼저 보여준다.

- 카드 대신 글자 크기와 굵기, 여백, 정렬과 얇은 구분선으로 정보의 위계를 만든다.
- 내용에 맞춰 문단 길이를 정하되, 별도 수치 블록이나 과장된 인용문으로 강조하지 않는다.
- 연도, 역할과 기술 정보도 본문 위나 아래의 같은 칼럼에 둔다. 장식용 영역 번호와 옆 칼럼은 사용하지 않는다.
- 그래픽을 제거해도 의미가 그대로라면 그래픽을 만들지 않는다.
- 다음 영역의 강한 위쪽 구분선과 현재 영역의 아래쪽 구분선 사이에 내용이 없다면 강한 구분선 하나만 남긴다. 항목 사이의 구분선은 유지한다.
- 페이지 기본 바탕은 흰색 하나로 유지한다. 반복되는 영역 배경과 카드 그림자를 사용하지 않는다.
- 둥근 모서리는 설명용 보조 영역에 필요한 경우 최대 6px까지만 사용한다. 큰 둥근 카드와 pill 태그를 기본 표현으로 사용하지 않는다.

## 글꼴과 글자 체계

기본 글꼴은 `Pretendard Variable`, `Pretendard`, `system-ui` 순서로 사용한다. 글꼴 굵기는 400, 500, 600과 700 네 단계로 제한하고 800~900을 장식용으로 추가하지 않는다.

- 이름과 영역 제목은 본문보다 구별되지만 화면을 지배하지 않는 크기와 굵기로 표시한다.
- 소개 문구도 본문으로 배치하며 대형 슬로건처럼 배치하지 않는다.
- 본문은 1rem, 400, 줄 높이 1.7~1.75를 기본으로 한다.
- 날짜와 기술 정보는 .875rem을 기본으로 한다.
- 수치 전용 글자 단계는 없앤다. 수치와 조건은 본문과 같은 크기로 읽는다.

이름, 소개, 경력과 연락처는 같은 본문 폭과 왼쪽 기준선을 사용한다. 제목 크기와 간격의 구현 시작값은 `DESIGN.md`에서 관리하고 한국어 및 영어 화면을 보고 조정한다. 크기, 굵기, 여백과 정렬로 차이를 만들며 색만으로 위계를 대신하지 않는다.

## 색상

첫 버전은 밝은 테마를 기본으로 한다.

- Brand base: `#EE5166`
- Brand strong: `#C62A44`
- Brand hover: `#B4233C`
- Brand subtle: `#FFF1F3`
- Brand subtle strong: `#FDE4E8`
- Surface default: `#FFFFFF`
- Surface subtle: `#F7F7F8`
- Text primary: `#18181B`
- Text secondary: `#52525B`
- Text muted: `#71717A`
- Border default: `#E4E4E7`
- Border strong: `#8B8B95`

`#EE5166`은 흰색 위 일반 본문이나 보조 정보의 글자색으로 사용하지 않는다. 일반 크기의 브랜드 글자와 링크에는 `#C62A44` 또는 그보다 대비가 높은 색을 사용한다. 색만으로 전후 변화, 링크나 현재 상태를 전달하지 않는다.

## 여백과 반응형 배치

기본 여백 값은 `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 128`을 사용한다. 반복되는 관계를 표현하는 값만 디자인 토큰으로 만든다.

데스크톱과 모바일 모두 한 열이다. 페이지 바깥 여백만 늘어나며, 회사 정보, 기여, 오픈소스, 독립 작업, 학력과 연락처를 각각 다른 열로 분리하지 않는다. 좌우 여백은 `clamp(1rem, 3vw, 2rem)`을 유지하고 긴 본문을 읽기 편한 최대 폭을 `DESIGN.md`에 기록한다.

반응형 분기는 프로필 링크의 표현과 언어 링크 수에만 사용한다. 데스크톱 외부 링크는 줄바꿈 가능한 가로 텍스트 목록을 유지하고 모바일에서는 본문 왼쪽에서 시작하는 가로 아이콘 목록으로 바꾼다. 모바일 목록에는 일정한 `gap`을 사용하며 남는 너비를 분산하지 않는다. 아이콘의 보이는 크기는 CSS `clamp()`로 점진적으로 줄이되 조작 영역은 44px로 유지한다. 목록을 줄바꿈하거나 DOM 순서를 CSS `order`로 바꾸지 않는다.

기존 1200px 바깥 구성, 48rem과 70rem의 다중 열 전환 및 42rem, 36rem과 34rem의 내부 가로 배치 전환은 폐기한다. 단일 칼럼이 유지되는 구성에 컨테이너 쿼리를 형식적으로 추가하지 않는다.

좁은 화면에서도 내용과 읽는 순서를 유지한다. 글자를 줄이거나 가로 스크롤, 캐러셀과 접이식 상세에 내용을 숨겨 분량을 줄이지 않는다. 같은 문장 안의 짧은 링크와 메타정보는 줄바꿈할 수 있다.

## 조작과 움직임

주소 이동은 기본 HTML 링크를 사용한다. 마우스를 올린 상태, 키보드 포커스, 누르는 상태와 필요한 현재 위치를 분명하게 표현한다. 외부 링크를 새 창으로 여는 동작을 기본값으로 강제하지 않는다.

모바일 프로필 아이콘도 기본 HTML 링크로 제공한다. 아이콘은 링크 목적을 대신해 읽히지 않게 보조 기술에서 제외하고, 각 링크에는 기존 텍스트와 목적 설명을 이용한 접근 가능한 이름을 제공한다. 링크 목록을 열고 닫는 상태, 배경 스크롤 제어와 클라이언트 script는 추가하지 않는다.

움직임은 링크 반응, 현재 위치와 짧은 상태 변화 설명에만 사용한다. 모든 영역의 자동 등장, 시차 효과, 커서 대체, 숫자 증가 애니메이션과 계속 움직이는 배경을 사용하지 않는다. `prefers-reduced-motion: reduce`에서는 필수적이지 않은 변형과 움직임을 제거하거나 즉시 전환한다. 콘텐츠를 애니메이션 완료 뒤에만 보이게 만들지 않는다.

## 접근성

접근성 목표는 WCAG 2.2 AA다.

- 문서 구조에 맞는 `header`, `main`, `section`과 `footer`를 사용하고 개발자 이름에 하나의 `h1`을 둔다. `header`는 회사나 영역의 제목 묶음에 사용할 수 있지만 네비게이션 바를 만들 근거로 쓰지 않는다.
- 일반 텍스트는 최소 4.5:1, 큰 텍스트는 최소 3:1의 명암비를 충족한다.
- 의미 있는 그래픽과 직접 만든 포커스 표시는 인접 색과 최소 3:1의 명암비를 충족한다.
- 포인터 대상은 원칙적으로 24×24 CSS px 이상이거나 WCAG가 명시한 예외를 충족한다.
- 모든 링크와 조작 요소를 키보드로 사용할 수 있고 `focus-visible` 표시가 보여야 한다.
- 모바일 프로필 아이콘 링크는 각각 목적이 구분되는 접근 가능한 이름과 44×44 CSS px 조작 영역을 제공해야 한다.
- 모바일 프로필 아이콘의 첫 조작 영역은 본문 왼쪽 기준선에서 시작하고, 화면 폭이 달라져도 인접 조작 영역 사이의 간격은 같아야 한다.
- 고정 요소가 포커스를 완전히 가리지 않아야 한다. 같은 페이지 안의 이동에는 필요한 `scroll-margin`을 둔다.
- 320px 폭과 200% 글자 확대에서도 정보와 조작 수단이 사라지거나 페이지 전체에 가로 스크롤이 생기지 않아야 한다.
- 의미 있는 도식에는 같은 내용을 전달하는 인접 본문 또는 `figcaption`을 제공한다.

## 기본 구성에서 제외하는 표현

검은 바탕과 네온 그라디언트, glassmorphism, Bento grid, 큰 둥근 카드 반복, 떠 있는 구체와 입체 물체, 기술 로고의 반복 이동, 가짜 터미널, 움직이는 격자 배경, 커서 조명, 장식용 차트, 프로젝트 카드 격자, 별도 성과 대시보드, 추천사와 일반적인 SaaS 행동 유도 영역을 사용하지 않는다.

Drawer, modal, toast, table, tab, filter, search, pagination, carousel, tooltip, form validation, loading skeleton, empty state와 command palette를 추가하지 않는다. 모바일 프로필 링크를 숨기는 메뉴, 중첩 목록과 별도 행동 유도 문구를 넣지 않는다.

## 디자인 체계와 제작 순서

현재 Astro와 Tailwind CSS 기반의 한국어 및 영어 정적 페이지가 있다. 이번 배치 변경은 기존 FSD 구성, JSON 문구 관리, 자체 제공 Pretendard와 정적 제공 방식을 유지한다. 모바일 프로필의 네 SVG에 한해 Astro 빌드 시점 컴포넌트인 `phosphor-astro`를 사용하며 UI 컴포넌트 모음과 클라이언트 런타임은 추가하지 않는다.

저장소 최상위 `DESIGN.md`에는 적용할 시각 규칙과 현재 구현에 반영했는지를 구분해 기록한다. 변경 플랜은 기존 컴포넌트와 타입을 교체 및 제거할 위치를 명시한다. 문서만 바뀐 상태를 화면 구현 완료로 표시하지 않는다.

## 완료 기준

첫 버전은 다음 항목을 실제 화면에서 확인할 수 있어야 한다.

- 한 페이지를 읽는 것만으로 개발자가 해결해 온 문제, 기술적 판단과 확인된 기여를 설명할 수 있다.
- Identity에서 Experience로 이어지며 각 경력의 문제, 직접 수행한 변경 방식과 확인 결과를 본문만으로 이해할 수 있다. 수치는 비교 대상과 조건을 같은 문단에서 읽을 수 있다.
- React Router와 Outline 기여를 실제 PR 및 공식 릴리스에서 확인할 수 있다.
- AI Agent Workflow와 Offline Translation Web App이 회사 경력과 다른 독립 작업으로 구분된다.
- 네비게이션 바와 다중 칼럼이 없고, 숫자와 소개 문구를 대형 글자로 강조하지 않는다.
- Experience와 Open Source 제목 다음에 편집 방식을 설명하는 도입 문구, 첫 항목 구분선과 그 자리를 대신하는 빈 여백이 없다.
- 데스크톱에서 외부 링크가 소개 본문에 있고 KO와 EN이 화면 오른쪽 상단에 있다. 모바일에서는 같은 위치에 네 외부 링크의 아이콘이 한 행으로 보이고 한국어 화면에는 EN, 영어 화면에는 KO만 이름 오른쪽에 보인다.
- 모바일 아이콘 링크, 언어 전환, 본문 바로가기, 외부 링크와 Contact를 키보드와 터치로 사용할 수 있다.
- Background 제목과 첫 항목 사이에 구분선 및 삭제한 선의 여백이 없고 두 번째 이후 항목의 구분선은 유지된다.
- 320px, 390px와 1440px 폭, 200% 글자 확대와 움직임 감소 설정에서 내용과 읽는 순서가 유지된다.
- 색상과 포커스 표시가 정한 명암비를 충족한다.
- 한국어 JSON의 문구를 바꾸면 UI 코드를 수정하지 않고 화면에 반영된다.
- 한국어와 영어가 같은 정보 구조, 기여 사실과 비교 조건을 제공한다.

요구사항과 조사 문서의 완성만으로 웹사이트 구현이 완료됐다고 판단하지 않는다.

## 구현 전에 정할 사항

- 배포 방식과 지원 브라우저의 최종 목록.
- `30초 이내 배포` 수치를 홈페이지에 사용할 수 있는 근거와 비교 조건.

어두운 테마, 보조 고정폭 글꼴, 삽화 체계, 복잡한 애니메이션, 겹쳐 뜨는 UI와 입력 양식 체계는 첫 버전 요구사항이 아니다.
