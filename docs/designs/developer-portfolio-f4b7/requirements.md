# 편집형 단일 페이지 개발자 소개 홈페이지 요구사항

개발자 소개 사이트의 홈페이지는 프론트엔드 개발자로서 해결해 온 문제와 확인된 기여를 채용담당자와 개발자에게 소개하는 단일 페이지 기술 프로필이다. 방문자는 다른 페이지로 이동하지 않고도 어떤 문제를 해결해 왔는지, 어떤 기술적 판단을 내리는지, 외부에서 확인할 수 있는 작업이 무엇인지 파악할 수 있어야 한다.

사이트는 `Technical Publication / Career Index / Evidence-driven` 방향을 유지하되, 네비게이션 바 없는 단일 칼럼으로 구성한다. 편집형이라는 이유로 화면을 여러 열로 나누거나 숫자와 문구를 과장되게 강조하지 않는다. 이력서와 포트폴리오의 내용을 그대로 옮기거나 일반적인 포트폴리오 카드 모음으로 재구성하지 않는다.

이 문서는 사이트의 콘텐츠, 시각 규칙과 구현 결과가 충족해야 할 요구사항이다. 외부 사이트 관찰과 적용 판단은 [개인 사이트 재조사](references/personal-site-recheck.md)에서 구분하며, 모바일 프로필 링크의 아이콘과 반응형 배치 근거는 [모바일 프로필 아이콘 조사](references/mobile-profile-icons.md)에 기록한다. [모바일 Drawer 조사](references/mobile-drawer.md)는 교체 전 판단을 남긴 기록으로만 보존한다.

## 모호한 상황의 확인

작업 중 요구사항의 의미가 분명하지 않으면 임의로 확정하지 않는다. 선택에 따라 방문자가 보게 될 내용이나 조작 방식이 달라지는 경우에는 질문과 선택지를 먼저 제시한다.

답변이 필요한 사항은 미결정으로 남기고 그 답변에 따라 달라지는 작업을 기다린다. 영향을 받지 않는 자료 확인과 준비는 계속할 수 있다.

## 사이트의 역할과 자료 활용

사이트는 다음 질문에 빠르게 답해야 한다.

- 어떤 프론트엔드 문제를 주로 해결해 왔는가?
- 그 설명을 뒷받침하는 실제 기여는 무엇인가?
- 외부에서 직접 확인할 수 있는 기여는 무엇인가?
- 자세한 이력과 기술 글은 어디에서 확인할 수 있는가?

2026년 11월 23일에 제공된 포트폴리오를 홈페이지 소개, 경력과 프로젝트 문구 갱신의 기준 자료로 사용한다. 포트폴리오에서 사용자가 겪은 문제, 담당 범위, 기술적 판단과 확인된 결과를 선별하고, 홈페이지의 섹션별 역할에 맞춰 새로 쓴다. PDF의 문장, 목차, 도식과 화면 구성을 옮기지 않는다.

기존 문구와 새 포트폴리오의 수치가 다르면 지표의 정의와 측정 조건을 확인한다. 새 포트폴리오의 측정 결과를 쓰는 경우 이전 자료의 수치나 조건과 섞지 않는다. 회사 내부 화면, 비공개 시스템과 확인되지 않은 기관명이나 고객사 정보는 게재하지 않는다.

개인 웹사이트만 읽어도 각 경력에서 누구에게 어떤 가치를 제공했고, 그 설명을 뒷받침하는 변화와 근거가 무엇인지 알 수 있어야 한다. 구현 방식은 결과를 이해하는 데 필요한 정도만 설명하며 코드, 처리 순서, 시행착오와 재현 절차를 포함한 긴 해결 과정은 `blog.nwlee.com`에서 관리한다. 블로그, 이력서, GitHub와 LinkedIn은 목적이 드러나는 이름으로 연결한다.

## 개발자 소개와 편집 기준

소개에서 앞세울 기준은 다음 문장이다.

> 사용자가 서비스를 이용하는 데 지장을 주는 문제의 원인을 찾고, 서비스 요구사항과 기존 시스템에 맞는 해결 방법을 설계하는 프론트엔드 엔지니어.

이 문장은 콘텐츠를 고르는 기준이며 첫 화면에 그대로 사용해야 하는 고정 문구는 아니다. 실제 소개 문구는 사실과 수치 조건을 유지하면서 자연스러운 한국어로 다듬는다.

- `React를 잘합니다`처럼 근거 없는 자기평가보다 실제 변화, 수치와 외부에서 확인 가능한 기여를 먼저 보여준다.
- 기술 이름은 사용한 이유나 결과를 설명하는 문장에 포함한다. Projects의 기간과 기술 표기는 기존 위치에 둔다.
- 수치는 설명 문장의 일부로 둔다. 큰 숫자, 강조색과 별도 성과판으로 시선을 끌지 않는다.
- 수치는 대상과 비교 조건을 함께 쓴다. 새 비율이나 성과를 계산해 보태지 않는다.
- `설계`, `주도`, `담당`과 `검증`은 자료에서 확인되는 역할에만 사용한다.
- 회사 프로젝트를 장기간 운영한 독립 서비스처럼 표현하거나 짧은 수행 기간을 앞세워 강조하지 않는다.
- 회사 요약은 제공한 가치, 기여 제목은 달라진 결과, 본문은 그 결과를 뒷받침하는 문제와 근거를 맡는다. 같은 사실이나 확인 행위를 여러 단계에서 반복하지 않는다.
- 성과를 부정하는 방어적 설명은 방문자용 본문에 넣지 않는다. 비교 조건을 문장 안에 정확히 밝히고, 자료가 뒷받침하지 않는 해석은 주장하지 않는다.

## 한 페이지의 정보 순서

`/` 한 페이지를 다음 순서로 구성한다.

1. Identity
2. Experience
3. Open Source
4. Projects
5. Guides
6. Background
7. Contact와 Footer

개인 프로젝트 영역은 두 언어에서 `Projects`로 표시하고, 직접 이동 주소는 `#projects`를 사용한다. 문구 키, 타입과 컴포넌트도 프로젝트라는 뜻에 맞춰 이름을 정한다.

별도의 `Selected Work`, `Skills` 영역이나 프로젝트 목록을 중복해서 만들지 않는다. 경력과 프로젝트의 내부 상세 페이지도 추가하지 않는다. 문구 개선 사례는 [쇼케이스 요구사항](../better-terms-showcase-6e2/requirements.md)에 따라 `/projects/terms`에서 보여준다. About은 Identity가 대신한다. 개발자 소개 화면은 모든 화면 폭에서 같은 순서로 세로 스크롤하며 읽는다.

네비게이션 바, 고정 목차, 메뉴 버튼과 Drawer를 만들지 않는다. 데스크톱에서는 외부 자료 링크를 소개 본문에 유지하고 언어 선택은 화면 오른쪽 상단에 둔다. 모바일에서는 외부 자료 링크를 같은 본문 위치의 아이콘 목록으로 바꾸고 현재 화면과 다른 언어 하나만 이름 오른쪽에 표시한다. 키보드 사용을 위한 본문 바로가기와 기존 영역 id를 통한 직접 이동은 유지한다.

## Identity

첫 영역에는 이름, `Frontend Engineer`, 한두 문장의 소개와 GitHub, Blog, LinkedIn 및 Résumé 링크를 둔다. 보조 문장은 대용량 응답을 처리할 때 화면이 멈추는 문제와 여러 탭에서 같은 메모를 편집할 때 일부 입력이 사라지는 문제 가운데 소개를 뒷받침할 사례를 사용한다. 기술 이름은 해결한 문제와 연결해 설명한다.

데스크톱에서는 네 링크를 현재처럼 한 행에서 줄바꿈 가능한 텍스트 목록으로 표시한다. 모바일에서는 같은 순서와 목적지를 유지한 아이콘 목록을 한 행에 표시하며 텍스트 목록은 숨긴다. 아이콘 목록은 본문 왼쪽 기준선에서 시작하고 인접한 링크 사이에 같은 간격을 둔다. 남는 가로 너비를 링크 사이에 분배하지 않는다. 각 아이콘 링크는 44px 조작 영역을 유지하고 보이는 SVG는 화면 폭에 따라 24px에서 최소 18px까지 줄어들 수 있다. 목록은 줄바꿈하지 않으며 320px 이하에서도 페이지의 가로 오버플로우를 만들지 않아야 한다.

이름과 언어 링크는 하나의 가로 Flex 행에 두고 `align-items: center`로 세로축 중앙을 맞춘다. 데스크톱에서는 KO와 EN을 모두 표시하고 모바일에서는 한국어 화면에 EN, 영어 화면에 KO만 표시한다. 양쪽 요소를 배치할 때 `position: absolute`나 아이콘 전용 위치 보정을 사용하지 않는다.

프로필 사진, 기술 로고 모음, 숙련도 표시, 성과 대시보드, 3D 물체, 추정한 회사 화면과 터미널 모양을 넣지 않는다. Identity에 `100vh`를 강제하지 않고 다음 Experience의 시작이 자연스럽게 이어지게 한다.

## Experience

Experience의 최상위 단위는 회사다. 회사 안에서는 SI 프로젝트를 각각 전시하지 않고 확인된 `Engineering Contribution`으로 편집한다.

`Experience` 제목 아래에는 영역의 작성 방식이나 웹사이트 편집 방식을 설명하는 도입 문구를 두지 않는다. 제목 다음의 첫 회사 앞에 구분선을 넣지 않으며, 도입 문구와 구분선을 제거한 자리에 빈 여백을 남기지 않는다.

각 회사에는 회사명, 기간, 역할과 사용자가 얻은 변화나 운영상 가치를 요약하고 그 아래에 기여 설명을 이어 쓴다. 회사 정보와 기여를 좌우 열로 나누거나 독립적인 대형 카드로 만들지 않는다.

각 회사의 기여 항목은 제목과 본문 문단으로 표시한다. 기여 하단의 짧은 설명, 슬래시, 기술 목록과 그 줄에 사용하던 여백을 제거한다. 회사명, 재직 기간, 역할과 회사 소개는 기존 위치에 둔다.

각 기여에는 어떤 기능이나 사용 상황이 나아졌는지, 그 변화를 어떤 근거로 확인할 수 있는지가 먼저 드러나야 한다. 기술 선택과 구현 방식은 가치와 결과를 설명하는 데 필요한 내용만 남긴다. 항목의 분량을 억지로 맞추거나 모든 항목에 같은 소제목을 반복하지 않으며, 자료가 뒷받침하는 내용만 서술한다.

인공지능팩토리의 소개는 다음 사례를 중심으로 갱신한다. 사용자에게 생긴 변화와 담당 범위가 드러나는 제목과 설명을 사용한다.

- **실행 이력 화면의 응답 처리:** Web Worker로 API 요청, JSON 파싱과 화면용 데이터 변환을 옮긴 판단을 설명한다. 문제가 발생한 동일 응답으로 두 방식을 각각 3회 측정했을 때 포트폴리오가 제시한 페이지 렌더링 지연은 약 360 ms에서 50 ms 이하로 줄었다. 이 수치는 기존 최대 프레임 갱신 시간 간격과 별개의 지표다. 새로고침 후에도 사용량 차트의 이력과 실시간 값을 확인할 수 있게 한 변경은 REST와 SSE 값이 서로 덮어쓰던 문제의 해결로 설명한다. (4~7쪽)
- **호스트 연동용 페이지 모듈:** 호스트가 라우팅을 정하고 호스트 코드를 수정할 수 없는 상황에서 페이지 단위로 통합한 경험을 소개한다. 호스트의 QueryClient가 있으면 공유하고, 없으면 패키지의 공용 QueryClient를 쓰는 방식과 스타일 충돌 대응은 통합 조건을 이해하는 데 필요한 만큼 설명한다. (8~10쪽)
- **서버 사용량 대시보드:** 브라우저가 Next.js API를 통해 표시할 값만 받는 조회 방식과, 첫 조회 이후 마지막으로 받은 시각보다 새로운 값만 요청한 변경을 설명한다. 약 600초 동안 전체 구간을 반복 조회한 경우의 누적 응답 크기 약 96.5 MB와 최신 값만 요청한 경우의 약 41 KB를 비교한다. (13쪽)
- **문서 생성과 결과 확인:** 정기 조회를 작업 단계가 바뀔 때 상세 정보를 확인하는 방식으로 바꿔 작업 한 건의 상세 API 조회가 150~200회에서 30회로 줄어든 기록을 사용한다. 생성 문서를 내려받기 전에 항목별 작성 상태, 초안과 문서 생성 관련 정보를 확인할 수 있게 한 UI 설계와 API 협의와 완료 이벤트 직후 다운로드를 활성화한 변경도 소개한다. (14~15쪽)

도커 이미지 실행 플랫폼의 병렬 작업은 작업 Pod별 사용량 차트와 화면 상태를 설명하는 데 필요한 경우에만 소개한다. 메시지 수신과 실행 엔진에서 맡은 역할을 함께 다룰 때에는 프론트엔드 기여와 구분한다. (11~12쪽)

AI 채팅의 스트리밍 사례는 일반 텍스트와 SSE 필드가 포함된 응답을 같은 화면에서 표시하기 위해, SSE 필드가 청크 경계에서 나뉘었을 때 형식 판별을 보류한 판단을 중심으로 소개한다. 회사 경력에 배치하려면 담당 회사와 공개 가능한 설명 범위를 먼저 확인한다. (16쪽)

크러스트유니버스 및 Quarkonix 경력도 결과만 압축하지 않는다. 주기적 refetch 환경의 optimistic update, Vite 설정과 React lazy loading 및 적용 절차 문서화, Chrome DevTools를 이용한 WebSocket 연결 중단 원인 확인을 각각 설명한다. 어느 회사의 일인지 추가 근거 없이 분리하거나 확인되지 않은 오류 원인, 수정 코드와 성과 수치를 만들지 않는다.

현재 기여는 본문만으로 이해할 수 있게 구성한다. 기존 기술 도식은 문장으로 대체하며, 자세한 구조도와 코드는 블로그에서 설명한다.

## Open Source

React Router와 Outline 기여를 회사 경력과 구분된 외부 확인 자료로 소개한다. 큰 프로젝트 카드나 GitHub 화면 이미지 대신 변경 내용, 병합 상태, 공식 릴리스와 PR 링크를 읽기 쉬운 행으로 제공한다.

영역의 작성 방식이나 웹사이트 편집 방식을 설명하는 도입 문구는 두지 않는다. 제목 다음의 첫 기여 앞에 구분선을 넣지 않고 불필요한 빈 여백도 만들지 않는다. 병합 상태와 공식 릴리스 포함 여부는 각 항목의 릴리스 및 PR 링크로 확인할 수 있게 한다.

- React Router PR #14689와 v7.13.1
- Outline PR #10759와 v1.2.0

실시간 별 수, 기여 횟수나 저장소 로고 모음을 추가하지 않는다.

## Projects

`Projects`에는 회사 Experience와 구분한 개인 프로젝트를 소개한다. `회사 프로젝트 밖에서 문제를 정의하고 구현한 작업입니다.`처럼 사이트의 편집 방식을 설명하는 도입 문구는 두지 않는다. 제목 다음의 첫 프로젝트 앞에는 구분선을 넣지 않고 32px 뒤에 내용을 시작한다. 프로젝트를 옆으로 배치하거나 한쪽을 어긋나게 놓지 않는다. `#projects` 주소에서 이 영역으로 바로 이동할 수 있어야 한다.

프로젝트 설명은 여러 문단으로 구성한다. 시작한 이유와 사용자가 얻는 이점, 직접 발견하고 해결한 문제를 내용에 맞게 나눈다. 같은 사실을 되풀이하거나 문단 수를 맞추려고 설명을 늘리지 않는다. 한국어와 영어에서 같은 사실을 읽을 수 있어야 하며, 코드 작성 방법과 상세한 구현 순서를 중심으로 설명하지 않는다.

- **AI Agent Workflow:** 스크립트가 일상 표현과 문맥에 따라 뜻이 달라지는 표현을 찾고, AI 에이전트가 대상과 동작을 확인해 문장을 수정하는 절차를 소개한다. 문서 작성 스킬은 문서의 목적과 의도에 맞는 구조를 적용하고 필요한 정보가 있으면 사용자에게 알린다. 표현 개선 사례는 쇼케이스로 연결한다. (27~28쪽)
- **Offline Translation Web App:** 사용할 언어의 모델을 미리 저장한 뒤 네트워크 연결 없이 한국어와 영어, 한국어와 일본어 사이를 번역하는 사용 방식을 먼저 설명한다. Web Worker, IndexedDB, 브라우저 캐시와 GitHub Actions 배포 자동화를 그 방식을 구현한 기술 정보로 제공한다. `30초 이내 배포`는 근거와 조건을 확인한 경우에만 사용한다.
- **Personal Notes Workspace:** 첫 문단에 지침과 명령을 기록하고, 필요한 내용을 골라 한 번에 복사하는 용도를 설명한다. 이후 다중 탭 편집 동기화와 E2E 테스트 설계, ESLint 진입점 규칙, 키보드 접근성과 기능별 Provider를 각각 한 문단에 설명한다. 기간은 기존 한국어 및 영어 표기를 유지한다. (17~25쪽)

실제 서비스로 이동하는 링크는 프로젝트 제목에 둔다. Personal Notes Workspace는 제목을 누르면 메모 앱으로 이동하고, 제목 끝에 외부 링크 아이콘을 표시한다. 제목과 아이콘은 함께 누를 수 있어야 하며, 같은 앱 링크를 설명 아래에 반복하지 않는다.

저장소와 문구 개선 사례 링크는 설명의 마지막 문단 아래, 기간 및 기술 정보 앞에 둔다. AI Agent Workflow에는 GitHub 저장소와 문구 개선 사례 링크를, Personal Notes Workspace에는 GitHub 저장소 링크를 제공한다. 개발자가 아닌 방문자도 목적을 알 수 있도록 링크 이름을 텍스트로 표시한다.

서비스 주소가 없는 AI Agent Workflow와 Offline Translation Web App의 제목은 일반 제목으로 유지한다. 저장소나 문구 개선 사례를 서비스 링크로 대신 연결하지 않는다. 연결할 주소와 배치 근거는 [프로젝트 링크와 문단 구성 조사](references/project-links-and-paragraphs.md)에 있다.

일기 관리 및 분석 팀 프로젝트는 홈페이지의 필수 소개 항목이 아니다. 개인 메모 앱의 선정 근거는 [프로젝트 선정](decisions/project-availability.md)에 있다. 이후 새로운 개인 프로젝트를 추가할 때에는 개발자의 판단과 확인 가능한 결과를 보태는지 먼저 확인한다.

## Guides

한국어와 영어 홈페이지에서 `Projects` 다음과 `Background` 앞에 `Guides`를 배치한다. 목록의 각 항목은 하나의 코드 가이드 주제를 소개한다. 첫 버전에는 `Frontend` 항목 하나를 표시한다.

한국어 홈페이지에서 `Guides`의 설명은 다음 문구를 사용한다.

> AI가 플랜을 세우고 작업을 진행하는데 사용할 수 있는 가이드를 지속적으로 관리하고 있습니다.

### Frontend

- 항목 제목 `Frontend`는 `/codes/frontend`로 연결하는 링크로 표시한다. 제목에 밑줄을 표시하고 마우스를 올리면 제목과 밑줄이 브랜드 빨간색으로 바뀐다.
- 한국어 항목 설명은 “프론트엔드, 컴포넌트 관리 관련 코드 규칙”으로 표시한다.
- 제목은 왼쪽에, Markdown 원문 아이콘은 오른쪽에 배치한다. 두 요소를 포함하는 Flex 행에 `justify-content: space-between`과 `align-items: center`를 적용한다.
- 오른쪽의 파란색 Markdown 아이콘은 `/codes/frontend.md`로 연결한다. 아이콘 링크에 보조 기술이 전달할 수 있는 접근 가능한 이름을 지정한다. 이 주소에서 [frontend.md](codes/frontend.md) 전체를 하나의 Markdown 파일로 제공한다.

## Background와 Contact

Background에는 학력, 정보처리기사와 TOEIC Speaking 정보를 압축해서 제공한다. 교육 과정과 단기 활동은 이력서에 남기고 첫 버전 홈페이지에는 넣지 않는다. 제목 다음의 첫 항목 앞에 구분선을 넣지 않고 32px 뒤에 내용을 시작한다. 삭제한 선의 padding과 빈 여백을 남기지 않으며 두 번째 이후 항목의 구분선은 유지한다.

Contact는 별도 안내 문구 없이 Email, GitHub, Blog, LinkedIn과 Résumé를 나열한다. 제목 다음의 첫 링크 앞에 구분선을 넣지 않고 32px 뒤에 내용을 시작한다. 삭제한 문구와 선의 여백은 남기지 않는다. 전화번호와 연락 양식은 넣지 않는다.

## 글과 언어 관리

한국어 화면을 먼저 제작하고 확인한 다음 영어 문구를 추가한다. 소개, 제목, 설명, 링크 이름과 상태 문구는 UI 코드와 분리한 JSON으로 관리한다. 한국어는 `src/shared/terms/ko.json`, 영어는 `src/shared/terms/en.json`에서 관리한다.

블로그 글 목록과 검색 기능은 홈페이지에 복제하지 않는다. Identity와 Contact에서 Blog로 이동할 수 있게 한다. 한국어 `/`와 영어 `/en/`는 같은 UI와 정보 순서를 사용한다. 언어 전환을 없애지 않는다. 데스크톱에서는 화면 오른쪽 상단에 KO와 EN을 가로 Flex 목록으로 표시하고 현재 언어는 글자와 `aria-current="page"`로 함께 구분한다. 모바일에서는 현재 언어를 반복하지 않고 한국어 화면에는 EN, 영어 화면에는 KO 링크 하나만 표시한다.

## 편집형 시각 규칙

화면은 개발자의 소개와 경력을 차례로 읽는 한 편의 글처럼 구성한다. 장식보다 내용을 먼저 읽게 하고, 주장보다 근거를 먼저 보여준다.

- 카드 대신 글자 크기와 굵기, 여백, 정렬과 얇은 구분선으로 정보의 위계를 만든다.
- 내용에 맞춰 문단 길이를 정하되, 별도 수치 블록이나 과장된 인용문으로 강조하지 않는다.
- 연도, 역할과 기술 정보도 본문 위나 아래의 같은 칼럼에 둔다. 장식용 영역 번호와 옆 칼럼은 사용하지 않는다.
- 그래픽을 제거해도 의미가 그대로라면 그래픽을 만들지 않는다.
- 다음 영역의 강한 위쪽 구분선과 현재 영역의 아래쪽 구분선 사이에 내용이 없다면 강한 구분선 하나만 남긴다. 항목 사이의 구분선은 유지한다.
- 페이지 기본 바탕은 흰색 하나로 유지한다. 반복되는 영역 배경과 카드 그림자를 사용하지 않는다.
- 둥근 모서리는 설명용 보조 영역에 필요한 경우 최대 6px까지만 사용한다. 큰 둥근 카드와 pill 태그를 기본 표현으로 사용하지 않는다.

## 글꼴과 글자 체계

기본 글꼴은 `Pretendard Variable`, `Pretendard`, `system-ui` 순서로 사용한다. 글꼴 굵기는 400, 500, 600과 700 네 단계로 제한하고 800~900을 장식용으로 추가하지 않는다.

- 이름과 영역 제목은 본문보다 구별되지만 화면을 지배하지 않는 크기와 굵기로 표시한다.
- 소개 문구도 본문으로 배치하며 대형 슬로건처럼 배치하지 않는다.
- 본문은 1rem, 400, 줄 높이 1.7~1.75를 기본으로 한다.
- 날짜와 기술 정보는 .875rem을 기본으로 한다.
- 수치 전용 글자 단계는 없앤다. 수치와 조건은 본문과 같은 크기로 읽는다.

이름, 소개, 경력과 연락처는 같은 본문 폭과 왼쪽 기준선을 사용한다. 제목 크기와 간격의 구현 시작값은 `DESIGN.md`에서 관리하고 한국어 및 영어 화면을 보고 조정한다. 크기, 굵기, 여백과 정렬로 차이를 만들며 색만으로 위계를 대신하지 않는다.

- Brand hover: `#B4233C`
- Brand subtle: `#FFF1F3`
- Brand subtle strong: `#FDE4E8`
- Surface default: `#FFFFFF`
- Surface subtle: `#F7F7F8`
- Text primary: `#18181B`
- Text secondary: `#52525B`
- Text muted: `#71717A`
- Border default: `#E4E4E7`

`#EE5166`은 흰색 위 일반 본문이나 보조 정보의 글자색으로 사용하지 않는다. 일반 크기의 브랜드 글자와 링크에는 `#C62A44` 또는 그보다 대비가 높은 색을 사용한다. 색만으로 전후 변화, 링크나 현재 상태를 전달하지 않는다. 스킬 문구 비교에 쓰는 배경색은 [쇼케이스 요구사항](../better-terms-showcase-6e2/requirements.md)을 따른다.

## 여백과 반응형 배치

기본 여백 값은 `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 128`을 사용한다. 반복되는 관계를 표현하는 값만 디자인 토큰으로 만든다.

데스크톱과 모바일 모두 한 열이다. 페이지 바깥 여백만 늘어나며, 회사 정보, 기여, 오픈소스, 독립 작업, 학력과 연락처를 각각 다른 열로 분리하지 않는다. 좌우 여백은 `clamp(1rem, 3vw, 2rem)`을 유지하고 긴 본문을 읽기 편한 최대 폭을 `DESIGN.md`에 기록한다.

반응형 분기는 프로필 링크의 표현과 언어 링크 수에만 사용한다. 데스크톱 외부 링크는 줄바꿈 가능한 가로 텍스트 목록을 유지하고 모바일에서는 본문 왼쪽에서 시작하는 가로 아이콘 목록으로 바꾼다. 모바일 목록에는 일정한 `gap`을 사용하며 남는 너비를 분산하지 않는다. 아이콘의 보이는 크기는 CSS `clamp()`로 점진적으로 줄이되 조작 영역은 44px로 유지한다. 목록을 줄바꿈하거나 DOM 순서를 CSS `order`로 바꾸지 않는다.

기존 1200px 바깥 구성, 48rem과 70rem의 다중 열 전환 및 42rem, 36rem과 34rem의 내부 가로 배치 전환은 폐기한다. 단일 칼럼이 유지되는 구성에 컨테이너 쿼리를 형식적으로 추가하지 않는다.

화면 너비가 줄어도 본문 내용과 표시 순서를 유지한다. 글자 크기를 줄이거나 가로 스크롤, 캐러셀, 접이식 영역에 내용을 배치해 표시 분량을 줄이지 않는다. 같은 문장 안의 짧은 링크와 메타정보는 줄바꿈할 수 있다.

## 조작과 움직임

주소 이동은 기본 HTML 링크를 사용한다. 마우스를 올린 상태, 키보드 포커스, 누르는 상태와 필요한 현재 위치를 분명하게 표현한다. 외부 링크를 새 창으로 여는 동작을 기본값으로 강제하지 않는다.

모바일 프로필 아이콘도 기본 HTML 링크로 제공한다. 아이콘은 링크 목적을 대신해 읽히지 않게 보조 기술에서 제외하고, 각 링크에는 기존 텍스트와 목적 설명을 이용한 접근 가능한 이름을 제공한다. 링크 목록을 열고 닫는 상태, 배경 스크롤 제어와 클라이언트 script는 추가하지 않는다.

움직임은 링크 반응, 현재 위치와 짧은 상태 변화 설명에만 사용한다. 모든 영역의 자동 등장, 시차 효과, 커서 대체, 숫자 증가 애니메이션과 계속 움직이는 배경을 사용하지 않는다. `prefers-reduced-motion: reduce`에서는 필수적이지 않은 변형과 움직임을 제거하거나 즉시 전환한다. 콘텐츠를 애니메이션 완료 뒤에만 보이게 만들지 않는다.

## 접근성

접근성 목표는 WCAG 2.2 AA다.

- 문서 구조에 맞는 `header`, `main`, `section`과 `footer`를 사용하고 개발자 이름에 하나의 `h1`을 둔다. `header`는 회사나 영역의 제목 묶음에 사용할 수 있지만 네비게이션 바를 만들 근거로 쓰지 않는다.
- 일반 텍스트는 최소 4.5:1, 큰 텍스트는 최소 3:1의 명암비를 충족한다.
- 의미 있는 그래픽과 직접 만든 포커스 표시는 인접 색과 최소 3:1의 명암비를 충족한다.
- 포인터 대상은 원칙적으로 24×24 CSS px 이상이거나 WCAG가 명시한 예외를 충족한다.
- 모든 링크와 조작 요소를 키보드로 사용할 수 있고 `focus-visible` 표시가 보여야 한다.
- 모바일 프로필 아이콘 링크는 각각 목적이 구분되는 접근 가능한 이름과 44×44 CSS px 조작 영역을 제공해야 한다.
- 모바일 프로필 아이콘의 첫 조작 영역은 본문 왼쪽 기준선에서 시작하고, 화면 폭이 달라져도 인접 조작 영역 사이의 간격은 같아야 한다.
- 고정 요소가 포커스를 완전히 가리지 않아야 한다. 같은 페이지 안의 이동에는 필요한 `scroll-margin`을 둔다.
- 320px 폭과 200% 글자 확대에서도 정보와 조작 수단이 사라지거나 페이지 전체에 가로 스크롤이 생기지 않아야 한다.
- 의미 있는 도식에는 같은 내용을 전달하는 인접 본문 또는 `figcaption`을 제공한다.

## 기본 구성에서 제외하는 표현

검은 바탕과 네온 그라디언트, glassmorphism, Bento grid, 큰 둥근 카드 반복, 떠 있는 구체와 입체 물체, 기술 로고의 반복 이동, 가짜 터미널, 움직이는 격자 배경, 커서 조명, 장식용 차트, 프로젝트 카드 격자, 별도 성과 대시보드, 추천사와 일반적인 SaaS 행동 유도 영역을 사용하지 않는다.

Drawer, modal, toast, table, tab, filter, search, pagination, carousel, tooltip, form validation, loading skeleton, empty state와 command palette를 추가하지 않는다. 모바일 프로필 링크를 숨기는 메뉴, 중첩 목록과 별도 행동 유도 문구를 넣지 않는다.

## 디자인 체계와 제작 순서

현재 Astro와 Tailwind CSS 기반의 한국어 및 영어 정적 페이지가 있다. 이번 배치 변경은 기존 FSD 구성, JSON 문구 관리, 자체 제공 Pretendard와 정적 제공 방식을 유지한다. 모바일 프로필의 네 SVG와 Guides의 Markdown 아이콘은 Astro 빌드 시점 컴포넌트인 `phosphor-astro`를 사용한다. UI 컴포넌트 모음과 클라이언트 런타임은 추가하지 않는다.

저장소 최상위 `DESIGN.md`에는 적용할 시각 규칙과 현재 구현에 반영했는지를 구분해 기록한다. 변경 플랜은 기존 컴포넌트와 타입을 교체 및 제거할 위치를 명시한다. 문서만 바뀐 상태를 화면 구현 완료로 표시하지 않는다.

## 완료 기준

첫 버전은 다음 항목을 실제 화면에서 확인할 수 있어야 한다.

- 한 페이지를 읽는 것만으로 개발자가 해결해 온 문제, 기술적 판단과 확인된 기여를 설명할 수 있다.
- Identity에서 Experience로 이어지며 사용자가 얻은 변화, 개발자의 기여와 이를 뒷받침하는 근거를 본문만으로 이해할 수 있다. 수치는 비교 대상과 조건을 같은 문단에서 읽을 수 있다.
- 한국어와 영어의 Experience에는 회사명, 재직 기간, 역할과 소개가 표시된다. 모든 회사의 기여 항목에는 제목과 본문이 표시되며, 하단 보조 정보 줄과 그 줄에 사용하던 여백이 없다.
- React Router와 Outline 기여를 실제 PR 및 공식 릴리스에서 확인할 수 있다.
- 두 언어에서 `Projects` 제목 아래에 AI Agent Workflow, Personal Notes Workspace와 Offline Translation Web App이 회사 경력과 구분되어 표시된다.
- 소개와 기여 설명은 PDF 문구를 옮기지 않고, 각 영역에서 방문자가 알아야 할 문제, 판단과 결과를 전달한다. 회사 경력, 개인 프로젝트와 오픈소스 기여가 기존 정보 순서에서 구분된다.
- 경력 수치는 한국어와 영어 모두에서 새 포트폴리오의 지표, 비교 조건 및 결과와 일치한다. 실행 이력 화면의 렌더링 지연, 대시보드의 누적 응답 크기와 문서 생성 작업의 상세 API 조회 횟수를 각각 확인한다.
- 한국어와 영어에서 AI Agent Workflow는 두 문단, Personal Notes Workspace는 다섯 문단으로 표시하며, 같은 목적과 기여 사실을 전달한다. Personal Notes Workspace에서 여러 탭의 편집 내용을 보존한 방법과 확인 범위를 파악할 수 있고, AI Agent Workflow에서 문구 검사와 문맥에 따른 수정의 관계를 이해할 수 있다.
- Personal Notes Workspace의 제목과 외부 링크 아이콘을 누르면 실제 메모 앱이 열린다. AI Agent Workflow의 저장소와 문구 개선 사례, Personal Notes Workspace의 저장소는 설명 아래에서 열 수 있다. `#projects`에서 Projects로 바로 이동할 수 있다.
- 한국어와 영어 홈페이지에서 `Projects`, `Guides`, `Background` 순서로 표시된다. `Guides`에는 소개 문구와 `Frontend` 항목 하나가 표시된다.
- `Frontend` 제목에서 상세 페이지를, 같은 행 오른쪽의 파란색 아이콘에서 Markdown 원문을 열 수 있다. 제목에는 기본 밑줄이 표시되고 마우스를 올리면 글자와 밑줄이 빨간색으로 바뀐다. 두 링크에는 별도 표시용 문구 없이 키보드로 이동할 수 있다.
- `Frontend` 상세 페이지에 지정된 소개 문구가 표시되고, [Frontend 상세 페이지](#frontend-상세-페이지)에 정한 순서대로 네 주제를 읽을 수 있다. 각 주제는 컴포넌트의 배치와 구성 사례에서 설명한다.
- Frontend와 Terms 상세 페이지의 본문 폭이 일치한다. 두 페이지에서 홈 아이콘과 제목이 같은 행의 가로 및 세로 중앙에 정렬되고, 아이콘을 선택하면 홈페이지로 이동한다.
- 상세 페이지 본문은 원문의 서술 방식과 코드 예시를 보존한다. 화면 문구에서 규칙의 대상, 행동과 적용 조건을 구별할 수 있다.
- 네비게이션 바와 다중 칼럼이 없고, 숫자와 소개 문구를 대형 글자로 강조하지 않는다.
- Experience와 Open Source 제목 다음에 편집 방식을 설명하는 도입 문구, 첫 항목 구분선과 그 자리를 대신하는 빈 여백이 없다.
- 데스크톱에서 외부 링크가 소개 본문에 있고 KO와 EN이 화면 오른쪽 상단에 있다. 모바일에서는 같은 위치에 네 외부 링크의 아이콘이 한 행으로 보이고 한국어 화면에는 EN, 영어 화면에는 KO만 이름 오른쪽에 보인다.
- 모바일 아이콘 링크, 언어 전환, 본문 바로가기, 외부 링크와 Contact를 키보드와 터치로 사용할 수 있다.
- Background 제목과 첫 항목 사이에 구분선 및 삭제한 선의 여백이 없고 두 번째 이후 항목의 구분선은 유지된다.
- 320px, 390px와 1440px 화면 너비, 200% 글자 확대와 움직임 감소 설정에서 본문 내용과 표시 순서가 유지된다.
- 색상과 포커스 표시가 정한 명암비를 충족한다.
- 한국어 JSON의 문구를 바꾸면 UI 코드를 수정하지 않고 화면에 반영된다.
- 한국어와 영어가 같은 정보 구조, 기여 사실과 비교 조건을 제공한다.

요구사항과 조사 문서의 완성만으로 웹사이트 구현이 완료됐다고 판단하지 않는다.

웹 서비스에서 문제가 발생하는 조건과 원인을 분석하고, 요구사항과 기존 시스템에 맞는 해결 방법을 설계합니다.

대용량 API 응답 때문에 화면이 멈추는 문제를 해결하기 위해 JSON 파싱과 데이터 변환을 Web Worker로 분리했습니다. 같은 메모를 여러 탭에서 편집할 때는 각 탭에서 발생한 사용자 입력을 보존하기 위해 메모 업데이트 구조를 설계했습니다.

### 인공지능팩토리

- **기간** 2025.08 - 현재
- **소개** 실행 이력 상세 화면, 서버 사용량 대시보드와 AI 문서 생성 서비스의 프론트엔드를 개발했습니다. 대용량 API 응답으로 화면이 멈추는 문제를 해결하고 서버 리소스 데이터 API의 누적 응답 전송량을 줄였습니다. 사용자가 문서를 내려받기 전에 초안과 문서 생성 정보를 확인할 수 있도록 화면을 설계하고 API 데이터 구성 방안에 대해 커뮤니케이션했습니다.

#### 실행 이력 상세 화면의 렌더링 지연 대응

**내용**

일부 실행 이력의 상세 화면을 열면 화면이 멈추는 이슈가 보고되었습니다. 일주일 동안 생성된 실행 이력에서 화면이 멈추는 실행 이력을 식별하고, Chrome DevTools의 네트워크와 성능 패널에서 API 요청 시간과 응답 데이터 처리 시간을 확인했습니다. 응답 크기가 300 MB 이상인 사례에서 API 응답을 화면 표시값으로 변환하는 데 시간이 걸리는 것을 확인했습니다.

실행 이력 상세 화면의 API 요청, JSON 파싱과 표시값 변환은 Web Worker에서 수행하고, 페이지에는 변환된 값만 전달하도록 설계했습니다.

페이지 성능 개선 여부를 확인하기 위해 Web Worker 적용 전후 성능을 측정할 수 있는 테스트 환경을 구성했습니다. 화면에 제공되는 데이터가 유지됨을 확인할 수 있었고, 렌더링 지연은 약 360 ms에서 50 ms 이하로 감소했습니다.

여러 API에서 Worker를 재사용하기 위해 Comlink로 페이지에 정의한 변환 함수를 전달하는 방식과 Codegen으로 API별 모듈을 생성하는 방식을 검토했습니다. Comlink 방식에서는 변환 함수가 메인 스레드에서 실행될 수 있었고, 화면 멈춤을 해결하는 데 API별 모듈 생성이 필요하지 않았습니다. 두 방식을 전부 도입하는 대신 현재 마주한 페이지 문제 해결에 집중했습니다.

#### 외부 서비스의 라우팅과 조회 캐시를 유지하는 페이지 모듈 설계

**내용**

다른 팀의 서비스가 포함된 프로젝트에서 우리 프론트엔드를 라이브러리 형태로 통합하면서도 모듈을 사용하는 팀이 라우팅 구조를 자유롭게 정할 수 있어야 했습니다. 서비스 코드를 임의로 수정하거나 별도 레이아웃을 제공하지 못하는 조건에서, 페이지 모듈을 가져오는 쪽에서 별도 설정 없이 페이지의 화면과 기능을 사용할 수 있도록 구성했습니다.

서비스가 별도의 QueryClient를 제공하면 이를 공유하고, 제공하지 않으면 패키지의 페이지들이 공용 QueryClient를 사용하도록 설계했습니다. 같은 조회 키에 대한 값과 캐시 초기화 규칙이 페이지마다 달라지는 문제를 방지할 수 있었습니다.

배포된 서비스 확인 결과 스타일이 CSS 레이어 외부에 정의되어 있는 경우 Tailwind CSS 레이어 안의 패키지 스타일이 비활성화되는 이슈를 발견했습니다. 패키지 설정에서 Tailwind의 테마, 초기화 스타일과 유틸리티를 레이어 지정 없이 불러오도록 변경했습니다.

#### 도커 이미지 실행 요청 관리 및 실행 구조 개선

**내용**

기존 메시지 서비스는 실행 중인 작업이 끝날 때까지 Kafka에서 다음 요청을 받지 못했습니다. 작업 완료 후가 아닌, 메시지 수신 직후 Kafka 오프셋을 갱신하는 방식을 논의했습니다. 대기 요청을 서비스 메모리에만 저장하면 재시작할 때 그 요청을 잃을 수 있어, 요청과 상태를 데이터베이스에 기록한 뒤 Kafka 오프셋을 갱신하도록 접수 절차를 설계했습니다.

배정 단계에서는 데이터베이스에서 대기 작업을 조회해 미리 생성한 실행용 Pod 중 비어 있는 Pod에 한 건씩 배정했습니다. Pod를 준비할 수 있도록 작업 엔진을 미리 도커 이미지로 빌드할 때 발생하는 여러 이슈에 대응했습니다. 서비스 재시작 뒤에도 대기 작업을 조회할 수 있고, 여러 Pod에서 작업을 동시에 실행할 수 있게 됐습니다.

기존 프론트엔드의 실행 이력 목록 화면에는 Pod별 리소스 사용량을 확인할 수 있도록 차트 탭 UI와 탭 선택 상태를 설계했습니다.

#### 다운로드 전에 문서 초안과 생성 정보 확인

**내용**

사용자 의견을 통해 AI로 생성된 문서의 내용을 확인하려면 파일을 반드시 내려받아야 한다는 불편함이 있음을 확인했습니다. HWPX 렌더링 라이브러리 검토 결과 우리 프로젝트에 도입하기에는 여러 리스크가 있었고, 문서 생성 관련 정보를 제공할 수 없음을 확인했습니다.

문서 상세 내용과 생성 정보를 제공할 수 있도록 사용자 의견을 바탕으로 필요한 응답 필드를 정리해 문서 생성 API 담당자와 협의하고, 화면과 Java 프록시 API를 설계했습니다.

사용자는 파일을 내려받기 전에 항목별 작성 상태와 초안, 문서 생성 관련 정보를 확인할 수 있게 됐습니다.

상세 상태 API의 응답을 기다리는 중에도 문서 생성 완료 이벤트를 수신하면 상세 페이지 링크와 다운로드 버튼을 즉시 활성화하도록 구성했습니다.

#### 문서 생성 상태 조회 횟수 절감

**내용**

문서 생성의 진행 상태를 정기적으로 조회하면, 호출 간격이 짧을 때는 상태가 그대로여도 상세 API 호출이 증가하고 간격이 길 때는 실제 진행 단계가 화면에 늦게 반영될 수 있었습니다.

기존 SSE API가 문서 생성 단계가 바뀔 때만 이벤트를 전송한다는 점을 활용해, 단계 변경 이벤트를 받은 뒤 상세 API를 호출하고 응답에 따라 화면을 갱신하도록 설계했습니다. 문서 생성 한 건당 상세 API 조회 횟수는 150~200회에서 30회로 감소했습니다.

#### 대시보드 전송 효율 개선

**내용**

마지막 요청 시각 이후의 값만 가져오도록 조회 방식을 바꿔 10분 동안의 전송량을 96.5 MB에서 41 KB로 줄였습니다. 브라우저에서 Prometheus를 직접 호출하지 않도록 Next.js API를 설계하고 구현했습니다. 배포된 대시보드의 표시값과 실제 응답을 대조해 정확성을 확인했습니다.

### 오픈소스

#### React Router

**내용**

선택적 매개변수 앞에 슬래시가 빠진 URL도 라우팅 규칙을 준수하는 문제가 있었습니다. Suffix가 없는 패턴에서는 선택적 매개변수와 그 앞의 슬래시를 함께 생략할 수 있도록 URL 일치 규칙을 수정했습니다. 리뷰에서 기존 확장자 패턴의 호환성을 확인하고, 확장자가 붙는 패턴은 슬래시를 유지한 상태에서 매개변수 값만 생략할 수 있도록 했습니다. 잘못 일치하던 URL과 기존 확장자 패턴을 모두 검사하는 테스트를 추가했고, 수정 사항은 v7.13.1에 반영됐습니다.

**링크**

[PR #14689](https://github.com/remix-run/react-router/pull/14689), [v7.13.1 릴리스](https://github.com/remix-run/react-router/releases/tag/react-router@7.13.1)

#### Outline

**내용**

일반 문단과 표 셀에서 인라인 이미지 앞의 마지막 글자를 Delete나 Backspace로 지울 수 없었습니다. 일반 텍스트와 선택 영역의 삭제 동작을 유지할 수 있도록, 텍스트를 선택하지 않은 상태에서 이미지 바로 앞에 남은 한 글자를 지우는 경우에만 별도 규칙을 적용했습니다. 수정 후에는 이미지 앞에 남은 한 글자를 삭제할 수 있게 됐으며, 변경 사항은 v1.2.0에 반영됐습니다.

### 프로젝트

#### AI 에이전트 기반 작업 진행

팀원들이 문서의 내용을 직관적으로 파악할 수 있도록 AI로 문서를 작성할 때 사용할 수 있는 표현 검토 스킬을 설계했습니다. 스크립트가 반복되는 일상 표현과 문맥에 따라 뜻이 달라지는 표현을 발견하면, AI 에이전트가 대상과 동작을 확인한 뒤 문장을 수정합니다. 예를 들어 ‘문서 공유의 경계’를 제한된 공유 설정에서 누가 문서를 열람할 수 있는지 설명하는 문장으로 개선할 수 있습니다.

AI 에이전트가 문서를 작성할 때 사용자의 프롬프트를 잘못 해석하는 상황을 방지하기 위해서 사용자의 문서 작성을 돕는 스킬을 설계했습니다. 작성된 문서에 대해서 문서의 목적과 의도를 파악한 다음 문서에 필요한 구조를 적용합니다. 문서에 필요한 정보가 있다면 사용자에게 명시적으로 안내할 수 있습니다.

#### Personal Notes Workspace

반복해서 쓰는 지침과 명령을 메모에 기록하고, 여러 메모에서 필요한 내용을 골라 순서를 정한 뒤 한 번에 복사할 수 있도록 구현했습니다.

사용자의 메모 수정을 방해하지 않으면서 각 탭의 변경이 보존되도록 Yjs의 Y.Text로 삽입과 삭제가 병합되도록 데이터 구조를 설계했습니다. 탭에 표시한 내용과 저장 내용을 일치시키기 위해 IndexedDB에 먼저 저장한 뒤 BroadcastChannel로 다른 탭에 알리도록 했습니다. 다른 탭은 저장된 변경을 파악하고, 각 탭의 입력이 모두 표시되는지 확인할 E2E 테스트를 설계했습니다.

ESLint와 JS Boundaries로 FSD 계층 사이에서 지정한 진입점만 참조하도록 검사하고, 서버와 브라우저 모듈이 섞이지 않도록 진입점을 구분하도록 했습니다.

React Aria로 일괄 복사 순서 메뉴에 방향키 조작을 추가했습니다. 메뉴를 닫으면 더보기 버튼으로 초점을 돌려주고, 다른 메모를 편집 중이면 순서 저장이 끝나도 입력란의 초점을 유지합니다. 키보드로 패널 너비를 조절하고 메모를 앞으로 옮겨도 Tab 순서가 유지되는지 테스트했습니다.

IndexedDB Provider는 서비스 최상위에, 일괄 복사 Provider는 관련 화면이 공유하는 레이아웃에, 편집 Provider는 각 편집 페이지에 배치했습니다. 자동 저장 테스트에는 필요한 구현만 주입할 수 있고 구현을 바꿔도 UI 코드를 유지할 수 있습니다.

**링크**

[메모 앱](https://notes.nwlee.com), [Personal Notes Workspace 소스 코드](https://github.com/nwleedev/nwleedev/tree/main/apps/notes)

## 고유의 코드 규칙

고유의 코드 스타일, 케이스, 예시 등을 리서치하고 구성한 다음 공식 문서 페이지 형태로 제공하고 싶습니다.

대표 목적은 다음과 같다.

- 다양한 사람들이 코드 스타일을 확인할 수 있도록 한다.
- AI 에이전트가 서비스 개발 플랜을 구성할 때 웹 사이트에 있는 코드 스타일을 참고하여 어떻게 코드를 작성할지 구체적으로 플랜을 작성하도록 한다.

초기 코드 가이드는 홈페이지의 [Guides](#guides)에서 열 수 있다.

### Frontend 상세 페이지

`/codes/frontend`에서는 `frontend.md`의 규칙과 예시를 바탕으로 화면, 기능 컴포넌트와 공용 UI를 어디에 배치하고 어떻게 조합할지 설명한다. 페이지 제목 아래에 다음 소개 문구를 표시한다.

> 프론트엔드 프로젝트에서 컴포넌트를 어떻게 조직하고 관리할지에 대해서 지속적으로 리서치 및 규칙화하고 있습니다.

본문과 하단 영역은 [Terms 쇼케이스](../better-terms-showcase-6e2/requirements.md)와 같은 최대 너비 60rem과 좌우 여백을 사용한다. 제목은 왼쪽에, 홈 아이콘은 오른쪽에 배치한다. 두 요소를 포함하는 Flex 행에 `justify-content: space-between`과 `align-items: center`를 적용한다. 아이콘을 선택하면 `/`로 이동한다.

소개 문구 뒤에 다음 순서로 네 주제를 배치한다.

1. **Provider 기반 의존성 주입.** 기능 구현을 Provider를 통해 전달하는 조건과, 기능을 사용하는 컴포넌트가 Context 값에 접근할 수 있도록 Provider를 배치하는 기준을 설명한다.
2. **Children 기반 합성과 Compound Components 사용.** `children`으로 여러 컴포넌트를 조합하는 방법과 하위 컴포넌트들이 UI 상태를 공유할 때 Compound Components를 사용하는 기준을 설명한다.
3. **네이밍.** 폴더명, 파일명과 타입명으로 컴포넌트와 모듈의 역할을 식별하는 기준을 설명한다.
4. **FSD.** FSD 계층에 따라 모듈을 배치하고 모듈 간 import 방향을 판단하는 기준을 설명한다.

네 주제 제목은 같은 페이지의 각 제목 위치로 이동하는 링크로 표시한다. 제목에는 기존 브랜드 강조색을 사용하고, 제목에 마우스를 올리면 밑줄을 표시한다. 제목 위의 구분선은 제거하고 주제 사이의 여백으로 구분한다.

### 코드 가이드 원문과 작성 기준

페이지를 구성하기 위한 코드 규칙 및 예시 내용은 다음과 같은 위치에 구성된다. 다음은 예시이다.

- docs/designs/developer-portfolio-f4b7/codes/
  - frontend.md
  - backend.md
  - database.md
  - `<topic>`.md

웹에 표시할 항목을 원문에서 선택하고, 화면 구성에 맞춰 항목을 나누거나 재배치할 수 있다. 선택한 규칙의 본문과 코드 예시는 원문을 유지한다.

상세 페이지는 `frontend.md`처럼 코드 예시 앞에 적용 조건과 이유를 설명한다. 규칙의 의미와 서술 방식을 보존한다. 방문자에게 표시하는 본문과 제목에는 일상 표현이나 대상, 행동 또는 적용 조건이 모호한 문구를 사용하지 않는다. 선택한 문구에 교정이 필요하면 원문에서 뜻을 확인해 표현을 다듬고 같은 문구를 화면에 표시한다.

Provider를 설명할 때는 Provider의 하위에 배치하는 컴포넌트, Context에 전달하는 값과 Hook이 반환하는 값을 각각 명시한다. 제목과 일반 본문에서 합성 방식을 가리킬 때는 Children으로 표기한다. React의 Props 이름을 가리키는 인라인 코드와 코드 예시는 `children` 표기를 유지한다.

코드 예시 조사와 작성 기준은 다음과 같다.

- 코드 가이드 문서를 구성할 때 이 저장소의 구현 코드를 참고 자료에서 제외한다.
- 널리 알려져 있고 지속적으로 유지보수되는 외부 오픈소스 저장소에서 코드 예시를 찾는다. 저장소의 인지도와 최근 커밋 또는 릴리스 이력을 확인한다.
- 여러 예시가 해결하려는 문제와 구현을 선택한 이유를 비교한다. 각 예시의 적용 조건을 검토하고 가이드의 목적에 맞게 코드 예시를 작성한다.

codes 폴더에 있는 파일의 경우 공통점은 다음과 같다.

- 파일 상단에는 규칙 목록이 나열되어있다. 그리고 규칙 목록 다음에는 각각의 주제에 대해서 상세 지침이 코드와 함께 작성되어야 한다.
- 상세 지침을 아무렇게 작성하지 않는다. 규칙 목록에 있는 각 규칙에 대해서 직관적으로 이해할 수 있도록 상세 지침을 구성한다.

상세 지침의 경우 다음과 같이 구성되어야 한다.

```
### <세부 주제 제목>

<세부 주제에 대한 간략한 설명>

#### <코드 예시에 대한 짧은 제목>

<이런 코드를 작성해야 하는 이유 OR 작성하지 않아야 하는 이유>

<작성해야 하는 또는 작성하지 않아야 하는 코드 예시>
```

### 가이드 확장

가이드가 늘어나고 주제가 세분화되면 `/codes`에 별도 목록 페이지가 필요한지 검토한다.

만약 페이지가 완성되었다고 판단되면, AI 에이전트가 작업을 진행할 때 코드 규칙을 활용할 수 있도록 규칙을 MCP나 스킬로도 구축하는 방안에 대해서도 검토해주세요.
