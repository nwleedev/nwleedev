# 편집형 단일 페이지 개발자 소개 웹사이트 요구사항

`nwlee.com`은 프론트엔드 개발자로서 해결해 온 문제와 확인된 기여를 채용담당자와 개발자에게 소개하는 단일 페이지 기술 프로필이다. 방문자는 다른 페이지로 이동하지 않고도 어떤 문제를 해결해 왔는지, 어떤 기술적 판단을 내리는지, 외부에서 확인할 수 있는 작업이 무엇인지 파악할 수 있어야 한다.

사이트는 `Technical Publication / Career Index / Evidence-driven` 방향의 편집형 화면으로 제작한다. 이력서와 포트폴리오의 내용을 그대로 옮기거나 일반적인 포트폴리오 카드 모음으로 재구성하지 않는다.

이 문서는 사이트의 콘텐츠, 시각 규칙과 구현 결과가 충족해야 할 요구사항이다. 외부 자료에서 확인한 사실과 구현 중 확인할 항목은 [편집형 디자인 조사](references/editorial-design-system.md)에서 구분한다.

## 모호한 상황의 확인

작업 중 요구사항의 의미가 분명하지 않으면 임의로 확정하지 않는다. 선택에 따라 방문자가 보게 될 내용이나 조작 방식이 달라지는 경우에는 질문과 선택지를 먼저 제시한다.

답변이 필요한 사항은 미결정으로 남기고 그 답변에 따라 달라지는 작업을 기다린다. 영향을 받지 않는 자료 확인과 준비는 계속할 수 있다.

## 사이트의 역할과 자료 활용

사이트는 다음 질문에 빠르게 답해야 한다.

- 어떤 프론트엔드 문제를 주로 해결해 왔는가?
- 그 설명을 뒷받침하는 실제 기여는 무엇인가?
- 외부에서 직접 확인할 수 있는 기여는 무엇인가?
- 자세한 이력과 기술 글은 어디에서 확인할 수 있는가?

이력서, 포트폴리오와 프로젝트에서 확인한 역할, 판단, 변화와 기술 관계를 소개 자료로 사용한다. PDF의 문장, 화면 비율, 분홍색 선과 어두운 하단 영역을 복제하지 않는다. 회사 내부 화면이나 시스템 구조를 추정해서 만들지 않으며, 확인되지 않은 기관명과 고객사 정보도 게재하지 않는다.

상세한 배경, 제약, 구현과 검증 과정은 `blog.nwlee.com`에서 관리한다. 개인 웹사이트에는 판단과 확인된 변화만 간결하게 소개하고 블로그, 이력서, GitHub와 LinkedIn을 목적이 드러나는 이름으로 연결한다.

## 개발자 소개와 편집 기준

소개에서 앞세울 기준은 다음 문장이다.

> 서비스에서 발생하는 문제의 원인을 찾고, 데이터 흐름과 비동기 상태를 개선하며 배포 후 실제 동작까지 확인하는 프론트엔드 엔지니어.

이 문장은 콘텐츠를 고르는 기준이며 첫 화면에 그대로 사용해야 하는 고정 문구는 아니다. 실제 소개 문구는 사실과 수치 조건을 유지하면서 자연스러운 한국어로 다듬는다.

- `React를 잘합니다`처럼 근거 없는 자기평가보다 실제 변화, 수치와 외부에서 확인 가능한 기여를 먼저 보여준다.
- 기술 이름은 독립적인 역량 목록이 아니라 그 기술을 사용한 경험 옆의 보조 정보로 둔다.
- 강한 수치는 별도 성과판으로 분리하지 않고 수치가 나온 경험의 문맥 안에 둔다.
- 수치는 대상과 비교 조건을 함께 쓴다. 새 비율이나 성과를 계산해 보태지 않는다.
- `설계`, `주도`, `담당`과 `검증`은 자료에서 확인되는 역할에만 사용한다.
- 회사 프로젝트를 장기간 운영한 독립 서비스처럼 표현하거나 짧은 수행 기간을 핵심 정보로 강조하지 않는다.

## 한 페이지의 정보 순서

`/` 한 페이지를 다음 순서로 구성한다.

1. Header
2. Identity
3. Experience
4. Open Source
5. Independent Work
6. Background
7. Contact와 Footer

별도의 `Selected Work`, `Skills`, `Projects` 영역과 내부 상세 페이지를 만들지 않는다. 페이지 안의 이동은 Experience, Open Source, Independent Work와 Contact를 가리킨다. About은 Identity가 대신한다.

헤더는 페이지 바탕의 일부로 보이게 구성한다. 떠 있는 도크나 카드로 만들지 않는다. 고정 여부는 실제 페이지 길이와 포커스 가림 여부를 확인한 뒤 결정한다. 좁은 화면에서는 링크를 자연스럽게 줄바꿈할 수 있으면 접이식 메뉴를 추가하지 않는다.

## Identity

첫 영역에는 이름, `Frontend Engineer`, 한두 문장의 소개와 GitHub, Blog, LinkedIn 및 Résumé 링크를 둔다. TypeScript와 React 기반 서비스에서 실시간 데이터, 장시간 작업, 운영 대시보드와 서비스 품질 문제를 해결해 온 경험을 보조 문장으로 설명할 수 있다.

프로필 사진, 기술 로고 모음, 숙련도 표시, 성과 대시보드, 3D 물체, 추정한 회사 화면과 터미널 모양을 넣지 않는다. Identity에 `100vh`를 강제하지 않고 다음 Experience의 시작이 자연스럽게 이어지게 한다.

## Experience

Experience의 최상위 단위는 회사다. 회사 안에서는 SI 프로젝트를 각각 전시하지 않고 확인된 `Engineering Contribution`으로 편집한다.

각 회사에는 기간, 회사명, 역할과 맡은 일을 짧게 설명한다. 회사마다 독립적인 대형 카드를 만들지 않는다.

첫 버전에서 인공지능팩토리의 기여는 다음 네 항목으로 구성한다.

- **Data & Monitoring:** 운영 대시보드의 조회 및 변환 구조 개선과 잘못 표시된 지표 교정. `10분 기준 96.5 MB → 41 KB`를 조건과 함께 표시한다.
- **Async State & Realtime:** 5~10분 문서 생성 작업의 상태 확인을 반복 조회에서 이벤트를 계기로 서버 상태를 다시 확인하는 방식으로 변경. `100~200회 → 10회 이하 상태 요청`을 작업 조건과 함께 표시한다.
- **Browser Runtime & Realtime Data:** 약 5 MB 응답의 호출 및 변환 중 발생하던 `3~4초 화면 정지`를 해결한 경험과 REST 및 실시간 데이터 병합을 설명한다.
- **Reliability & Delivery:** 인증된 실제 사용 흐름을 확인하는 `70개 이상의 실행 가능한 E2E 시나리오`와 그 과정에서 발견한 인증 상태 문제를 설명한다.

크러스트유니버스 및 Quarkonix 경력은 상태 일관성, 로딩 성능과 WebSocket 연결 문제를 압축해서 소개한다. 자료에 정확한 수치가 없는 항목에는 새로운 수치를 만들지 않는다.

설명에 꼭 필요한 경우에만 `Browser → Next.js API → Prometheus`, `Event → Server state check → UI update`, `API → SharedWorker → Main Thread` 관계를 단순한 도식으로 제공한다. 모든 경험에 도식을 반복하지 않는다.

## Open Source

React Router와 Outline 기여를 회사 경력과 구분된 외부 확인 자료로 소개한다. 큰 프로젝트 카드나 GitHub 화면 이미지 대신 변경 내용, 병합 상태, 공식 릴리스와 PR 링크를 읽기 쉬운 행으로 제공한다.

- React Router PR #14689와 v7.13.1
- Outline PR #10759와 v1.2.0

실시간 별 수, 기여 횟수나 저장소 로고 모음을 추가하지 않는다.

## Independent Work

독립 작업은 회사 Experience와 다른 모양으로 구분하고 실제 작업 단위로 소개한다.

- **AI Agent Workflow:** 요구사항, 조사, 결정과 구현을 구분하기 위한 저장소 규칙, Skill과 한국어 문구 검사 작업을 소개한다.
- **Offline Translation Web App:** 네트워크가 없는 환경을 위한 Web Worker, IndexedDB, 브라우저 캐시와 배포 자동화를 소개한다. `30초 이내 배포`는 근거와 조건을 확인한 경우에만 사용한다.

일기 관리 및 분석 팀 프로젝트와 개인 메모 앱은 첫 버전의 필수 소개 항목이 아니다. 이후 새로운 독립 작업을 추가할 때에는 개발자의 판단과 확인 가능한 결과를 보태는지 먼저 확인한다.

## Background와 Contact

Background에는 학력, 정보처리기사와 TOEIC Speaking 정보를 압축해서 제공한다. 교육 과정과 단기 활동은 이력서에 남기고 첫 버전 홈페이지에는 넣지 않는다.

Contact는 Email, GitHub, Blog, LinkedIn과 Résumé를 나열하는 연락처 안내로 구성한다. 전화번호와 연락 양식은 넣지 않는다.

## 글과 언어 관리

한국어 화면을 먼저 제작하고 확인한 다음 영어 문구를 추가한다. 소개, 제목, 설명, 링크 이름과 상태 문구는 UI 코드와 분리한 JSON으로 관리한다. 한국어는 `src/shared/terms/ko.json`, 영어는 `src/shared/terms/en.json`에서 관리한다.

블로그 글 목록과 검색 기능은 홈페이지에 복제하지 않는다. Header, Identity와 Contact에서 Blog로 이동할 수 있게 한다.

## 편집형 시각 규칙

화면은 한 편의 긴 기술 출판물처럼 보여야 한다. 장식보다 내용을 먼저 읽게 하고, 주장보다 근거를 먼저 보여준다.

- 카드 대신 글자 크기와 굵기, 여백, 정렬과 얇은 구분선으로 정보의 위계를 만든다.
- 모든 내용 묶음을 같은 크기와 구조로 반복하지 않는다. 수치 중심, 구조 설명 중심과 외부 근거 중심 항목은 서로 다른 밀도로 편집한다.
- 본문 옆의 낮은 위계 정보에는 연도, 회사, 영역 번호와 기술 맥락을 배치할 수 있다.
- 그래픽을 제거해도 의미가 그대로라면 그래픽을 만들지 않는다.
- 페이지 기본 바탕은 흰색 하나로 유지한다. 반복되는 영역 배경과 카드 그림자를 사용하지 않는다.
- 둥근 모서리는 설명용 보조 영역에 필요한 경우 최대 6px까지만 사용한다. 큰 둥근 카드와 pill 태그를 기본 표현으로 사용하지 않는다.

## 글꼴과 글자 체계

기본 글꼴은 `Pretendard Variable`, `Pretendard`, `system-ui` 순서로 사용한다. 글꼴 굵기는 400, 500, 600과 700 네 단계로 제한하고 800~900을 장식용으로 추가하지 않는다.

- Display: `clamp(2.5rem, 2rem + 2vw, 3.5rem)`, 700, 줄 높이 1.15
- Section Title: `clamp(1.75rem, 1.6rem + .5vw, 2rem)`, 700, 줄 높이 1.3
- Item Title: 1.25~1.375rem, 600, 줄 높이 1.4
- Lead: `clamp(1.125rem, 1.05rem + .3vw, 1.25rem)`, 400 또는 500, 줄 높이 1.65
- Body: 1rem, 400, 줄 높이 1.7~1.75
- Metadata와 Label: .875rem, 500 또는 600
- Metric: `clamp(2rem, 1.6rem + 1.5vw, 2.5rem)`, 700, 줄 높이 1.15

일반 본문은 최대 42rem, 소개와 기술 설명은 최대 48rem을 기준으로 한다. 크기, 굵기, 여백, 위치, 색 순서로 차이를 만들며 색만으로 위계를 대신하지 않는다.

## 색상

첫 버전은 밝은 테마를 기본으로 한다.

- Brand base: `#EE5166`
- Brand strong: `#C62A44`
- Brand hover: `#B4233C`
- Brand subtle: `#FFF1F3`
- Brand subtle strong: `#FDE4E8`
- Surface default: `#FFFFFF`
- Surface subtle: `#F7F7F8`
- Text primary: `#18181B`
- Text secondary: `#52525B`
- Text muted: `#71717A`
- Border default: `#E4E4E7`
- Border strong: `#8B8B95`

`#EE5166`은 흰색 위 일반 본문이나 보조 정보의 글자색으로 사용하지 않는다. 일반 크기의 브랜드 글자와 링크에는 `#C62A44` 또는 그보다 대비가 높은 색을 사용한다. 색만으로 전후 변화, 링크나 현재 상태를 전달하지 않는다.

## 여백과 반응형 배치

기본 여백 값은 `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 128`을 사용한다. 반복되는 관계를 표현하는 값만 디자인 토큰으로 만든다.

페이지 내용은 최대 1200px이며 좌우 여백은 `clamp(1rem, 3vw, 2rem)`으로 조절한다. 기본은 한 열이고, 약 48rem에서 영역 정보와 본문을 나눌 수 있다. 약 70rem에서 12열 편집 그리드와 여백 정보 영역을 사용할 수 있다. 실제 Pretendard 한글 줄바꿈과 콘텐츠 배치가 어색하면 값을 조정하고 그 이유를 `DESIGN.md`에 기록한다.

Contribution, Evidence Row와 System Figure는 페이지 전체 폭이 아니라 각 구성 요소가 사용할 수 있는 폭에 반응하도록 컨테이너 쿼리를 우선 검토한다. 초기 비교값은 각각 약 42rem, 36rem과 34rem이다. 이 값은 전역 반응형 기준으로 승격하지 않는다.

좁은 화면에서도 내용과 읽는 순서를 유지한다. 수치를 지나치게 줄이거나 캐러셀 안에 내용을 숨기지 않고, 기술 도식이 가로로 읽히지 않으면 세로로 바꾼다.

## 조작과 움직임

주소 이동은 기본 HTML 링크를 사용한다. 마우스를 올린 상태, 키보드 포커스, 누르는 상태와 필요한 현재 위치를 분명하게 표현한다. 외부 링크를 새 창으로 여는 동작을 기본값으로 강제하지 않는다.

움직임은 링크 반응, 현재 위치와 짧은 상태 변화 설명에만 사용한다. 모든 영역의 자동 등장, 시차 효과, 커서 대체, 숫자 증가 애니메이션과 계속 움직이는 배경을 사용하지 않는다. `prefers-reduced-motion: reduce`에서는 필수적이지 않은 변형과 움직임을 제거하거나 즉시 전환한다. 콘텐츠를 애니메이션 완료 뒤에만 보이게 만들지 않는다.

## 접근성

접근성 목표는 WCAG 2.2 AA다.

- 문서 구조에 맞는 `header`, `nav`, `main`, `section`과 `footer`를 사용하고 개발자 이름에 하나의 `h1`을 둔다.
- 일반 텍스트는 최소 4.5:1, 큰 텍스트는 최소 3:1의 명암비를 충족한다.
- 의미 있는 그래픽과 직접 만든 포커스 표시는 인접 색과 최소 3:1의 명암비를 충족한다.
- 포인터 대상은 원칙적으로 24×24 CSS px 이상이거나 WCAG가 명시한 예외를 충족한다.
- 모든 링크와 조작 요소를 키보드로 사용할 수 있고 `focus-visible` 표시가 보여야 한다.
- 고정 요소가 포커스를 완전히 가리지 않아야 한다. 같은 페이지 안의 이동에는 필요한 `scroll-margin`을 둔다.
- 320px 폭과 200% 글자 확대에서도 정보와 조작 수단이 사라지거나 페이지 전체에 가로 스크롤이 생기지 않아야 한다.
- 의미 있는 도식에는 같은 내용을 전달하는 인접 본문 또는 `figcaption`을 제공한다.

## 기본 구성에서 제외하는 표현

검은 바탕과 네온 그라디언트, glassmorphism, Bento grid, 큰 둥근 카드 반복, 떠 있는 구체와 입체 물체, 기술 로고 흐름, 가짜 터미널, 움직이는 격자 배경, 커서 조명, 장식용 차트, 프로젝트 카드 격자, 별도 성과 대시보드, 추천사와 일반적인 SaaS 행동 유도 영역을 사용하지 않는다.

첫 버전에 modal, drawer, toast, table, tab, filter, search, pagination, carousel, tooltip, form validation, loading skeleton, empty state와 command palette를 추가하지 않는다. 실제 요구가 생겼을 때만 디자인 체계를 확장한다.

## 디자인 체계와 제작 순서

현재 브랜치에는 애플리케이션 소스와 의존성 명세가 없다. 구현 전에 프레임워크, 정적 제공 방식, 스타일 작성 방식, 기존 자산, 글꼴 제공 방식, 아이콘, 지원 브라우저와 검사 도구를 정한다.

기술 선택 뒤 저장소 최상위 `DESIGN.md`에 실제 토큰 이름, 글꼴 제공 방식, 글자 체계, 색상 역할, 여백, 그리드, 구성 요소와 상태, 컨테이너 쿼리 기준, 움직임, 포커스, 반응형 예외와 도식 사용 규칙을 기록한다. 요구사항의 숫자를 복사하는 데 그치지 않고 실제 한국어 화면과 구현이 일치하는지 확인한다.

## 완료 기준

첫 버전은 다음 항목을 실제 화면에서 확인할 수 있어야 한다.

- 한 페이지를 읽는 것만으로 개발자가 해결해 온 문제, 기술적 판단과 확인된 기여를 설명할 수 있다.
- Identity에서 Experience로 자연스럽게 이어지고 회사에서 만든 네 가지 기여의 수치와 조건을 함께 읽을 수 있다.
- React Router와 Outline 기여를 실제 PR 및 공식 릴리스에서 확인할 수 있다.
- AI Agent Workflow와 Offline Translation Web App이 회사 경력과 다른 독립 작업으로 구분된다.
- Header, 페이지 안의 이동, 외부 링크와 Contact를 키보드와 터치로 사용할 수 있다.
- 320px, 390px와 1440px 폭, 200% 글자 확대와 움직임 감소 설정에서 내용과 읽는 순서가 유지된다.
- 색상과 포커스 표시가 정한 명암비를 충족한다.
- 한국어 JSON의 문구를 바꾸면 UI 코드를 수정하지 않고 화면에 반영된다.
- 한국어 화면을 확인한 뒤 영어 JSON을 추가해 같은 정보 구조로 읽을 수 있다.

요구사항과 조사 문서의 완성만으로 웹사이트 구현이 완료됐다고 판단하지 않는다.

## 구현 전에 정할 사항

- 프레임워크, 정적 제공 방식, 배포 방식과 지원 브라우저.
- Pretendard를 로컬 파일, 패키지 또는 외부 CDN 중 어떤 방식으로 제공할지.
- 실제 이메일, GitHub, Blog, LinkedIn과 Résumé 주소.
- Header 고정 여부와 현재 영역 표시 방식.
- 영어 버전의 기본 언어와 언어별 주소.
- `30초 이내 배포` 수치를 홈페이지에 사용할 수 있는 근거와 비교 조건.

어두운 테마, 보조 고정폭 글꼴, 삽화 체계, 복잡한 애니메이션, 겹쳐 뜨는 UI와 입력 양식 체계는 첫 버전 요구사항이 아니다.
