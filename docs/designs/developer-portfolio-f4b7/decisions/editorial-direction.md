# 편집형 시각 방향과 디자인 기준

사이트의 시각 방향은 `Technical Publication / Career Index / Evidence-driven`을 유지하되, 네비게이션 바 없는 단일 칼럼으로 변경한다. 밝은 바탕, Pretendard와 제한된 분홍색 링크를 유지하고, 개발자의 경력과 기술적 기여를 차례로 읽는 본문으로 구성한다. 비대칭 다중 칼럼과 큰 수치 표현은 사용하지 않는다.

이 결정은 [편집형 시각 규칙](../requirements.md#편집형-시각-규칙), [글꼴과 글자 체계](../requirements.md#글꼴과-글자-체계), [색상](../requirements.md#색상)과 [여백과 반응형 배치](../requirements.md#여백과-반응형-배치)에 적용한다. 현재 비교 근거는 [세 개인 사이트 재조사](../references/personal-site-recheck.md), 기존 색상과 글꼴의 근거는 [편집형 디자인 조사](../references/editorial-design-system.md)에 있다.

## 비교한 방향과 선택 이유

프로젝트 화면을 앞세우는 포트폴리오 구성과 회사 기여를 편집한 기술 프로필 구성을 비교했다. 첫 번째 방식은 독립 애플리케이션의 UI를 빠르게 보여줄 수 있지만, 현재 자료에서 가장 강하게 확인되는 운영 대시보드, 장시간 비동기 작업, 브라우저 처리와 E2E 검증 경험을 회사 화면 없이 설명하기 어렵다.

기술 프로필 구성은 회사별 Engineering Contribution, 수치, 기술 정보와 외부 기여를 같은 페이지에서 이어 읽게 한다. 회사 내부 화면을 추정하지 않고도 문제, 판단과 결과를 보여줄 수 있으며 단일 페이지 소개와 블로그의 역할도 구분할 수 있어 선택했다.

배치에서는 기존의 회사 정보와 본문을 좌우로 나누는 방식, Brittany의 고정 소개와 탐색, Paco의 일부 가로 목록, Emil의 세로 본문을 비교했다. 이번 구성은 화면 폭마다 읽는 순서를 다시 배우지 않도록 한 칼럼을 선택한다. 네비게이션 바를 없애더라도 언어 선택과 외부 링크, 키보드용 본문 바로가기는 유지한다. 참조 사이트의 모든 요소를 함께 채택하지 않는다.

## 반복할 시각 특징

- 연도, 역할과 기술 맥락은 같은 칼럼에서 본문보다 낮은 위계로 둔다.
- 수치는 기여를 설명하는 본문 문장에 포함하고 크기나 색으로 별도 강조하지 않는다.
- 오픈소스와 배경 정보도 제목 다음 설명을 읽는 세로 목록으로 제공한다.
- 얇은 구분선과 `#EE5166` 계열의 제한된 강조를 반복한다.
- 글자 크기, 굵기, 여백과 정렬을 색보다 먼저 사용한다.

## 확정한 시작값

- 글꼴: `Pretendard Variable`, `Pretendard`, `system-ui`
- 기본 바탕: `#FFFFFF`
- 주요 본문: `#18181B`
- 브랜드 기준색: `#EE5166`
- 일반 브랜드 글자와 링크: `#C62A44`
- 마우스를 올리거나 누른 링크: `#B4233C`
- 좌우 여백: `clamp(1rem, 3vw, 2rem)`
- 여백 값: `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 128`

색상과 글꼴은 유지한다. 이전 1200px 폭과 다중 칼럼 전환값은 폐기한다. 새 본문 폭과 제목 크기는 [DESIGN.md](../../../../DESIGN.md)의 구현 시작값을 화면에서 확인하고 조정한다. 이 값은 참조 사이트의 측정값이나 이미 적용된 값이 아니다.

플랜은 Header, 수치 전용 UI, 그림 및 이를 표현하는 타입을 제거하고 기존 영역을 단일 칼럼으로 교체한다. 긴 본문을 읽기 어렵다면 분량, 여백과 문장을 먼저 조정하며 승인 없이 메뉴나 다중 칼럼을 복원하지 않는다.

## 사용하지 않는 표현

첫 버전에는 3D 물체, 가짜 회사 화면, 전체 화면 Hero, 반복되는 큰 둥근 카드, Bento grid, 기술 로고 모음, 별도 성과판, 가짜 터미널, 계속 움직이는 배경과 모든 영역의 등장 애니메이션을 사용하지 않는다.

어두운 테마, 보조 고정폭 글꼴, 삽화 체계와 복잡한 움직임은 현재 필요가 없어 정하지 않는다. 이후 실제 요구가 생기면 이 결정과 접근성 및 성능 조건을 함께 다시 검토한다.
