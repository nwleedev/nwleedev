# FSD 구조와 문구 저장 위치

FSD 구조를 사용하고, 웹사이트의 메시지, 단어, 용어와 표현은 하나의 `src/shared/terms` 폴더에서 관리한다. 한국어는 `ko.json`, 영어는 `en.json`에 둔다. `i18n`을 중간 폴더로 추가하지 않는다.

이 문서는 [글과 언어 관리 요구사항](../requirements.md#글과-언어-관리)을 구현할 때 따를 결정이다. 소개 문구를 계속 다듬고 두 언어의 표현을 함께 살펴볼 수 있도록, 문구를 어디에 모으고 어떤 이름으로 관리할지를 정한다.

## 선택한 구성과 이유

`terms`는 짧은 단어나 용어뿐 아니라 소개 문장, 안내 메시지와 화면 표현 전반을 관리하는 이름이다. 언어별 파일을 한 곳에 모으면 페이지의 구현 위치를 찾아다니지 않고 사이트 전체의 문구를 수정하고 비교할 수 있다.

```text
src/
  shared/
    terms/
      ko.json
      en.json
```

`terms`는 Shared 레이어 안의 세그먼트로 둔다. FSD의 새로운 최상위 레이어로 추가하지 않는다. `terms`에서 페이지나 기능 구현을 가져오지 않도록 하고, 상위 레이어에서 필요한 문구를 사용한다. 이 배치의 공식 문서 근거는 [JSON 문구 관리와 FSD 구성 조사](../references/content-and-site-direction.md#json-문구-관리와-fsd-구성)에 있다.

## 비교한 대안

페이지나 기능별로 `terms`를 분산하면 구현 코드와 그 화면에서 사용하는 문구를 가까이 둘 수 있다. 이 사이트에서는 개발자 소개, 프로젝트와 사례의 표현을 함께 편집하는 편의를 우선하므로 한 폴더에 모은다.

`src/shared/i18n/terms`는 번역 설정과 문구 파일을 `i18n` 아래로 묶는 구성이다. 현재 결정은 문구를 모아 관리하는 것이므로 `src/shared/terms`로 직접 접근하는 구성을 선택한다. `messages` 대신 `terms`라는 이름을 사용하되, 번역 라이브러리의 API 식별자까지 바꾸는 것은 아니다.

## 구현에 미치는 영향과 이후 결정

문구를 한 곳에 저장한다는 결정은 모든 문구를 매번 브라우저로 전송한다는 뜻이 아니다. 필요한 문구를 불러오는 방식은 프레임워크와 번역 라이브러리를 정할 때 구체화한다. 기능의 상태 관리와 실행 로직은 문구와 분리한다.

언어별 파일은 하나씩 둔다. [제작 순서](../requirements.md#글과-언어-관리)에 따라 한국어 제작 단계에는 `ko.json`으로 문구를 관리하고, 한국어 웹사이트를 제작한 뒤 영어 문구를 구성할 때 `en.json`을 추가한다. 위 폴더 예시는 두 언어를 제공할 때의 구성이다.

문구가 늘어 편집하기 어려워지면 같은 `terms` 폴더 안에서 파일을 나누는 방식을 다시 검토한다. 긴 사례 본문은 개인 웹사이트에 싣지 않으므로 이 사이트의 저장 형식 결정에서 제외한다.

한국어를 기본 언어로 두고 `/`에서 제공하며 영어는 `/en/`에서 제공한다. Identity의 소개 아래에 놓인 KO와 EN 텍스트 링크가 두 주소를 연결한다. 별도의 네비게이션 바는 만들지 않는다. 두 JSON은 같은 필수 필드를 사용하며 누락이나 다른 자료형은 빌드를 중단한다. 다른 언어의 문구로 자동 대체하지 않는다.

기여 설명의 확장은 두 언어에 함께 적용한다. 표현 방식별 수치와 도식 객체 대신 제목, 본문 문단 배열과 기술 정보를 사용한다. 숫자, 단위와 비교 조건은 번역할 때에도 같은 문단에 남긴다.

저장 방식의 확정은 소개 문구 초안의 최종 확정을 뜻하지 않는다. [개발자 소개 문구](../references/developer-introduction.md)는 계속 수정할 수 있는 편집 제안으로 유지한다.
