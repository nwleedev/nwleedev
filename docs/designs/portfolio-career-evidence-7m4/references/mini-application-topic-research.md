# 세 가지 미니 웹 애플리케이션 주제 조사

결론은 개인 메모에서 반복 문장을 찾아 템플릿으로 정리하는 도구가 첫 구현 후보로 가장 현실적이고, GeoJSON과 GeoTIFF를 다루는 위성영상 검토 도구가 기술적 깊이를 보완할 두 번째 후보라는 것이다. 이동 방향에 맞춰 3D 공간을 즉시 생성하는 구상은 2026년 8월 29일 현재 공식 문서가 밝힌 생성 지연과 공간 연결 제약 때문에 그대로 구현하기 어렵다. 세 번째 후보는 사전 생성한 공간에서 바로 이동하고 포털을 선택하면 다음 공간을 비동기로 준비하는 제한된 실험으로 바꿔야 한다.

이 우선순위와 후보별 구상은 [포트폴리오 경력 증거 요구사항](../requirements.md)을 바탕으로 조사한 제안이며 승인된 구현 결정이 아니다. 이 문서는 세 주제를 실제 사용자 과업, 기존 사례와 다른 점, 브라우저와 서버의 책임, 검증 절차와 측정값, 운영 부담과 중단 조건으로 비교한다.

## 조사 결론

- **조사 사실:** 위성영상 탐색과 비교는 NASA Worldview, Copernicus Browser와 LandsatLook가 이미 폭넓게 제공한다. 단순 지도, 날짜 선택과 레이어 전환만 구현하면 기존 도구의 축소판이 된다.
- **조사 사실:** 텍스트 조각 수집, 묶음 복사와 동적 템플릿은 여러 서비스에 나뉘어 존재한다. 반면 개인이 이미 작성한 문장에서 반복을 찾고, 원문 차이를 확인한 뒤, 사람이 변수 구간을 정해 템플릿으로 바꾸는 흐름은 조사한 사례에서 하나의 과업으로 제공되지 않았다.
- **조사 사실:** World Labs Marble은 프롬프트로 탐색 가능한 3D 공간을 만들고 확장할 수 있지만, 외부 개발자용 API의 공간 생성에는 약 5분이 걸린다고 안내한다. Google DeepMind Genie 3도 실시간 상호작용을 시연하지만 일관성 유지 시간과 가능한 행동에 한계가 있다고 밝힌다.
- **분석:** 현재 사용자를 모집하기 어렵다는 조건에서는 정답이 있는 입력 자료와 재현 절차로 정확성, 반응성, 오류 복구와 접근성을 검증할 수 있는 후보가 유리하다. 개인 메모 후보와 위성영상 후보는 고정 자료만으로도 이런 증거를 만들 수 있다.
- **분석:** 세 후보는 서로 다른 프론트엔드 역량을 보여준다. 개인 메모 후보는 복잡한 선택 상태, 텍스트 처리와 개인정보 보호를, 위성영상 후보는 대용량 래스터 처리, 좌표계와 시각화를, 3D 후보는 렌더링, 비동기 작업과 실패 복구를 중심에 둔다.
- **제안:** 세 후보를 각각 `반복 문장 정리 작업대`, `위성영상 변화 검토 작업대`, `생성 세계 전환 실험실`이라는 이름과 과업으로 비교한다. 순서와 이름은 아직 승인되지 않았다.

## 조사 대상과 방법

조사는 2026년 8월 29일에 접근할 수 있었던 표준 문서, 공식 서비스 문서, 공식 소스 저장소와 연구 원문을 우선했다. 웹 브라우저에서 NASA Worldview, Copernicus Browser와 World Labs Marble의 실제 화면을 확인해 문서에 적힌 조작과 정보가 현재 인터페이스에서 어떻게 드러나는지도 비교했다.

포트폴리오 방문자는 결과를 평가하는 독자이지 세 후보가 해결할 문제의 실제 사용자를 대신하지 않는다. 각 후보에는 별도의 사용자와 완료할 과업이 있어야 하며, 방문자 수나 화면의 시각적 인상을 사용자 성과로 제시하지 않는다. 이 기준은 [채용 판단에 도움이 되는 포트폴리오 경력 증거 조사](portfolio-career-evidence-research.md)에서 확인한 증거 원칙을 따른다.

이번 조사에서는 라이브러리, 위성영상 제공자와 외부 생성 API를 선택하지 않았고, 생성 API를 직접 호출해 지연과 비용을 측정하지 않았다. 상용 서비스 문서는 사용자가 할 수 있는 조작과 제공 조건을 확인하는 근거로만 사용했으며 효과나 시장 수요를 입증하는 자료로 사용하지 않았다. 실제 사용자 인터뷰, 위성영상 이용 조건 검토와 법률 판단도 진행하지 않았다.

## 후보를 비교한 기준

결론은 구현 난이도가 낮은 주제보다, 사용자 과업과 실패 조건을 설명하고 같은 조건에서 결과를 다시 확인할 수 있는 주제를 먼저 검토해야 한다는 것이다.

- 기존 제품을 축소해서 다시 만드는 대신 해결할 판단이나 반복 작업이 분명한가.
- 현재 사용자를 모집하지 못해도 고정된 입력과 예상 결과로 중요한 주장을 검증할 수 있는가.
- 프론트엔드가 맡은 상태, 계산, 표현과 오류 복구를 외부 모델의 성능과 구분할 수 있는가.
- 접근성, 개인정보, 데이터 출처와 실패 시 복구 방법을 과업 안에서 다룰 수 있는가.
- 한 명이 공개 상태로 유지할 때 데이터, 서버, 생성 비용과 외부 서비스 변경을 감당할 수 있는가.
- 사례 설명에서 선택한 대안, 측정 조건, 결과와 한계를 함께 제시할 수 있는가.

## 주제 1. 위성영상 변화 검토 작업대

### 제안 결론

GeoJSON과 GeoTIFF를 사용하는 후보는 범용 위성영상 뷰어가 아니라, 비교할 장면의 품질을 확인하고 변화 구역과 판단 근거를 다시 검토할 수 있게 내보내는 작업대로 제한하는 편이 좋다. 이 형태라면 공간 자료 해석, 대용량 파일 처리, 비동기 요청, 시각화와 정확성 검증을 하나의 과업으로 연결할 수 있다.

### 공식 자료와 실제 사례에서 확인한 사실

[GeoJSON RFC 7946](https://www.rfc-editor.org/rfc/rfc7946)은 Feature와 FeatureCollection의 JSON 표현을 정의하고 좌표를 WGS 84의 경도, 위도 순서로 사용한다. 따라서 GeoJSON은 위성영상 자체보다 관심 영역, 판독 다각형과 주석을 기록하는 데 알맞다. 다른 좌표계의 래스터와 함께 표시할 때에는 좌표 순서와 재투영을 별도로 검증해야 한다.

[OGC GeoTIFF 1.1 표준](https://docs.ogc.org/is/19-008r4/19-008r4.html)은 TIFF 안에 래스터의 위치 변환과 좌표 참조 정보를 기록하는 방식을 정의한다. [OGC Cloud Optimized GeoTIFF 1.0 표준](https://docs.ogc.org/is/21-026/21-026.html)은 타일, 축소 해상도 영상과 HTTP Range 요청을 이용해 필요한 부분부터 읽을 수 있게 한다. 원격 COG를 브라우저에서 읽으려면 제공 서버가 Range 요청과 CORS를 허용해야 하며, 파일이 COG 형식이라는 사실만으로 빠른 화면이 보장되지는 않는다.

[STAC 1.1.0 사양](https://github.com/radiantearth/stac-spec)은 촬영 시간, 공간 범위, 자산 링크를 가진 Item을 GeoJSON Feature로 표현한다. STAC은 영상을 그리는 형식이 아니라 장면을 찾고 GeoTIFF나 COG 자산으로 연결하는 메타데이터 구조다. 연결된 JSON 파일만으로 정적 Catalog를 만들 수 있지만 임의의 공간과 시간 조건으로 검색하려면 보통 STAC API가 필요하다.

[geotiff.js 공식 저장소](https://github.com/geotiffjs/geotiff.js)는 브라우저에서 로컬 또는 원격 TIFF를 열고, 범위나 경계 상자로 일부 픽셀과 밴드를 읽고, Worker pool로 디코딩할 수 있음을 보여준다. 2026년 3월 11일 공개된 v3.0.5까지 확인했다. 이 자료는 브라우저 처리 가능성의 근거이며 이 문서에서 의존성 채택을 결정하지 않는다.

웹 브라우저에서 확인한 [NASA Worldview](https://worldview.earthdata.nasa.gov/)는 레이어, 사건, 날짜 축, 차트, 비교와 내려받기를 하나의 화면에 제공한다. [Copernicus Browser 공식 문서](https://documentation.dataspace.copernicus.eu/Applications/Browser.html)는 관심 영역, 거리와 면적 측정, 좌우 비교, 시간 경과 영상, 스펙트럼과 시계열 분석, GeoTIFF 내려받기를 지원한다고 설명한다. [LandsatLook 2.0 안내서](https://landsatlook.usgs.gov/assets/documents/LandsatLook_2.0_User_Guide.pdf)도 모자이크, 구름 제거, 밴드 조합과 지수를 제공한다. 이 범위를 다시 만드는 것은 한 명이 유지할 미니 애플리케이션의 목적과 맞지 않는다.

### 사용자와 완료할 과업

가장 구체적인 사용자는 공개 위성영상으로 지역 변화를 조사하는 환경 보도, 교육 또는 비영리 조사 담당자다. 사용자는 다음 과정을 완료한다.

1. 조사할 질문과 GeoJSON 관심 영역을 고른다.
2. STAC 메타데이터에서 촬영일, 센서, 공간 해상도와 구름량을 확인해 비교할 두 장면을 선택한다.
3. 같은 표시 조건에서 두 시점을 스와이프하거나 좌우로 비교하고, 변화로 판단한 구역을 표시한다.
4. 구름, 계절, 센서와 해상도 차이처럼 판단을 흔드는 요인을 확인한다.
5. 관심 영역, 선택한 장면과 자산, 표시 조건, 판독 구역과 설명을 한 묶음으로 내보낸다.

첫 버전은 자동으로 산림 훼손이나 침수 여부를 판정하지 않는다. 센서, 대기 보정, 구름 마스크와 시기 조건이 맞지 않으면 화면의 색 차이가 실제 변화가 아닐 수 있기 때문이다. 준비된 사례에서 `시각적 변화 검토`를 지원한다고 설명하고 과학적 변화 탐지 결과라고 확대하지 않는다.

### 브레인스토밍한 구상

추천 형태는 `질문 설정 → 장면 품질 확인 → 두 시점 비교 → 변화 구역 표시 → 판독 기록 내보내기` 흐름이다. 지도보다 선택 근거와 재현 정보가 결과물의 중심이 된다.

다른 형태도 가능하지만 첫 범위에는 각각 조건이 붙는다.

- **장면 적합성 검사기:** 관심 영역을 포함하는 장면을 찾고 구름량, 촬영일, 해상도와 실제 썸네일을 함께 비교한다. 변화 판독을 제외해 다룰 동작이 가장 적으므로 초기 검증에 알맞다.
- **경계 품질 검토기:** 행정, 농지 또는 시설 경계 GeoJSON과 영상을 겹쳐 어긋난 구역을 표시한다. 실제 검토자가 정의한 정답 자료가 있을 때만 성립한다.
- **밴드 조합 학습 도구:** 고정 사례에서 밴드와 지수 계산 결과를 비교한다. 교육 과업은 분명하지만 센서별 scale, offset과 기준 계산을 검증할 자료가 필요하다.
- **범용 탐색기:** 여러 데이터 제공자, 전 지구 검색과 임의 분석을 지원하는 형태는 기존 공식 도구와 겹치고 운영 범위가 너무 커서 제외한다.

### 첫 구현에 포함할 항목과 배포 방식

첫 범위는 사용 허가를 확인한 고정 사례 두세 개, 각 사례의 GeoJSON 관심 영역과 비교 가능한 COG 두 장면을 제공하는 정적 애플리케이션이다. 로컬 GeoJSON과 GeoTIFF 불러오기, 두 시점 비교, 판독 다각형과 메모, 판독 기록 JSON과 GeoJSON 내보내기를 포함할 수 있다. 서버로 원본 파일을 전송하지 않고 브라우저 Worker에서 필요한 범위만 처리하면 개인정보와 운영 부담을 줄일 수 있다.

원격 COG는 Range와 CORS를 지원할 때만 정적 배포에서 직접 사용한다. 인증 키가 필요한 자료, 여러 장면의 전체 해상도 모자이크, 긴 기간의 픽셀 시계열, 임의 좌표계 변환, 계정별 영구 공유와 공동 편집은 서버 책임이 생기므로 첫 범위에서 제외한다.

### 검증 가능한 프론트엔드 증거

고정된 COG와 예상 판독 결과를 사용하면 별도의 사용자를 모집하지 않아도 다음 결과를 반복 측정할 수 있다.

- 전체 파일 크기와 실제 전송한 바이트, Range 요청 수와 캐시 적중 수
- 헤더 해석, 타일 디코딩, 재투영과 첫 비교 화면까지 걸린 시간
- 관심 영역을 빠르게 바꿀 때 이전 요청을 취소하고 마지막 선택 결과만 표시하는지 여부
- Worker 사용 전후 메인 스레드의 긴 작업, 프레임 지연과 최대 메모리
- 기준 좌표와 화면 좌표의 왕복 오차, 기준 다각형과 계산한 면적의 오차
- NoData, 구름 마스크, 밴드 scale과 offset, 타일 경계와 날짜변경선 사례의 처리 결과
- 포인터 없이 관심 영역과 장면을 선택하고 같은 메타데이터와 판독 결과를 텍스트 목록에서 확인하는 과업

실제 사용자 평가를 진행할 수 있게 되면 장면 선택 이유를 설명하고 준비된 변화 구역을 찾는 과정을 관찰한다. 이 결과는 형성 평가로 기록하며 소수 참여자의 성공률을 전체 사용자 성과로 확대하지 않는다.

### 위험과 중단 조건

- 비교 가능한 장면을 확보하지 못하면 변화 검토를 중단하고 장면 적합성 검사기로 줄인다.
- COG 제공자가 Range와 CORS를 지원하지 않으면 무단 프록시를 만들지 않고, 사용 허가를 확인한 고정 자료나 로컬 파일만 지원한다.
- 좌표계, NoData, 밴드 해석과 구름 조건을 사례 설명에서 재현할 수 없으면 자동 계산 결과를 공개하지 않는다.
- 임의 GeoTIFF 지원이 메모리, 압축 방식과 불완전한 좌표 정보 때문에 예측할 수 없으면 지원 형식과 파일 크기를 명시적으로 제한한다.
- 외부 자료 URL, 할당량과 카탈로그가 바뀔 수 있으므로 고정 사례의 출처, 촬영일, 처리 수준, 라이선스와 마지막 확인일을 함께 보존한다.

## 주제 2. 반복 문장 정리 작업대

### 제안 결론

이 후보는 범용 메모장이 아니라, 개인 메모에서 필요한 조각을 모으고 반복되는 문장을 근거와 함께 비교한 뒤 재사용 템플릿으로 정리하는 도구로 제한한다. 세 후보 가운데 사용자 과업, 로컬 우선 배포, 재현 가능한 검증과 한 명의 운영 부담이 가장 잘 맞는다.

### 공식 자료와 실제 사례에서 확인한 사실

[Google Docs의 비연속 텍스트 선택 안내](https://workspaceupdates.googleblog.com/2022/05/multiple-text-selections-in-google-docs.html)는 떨어진 여러 텍스트를 함께 선택해 복사하거나 서식을 적용하는 과업이 실제 제품에 있음을 보여준다. [Readwise Reader 내보내기 문서](https://docs.readwise.io/reader/docs/faqs/exporting)는 문서나 태그별 하이라이트와 메모를 클립보드 또는 Markdown으로 내보내고 Jinja2 템플릿을 편집할 수 있다고 설명한다. [Text Blaze 동적 스니펫 안내](https://blaze.today/guides/dynamic-commands/)는 입력 칸, 선택 항목과 조건을 가진 재사용 문구를 제공한다.

이 사례들은 수집, 복사와 이미 만든 템플릿의 재사용을 각각 해결한다. 조사한 공식 문서에서는 사용자가 과거에 쓴 여러 문장을 비교하고 반복된 부분과 달라지는 부분을 확인한 뒤, 원문 사례를 검증 자료로 유지하면서 템플릿으로 바꾸는 전체 흐름을 확인하지 못했다. 이 결과는 시장에 같은 제품이 없다는 증명이 아니라, 조사 범위에서 차별화할 과업을 찾았다는 뜻이다.

[W3C Selection API](https://www.w3.org/TR/selection-api/)는 문서 선택을 Range와 연결하지만 여러 Range를 한 선택에 두는 동작은 브라우저 엔진 사이에 차이가 있었음을 기록한다. 특별한 다중 선택 동작에 의존하지 않고 사용자가 한 번 선택한 범위를 애플리케이션 상태에 차례로 추가해야 한다.

[W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/)의 TextQuoteSelector는 선택한 정확한 문자열과 앞뒤 문맥을 기록해 원문의 위치를 다시 찾을 수 있게 한다. 편집 후 위치가 바뀔 수 있으므로 시작과 끝 위치만 저장하는 방식보다 이 구조를 함께 사용하는 편이 적합하다.

[W3C Clipboard API and Events, 2026년 6월 24일 초안](https://www.w3.org/TR/clipboard-apis/)은 비동기 클립보드 접근이 사용자 동작, 권한과 보안 조건에 영향을 받는다고 설명한다. [W3C Indexed Database API 3.0](https://www.w3.org/TR/IndexedDB/)은 브라우저에서 구조화된 데이터를 비동기로 저장하는 근거를 제공하지만, 브라우저 저장소는 사용자가 사이트 데이터를 지우거나 저장 공간을 회수하면 사라질 수 있다.

### 사용자와 완료할 과업

주 사용자는 배포 공지, 장애 회고, 검토 답변과 운영 안내처럼 비슷한 문서를 반복해서 작성하는 개발자나 기술 문서 작성자다. 고객 지원 담당자와 연구자도 후보가 될 수 있지만 개인정보와 출처 보존 조건이 달라 별도 검증이 필요하다.

사용자는 다음 과정을 완료한다.

1. 직접 작성한 plain text 또는 Markdown 메모를 만들거나 불러온다.
2. 필요한 문장이나 문단을 선택하고 명시적인 추가 동작으로 `문장 바구니`에 누적한다.
3. 바구니의 조각을 순서대로 배치하고 구분자와 출처를 확인해 복사한다.
4. 여러 메모에서 정확히 반복되거나 어휘가 많이 겹치는 문장을 출처와 차이 표시로 검토한다.
5. 반복된 공통 부분과 문서마다 달라지는 부분을 확인하고, 사람이 변수 이름과 범위를 정해 템플릿으로 저장한다.
6. 템플릿을 원문 사례에 다시 적용해 빠진 문장, 잘못 묶인 변수와 예외를 확인한다.

특별한 클릭 방식은 빠른 조작으로 제공할 수 있지만 유일한 방법으로 두지 않는다. 텍스트 선택 뒤 보이는 추가 버튼, 키보드 동작과 체크박스 목록에서도 같은 과업을 완료할 수 있어야 한다.

### 반복과 유사성을 구분하는 방법

`겹치는 텍스트`는 하나의 점수로 정의하지 않는다. 첫 범위에서는 다음 세 종류를 따로 보여주고 자동으로 합치지 않는다.

- **정확한 반복:** 공백과 줄바꿈 같은 정규화 규칙을 적용한 뒤 문자열이 같다.
- **포함 관계:** 한 문장이나 문단의 대부분이 다른 문장 안에 그대로 들어 있다.
- **어휘상 근접 반복:** 단어 또는 문자 n-gram 집합이 정한 임계값 이상 겹친다. 점수와 임계값, 차이 표시를 함께 보여준다.

뜻은 비슷하지만 사용하는 단어가 다른 의미 유사성은 첫 범위에서 제외한다. 서버 모델로 개인 메모를 보내거나 브라우저에서 큰 임베딩 모델을 내려받기 전에, 정확한 반복과 어휘 중복만으로 실제 과업이 해결되지 않는다는 근거가 필요하다. 부정어, 숫자와 시제 하나가 뜻을 바꿀 수 있으므로 어떤 방식도 문장을 자동 병합하거나 템플릿으로 확정하지 않는다.

### 브레인스토밍한 구상

추천 형태는 `메모 작성 → 문장 바구니 수집 → 반복 유형별 검토 → 차이 확인 → 사람의 템플릿 확정 → 원문 사례 재검증` 흐름이다. 템플릿은 결과만 저장하지 않고 어떤 원문에서 공통 부분과 변수를 정했는지도 연결한다.

첫 형태와 맞닿은 다른 구상은 다음과 같다.

- **문장 조립 바구니:** 여러 텍스트 조각을 빠르게 모아 순서와 구분자를 정하고 plain text나 Markdown으로 복사하는 과업에만 집중한다. 반복 탐지가 충분히 정확하지 않을 때 남길 수 있는 최소 형태다.
- **반복 표현 검토기:** 템플릿 생성 없이 정확한 반복, 포함 관계와 어휘 중복을 출처와 차이로만 보여준다. 자동화보다 신뢰 가능한 검토가 중요할 때 적합하다.
- **답변 템플릿 정리기:** 여러 답변 초안에서 이름, 날짜와 상태처럼 바뀌는 부분을 사람이 변수로 지정한다. 고객정보가 들어간 실제 자료를 사용할 때에는 로컬 처리와 비식별 검증 자료가 필요하다.
- **범용 지식 관리 도구:** 협업 편집, 브라우저 확장, 모든 외부 앱 수집과 의미 검색을 함께 제공하는 형태는 기존 메모 제품과 겹치고 첫 범위를 벗어나므로 제외한다.

### 첫 구현에 포함할 항목과 배포 방식

첫 범위는 가입과 동기화가 없는 단일 기기용 로컬 우선 애플리케이션이다. 앱에서 만든 plain text와 Markdown 메모, 준비된 검증 자료, 문단 단위 문장 바구니, 정확한 반복과 어휘상 근접 반복, 차이 표시, 사람이 확정하는 템플릿, plain text와 Markdown 복사, JSON 내보내기와 다시 불러오기를 포함한다.

이 범위는 `사용자마다 자신의 메모를 기록한다`는 방향을 한 브라우저의 개인 공간으로 먼저 검증한다. 실제 계정별 저장, 여러 기기 동기화와 공유가 승인되면 인증, 사용자별 접근 제어, 백업, 충돌 처리와 삭제 책임을 서버에 추가해야 한다. 로컬 우선이라는 표현이 자동 암호화나 영구 보존을 뜻하지 않으므로 내보내기와 복구 방법은 첫 범위에도 필요하다.

### 검증 가능한 프론트엔드 증거

사람이 반복 유형과 템플릿 후보를 미리 표시한 검증 자료를 만들면 다음 결과를 반복해서 확인할 수 있다.

- 포인터, 키보드와 터치로 같은 문단을 바구니에 추가하고 같은 순서로 복사하는지 여부
- 문장 앞뒤를 수정한 뒤 TextQuoteSelector와 위치 정보를 이용해 원문을 다시 찾은 비율과 실패 표시
- 정확한 반복, 포함 관계와 어휘상 근접 반복의 precision, recall, 임계값별 오탐 사례
- 템플릿이 원문 사례를 다시 만들 때 빠진 공통 문장, 잘못 지정한 변수와 예외를 차이로 찾는지 여부
- 1,000개 이상의 문단을 분석할 때 Worker 사용 전후의 긴 작업, 입력 지연, 취소된 분석과 최대 메모리
- 클립보드 권한이 거부됐을 때 복사할 텍스트를 별도 화면에 제공하고 plain text와 Markdown 형식을 보존하는지 여부
- IndexedDB 구조 변경, 저장 공간 오류, 새로고침과 오프라인 상태에서 내보내기와 다시 불러오기 결과가 같은지 여부
- 겹치는 표시를 색만으로 구분하지 않고 목록과 텍스트 차이로도 찾을 수 있는지 여부

초기 검증 기준으로는 현실적인 메모 20개에서 재사용할 템플릿 후보가 3개도 나오지 않으면 템플릿화를 빼고 문장 바구니와 중복 검토만 남기는 방안을 제안한다. 신뢰도가 높은 제안의 precision이 90%에 이르지 못하면 근접 반복을 자동 묶음으로 표시하지 않고 정확한 반복만 제공한다. 일반적인 문장 추가와 삭제 뒤 원문 재연결 실패가 5%를 넘으면 자동 복원을 중단하고 다시 찾지 못한 선택을 `재확인 필요`로 표시한다. 이 수치는 승인된 품질 기준이 아니라 과장을 막기 위한 초기 중단 기준 제안이다.

### 위험과 중단 조건

- 개인 메모에는 계정, 고객, 건강과 업무 정보가 섞일 수 있다. HTML을 그대로 렌더링하지 않고 외부 전송을 기본값으로 삼지 않으며, 동기화가 필요해질 때 보관, 암호화와 삭제 조건을 별도로 결정한다.
- 어휘가 비슷해도 부정어, 숫자, 시제와 책임 주체가 다르면 뜻이 반대일 수 있다. 출처와 차이를 보여준 뒤 사용자가 확정하게 하고 자동 병합은 제공하지 않는다.
- 브라우저 저장소가 삭제되거나 용량을 회수당할 수 있다. 내보내기와 다시 불러오기 왕복 검증이 성립하지 않으면 실제 개인 메모 저장 기능을 사용자에게 제공하지 않는다.
- 외부 문서에서 가져온 문구에는 저작권과 출처 문제가 생길 수 있다. 원본 위치와 작성 구분을 보존하고 자동 공개나 공유를 제공하지 않는다.
- 특별한 클릭이 브라우저 기본 선택, 터치와 보조기술 조작을 방해하면 보조 기능으로만 남기고 명시적인 추가 버튼과 목록 조작을 기본 흐름으로 사용한다.

## 주제 3. 생성 세계 전환 실험실

### 제안 결론

사용자가 이동할 때마다 진행 방향의 3D 배경을 끊김 없이 추가 생성하는 구상은 첫 버전에서 약속하지 않는다. 사전 생성한 시작 공간에서 즉시 이동하고, 사용자가 포털을 선택하면 다음 독립 공간을 서버에서 비동기로 생성하거나 캐시에서 불러오는 형태가 현재 공개된 도구와 한 명의 운영 범위에 더 맞는다.

### 공식 자료와 실제 사례에서 확인한 사실

웹 브라우저에서 확인한 [World Labs Marble](https://marble.worldlabs.ai/)은 프롬프트로 만든 3D 공간을 탐색하고 공유하는 흐름을 제공한다. [Marble 공식 문서](https://docs.worldlabs.ai/)는 텍스트, 이미지, 영상과 거친 3D 구조에서 지속성 있는 공간을 만들고 편집, 확장과 내보내기를 지원한다고 설명한다. 따라서 `프롬프트 → 3D 공간 → 이동과 공유`만으로는 기존 제품과 차이가 약하다.

[World Labs API 시작 안내](https://docs.worldlabs.ai/api)는 한 공간 생성에 약 5분이 걸리고 SPZ splat, GLB 충돌 모델, 파노라마와 설명을 결과로 제공한다고 안내한다. [Marble Expand 안내](https://docs.worldlabs.ai/marble/create/prompt-guides/expand)는 공식 화면에서 선택한 방향으로 공간을 확장하는 기능을 설명하지만, 2026년 8월 29일에 검토한 [공개 OpenAPI](https://docs.worldlabs.ai/api/reference/openapi)에서는 기존 공간과 이어지는 확장을 보장하는 별도 endpoint를 확인하지 못했다. 이 문장은 공개 API 문서에서 확인하지 못한 사실에 근거한 추론이며, 기능이 존재하지 않는다고 단정하지 않는다.

[Google DeepMind Genie 3 발표](https://deepmind.google/blog/genie-3-a-new-frontier-for-world-models/)는 텍스트에서 만든 환경을 720p, 초당 24프레임으로 실시간 탐색하고 몇 분 동안 일관성을 유지하는 연구 결과를 소개한다. 같은 자료는 가능한 행동, 여러 행위자의 상호작용, 실제 장소의 정확성과 긴 상호작용에 한계가 있다고 밝힌다. 연구 시연은 일반 개발자가 호출할 수 있는 3D 자산 생성 API나 장기적인 공간 연결을 보장하지 않는다.

[Khronos glTF 2.0 Registry](https://registry.khronos.org/glTF/)는 장면과 모델을 런타임에 전달하는 형식을 제공한다. [Spark 공식 저장소](https://github.com/sparkjsdev/spark)는 SPZ splat을 Three.js에서 렌더링하는 구현을 공개한다. 이 자료들은 생성 결과를 브라우저에서 표시할 수 있다는 근거이지, 프롬프트 생성이 브라우저 안에서 실행되거나 서로 다른 결과의 지형과 충돌이 자연스럽게 이어진다는 근거는 아니다.

### 사용자와 완료할 과업

가장 현실적인 사용자는 짧은 상호작용형 3D 장면을 검토하는 제작자다. 사용자는 다음 과정을 완료한다.

1. 사전 생성된 시작 공간에서 즉시 이동하고 조작 방식을 익힌다.
2. 제한된 프롬프트나 선택지로 다음 공간의 분위기와 방향을 정한다.
3. 현재 공간을 계속 탐색하는 동안 생성 작업의 대기, 성공과 실패 상태를 확인한다.
4. 준비된 포털을 선택해 독립된 다음 공간으로 전환한다.
5. 생성 실패, 네트워크 중단이나 비용 상한에 도달하면 캐시 공간 또는 2D 대체 경로로 과업을 마친다.

포트폴리오 방문자는 이 과정을 체험할 수 있지만, 시각적 인상을 생성 모델의 품질이나 사용자 문제 해결 성과로 제시하지 않는다. 사례 설명은 프론트엔드가 맡은 자산 전환, 상태 표현, 입력, 성능과 복구를 생성 제공자의 결과와 구분해야 한다.

### 브레인스토밍한 구상

추천 형태는 `사전 생성 시작 공간 → 포털 선택 → 생성 작업 시작 → 현재 공간에서 대기 활동 → 준비된 다음 공간으로 전환 → 실패 시 캐시나 2D 대체 화면` 흐름이다. 생성 모델보다 기다림과 실패를 다루는 프론트엔드가 중심이 된다.

연속성이 더 중요하면 다음 대안을 검토할 수 있다.

- **결정적인 지형과 AI 분위기:** 좌표, 지형, 충돌과 이동 가능 구역은 seed 기반 절차 생성으로 고정하고 AI는 파노라마, 텍스처나 분위기만 만든다. 공간 연결은 설명하기 쉬워지지만 `이동하며 3D 세계를 생성한다`는 원래 구상과는 달라진다.
- **사전 생성 청크 재생:** 여러 공간과 연결을 미리 만들고 사용자의 방향에 따라 캐시된 청크를 불러온다. 가장 안정적이지만 생성형 경험이라는 주장은 제한해야 한다.
- **생성 진행 관찰 도구:** 다음 자산의 대기열, 내려받기, 품질 전환과 실패 상태를 시각화한다. 게임보다 3D 스트리밍과 비동기 상태를 검토하는 개발 도구에 가깝다.
- **이동 중 무한 생성:** 사용자의 속도보다 빠르게 지형, 충돌과 시각 자산을 만들고 이어 붙여야 하므로 현재 외부 개발자용 API만으로는 첫 범위에서 제외한다.

### 첫 구현에 포함할 항목과 배포 방식

첫 범위는 데스크톱 우선, 캐릭터 한 개, 사전 생성 시작 공간 한 개, 캐시 목적지 최대 세 개, 한 세션의 실시간 생성 작업 최대 한 건, 포털 전환, 별도 GLB 충돌 모델, 단계별 splat 품질, 파노라마와 2D 대체 화면으로 제한한다. 멀티플레이, WebXR, NPC 생성, 무제한 프롬프트, 이동 중 무한 확장과 브라우저 내 생성 모델은 제외한다.

브라우저는 이동과 카메라, 현재 공간과 포털, 자산의 단계별 내려받기, 입력 방식, 품질 조절, 캐시와 실패 화면을 맡는다. 서버는 제공자 키 보호, 프롬프트 제한, 생성과 상태 조회, 재시도, 요청 중복 제거, 결과 캐시, 세션별 비용과 동시 작업 상한을 맡는다. 생성 서비스가 지형 축척, 안전한 시작 위치, 충돌과 이웃 공간을 이어 준다고 가정하지 않는다.

완전한 정적 배포는 미리 생성하고 사용 허가를 확인한 자산만 재생할 때 가능하다. 사용자 프롬프트를 외부 생성 API로 보내는 순간 비밀 키, 요청 제한, 비용, 입력 정보와 결과 보관을 관리할 서버가 필요하다.

### 검증 가능한 프론트엔드 증거

- 사전 생성 시작 공간에서 처음 이동할 수 있을 때까지 걸린 시간과 실시간 생성 작업의 대기 시간을 분리한 기록
- 낮은 품질부터 전체 품질까지 자산 전환 시간, 내려받은 바이트, 프레임 시간, 최대 메모리와 두 번의 공간 전환 뒤 회수된 메모리
- 사용자가 방향을 바꿀 때 불필요해진 자산 요청을 취소하고 캐시를 재사용하는지 여부
- GLB 충돌 모델의 안전한 시작 위치, 이동 불가 구역, 낙하와 끼임에서 복구했는지 여부
- 요청 제한, 네트워크 중단, 생성 실패와 만료된 자산 URL을 재현했을 때 재시도와 대체 화면으로 과업을 마치는지 여부
- 공간 사이의 지면 높이, 축척, 색조와 이동 감각 차이를 포털 전환으로 설명하는지 여부
- 키보드 이동과 포털 선택, 카메라 감도, 움직임 감소, pointer lock이 없는 조작과 2D 대체 경로

### 위험과 중단 조건

- 외부 개발자용 생성 API의 약 5분 대기 시간은 이동 중 즉시 생성과 맞지 않는다. 사전 생성 공간 없이 첫 이동 가능 상태가 10초 안에 나오지 않으면 방문자를 실시간 생성에 기다리게 하지 않는다.
- 생성 작업은 [World Labs API 가격 안내](https://docs.worldlabs.ai/api/pricing)에 따른 credits를 사용한다. 한 세션에서 승인한 요청 수나 비용 상한을 넘으면 추가 생성을 막고 캐시된 공간만 제공한다.
- 별도로 생성한 공간은 지면, 축척, 조명, 스타일과 충돌이 서로 이어지지 않을 수 있다. 안전한 시작 위치와 통로를 찾지 못하면 생성 자산을 폐기하고 준비된 대체 공간으로 전환한다.
- 목표 중급 기기에서 낮은 품질 장면이 초당 30프레임을 유지하지 못하거나 공간을 두 번 전환한 뒤 메모리가 회수되지 않으면 자산 품질과 전환 수를 줄인다. 기기와 장면 조건은 결과와 함께 기록한다.
- 프롬프트는 외부 제공자에게 전달될 수 있다. 민감한 입력을 받지 않고 전송 대상, 보관 조건과 제공자를 입력 전에 알릴 수 없으면 사용자 프롬프트 생성을 제공하지 않는다.
- 인터넷에서 누구나 볼 수 있는 포트폴리오에 생성 결과를 사용할 권리는 계정과 API 조건에 따라 달라질 수 있다. 배포 전에 [World Labs 이용 약관](https://docs.worldlabs.ai/terms-of-service), 선택한 요금제와 각 입력 자산의 권리를 다시 확인한다.
- 포털 방식이 보여주려는 프론트엔드 판단을 설명하지 못하고, 공간 연결 기능도 외부 개발자용 API 문서에서 확인되지 않으면 이 후보를 구현하지 않는다.

## 세 후보의 제안 순서

### 1순위 제안: 반복 문장 정리 작업대

첫 후보는 텍스트 선택, 복합 상태, 비교, 로컬 저장, 내보내기와 접근성을 하나의 실제 작성 과업으로 연결한다. 고정된 메모 자료로 정확성과 성능을 검증할 수 있고 서버와 외부 AI 없이도 필수 흐름이 성립한다. 다만 현실적인 메모 표본에서 반복과 템플릿 과업이 실제로 발생하는지 먼저 확인해야 한다.

### 2순위 제안: 위성영상 변화 검토 작업대

두 번째 후보는 공간 자료와 대용량 래스터를 다루는 기술적 깊이가 분명하고 누구나 확인할 수 있는 고정 사례로 검증할 수 있다. 단순 뷰어를 피하고 장면 품질, 판독 근거와 재현 정보에 집중해야 한다. 자료 출처와 이용 조건, 좌표계와 비교 가능한 장면 선정이 첫 준비 과업이다.

### 조건부 연구 후보: 생성 세계 전환 실험실

세 번째 후보는 시각적 인상이 크지만 외부 생성 모델, 서버, 비용과 자산 권리에 대한 의존도도 가장 높다. 원래 구상에서 빠질 수 없는 이동 중 즉시 확장은 현재 근거로 약속할 수 없다. 포털 기반 전환이나 결정적인 지형과 AI 분위기 조합이 포트폴리오에서 보여주려는 판단과 맞는지 확인한 뒤 제한된 기술 시연으로만 검토한다.

세 후보를 모두 구현해야 한다는 결정은 없다. 하나의 잘 검증된 과업이 세 개의 기술 시연보다 [포트폴리오 정체성 사례 조사](portfolio-site-identity-cases.md)에서 정리한 목표와 더 잘 맞는다.

## 요구사항과 다음 결정에 미치는 영향

이번 조사로 승인된 것은 사용자가 제시한 세 주제를 비교 대상으로 삼는 것까지다. 후보 이름, 구현 순서, 포함할 동작, 외부 의존성과 초기 중단 기준은 조사에서 도출한 제안이며 [요구사항](../requirements.md)을 변경하지 않는다.

다음 판단에는 요구사항 작성자의 결정이 필요하다.

- 첫 구현 후보를 세 주제 가운데 어느 것으로 정할지
- 개인 메모 후보에서 `겹치는 텍스트`를 정확한 반복, 포함 관계와 어휘상 근접 반복까지로 제한할지
- 위성영상 후보에서 사용할 조사 사례, 자료 출처, 비교 가능한 두 시점과 결과물 형식을 무엇으로 정할지
- 3D 후보에서 이동 중 생성이라는 원래 구상을 포털 전환이나 절차 생성 혼합 방식으로 바꿀 수 있는지
- 계정별 저장, 여러 기기 동기화, 외부 생성 API와 월 운영 비용을 어느 시점에 허용할지
- 예상 사용자를 누구로 정하고 사용자를 모집할 수 있을 때 어떤 과업으로 형성 평가할지

이 결정 전에는 구현 계획, 의존성 선택과 API 요청 및 응답 형식을 작성하지 않는다.
