# 세 가지 미니 웹 애플리케이션 주제 조사

결론은 개인 메모에서 LLM 없이 어휘상 근접 반복을 찾아 템플릿으로 정리하는 도구가 첫 구현 후보로 가장 현실적이고, GeoJSON과 GeoTIFF를 다루는 위성영상 검토 도구가 기술적 깊이를 보완할 두 번째 후보라는 것이다. 3D 후보는 키보드로 이동하는 캐릭터, 중력, 벽 충돌과 지면 판정이 먼저 성립해야 한다. 다음 배경은 현재 청크의 끝에 가까워질 때 준비하되, 충돌체와 이동 가능한 지면을 검증하기 전에는 물리 장벽을 열지 않는 청크 방식이 요구사항에 가장 가깝다. 현재 외부 생성 API의 지연을 고려하면 화면에 보이는 생성 자산과 즉시 이동할 수 있는 충돌 지형을 분리해야 하며, 포털 전환만으로는 요구사항을 충족하지 못한다.

이 우선순위와 후보별 구상은 [포트폴리오 경력 증거 요구사항](../requirements.md)을 바탕으로 조사한 제안이며 승인된 구현 결정이 아니다. 이 문서는 세 주제를 실제 사용자 과업, 기존 사례와 다른 점, 브라우저와 서버의 책임, 검증 절차와 측정값, 운영 부담과 중단 조건으로 비교한다.

## 조사 결론

- **조사 사실:** 위성영상 탐색과 비교는 NASA Worldview, Copernicus Browser와 LandsatLook가 이미 폭넓게 제공한다. 단순 지도, 날짜 선택과 레이어 전환만 구현하면 기존 도구의 축소판이 된다.
- **조사 사실:** 텍스트 조각 수집, 묶음 복사와 동적 템플릿은 여러 서비스에 나뉘어 존재한다. 반면 개인이 이미 작성한 문장에서 반복을 찾고, 원문 차이를 확인한 뒤, 사람이 변수 구간을 정해 템플릿으로 바꾸는 흐름은 조사한 사례에서 하나의 과업으로 제공되지 않았다.
- **조사 사실:** World Labs Marble은 프롬프트로 탐색 가능한 3D 공간과 별도의 GLB 충돌 모델을 만들 수 있지만, 외부 개발자용 API의 공간 생성에는 약 5분이 걸린다고 안내한다. 생성 충돌 모델에는 구멍과 떠 있는 면이 생길 수 있어 이동 전에 별도 검증이 필요하다. Google DeepMind Genie 3도 실시간 상호작용을 시연하지만 일관성 유지 시간과 가능한 행동에 한계가 있다고 밝힌다.
- **분석:** 현재 사용자를 모집하기 어렵다는 조건에서는 정답이 있는 입력 자료와 재현 절차로 정확성, 반응성, 오류 복구와 접근성을 검증할 수 있는 후보가 유리하다. 개인 메모 후보와 위성영상 후보는 고정 자료만으로도 이런 증거를 만들 수 있다.
- **분석:** 세 후보는 서로 다른 프론트엔드 역량을 보여준다. 개인 메모 후보는 복잡한 선택 상태, 재현 가능한 문자열 비교와 개인정보 보호를, 위성영상 후보는 대용량 래스터 처리, 좌표계와 시각화를, 3D 후보는 렌더링과 물리 상태의 분리, 연속 청크 상태, 비동기 작업과 실패 복구를 중심에 둔다.
- **제안:** 세 후보를 각각 `반복 문장 정리 작업대`, `위성영상 변화 검토 작업대`, `검증된 생성 세계 보행 실험실`이라는 이름과 과업으로 비교한다. 순서와 이름은 아직 승인되지 않았다.

## 조사 대상과 방법

조사는 2026년 8월 29일에 시작해 8월 30일에 보강했으며, 접근할 수 있었던 표준 문서, 공식 서비스 문서, 공식 소스 저장소와 연구 원문을 우선했다. 웹 브라우저에서 NASA Worldview, Copernicus Browser, World Labs Marble과 Three.js의 1인칭 게임 예제를 확인해 문서에 적힌 조작과 정보가 현재 인터페이스에서 어떻게 드러나는지도 비교했다.

포트폴리오 방문자는 결과를 평가하는 독자이지 세 후보가 해결할 문제의 실제 사용자를 대신하지 않는다. 각 후보에는 별도의 사용자와 완료할 과업이 있어야 하며, 방문자 수나 화면의 시각적 인상을 사용자 성과로 제시하지 않는다. 이 기준은 [채용 판단에 도움이 되는 포트폴리오 경력 증거 조사](portfolio-career-evidence-research.md)에서 확인한 증거 원칙을 따른다.

이번 조사에서는 라이브러리, 위성영상 제공자와 외부 생성 API를 선택하지 않았고, 생성 API를 직접 호출해 지연, 비용과 생성 충돌 모델의 품질을 측정하지 않았다. 텍스트 비교 임계값도 실제 메모 자료로 보정하지 않았다. 상용 서비스 문서는 사용자가 할 수 있는 조작과 제공 조건을 확인하는 근거로만 사용했으며 효과나 시장 수요를 입증하는 자료로 사용하지 않았다. 실제 사용자 인터뷰, 위성영상 이용 조건 검토와 법률 판단도 진행하지 않았다.

## 후보를 비교한 기준

결론은 구현 난이도가 낮은 주제보다, 사용자 과업과 실패 조건을 설명하고 같은 조건에서 결과를 다시 확인할 수 있는 주제를 먼저 검토해야 한다는 것이다.

- 기존 제품을 축소해서 다시 만드는 대신 해결할 판단이나 반복 작업이 분명한가.
- 현재 사용자를 모집하지 못해도 고정된 입력과 예상 결과로 중요한 주장을 검증할 수 있는가.
- 프론트엔드가 맡은 상태, 계산, 표현과 오류 복구를 외부 모델의 성능과 구분할 수 있는가.
- 접근성, 개인정보, 데이터 출처와 실패 시 복구 방법을 과업 안에서 다룰 수 있는가.
- 한 명이 공개 상태로 유지할 때 데이터, 서버, 생성 비용과 외부 서비스 변경을 감당할 수 있는가.
- 사례 설명에서 선택한 대안, 측정 조건, 결과와 한계를 함께 제시할 수 있는가.

## 주제 1. 위성영상 변화 검토 작업대

### 제안 결론

GeoJSON과 GeoTIFF를 사용하는 후보는 범용 위성영상 뷰어가 아니라, 비교할 장면의 품질을 확인하고 변화 구역과 판단 근거를 다시 검토할 수 있게 내보내는 작업대로 제한하는 편이 좋다. 이 형태라면 공간 자료 해석, 대용량 파일 처리, 비동기 요청, 시각화와 정확성 검증을 하나의 과업으로 연결할 수 있다.

### 공식 자료와 실제 사례에서 확인한 사실

[GeoJSON RFC 7946](https://www.rfc-editor.org/rfc/rfc7946)은 Feature와 FeatureCollection의 JSON 표현을 정의하고 좌표를 WGS 84의 경도, 위도 순서로 사용한다. 따라서 GeoJSON은 위성영상 자체보다 관심 영역, 판독 다각형과 주석을 기록하는 데 알맞다. 다른 좌표계의 래스터와 함께 표시할 때에는 좌표 순서와 재투영을 별도로 검증해야 한다.

[OGC GeoTIFF 1.1 표준](https://docs.ogc.org/is/19-008r4/19-008r4.html)은 TIFF 안에 래스터의 위치 변환과 좌표 참조 정보를 기록하는 방식을 정의한다. [OGC Cloud Optimized GeoTIFF 1.0 표준](https://docs.ogc.org/is/21-026/21-026.html)은 타일, 축소 해상도 영상과 HTTP Range 요청을 이용해 필요한 부분부터 읽을 수 있게 한다. 원격 COG를 브라우저에서 읽으려면 제공 서버가 Range 요청과 CORS를 허용해야 하며, 파일이 COG 형식이라는 사실만으로 빠른 화면이 보장되지는 않는다.

[STAC 1.1.0 사양](https://github.com/radiantearth/stac-spec)은 촬영 시간, 공간 범위, 자산 링크를 가진 Item을 GeoJSON Feature로 표현한다. STAC은 영상을 그리는 형식이 아니라 장면을 찾고 GeoTIFF나 COG 자산으로 연결하는 메타데이터 구조다. 연결된 JSON 파일만으로 정적 Catalog를 만들 수 있지만 임의의 공간과 시간 조건으로 검색하려면 보통 STAC API가 필요하다.

[geotiff.js 공식 저장소](https://github.com/geotiffjs/geotiff.js)는 브라우저에서 로컬 또는 원격 TIFF를 열고, 범위나 경계 상자로 일부 픽셀과 밴드를 읽고, Worker pool로 디코딩할 수 있음을 보여준다. 2026년 3월 11일 공개된 v3.0.5까지 확인했다. 이 자료는 브라우저 처리 가능성의 근거이며 이 문서에서 의존성 채택을 결정하지 않는다.

웹 브라우저에서 확인한 [NASA Worldview](https://worldview.earthdata.nasa.gov/)는 레이어, 사건, 날짜 축, 차트, 비교와 내려받기를 하나의 화면에 제공한다. [Copernicus Browser 공식 문서](https://documentation.dataspace.copernicus.eu/Applications/Browser.html)는 관심 영역, 거리와 면적 측정, 좌우 비교, 시간 경과 영상, 스펙트럼과 시계열 분석, GeoTIFF 내려받기를 지원한다고 설명한다. [LandsatLook 2.0 안내서](https://landsatlook.usgs.gov/assets/documents/LandsatLook_2.0_User_Guide.pdf)도 모자이크, 구름 제거, 밴드 조합과 지수를 제공한다. 이 범위를 다시 만드는 것은 한 명이 유지할 미니 애플리케이션의 목적과 맞지 않는다.

### 사용자와 완료할 과업

가장 구체적인 사용자는 공개 위성영상으로 지역 변화를 조사하는 환경 보도, 교육 또는 비영리 조사 담당자다. 사용자는 다음 과정을 완료한다.

1. 조사할 질문과 GeoJSON 관심 영역을 고른다.
2. STAC 메타데이터에서 촬영일, 센서, 공간 해상도와 구름량을 확인해 비교할 두 장면을 선택한다.
3. 같은 표시 조건에서 두 시점을 스와이프하거나 좌우로 비교하고, 변화로 판단한 구역을 표시한다.
4. 구름, 계절, 센서와 해상도 차이처럼 판단을 흔드는 요인을 확인한다.
5. 관심 영역, 선택한 장면과 자산, 표시 조건, 판독 구역과 설명을 한 묶음으로 내보낸다.

첫 버전은 자동으로 산림 훼손이나 침수 여부를 판정하지 않는다. 센서, 대기 보정, 구름 마스크와 시기 조건이 맞지 않으면 화면의 색 차이가 실제 변화가 아닐 수 있기 때문이다. 준비된 사례에서 `시각적 변화 검토`를 지원한다고 설명하고 과학적 변화 탐지 결과라고 확대하지 않는다.

### 브레인스토밍한 구상

추천 형태는 `질문 설정 → 장면 품질 확인 → 두 시점 비교 → 변화 구역 표시 → 판독 기록 내보내기` 흐름이다. 지도보다 선택 근거와 재현 정보가 결과물의 중심이 된다.

다른 형태도 가능하지만 첫 범위에는 각각 조건이 붙는다.

- **장면 적합성 검사기:** 관심 영역을 포함하는 장면을 찾고 구름량, 촬영일, 해상도와 실제 썸네일을 함께 비교한다. 변화 판독을 제외해 다룰 동작이 가장 적으므로 초기 검증에 알맞다.
- **경계 품질 검토기:** 행정, 농지 또는 시설 경계 GeoJSON과 영상을 겹쳐 어긋난 구역을 표시한다. 실제 검토자가 정의한 정답 자료가 있을 때만 성립한다.
- **밴드 조합 학습 도구:** 고정 사례에서 밴드와 지수 계산 결과를 비교한다. 교육 과업은 분명하지만 센서별 scale, offset과 기준 계산을 검증할 자료가 필요하다.
- **범용 탐색기:** 여러 데이터 제공자, 전 지구 검색과 임의 분석을 지원하는 형태는 기존 공식 도구와 겹치고 운영 범위가 너무 커서 제외한다.

### 첫 구현에 포함할 항목과 배포 방식

첫 범위는 사용 허가를 확인한 고정 사례 두세 개, 각 사례의 GeoJSON 관심 영역과 비교 가능한 COG 두 장면을 제공하는 정적 애플리케이션이다. 로컬 GeoJSON과 GeoTIFF 불러오기, 두 시점 비교, 판독 다각형과 메모, 판독 기록 JSON과 GeoJSON 내보내기를 포함할 수 있다. 서버로 원본 파일을 전송하지 않고 브라우저 Worker에서 필요한 범위만 처리하면 개인정보와 운영 부담을 줄일 수 있다.

원격 COG는 Range와 CORS를 지원할 때만 정적 배포에서 직접 사용한다. 인증 키가 필요한 자료, 여러 장면의 전체 해상도 모자이크, 긴 기간의 픽셀 시계열, 임의 좌표계 변환, 계정별 영구 공유와 공동 편집은 서버 책임이 생기므로 첫 범위에서 제외한다.

### 검증 가능한 프론트엔드 증거

고정된 COG와 예상 판독 결과를 사용하면 별도의 사용자를 모집하지 않아도 다음 결과를 반복 측정할 수 있다.

- 전체 파일 크기와 실제 전송한 바이트, Range 요청 수와 캐시 적중 수
- 헤더 해석, 타일 디코딩, 재투영과 첫 비교 화면까지 걸린 시간
- 관심 영역을 빠르게 바꿀 때 이전 요청을 취소하고 마지막 선택 결과만 표시하는지 여부
- Worker 사용 전후 메인 스레드의 긴 작업, 프레임 지연과 최대 메모리
- 기준 좌표와 화면 좌표의 왕복 오차, 기준 다각형과 계산한 면적의 오차
- NoData, 구름 마스크, 밴드 scale과 offset, 타일 경계와 날짜변경선 사례의 처리 결과
- 포인터 없이 관심 영역과 장면을 선택하고 같은 메타데이터와 판독 결과를 텍스트 목록에서 확인하는 과업

실제 사용자 평가를 진행할 수 있게 되면 장면 선택 이유를 설명하고 준비된 변화 구역을 찾는 과정을 관찰한다. 이 결과는 형성 평가로 기록하며 소수 참여자의 성공률을 전체 사용자 성과로 확대하지 않는다.

### 위험과 중단 조건

- 비교 가능한 장면을 확보하지 못하면 변화 검토를 중단하고 장면 적합성 검사기로 줄인다.
- COG 제공자가 Range와 CORS를 지원하지 않으면 무단 프록시를 만들지 않고, 사용 허가를 확인한 고정 자료나 로컬 파일만 지원한다.
- 좌표계, NoData, 밴드 해석과 구름 조건을 사례 설명에서 재현할 수 없으면 자동 계산 결과를 공개하지 않는다.
- 임의 GeoTIFF 지원이 메모리, 압축 방식과 불완전한 좌표 정보 때문에 예측할 수 없으면 지원 형식과 파일 크기를 명시적으로 제한한다.
- 외부 자료 URL, 할당량과 카탈로그가 바뀔 수 있으므로 고정 사례의 출처, 촬영일, 처리 수준, 라이선스와 마지막 확인일을 함께 보존한다.

## 주제 2. 반복 문장 정리 작업대

### 제안 결론

이 후보는 범용 메모장이 아니라, 개인 메모에서 필요한 조각을 모으고 반복되는 문장을 근거와 함께 비교한 뒤 재사용 템플릿으로 정리하는 도구로 제한한다. 세 후보 가운데 사용자 과업, 로컬 우선 배포, 재현 가능한 검증과 한 명의 운영 부담이 가장 잘 맞는다.

### 공식 자료와 실제 사례에서 확인한 사실

[Google Docs의 비연속 텍스트 선택 안내](https://workspaceupdates.googleblog.com/2022/05/multiple-text-selections-in-google-docs.html)는 떨어진 여러 텍스트를 함께 선택해 복사하거나 서식을 적용하는 과업이 실제 제품에 있음을 보여준다. [Readwise Reader 내보내기 문서](https://docs.readwise.io/reader/docs/faqs/exporting)는 문서나 태그별 하이라이트와 메모를 클립보드 또는 Markdown으로 내보내고 Jinja2 템플릿을 편집할 수 있다고 설명한다. [Text Blaze 동적 스니펫 안내](https://blaze.today/guides/dynamic-commands/)는 입력 칸, 선택 항목과 조건을 가진 재사용 문구를 제공한다.

이 사례들은 수집, 복사와 이미 만든 템플릿의 재사용을 각각 해결한다. 조사한 공식 문서에서는 사용자가 과거에 쓴 여러 문장을 비교하고 반복된 부분과 달라지는 부분을 확인한 뒤, 원문 사례를 검증 자료로 유지하면서 템플릿으로 바꾸는 전체 흐름을 확인하지 못했다. 이 결과는 시장에 같은 제품이 없다는 증명이 아니라, 조사 범위에서 차별화할 과업을 찾았다는 뜻이다.

[W3C Selection API](https://www.w3.org/TR/selection-api/)는 문서 선택을 Range와 연결하지만 여러 Range를 한 선택에 두는 동작은 브라우저 엔진 사이에 차이가 있었음을 기록한다. 특별한 다중 선택 동작에 의존하지 않고 사용자가 한 번 선택한 범위를 애플리케이션 상태에 차례로 추가해야 한다.

[W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/)의 TextQuoteSelector는 선택한 정확한 문자열과 앞뒤 문맥을 기록해 원문의 위치를 다시 찾을 수 있게 한다. 편집 후 위치가 바뀔 수 있으므로 시작과 끝 위치만 저장하는 방식보다 이 구조를 함께 사용하는 편이 적합하다.

[W3C Clipboard API and Events, 2026년 6월 24일 초안](https://www.w3.org/TR/clipboard-apis/)은 비동기 클립보드 접근이 사용자 동작, 권한과 보안 조건에 영향을 받는다고 설명한다. [W3C Indexed Database API 3.0](https://www.w3.org/TR/IndexedDB/)은 브라우저에서 구조화된 데이터를 비동기로 저장하는 근거를 제공하지만, 브라우저 저장소는 사용자가 사이트 데이터를 지우거나 저장 공간을 회수하면 사라질 수 있다.

[Unicode 정규화 표준 UAX #15](https://www.unicode.org/reports/tr15/)는 NFC가 한글 음절과 자모처럼 표준적으로 같은 문자열을 일관된 표현으로 만들면서 호환 문자 구분은 보존한다고 설명한다. NFKC는 의미 있는 구분도 없앨 수 있어 임의의 메모에 일괄 적용하지 않는다. [Unicode 텍스트 분절 표준 UAX #29](https://unicode.org/reports/tr29/)는 자소 묶음, 단어와 문장 경계를 정의하면서 언어별 조정이 필요할 수 있다고 밝힌다. [ECMA-402의 `Intl.Segmenter`](https://tc39.es/ecma402/#sec-segmenter-objects)는 브라우저에서 로케일에 맞춘 자소 묶음, 단어와 문장 분절을 사용할 표준 근거를 제공한다.

[Broder의 문서 유사성과 포함 관계 연구](https://www.cs.princeton.edu/courses/archive/spring13/cos598C/broder97resemblance.pdf)는 n-gram 집합의 교집합을 합집합과 비교하는 대칭 점수와 짧은 문서가 긴 문서에 들어 있는 정도를 재는 방향성 점수를 구분한다. [Winnowing 연구 원문](https://theory.stanford.edu/~aiken/publications/papers/sigmod03.pdf)은 긴 문서에서 일정 길이 이상의 동일한 부분을 지역 지문으로 찾는 방법을 설명한다. 두 방법은 문자열에 실제로 겹치는 부분이 있는지 찾는 근거이며 뜻만 비슷한 문장을 판정하는 의미 모델이 아니다.

[EACL 2026 한국어 형태 연구](https://aclanthology.org/2026.eacl-short.22/)는 한국어 어절이 어근에 조사와 어미가 붙고 활용과 축약으로 표면형이 달라질 수 있음을 설명한다. 띄어쓰기 단위의 단어 비교만 사용하면 `배포한다`와 `배포했습니다` 같은 반복을 놓칠 수 있으므로 단어 n-gram과 문자 n-gram을 서로 다른 근거로 함께 확인할 필요가 있다.

### 사용자와 완료할 과업

주 사용자는 배포 공지, 장애 회고, 검토 답변과 운영 안내처럼 비슷한 문서를 반복해서 작성하는 개발자나 기술 문서 작성자다. 고객 지원 담당자와 연구자도 후보가 될 수 있지만 개인정보와 출처 보존 조건이 달라 별도 검증이 필요하다.

사용자는 다음 과정을 완료한다.

1. 직접 작성한 plain text 또는 Markdown 메모를 만들거나 불러온다.
2. 필요한 문장이나 문단을 선택하고 명시적인 추가 동작으로 `문장 바구니`에 누적한다.
3. 바구니의 조각을 순서대로 배치하고 구분자와 출처를 확인해 복사한다.
4. 여러 메모에서 정확히 반복되거나 어휘가 많이 겹치는 문장을 출처와 차이 표시로 검토한다.
5. 반복된 공통 부분과 문서마다 달라지는 부분을 확인하고, 사람이 변수 이름과 범위를 정해 템플릿으로 저장한다.
6. 템플릿을 원문 사례에 다시 적용해 빠진 문장, 잘못 묶인 변수와 예외를 확인한다.

특별한 클릭 방식은 빠른 조작으로 제공할 수 있지만 유일한 방법으로 두지 않는다. 텍스트 선택 뒤 보이는 추가 버튼, 키보드 동작과 체크박스 목록에서도 같은 과업을 완료할 수 있어야 한다.

### LLM 없는 어휘상 근접 반복 탐지 절차

결론은 `원문 보존 → NFC 분석본 → 문단 중심 분절 → 정확한 반복과 포함 관계 → 문자와 단어 n-gram 비교 → 중요 표현 충돌 확인 → 차이 표시 → 사람의 템플릿 확정` 순서다. 모든 판정은 같은 입력과 설정에서 다시 계산할 수 있어야 하며 LLM 호출은 필수 흐름에 포함하지 않는다.

`겹치는 텍스트`는 하나의 점수로 정의하지 않는다. 첫 범위에서는 다음 세 종류를 따로 보여주고 자동으로 합치지 않는다.

- **정확한 반복:** 원문은 보존하고 NFC, 줄바꿈과 연속 공백처럼 명시한 규칙만 적용한 분석본의 문자열이 같다.
- **포함 관계:** 한 문장이나 문단의 n-gram 대부분이 다른 문장 안에 들어 있다. 짧은 문장과 긴 문단을 비교할 때 양방향 포함 점수를 따로 계산한다.
- **어휘상 근접 반복:** 단어 n-gram과 Unicode 자소 묶음 기준 문자 n-gram이 각각 정한 임계값 이상 겹친다. Jaccard 점수, 양방향 포함 점수, 길이 비율과 실제로 겹치는 부분을 함께 보여준다.

이 문서에서 어휘상 근접 반복은 같은 표면 어휘나 연속된 글자가 상당 부분 다시 나타나는 경우다. `검토했습니다`와 `검토했고`는 후보가 될 수 있지만, 어휘가 다른 `확인했다`와 `검토했다`를 뜻이 같다는 이유만으로 찾지는 않는다. 의미상 바꿔 쓴 문장은 첫 범위 밖이다.

분석 단위는 Markdown 문단과 목록 항목을 우선하고 문장 분절은 보조로 사용한다. 단어 n-gram은 어휘와 가까운 설명을 제공하고 문자 n-gram은 한국어 활용, 띄어쓰기와 짧은 수정에도 남는 공통 부분을 찾는다. 두 점수를 하나로 숨기지 않아 어느 근거로 후보가 되었는지 확인할 수 있게 한다. Winnowing은 긴 동일 구간의 위치를 찾는 보조 수단으로만 사용한다.

첫 범위의 작은 메모 모음은 모든 문단 쌍에 정확한 Jaccard와 포함 점수를 계산한다. 자료가 커져 전체 비교가 정한 반응 시간이나 메모리 한도를 넘을 때에는 희귀 n-gram 역색인이나 Winnowing으로 후보를 먼저 줄인다. MinHash와 LSH는 규모가 더 커졌을 때 검토할 근사 검색이며, 최종 점수는 후보 원문에 정확한 비교를 다시 수행해 정한다. 근사 검색이 검증 자료의 반복을 놓치면 자료 수를 제한하거나 정확한 비교로 돌아간다.

후보 쌍에는 diff를 적용해 공통 부분과 달라진 구간을 보여주지만, 차이를 자동 변수로 확정하지 않는다. 부정 표현, 숫자, 날짜, 버전, 단위, `이상`과 `이하`, 의무와 가능, 책임 주체가 달라지면 `충돌 가능`으로 표시하고 높은 신뢰도 묶음과 자동 템플릿 제안을 막는다. 조사와 어미를 일괄 삭제하는 정규화도 주체, 목적어, 시제와 조건을 바꿀 수 있어 사용하지 않는다.

### 브레인스토밍한 구상

추천 형태는 `메모 작성 → 문장 바구니 수집 → 반복 유형별 검토 → 차이 확인 → 사람의 템플릿 확정 → 원문 사례 재검증` 흐름이다. 템플릿은 결과만 저장하지 않고 어떤 원문에서 공통 부분과 변수를 정했는지도 연결한다.

첫 형태와 맞닿은 다른 구상은 다음과 같다.

- **문장 조립 바구니:** 여러 텍스트 조각을 빠르게 모아 순서와 구분자를 정하고 plain text나 Markdown으로 복사하는 과업에만 집중한다. 반복 탐지가 충분히 정확하지 않을 때 남길 수 있는 최소 형태다.
- **반복 표현 검토기:** 템플릿 생성 없이 정확한 반복, 포함 관계와 어휘 중복을 출처와 차이로만 보여준다. 자동화보다 신뢰 가능한 검토가 중요할 때 적합하다.
- **답변 템플릿 정리기:** 여러 답변 초안에서 이름, 날짜와 상태처럼 바뀌는 부분을 사람이 변수로 지정한다. 고객정보가 들어간 실제 자료를 사용할 때에는 로컬 처리와 비식별 검증 자료가 필요하다.
- **범용 지식 관리 도구:** 협업 편집, 브라우저 확장, 모든 외부 앱 수집과 의미 검색을 함께 제공하는 형태는 기존 메모 제품과 겹치고 첫 범위를 벗어나므로 제외한다.

### 첫 구현에 포함할 항목과 배포 방식

첫 범위는 가입과 동기화가 없는 단일 기기용 로컬 우선 애플리케이션이다. 앱에서 만든 plain text와 Markdown 메모, 준비된 검증 자료, 문단 단위 문장 바구니, 정확한 반복과 어휘상 근접 반복, 차이 표시, 사람이 확정하는 템플릿, plain text와 Markdown 복사, JSON 내보내기와 다시 불러오기를 포함한다. 반복 판정은 메모를 외부로 보내거나 LLM을 호출하지 않고 브라우저 안에서 처리한다.

이 범위는 `사용자마다 자신의 메모를 기록한다`는 방향을 한 브라우저의 개인 공간으로 먼저 검증한다. 실제 계정별 저장, 여러 기기 동기화와 공유가 승인되면 인증, 사용자별 접근 제어, 백업, 충돌 처리와 삭제 책임을 서버에 추가해야 한다. 로컬 우선이라는 표현이 자동 암호화나 영구 보존을 뜻하지 않으므로 내보내기와 복구 방법은 첫 범위에도 필요하다.

### 검증 가능한 프론트엔드 증거

사람이 `정확한 반복`, `포함 관계`, `어휘상 근접 반복`, `뜻만 비슷함`, `중요 표현이 충돌함`을 미리 표시한 검증 자료를 만들면 다음 결과를 반복해서 확인할 수 있다. 띄어쓰기, 조사와 어미, 문장 삽입과 순서가 달라진 양성 사례와 숫자, 부정, 조건, 의무 수준과 책임 주체만 달라진 음성 사례를 함께 둔다. 임계값을 조정할 자료와 마지막에 확인할 자료는 분리한다.

[NIST TREC 평가 지표 정의](https://trec.nist.gov/pubs/trec22/appendices/measures.pdf)에 따라 precision은 표시한 후보 중 실제 반복인 비율, recall은 정답 반복 중 찾은 비율로 계산한다. 관계 유형과 한국어 변형 유형별 수치를 따로 기록하고 하나의 평균으로 오탐을 숨기지 않는다.

- 포인터, 키보드와 터치로 같은 문단을 바구니에 추가하고 같은 순서로 복사하는지 여부
- 문장 앞뒤를 수정한 뒤 TextQuoteSelector와 위치 정보를 이용해 원문을 다시 찾은 비율과 실패 표시
- 정확한 반복, 포함 관계와 어휘상 근접 반복의 precision, recall, 문자와 단어 n-gram 임계값별 오탐 사례
- 점수 근거로 표시한 공통 부분이 사람이 표시한 실제 중복 구간과 맞는지 여부
- 숫자, 부정, 조건, 의무 수준과 책임 주체가 충돌한 후보가 높은 신뢰도 묶음에 들어가는지 여부
- 템플릿이 원문 사례를 다시 만들 때 빠진 공통 문장, 잘못 지정한 변수와 예외를 차이로 찾는지 여부
- 1,000개 문단의 499,500개 쌍을 비교할 때 [WHATWG Web Workers 표준](https://html.spec.whatwg.org/dev/workers.html)에 따른 Worker 사용 전후의 전체 분석 시간, 첫 후보 표시 시간, 긴 작업, 입력 지연, 취소된 분석, 전달한 데이터 양과 최대 메모리
- 클립보드 권한이 거부됐을 때 복사할 텍스트를 별도 화면에 제공하고 plain text와 Markdown 형식을 보존하는지 여부
- IndexedDB 구조 변경, 저장 공간 오류, 새로고침과 오프라인 상태에서 내보내기와 다시 불러오기 결과가 같은지 여부
- 겹치는 표시를 색만으로 구분하지 않고 목록과 텍스트 차이로도 찾을 수 있는지 여부

초기 검증 기준으로는 현실적인 메모 20개에서 재사용할 템플릿 후보가 3개도 나오지 않으면 템플릿화를 빼고 문장 바구니와 중복 검토만 남기는 방안을 제안한다. 신뢰도가 높은 제안의 precision이 90%에 이르지 못하거나 숫자와 부정 충돌 사례가 높은 신뢰도 묶음에 하나라도 들어가면 근접 반복을 자동 묶음으로 표시하지 않고 점수와 근거만 제공한다. 일반적인 문장 추가와 삭제 뒤 원문 재연결 실패가 5%를 넘으면 자동 복원을 중단하고 다시 찾지 못한 선택을 `재확인 필요`로 표시한다. 이 수치는 승인된 품질 기준이 아니라 과장을 막기 위한 초기 중단 기준 제안이다.

### 위험과 중단 조건

- 개인 메모에는 계정, 고객, 건강과 업무 정보가 섞일 수 있다. HTML을 그대로 렌더링하지 않고 외부 전송을 기본값으로 삼지 않으며, 동기화가 필요해질 때 보관, 암호화와 삭제 조건을 별도로 결정한다.
- 어휘가 비슷해도 부정어, 숫자, 시제와 책임 주체가 다르면 뜻이 반대일 수 있다. 출처와 차이를 보여준 뒤 사용자가 확정하게 하고 자동 병합은 제공하지 않는다.
- 브라우저 저장소가 삭제되거나 용량을 회수당할 수 있다. 내보내기와 다시 불러오기 왕복 검증이 성립하지 않으면 실제 개인 메모 저장 기능을 사용자에게 제공하지 않는다.
- 외부 문서에서 가져온 문구에는 저작권과 출처 문제가 생길 수 있다. 원본 위치와 작성 구분을 보존하고 자동 공개나 공유를 제공하지 않는다.
- 특별한 클릭이 브라우저 기본 선택, 터치와 보조기술 조작을 방해하면 보조 기능으로만 남기고 명시적인 추가 버튼과 목록 조작을 기본 흐름으로 사용한다.

## 주제 3. 검증된 생성 세계 보행 실험실

### 제안 결론

이 후보는 프롬프트로 만든 화면을 둘러보는 뷰어가 아니라, 키보드로 캐릭터처럼 이동하면서 진행 방향의 다음 청크를 준비하는 탐험 도구여야 한다. 캡슐 형태의 캐릭터 충돌체, 중력, 접지 상태, 벽 충돌, 경사와 계단 제한을 브라우저가 계속 계산한다. 다음 청크는 화면 자산과 충돌체, 지면과 연결 통로 검사를 모두 통과한 뒤에만 열며, 준비 전에는 실제 충돌체가 있는 관문으로 진입을 막는다.

외부 개발자용 API의 약 5분 생성 시간을 이동 중에 숨기기는 어렵다. 첫 범위에서는 규칙으로 재현되는 지형과 충돌체를 먼저 준비하고, 프롬프트로 만든 화면 자산을 비동기로 입히는 혼합 구조가 가장 현실적이다. 생성 모델이 이어지는 지형과 충돌체까지 전부 만들면서 중단 없이 걷는 형태를 필수로 해석하면 외부 개발자가 이용할 수 있는 공식 API 문서만으로는 구현 가능하다고 판단할 수 없다.

### 공식 자료와 실제 사례에서 확인한 사실

웹 브라우저에서 확인한 [World Labs Marble](https://marble.worldlabs.ai/)은 프롬프트로 만든 3D 공간을 탐색하고 공유하는 흐름을 제공한다. [World Labs API](https://docs.worldlabs.ai/api)는 한 번의 공간 생성에 약 5분이 걸리고, 화면에 표시할 SPZ splat과 별도의 GLB 충돌 모델을 결과로 제공한다고 안내한다. [내보내기 사양](https://docs.worldlabs.ai/marble/export/specs)은 충돌 모델을 간단한 물리 계산용 10만 개에서 20만 개 삼각형의 거친 메시(mesh)로 설명한다. [Mesh 안내](https://docs.worldlabs.ai/marble/export/mesh)는 충돌 모델을 화면 자산으로 사용하지 말아야 하고, 재구성 결과에 구멍과 떠 있는 면이 생길 수 있다고 밝힌다. 화면이 보인다는 사실만으로 걸을 수 있는 바닥과 막힌 벽이 존재한다고 판단할 수 없다.

[World Labs의 3인칭 이동 사례](https://www.worldlabs.ai/labs/showcase/third-person-controller)는 splat과 충돌 모델을 함께 사용하고 별도의 캐릭터 이동 제어로 충돌, 경사, 계단, 중력과 접지 상태를 처리한다. 이 사례는 미리 생성한 한 공간에서 게임과 같은 이동이 가능하다는 근거이지, 이동 중에 이어지는 공간을 생성한다는 근거는 아니다.

웹 브라우저에서 확인한 [Three.js 1인칭 게임 예제](https://threejs.org/examples/games_fps.html)는 WASD 이동과 점프를 제공하고, [Octree 문서](https://threejs.org/docs/pages/Octree.html)에 설명된 공간 분할 구조와 캡슐 충돌 검사를 사용한다. 공식 예제 소스에서는 바닥 법선으로 접지 상태를 정하고 중력, 충돌 보정과 추락 복구를 따로 적용한다. 렌더링만으로 벽 관통과 허공 보행을 막을 수 없음을 보여주는 재현 가능한 사례다.

[Rapier 캐릭터 이동 제어 문서](https://rapier.rs/docs/user_guides/javascript/character_controller/)는 장애물에 맞춘 이동 보정, 경사 제한, 계단 오르기, 지면 밀착과 접지 결과를 제공한다. [Rapier 장면 질의 문서](https://rapier.rs/docs/user_guides/javascript/scene_queries/)의 캡슐 교차 검사, shape cast와 ray cast는 안전한 시작 위치와 발아래 지면을 검사하는 방법을 설명한다. [Recast Navigation 소개](https://recastnav.com/md_Docs_2__1__Introduction.html)는 삼각형 지형을 이동 가능한 navmesh로 변환하고 타일 단위 구조를 만들 수 있음을 보여준다. navmesh는 이동 가능한 구역과 연결성을 확인하는 보조 자료이며, 직접 조작하는 캐릭터의 벽 관통을 막는 충돌체를 대신하지 않는다.

[Marble Expand 안내](https://docs.worldlabs.ai/marble/create/prompt-guides/expand)는 공식 화면에서 한 방향으로 기존 공간을 확장하는 기능을 설명한다. 그러나 2026년 8월 30일에 다시 검토한 [공개 OpenAPI](https://docs.worldlabs.ai/api/reference/openapi)에서는 기존 공간과 이어지는 확장을 자동화하거나 진행 중인 생성을 취소하는 API 작업을 확인하지 못했다. 이는 외부 개발자용 API 문서에서 확인한 내용이며 다른 기능의 부재를 뜻하지 않는다.

[Google DeepMind Genie 3 발표](https://deepmind.google/blog/genie-3-a-new-frontier-for-world-models/)는 텍스트로 만든 환경을 720p, 초당 24프레임으로 실시간 탐색하고 몇 분 동안 일관성을 유지하는 연구 결과를 소개한다. 같은 자료는 가능한 행동과 긴 상호작용에 한계가 있다고 밝힌다. 영상 형태의 세계 모델은 브라우저가 충돌 계산에 쓸 3D 지형을 제공한다는 근거가 아니다.

### 사용자와 완료할 과업

가장 현실적인 사용자는 짧은 상호작용형 3D 공간을 만들고 이동 감각을 검토하는 제작자다. 사용자는 다음 과정을 완료한다.

1. 프롬프트로 공간의 분위기와 다음 진행 방향을 정한다.
2. 검증된 시작 청크에서 키보드로 걷고, 벽과 경사, 계단과 낙하 구역의 반응을 확인한다.
3. 현재 청크의 끝에 가까워지면 진행 방향의 다음 청크가 생성, 전송과 검사를 거치는 상태를 확인한다.
4. 다음 청크가 준비 중이면 현재 청크 끝의 물리 관문에 막혀 허공이나 충돌체가 없는 화면으로 진입하지 않는다.
5. 검사를 통과한 청크가 연결되면 관문이 열리고 같은 이동 조작으로 다음 구역을 탐색한다.
6. 생성이나 검사에 실패하면 검증된 캐시 청크, 현재 공간의 우회로 또는 2D 대체 화면으로 과업을 마친다.

포트폴리오 방문자는 이 과정을 체험할 수 있지만, 시각적 인상을 생성 모델의 품질이나 사용자 문제 해결 성과로 제시하지 않는다. 사례 설명은 프론트엔드가 맡은 이동, 충돌, 청크 상태, 성능과 복구를 생성 제공자의 결과와 구분해야 한다.

### 브레인스토밍한 구상

추천 형태는 `검증된 시작 청크 → 키보드 보행 → 청크 끝 접근 감지 → 다음 청크 생성과 검사 → 물리 관문 해제 → 연속 보행 → 실패 시 검증된 대체 화면` 흐름이다. `사용자가 이동할 때마다 필요한 배경을 추가한다`는 조건은 키 입력마다 생성을 요청한다는 뜻이 아니라, 이동 방향과 남은 거리를 바탕으로 다음 청크를 한 번만 준비하고 준비 상태에 따라 진입 가능 여부를 바꾼다는 뜻으로 구체화한다.

이 흐름을 구현할 수 있는 구상은 다음처럼 나뉜다.

- **재현 가능한 지형과 생성 화면 자산:** 좌표, 지형, 충돌체와 연결 통로는 시드 값과 규칙으로 먼저 만들고, 프롬프트는 splat, 파노라마, 텍스처나 분위기를 만든다. 생성 지연과 실패가 이동 안전성을 깨뜨리지 않아 첫 범위에 가장 알맞다.
- **생성 충돌 모델을 쓰는 청크:** 생성 결과의 화면 자산과 충돌 모델을 함께 받되 축척, 지면, 시작 위치, 연결 통로와 구멍 검사를 통과한 결과만 다음 청크로 사용한다. 실패율과 대기 시간을 실제 API로 측정하기 전에는 첫 범위로 확정하지 않는다.
- **사전 생성 청크와 실시간 외형 교체:** 연결 구조와 몇 개 청크를 미리 검증하고, 이동 중에는 캐시한 청크를 즉시 연결한 뒤 생성된 외형만 바꾼다. 안정적이지만 생성되는 부분을 사례 설명에서 정확히 밝혀야 한다.
- **독립 공간의 포털 전환:** 비동기 상태와 자산 교체를 보여줄 수는 있지만 같은 지도에서 게임 캐릭터처럼 계속 걷는 조건을 충족하지 못하므로 대체 화면으로만 남긴다.

### 첫 구현에 포함할 항목과 배포 방식

첫 범위는 데스크톱 우선, 캐릭터 한 개, 검증된 시작 청크 한 개, 한 방향으로 연결되는 다음 청크 한 개, 한 세션의 생성 작업 최대 한 건으로 제한한다. 키보드 이동, 카메라, 캡슐 충돌체, 중력, 접지 상태, 경사와 계단 제한, 물리 관문, 청크 상태, 생성 화면 자산과 캐시 대체 화면을 포함한다. 멀티플레이, WebXR, NPC, 전투, 무제한 프롬프트와 여러 갈래의 무한 확장은 제외한다.

브라우저는 입력과 카메라, 캐릭터의 이동 보정, 중력과 접지 상태, 현재 청크와 관문, 자산의 단계별 내려받기, 품질 조절, 캐시와 실패 화면을 맡는다. 서버는 제공자 키 보호, 프롬프트 제한, 생성과 상태 조회, 재시도, 요청 중복 제거, 생성 자산 캐시, 세션별 비용과 동시 작업 상한을 맡는다. 이 구분은 특정 라이브러리나 생성 제공자의 채택 결정이 아니다.

다음 청크는 화면 자산과 충돌체를 모두 해석하고, 실제 자산의 좌표와 축척을 맞추고, 이전 출구와 다음 입구를 연결한 뒤에만 활성화한다. 시작 캡슐이 충돌체와 겹치지 않아야 하고, 발아래 지면과 머리 위 여유 공간이 있어야 하며, 허용 경사 안에서 청크 내부까지 접지 상태를 유지하는 짧은 이동 구간이 있어야 한다. 조건 하나라도 실패하면 현재 청크 끝의 관문을 열지 않는다.

완전한 정적 배포는 미리 생성하고 사용 허가를 확인한 자산만 재생할 때 가능하다. 사용자 프롬프트를 외부 생성 API로 보내는 순간 비밀 키, 요청 제한, 비용, 입력 문구와 생성 자산의 보관을 관리할 서버가 필요하다.

### 검증 가능한 프론트엔드 증거

- 벽 정면, 모서리, 문틀과 얇은 벽을 서로 다른 속도로 향했을 때 충돌체를 통과하지 않는지 여부
- 평지, 내리막, 계단, 허용 경사와 초과 경사에서 접지, 미끄러짐과 이동 결과
- 발아래 충돌체가 없을 때 걷기 상태를 유지하지 않고 중력과 낙하 상태를 적용하는지 여부
- 잘못된 시작 위치, 청크의 구멍과 바닥 밖 추락에서 마지막 안전 지점으로 복구하는지 여부
- 청크 준비 전에는 어떤 입력 순서에서도 현재 청크 끝에 있는 관문의 충돌체를 제거하지 않는지 여부
- 방향을 빠르게 바꾸거나 같은 청크 끝을 반복해서 오갈 때 생성 요청을 중복하지 않고 불필요한 요청을 취소하거나 무시하는지 여부
- 화면에 보이는 벽과 충돌 벽, 보이는 바닥과 판정 지면의 거리 오차
- 시작 조작 가능 시간과 생성, 전송 및 검사의 중앙값과 95번째 백분위 시간
- 청크 연결 전후 프레임 시간, 내려받은 바이트, GPU와 JavaScript 메모리, 이전 청크 회수 결과
- pointer lock을 사용할 수 없거나 움직임 감소를 선호하는 조건에서 제공하는 조작과 2D 대체 화면

### 위험과 중단 조건

- 외부 개발자용 생성 API의 약 5분 대기 시간은 일반적인 보행 속도에서 이동 중 즉시 생성과 맞지 않는다. 필요한 사전 준비 거리를 `최대 이동 속도 × 생성, 전송 및 검사의 95번째 백분위 시간 + 안전 여유`로 설명할 수 없으면 끊김 없는 생성을 주장하지 않고 물리 관문 대기나 사전 생성 방식을 표시한다.
- 생성 충돌 모델에서 안전한 시작 위치와 연결 통로를 찾지 못하거나 화면 자산과 충돌체가 같은 위치를 가리키는 검사 기준을 만들지 못하면 그 청크를 폐기한다. 검증 자료에서 벽 관통이나 충돌체가 없는 지면의 보행이 한 번이라도 재현되면 사이트에 배포하지 않는다.
- 생성한 자산의 좌표, 축척과 지면 기준을 자산마다 재현할 수 없으면 서로 다른 자산을 직접 연결하지 않는다. 내보내기 사양은 기본 좌표계를 OpenCV로 설명하지만 [2025년 12월 릴리스 노트](https://docs.worldlabs.ai/marble/release-notes)는 내보내기 좌표계가 OpenGL로 바뀌었다고 기록하므로, 문서의 한 설명을 고정 가정하지 않고 실제 고정 자산으로 화면과 충돌 위치를 함께 검사한다.
- 생성 작업은 [World Labs API 가격 안내](https://docs.worldlabs.ai/api/pricing)에 따른 크레딧(credits)을 사용한다. 한 세션에서 승인한 요청 수나 비용 상한을 넘으면 추가 생성을 막고 검증된 캐시 청크만 제공한다.
- 목표 중급 기기에서 낮은 품질 장면이 초당 30프레임을 유지하지 못하거나 청크를 두 번 연결한 뒤 메모리가 회수되지 않으면 동시에 유지하는 청크와 자산 품질을 줄인다. 기기와 장면 조건은 결과와 함께 기록한다.
- 프롬프트는 외부 제공자에게 전달될 수 있다. 민감한 입력을 받지 않고 전송 대상, 보관 조건과 제공자를 입력 전에 알릴 수 없으면 사용자 프롬프트 생성을 제공하지 않는다.
- 인터넷에서 누구나 볼 수 있는 포트폴리오에 생성 결과를 사용할 권리는 계정과 API 조건에 따라 달라질 수 있다. 배포 전에 [World Labs 이용 약관](https://docs.worldlabs.ai/terms-of-service), 선택한 요금제와 각 입력 자산의 권리를 다시 확인한다.

## 세 후보의 제안 순서

### 1순위 제안: 반복 문장 정리 작업대

첫 후보는 텍스트 선택, 복합 상태, 비교, 로컬 저장, 내보내기와 접근성을 하나의 실제 작성 과업으로 연결한다. 고정된 메모 자료로 정확성과 성능을 검증할 수 있고 서버와 외부 AI 없이도 필수 흐름이 성립한다. 다만 현실적인 메모 표본에서 반복과 템플릿 과업이 실제로 발생하는지 먼저 확인해야 한다.

### 2순위 제안: 위성영상 변화 검토 작업대

두 번째 후보는 공간 자료와 대용량 래스터를 다루는 기술적 깊이가 분명하고 누구나 확인할 수 있는 고정 사례로 검증할 수 있다. 단순 뷰어를 피하고 장면 품질, 판독 근거와 재현 정보에 집중해야 한다. 자료 출처와 이용 조건, 좌표계와 비교 가능한 장면 선정이 첫 준비 과업이다.

### 조건부 연구 후보: 검증된 생성 세계 보행 실험실

세 번째 후보는 실제 키보드 보행, 충돌과 지면 판정, 청크 활성화 조건을 구현해야 하므로 시각 자산 뷰어보다 범위가 크다. 외부 생성 모델, 서버, 비용과 자산 권리에 대한 의존도도 가장 높다. 규칙으로 재현되는 충돌 지형과 생성 화면 자산을 조합하는 방식이 `배경 생성` 요구를 충족하는지 정한 뒤 제한된 기술 시연으로 검토한다. 생성 모델이 연결 지형까지 전부 만들면서 중단 없이 걷는 조건이라면 현재 근거로 첫 구현 후보가 될 수 없다.

세 후보를 모두 구현해야 한다는 결정은 없다. 하나의 잘 검증된 과업이 세 개의 기술 시연보다 [포트폴리오 정체성 사례 조사](portfolio-site-identity-cases.md)에서 정리한 목표와 더 잘 맞는다.

## 요구사항과 다음 결정에 미치는 영향

사용자가 추가로 확정한 조건은 개인 메모 후보가 LLM 없이 어휘상 근접 반복을 찾아야 한다는 점과 3D 후보가 키보드 보행, 벽 충돌과 지면 판정을 제공해야 한다는 점이다. 이 조건은 [요구사항](../requirements.md)에 반영했다. 탐지 점수와 임계값, 혼합형 3D 구조, 후보 이름, 구현 순서, 외부 의존성과 초기 중단 기준은 조사에서 도출한 제안이며 아직 승인된 구현 결정이 아니다.

다음 판단에는 요구사항 작성자의 결정이 필요하다.

- 첫 구현 후보를 세 주제 가운데 어느 것으로 정할지
- 위성영상 후보에서 사용할 조사 사례, 자료 출처, 비교 가능한 두 시점과 결과물 형식을 무엇으로 정할지
- 3D 후보에서 규칙으로 재현되는 지형과 충돌체 위에 프롬프트로 만든 화면 자산을 입히는 혼합 구조를 `배경 생성`으로 인정할지
- 생성 충돌 모델을 다음 청크에 사용하려면 허용할 대기 시간, 연결 실패율과 자산 폐기 비용을 어디까지로 정할지
- 계정별 저장, 여러 기기 동기화, 외부 생성 API와 월 운영 비용을 어느 시점에 허용할지
- 예상 사용자를 누구로 정하고 사용자를 모집할 수 있을 때 어떤 과업으로 형성 평가할지

이 결정 전에는 구현 계획, 의존성 선택과 API 요청 및 응답 형식을 작성하지 않는다.
