# 일괄 복사 패널 개선의 구현 가능성과 설계 제안

화면 개선은 서버 전환과 독립적으로 착수할 수 있다. 이동 메뉴, 팝오버, 패널 크기와 카드 표현을 맡는 기존 모듈이 있어 새 UI 프레임워크나 저장 테이블은 필요하지 않다. 다만 로고 자산 선택과 카드 헤더 후보 채택은 완료 전에 남은 판단이다. 아래 제안은 [요구사항](../requirements.md)의 데스크탑 패널과 추가 화면 개선에 적용하며 구현 완료를 뜻하지 않는다.

## 초기 코드와 원인 후보

2026년 11월 5일 React 19.2.8, Next.js 16.3.3, Tailwind CSS 4.3.3 및 Playwright 1.64.1을 지정한 `apps/notes/package.json`과 다음 소스를 확인했다.

- `features/edit-batch-copy/ui/batch-copy-list.tsx`는 현재 위치와 `reorderButtonsEnabled`를 함께 사용해 이동 동작을 만든다. 데스크탑 패널만 위치 조건으로 판단하도록 바꿀 수 있다. 설정 자료를 통째로 삭제하면 모바일 동작도 바뀌므로 데스크탑 설정 UI와 패널에서의 적용을 제거하고 모바일 값은 유지한다.
- `shared/ui/action-popover/use-action-popover.ts`는 위치를 `(0, 0)`으로 초기화하고 `toggle`에서 크기를 측정한 뒤 React 상태를 변경한다. 표시 시작과 위치 확정의 순서가 분리되어 있어 첫 화면이 잘못된 위치에 그려질 가능성이 있다. 코드상 원인 후보이며 실제 첫 프레임 촬영은 아직 하지 않았다.
- `_pages/notes/ui/batch-copy-workspace.tsx`는 일괄 복사와 속성 패널의 너비를 같은 CSS 값으로 사용한다. 일괄 복사 너비 조절값을 공통 값에 무조건 적용하면 속성 패널까지 바뀐다. 사용자 조절값은 일괄 복사에만 적용한다.
- `features/edit-batch-copy/model/use-batch-copy-pointer-reorder.ts`는 삽입선에 가까워지면 이동 카드의 y좌표를 다른 위치로 옮긴다. 프레임 지연과 별개로 좌표가 갑자기 바뀔 수 있다. 선과 카드의 표시 순서를 조정하는 안을 먼저 비교하고 포인터 추적에 긴 transition을 추가해 현상을 가리지 않는다.

## 현재 코드와 남은 영향

이동 메뉴의 설정 분리와 패널 크기 조절은 현재 코드에 반영돼 있다. `use-action-popover.ts`도 위치 상태를 없애고 열기, 측정과 좌표 적용을 같은 클릭 처리에서 수행한다. 위의 초기 원인 후보를 현재 결함으로 간주하지 않는다. [MDN showPopover 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/showPopover)의 top layer 표시와 실제 위치 계산은 별개이므로 카드 배치 변경 후 화면 아래 항목과 패널 너비 변경 조건을 다시 확인해야 한다.

`tokens.css`에는 일괄 복사 전용 기본 너비 320px, 헤더 60px와 좌우 여백 0.75rem이 있다. `panel-width-storage.ts`는 너비만 localStorage에 보관한다. 카드 변경 전 본문 크기 1.125rem은 속성 패널과 공유했고 `batch-copy-list.tsx`의 실제 항목과 이동 카드 모두 가로 세 열이었다. 카드 후보 구현은 본문 전용 토큰과 두 표시의 상하 배치를 함께 적용한다. 모바일 글자 크기까지 변경할 이유는 없다.

소스와 이전 실행 기록을 대조했으며 새 실행 화면을 촬영하거나 성능을 측정하지는 않았다. 최초 검토 아래의 치수 및 구현 제안 중 이미 반영된 항목과 남은 작업은 [현재 플랜](../plan.md#추가-화면-개선-절차)에서 구분한다.

추가 대조에서 카드의 상하 배치와 본문 전용 1.0625rem 토큰을 확인했다. 작업 트리의 드래그 변경은 이동 카드가 삽입선과 겹칠 때 y좌표를 바꾸던 처리를 제거한다. `shared/ui/drop-indicator`는 항목 사이 간격의 절반에 선을 표시하며 데스크탑은 왼쪽, 모바일은 오른쪽 원형 끝점을 사용한다. 이 변경의 존재와 전체 드래그 성능 개선은 별개의 판단이다.

[Atlassian 드래그 디자인 가이드](https://atlassian.design/components/pragmatic-drag-and-drop/design-guidelines)는 삽입선을 항목 사이 간격의 중앙에 표시하고 이동 대안을 기존 더보기 메뉴에 제공한다. 이 서비스에는 중앙 배치 원칙을 적용하되 색과 끝점 방향은 자체 시안을 따른다. Atlassian 라이브러리의 도입이나 모든 치수의 복제를 전제로 하지 않는다.

## 팝오버의 첫 표시

목표는 처음 보이는 프레임부터 버튼에 맞는 위치에 표시하는 것이다. 기존 네이티브 popover와 포커스 복귀, 바깥 누르기 닫힘은 유지한다. 열기 전 준비와 크기 측정, 위치 확정을 한 표시 과정으로 다루고 위치가 준비되기 전의 내용을 보이지 않게 하는 방법을 검토한다. 닫힌 요소의 크기가 항상 측정된다고 가정하지 않는다.

[MDN의 beforetoggle 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/beforetoggle_event)은 상태 변경 전 이벤트를, [toggle 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/toggle_event)은 상태 변경 후 이벤트를 구분한다. [React의 useLayoutEffect](https://react.dev/reference/react/useLayoutEffect)는 화면에 그리기 전에 측정과 재배치를 완료하는 tooltip 예제를 제공한다. 그러나 네이티브 popover가 이미 표시된 뒤 발생한 이벤트를 Effect로 옮기기만 하면 첫 프레임까지 소급해서 숨길 수 있는 것은 아니다. 열기와 측정의 전체 순서를 확인해야 한다.

CSS anchor positioning을 유일한 방법으로 정하지 않는다. 저장소의 최소 브라우저 버전 전체에 적용 가능한지 확인되지 않았고 현재 네이티브 popover도 최소 버전 호환성을 별도로 확인해야 한다. 최신 세 브라우저 검사만으로 선언된 최소 버전까지 지원한다고 판정하지 않는다.

## 선언된 최소 버전과 Popover API

현재 최소 버전 선언과 팝오버 호출에는 불일치가 있다. `apps/notes/package.json`은 Chrome 및 Edge 111 이상과 Safari 16.4 이상을 선언하지만 `use-action-popover.ts`는 기능 검사 없이 `togglePopover()`와 `hidePopover()`를 호출한다.

2026년 11월 5일 확인한 [MDN 호환성 자료의 HTMLElement 항목](https://github.com/mdn/browser-compat-data/blob/8d371e9fb68c0cdc1908fa370358f6659aaec513/api/HTMLElement.json)은 두 API의 제공 시작을 Chrome 114, Safari 17과 Firefox 125로 기록한다. 따라서 현재 선언의 모든 버전에서 메뉴가 작동한다는 판단은 성립하지 않는다. 이는 소스 및 호환성 자료 대조이며 해당 구버전 브라우저에서 실행한 결과는 아니다.

최소 버전을 임의로 올리지 않고 기존 지원 조건을 유지하는 대체 처리를 우선 조사한다. 공통 팝오버의 첫 위치, 바깥 누르기, Escape와 포커스 복귀가 같은 결과를 내야 한다. API 부재만 흉내 낸 검사로 구버전 CSS와 전체 화면 호환성까지 증명하지 않는다. 스타일 도구가 요구하는 브라우저 버전도 함께 확인한 뒤 변경 대상을 정한다.

### CSS 도구의 조건과 선택지

Popover API 보완만으로 최소 버전 검증이 끝나지는 않는다. [Tailwind CSS 4 호환성 문서](https://tailwindcss.com/docs/compatibility#browser-support)는 Chrome 111, Safari 16.4와 Firefox 128을 공식 기준으로 설명한다. 프로젝트의 Firefox 125 선언은 이 기준보다 낮다. [MDN의 property 호환성 자료](https://github.com/mdn/browser-compat-data/blob/8d371e9fb68c0cdc1908fa370358f6659aaec513/css/at-rules/property.json)에서도 Firefox의 `@property` 제공 시작은 128이다.

다만 [Tailwind CSS 4.1의 구버전 개선 설명](https://tailwindcss.com/blog/tailwindcss-v4-1#improved-compatibility-with-older-browsers)은 그림자와 변환 등의 초기값 보완을 설명한다. 현재 4.3.3으로 생성된 CSS에도 구형 Firefox와 Safari를 대상으로 하는 `@supports` 아래의 초기값 선언이 있다. 공식 기준보다 낮다는 사실만으로 모든 화면이 실패한다고 단정하거나 스타일 도구의 교체를 필수로 정하지 않는다.

`globals.css`의 탐색 서랍은 기본 열린 상태의 opacity와 transform을 별도로 정의한다. `@starting-style`과 `allow-discrete`는 진입 및 종료 효과에 사용한다. 이 구문을 처리하지 못하는 브라우저에서 효과가 생략되는 것과 서랍 자체를 열 수 없는 문제는 구분해서 확인한다.

선택지는 현재 최소 버전을 유지하고 팝오버 대체 처리 및 구버전 실행 증거를 추가하는 안과 Chrome 및 Edge 114, Safari 17, Firefox 128 이상으로 기준을 변경하는 안이다. 후자는 현재 조사한 필수 API와 CSS 도구의 기준을 맞추는 제안이며 전체 기능 호환성을 보증하는 숫자는 아니다. 지원 조건 변경은 아직 결정하지 않았다.

현재 기준을 유지한다면 공통 팝오버에서 열린 상태, 화면 기준 배치, 바깥 누르기와 Escape, 포커스 복귀를 처리해야 한다. 단순히 API 호출을 건너뛰면 메뉴가 열리지 않거나 지원되지 않는 `popover` 속성을 가진 내용이 상시 표시될 수 있다. 메모 카드의 변환과 모달 안에서도 잘림 없이 동작해야 하므로 일반 fixed 요소로 바꾸기만 하는 안은 충분하지 않다. 기존 카드별 명령은 유지하고 공통 UI 안에서 처리하는 방향을 우선한다.

## 패널 크기와 기기별 보관

실행 계획의 초기 후보는 기본 320px, 최소 280px, 최대 `640px`와 `작업 영역 너비 - 48rem` 중 작은 값이다. 현재 나란한 패널 전환 기준인 작업 영역 72rem을 유지하면서 메모 보드에 최소 48rem을 남기는 계산이다. 이 수치는 표준값이 아니라 현재 보드와 패널의 공간을 나누는 제안이다. 글자 확대와 320px 패널의 실제 내용을 확인한 뒤 조정한다.

오른쪽에 붙은 패널의 왼쪽 변을 왼쪽으로 옮기면 너비가 늘어나고 오른쪽으로 옮기면 줄어든다. 나란한 패널에만 크기 조절을 제공하고 기존 모달에는 적용하지 않는 안을 권한다. 창을 줄이면 표시 너비만 허용값으로 보정하며 저장한 선호 너비는 유지한다. 다시 넓히면 저장값을 사용할 수 있다. 취소나 포인터 상실은 조절 전 너비로 돌아가고 완료한 너비만 보관한다.

[W3C Window Splitter 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/)은 두 영역의 상대 크기를 조절하는 separator와 방향키, 현재값 및 최솟값과 최댓값을 설명한다. 문서 자체에 예제와 검토가 미완료라는 주의가 있으므로 완성된 구현의 인증 근거로 사용하지 않는다. 여기서는 세로 조절선의 역할과 키보드 방향을 참고한다. 접기 기능은 별도 추가하지 않는다. [Pointer Events](https://www.w3.org/TR/pointerevents3/)의 capture 및 취소를 적용해 테두리 바깥에서 손을 떼어도 종료되며 정상 종료 뒤 capture 해제를 취소로 다시 처리하지 않게 한다.

너비는 같은 기기의 같은 브라우저 프로필과 사이트 주소에서 유지하는 표시 설정이다. `localStorage`에 숫자 하나를 보관하는 안을 권한다. [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)는 origin별 브라우저 세션 간 보관과 보안 정책에 따른 실패를 설명한다. 브라우저 자료 삭제와 다른 프로필에서는 복원할 수 없으며 서버 동기화로 보완하지 않는다. 저장을 거부한 브라우저에서도 현재 화면의 너비 조절은 작동하고 다음 접속에서는 기본값을 사용하도록 한다. 메모나 편집 초안을 함께 보관하지 않는다.

## 카드와 헤더의 검토 결과

패널 자체 헤더는 약 60px로 줄이고 제목, 항목 수와 닫기 버튼을 수직 중앙에 맞추는 안을 사용한다. 기존 공통 토큰 5.5rem 대신 일괄 복사 전용 60px 토큰을 사용한다. 320px 기본 너비에서 제목과 항목 수가 닫기 버튼을 밀어내지 않는지 확인한다. 이 60px 조건은 항목 헤더와 페이지 탐색 헤더에 적용하지 않는다.

패널 좌우 여백은 각각 0.75rem으로 줄인다. 변경 전 패널 여백은 1.5rem이고 본문 크기는 1.125rem이었다. 일반 메모의 `note-card.tsx` 본문은 `text-base`를 사용한다. 패널 본문은 일반 메모 기본값 1rem보다 조금 큰 1.0625rem을 후보로 제안한다. 기본 루트 크기 16px에서는 17px이며 변경 전 패널 18px보다 작다. 320px 패널에서 좌우 여백만 바꾸면 내부 가용 폭은 24px 늘어난다. 이 계산은 테두리와 항목 내부 여백을 제외한 비교다. 일괄 복사 전용 토큰을 사용해 속성 패널과 모바일의 기존 치수를 유지한다.

데스크탑 패널 항목도 44px 헤더 아래에 본문을 두는 안이 적합하다. 폭 320px에서 좌우 제어가 본문과 같은 행에 있으면 읽을 폭이 더 줄어들기 때문이다. 공통점은 헤더의 핸들 및 더보기 위치와 본문 배치다. 모바일의 짧은 터치 복사와 길게 누르기 추가는 데스크탑에 옮기지 않는다. 짧은 카드가 높아지는 단점은 실제 줄 수와 목록 밀도로 비교한다.

서비스 탐색 헤더와 항목 헤더는 각각 44px지만 같은 컴포넌트로 합치지 않는다. 탐색 헤더는 페이지 이동을, 항목 헤더는 메모 이동과 해당 항목의 동작을 제공한다. 서비스 로고는 미지정이므로 임의 이미지 생성이나 다른 서비스의 로고 재사용을 하지 않는다.

## 판정

모달 재열기 실패에서는 DOM의 닫힘과 활성 패널 상태 해제 사이에 다음 Enter 입력이 들어왔다. 브라우저 이벤트 기록은 `cancel`, Enter 및 click, `close` 순서를 보였다. 기존 코드가 `close`를 받을 때까지 활성 패널을 유지해 실행 버튼의 재열기 요청을 닫기로 판단하는 문제다. [HTML 표준의 다이얼로그 닫기 절차](https://html.spec.whatwg.org/multipage/interactive-elements.html#close-the-dialog)도 `close` 이벤트를 보내는 작업을 큐에 넣도록 정한다. 이 문제는 항목 팝오버의 좌표 깜빡임과 다르다.

`use-batch-copy-panel.ts`는 선택 해제가 아닌 닫기 요청에서 네이티브 다이얼로그 종료, 활성 패널 해제와 실행 버튼 포커스 복귀를 함께 처리한다. 다시 열린 다이얼로그에는 이전 `close` 이벤트를 적용하지 않는다. [MDN cancel 이벤트 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/cancel_event)의 기본 동작 취소를 사용하며 DOM의 open 속성을 직접 제거하지 않는다. [React의 외부 시스템 동기화 설명](https://react.dev/learn/synchronizing-with-effects)에 따라 기존 Effect는 활성 패널과 네이티브 표시를 연결하는 역할을 유지한다. 새 상태 모듈이나 지연 타이머는 필요하지 않다.

- `pass`: 설정에 의존하지 않는 데스크탑 이동 메뉴, 팝오버 첫 위치 보장과 기기별 패널 너비 보관은 기존 모듈을 변경해 구현할 수 있다. 전용 테이블과 범용 이벤트 시스템이 필요하지 않다.
- `needs revision`: 카드 후보 배치의 시각 확정과 실제 기기 확인이 남아 있다. 모달 재열기 수정과 화면 통합 E2E 206건 및 속성 모달 추가 검사 3건은 통과했다. 플랜에는 50개 항목의 드래그 측정, 목록 양 끝의 삽입선과 패널 최소 및 최대 너비의 팝오버 위치 검사 증거가 있다. 모달과 모바일 카드의 루트 글자 크기 200% 검사도 통과했다. 이 조건들을 미검증으로 되돌리지 않는다. 과거 실제 브라우저 200% 및 400% 검사와 최근 카드 및 헤더 변경 이후에 확인한 화면과 동작은 구분하며 실제 휴대전화 입력은 미완료다.
- `needs human input`: 서비스 로고 자산 선택과 검토 대상으로 남아 있는 데스크탑 및 모바일 카드 헤더의 채택. 이 판단은 독립적인 메뉴 및 팝오버 작업을 막지 않는다.
- `not applicable`: 모달 재열기 수정에는 새 순수 규칙과 저장 구조 변경이 없어 TDD와 데이터 마이그레이션 검사를 적용하지 않는다. 실제 브라우저 이벤트와 화면 상태는 기존 E2E로 확인한다.
