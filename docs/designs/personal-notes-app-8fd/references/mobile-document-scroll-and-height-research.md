# 모바일 문서 스크롤과 화면 높이 조사

## 결론

모바일에서 메모 상세와 일괄 복사 확인 화면을 아래로 스크롤하면 하단 동작이 위로 밀리고 그 아래에 빈 공간이 나타날 수 있다. 두 화면의 하단 동작은 각 화면 내부에서는 마지막 행에 배치돼 있지만, 문서 자체가 화면보다 높아지면 화면 전체와 함께 움직인다. 현재 코드에서 가장 직접적인 원인은 `body`의 최소 높이 `100vh`와 과업 화면의 높이 `100dvh`를 함께 사용하는 것이다. 브라우저 주소창이 보이는 동안 두 높이가 다르면 과업 화면 아래에도 문서 스크롤 범위가 남는다.

이 높이 충돌은 두 화면만의 문제가 아니다. 메모 화면도 같은 `100dvh` 프레임을 사용하므로 평상시 목록의 새 메모 버튼, 일괄 복사 수집 중 하단 동작, 넓은 화면의 보기 제어가 문서 스크롤에 따라 이동할 위험이 있다. 보조 화면 네 곳에는 별도의 높이 중복이 있어 짧은 콘텐츠에서도 불필요한 문서 스크롤이 생길 수 있다. 각 화면에서 실제 증상이 발생했는지는 대상 모바일 브라우저에서 따로 확인해야 한다.

## 조사 질문과 기준

2026년 9월 24일 현재 코드와 모바일 화면 캡처를 비교했다. [요구사항의 화면별 프레임과 하단 동작](../requirements.md#반드시-지킬-조건)은 메모 상세 저장 영역과 일괄 복사 수집 동작이 현재 보이는 화면 아래쪽에 남고, 일괄 복사 확인 및 저장 목록 관리에도 하단 작업 동작이 있음을 정한다. 이번 조사는 두 작업 화면의 증상과 같은 높이 계산을 사용하는 다른 화면의 영향을 구분한다. 새 탐색 방식, 자료 저장 규칙과 화면별 고정 위치 제어는 조사 대상이 아니다.

## 현재 코드에서 확인한 화면별 영향

### 메모 상세와 일괄 복사 화면

[`body` 스타일](../../../../apps/notes/src/_app/styles/globals.css)은 `min-height: 100vh`를 사용한다. [`TaskPageFrame`](../../../../apps/notes/src/_app/ui/task-page-frame.tsx)은 `height: 100dvh`에 해당하는 `h-dvh`를 사용하고 내부 넘침을 숨긴다. `/notes/[noteId]`와 `/batch-copy`가 이 프레임을 공유한다.

[메모 상세](../../../../apps/notes/src/_pages/notes/ui/note-detail-page.tsx), [모바일 일괄 복사 확인](../../../../apps/notes/src/_pages/batch-copy/ui/mobile-batch-copy-confirmation.tsx), [저장 목록 관리](../../../../apps/notes/src/_pages/batch-copy/ui/batch-copy-start-page.tsx)의 하단 버튼은 각각 화면 본문의 마지막 Grid 행이다. 프레임 내부의 스크롤과 별개로 문서가 스크롤되면 버튼도 화면 위쪽으로 이동한다.

제공된 Android 캡처에서는 메모 상세 헤더가 화면 위로 사라지고 저장 동작 아래에 빈 문서 영역이 보인다. 이는 위 높이 충돌에서 예상되는 결과와 일치한다. 다만 캡처만으로는 `100vh`, `100dvh`와 실제 문서 스크롤 높이의 계산값을 읽을 수 없으므로 대상 기기에서 수치를 확인해야 한다. `/batch-copy`의 확인 단계와 저장 목록 관리 단계는 같은 프레임과 하단 행을 사용하므로 두 단계 모두 확인 대상이다.

### 메모 화면

`/`의 [`NotesWorkspaceFrame`](../../../../apps/notes/src/_app/ui/notes-workspace-frame.tsx)도 `h-dvh`와 내부 넘침 숨김을 사용한다. 따라서 `body`가 더 크면 프레임 아래의 빈 영역으로 문서 전체를 스크롤할 수 있다.

좁은 화면의 [메모 목록](../../../../apps/notes/src/_pages/notes/ui/mobile-note-list.tsx)은 프레임 안에서 별도로 스크롤하고, [새 메모 제어와 일괄 복사 수집 동작](../../../../apps/notes/src/_pages/notes/ui/mobile-notes-workspace.tsx)은 그 프레임을 기준으로 배치한다. 넓은 화면의 보드 제어도 같은 프레임에 속한다. 메모와 목록의 자체 스크롤은 유지해야 하며, 바깥 문서의 불필요한 스크롤만 없애야 한다.

### 사용 빈도, 텍스트 분석, 템플릿 및 설정

`/usage`, `/analysis`, `/templates`, `/settings`는 [`DocumentPageFrame`](../../../../apps/notes/src/_app/ui/document-page-frame.tsx)의 `min-h-dvh` 안에 탐색과 본문을 둔다. 네 페이지의 본문은 각각 다시 `min-h-screen`, 즉 최소 `100vh`를 사용한다. 짧은 본문에도 탐색 높이와 본문 최소 높이를 더한 문서가 만들어지므로 불필요한 세로 스크롤이 생길 수 있다. 이 화면들에는 메모 상세처럼 하단에 고정해야 하는 작업 행이 없어 캡처와 같은 버튼 이동 증상으로 단정할 수는 없다. 콘텐츠가 길 때의 일반 문서 스크롤은 보존해야 한다.

### 접속 주소 확인과 오류

[`RuntimeAccessGuard`](../../../../apps/notes/src/_app/ui/runtime-access-guard.tsx)는 접속 주소 확인 및 오류 상태에 `min-h-screen`을 사용한다. 이 상태는 페이지 프레임을 렌더링하지 않으므로 `100vh`가 현재 보이는 높이보다 클 때 안내의 중심이 밀리거나 문서 스크롤이 생길 수 있다. 하단 버튼은 없고 짧은 상태 화면에 한정된다.

## 표준과 공식 설명

[CSS Values and Units Level 4](https://www.w3.org/TR/css-values-4/#viewport-variants)는 기본 `vh`를 큰 표시 영역, `dvh`를 브라우저 UI의 펼침과 접힘을 반영하는 동적 표시 영역으로 정의한다. 모바일 주소창이 펼쳐진 상태에서는 같은 화면에서 두 값이 다를 수 있다. [Chrome의 모바일 표시 영역 설명](https://developer.chrome.com/blog/whats-new-css-ui-2023#dynamic-viewport-units)은 `100vh`가 모바일 브라우저 탐색 막대의 변화를 반영하지 않아 불필요한 스크롤을 만들 수 있다고 설명한다. Tailwind CSS의 [높이](https://tailwindcss.com/docs/height)와 [최소 높이](https://tailwindcss.com/docs/min-height) 문서는 현재 코드의 `h-dvh`가 `height: 100dvh`, `min-h-screen`이 `min-height: 100vh`임을 확인한다.

동적 표시 영역은 브라우저 UI의 상태에 따라 달라지지만 화면 키보드가 차지하는 공간까지 모든 브라우저에서 같은 방식으로 줄인다고 보장하지 않는다. [CSS 명세의 동적 표시 영역 설명](https://www.w3.org/TR/css-values-4/#viewport-variants)은 화면 키보드처럼 콘텐츠 위에 겹치는 UI가 표시 영역 단위에 영향을 주지 않을 수 있다고 밝힌다. 따라서 주소창 문제의 수정과 키보드 및 safe area 검사는 분리해야 한다.

## 수정 범위와 확인 방법

- 모든 정상 route가 자체 프레임을 가지므로 전역 `body`의 `100vh` 최소 높이 필요성을 제거하고, `NotesWorkspaceFrame`과 `TaskPageFrame`의 `100dvh` 및 내부 스크롤을 유지한다. 문서 전체에 `overflow: hidden`을 추가해 증상을 가리지 않는다.
- 보조 화면의 본문 네 곳에서는 탐색 높이를 다시 더하는 `min-h-screen`을 제거하고, `DocumentPageFrame`이 정한 최소 높이와 콘텐츠 길이에 따른 자연스러운 문서 스크롤을 사용한다. 접속 주소 확인 및 오류 상태는 별도로 현재 보이는 높이에 맞춘다. 새 프레임이나 JavaScript 높이 계산은 필요하지 않다.
- 기존 브라우저 검사에서 메모 목록, 수집, 상세, 일괄 복사 확인과 관리의 동작을 실제로 실행한다. 버튼이 보이는 화면 아래쪽에 남는지, 긴 본문 또는 목록만 스크롤되는지, 짧은 보조 화면에 탐색 높이만큼의 빈 스크롤이 없는지 확인한다. CSS class나 프레임의 DOM 중첩 대신 사용자에게 보이는 위치와 동작을 판정한다.
- 실제 Android 브라우저에서는 주소창을 펼치고 접은 상태의 문서 스크롤 높이, 보이는 화면 높이와 하단 동작 위치를 비교한다. 화면 키보드, safe area, 짧은 내용과 긴 내용도 별도로 확인한다. 고정 크기의 데스크톱 브라우저 흉내 내기는 주소창 변화의 완료 증거가 아니다.

## 이번 조사와 이전 조사

[이전 모바일 표시 영역 조사](mobile-viewport-controls-research.md)는 당시 `ApplicationFrame`의 Grid 자동 배치 때문에 프레임 내부 콘텐츠가 짧아졌다고 기록했다. 지금은 화면 목적별 프레임을 사용하며, 현재 조사에서 찾은 `body`와 프레임 사이의 높이 차이는 별개의 원인이다. 이전 조사의 실행 수치를 현재 프레임의 재현 수치로 사용하지 않는다.

메모 상세 외 화면의 사용자 제보는 일괄 복사 확인까지이며, 나머지 화면의 영향은 코드에서 도출한 가능성이다. 현재 조사에서는 Android 기기의 계산된 높이와 스크롤 범위를 직접 계측하지 않았다. 계측 결과가 높이 충돌과 맞지 않거나 수정 뒤에도 문서 전체가 움직이면, 특정 본문 요소의 최소 크기와 브라우저의 키보드 처리부터 다시 추적해야 한다.
