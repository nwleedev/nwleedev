# 상용 수준의 조작 경험을 위한 조사

## 결론

개인 메모 애플리케이션의 상용 수준 UX는 장식이나 기능 수가 아니라 입력 직후의 반응, 예측 가능한 결과, 작업 맥락 유지와 실패 복구로 판단한다. 복사와 저장처럼 자주 쓰는 동작은 즉시 결과를 보여주고, 재정렬과 삭제처럼 되돌릴 수 있는 동작은 화면을 먼저 갱신한 뒤 저장 실패에서 정확한 이전 상태로 돌아갈 수 있어야 한다. 사용자가 읽고 행동해야 하는 오류는 자동으로 사라지는 토스트에만 두지 않는다.

이번 조사에서 유지할 기능은 자유 배치, 넓은 화면 자동 저장, 좁은 화면 상세 편집과 명시적 저장, 개별 복사, 일괄 복사, 삭제 취소, 속성 조정, 사용 기록, 분석, 템플릿과 설정이다. 변경할 부분은 드래그 시작 영역, 재정렬 피드백, 알림 배치와 수명, 오류 표시 위치, 모바일 관리 동작의 표현이다. 저장 자료 형식과 기능 범위는 바꾸지 않는다.

## 조사 범위와 현재 조건

2026년 9월 22일에 제안서, 요구사항, 계획, `apps/notes/DESIGN.md`와 현재 화면 구현을 함께 확인했다. 설치된 주요 버전은 Next.js 16.3.3, React 19.2.8, React Hook Form 7.86, Zod 4.4, Vitest 4.1.11과 Playwright 1.62.1이다. 이번 문서 작업은 새로운 외부 의존성을 선택하지 않는다.

현재 구현에서 다음 차이를 확인했다.

- `ActionToast`는 성공과 오류를 구분하지 않고 닫기 버튼과 5초 타이머를 사용하며, hover 및 `focus-within`에서 시간을 멈추지 않는다.
- 메모 화면은 일반 알림을 오른쪽 위에, 삭제 취소를 중앙 아래에 표시해 서로 다른 알림 영역을 만든다.
- 모바일 일괄 복사 항목은 항목 전체에서 길게 누르기 재정렬을 시작한다. 저장 목록과 모바일 확인 화면에는 위치 선택 상태에서 영구 삽입선과 `이 위치로 이동` 문구가 나타난다.
- 모바일 메모의 500ms 길게 누르기와 10 CSS px 이동 한계, 길게 누른 뒤 상세 이동 억제는 이미 구현되어 있으나 실제 touch 입력 순서로 다시 확인해야 한다.
- 좁은 화면 상세 편집은 저장 버튼과 이탈 확인을 제공하지만 성공을 토스트로 알린다. 넓은 화면 자동 저장 실패도 다른 일시 알림과 같은 영역을 사용한다.

## 조사에서 도출한 적용 규칙

### 동작은 시작, 진행, 완료와 복구 상태를 가져야 한다

화면은 입력이 시작됐는지, 현재 어디에 놓을 수 있는지, 사용자가 손을 뗀 뒤 무엇이 바뀌었는지를 같은 순서로 설명해야 한다. 재정렬은 `대기 → 누름 → 드래그 → 저장 중 → 완료 또는 복구` 상태로 다룬다. 유효한 놓기 위치에서만 삽입선을 보여주고, 놓는 즉시 화면 순서를 바꾼다. 저장 실패에서는 드래그 시작 전의 항목 순서, 선택과 포커스를 복원하고 다시 시도할 동작을 제공한다.

[Atlassian Drag and Drop 디자인 지침](https://atlassian.design/components/pragmatic-drag-and-drop/design-guidelines)은 항목에 다른 조작 요소가 있으면 이동 핸들만 드래그 시작점으로 쓰고, 상대 위치를 보여줄 때 놓기 표시를 사용하며, 놓은 뒤 화면을 즉시 갱신하도록 안내한다. [Apple Drag and Drop 지침](https://developer.apple.com/design/human-interface-guidelines/drag-and-drop)은 이동 대상을 계속 식별할 수 있는 피드백, 예상 가능한 이동 및 복사 결과와 되돌리기 수단을 권한다. 따라서 회전이나 넓은 accent 채우기보다 raised 깊이, 원래 자리의 변화와 삽입선을 사용한다.

목록 가장자리에서 목표 위치가 화면 밖으로 나가면 현재 스크롤 영역만 자동으로 이동시킨다. 포인터가 유효한 목록 밖에 있거나 `pointercancel`, 완료 전 `lostpointercapture`가 발생하면 순서를 바꾸지 않는다. 모바일에서는 왼쪽 이동 핸들에서 500ms 동안 10 CSS px 안에 머문 경우에만 드래그를 시작하며, 본문 누르기는 세로 스크롤과 텍스트 읽기를 유지한다.

### 드래그와 제스처는 유일한 실행 방법이 아니다

[WCAG 2.2 Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements)은 드래그로 완성하는 기능에 드래그가 필요 없는 단일 포인터 방법도 제공하도록 요구한다. [Atlassian 접근성 지침](https://atlassian.design/components/pragmatic-drag-and-drop/accessibility-guidelines)은 더보기에서 같은 이동 결과를 선택하고, 완료 뒤 원래 실행 지점에 포커스를 유지하며, 이동한 항목과 이전 및 새 위치를 live region으로 알리는 흐름을 제시한다.

따라서 복사 아이콘과 이동 핸들은 항상 발견할 수 있게 두고, `Command+클릭`, 길게 누르기와 드래그는 빠른 입력으로만 사용한다. 일괄 복사 항목의 더보기는 드래그와 같은 삽입식 위치 이동을 제공한다. 이동 뒤 같은 항목의 실행 버튼에 포커스를 유지하고, 항목 이름과 새 순서를 정중한 상태 메시지로 전달한다.

### 피드백 표면은 사용자가 해야 할 다음 행동으로 고른다

[Fluent 2 Toast 지침](https://fluent2.microsoft.design/components/web/react/core/toast/usage)은 토스트를 중요하지 않은 일시 정보에 사용하고, 반드시 처리해야 하는 내용에는 message bar나 dialog 같은 지속 표면을 사용하도록 안내한다. 동작 없는 토스트는 일정 시간이 지나면 닫을 수 있지만 hover에서 타이머를 멈추며, 다시 찾을 수 없는 정보에 닫기 버튼을 두지 않는다. [WCAG 2.2 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages)는 포커스를 옮기지 않고도 보조 기술이 결과를 알 수 있어야 한다고 설명한다.

개인 메모에서는 다음 기준을 적용한다.

| 상황 | 표시 방식 | 수명과 포커스 |
| --- | --- | --- |
| 복사 성공 | 공유 알림 영역의 `복사됨` | 짧게 표시, 닫기 버튼 없음, 포커스 유지 |
| 실행 취소 가능한 삭제 | 공유 알림 영역의 `메모를 삭제했습니다.`와 `실행 취소` | 5초, hover와 `focus-within`에서 일시 정지, 한 건만 표시 |
| 다시 시도할 수 있는 일시 실패 | 공유 알림 영역의 오류와 `다시 시도` | 조작하는 동안 사라지지 않으며 포커스 유지 |
| 화면 자료 불러오기 또는 저장 실패 | 실패한 내용 가까이의 지속 상태와 `다시 시도` | 성공하거나 사용자가 화면을 떠날 때까지 유지 |
| 저장하지 않은 변경으로 이동 | modal dialog | 선택할 때까지 유지, dialog 안에서 포커스 관리 |
| 자동 저장 성공 | 표시하지 않음 | 입력 흐름 유지 |
| 좁은 화면의 명시적 저장 성공 | 저장 버튼의 짧은 상태 변화 | 별도 토스트 없음 |

알림은 화면마다 하나의 예측 가능한 영역과 현재 메시지 한 건만 사용한다. 새 메시지는 이전 메시지를 바꾸고 수명을 다시 센다. 화면의 핵심 본문과 고정 실행 제어를 가리지 않는 위치는 대표 너비에서 확인한 뒤 토큰과 layout으로 확정한다. 오류 원문이 길거나 다시 확인해야 하면 토스트 본문에 모두 넣지 않고 해당 작업 가까이의 지속 상태로 옮긴다.

### 선택을 강제할 때만 dialog를 사용한다

[WAI-ARIA APG Modal Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)은 modal dialog가 바깥 내용을 실제로 조작할 수 없게 하고, 포커스를 dialog 안으로 옮겨 순환시키며, 닫은 뒤 실행 지점 또는 다음 흐름의 논리적 위치로 돌려보내야 한다고 설명한다. 이 규칙은 좁은 화면 상세 편집의 저장하지 않은 변경 이탈 확인에 적용한다. 복사 성공, 자동 저장 성공과 되돌릴 수 있는 삭제에는 dialog를 사용하지 않는다.

### 관리 동작은 화면 크기와 조작 횟수에 맞춘다

[Apple Context Menus 지침](https://developer.apple.com/design/human-interface-guidelines/context-menus)은 핵심 명령을 숨은 메뉴에만 두지 않고, 짧고 관련 있는 보조 명령만 제공하며, 위험 동작을 마지막에 배치하도록 안내한다. 넓은 화면에서는 실행 버튼 가까이의 backdrop 없는 동작 선택창이 적합하다. 모바일에서는 위치 변경, 복제와 삭제처럼 여러 행을 눌러야 하므로 pointer용 선택창을 그대로 줄이지 않고 touch 조작 영역을 확보한 action sheet 방향을 우선한다.

모바일 관리 표면의 정확한 높이, 닫기 제스처와 위치 이동 단계는 아직 승인되지 않았다. U17에서 대표 항목 수, 320 CSS px, 화면 키보드와 safe area를 함께 비교한 뒤 결정해야 한다. 결정 전에도 더보기의 기능, 항목 이름을 포함한 접근 가능한 이름, `Escape` 및 바깥 누르기, 실행 뒤 포커스 복원은 유지한다.

## 구현 순서에 미치는 영향

1. 공통 알림 영역과 성공, 실행 취소, 일시 실패 및 지속 오류의 사용 기준을 먼저 만든다. 화면마다 별도 위치와 수명 규칙을 만들지 않는다.
2. 좁은 화면 메모에서 복사 아이콘, 길게 누르기, 상세 이동과 명시적 저장의 한 입력 한 결과를 확인한다.
3. 넓은 메모와 일괄 복사 항목을 명시적인 이동 핸들로 바꾸고 드래그 수명, 자동 스크롤, 즉시 반영과 실패 복구를 연결한다.
4. 보조 화면의 불러오기 및 제출 오류를 지속 상태로 옮기고, 마지막 통합 검사에서 피드백 표면과 포커스 복원을 route 전체에서 대조한다.

새로운 드래그, toast 또는 dialog 의존성은 이번 결정으로 추가하지 않는다. 현재 Pointer Events, HTML popover 및 dialog와 자체 `shared/ui`로 요구 결과를 만들 수 있는지 먼저 확인한다. 플랫폼 한계가 실제 브라우저 검사에서 확인되면 의존성과 전이 의존성, 공식 권장 통합 방식 및 현재 구현을 다시 비교한 뒤 별도 승인을 받는다.

## 완료를 판단할 관찰 결과

- 같은 pointer 입력이 복사와 상세 이동, 드래그와 항목 실행, 메모 이동과 캔버스 이동을 함께 실행하지 않는다.
- 재정렬 직후 새 순서가 보이고, 저장 실패를 만들면 이전 순서, 같은 항목의 선택과 포커스가 돌아오며 다시 시도할 수 있다.
- 이동 핸들, 더보기의 위치 변경과 키보드 조작이 같은 삽입 결과를 만든다. 보조 기술은 이동한 항목과 새 위치를 한 번 전달받는다.
- 현재 알림은 한 영역의 한 건뿐이며 새 결과가 수명을 다시 시작한다. 동작이 있는 알림은 hover와 `focus-within`에서 시간이 멈춘다.
- 자동 저장 성공은 편집을 방해하지 않는다. 자동 저장 실패는 입력과 초안을 보존한 지속 상태로 남고, 좁은 화면의 저장 버튼은 진행, 성공과 실패를 구분한다.
- `prefers-reduced-motion`에서는 상태 이해에 필요하지 않은 전환을 제거해도 시작, 놓기, 완료와 복구를 구분할 수 있다.

## 남은 결정

- 좁은 화면 일괄 복사 항목의 관리 표면은 action sheet 방향만 승인됐고 세부 배치와 닫기 방식은 아직 정하지 않았다.
- 좁은 화면 전역 탐색 방식은 기존 결정과 같이 미정이다.
- 공유 알림 영역의 정확한 화면 좌표는 핵심 본문, 오른쪽 패널, 하단 실행 제어와 safe area가 겹치지 않는 대표 화면 검토에서 확정한다.
