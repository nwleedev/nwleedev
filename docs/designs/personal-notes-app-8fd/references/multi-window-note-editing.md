# 여러 창에서 같은 메모를 편집할 때의 저장과 복구

두 창이 같은 메모를 열었을 때 먼저 구별할 것은 사용자가 바꾼 값이다. 한 창은 본문을 고치고 다른 창은 카드만 옮겼다면 두 변경을 함께 보존할 수 있다. 두 창이 본문을 서로 다르게 고쳤다면 어느 값을 저장하고 다른 입력을 어떻게 돌려줄지 결정해야 한다. 저장에 실패한 창을 닫은 뒤에도 그 입력을 복구할지는 별개의 문제다.

사용성 측면에서는 두 변경을 함께 보존할 수 있는 일은 조용히 처리하고, 서로 다른 두 본문 중 하나를 선택해야 할 때만 편집기에서 차이를 보여주는 방식을 제안한다. 저장 실패 후에는 현재 입력을 들고 다시 시도할 수 있어야 한다. 다음에 열었을 때도 복구할 수 있다는 안내는 실제로 보관한 입력에 한해 제공한다.

2026년 11월 6일 기준 커밋 `4bb081c`의 IndexedDB 버전 4를 대상으로 한다. 아래 사례는 같은 브라우저 프로필로 같은 사이트를 연 두 화면에서 가능한 쓰기 순서를 코드로 추적한 것이다. 실제 브라우저에서 발생 빈도나 재현 여부는 확인하지 않았다. [여러 탭과 창의 요구사항](../requirements.md#여러-탭과-창에서-메모-사용)

## 같은 본문을 두 번 편집한 경우

두 창에서 원문 `10시`를 연다. A가 `11시`를 저장한 뒤 B가 이전 화면에서 입력한 `12시`를 자동 저장한다. 현재 앱은 각 창이 보관한 메모로 새 레코드를 만든다. 저장소는 같은 ID가 있는지 확인하고 전달받은 레코드 전체를 쓴다. 두 편집이 같은 본문 버전에서 시작하면 양쪽 모두 같은 다음 버전 번호를 만들 수 있다. 이 순서대로 저장에 성공하면 다시 열었을 때 보이는 값은 `12시`다. [본문 저장](../../../../apps/notes/src/_pages/notes/model/save-note-content.ts) / [버전 계산](../../../../apps/notes/src/entities/note/model/note.ts) / [메모 저장소](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)

IndexedDB는 같은 저장소에서 겹치는 쓰기 트랜잭션의 실행 순서를 조정한다. 두 번째 쓰기가 시작되기 전에 B의 화면에 이미 담겨 있던 본문까지 최신 값으로 바꾸지는 않는다. 두 번째 쓰기에서 같은 키에 `put`하면 해당 레코드가 교체된다. [IndexedDB 트랜잭션 실행 규칙](https://www.w3.org/TR/IndexedDB-3/#transaction-scheduling) / [MDN의 put 동작](https://developer.mozilla.org/en-US/docs/Web/API/IDBObjectStore/put)

**미결 사항.** 먼저 저장한 값을 유지하고 B가 선택하게 할지, 나중 값을 적용하고 대체 사실을 알릴지 정해야 한다. 두 화면에서 똑같이 `11시`를 입력한 경우에도 안내할지, 변경을 편집 중인 다른 창에 언제 표시할지도 미정이다. 정책을 비교할 때는 다시 연 메모의 본문, 두 편집 화면에 남은 입력, 각 화면에 표시한 저장 상태를 함께 확인한다.

## 한 창의 초안 정리와 다른 창의 저장 실패가 겹친 경우

현재 자동 저장은 초안 기록, 본문 저장, 초안 삭제 순으로 진행된다. 초안을 읽을 때는 메모 ID와 본문 버전을 확인하지만 삭제 요청에는 메모 ID만 사용한다. 다음 순서에서는 두 창에서 서로 다른 작업이 성공해도 복구할 자료를 잃을 수 있다. [자동 저장 순서](../../../../apps/notes/src/_pages/notes/model/save-note-content.ts) / [초안 조회와 삭제](../../../../apps/notes/src/entities/note/api/indexed-db-note-draft-repository.ts) / [MDN의 키를 이용한 삭제](https://developer.mozilla.org/en-US/docs/Web/API/IDBObjectStore/delete)

1. A가 본문 저장을 마치고 자신의 초안을 지우기 전에 B가 같은 메모에 새 초안을 기록한다.
2. B의 본문 저장이 실패한다. B 화면에는 아직 입력이 남아 있다.
3. A가 메모 ID로 초안을 지운다. 삭제 시점에 그 키에 들어 있는 값은 B의 초안이다.

기존 요구는 저장이 실패한 열린 화면에서 입력과 재시도 기회를 유지하는 것이다. 먼저 저장한 본문은 초안 정리에 실패해도 보존해야 한다. **미결 사항은 B를 새로고침하거나 닫았다가 다시 열었을 때 어느 입력까지 복구할지**다. 두 창의 미저장 입력을 각각 복구해야 한다면 같은 메모에서 나온 두 입력을 구별할 근거가 필요하다. 초안 개수와 저장 형식은 이 사례만으로 정할 수 없다. [초안 정리 재시도 결정](../decisions/note-draft-cleanup-retry.md)

## 본문 충돌과 분리해서 확인할 사례

- **서로 다른 메모.** A와 B가 각각 새 메모를 만들거나 서로 다른 메모를 수정한 뒤 다시 열면 양쪽 변경이 모두 남아야 한다. 기존 요구사항에 명시된 비교 기준이다. [여러 탭과 창의 요구사항](../requirements.md#여러-탭과-창에서-메모-사용)
- **본문과 위치.** A가 본문을 저장한 뒤 B가 같은 카드의 위치만 옮긴다. 현재 B는 이전 본문이 든 레코드 전체를 저장할 수 있다. 다시 열어서 본문과 위치를 각각 확인하면 두 변경 중 어느 쪽이 사라졌는지 알 수 있다. [화면의 위치 변경](../../../../apps/notes/src/_pages/notes/model/use-notes-data-model.ts) / [메모 저장소](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)
- **삭제와 겹침 순서.** A가 메모를 삭제한 뒤 B가 이전 화면에서 다른 카드를 맨 앞으로 보낸다. B의 배열 전체를 저장하면 삭제한 메모가 다시 생길 수 있다. 다시 연 목록에서 해당 ID가 보이는지 확인한다. 삭제된 메모에 B의 미저장 본문까지 있는 경우 그 입력을 어떻게 돌려줄지는 미정이다. [겹침 순서 변경과 일괄 저장](../../../../apps/notes/src/_pages/notes/model/use-notes-data-model.ts) / [일괄 저장 구현](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)

## 사용자가 편집을 계속할 수 있는 방식

다음은 같은 브라우저에서 메모를 작성하거나 복사하는 사람을 위한 설계 후보이다. 2026년 11월 6일에 확인한 서비스 안내와 이 앱의 편집 동작을 비교했다. 아래 문구는 동작을 설명하는 예시다. 사용자 관찰 자료가 없어 발생 빈도는 알 수 없다. 우선순위는 원문을 잃을 가능성과 사용자가 직접 복구하는 데 드는 수고를 기준으로 판단했다.

### 다른 창에서 같은 본문을 수정했을 때

Joplin은 충돌한 로컬 메모를 별도 노트북에 복사하고 두 내용을 비교할 수 있게 한다. Dropbox는 충돌 사본을 파일로 남기고 이름으로 구별한다. 사본을 남기면 뒤늦게 필요한 문장을 꺼낼 수 있지만 사용자가 두 버전의 위치와 차이를 알아내야 한다. 실제로 Joplin 사용자가 충돌 노트북에서 메모를 발견하고도 어떻게 복구하는지 물은 사례가 있다. 이는 구버전의 개별 신고로, 현재 Joplin이나 이 앱에서 같은 문제가 얼마나 자주 생기는지는 알려주지 않는다. [Joplin 충돌 안내](https://joplinapp.org/help/apps/conflict/) / [Joplin 사용자 신고](https://github.com/laurent22/joplin/issues/4147) / [Dropbox 충돌 사본 안내](https://help.dropbox.com/organize/conflicted-copy)

이 앱에서는 사용자가 글을 쓰던 자리에서 비교를 시작하는 편이 적합하다. 두 창이 같은 값으로 끝났으면 저장된 본문과 일치하는지 확인한 뒤 평소 편집을 이어간다. 값이 다르면 입력칸에 내가 쓰던 글을 그대로 두고 근처에 “다른 창에서 이 메모를 수정했습니다”와 “두 내용 보기”를 표시하는 방식이다. 안내가 나타날 때 커서, 선택 영역과 한글 조합을 유지한다. 키 입력마다 같은 경고를 되풀이하지 않는다. 기존 모바일 편집기에는 상태를 읽어 주는 영역과 조합 시작 및 종료 처리가 있다. [편집 화면](../../../../apps/notes/src/_pages/notes/ui/note-detail-page.tsx) / [W3C 상태 메시지 해설](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

비교 화면은 “다른 창에 저장된 내용”과 “이 창에서 작성한 내용”으로 구분한다. 모바일에서는 두 본문을 위아래로 읽고 필요한 부분을 선택할 수 있게 한다. 예를 들어 “오후 **11시**”와 “오후 **12시**”의 차이를 색 없이도 읽을 수 있어야 한다. 비교를 닫으면 원래 입력 위치로 돌아오고 어느 쪽도 버리지 않는다. 적용하려는 순간 다른 창에서 또 수정했다면 새 내용을 다시 비교한다. 마지막 입력을 곧바로 적용하는 방식은 선택을 한 번 줄이지만 먼저 저장한 문장을 잃을 수 있다. 별도 사본을 남기는 방식은 나중에 판단할 수 있지만 사본을 다시 찾고 정리해야 한다. 기본 동작과 사본 보관 기간은 미정이다.

### 저장 실패와 복구 초안 정리가 겹칠 때

사용자가 먼저 알아야 하는 것은 지금 보이는 문장을 다시 입력해야 하는지 여부다. 본문 저장이 실패했다면 입력과 선택 영역을 유지하고 편집기 옆에 “저장하지 못했습니다”와 “다시 시도”를 남긴다. 실패가 반복돼도 계속 편집하거나 텍스트를 선택해 복사할 수 있게 한다. 반대로 본문은 저장됐고 사용이 끝난 초안 삭제만 실패했다면 사용자에게 같은 본문을 재입력시키지 않고 정리만 다시 시도한다. 다른 창의 입력이 그사이에 생겼다면 정리 대상에서 제외해야 한다. [기존 실패 복구 결정](../decisions/note-draft-cleanup-retry.md) / [현재 실패 표시와 재시도 버튼](../../../../apps/notes/src/_pages/notes/ui/note-detail-page.tsx)

복구용 사본의 저장까지 실패했다면 “이 창을 나가면 입력을 잃을 수 있습니다”라고 안내할 수 있다. 앱 안에서 나가려 할 때는 편집을 계속할지 선택하게 한다. 모바일에서 브라우저를 강제 종료하면 이탈 이벤트 자체가 오지 않을 수 있어 종료 직전 경고만으로 복구를 약속할 수 없다. 재실행 시 복구를 제공하기로 한다면 원래 메모를 열었을 때 저장된 본문과 복구 가능한 입력을 구별해 보여주고, 사용자가 고르기 전까지 어느 쪽도 덮어쓰지 않는 방안을 비교한다. [MDN의 모바일 이탈 이벤트 제약](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)

### 새 메모, 카드 이동, 삭제가 다른 창에 반영될 때

- **서로 다른 메모 작성.** 목록으로 돌아오면 두 창의 메모가 모두 보여야 한다. 내가 보고 있던 메모와 스크롤 위치를 유지할 수 있다면 다른 메모의 추가를 매번 알릴 필요가 없다. 내 창에서 직접 새 메모를 만든 경우에는 기존 요구대로 새 메모가 바로 보여야 한다. [모바일 목록 요구사항](../requirements.md#모바일-메모-목록의-순서)
- **본문과 위치를 각각 변경.** 한 창에서 시간을 고치고 다른 창에서는 카드만 옮겼다면, 다음에 카드를 누를 때 새 위치에서 수정한 시간을 복사할 수 있어야 한다. 두 값을 함께 남길 수 있는데 사용자에게 어느 변경을 버릴지 묻는 창을 띄우면 불필요한 판단이 된다. 드래그 도중 외부 갱신이 도착해도 카드가 손가락 아래에서 튀지 않도록 놓거나 취소한 뒤 배치를 반영하는 방안을 제안한다. [메모 저장과 일괄 저장](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)
- **삭제와 겹침 순서 변경.** 다른 카드가 삭제됐다면 현재 선택과 키보드 포커스를 유지하고 삭제된 카드만 목록에서 제외한다. 지금 편집하던 카드가 삭제된 경우에는 입력 유무에 따라 처리한다. 미저장 입력이 없다면 짧게 이유를 알리고 인접한 카드나 목록 제목으로 포커스를 옮긴다. 입력이 있다면 “다른 창에서 이 메모를 삭제했습니다”를 편집기 옆에 표시하고 글을 복사하거나 새 메모로 보관하는 선택지를 검토한다. 새 메모로 보관할 경우 저장 성공 뒤에만 편집기를 떠나야 하며, 원래 메모의 삭제 취소와는 별개의 동작이다. [삭제 복원 요구사항](../requirements.md#고정-높이-바텀-시트와-삭제)
- **오래 열어 둔 창으로 복귀.** 첫 후보는 창에 돌아올 때 최신 메모를 확인하는 방식이다. 읽기 중인 메모는 최신 내용으로 갱신하되, 작성 중이면 화면의 입력과 저장된 본문을 먼저 비교한다. 계속 열려 있는 두 창에 즉시 반영하면 최신 상태를 빨리 볼 수 있는 대신 한글 입력, 드래그, 선택 중인 텍스트를 방해할 기회도 늘어난다. 어느 방식을 택하든 저장 직전에 최신 값을 확인해야 창을 전환하지 않고 나란히 사용하는 경우도 처리할 수 있다. [IndexedDB 트랜잭션 실행 규칙](https://www.w3.org/TR/IndexedDB-3/#transaction-scheduling)

## 사용성 확인 과업

컴퓨터에서는 같은 프로필의 두 창을 나란히 두고, 모바일에서는 두 탭을 오가며 확인한다. 아래는 검증할 과업이며 실행 결과는 아직 없다.

1. 다른 창에서 바꾼 시간을 확인하면서 내가 쓰던 문장을 이어 쓴다. 어느 값이 저장됐는지 설명할 수 있는지, 비교를 보류해도 입력과 커서가 남는지 관찰한다. 모바일에서는 한글 조합 도중 알림이 올 때와 키보드로 비교를 닫고 본문으로 돌아갈 때도 확인한다.
2. 저장이 실패한 메모에서 한 줄을 더 쓰고 다시 시도한다. 재입력 없이 마지막 문장까지 다시 열 수 있는지 확인한다. 저장 실패와 초안 정리 실패를 따로 일으켜 사용자가 이미 저장된 본문을 또 저장해야 한다고 오해하는지도 본다. 종료 후 복구를 제안하는 안은 실제로 남은 사본과 화면의 안내가 일치해야 한다.
3. A에서 시간을 수정하고 B에서 카드 위치를 바꾼 뒤 그 카드를 복사한다. 올바른 시간이 복사되고 위치가 유지되는지 확인한다. 이어 A에서 카드를 삭제하고 B에서 다른 카드의 겹침 순서를 바꿔 삭제된 카드가 다시 나타나는지 살핀다. B에서 삭제된 카드를 편집 중이었다면 글을 잃지 않고 다음 행동을 찾을 수 있는지도 확인한다.

독립적인 변경을 함께 보존하는 동작과 입력을 방해하지 않는 상태 표시는 별도로 검토할 수 있다. 같은 본문을 두 번 편집한 뒤의 최종 선택과 창을 닫은 뒤 복구할 입력의 범위는 위 과업으로 비교할 대상이다. 이 두 선택이 정해져야 보관할 자료와 삭제 시점을 결정할 수 있다.
