# 여러 창에서 같은 메모를 편집할 때의 저장과 복구

메모별 기준 본문과 별도로 편집한 부분을 저장하면 두 창의 입력을 자동으로 합칠 수 있다. 메모 전체의 삭제에는 목록에서 메모가 사라지는 시점과 삭제 취소로 돌아오는 본문을 함께 정해야 한다. [여러 탭과 창의 요구사항](../requirements.md#여러-탭과-창에서-메모-사용)

## 변경분 저장소 이름

`noteTextEdits`를 권한다. 메모 본문을 편집해 저장한 변경분이라는 뜻이 드러나고, 모바일 목록 순서나 카드 배치 변경과 구별된다. 한 건은 메모 ID, 같은 쓰기를 다시 식별할 변경 ID, 하나 이상의 편집을 담은 CRDT 바이너리로 구성할 수 있다. 입력 횟수와 레코드 수를 일치시킬 필요는 없다.

- `noteContentChanges`는 현재 메모 모델의 `content`와 맞아 코드를 따라가기 쉽다. 본문이 일반 텍스트인 지금은 `Text`가 저장 대상을 더 구체적으로 알려준다.
- `noteTextChanges`는 삽입과 삭제를 모두 포함하며 병합한 변경분도 자연스럽게 부를 수 있다. `noteEdits`는 짧지만 위치와 크기 편집도 들어갈 것처럼 읽힌다.
- `noteUpdates`의 `update`는 Yjs가 직렬화한 변경분에 쓰는 용어다. 저장소 이름만 보면 메모의 어느 부분을 담는지 알기 어렵다. `history`나 `drafts`도 피한다. 저장된 변경분은 원문 복원에 쓰이고 기준 본문에 합친 뒤 제거할 수 있다. [Yjs 문서 변경분](https://docs.yjs.dev/api/document-updates)

현재 사용 횟수 인덱스는 메모 ID, 본문 리비전, 복사 당시 원문을 함께 사용한다. 예를 들어 원문을 ‘우유 → 빵 → 우유’로 고치면 두 시점의 ‘우유’가 구별된다. 리비전 칼럼을 제거할 때 이들을 원문만으로 합산하면 기존 기록의 구분이 사라진다. 이전 시점의 복사 횟수와 원문을 보존할 이전 방법을 확인해야 한다. [현재 사용 기록 인덱스](../../../../apps/notes/src/_app/composition/indexed-db/open-personal-notes-database.ts)

## 삭제와 본문 편집이 겹칠 때

**삭제와 수정에도 CRDT를 적용할 수 있다.** 다만 텍스트 CRDT 안에서 몇 글자를 지우는 것과 목록에서 메모 하나를 제거하는 것은 다른 연산이다. 후자는 어떤 메모가 목록에 속하는지 나타내는 자료에 규칙을 둬야 한다. 두 사람이 서로의 조작을 보기 전에 각각 수정과 삭제를 끝냈다면, 전달 순서를 바꿔도 각 창의 목록과 본문은 같은 결과에 도달해야 한다. [Preguiça 외의 CRDT 집합 연산 설명](https://arxiv.org/pdf/1805.06358)

예를 들어 A가 장보기 메모를 지우는 동안 B가 그 메모에 ‘우유’를 추가한다.

- **삭제 우선 후보.** 두 창의 목록에서 메모가 사라진다. B의 늦은 본문 저장은 목록에 메모를 다시 추가하지 않는다. B가 여전히 글을 쓰고 있다면 열린 편집기에서 자신의 입력을 복사할 기회를 주는 방안을 권한다. A의 삭제를 존중하면서 B의 입력을 갑자기 지우지 않을 수 있다.
- **편집 우선 후보.** 동시에 들어온 편집을 메모를 유지하려는 동작으로 정의하면 두 창에서 ‘우유’가 포함된 메모가 보인다. B의 입력은 자연스럽게 남지만 A는 삭제한 메모가 다시 나타나는 경험을 한다. 중첩된 값을 편집하는 동안 상위 항목을 삭제하는 문제를 실제로 다룬 예가 있다. 이 논문의 규칙을 메모 앱에 그대로 적용해야 하는 것은 아니다. [Kleppmann과 Beresford의 JSON CRDT](https://www.cl.cam.ac.uk/~arb33/papers/KleppmannBeresford-CRDT-JSON-TPDS2017.pdf)

**삭제 우선과 삭제 취소.** 메모의 표시 여부를 본문과 별도로 다루면 평범한 본문 편집에는 복원 권한을 주지 않아도 된다. 삭제를 본 뒤 사용자가 명시적으로 취소하면 같은 ID로 메모를 다시 표시한다. 그때 ‘우유’까지 복원하려면 숨겨 둔 본문에도 적용 가능한 변경분을 보존해야 한다. 삭제 당시 본문만 복원하려면 복원 전에 예약된 쓰기와 복원한 메모의 새 편집을 구별해야 한다. 이 경우 메모 ID가 존재하는지만 검사하면 늦게 도착한 옛 쓰기가 통과한다.

같은 프로필의 탭들이 하나의 IndexedDB를 공유하는 동안에는 편집 기록과 삭제 상태를 같은 읽기/쓰기 트랜잭션에서 확인하는 방법도 가능하다. 독립적으로 삭제 상태를 복제하는 CRDT를 택한다면 삭제 사실이나 그와 동등한 인과 정보를 보존해야 한다. 레코드를 물리적으로 지우는 것만으로는 오래된 복제본의 재등장을 막을 수 없다. 삭제 우선 여부, 복원할 본문과 삭제 정보를 정리할 시점은 함께 결정한다. [IndexedDB 트랜잭션 규칙](https://www.w3.org/TR/IndexedDB-3/#transaction-scheduling)

**확인할 사례.** A의 삭제와 B의 편집을 양쪽 순서로 전달한 뒤 새 창에서도 목록이 일치하는지 본다. 이어 A에서 삭제를 취소한 직후 B의 오래된 재시도를 전달한다. 복원된 본문이 선택한 정책과 일치하고 같은 글자가 두 번 나타나지 않아야 한다. 현재 삭제는 메모 revision을 검사하므로 이 사례는 새 구조의 검증 대상으로 남는다. [현재 메모 삭제](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)

2026년 11월 6일 기준 커밋 `4bb081c`의 IndexedDB 버전 4를 대상으로 한다. 아래 사례는 같은 브라우저 프로필로 같은 사이트를 연 두 화면에서 가능한 쓰기 순서를 코드로 추적한 것이다. 실제 브라우저에서 발생 빈도나 재현 여부는 확인하지 않았다. [여러 탭과 창의 요구사항](../requirements.md#여러-탭과-창에서-메모-사용)

## 같은 본문을 두 번 편집한 경우

두 창에서 원문 `10시`를 연다. A가 `11시`를 저장한 뒤 B가 이전 화면에서 입력한 `12시`를 자동 저장한다. 현재 앱은 각 창이 보관한 메모로 새 레코드를 만든다. 저장소는 같은 ID가 있는지 확인하고 전달받은 레코드 전체를 쓴다. 두 편집이 같은 본문 버전에서 시작하면 양쪽 모두 같은 다음 버전 번호를 만들 수 있다. 이 순서대로 저장에 성공하면 다시 열었을 때 보이는 값은 `12시`다. [본문 저장](../../../../apps/notes/src/_pages/notes/model/save-note-content.ts) / [버전 계산](../../../../apps/notes/src/entities/note/model/note.ts) / [메모 저장소](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)

IndexedDB는 같은 저장소에서 겹치는 쓰기 트랜잭션의 실행 순서를 조정한다. 두 번째 쓰기가 시작되기 전에 B의 화면에 이미 담겨 있던 본문까지 최신 값으로 바꾸지는 않는다. 두 번째 쓰기에서 같은 키에 `put`하면 해당 레코드가 교체된다. [IndexedDB 트랜잭션 실행 규칙](https://www.w3.org/TR/IndexedDB-3/#transaction-scheduling) / [MDN의 put 동작](https://developer.mozilla.org/en-US/docs/Web/API/IDBObjectStore/put)

**레코드 전체를 쓰는 이전 방식의 선택지.** 먼저 저장한 값을 유지하고 B가 선택하게 할지, 나중 값을 적용하고 대체 사실을 알릴지 정해야 한다. 두 화면에서 똑같이 `11시`를 입력한 경우에도 안내할지, 변경을 편집 중인 다른 창에 언제 표시할지도 미정이다. 정책을 비교할 때는 다시 연 메모의 본문, 두 편집 화면에 남은 입력, 각 화면에 표시한 저장 상태를 함께 확인한다.

## 한 창의 초안 정리와 다른 창의 저장 실패가 겹친 경우

현재 자동 저장은 초안 기록, 본문 저장, 초안 삭제 순으로 진행된다. 초안을 읽을 때는 메모 ID와 본문 버전을 확인하지만 삭제 요청에는 메모 ID만 사용한다. 다음 순서에서는 두 창에서 서로 다른 작업이 성공해도 복구할 자료를 잃을 수 있다. [자동 저장 순서](../../../../apps/notes/src/_pages/notes/model/save-note-content.ts) / [초안 조회와 삭제](../../../../apps/notes/src/entities/note/api/indexed-db-note-draft-repository.ts) / [MDN의 키를 이용한 삭제](https://developer.mozilla.org/en-US/docs/Web/API/IDBObjectStore/delete)

1. A가 본문 저장을 마치고 자신의 초안을 지우기 전에 B가 같은 메모에 새 초안을 기록한다.
2. B의 본문 저장이 실패한다. B 화면에는 아직 입력이 남아 있다.
3. A가 메모 ID로 초안을 지운다. 삭제 시점에 그 키에 들어 있는 값은 B의 초안이다.

본문 저장에 실패하면 열린 화면의 입력을 유지하고 앱이 내부에서 재시도한다. 먼저 저장한 본문은 초안 정리에 실패해도 보존해야 한다. **미결 사항은 B를 새로고침하거나 닫았다가 다시 열었을 때 어느 입력까지 복구할지**다. 두 창의 미저장 입력을 각각 복구해야 한다면 같은 메모에서 나온 두 입력을 구별할 근거가 필요하다. 초안 개수와 저장 형식은 이 사례만으로 정할 수 없다. [초안 정리 재시도 결정](../decisions/note-draft-cleanup-retry.md)

## 본문 충돌과 분리해서 확인할 사례

- **서로 다른 메모.** A와 B가 각각 새 메모를 만들거나 서로 다른 메모를 수정한 뒤 다시 열면 양쪽 변경이 모두 남아야 한다. 기존 요구사항에 명시된 비교 기준이다. [여러 탭과 창의 요구사항](../requirements.md#여러-탭과-창에서-메모-사용)
- **본문과 위치.** A가 본문을 저장한 뒤 B가 같은 카드의 위치만 옮긴다. 현재 B는 이전 본문이 든 레코드 전체를 저장할 수 있다. 다시 열어서 본문과 위치를 각각 확인하면 두 변경 중 어느 쪽이 사라졌는지 알 수 있다. [화면의 위치 변경](../../../../apps/notes/src/_pages/notes/model/use-notes-data-model.ts) / [메모 저장소](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)
- **삭제와 겹침 순서.** A가 메모를 삭제한 뒤 B가 이전 화면에서 다른 카드를 맨 앞으로 보낸다. B의 배열 전체를 저장하면 삭제한 메모가 다시 생길 수 있다. 다시 연 목록에서 해당 ID가 보이는지 확인한다. 삭제된 메모에 B의 미저장 본문까지 있는 경우 그 입력을 어떻게 돌려줄지는 미정이다. [겹침 순서 변경과 일괄 저장](../../../../apps/notes/src/_pages/notes/model/use-notes-data-model.ts) / [일괄 저장 구현](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)

## 본문 전체를 비교하던 이전 제안

아래 사례는 본문 자동 병합을 선택하기 전의 비교안이다. 새 설계에서는 변경분을 자동 병합하고 모바일 목록은 날짜로 정렬하지 않는다.

아래는 같은 브라우저 프로필에서 같은 사이트를 연 경우의 설계 제안이다. [요구사항](../requirements.md#기능-변경에-따른-텍스트-카피)에 따라 사용자가 해야 할 일은 해당 메모에서 바로 실행할 수 있게 한다. 버튼 이름은 배치와 동작을 비교하기 위한 후보이다.

### 다른 창에서 같은 본문을 수정했을 때

Joplin은 충돌한 로컬 메모를 별도 노트북에 복사하고 두 내용을 비교할 수 있게 한다. Dropbox는 충돌 사본을 파일로 남기고 이름으로 구별한다. 사본을 남기면 뒤늦게 필요한 문장을 꺼낼 수 있지만 사용자가 두 버전의 위치와 차이를 알아내야 한다. 실제로 Joplin 사용자가 충돌 노트북에서 메모를 발견하고도 어떻게 복구하는지 물은 사례가 있다. 이는 구버전의 개별 신고로, 현재 Joplin이나 이 앱에서 같은 문제가 얼마나 자주 생기는지는 알려주지 않는다. [Joplin 충돌 안내](https://joplinapp.org/help/apps/conflict/) / [Joplin 사용자 신고](https://github.com/laurent22/joplin/issues/4147) / [Dropbox 충돌 사본 안내](https://help.dropbox.com/organize/conflicted-copy)

**비교가 필요한 때.** 이 창에서 본문을 고치지 않았다면 다른 창이 저장한 글을 반영한다. 양쪽에서 고쳐도 결과가 같으면 저장 여부를 확인한 뒤 평소처럼 편집한다. 같은 원문을 서로 다르게 고쳤을 때만 이 메모의 자동 덮어쓰기를 멈추고 현재 입력을 보존하면서 다음 조작을 제공한다.

- **데스크탑에서는 해당 카드에서 연다.** 카드 안의 본문 바로 아래에 `변경 비교` 버튼을 둔다. 입력 중에 창을 띄우거나 오른쪽 패널을 바꾸지 않는다. 누르면 두 본문을 나란히 읽을 수 있는 비교 창을 연다. 비교를 미뤄도 카드의 복사 버튼으로 지금 보이는 입력을 가져갈 수 있다.
- **모바일에서는 메모 수정 화면에서 연다.** 상단에는 현재 입력의 저장 상태를 표시하고 헤더 바로 아래에 `변경 비교` 버튼을 둔다. 손가락으로 누를 자리를 확보하면서 뒤로, 실행 취소와 다시 실행도 평소 자리에서 쓸 수 있다. 비교를 누르면 한 화면에서 두 본문을 위아래로 읽는다. 목록에서 본문을 누르는 조작은 계속 복사에 사용한다. 일괄 복사에 이미 담은 문장도 담을 때의 내용과 순서를 유지한다.
- **선택 결과를 본문 곁에서 확인한다.** 예를 들어 A가 약속 시간을 `11시`로 저장했고 B가 `12시`로 고쳤다면, B에게 `저장된 내용` 아래에 **11시**, `이 창의 입력` 아래에 **12시**를 보여준다. 각 제목과 본문을 짝지어 읽을 수 있게 하고 달라진 구절을 굵기나 밑줄로도 구별한다. 긴 메모는 달라진 문장과 앞뒤 문장을 먼저 보여주고 양쪽 원문 전체를 펼쳐 복사할 수 있게 한다. `저장된 내용 사용`을 누르면 편집기에 11시가 남고, `이 창의 입력으로 저장`을 누르면 저장 성공 뒤에 12시가 남는다.
- **닫기와 적용을 구분한다.** 비교를 닫거나 뒤로 가면 어느 쪽도 적용하지 않고 원래 메모에서 편집을 이어간다. 다시 열 때는 그동안 이 창에서 더 쓴 글도 포함한다. 적용 직전에 저장된 쪽이 또 바뀌었으면 이 창의 입력을 남긴 채 최신 본문으로 비교를 갱신한다. 선택한 본문을 쓰는 중에 저장만 실패하면 앱이 내부에서 재시도한다. 그사이에 다른 창에서 본문을 바꿨다면 다시 비교한다.

변경을 감지한 순간에는 커서, 선택 영역과 한글 조합을 유지한다. 화면 읽기 도구에는 상태가 바뀐 때 한 번 알린다. 사용자가 비교를 열면 두 본문의 제목부터 읽을 수 있게 하고, 키보드로 닫으면 비교 버튼으로 포커스를 돌린다. 쓸 때의 커서 위치는 편집기에 보존한다. [W3C 상태 메시지 해설](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) / [W3C 대화상자 키보드 동작](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

### 저장 실패와 복구 초안 정리가 겹칠 때

데스크탑과 모바일 모두 본문 저장 실패는 앱이 내부에서 처리한다. 사용자는 별도 안내나 버튼 없이 계속 쓰거나 복사할 수 있다. 예를 들어 첫 문장의 저장이 실패한 뒤 한 줄을 더 쓰면 앱은 두 줄을 함께 저장한다. 본문은 저장됐고 초안 삭제만 실패했다면 정리만 다시 시도한다. 그사이에 생긴 다른 창의 입력은 보존한다. [본문 자동 저장 실패 요구사항](../requirements.md#본문-자동-저장-실패) / [초안 정리 재시도 결정](../decisions/note-draft-cleanup-retry.md)

앱 안에서 미저장 입력을 둔 채 나가려 할 때는 기존 이탈 확인에서 편집을 계속하거나 나가기를 선택한다. 모바일에서 브라우저를 강제 종료하면 이탈 이벤트 자체가 오지 않을 수 있어 종료 직전 경고만으로 복구를 약속할 수 없다. 재실행 시 복구를 제공하기로 한다면 원래 메모를 열었을 때 저장된 본문과 복구 가능한 입력을 구별해 보여주고, 사용자가 고르기 전까지 어느 쪽도 덮어쓰지 않는 방안을 비교한다. [MDN의 모바일 이탈 이벤트 제약](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)

### 새 메모, 카드 이동, 삭제가 다른 창에 반영될 때

- **모바일 목록의 첫 자리.** 직접 순서를 정하기 전에는 최근 업데이트한 메모부터 보여준다. 어느 순서에서든 이 창에서 새로 만들면 목록 맨 위에서 바로 찾을 수 있고, 나머지 카드의 상대 순서는 유지한다. 다른 창에서 만든 메모도 맨 위에 두되 목록 중간을 읽던 사람의 스크롤 위치는 보고 있던 카드에 맞춘다. 핸들로 옮긴 순서는 다시 열어도 유지한다. 수동 정렬 뒤 기존 본문을 수정했을 때의 위치와 카드 배치만 바꿔도 업데이트 날짜가 바뀌어야 하는지는 미정이다. [모바일 목록 요구사항](../requirements.md#모바일-메모-목록의-순서)
- **두 창에서 같은 목록 정렬.** 드래그 중 다른 탭에서 순서가 바뀌면 놓을 때까지 손가락 아래 카드와 삽입선을 유지한다. 놓으려던 위치가 달라졌다면 최신 목록에서 옮기던 카드의 핸들로 포커스를 돌려 다시 놓을 수 있게 한다. 두 탭이 같은 카드를 서로 다른 위치에 놓았을 때의 최종 순서는 별도로 정한다.
- **본문과 위치를 각각 변경.** 한 창에서 시간을 고치고 다른 창에서는 카드만 옮겼다면, 다음에 카드를 누를 때 새 위치에서 수정한 시간을 복사할 수 있어야 한다. 두 값을 함께 남길 수 있는데 사용자에게 어느 변경을 버릴지 묻는 창을 띄우면 불필요한 판단이 된다. 드래그 도중 외부 갱신이 도착해도 카드가 손가락 아래에서 튀지 않도록 놓거나 취소한 뒤 배치를 반영하는 방안을 제안한다. [메모 저장과 일괄 저장](../../../../apps/notes/src/entities/note/api/indexed-db-note-repository.ts)
- **삭제와 겹침 순서 변경.** 다른 카드가 삭제됐다면 현재 선택과 키보드 포커스를 유지하고 삭제된 카드만 목록에서 제외한다. 지금 편집하던 카드가 삭제된 경우에는 입력 유무에 따라 처리한다. 미저장 입력이 없다면 짧게 이유를 알리고 인접한 카드나 목록 제목으로 포커스를 옮긴다. 입력이 있다면 “다른 창에서 이 메모를 삭제했습니다”를 편집기 옆에 표시하고 글을 복사하거나 새 메모로 보관하는 선택지를 검토한다. 새 메모로 보관할 경우 저장 성공 뒤에만 편집기를 떠나야 하며, 원래 메모의 삭제 취소와는 별개의 동작이다. [삭제 복원 요구사항](../requirements.md#고정-높이-바텀-시트와-삭제)
- **오래 열어 둔 창으로 복귀.** 첫 후보는 창에 돌아올 때 최신 메모를 확인하는 방식이다. 읽기 중인 메모는 최신 내용으로 갱신하되, 작성 중이면 화면의 입력과 저장된 본문을 먼저 비교한다. 계속 열려 있는 두 창에 즉시 반영하면 최신 상태를 빨리 볼 수 있는 대신 한글 입력, 드래그, 선택 중인 텍스트를 방해할 기회도 늘어난다. 어느 방식을 택하든 저장 직전에 최신 값을 확인해야 창을 전환하지 않고 나란히 사용하는 경우도 처리할 수 있다. [IndexedDB 트랜잭션 실행 규칙](https://www.w3.org/TR/IndexedDB-3/#transaction-scheduling)

## 이전 비교 화면의 사용성 확인 과업

컴퓨터에서는 같은 프로필의 두 창을 나란히 두고, 모바일에서는 두 탭을 오가며 확인한다. 아래는 검증할 과업이며 실행 결과는 아직 없다.

1. 다른 창에서 바꾼 시간을 확인하면서 내가 쓰던 문장을 이어 쓴다. 어느 값이 저장됐는지 설명할 수 있는지, 비교를 보류해도 입력과 커서가 남는지 관찰한다. 모바일에서는 한글 조합 도중 알림이 올 때와 키보드로 비교를 닫고 본문으로 돌아갈 때도 확인한다.
2. 본문 저장을 한 번 실패시킨 뒤 같은 메모에 한 줄을 더 쓴다. 실패 안내나 수동 조작 없이 편집을 이어가고, 내부 재시도가 성공한 뒤 다시 열면 마지막 문장까지 남는지 확인한다. 초안 정리만 실패한 경우에도 이미 저장된 본문을 다시 쓸 필요가 없어야 한다. 종료 후 복구를 제안하는 안은 실제로 남은 사본과 화면의 안내가 일치해야 한다.
3. A에서 시간을 수정하고 B에서 카드 위치를 바꾼 뒤 그 카드를 복사한다. 올바른 시간이 복사되고 위치가 유지되는지 확인한다. 이어 A에서 카드를 삭제하고 B에서 다른 카드의 겹침 순서를 바꿔 삭제된 카드가 다시 나타나는지 살핀다. B에서 삭제된 카드를 편집 중이었다면 글을 잃지 않고 다음 행동을 찾을 수 있는지도 확인한다.
4. 모바일에서 어제 만든 메모를 오늘 수정하고 기본 정렬을 본다. 핸들로 두 카드를 바꿔 다시 연 뒤 새 메모를 만든다. 새 메모가 첫 번째인지, 나머지 카드의 상대 순서와 일괄 복사에 미리 담은 문장 및 결합 순서가 유지되는지 확인한다.
5. B가 비교 화면을 연 채로 A에서 시간을 다시 바꾼다. B가 방금 본 선택지를 눌렀을 때 최신 본문을 알아보고 자기 입력도 다시 찾을 수 있는지 본다. 비교를 보류한 뒤 데스크탑 카드에서 복사하거나 모바일에서 편집을 이어가는 과업도 함께 본다.

먼저 확인할 과업은 1번과 2번이다. 두 본문의 차이를 알아보고 입력을 잃지 않은 채 다시 쓸 수 있는지에 따라 비교 화면의 배치와 동작을 판단할 수 있다. 같은 메모의 동시 편집 처리 방식, 창을 닫은 뒤 복구할 입력의 범위와 수동 정렬 뒤 수정한 메모의 위치는 미정이다. 열린 편집기에서 두 본문을 보여주는 데 필요한 값과 창을 닫은 뒤에도 보관할 값은 따로 정한다. 이 권장안만으로 초안 전용 테이블이나 변경 이력 테이블의 필요성을 결정할 수 없다.
