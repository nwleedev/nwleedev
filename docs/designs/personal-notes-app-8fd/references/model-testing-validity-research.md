# 메모 탐색 테스트의 검증력과 완료 판정 조사

U12의 문제는 생성 도구 부재가 아니라 기대값의 독립성, 행동 직후 관찰과 결함 탐지 증거가 부족한 상태에서 완료를 표시한 데 있다. 기존 계획에 이미 있던 통제된 결함, 축소 및 재현 조건을 실제 완료 판정에 적용해야 한다. 테스트 수를 늘리거나 다른 실행기를 설치하는 것만으로 해결되지 않는다.

2026년 9월 13일에 메모 모델 테스트 세 파일, IndexedDB 검사, 브라우저 생성형 검사와 U12 계획 및 실행 기록을 비교했다. 기준은 [요구사항의 모델 기반 탐색 테스트](../requirements.md#모델-기반-탐색-테스트)다. 확인한 설치 버전은 fast-check 4.10.0, pure-rand 8.4.2, Vitest 4.1.11과 Playwright 1.62.1이다. 아래 코드 판정은 읽기 조사이며 결함 주입 실험 결과가 아니다. 서비스의 새로운 버그 발견이나 전체 테스트의 부실을 주장하지 않는다.

## 보완 후에도 남은 문제와 근본 원인

2026년 9월 13일의 후속 조사에서도 로컬 완료 판정은 `needs revision`이다. 원문과 revision의 직접 비교, 제한된 결함 탐지와 실제 IndexedDB 재조회는 유효하다. 그러나 이 증거를 일반 탐색의 실패 재현, 자동 저장 시점과 겹친 메모의 조작 검증까지 확대할 수 없다. 아래 내용은 fast-check 4.10.0, Vitest 4.1.11과 Playwright 1.62.1을 사용하는 현재 코드에 대한 조사다. 새 결함 주입이나 브라우저 장애 재현을 수행한 결과는 아니다.

### 실패 보고와 행동 계측

세 모델의 일반 탐색은 `fc.check` 뒤 `assert.equal(details.failed, false)`를 실행한다. 실패하면 seed, counterexample, 원래 오류와 replayPath를 출력하기 전에 단순 boolean 비교에서 끝난다. 오류는 탐지해도 그 실행을 재현할 자료를 잃는다. [fast-check 4.10.0 RunDetails 소스](https://github.com/dubzzz/fast-check/blob/v4.10.0/packages/fast-check/src/check/runner/reporter/RunDetails.ts)는 실패 입력, 오류, seed와 축소 정보를 반환한다. 이 정보를 일반 탐색의 실패 보고에도 연결해야 한다.

현재 로그의 `skipped`는 `numSkips`다. 같은 소스는 이를 “Number of skipped entries due to failed pre-condition”으로 설명한다. [같은 버전 ModelRunner](https://github.com/dubzzz/fast-check/blob/v4.10.0/packages/fast-check/src/check/model/ModelRunner.ts)는 명령의 `check`가 참일 때만 `run`을 호출한다. 두 동작은 별개이므로 `numSkips=0`을 명령 생략 0회로 해석할 수 없다. 명령 종류별 생성, 실행과 조건 거절을 따로 집계하고 최초 탐색과 축소 중 실행량도 구분해야 한다.

### 입력 축소와 행동 순서 축소

현재 통제된 결함 검사는 고정된 저장 또는 복사 순서의 문자열과 삭제 순서의 위치 숫자를 축소한다. 일반 탐색의 `fc.commands`에서 불필요한 행동이 제거되고 같은 위반이 재현된다는 증거는 아니다. [fast-check 재현 설명](https://fast-check.dev/docs/advanced/model-based-testing/#replay-model-based-tests)은 명령 생성의 재실행에 seed와 path뿐 아니라 replayPath도 사용한다. 고정 순서의 입력 재현과 생성한 행동 순서의 재현을 각각 확인해야 한다.

결함 검사에서 `failed=true`나 `.rejects.toThrow()`만 확인하면 다른 예외도 성공 증거가 될 수 있다. [Stryker의 상태 구분](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/)은 검증 실패, 실행 오류와 컴파일 오류를 구분한다. 현재 검사는 선택한 결함에 대한 관찰식의 민감도를 보여주지만, 서비스 전체의 결함 탐지율을 뜻하지 않는다. 의도한 불변 조건 이름과 예상 및 실제 값의 차이를 확인하고 정상 실행은 같은 입력으로 통과시켜야 한다. 별도 mutation 도구나 점수 목표는 필요하지 않다.

### 모델과 실행 대상 사이의 자료 전달

저장 모델은 기대값을 독립적으로 계산하도록 바뀌었지만 실제 반환 요청을 실행 대상에 보관하지 않는다. 완료 명령에서 모델의 pending 값으로 요청을 다시 만들므로 요청의 ID나 메모 자료가 잘못 전달되는 일부 오류를 가릴 수 있다. 삭제 모델도 모델 쪽 메모를 `rememberRemovedNote`에 전달한다. 같은 행동 입력을 공유하는 것과 기대 상태를 실제 실행의 자료로 사용하는 것을 구분해야 한다.

생명 주기 모델의 정렬, 대상 추출, 앞뒤 삽입과 번호 재배정은 운영 알고리즘과 유사하다. 모델에서 운영 함수를 호출하지 않더라도 같은 계산을 복제하면 같은 오류를 낼 수 있다. 모델의 `revision`과 `updatedAt`은 계산하지만 관찰에서 제외하며 모든 제거 시각도 같다. 따라서 이 모델만으로 전체 스냅샷 복원이나 시간에 따른 만료 조합을 검증했다고 할 수 없다.

[fast-check 모델 지침](https://fast-check.dev/docs/advanced/model-based-testing/)과 [Hypothesis 상태 기반 검사](https://hypothesis.readthedocs.io/en/latest/stateful.html)는 기대값과 실행 대상을 별도로 유지하면서 행동 후 상태를 비교한다. 순서 모델에는 ID의 상대 순서와 삭제 스냅샷 등 필요한 정보만 두고, 저장 번호 규칙은 별도의 고정 기대값과 비교하는 방식을 적용할 수 있다. 이는 기존 독립 모델 조건의 구현 제안이다.

### 저장의 원인과 완료 시점

브라우저 검사는 800ms를 진행한 뒤 새로고침한다. 운영 hook은 `pagehide`와 문서 숨김에서도 저장하므로 최종 원문만으로 어느 동작이 저장을 완료했는지 구분할 수 없다. [Playwright Clock](https://playwright.dev/docs/clock)은 타이머를 제어하지만 [IndexedDB transaction 수명](https://www.w3.org/TR/IndexedDB/#transaction-lifecycle)의 commit 완료까지 보장하지 않는다. 페이지 이탈 전에 실제 저장 자료를 읽어 자동 저장 완료를 관찰해야 한다. 입력칸의 값은 아직 저장되지 않은 입력도 표시하므로 대체 증거가 아니다.

저장소 고정 검사는 초안을 저장한 뒤 삭제하고 마지막의 부재만 확인한다. 초안 쓰기가 무시되는 오류를 구별하려면 쓰기 직후 읽기가 필요하다. 논리적 요청 및 완료 순서 검사와 실제 진행 중 Promise를 사용하는 기존 hook 및 provider 검사는 각각 맡은 책임을 유지한다. 이번 보완을 동시성 탐색 엔진 도입으로 확대하지 않는다.

### 화면에서 보존과 조작을 구분

복원 E2E는 버튼을 누른 뒤 원문 목록을 확인하지만 실제 겹침 순서와 복원 포커스를 관찰하지 않는다. 순서 변경이 무시돼도 원문 검사는 통과할 수 있다. 새로고침 뒤 `all()`은 로딩을 기다리지 않으며 `arrayContaining`은 추가 메모를 허용한다. [Playwright locator 문서](https://playwright.dev/docs/api/class-locator#locator-all)는 목록이 준비된 뒤 `all()`을 호출하도록 안내한다. 새로고침 후 정확한 개수와 원문을 기다려 확인하고, 겹친 위치에서 실제 입력이 전달된 메모와 키보드 포커스를 확인해야 한다.

삭제 전 `zIndex` 보존은 결정된 상태다. 같은 숫자의 화면 표시 순서와 명시적 순서 변경의 동률 정렬이 서로 다를 가능성은 기존 [복원 조사](note-restoration-z-index-research.md)에 남아 있다. 기존 상대 순서 유지 조건과 실제 결과가 충돌하면 그 정책만 별도 판단 대상으로 남긴다. 테스트를 통과시키기 위해 복원값을 재배정하지 않는다.

### 완료 판정이 반복해서 앞선 이유

직접 원인은 예상 자료를 실제 입력에 섞는 연결, 관찰되지 않은 중간 상태, 다른 의미의 집계값과 제한된 결함 검사의 확대 해석이다. 공통 원인은 요구사항별로 어떤 오류를 구별해야 하는지와 어느 시점의 결과로 판단할지를 완료 기록에 연결하지 않은 것이다. 이 때문에 파일 추가, 전체 통과와 일부 결함 탐지를 단계 전체 완료로 해석했다.

이미 문서에 적힌 자동 저장 시점 분리와 명령별 집계 조건이 구현 완료 표시에 반영되지 않은 점이 이 원인 판단을 뒷받침한다. 도구 부족, 작성자의 의도나 시간 압박은 근거가 없으므로 원인으로 단정하지 않는다. 개발 지침의 fast-check 미구성 문구도 현재 설치 상태와 달라 문서 간 상태가 일치하지 않는다.

보완은 실패 보고와 명령 계측, 저장 입력 분리, 생명 주기 및 복사 모델, 저장 완료와 실제 화면 조작 순으로 진행한다. 각 항목은 유지할 정상 결과, 구별할 오류, 관찰 위치와 통과 증거를 갖춘 뒤 완료한다. 기존 테스트 통과 기록은 유지하되 그 기록이 증명하지 못한 조건은 미완료로 정정한다. 실행 순서와 중단 조건은 [플랜의 재보완 절차](../plan.md#로컬-검증력-재보완-절차)에서 관리한다.

## 제안 내용의 적용 순서와 필요한 산출물

첫 산출물은 메모 저장 도메인 하나에서 행동 생성, 판정, 실패 순서 축소, 로그 기록과 재현이 연결된 실행이다. 메모 전체의 기능별 검사는 그 실행을 입증한 뒤 확장한다. 기준은 [모델 기반 탐색 요구사항](../requirements.md#모델-기반-탐색-테스트)이며, 여기서는 기존 조건을 현재 파일과 작업 순서에 연결한다. 요구사항이나 이미 결정한 메모 동작을 변경하지 않는다.

### 행동 모델과 실행 대상

저장 모델은 현재 입력, 마지막 저장 원문과 revision, 진행 중 요청, 초안과 정리가 남은 상태를 구분한다. 각 행동에는 요구사항 소제목, 실행 조건, 바뀔 값, 유지할 값과 관찰값을 연결한다. 정상 행동은 편집, 저장 요청과 저장 완료를 중심으로 시작하고 재시도 및 복구 관찰을 연결한다. 이름만 있는 행동이나 상태를 바꾸지 않는 관찰을 정상 상태 전이 수에 포함하지 않는다.

비정상 시도는 저장 중 중복 요청과 기준 revision이 다른 초안의 복구 시도처럼 이미 거부 조건이 정해진 행동을 최소 두 종류 실제 실행한다. 같은 원문의 다음 저장은 초안 정리를 위한 허용된 행동이므로 비정상 시도로 세지 않는다. 저장소 실패 주입은 실행 환경의 실패 조건이며, 이것만으로 비정상 사용자 시도 두 개를 충족했다고 판단하지 않는다.

불변 조건은 성공한 원문 및 revision의 일치, 실패 뒤 입력 및 복구 자료 보존, 중복 요청으로 진행 중 요청이 바뀌지 않음과 정리 재시도에서 메모를 재작성하지 않음으로 구체화한다. 정답 모델은 실제 반환 요청에서 상태를 복사하지 않고 실행 대상은 실제 요청을 보관한다. Domain Adapter는 기존 저장 명령을 호출하는 역할이며 새 운영 API나 별도 패키지를 뜻하지 않는다.

### 탐색 정책과 판정

첫 저장 탐색에는 반복 입력, 저장 중 재입력 및 중복 요청, 실패 후 재시도, 빈 원문과 Unicode 원문, 오래된 초안과 긴 행동 순서를 연결한다. 임의 행동 배열 하나를 만들었다는 사실만으로 각 정책이 실행됐다고 보지 않는다. 각 정책이 어떤 명령과 입력 생성기에 연결됐는지 확인하고 필수 순서는 고정 사례로도 실행한다. 새로고침은 실제 저장 및 화면 단계에서, 비동기 완료 순서의 자동 탐색은 후속 확장에서 다룬다.

판정은 정상 전이, 허용된 거부, 요구사항 위반, 요구사항 모순, 기대값 미정과 환경 실패를 구분한다. 미정 상태를 성공으로 세거나 임의 기대값을 채우지 않는다. 도메인별로 실제 발생 가능한 상태만 표현하며 이 분류를 위해 범용 상태 머신을 만들지 않는다.

### 실패 발견부터 재현까지

일반 탐색에 연결한 통제된 결함이 지정한 불변 조건에서 실패해야 한다. 그 실행에 필요 없는 행동이 줄어든 사례를 확보하고, 축소 전후 순서와 남은 위반을 비교한다. 모든 축소가 최단 순서임을 수학적으로 증명할 필요는 없다. [fast-check의 명령 축소 및 재현](https://fast-check.dev/docs/advanced/model-based-testing/#replay-model-based-tests)을 사용하고 별도 축소기를 구현하지 않는다.

실패 기록에는 seed, path, 필요한 replayPath, 행동과 입력, 축소된 순서, 초기 및 실패 상태, 실행 계층, 불변 조건 이름과 예상 및 실제 값을 포함한다. 도구 버전, 프로필과 실행한 Git revision도 식별한다. 로그만 전달받은 실행에서도 동일 실패를 만들고 난수 없는 직접 순서에서도 재현한다. 정상 실행에는 같은 입력과 관찰식을 적용해 통과시킨다. 컴파일 오류나 임의 예외는 불변 조건 검출의 증거가 아니다.

### 프로필, CI와 회귀 사례

`note-model-settings.ts`에는 이미 `local-fast`, `pr`, `main`, `nightly`가 있으므로 네 프로필을 새로 추가할 필요는 없다. 현재 값의 생성 시간, 실행량과 축소 비용을 측정해 적정성을 판단하고 실제 선택한 프로필이 로그에 나오게 한다. 현재 세 모델의 `profile=local-fast` 문자열은 다른 프로필을 선택해도 바뀌지 않으므로 선택값과 표시값의 일치가 필요하다.

로컬 저장 PoC의 증거와 CI 증거는 별도로 표시한다. CI 서비스와 원격 저장소 미정은 로컬 실행을 막지 않지만 CI 최소 실패 순서 로그가 없으면 PoC 전체 완료로 표시하지 않는다. 기존 명령과 잠금 파일로 정상 검사, 통제된 결함의 예상 실패 판정과 재현을 수행하고, 예상한 결함 탐지 확인이 CI 자체를 항상 실패하게 만들지 않도록 한다. 실제 미예상 위반은 실패로 보고해야 한다.

중요한 실제 실패는 읽을 수 있는 행동 및 입력으로 회귀 사례에 보존한다. 실제 서비스 오류, 요구사항의 누락 발견과 통제된 결함 탐지는 별도로 기록한다. 실제 버그를 반드시 하나 찾아야 완료한다는 목표를 만들거나 모든 축소 결과를 예제 테스트로 복사하지 않는다.

### 메모 확장과 보류할 작업

저장 PoC의 로컬 합격 뒤 생명 주기와 개별 복사에 같은 판정 및 재현 방식을 적용한다. 반복 책임을 확인한 보고 및 프로필 코드만 공통화한다. 제안의 파일 트리나 interface 예시를 그대로 복사할 필요는 없다. 현재 `apps/notes`와 테스트 배치를 유지하며 책임이 실제로 같을 때만 추출한다.

실제 IndexedDB는 초안 쓰기, 메모 저장, 삭제와 복원 직후 자료를 확인한다. Browser Adapter에서는 작성, 저장, 재시도와 새로고침 등 도메인과 의미가 같은 행동을 연결하고, 브라우저가 막아 실행하지 못한 행동을 도메인 실행 성공으로 세지 않는다. 기존의 고정 E2E와 원문 생성 검사는 유지하되 공유 행동 모델의 구현 완료로 보고하지 않는다. [Playwright 실행 설정](https://playwright.dev/docs/test-configuration)은 실행 환경을 정하며, 저장 완료 관찰에는 별도로 [IndexedDB transaction 규칙](https://www.w3.org/TR/IndexedDB/#transaction-lifecycle)을 적용한다.

HTTP Adapter는 실제 애플리케이션 API가 없으므로 이번 로컬 앱 작업에 적용하지 않는다. 공통 패키지, Codex Skill, XState, 범용 UI 탐색과 동시성 자동 탐색은 첫 저장 PoC의 완료 조건이 아니다. 공통 패키지는 두 번째 적용과 요구사항에 기록된 추출 조건을 확인한 뒤 판단한다. 일괄 복사 목록은 요구사항 확인 전까지 보류하며, 현재 메모 저장 및 복원의 결정은 유지한다.

## 초기 조사 기록의 적용 범위

다음 절은 독립 모델 보완 전 코드에 대한 초기 조사다. 현재 해결 여부와 남은 작업은 위 후속 조사 및 플랜을 따른다. 특히 기대값을 실제 반환값에서 계산하던 방식, 좌표 관찰 누락과 시간 중단 설정 부재를 현재도 그대로 남은 문제로 해석하지 않는다.

## 기대값이 실제 구현에서 나온다

`note-content.model.test.ts`의 `RequestSaveCommand`는 실제 반환값의 상태와 요청을 모델에 복사한다. `CompleteSaveCommand`도 실제 성공 및 실패 분기에 따라 기대 상태를 정한다. 모델의 실패 설정은 저장되지만 예상 분기를 독립적으로 결정하는 데 사용되지 않는다.

예를 들어 요청 함수가 항상 요청을 만들지 않으면 완료 명령은 실행 조건에서 생략되고, 저장 전 원문이 그대로라는 검사는 통과할 수 있다. 이는 코드에서 도출한 반례 후보다. 입력이 바뀌었는지, 요청이 진행 중인지와 주입한 실패를 기준으로 먼저 예상 전이를 정해야 한다.

[fast-check 공식 문서](https://fast-check.dev/docs/advanced/model-based-testing/)는 모델을 단순화하면서도 “avoid testing the code by comparing it to itself”라고 설명한다. [Hypothesis 상태 기반 검사](https://hypothesis.readthedocs.io/en/latest/stateful.html)는 비교 대상과 모델에 같은 행동을 적용한 뒤 결과를 확인하는 사례를 제공한다. 두 자료를 비교하면 중요한 조건은 모델의 코드 길이가 아니라 기대값을 실제 반환값과 독립적으로 정할 수 있는지다.

복사 모델에서도 `reviseNote`로 기대 메모를 직접 갱신한다. 입력 준비에는 운영 함수를 사용할 수 있지만 원문 revision의 정확성을 증명하려면 별도의 예상 변경 횟수와 복사 당시 원문을 비교해야 한다. 모든 운영 함수 재사용을 금지하는 대신 검사하려는 규칙의 기대값에 같은 함수를 사용하는지 확인한다.

## 보존 검사와 동작 성공 검사가 분리되어 있다

`note-lifecycle.model.test.ts`는 좌표를 바꾼 뒤 원문 revision과 Tab 순서를 비교하지만 요청한 좌표를 비교하지 않는다. 복원 뒤 원문과 geometry도 모델 비교에서 빠져 있다. `copy-note.model.test.ts`는 사용 기록의 revision이 현재 값 이하인지만 검사하므로 모든 기록이 이전 원문에 잘못 연결된 경우를 구별하지 못할 수 있다.

`note-storage.model.indexeddb.test.ts`는 삭제 뒤 바로 같은 메모를 저장하고 최종 목록만 비교한다. 삭제를 생략해도 같은 최종 목록이 나온다. 초안 저장 뒤 정리한 결과만 읽는 검사도 초안이 중간에 실제로 저장됐는지 별도로 증명하지 않는다. 의미 있는 변경 직후의 상태와 보존할 상태를 함께 관찰해야 한다.

[Stryker의 상태 구분](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/)은 코드를 실행한 검사와 결함을 찾아 실패한 검사를 구별한다. 이 관점에서는 저장 무시, 이동 무시, 삭제 무시와 잘못된 원문 버전 기록을 구별하는 사례가 필요하다. Stryker 설치나 점수 목표를 제안하는 것은 아니다. 기존 도구에서 제한된 결함 사례를 실행하는 것으로 먼저 확인한다.

`expect(true).toBe(true)`는 저장, 이동이나 복원이 올바른지 증명하지 않는다. 다만 같은 테스트 안의 `fc.assert`와 명령별 assertion은 실패할 수 있으므로 파일 전체가 항상 통과한다고 해석해서도 안 된다. 형식상 검증문이 있다는 사실과 실제 검증력을 분리한다.

## 행동 생성과 실제 실행량이 다르다

`RequestSaveCommand.check`는 저장 중 요청을 제외하고, 복원 명령은 빈 이력을 제외한다. 정상 행동에 필요한 조건일 수 있지만 중복 요청과 빈 이력 시도를 탐색했다고 볼 수는 없다. 생성 수, 실행 수와 생략 수가 없어 필수 비정상 시도가 실행됐는지 확인할 수 없다.

[fast-check 명령 설명](https://fast-check.dev/docs/advanced/model-based-testing/#replay-model-based-tests)은 실제 실행한 명령과 생략한 명령을 구별하며 `replayPath`에 그 이력을 반영한다. 따라서 정상 명령의 조건을 무조건 제거하지 않고, 요구사항이 정해진 비정상 시도를 별도 명령과 고정 순서로 실행해야 한다.

[시간 제한 공식 문서](https://fast-check.dev/docs/configuration/timeouts/)는 `interruptAfterTimeLimit`으로 중단해도 적어도 한 사례가 성공했다면 기본적으로 성공할 수 있다고 명시한다. 현재 설정에는 중단을 실패로 처리하는 옵션과 실행량 판정이 없다. 이는 중단이 발생했다는 증거가 아니라 미완료 탐색을 성공으로 오인할 수 있다는 설정상 위험이다. 필수 사례 실행과 시간 예산 내 추가 탐색을 구별해 기록해야 한다.

## 논리적 저장 순서와 실제 비동기 실행이 다르다

저장 모델의 요청 명령은 상태 함수만 호출하고 실제 `saveNoteContent`는 완료 명령에서 시작한다. 따라서 A 요청 뒤 B 입력을 만드는 순서는 논리적 요청 보존을 검사하지만 진행 중인 실제 저장 Promise와 새 입력의 충돌을 재현하지는 않는다. 대기 저장소를 사용하는 기존 provider 검사는 다른 책임을 맡는다.

`notes-model.spec.ts`의 생성형 검사는 두 문자열을 바꿀 뿐 행동 순서는 고정한다. 실제 IndexedDB 파일도 고정 사례 두 개이며 도메인 명령을 연결한 생성형 저장소 실행은 아니다. 후보별 새 BrowserContext와 새 연결 조회는 유효하지만 행동 모델 공유의 완료 증거는 아니다.

[Playwright Clock](https://playwright.dev/docs/clock)은 타이머와 시각 API를 제어하고, [IndexedDB transaction 수명](https://w3c.github.io/IndexedDB/#transaction-lifecycle)은 별도의 commit 및 complete 절차를 정의한다. 이를 비교하면 800ms 진행이나 입력값 확인만으로 저장 완료를 추정할 수 없다. 새로고침 뒤 값 확인은 저장 보존의 증거지만 그 저장이 자동 저장 때문인지 이탈 시 저장 때문인지는 분리해서 확인해야 한다.

Clock 문서는 앱이 타이머를 사용하기 전에 설치하도록 요구한다. 현재 화면 진입 뒤 설치하는 순서의 영향도 확인해야 한다. 이는 불규칙한 실패가 관찰됐다는 주장이 아니다. 저장 완료를 관찰하는 방법과 시각 설치 시점을 후속 구현에서 정할 필요가 있다는 뜻이다.

[Kubeflow Pipelines의 고정 변경 e27593f](https://github.com/kubeflow/pipelines/commit/e27593f828a3189a48e50b5b4190cb8d31ed142e)는 내부 `setState` 및 스냅샷 검사에서 파일 업로드와 입력값 결과를 확인하는 검사로 바꾼 사례다. 이 변경은 관찰 대상을 고르는 근거이며 메모 앱에서 같은 장애가 발생했다는 증거는 아니다. 기존 [테스트 지침](../../../dev/personal-notes-app/test-anti-patterns.md)의 결과 중심 기준을 적용한다.

## 완료 기준이 실행 기록과 연결되지 않았다

U12에는 통제된 결함 탐지, 축소, seed 재실행과 입력 직접 실행이 이미 적혀 있다. 그러나 실행 기록은 파일 추가와 통과 개수를 근거로 단계 1, 3, 4를 완료로 표시했다. 실패 재현 자료, 필수 행동 실행량과 정상 및 결함 실행 비교가 빠져 있어 완료 조건과 증거가 맞지 않는다.

현재 Playwright가 기록한 `.last-run.json`에는 성공 상태와 빈 실패 목록이 있다. 이 파일에는 실행 명령, 검사 개수와 Git revision이 없어 이전 전체 96개 실행의 증거로 특정할 수 없다. 명령 종료와 마지막 집계를 함께 확보한 실행만 확정 기록으로 남겨야 한다. 파일이 없거나 과정이 종료됐다는 사실도 성공 증거가 아니다.

저장소의 테스트 안티패턴 지침은 이미 약한 검증문과 구현 복제를 금지한다. 지침 추가만으로 해결하기 어려운 이유다. 단계별로 요구한 증거를 같은 실행 기록에서 읽을 수 있어야 하며, 미확인 항목이 있으면 완료를 표시하지 않아야 한다.

## 원인과 다음 작업의 관계

확인한 직접 원인은 실제 반환값에 종속된 기대값, 빠진 중간 관찰, 생략된 행동을 드러내지 않는 기록과 실행 계층의 혼동이다. 이 때문에 결함이 있어도 성공할 수 있는 검사가 생기고, 그 성공을 기능 검증 완료로 확대해 해석했다.

작업 절차의 근본 원인은 계획의 완료 조건을 증거에 연결하지 않은 채 여러 기능으로 확장한 것이다. 코드와 완료 기록의 불일치가 이 판단을 뒷받침한다. 시간 압박, 도구의 한계나 특정 작성 주체의 의도는 확인할 자료가 없으므로 원인으로 단정하지 않는다.

후속 작업은 기대값과 관찰 항목 확정, 저장 모델 보완, 통제된 결함 및 재현 증명, 다른 메모 기능 보완, 실제 저장 및 화면 연결, 실행 증거 확인 순서다. 세부 절차는 [U12 보완 순서](../plan.md#보완-순서와-단계별-완료-증거)에서 관리한다. 이번 조사에서는 테스트, 운영 코드, 의존성과 CI를 변경하지 않았다.

조사 당시 미정이던 `zIndex` 복원은 [삭제 복원 결정](../decisions/note-removal-recovery.md)에서 삭제 전 숫자 보존과 중복 허용으로 확정했다. 항상 고유하다는 이전 조건은 명시적 맨 앞 및 맨 뒤 이동 직후의 조건으로 바뀌었다. 화면과 저장에 적용하는 방법 및 남은 동률 처리 확인은 [추가 조사](note-restoration-z-index-research.md)에서 관리한다.
