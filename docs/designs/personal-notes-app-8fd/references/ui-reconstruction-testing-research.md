# UI 재구축 테스트 선정 조사

## 결론

UI 재구축 테스트는 구성요소와 hook의 모양이 아니라 사용자가 저장한 내용을 다시 찾고, 편집하고, 복사하며, 실패 뒤에도 원문과 작업 상태를 잃지 않는지를 확인해야 한다. U13부터 U18 가운데 새 TDD가 필요한 부분은 U17에서 추가하는 순수 재정렬 전이뿐이다. 입력 임계값, pointer capture, 포커스, 반응형 배치, Clipboard, IndexedDB와 Worker처럼 브라우저 또는 외부 시스템이 결과에 관여하는 절차는 TDD로 대체하지 않는다.

이 결론은 현재 요구사항과 [모듈별 TDD와 동작 검증 결정](../decisions/verification-strategy.md), [테스트 전략](../../../dev/personal-notes-app/testing-strategy.md), [테스트 안티패턴](../../../dev/personal-notes-app/test-anti-patterns.md)을 기준으로 2026년 9월 22일에 다시 검토한 결과다. 별도 조사에서 확인한 사용자 목적은 테스트 우선순위를 정하는 보조 근거로만 사용했으며, 승인되지 않은 기능은 테스트 대상으로 추가하지 않았다.

## 테스트 케이스는 사용자 과업과 실패 위험에서 고른다

[Playwright 권장사항](https://playwright.dev/docs/best-practices)은 사용자가 보고 조작하는 결과를 검사하고 함수명, 배열 형태와 CSS class 같은 구현 세부를 피하라고 안내한다. [Testing Library query 지침](https://testing-library.com/docs/queries/about/)도 접근 가능한 role과 이름, label을 우선해 실제 사용 방식에 가까운 검사를 작성하도록 설명한다. 후자는 선택자 원칙의 근거로만 사용하며 현재 설치되지 않은 테스트 라이브러리를 추가하지 않는다.

각 사례는 코드를 작성하기 전에 다음 다섯 항목을 설명할 수 있어야 한다.

1. 어떤 승인된 요구사항이나 결정의 결과를 보호하는가.
2. 시작 자료는 무엇이며 사용자가 어떤 제어를 어떤 순서로 실행하는가.
3. 화면, Clipboard, 저장소 또는 다시 연 route에서 무엇을 관찰하는가.
4. 어떤 잘못된 동작을 이 검증문이 구별하는가.
5. 같은 결과를 이미 더 직접적으로 확인하는 검사가 있는가.

다섯 번째 항목에서 기존 증거가 충분하면 새 테스트를 추가하지 않는다. 기존 테스트가 DOM 구조나 이전 문구에 묶여 승인된 결과를 보호하지 못하면 그 검사를 사용자 결과 기준으로 교체한다. 테스트 수와 coverage 수치는 사례 선정 근거로 사용하지 않는다.

대표 사례는 사용자가 저장한 원문을 실제 제어로 다시 사용하는 과업에서 시작한다. 빈 원문, 긴 원문, 같은 원문을 가진 서로 다른 메모, 저장 실패, 권한 거절, 취소와 route 재진입은 서로 다른 결함을 찾을 때만 별도 사례로 둔다. 승인되지 않은 기능을 사례에 끼워 넣거나 외부 서비스의 화면과 문구를 예상값으로 사용하지 않는다.

## TDD는 안정된 순수 규칙에만 적용한다

TDD는 구현 전에 입력, 결과와 불변 조건을 설명할 수 있고 브라우저를 흉내 내지 않아도 같은 결함을 재현할 수 있을 때만 적용한다. 현재 UI 재구축에서 이 조건을 새로 만족하는 부분은 U17의 재정렬 session 상태 전이뿐이다.

재정렬 session TDD는 pointer 좌표나 reducer action 문자열을 고정하지 않는다. 다음 사용자 결과를 순수 입력과 결과로 표현한다.

- 임계값을 넘기 전 취소하면 원래 순서가 유지된다.
- 유효한 앞뒤 위치에서 완료하면 항목 ID와 삽입 index로 된 명령 하나가 생긴다.
- 자기 위치 또는 유효하지 않은 위치에서는 저장 명령이 생기지 않는다.
- 저장 실패를 받으면 작업 전 순서와 다시 시도할 명령이 복구된다.
- 새 session이 시작되면 이전 session의 preview와 실패 상태가 섞이지 않는다.

테스트는 `idle`, `dragging` 같은 내부 상태 이름, reducer action 문자열, hook 호출 횟수와 ref 값을 검사하지 않는다. module이 제공하는 전이 함수에 사용자 입력을 주고 순서, 명령 발생 여부와 복구 자료만 확인한다. 실제 pointer capture, 500ms 길게 누르기, 가장자리 자동 scroll, focus와 live region은 브라우저 검사에 남긴다.

U13의 알림 시간, U14의 탐색, U15의 메모 gesture, U16의 길게 누르기와 상세 폼, U18의 Page hook 이동은 새 TDD 대상이 아니다. 이미 TDD가 적용된 복사 명령, 메모 저장 전이, 삭제 복구, 사용 횟수, 분석과 템플릿 순수 규칙은 구현 결과가 바뀌지 않으므로 기존 테스트를 회귀 기준으로 먼저 실행한다. 리팩터링을 통과시키려고 함수나 hook 단위 테스트를 새로 만들지 않는다.

## 시간과 순서를 하드코딩하지 않고 요구사항에서 얻는다

[Playwright Clock](https://playwright.dev/docs/clock)은 애플리케이션이 타이머를 만들기 전에 clock을 설치하고 시간을 진행해 실제 화면 결과를 확인할 수 있게 한다. [Vitest timer 지침](https://vitest.dev/guide/mocking/timers)은 순수 timer 규칙을 실제 대기 없이 검사하는 방법을 제공한다. 이 저장소에서는 브라우저 UI의 알림, 길게 누르기와 자동 저장은 Playwright Clock으로 확인하고, 이미 승인된 순수 시간 전이만 Vitest fake timer 또는 주입한 clock으로 검사한다.

5초 알림, 500ms 길게 누르기, 800ms 자동 저장, 5 CSS px와 10 CSS px 임계값처럼 요구사항이 정한 수치는 테스트에 독립적으로 적을 수 있다. 운영 상수를 import해 예상값에도 사용하지 않는다. 요구사항에 없는 대기 시간, 화면 좌표와 항목 개수는 테스트 통과를 위해 임의로 정하지 않는다.

순서 검사는 고정 ID 대신 실행 중 생성된 entity ID를 보관해 같은 대상을 추적한다. 문구는 사용자가 입력한 원문으로서 테스트가 정할 수 있지만, `note-1`, `item-2`처럼 실행 코드가 만들 식별자를 예상하지 않는다. 서로 같은 원문을 가진 두 메모를 구분해야 하는 사례에서는 화면에서 생성한 두 ID와 각 메모가 차지한 상대 순서를 사용한다.

## 예상값과 실제 값은 서로 다른 출처에서 얻는다

실제 값은 실행 중인 화면, Clipboard, 새 IndexedDB 연결 또는 다시 연 route에서 읽는다. 예상값은 요구사항의 문구 및 수치, 승인된 순서 규칙과 테스트가 직접 입력한 원문에서 얻는다. 운영 정규화 함수, 운영 selector와 같은 계산으로 예상값을 만들지 않는다.

검증문은 다음 결과 가운데 필요한 것만 확인한다.

- 편집하거나 복사한 원문이 공백과 줄바꿈을 포함해 보존되는가.
- 같은 원문의 다른 메모와 다른 revision을 섞지 않는가.
- 저장 성공 뒤 새로고침해도 순서와 원문이 유지되는가.
- 실패 뒤 원문, 선택과 다시 시도 가능 상태가 유지되는가.
- 취소나 pointer 중단 뒤 저장, 복사 또는 route 이동이 발생하지 않는가.
- 작업 완료 알림이 실제 Clipboard 또는 저장 결과와 일치하는가.

모의 구현 호출 횟수, Context 값, hook 반환 객체, CSS class, DOM 자식 순서와 큰 snapshot은 위 결과를 대신하지 못한다. 오류를 만들기 위해 application interface의 가짜 구현을 사용할 수 있지만, 실제 브라우저 API와 저장소 동작은 대상 브라우저에서 별도로 확인한다.

## 테스트 계층은 같은 결함을 중복 검사하지 않는다

- Vitest TDD는 U17의 순수 전이와 이미 승인된 domain 및 application 규칙을 확인한다.
- Vitest Browser Mode는 실제 IndexedDB transaction과 provider가 새 연결에서 자료를 보존하는지 확인한다.
- Playwright Test는 운영 빌드에서 사용자가 제어를 찾고 실행해 화면, Clipboard, route와 저장 결과를 확인한다.
- 시각 검토는 색, 간격, 겹침, 잘림, 200% 확대, `forced-colors`와 반응형 배치를 확인한다.

한 결함을 더 낮은 비용의 계층에서 이미 직접 판정해도 실제 연결이 별도 위험이면 상위 계층에 대표 사례 하나를 둔다. 같은 분기와 예상값을 여러 도구에 복사하지 않는다. [Playwright 격리 지침](https://playwright.dev/docs/browser-contexts)은 각 테스트가 독립된 브라우저 상태에서 실행돼야 한다고 설명하므로, 다른 테스트가 만든 IndexedDB 자료, 선택 또는 clock에 의존하지 않는다.

[fast-check 모델 기반 테스트 지침](https://fast-check.dev/docs/advanced/model-based-testing/)은 모델을 실제 구현보다 단순하게 유지하고 명령을 실행 가능한 조건과 결과 검증으로 나누도록 안내한다. U13부터 U18의 새 예제 테스트를 모두 생성형 검사로 바꾸지 않는다. U12에서 승인한 대상에만 대표 사례 뒤의 행동 순서 탐색을 추가하고, 운영 reducer나 provider 상태를 모델에 복제하지 않는다.

## 계획에 미치는 영향

U13, U14, U15, U16과 U18은 새 TDD 없이 기존 순수 규칙 검사를 먼저 실행하고 브라우저에서 변경된 사용자 과업을 확인한다. U17은 `reorder-pointer-session.ts`의 순수 전이를 실패 테스트부터 작성하되 내부 상태 이름을 고정하지 않으며, 실제 drag와 저장 연결은 별도 브라우저 사례로 확인한다.

각 작업 단위의 계획에는 TDD 여부, 수정할 기존 테스트 파일, 사용자 입력, 관찰 결과, 잡아낼 오동작과 사용하지 않을 검증 방식을 함께 적는다. 기존 테스트가 보호하던 승인된 결과를 새 사례가 대신하면 중복 검사를 제거하되, 대체 증거를 확인하기 전에는 삭제하지 않는다.
