# 메모 선택, 속성 편집과 제거 복구 조사

## 결론

넓은 공간형 화면에서는 메모 선택, 속성 패널 활성화와 헤더 drag를 한 pointer 연속 입력에서 분리해야 한다. 이동으로 판정되지 않은 한 번의 헤더 클릭은 메모를 즉시 선택하고 얇은 붉은 테두리만 새로 표시한다. 브라우저의 `dblclick`과 선택 지점에 포커스가 있는 선택된 메모의 보조 키 없는 `Enter`는 속성 패널을 여는 별도 동작으로 사용한다. 선택을 일부러 지연해 더블클릭을 기다릴 필요는 없으며, 이동 기준을 넘긴 뒤의 `click`과 `dblclick`은 모두 억제해야 한다.

메모 선택은 빈 캔버스에서 이동 없이 끝난 클릭, 보조 키 없는 `Escape` 또는 `Command` keydown으로 해제한다. 이 입력은 선택 ID와 붉은 테두리만 지우며 속성 패널 대상, 속성 초안, 최근 활성 패널과 일괄 복사 자료를 지우지 않는다. 캔버스의 상위 handler에서 모든 click을 선택 해제로 처리하면 메모와 패널의 조작까지 함께 실행되므로, 빈 캔버스 자체에서 끝난 입력인지 확인해야 한다.

`Command`를 누르는 동안 헤더의 자리까지 없애면 메모 본문과 외곽 크기가 움직인다. 헤더의 높이는 유지하면서 시각 요소와 조작만 숨기고, 본문의 `Command+클릭`과 `Command+Option+클릭`이 선택 이벤트로 전파되지 않게 해야 한다. 보조 키 상태는 각 pointer event의 `metaKey`를 우선 확인하고 `keydown`, `keyup`, 창의 포커스 상실과 문서 숨김을 함께 처리해 헤더가 계속 숨은 상태로 남지 않게 한다.

헤더 drag 중 오른쪽 패널이 열리거나 닫히면 캔버스가 사용하는 열의 크기가 달라질 수 있다. drag가 끝나거나 취소될 때까지 패널 표시 여부와 캔버스의 계산 크기를 애플리케이션 동작으로 바꾸지 않고, 시작 때의 좌표 변환 기준을 유지해야 한다. Pointer capture는 pointer가 헤더 밖으로 나간 뒤에도 같은 drag 세션을 이어가는 수단이다.

속성 입력은 사용자가 편집하는 문자열과 저장된 수치 geometry를 분리해야 한다. `blur`, 패널 밖 클릭과 `Enter`는 같은 적용 명령으로 모으고, `0`보다 크며 승인된 상한 이하인 유한한 값 가운데 실제로 달라진 입력만 한 번 저장해야 한다. 잘못된 입력은 저장 자료와 revision을 바꾸지 않고 오류가 난 입력 가까이에서 고칠 방법을 알려야 한다.

오른쪽 속성 패널과 일괄 복사 패널은 마지막으로 활성화한 패널 하나만 표시한다. 헤더 더블클릭 또는 선택된 메모의 선택 지점에서 실행한 `Enter`는 속성 패널을 활성화하고 일괄 복사 동작은 일괄 복사 패널을 활성화한다. 한 번의 헤더 클릭, `Tab` 선택과 선택 해제는 최근 활성 패널을 바꾸지 않는다. 따라서 선택한 메모 ID와 속성 패널 대상 ID를 같은 값으로 간주하면 안 된다.

메모 제거는 즉시 결과를 보여주되 되돌릴 수 있어야 한다. 메모 작업 주 영역의 중앙 하단에 `메모를 제거했습니다.`와 `취소`를 함께 표시하고, 취소하면 원문, 위치, 크기와 겹침 순서를 복원한다. 이 알림은 변환되는 캔버스 안에 두지 않는다. 실행 취소 동작을 포함하므로 단순한 시간제 성공 알림처럼 너무 빨리 없애면 안 되며, 알림이 나타날 때 현재 키보드 포커스를 빼앗지 않아야 한다.

## 조사 질문과 적용 범위

이 조사는 [개인 메모 애플리케이션 요구사항](../requirements.md)의 넓은 화면 메모 조작에 다음 결과를 추가하기 위해 수행했다.

- `Tab`으로 메모를 찾아 선택하고 헤더 클릭으로도 같은 선택을 만드는 방법
- 선택된 메모의 선택 지점에서 `Enter`로 속성 패널을 열되 메모 본문과 하위 조작의 키 입력을 보존하는 방법
- 빈 캔버스 클릭, `Escape`와 `Command`로 메모 선택만 해제하는 방법
- 선택과 키보드 포커스를 시각 및 보조 기술에서 구분하는 방법
- 선택한 메모의 좌표와 크기를 오른쪽 패널에서 수정하는 방법
- `blur`, 패널 밖 클릭과 `Enter`를 중복 저장 없이 적용하는 방법
- 메모 제거 직후 취소할 수 있는 알림의 위치, 포커스와 수명
- 저장된 `tabindex`를 따르고 시각적 겹침 순서와 독립적인 메모의 `Tab` 순서
- 메모 속성 패널과 일괄 복사 패널의 최근 활성 우선순위
- 좌표 및 크기의 `0` 이하 거부와 애플리케이션 상한 검증
- 한 번의 헤더 클릭, 더블클릭과 drag가 서로 중복 실행되지 않는 이벤트 규칙
- `Command`를 누르는 동안 헤더를 숨기면서 메모 크기와 키보드 포커스를 유지하는 방법
- 헤더 drag 중 오른쪽 패널 전환으로 캔버스 크기가 바뀌지 않게 하는 방법

공식 자료는 2026년 9월 2일에 확인했다. 선택과 패널 활성화는 Figma 애플리케이션의 화면 구성을 근거로 정하지 않고, 승인된 개인 메모 요구사항과 웹 이벤트 및 접근성 표준으로 검증했다. 내려받은 `.fig` 파일의 시각 비교도 이 입력 규칙의 근거로 사용하지 않았다.

## 한 번 클릭, 더블클릭과 키보드 동작

[UI Events Algorithms](https://w3c.github.io/uievents/event-algo.html)는 운영체제가 `mouseup` 직후 별도 `click`을 보내고 더블클릭을 별도로 판정한다고 설명한다. [UI Events](https://w3c.github.io/uievents/TR.html)는 더블클릭의 시간 및 거리 기준이 실행 환경 설정에 달려 있고 `UIEvent.detail`이 현재 클릭 횟수를 나타낸다고 정한다. 애플리케이션이 자체 지연 타이머로 같은 판정을 다시 만들면 운영체제 설정과 달라지고 한 번 클릭의 선택 피드백도 느려진다.

따라서 첫 `click`에서는 선택 ID와 얇은 붉은 테두리를 즉시 바꾸고, 같은 헤더의 이동 없는 `dblclick`에서만 속성 패널 대상과 최근 활성 패널을 바꾼다. 첫 클릭을 취소하거나 기다리지 않는다. 본문 클릭은 상시 편집 `textarea`의 커서 및 선택 범위와 보조 키 복사만 다루고, 상위 메모의 `pointerdown`이나 `focus` 전파로 선택을 만들지 않아야 한다.

[WAI 키보드 인터페이스 지침](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)은 `Tab`과 `Shift+Tab`이 구성요소 사이의 포커스를 이동하고, 포커스와 선택은 서로 다른 상태라고 설명한다. 선택이 포커스를 따라가는 단일 선택 구성도 가능하지만 다음 조건이 필요하다.

- 현재 키보드 포커스는 항상 보이고 선택 테두리와 구분돼야 한다.
- 메모 안의 본문과 아이콘 버튼도 논리적인 순서로 도달할 수 있어야 한다.
- 메모의 양의 `tabindex`가 페이지의 기본 focusable 요소보다 먼저 탐색되는 표준 동작을 고려해 전체 문서의 포커스 순서를 검증해야 한다.
- 선택한 메모에서 속성 패널로 포커스를 옮겨도 메모 선택은 유지해야 한다.
- 선택한 메모를 제거하면 포커스가 문서 본문으로 사라지지 않도록 다음 대상을 정해야 한다.

[HTML Standard](https://html.spec.whatwg.org/multipage/interaction.html#the-tabindex-attribute)는 같은 focus navigation scope 안에서 양의 `tabindex`가 낮은 요소부터 높은 요소 순으로 탐색한다고 정의한다. 현재 요구사항은 일반적인 DOM 순서 권고의 예외로 메모 사이의 순서를 명시적인 `tabindex` 값으로 관리한다. `zIndex`는 시각적 겹침만 나타내며 맨 앞으로 또는 맨 뒤로 보내기와 선택 표시를 위한 일시적 layer 변경은 `tabindex`를 바꾸지 않는다. 새 메모의 초기값, 누락되거나 중복된 이전 값의 정리와 메모 뒤에 이어질 본문, 헤더 아이콘, 오른쪽 패널 및 전역 탐색의 전체 포커스 순서는 구현 전에 결정해야 한다. 세부 근거는 [메모 Tab 순서, 항목 동작 팝오버와 모바일 지연 재정렬 조사](tab-order-popover-and-mobile-reorder-research.md)에 기록했다.

사용자가 요청한 얇은 붉은 테두리는 선택 표시다. [WCAG 2.2 Focus Appearance 설명](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)은 키보드 포커스 표시의 면적과 대비를 다루며, [Use of Color 설명](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)은 색만으로 상태를 전달하지 말라고 한다. 따라서 붉은색 자체만 바꾸는 대신 이전에 없던 테두리 형태를 추가하고, 고대비 환경에서도 선택을 구분할 대체 표현을 제공한다. 별도의 포커스 외곽선은 선택 테두리보다 충분히 두껍고 인접 색과 구분돼야 한다.

[WCAG 2.2 Keyboard](https://www.w3.org/TR/WCAG22/#keyboard)는 pointer로 제공한 기능을 특정 키 입력 시간에 의존하지 않고 키보드로도 실행할 수 있어야 한다고 요구한다. [On Focus 설명](https://www.w3.org/WAI/WCAG22/Understanding/on-focus.html)은 `Tab`으로 포커스가 도달한 것만으로 예상하지 못한 문맥 변화를 만들지 말라고 설명한다. [WAI 키보드 인터페이스 지침](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)은 포커스와 선택을 구분하고, 포커스 이동과 별도로 실행할 동작에 `Enter` 또는 `Space`를 사용하는 관례를 설명한다. 요구사항 책임자는 이 애플리케이션에서 보조 키 없는 `Enter`를 더블클릭과 동등한 패널 활성화 동작으로 승인했다. 따라서 `Tab`은 선택까지만 수행하고 선택 지점 자체에 포커스가 있을 때의 `Enter`가 속성 패널 대상과 최근 활성 패널을 바꾼다.

패널을 연 뒤 포커스를 메모에 유지하면 선택 문맥을 계속 확인하기 쉽지만, 양의 `tabindex` 때문에 패널 입력까지 많은 요소를 지나야 할 수 있다. 첫 패널 입력으로 포커스를 옮기면 즉시 편집할 수 있지만 공간형 메모 탐색 문맥에서 벗어난다. 어느 결과가 이 애플리케이션에 알맞은지는 요구사항으로 승인되지 않았으므로 전체 문서 포커스 순서와 함께 실제 키보드 흐름을 비교한 뒤 정해야 한다.

[UI Events](https://w3c.github.io/uievents/TR.html)는 키보드 event의 `key`, `repeat`와 `isComposing`을 표준 속성으로 정의한다. 패널 활성화는 `key === "Enter"`, 보조 키 없음, `repeat === false`, `isComposing === false`인 첫 `keydown`에 한 번만 실행한다. [React의 이벤트 응답 지침](https://react.dev/learn/responding-to-events)은 하위 요소의 event가 상위 요소로 전파된다고 설명한다. 따라서 메모 전체의 상위 handler나 Effect에서 `Enter`를 추론하지 않고, 선택 지점 자체가 event 대상일 때 직접 처리해야 한다. 그래야 편집 `textarea`의 줄바꿈, 헤더 아이콘 버튼의 실행과 속성 입력의 적용용 `Enter`를 가로채지 않는다.

## 선택 해제 입력

[Figma의 객체 선택 도움말](https://help.figma.com/hc/en-us/articles/360040449873-Select-layers-and-objects)은 빈 캔버스 클릭과 `Esc`를 전체 선택 해제 방법으로 제공한다. 이는 이번 요구사항의 근거가 아니라 공간형 편집 화면에서 이미 쓰이는 관례를 교차검증하는 자료다. 메모, 패널과 다른 조작 요소의 하위 click이 캔버스까지 전파됐다는 이유로 선택을 해제하면 안 되므로 이동 없이 끝난 빈 캔버스 자체의 click만 선택 해제로 처리한다. 캔버스 drag는 시점 이동으로 남기고 click 선택 해제와 중복 실행하지 않는다.

`Escape`는 보조 키가 없는 keydown이 애플리케이션에 전달됐을 때 선택 ID만 비우고 속성 패널 대상과 최근 활성 패널은 유지한다. 빈 캔버스 클릭은 브라우저 포커스를 바꿀 수 있고 `Command`는 포커스가 있던 헤더 조작을 숨길 수 있다. 세 입력 뒤 포커스를 어디에 둘지는 별도로 결정해야 하며, 속성 입력 초안을 되돌릴지도 선택 해제와 묶어 추정하지 않는다.

[UI Events 키 값 표](https://www.w3.org/TR/uievents-key/)는 macOS Command 키의 표준 `KeyboardEvent.key` 값을 `Meta`로 정하고, [UI Events](https://w3c.github.io/uievents/TR.html)는 `metaKey`로 조합 상태를 제공한다. Command 자체의 첫 keydown에서 선택을 해제하고 헤더 비노출 상태를 시작하되 `preventDefault()`를 호출하지 않는다. 그래야 이어지는 운영체제 및 브라우저 단축키와 `Command+클릭` 복사를 막지 않는다. `keyup`, 창의 포커스 상실이나 문서 숨김에서는 헤더를 다시 보이게 하지만 선택을 자동 복원하지 않는다.

## 헤더 drag와 캔버스 크기 유지

[Pointer Events Level 3](https://www.w3.org/TR/pointerevents3/#pointer-capture)는 pointer capture가 일반 hit test 대상 대신 지정한 요소로 이후 pointer event를 보내며 `pointerup` 또는 `pointercancel` 뒤 해제된다고 정의한다. 헤더에서 이동 후보를 시작하고 이름 있는 이동 거리 기준을 넘은 경우에만 drag로 확정하면 pointer가 헤더 밖으로 나가도 동작을 이어가면서 한 번 클릭과 구분할 수 있다.

drag로 확정한 뒤에는 같은 연속 입력에서 생기는 호환 `click`과 `dblclick`을 실행하지 않는다. 패널을 여는 동작도 `pointerdown`이나 이동 중 상태 변화가 아니라 drag가 아니었던 `dblclick`의 직접 event handler에서 실행한다. [React의 이벤트 응답 지침](https://react.dev/learn/responding-to-events)과 [이벤트와 Effect 분리 지침](https://react.dev/learn/separating-events-from-effects)은 특정 사용자 입력 결과를 event handler에서 처리하고, 렌더링 상태를 관찰하는 Effect로 다시 추론하지 말라고 설명한다.

[Resize Observer](https://www.w3.org/TR/resize-observer/)는 관찰한 요소의 계산 크기가 달라진 뒤 알림을 보낸다. 오른쪽 패널을 나란한 열로 추가하면 캔버스의 inline size가 달라지고 관찰 결과도 다시 계산될 수 있다. 따라서 drag 세션 동안 오른쪽 패널의 표시 여부, 캔버스 열 정의와 스크롤 정책을 애플리케이션 동작으로 바꾸지 않고, 시작 때 측정한 캔버스 크기와 좌표 변환 기준으로 메모 위치를 계산한다. 실제 브라우저 창 자체의 외부 resize까지 막는다는 뜻은 아니다.

## `Command` 상태의 헤더 비노출

[UI Events](https://www.w3.org/TR/uievents/#events-mouseevents)는 macOS의 Command 상태를 `metaKey`로 제공한다. 포인터 입력의 실제 `metaKey`를 복사와 선택 억제의 최종 근거로 사용하고, `keydown`과 `keyup`은 선택 해제와 헤더의 가시 상태를 바꾸는 데 사용한다. 시스템 단축키, 탭 전환이나 창 비활성화로 `keyup`을 받지 못할 수 있으므로 [HTML Standard의 문서 가시성 상태](https://html.spec.whatwg.org/multipage/interaction.html#page-visibility)와 창 `blur`에서도 눌린 상태를 초기화해야 한다.

[CSS Display Level 4](https://www.w3.org/TR/css-display-4/#visibility)는 `display: none`이 요소를 box tree에서 제거하는 반면 `visibility: hidden`은 보이지 않는 box가 layout에 계속 영향을 주도록 정의한다. 보이지 않는 box는 pointer로 조작할 수 없고 탐색에서도 빠진다. 이번 헤더는 이 성질처럼 시각 요소와 조작을 숨기되 헤더 행의 높이를 유지해 본문과 메모 외곽 크기를 움직이지 않게 한다. 다만 `Command`를 누른 순간 헤더 아이콘에 키보드 포커스가 있었다면 포커스 표시가 사라질 수 있으므로, 메모 바깥쪽의 `focus-visible` 표시 유지와 key release 뒤 복원을 실제 지원 브라우저에서 검증해야 한다.

## 좌표와 크기 입력

승인된 요구사항은 메모 표면의 상시 설정 버튼을 없애고, 오른쪽 속성 패널의 수치 입력과 캔버스 가장자리 및 꼭짓점 drag를 함께 제공한다. 이 병행 방식은 pointer drag가 어려운 사용자가 같은 위치 및 크기 결과를 만들 수 있게 하며, 특정 디자인 도구의 화면 구성을 근거로 추가 속성을 확장하지 않는다.

현재 범위에서 패널에 필요한 최소 속성은 다음 네 가지다.

- 작업 공간 좌표 X와 Y
- 메모 너비와 높이

겹침 순서와 삭제는 기존 헤더 아이콘 동작을 유지한다. 회전, 정렬, 비율 잠금과 수식 입력은 새 요구에 포함되지 않는다.

[HTML Standard의 입력 event 규칙](https://html.spec.whatwg.org/multipage/input.html#common-input-element-events)은 `input`이 사용자가 값을 바꿀 때 발생하고 `change`는 값을 확정하거나 제어가 포커스를 잃을 때 발생한다고 설명한다. [UI Events의 focus event 규칙](https://www.w3.org/TR/uievents/#events-focusevent-event-order)은 `blur`와 bubbling되는 `focusout`을 구분한다. 패널 밖 클릭은 결국 패널 입력의 포커스 이탈을 만들 수 있으므로 별도 document 클릭 저장과 입력 `blur` 저장을 각각 수행하면 같은 값을 두 번 적용할 수 있다.

구현 계획은 다음 책임을 분리해야 한다.

- 입력 중에는 X, Y, 너비와 높이를 문자열 초안으로 유지한다.
- `blur`, 패널 밖 클릭과 `Enter`는 하나의 멱등적인 적용 명령을 호출한다.
- 적용 명령은 속성 패널 대상 메모의 revision과 입력값을 검증하고, 유효하며 실제로 달라진 geometry만 저장한다.
- 패널 밖 클릭으로 다른 메모를 선택하려는 경우 이전 메모의 유효한 초안을 먼저 적용한 뒤 선택을 바꾼다.
- geometry 저장은 전체 revision만 바꾸고 content revision은 유지한다.

입력값은 유한한 수이고 `0`보다 커야 한다. 각 필드의 애플리케이션 상한도 같은 검증 절차에서 적용하되 정확한 수치는 지원 브라우저와 보드 성능을 측정한 뒤 요구사항 책임자가 승인해야 한다. HTML `min`과 `max`는 즉시 피드백에 사용하고 application command가 같은 범위를 다시 검증한다. 기존 좌표 `0` record를 새 입력 규칙 때문에 읽지 못하게 만들지 않으며 migration은 별도로 결정한다. 잘못된 입력에서 `Escape`가 수행할 일은 아직 정하지 않았다.

## 두 오른쪽 패널의 활성 순서

[모바일 일괄 복사 확인과 오른쪽 패널 우선순위 조사](mobile-batch-copy-confirmation-and-panel-priority-research.md)는 패널 종류를 자료 존재 여부가 아니라 승인된 사용자 동작으로 정하는 방식을 검토했다.

- 이동으로 판정되지 않은 헤더 더블클릭 또는 선택된 메모의 선택 지점에서 실행한 `Enter`는 속성 패널을 활성화한다.
- 한 번의 헤더 클릭과 `Tab`은 선택만 바꾸고 최근 활성 패널을 바꾸지 않는다.
- 빈 캔버스 클릭, `Escape`와 `Command`는 선택만 해제하고 최근 활성 패널을 바꾸지 않는다.
- `Command+Option+클릭`, 일괄 복사 항목 추가 또는 일괄 복사 제어 실행은 일괄 복사 패널을 활성화한다.
- 패널을 바꾸기 전에 속성 입력의 적용 계기가 생기면 공통 적용 명령을 실행한다. 잘못된 초안은 저장하지 않고 실행 중 상태에 남긴다.
- 패널 전환은 선택한 메모, 속성 패널 대상과 일괄 복사 항목을 지우지 않는다.

최근 활성 패널을 닫았을 때 이전 패널을 다시 표시할지 아무 패널도 표시하지 않을지는 아직 결정하지 않았다.

## 제거 결과와 취소 동작

[Apple의 Undo and redo 지침](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo)은 되돌릴 결과를 예측할 수 있게 이름 붙이고 복원된 결과를 확인할 수 있게 하라고 한다. 메모 제거 알림의 `취소`는 방금 제거한 메모를 되돌린다는 문맥 안에 있으므로 짧은 동작 이름으로 사용할 수 있다. 복원은 원문만 다시 만드는 것이 아니라 제거 전 geometry와 겹침 순서를 함께 되돌려야 한다.

[Fluent 2 Toast 지침](https://fluent2.microsoft.design/components/web/react/core/toast/usage)은 알림을 주 콘텐츠를 덜 가리는 일관된 위치에 두고, 사용자가 수행할 동작이 있는 알림을 단순 시간제 확인 알림과 다르게 다루라고 한다. [Carbon Notification 지침](https://carbondesignsystem.com/components/notification/usage/)은 동작이 있는 알림에는 하나의 명확한 버튼을 제공하고 사용자가 조작할 수 있도록 자동으로 너무 빨리 닫지 말라고 한다. 화면 중앙 하단이라는 승인된 위치는 이 애플리케이션의 메모 작업 주 영역을 기준으로 고정하되 상단 탐색, 오른쪽 패널과 캔버스 좌표 변환에는 속하지 않아야 한다.

[WAI의 `role=status` 기법](https://www.w3.org/WAI/WCAG21/Techniques/aria/ARIA22)은 상태 문구를 포커스 이동 없이 polite live region으로 전달할 수 있다고 설명한다. 제거 결과는 긴급 오류가 아니므로 문구를 이 방식으로 알리고, `취소`는 일반 버튼으로 다음 Tab 순서에서 접근하게 하는 구성이 적합하다. 알림이 나타났다는 이유로 현재 포커스를 `취소`로 옮기면 메모 편집과 키보드 탐색이 중단된다.

삭제한 메모 자체가 포커스를 갖고 있었다면 단순히 DOM에서 없애서는 안 된다. WAI 키보드 지침은 삭제 뒤 다음 항목 또는 논리적인 조작으로 포커스를 옮겨 문서 본문으로 잃지 않게 하라고 한다. 다음 메모, 이전 메모 또는 캔버스 제어 가운데 어느 대상을 사용할지는 메모의 Tab 순서와 함께 결정해야 한다.

## 문서와 계획에 미치는 영향

- 모바일 일괄 복사에는 `일괄 복사 상태`, 헤더의 뒤로가기, 하단 `초기화`와 횟수가 붙은 `다음`을 사용한다. `다음`은 작업 사본을 보여주는 별도 확인 페이지로 이동하고, 클릭 기록은 영구 저장 목록과 분리된 초안으로 모델링한다.
- 메모 선택, 속성 패널 대상, 보조 키 상태, 속성 초안과 제거 취소 기록은 서버 자료가 아니라 현재 애플리케이션 실행의 상태다. 빈 캔버스 클릭, `Escape`와 `Command`는 선택 ID만 비운다. `Command` 상태는 화면을 떠나거나 창 및 문서 상태가 바뀌면 즉시 해제하고 영구 저장하지 않는다. 실제 geometry 변경과 메모 제거 표시는 IndexedDB transaction이 완료된 뒤에만 성공으로 알린다.
- 직접 resize는 계속 제공하지만 키보드와 단일 pointer 사용자는 오른쪽 속성 패널에서 같은 크기 결과를 만들 수 있다. 기존의 드래그 전용 접근성 충돌 가운데 메모 크기 문제는 이 수치 입력으로 해소할 수 있다.
- 선택과 패널 표현은 실제 브라우저에서 저장된 `tabindex` 값과 Tab 이동, 선택 지점의 `Enter`, 입력기 조합, 하위 조작의 event 전파, `focus-visible`, 고대비, 한 번 클릭, `dblclick`, 빈 캔버스 클릭, `Escape`, drag 뒤 클릭 억제, pointer capture, `Command` keydown 및 keyup과 창 상태 복구, drag 중 캔버스 계산 크기, `blur`와 패널 밖 클릭을 확인해야 한다. 선택, 선택 해제와 패널 대상의 독립 전이, `tabindex` 불변 조건, geometry 검증과 제거 복원 명령만 TDD 후보가 된다.

## 아직 결정할 사항

- 새 메모의 `tabindex` 초기값과 증가 및 정리 규칙, 누락되거나 중복되거나 유효 범위를 벗어난 이전 값의 migration, 메모 뒤에 이어질 전체 문서 포커스 순서
- 선택 지점의 `Enter`로 속성 패널을 연 직후와 빈 캔버스 클릭, `Escape` 또는 `Command`로 선택을 해제한 직후의 포커스 이동
- 최근 활성 오른쪽 패널을 닫았을 때 이전 패널을 다시 표시할지
- 속성 패널 대상과 한 번 클릭으로 새로 선택한 메모가 다를 때 두 대상을 화면에서 어떻게 구분할지
- 속성 입력의 정확한 상한, 기존 `0` 좌표 record의 migration 여부, 잘못된 입력에서 포커스 이동을 막을지와 `Escape`가 초안을 되돌릴지
- 선택한 메모를 제거한 뒤 포커스와 선택을 어느 대상으로 옮길지
- 여러 메모를 연속으로 제거할 때 취소 기록과 알림을 쌓을지, 마지막 제거만 제공할지
- 제거 알림을 언제 닫고 새로고침 뒤에도 취소를 허용할지
- `Command`를 누른 순간 헤더 아이콘에 키보드 포커스가 있으면 어느 요소가 포커스를 유지하고 헤더 복원 뒤 어디로 돌아갈지

이 항목은 사용자 결과나 자료 수명을 바꾸므로 구현 담당자가 추정해 확정하지 않는다.
