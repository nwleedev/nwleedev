# 메모 선택, 속성 편집과 제거 복구 조사

## 결론

넓은 공간형 화면에서는 메모 선택과 키보드 포커스를 구분하면서 연결해야 한다. 메모는 각 선택 지점에 저장된 양의 `tabindex`가 낮은 순서대로 `Tab`에 도달하고, 헤더에 키보드 포커스가 도달하거나 사용자가 헤더를 클릭하면 단일 메모를 선택한다. 이 순서는 `zIndex`가 나타내는 시각적 겹침과 독립적이다. 선택은 얇은 붉은 테두리로 표시하고 키보드 포커스는 별도의 `focus-visible` 표시를 유지해야 한다. 선택한 메모의 X, Y, 너비와 높이는 오른쪽 속성 패널에서 수정할 수 있으며, 메모 가장자리와 꼭짓점의 직접 크기 조절도 그대로 유지한다.

속성 입력은 사용자가 편집하는 문자열과 저장된 수치 geometry를 분리해야 한다. `blur`, 패널 밖 클릭과 `Enter`는 같은 적용 명령으로 모으고, `0`보다 크며 승인된 상한 이하인 유한한 값 가운데 실제로 달라진 입력만 한 번 저장해야 한다. 잘못된 입력은 저장 자료와 revision을 바꾸지 않고 오류가 난 입력 가까이에서 고칠 방법을 알려야 한다.

오른쪽 속성 패널과 일괄 복사 패널은 마지막으로 활성화한 패널 하나만 표시한다. 메모 선택은 속성 패널을 활성화하고 일괄 복사 동작은 일괄 복사 패널을 활성화한다. 패널 전환은 선택한 메모, 속성 초안이나 일괄 복사 자료를 버리지 않는다.

메모 제거는 즉시 결과를 보여주되 되돌릴 수 있어야 한다. 메모 작업 주 영역의 중앙 하단에 `메모를 제거했습니다.`와 `취소`를 함께 표시하고, 취소하면 원문, 위치, 크기와 겹침 순서를 복원한다. 이 알림은 변환되는 캔버스 안에 두지 않는다. 실행 취소 동작을 포함하므로 단순한 시간제 성공 알림처럼 너무 빨리 없애면 안 되며, 알림이 나타날 때 현재 키보드 포커스를 빼앗지 않아야 한다.

## 조사 질문과 적용 범위

이 조사는 [개인 메모 애플리케이션 요구사항](../requirements.md)의 넓은 화면 메모 조작에 다음 결과를 추가하기 위해 수행했다.

- `Tab`으로 메모를 찾아 선택하고 헤더 클릭으로도 같은 선택을 만드는 방법
- 선택과 키보드 포커스를 시각 및 보조 기술에서 구분하는 방법
- 선택한 메모의 좌표와 크기를 오른쪽 패널에서 수정하는 방법
- `blur`, 패널 밖 클릭과 `Enter`를 중복 저장 없이 적용하는 방법
- 메모 제거 직후 취소할 수 있는 알림의 위치, 포커스와 수명
- 저장된 `tabindex`를 따르고 시각적 겹침 순서와 독립적인 메모의 `Tab` 순서
- 메모 속성 패널과 일괄 복사 패널의 최근 활성 우선순위
- 좌표 및 크기의 `0` 이하 거부와 애플리케이션 상한 검증

공식 자료는 2026년 9월 2일에 확인했다. Figma의 동작은 이 애플리케이션이 그대로 복제할 규격이 아니라, 공간형 객체를 선택하고 속성을 편집하는 정보 구조의 근거로 사용했다.

## 객체 선택과 오른쪽 속성 패널

[Figma의 객체 선택 안내](https://help.figma.com/hc/en-us/articles/360040449873-Select-layers-and-objects)는 캔버스의 객체를 클릭해 선택하고, `Tab`과 `Shift+Tab`으로 다음 및 이전 형제 객체를 선택하며, 선택한 객체의 정보가 오른쪽 속성 영역에 나타난다고 설명한다. [Figma의 오른쪽 속성 영역 안내](https://help.figma.com/hc/en-us/articles/360039832014-Design-prototype-and-explore-layer-properties-in-the-right-sidebar)는 선택한 객체의 배치와 크기를 편집할 수 있고, 아무 객체도 선택하지 않았을 때에는 객체 속성 대신 캔버스 수준 정보를 보여준다고 설명한다.

현재 애플리케이션은 왼쪽 레이어 패널을 두지 않으므로 메모 헤더가 캔버스 객체의 선택 지점이 된다. 헤더 클릭과 키보드 진입은 같은 단일 선택을 만들고, 오른쪽 패널은 선택한 메모만 대상으로 해야 한다. 본문 클릭은 상시 편집 `textarea`의 커서와 선택 범위를 다루는 기존 책임을 유지한다.

[WAI 키보드 인터페이스 지침](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)은 `Tab`과 `Shift+Tab`이 구성요소 사이의 포커스를 이동하고, 포커스와 선택은 서로 다른 상태라고 설명한다. 선택이 포커스를 따라가는 단일 선택 구성도 가능하지만 다음 조건이 필요하다.

- 현재 키보드 포커스는 항상 보이고 선택 테두리와 구분돼야 한다.
- 메모 안의 본문과 아이콘 버튼도 논리적인 순서로 도달할 수 있어야 한다.
- 메모의 양의 `tabindex`가 페이지의 기본 focusable 요소보다 먼저 탐색되는 표준 동작을 고려해 전체 문서의 포커스 순서를 검증해야 한다.
- 선택한 메모에서 속성 패널로 포커스를 옮겨도 메모 선택은 유지해야 한다.
- 선택한 메모를 제거하면 포커스가 문서 본문으로 사라지지 않도록 다음 대상을 정해야 한다.

HTML Standard는 같은 focus navigation scope 안에서 양의 `tabindex`가 낮은 요소부터 높은 요소 순으로 탐색한다고 정의한다. 현재 요구사항은 일반적인 DOM 순서 권고의 예외로 메모 사이의 순서를 명시적인 `tabindex` 값으로 관리한다. `zIndex`는 시각적 겹침만 나타내며 맨 앞으로 또는 맨 뒤로 보내기와 선택 표시를 위한 일시적 layer 변경은 `tabindex`를 바꾸지 않는다. 새 메모의 초기값, 누락되거나 중복된 이전 값의 정리와 메모 뒤에 이어질 본문, 헤더 아이콘, 오른쪽 패널 및 전역 탐색의 전체 포커스 순서는 구현 전에 결정해야 한다. 세부 근거는 [메모 Tab 순서, 항목 동작 팝오버와 모바일 지연 재정렬 조사](tab-order-popover-and-mobile-reorder-research.md)에 기록했다.

사용자가 요청한 얇은 붉은 테두리는 선택 표시다. [WCAG 2.2 Focus Appearance 설명](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)은 키보드 포커스 표시의 면적과 대비를 다루며, [Use of Color 설명](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)은 색만으로 상태를 전달하지 말라고 한다. 따라서 붉은색 자체만 바꾸는 대신 이전에 없던 테두리 형태를 추가하고, 고대비 환경에서도 선택을 구분할 대체 표현을 제공한다. 별도의 포커스 외곽선은 선택 테두리보다 충분히 두껍고 인접 색과 구분돼야 한다.

## 좌표와 크기 입력

[Figma의 위치 및 크기 조절 안내](https://help.figma.com/hc/en-us/articles/360039956914-Adjust-alignment-rotation-position-and-dimensions)는 객체의 왼쪽 위를 기준으로 X와 Y를 표시하고, 오른쪽 패널의 X, Y, W, H 필드와 캔버스 가장자리 및 꼭짓점 drag를 모두 제공한다. 이 병행 방식은 메모 표면의 상시 설정 버튼을 없애면서 pointer drag가 어려운 사용자가 수치로 위치와 크기를 바꿀 수 있게 한다.

현재 범위에서 패널에 필요한 최소 속성은 다음 네 가지다.

- 작업 공간 좌표 X와 Y
- 메모 너비와 높이

겹침 순서와 삭제는 기존 헤더 아이콘 동작을 유지한다. 회전, 정렬, 비율 잠금과 Figma의 수식 입력은 새 요구에 포함되지 않는다.

[HTML Standard의 입력 event 규칙](https://html.spec.whatwg.org/multipage/input.html#common-input-element-events)은 `input`이 사용자가 값을 바꿀 때 발생하고 `change`는 값을 확정하거나 제어가 포커스를 잃을 때 발생한다고 설명한다. [UI Events의 focus event 규칙](https://www.w3.org/TR/uievents/#events-focusevent-event-order)은 `blur`와 bubbling되는 `focusout`을 구분한다. 패널 밖 클릭은 결국 패널 입력의 포커스 이탈을 만들 수 있으므로 별도 document 클릭 저장과 입력 `blur` 저장을 각각 수행하면 같은 값을 두 번 적용할 수 있다.

구현 계획은 다음 책임을 분리해야 한다.

- 입력 중에는 X, Y, 너비와 높이를 문자열 초안으로 유지한다.
- `blur`, 패널 밖 클릭과 `Enter`는 하나의 멱등적인 적용 명령을 호출한다.
- 적용 명령은 선택한 메모 revision과 입력값을 검증하고, 유효하며 실제로 달라진 geometry만 저장한다.
- 패널 밖 클릭으로 다른 메모를 선택하려는 경우 이전 메모의 유효한 초안을 먼저 적용한 뒤 선택을 바꾼다.
- geometry 저장은 전체 revision만 바꾸고 content revision은 유지한다.

입력값은 유한한 수이고 `0`보다 커야 한다. 각 필드의 애플리케이션 상한도 같은 검증 절차에서 적용하되 정확한 수치는 지원 브라우저와 보드 성능을 측정한 뒤 요구사항 책임자가 승인해야 한다. HTML `min`과 `max`는 즉시 피드백에 사용하고 application command가 같은 범위를 다시 검증한다. 기존 좌표 `0` record를 새 입력 규칙 때문에 읽지 못하게 만들지 않으며 migration은 별도로 결정한다. 잘못된 입력에서 `Escape`가 수행할 일은 아직 정하지 않았다.

## 두 오른쪽 패널의 활성 순서

[모바일 일괄 복사 확인과 오른쪽 패널 우선순위 조사](mobile-batch-copy-confirmation-and-panel-priority-research.md)는 Figma의 문맥 속성 영역과 현재 화면을 비교해 패널 종류를 자료 존재 여부가 아니라 최근 사용자 동작으로 정하는 방식을 검토했다.

- 헤더 클릭 또는 `Tab`으로 메모가 선택되면 속성 패널이 활성화된다.
- `Command+Option+클릭`, 일괄 복사 항목 추가 또는 일괄 복사 제어 실행은 일괄 복사 패널을 활성화한다.
- 패널을 바꾸기 전에 속성 입력의 적용 계기가 생기면 공통 적용 명령을 실행한다. 잘못된 초안은 저장하지 않고 실행 중 상태에 남긴다.
- 패널 전환은 선택한 메모와 일괄 복사 항목을 지우지 않는다.

최근 활성 패널을 닫았을 때 이전 패널을 다시 표시할지 아무 패널도 표시하지 않을지는 아직 결정하지 않았다.

## 제거 결과와 취소 동작

[Apple의 Undo and redo 지침](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo)은 되돌릴 결과를 예측할 수 있게 이름 붙이고 복원된 결과를 확인할 수 있게 하라고 한다. 메모 제거 알림의 `취소`는 방금 제거한 메모를 되돌린다는 문맥 안에 있으므로 짧은 동작 이름으로 사용할 수 있다. 복원은 원문만 다시 만드는 것이 아니라 제거 전 geometry와 겹침 순서를 함께 되돌려야 한다.

[Fluent 2 Toast 지침](https://fluent2.microsoft.design/components/web/react/core/toast/usage)은 알림을 주 콘텐츠를 덜 가리는 일관된 위치에 두고, 사용자가 수행할 동작이 있는 알림을 단순 시간제 확인 알림과 다르게 다루라고 한다. [Carbon Notification 지침](https://carbondesignsystem.com/components/notification/usage/)은 동작이 있는 알림에는 하나의 명확한 버튼을 제공하고 사용자가 조작할 수 있도록 자동으로 너무 빨리 닫지 말라고 한다. 화면 중앙 하단이라는 승인된 위치는 이 애플리케이션의 메모 작업 주 영역을 기준으로 고정하되 상단 탐색, 오른쪽 패널과 캔버스 좌표 변환에는 속하지 않아야 한다.

[WAI의 `role=status` 기법](https://www.w3.org/WAI/WCAG21/Techniques/aria/ARIA22)은 상태 문구를 포커스 이동 없이 polite live region으로 전달할 수 있다고 설명한다. 제거 결과는 긴급 오류가 아니므로 문구를 이 방식으로 알리고, `취소`는 일반 버튼으로 다음 Tab 순서에서 접근하게 하는 구성이 적합하다. 알림이 나타났다는 이유로 현재 포커스를 `취소`로 옮기면 메모 편집과 키보드 탐색이 중단된다.

삭제한 메모 자체가 포커스를 갖고 있었다면 단순히 DOM에서 없애서는 안 된다. WAI 키보드 지침은 삭제 뒤 다음 항목 또는 논리적인 조작으로 포커스를 옮겨 문서 본문으로 잃지 않게 하라고 한다. 다음 메모, 이전 메모 또는 캔버스 제어 가운데 어느 대상을 사용할지는 메모의 Tab 순서와 함께 결정해야 한다.

## 문서와 계획에 미치는 영향

- 모바일 일괄 복사에는 `일괄 복사 상태`, 헤더의 뒤로가기, 하단 `초기화`와 횟수가 붙은 `다음`을 사용한다. `다음`은 작업 사본을 보여주는 별도 확인 페이지로 이동하고, 클릭 기록은 영구 저장 목록과 분리된 초안으로 모델링한다.
- 메모 선택, 속성 초안과 제거 취소 기록은 서버 자료가 아니라 현재 애플리케이션 실행의 상태다. 실제 geometry 변경과 메모 제거 표시는 IndexedDB transaction이 완료된 뒤에만 성공으로 알린다.
- 직접 resize는 계속 제공하지만 키보드와 단일 pointer 사용자는 오른쪽 속성 패널에서 같은 크기 결과를 만들 수 있다. 기존의 드래그 전용 접근성 충돌 가운데 메모 크기 문제는 이 수치 입력으로 해소할 수 있다.
- 선택과 패널 표현은 실제 브라우저에서 저장된 `tabindex` 값과 실제 Tab 이동, `focus-visible`, 고대비, 헤더 click, drag, `blur`, 패널 밖 클릭과 `Enter`를 확인해야 한다. 순수 `tabindex` 불변 조건, geometry 검증과 제거 복원 명령만 TDD 후보가 된다.

## 아직 결정할 사항

- 새 메모의 `tabindex` 초기값과 증가 및 정리 규칙, 누락되거나 중복되거나 유효 범위를 벗어난 이전 값의 migration, 메모 뒤에 이어질 전체 문서 포커스 순서
- 빈 캔버스를 클릭하거나 `Escape`를 누를 때 선택을 해제할지
- 최근 활성 오른쪽 패널을 닫았을 때 이전 패널을 다시 표시할지
- 속성 입력의 정확한 상한, 기존 `0` 좌표 record의 migration 여부, 잘못된 입력에서 포커스 이동을 막을지와 `Escape`가 초안을 되돌릴지
- 선택한 메모를 제거한 뒤 포커스와 선택을 어느 대상으로 옮길지
- 여러 메모를 연속으로 제거할 때 취소 기록과 알림을 쌓을지, 마지막 제거만 제공할지
- 제거 알림을 언제 닫고 새로고침 뒤에도 취소를 허용할지

이 항목은 사용자 결과나 자료 수명을 바꾸므로 구현 담당자가 추정해 확정하지 않는다.
