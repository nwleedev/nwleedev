# 삭제 메모의 zIndex 보존 적용 조사

복원 시 삭제 전 `zIndex`를 그대로 저장하고 중복을 허용한다. 현재 복원 및 일반 저장 코드는 이 방식과 맞으므로 우선 요구사항의 전역 고유성 조건과 테스트 기대값을 바꿔야 한다. 중복 해소를 위한 새 저장 형식이나 데이터베이스 버전 변경은 필요하지 않다는 것이 현재 코드 조사 결론이다. 구현 완료 판정에는 별도 실행 증거가 필요하다.

2026년 9월 13일에 [삭제 복원 결정](../decisions/note-removal-recovery.md), 운영 복원 함수, 메모 저장소, migration, 화면 및 앞뒤 이동 함수를 비교했다. 결정된 내용은 삭제 전 숫자 보존과 중복 허용이다. 아래의 화면 영향은 CSS 규칙과 코드로 도출한 분석이며 브라우저 실행 결과가 아니다.

## 저장과 다시 읽기

`apps/notes/src/_pages/notes/model/notes-data-provider.tsx`의 `restoreNote`는 전달받은 스냅샷을 저장하고 성공 뒤 목록에 추가한다. `apps/notes/src/entities/note/api/indexed-db-note-repository.ts`는 ID를 키로 `put`하며 일반 읽기에서 겹침 값을 정규화하지 않는다. 메모 스키마는 양의 안전 정수를 검사하지만 메모 간 `zIndex` 중복을 검사하지 않는다.

`open-personal-notes-database.ts`의 메모 store에는 `zIndex` 고유 index가 없다. [IndexedDB 표준](https://w3c.github.io/IndexedDB/#index-construct)은 “unique flag”가 설정된 index의 중복 키를 제한한다. 현재 메모 store의 키는 ID이므로 같은 `zIndex`를 가진 서로 다른 메모를 저장하기 위해 schema를 바꿀 이유는 없다.

일반 재조회와 새로고침에서도 저장한 중복 값이 남아야 한다. 복원 후 새로고침으로 사라지는 것은 실행 중 삭제 이력이며, 이미 복원해 저장한 메모가 아니다. 복원 저장이 실패하면 목록 및 다른 메모를 바꾸지 않고 기존 기한 안에서 재시도할 수 있는지 확인한다.

현재 `migrate-personal-notes-database.ts`는 이전 버전 자료의 겹침 값을 `1..N`으로 바꾼다. 이는 일반 읽기와 다르다. 이번 결정만으로 이전 버전 변환을 다시 실행하거나 새 migration을 만들지 않는다. 향후 현재 버전의 자료를 변환할 때는 허용된 중복을 손상으로 분류하지 않아야 한다. 이전 migration 완료 시의 고유성 검사는 모든 실행 상태의 불변 조건으로 확대하지 않는다.

## 중복 값과 화면 표시

[CSS 겹침 규칙](https://www.w3.org/TR/CSS22/visuren.html#z-index)은 같은 stacking context의 같은 stack level을 문서 트리 순서로 그린다고 정의한다. [CSS 페인팅 순서](https://www.w3.org/TR/CSS22/zindex.html)는 이 순서를 구체화한다. 중복 숫자 자체는 CSS 오류가 아니며 같은 조건에서는 DOM에서 뒤에 있는 메모가 앞에 그려진다.

`notes-collection.tsx`는 `tabIndex`로 정렬한 메모를 화면에 전달하고 `note-card.tsx`는 저장된 값을 CSS `zIndex`에 사용한다. 서로 다른 `tabIndex`를 가진 메모가 같은 stacking context에 있으면, 같은 `zIndex` 중에서는 더 큰 `tabIndex`의 메모가 앞에 표시될 것으로 예상된다. 이는 현재 구현의 영향이지 새로 승인된 동률 표시 정책은 아니다.

복원한 메모가 반드시 최상단에 보이거나 삭제 전의 모든 상대 순서를 되찾는다고 약속해서는 안 된다. 선택과 포커스 복원은 기존대로 유지하며, 이를 위해 저장 `zIndex`를 올리지 않는다. 중복을 숨기려고 DOM 순서나 `tabIndex`를 바꾸는 수정도 이번 결정에서 도출되지 않는다.

## 다음 맨 앞 또는 맨 뒤 이동

`note-order.ts`의 명시적 이동은 중복을 포함한 목록을 `zIndex`, 생성 시각, ID로 정렬하고 대상 메모를 옮긴 뒤 전체를 `1..N`으로 배정한다. 이 기존 동작은 유지한다. 고유성과 연속성은 이 명령이 성공한 직후의 조건이며 복원 직후의 조건이 아니다. 삭제 후에는 빈 번호도 생길 수 있다.

화면의 동률 순서와 명령의 동률 정리 순서는 서로 다를 수 있다. 생성 시각과 Tab 순서가 다른 자료를 준비해 차이를 확인해야 한다. 현재 동률 정리 규칙을 유지하는 검사와 화면에서 보이는 상대 순서까지 유지하라는 요구를 구분한다. 둘이 충돌하는 자료에서 표시 또는 정렬 기준을 바꾸는 것은 별도 결정으로 남긴다. 이 문제로 숫자 보존 검사를 보류하지 않는다.

## 단계 2와 실제 저장 및 화면의 확인 사례

고정 사례는 `A=1, B=2, C=3`에서 B 삭제, A를 맨 앞으로 이동, B 복원 순서다. 이동 뒤 `C=1, A=2`이고 복원 뒤에는 `C=1, A=2, B=2`여야 한다. 복원만으로 A와 C를 다시 번호 매기지 않는다. B의 ID, 원문, 크기, 좌표, 원문 revision과 Tab 순서도 스냅샷과 같아야 한다.

일반 저장소 재연결과 새로고침 뒤에도 이 값이 남는지 확인한다. 이어서 B를 맨 앞으로 보내면 `C=1, A=2, B=3`을 한 transaction에 저장하는 기존 명령을 검사한다. 이동 저장 실패는 이전의 중복 상태를 유지해야 한다. 새 메모 생성의 최댓값 다음 번호 배정과 여러 삭제의 LIFO 복원도 함께 확인한다.

[fast-check 모델 문서](https://fast-check.dev/docs/advanced/model-based-testing/)의 명령별 판정 방식에 맞춰 공통 검사는 양의 안전 정수 및 원문 보존을 확인하고, 복원 명령은 스냅샷 숫자 일치, 명시적 이동 명령은 고유한 `1..N`을 각각 검사한다. 단순 양수 검사만으로 복원을 통과시키지 않는다. 복원 숫자를 임의로 올리는 결함을 같은 판정으로 검출하고 축소 및 재현까지 확인한다.

서비스 변경이 필요한지는 이 사례의 관찰값으로 결정한다. 현재 코드와 같은 동작을 다시 구현하지 않고, 일반 읽기나 복원에서 승인된 숫자가 바뀌는 부분을 발견한 경우에만 보완한다. 이번 조사에서는 서비스 코드와 테스트를 변경하지 않았다.
