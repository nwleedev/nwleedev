# 메모 선택 표시, 보기 제어와 캔버스 확대 조사

2026년 9월 23일 현재 구현과 1280×900 CSS px의 별도 Chromium 브라우저 컨텍스트를 대조했다. 새 메모의 두 붉은 선은 헤더 구분선 두 개가 아니라 선택 표시와 본문 포커스 표시가 서로 다른 사각형을 그린 결과다. 보기 제어가 사라지는 현상은 메모 생성 자체보다 화면 밖 메모에 포커스를 주는 순간에 발생한다. 노트북 터치패드 핀치 확대와 마우스 보조키+휠 확대는 같은 캔버스 시점 계산을 공유할 수 있지만, 브라우저와 기기에 따라 전달되는 event가 다를 수 있으므로 실제 기기 확인이 필요하다.

## 확인한 화면과 코드

- 첨부된 첫 화면에서는 선택된 메모의 바깥 네 변과 헤더 아래 가로선이 붉다. `note-card.tsx`의 메모 최상위 요소는 선택 시 `::after`에 붉은 2px 외곽선을 그린다. 같은 파일의 `textarea`는 `focus-visible`일 때 안쪽으로 3px 윤곽선을 그린다. 새 메모 생성 뒤 `use-notes-collection-interactions.ts`가 본문에 자동 포커스를 준다. 실제 Chromium 계산값에서도 새 메모의 `textarea`는 `:focus-visible`이었고, 편집기 윤곽선은 `3px` 붉은색, 메모 선택 외곽선은 `2px` 붉은색이었다. 가로선은 편집기의 윗변이며 헤더 자체에는 별도 아래쪽 테두리가 없다.
- [요구사항](../requirements.md#반드시-지킬-조건)은 선택과 키보드 포커스를 구분하도록 하며, [메모 표면 통합 계획](../plan.md#u19-메모-표면과-헤더-통합)은 헤더와 본문을 한 표면으로 보이게 한다. 새 메모에만 적용하는 붉은 선의 개수나 헤더 아래의 붉은 선을 요구하지 않는다. 선택된 새 메모에 선택 표시가 나타나는 것은 현재 생성 뒤 선택 동작의 결과다. 두 번째 내부 가로선을 그대로 유지해야 한다는 근거는 없다. 다만 키보드 포커스를 없애서는 안 된다. [W3C의 포커스 가시성 설명](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible)은 키보드 조작 위치를 볼 수 있어야 한다고 하며, 텍스트 입력 위치를 나타내는 커서도 예시로 든다.
- 첨부된 두 번째 화면에서는 왼쪽 아래 보기 제어가 보이지 않는다. `notes-board.tsx`는 보기 제어를 `overflow-hidden`인 캔버스 viewport의 자식으로 둔다. `use-notes-collection-interactions.ts`는 새 메모를 만든 뒤 본문에 기본 `focus()`를 호출한다. [HTML 요소의 focus 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/focus)에 따르면 기본 포커스 동작은 대상이 보이도록 스크롤한다. [CSS overflow 설명](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow)에 따르면 `overflow: hidden`도 포커스와 스크립트에 의해 내부 스크롤이 가능하다.
- 같은 너비의 별도 Chromium 실행에서 새 메모를 순서대로 추가하자 첫 네 개까지 viewport `scrollLeft`가 0이고 보기 제어의 왼쪽 좌표가 12px이었다. 다섯 번째 메모가 현재 보이는 영역 밖에 놓이고 본문 포커스를 받은 직후 `scrollLeft`가 818px, 보기 제어의 왼쪽 좌표가 -806px이 됐다. 제어는 삭제된 것이 아니라 내부 스크롤에 따라 화면 밖으로 이동했다. 화면이 더 좁거나 이미 시점을 이동한 경우에는 다른 메모 개수에서도 발생할 수 있다. 첨부 화면의 정확한 조작 순서는 기록되지 않았으므로 이 재현 조건이 그 화면의 유일한 발생 조건이라고 단정하지 않는다.
- 이전 [메모 표면 통합 계획](../plan.md#u19-메모-표면과-헤더-통합)은 보기 제어가 포커스를 받을 때만 viewport 스크롤을 0으로 되돌렸다. 새 메모 본문이나 키보드로 멀리 있는 메모에 포커스를 옮기는 경우에는 이 복구가 실행되지 않는다. `overflow: clip`만 적용했던 시도는 화면 밖 메모를 포커스로 드러내지 못해 채택되지 않았다. 따라서 보기 제어를 스크롤 가능한 영역 밖에 놓고 포커스를 받는 메모가 화면에 나타나도록 시점 이동을 구현해야 한다.

## 다른 캔버스 서비스에서 확인한 입력 방식

[Figma의 확대 안내](https://help.figma.com/hc/en-us/articles/360041065034-Adjust-your-zoom-and-view-options)는 터치패드 두 손가락 핀치와 벌리기, Mac `Command` 또는 Windows `Ctrl`을 누른 마우스 휠, 확대와 축소 버튼 및 맞춤 동작을 캔버스 확대 수단으로 설명한다. 캔버스의 배율과 브라우저의 인터페이스 확대도 분리한다. [Miro의 입력 안내](https://help.miro.com/hc/en-us/articles/360017731053-Using-Miro-with-a-mouse-trackpad-or-touchscreen)는 터치패드 두 손가락 이동을 보드 이동, 핀치를 확대에 사용한다. 마우스만 쓸 때에는 기본 휠 확대를 제공하지만, 터치패드 모드에서는 `Ctrl` 또는 `Command`+휠 확대도 안내한다. [Microsoft Whiteboard의 키보드 안내](https://support.microsoft.com/en-us/whiteboard/whiteboard-keyboard-shortcuts)는 `Alt`+`+` 및 `Alt`+`-`와 캔버스 포커스 상태의 키보드 확대 동작을 제공한다. 서비스마다 기본 휠의 뜻이 달라 이 애플리케이션에 일반 휠 확대를 요구하는 공통 규칙은 없다.

[tldraw의 카메라 설명](https://tldraw.dev/sdk-features/camera)은 화면 위치와 배율을 한 시점 상태로 관리하고, 화면 좌표와 캔버스 좌표를 변환하며, 현재 포인터 지점을 향해 확대할 수 있다고 설명한다. 이는 이 애플리케이션의 저장된 메모 좌표를 바꾸지 않고 화면 시점만 갱신하는 방법과 맞는다. tldraw의 라이브러리나 입력 설정 화면을 가져와야 한다는 뜻은 아니다.

[MDN의 wheel event 설명](https://developer.mozilla.org/en-US/docs/Web/API/Element/wheel_event)은 휠이나 터치패드 확대가 `ctrlKey`가 참인 wheel event로 전달될 수 있고, 일부 브라우저에서는 연속 event 가운데 일부만 취소할 수 있다고 설명한다. [deltaMode 설명](https://developer.mozilla.org/en-US/docs/Web/API/WheelEvent/deltaMode)은 휠 변화량의 단위가 픽셀, 줄 또는 페이지일 수 있음을 명시한다. 따라서 `ctrlKey`만으로 물리적인 핀치와 `Ctrl`+휠을 구별한다고 주장하지 않고, 두 입력에 같은 확대 결과를 적용하는 편이 타당하다. Mac `Command`+휠도 같은 결과로 연결할 수 있다. 취소 가능한 event에서만 캔버스 안의 기본 확대를 막고, 화면 밖의 브라우저 확대나 일반 휠, 메모 본문 스크롤까지 전역으로 가로채지 않아야 한다.

## 계획에 반영할 조치와 남은 확인

1. 메모 표면은 선택 표시 한 번만 accent로 그리고, 본문 포커스가 헤더 아래에 별도의 붉은 가로선을 만들지 않게 한다. 포커스가 필요한 키보드 사용자는 선택과 다른 위치 또는 형태로 현재 입력 대상을 확인할 수 있어야 한다. 실제 표현은 일반, 선택, 본문 자동 포커스, 키보드로 이동한 본문, 강제 색상 화면을 비교해 정한다. 색상만 바꾸거나 포커스 표시를 무조건 제거하지 않는다.
2. 보기 제어와 변환되는 메모 영역의 배치 책임을 분리해 보기 제어를 캔버스의 보이는 왼쪽 아래에 유지한다. 화면 밖 메모 생성, 키보드 탐색과 hash 이동에서는 브라우저의 숨은 내부 스크롤에 의존하지 않고 현재 시점으로 대상 메모를 드러낸 뒤 포커스를 준다. 프로그램이 포커스를 줄 때에는 `preventScroll`을 검토하고, 자연스러운 `Tab` 탐색에도 대상 메모가 화면에 나타나는지 확인한다. `overflow: clip` 단독 변경은 같은 실패를 되풀이한다.
3. 넓은 메모 화면에서만 터치패드 핀치와 `Command`(Mac)/`Ctrl`(Windows)+마우스 휠을 캔버스 확대와 축소의 후보 입력으로 사용한다. 두 입력 모두 포인터 아래의 캔버스 지점을 유지하며 기존 화면 배율, 맞춤과 방향 제어에 연결한다. 일반 휠, 본문 입력과 스크롤, 브라우저 인터페이스 확대는 별도로 유지한다. 휠 입력을 받지 못하는 환경에서도 기존 확대와 축소 버튼이 동작해야 한다. 실제 터치패드 입력은 Chromium, Firefox와 WebKit에서 확인하고, 차이가 확인되기 전에는 비표준 제스처 처리나 기기 판별을 추가하지 않는다.
