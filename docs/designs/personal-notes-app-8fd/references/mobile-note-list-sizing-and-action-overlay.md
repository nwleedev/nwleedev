# 모바일 메모 목록 높이와 새 메모 제어 조사

## 결론

짧은 화면에서 메모 원문의 일부가 카드 경계에 잘리는 직접 원인은 목록의 자동 크기 Grid 행이 사용 가능한 높이 안에서 줄어드는 데 있다. 카드의 본문 버튼은 내용에 필요한 높이를 유지하지만 바깥 카드가 그보다 낮아지고, 카드의 `overflow-hidden`이 넘친 부분을 가린다. 새 메모 버튼은 이미 목록과 형제 관계의 절대 배치 요소이므로 높이를 차지하는 별도 행은 없다. 다만 목록의 고정 `7rem` 하단 여백이 평상시에도 공간을 예약하고, 카드 행이 사용할 높이도 줄인다.

목록은 내용에 따라 높이가 정해지는 카드를 세로로 쌓고, 합계가 화면보다 길면 목록 자체를 스크롤해야 한다. 새 메모 버튼은 메모 수와 관계없이 목록 위에 떠 있게 두며, 평상시에는 버튼 높이만큼 항상 비우는 하단 공간을 없앤다. 일괄 복사 수집 중에는 실제 하단 작업 영역을 목록 다음에 배치하고 목록의 스크롤 영역을 그 위에서 끝내야 한다. 두 상태에 같은 하단 여백을 적용하지 않고, 마지막 메모의 원문과 수정 동작 및 실제 safe area를 상태별로 확인한다. 이는 [요구사항의 좁은 화면 메모와 새 메모 제어](../requirements.md#반드시-지킬-조건)에 따른 구현 방향이지 모든 카드를 같은 고정 높이로 바꾸는 결정이 아니다.

## 조사 질문과 현재 코드

2026년 9월 23일에 메모 내용이 아닌 표시 영역 높이가 카드 높이를 바꾸는지, 새 메모 버튼 자체가 별도 행을 만드는지 조사했다. [모바일 목록](../../../../apps/notes/src/_pages/notes/ui/mobile-note-list.tsx)은 `grid`, `h-full`, 자동 행 크기, `content-start`, `overflow-auto`, `pt-16`과 `pb-28`을 한 요소에 사용한다. [모바일 카드](../../../../apps/notes/src/_pages/notes/ui/mobile-note-card.tsx)는 바깥 `article`에서 넘침을 가리고, 안쪽 본문 버튼의 높이를 `min-h-24`와 `max-h-48`로 제한한다. 카드의 수정 링크는 우측 상단에 절대 배치되어 있다.

[모바일 작업 화면](../../../../apps/notes/src/_pages/notes/ui/mobile-notes-workspace.tsx)의 새 메모 버튼은 목록의 형제 요소이며 `position: absolute`로 작업 화면의 우측 하단에 배치된다. 평상시에는 메모가 0개여도 나타나고, 일괄 복사 수집 중에는 숨는다. [디자인 토큰](../../../../apps/notes/src/_app/styles/tokens.css)의 버튼 크기는 `3rem`, 화면 가장자리 간격은 `1rem`이다. 버튼의 위치를 메모 수로 계산하는 코드는 없다.

## 브라우저에서 확인한 크기

Next.js 16.3.3과 Tailwind CSS 4.3.3을 사용하는 현재 소스를 Playwright 1.62.1의 Chromium에서 열었다. 너비를 `390 CSS px`로 유지하고 다섯 줄짜리 메모 네 개를 화면에서 생성하고 저장했다. 높이만 바꾼 결과는 다음과 같다.

- 높이 `740px`: 본문 버튼은 각각 `164px`인데 바깥 카드는 각각 `132px`다. 목록의 `clientHeight`와 `scrollHeight`가 모두 `740px`라 잘린 내용을 목록 스크롤로 볼 수도 없다.
- 높이 `850px`: 본문 버튼은 여전히 `164px`인데 바깥 카드는 각각 `159.5px`다.
- 높이 `1000px`: 본문 버튼은 `164px`, 바깥 카드는 테두리를 포함해 `166px`다.

같은 화면에서 소스 파일을 바꾸지 않고 브라우저의 스타일만 한 항목씩 변경했다. 자동 Grid 행을 내용 최대 크기로 바꾸면 높이 `740px`에서 카드가 `166px`로 회복되고 목록의 스크롤 높이가 `876px`가 됐다. 하단 여백만 `112px`에서 `16px`로 줄이면 카드가 `156px`에 그쳐 여전히 잘렸다. 세로 Flex 목록에서 카드의 축소를 막고 하단 여백을 `16px`로 두면 카드가 `166px`이고 목록 스크롤 높이가 `780px`였다. 따라서 큰 하단 여백은 증상을 악화하지만, 카드 압축의 근본 원인은 자동 행 또는 항목 축소를 허용한 목록 배치다.

`pb-28`은 `112px`의 내부 여백이며 버튼 요소가 만든 별도 행은 아니다. 현재 평상시와 일괄 복사 수집 중 모두에 적용되지만, 수집 중에는 `초기화`와 `다음`이 들어 있는 실제 하단 작업 영역을 피하는 용도로도 쓰인다. 메모 수가 적어 콘텐츠 높이가 화면보다 짧으면 마지막 카드 아래에 화면의 남은 높이도 보인다. 그 빈 영역 전부를 버튼 높이 또는 하단 여백 탓으로 돌릴 수 없다. 모든 카드를 남는 높이만큼 늘려 빈 곳을 채우면 내용별 높이라는 현재 요구와 충돌한다.

## 표준과 구현 선택

[CSS Grid의 자동 행과 항목 최소 크기](https://www.w3.org/TR/css-grid-2/#auto-tracks)는 자동 행이 고정된 목록 높이 안에서 내용의 원하는 높이와 다르게 계산될 수 있음을 설명한다. [CSS Flexible Box Layout의 `flex: none`](https://www.w3.org/TR/css-flexbox-1/#flex-common)은 항목이 남는 공간에 따라 늘거나 줄지 않게 한다. [Tailwind CSS의 `flex-col`](https://tailwindcss.com/docs/flex-direction)과 [`flex-none`](https://tailwindcss.com/docs/flex)은 현재 스타일 기반에서 이 세로 목록을 표현할 수 있다. Grid를 유지하며 행에 내용 기준 크기를 명시하는 방법도 가능하지만, 한 방향으로 쌓는 현재 목록은 Flex와 축소 금지가 의도를 더 직접 드러낸다.

[CSS Positioned Layout](https://www.w3.org/TR/css-position-3/#absolute-position)는 절대 배치된 요소가 형제의 크기와 위치 계산에 참여하지 않는다고 정한다. 따라서 평상시 새 메모 버튼은 카드 위에 뜰 수 있지만, 현재 수집 상태의 절대 배치 하단 영역 역시 목록 높이를 줄이지 않으므로 `pb-28`로 가림을 피하고 있다. [CSS Flexible Box Layout의 세로 배치와 축소 규칙](https://www.w3.org/TR/css-flexbox-1/#flex-common)을 적용해 수집 상태의 목록과 하단 작업 영역을 같은 세로 흐름에 두면 실제 작업 영역이 차지하는 높이만큼 목록이 줄고, 그 높이를 padding으로 다시 추정할 필요가 없다. [CSS Overflow의 스크롤 영역 설명](https://www.w3.org/TR/css-overflow-3/#scrollable)에 따르면 끝 여백은 스크롤 범위에 영향을 줄 수 있으므로, 평상시에도 수집 상태의 영역 높이를 복사해 넣지 않는다. [WCAG 2.2의 포커스 가림 설명](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum)은 떠 있는 제어가 포커스를 받은 다른 조작 요소를 완전히 가리지 않아야 한다는 확인 근거다.

## 계획에 미치는 영향과 한계

- 모바일 목록, 카드의 세로 배치와 수집 상태의 하단 작업 영역 배치를 바꾼다. 미리보기의 내용별 높이, `12rem` 상한, 본문 복사, 수정 링크와 IndexedDB 자료는 유지한다. 모바일 생성 뒤 목록에 남는 동작은 [좁은 화면 표현 결정](../decisions/responsive-note-presentation.md#48rem-미만의-목록과-상세-화면)에 따라 별도 절차에서 다룬다.
- 평상시 목록에는 수집 상태의 하단 영역 높이를 예약하지 않는다. 수집 중에는 `초기화`와 `다음`을 실제 하단 영역으로 두고, 목록은 그 위에서 스크롤한다. 기존 버튼 크기와 위치 토큰 및 상단 헤더의 배치는 유지한다. 내용 수 측정 state, 높이를 맞추는 spacer와 JavaScript 높이 계산은 만들지 않는다.
- 내용이 짧은 목록, 화면을 넘는 목록, 표시 높이 변화 및 safe area가 있는 모바일 브라우저에서 카드 본문과 수정 동작을 확인한다. 자동 브라우저 검사는 실제로 보이는 카드와 버튼의 위치 관계를 확인하되 CSS class나 내부 배치 알고리즘을 고정하지 않는다.

이번 수치는 데스크톱 Chromium의 표시 영역 크기를 바꾼 결과이며 Android 브라우저 도구 모음의 실제 접힘과 기기 safe area를 그대로 재현하지 않는다. 그 환경에서 마지막 카드의 수정 링크와 새 메모 버튼이 모두 눌리는지는 구현 뒤 실제 기기에서 확인해야 한다.
