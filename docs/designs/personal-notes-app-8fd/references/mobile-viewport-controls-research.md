# 모바일 표시 영역과 뒤로가기 제어 조사

## 결론

모바일 하단 동작이 목록 및 편집 영역 바로 뒤에 나타나는 원인은 동작 영역의 위치 지정 방식이 아니라 공통 application frame의 CSS Grid 자동 배치다. frame은 동적 표시 영역 높이를 올바르게 사용하고 있지만, 좁은 메모 화면에서 탐색 요소가 `display: none`이 되면 콘텐츠가 남은 높이 행이 아니라 첫 번째 자동 높이 행에 들어간다. 콘텐츠 높이로 축소된 상위 요소를 기준으로 상세 저장 영역과 일괄 복사 하단 동작이 배치되므로 기기 화면 아래쪽에 남지 않는다.

해결 방향은 콘텐츠를 frame의 두 번째 Grid 행에 명시적으로 배치하고 기존 내부 스크롤과 safe area 처리를 유지하는 것이다. 하단 동작에 별도 `position: fixed`를 추가하거나 동적 표시 영역 단위를 다른 높이로 바꾸면 공통 원인을 남긴 채 화면마다 보정 코드가 늘어난다.

뒤로가기는 외곽 테두리가 없는 조용한 아이콘 동작으로 표시하고, 화면 이동용 아이콘을 보드 시점 이동용 방향 아이콘과 분리한다. 공용 아이콘 하나의 모양을 바꾸면 회전해서 사용하는 보드 방향 제어까지 함께 바뀌므로 의미가 다른 두 사용처를 같은 구성요소로 유지하지 않는다.

## 조사 질문과 범위

2026년 9월 23일 기준으로 다음 질문을 조사했다.

- 동적 모바일 표시 영역 높이를 사용하면서도 하단 동작이 부모 요소 높이에 붙는 이유는 무엇인가.
- 메모 목록, 상세와 일괄 복사 화면의 현재 동작을 유지하면서 어느 공통 요소를 수정해야 하는가.
- 뒤로가기와 보드 방향 이동이 같은 화살표를 공유해도 되는가.

배포된 모바일 화면, 현재 소스와 CSS 표준을 비교했다. 새로운 전역 탐색, 하단 탐색 막대와 화면별 고정 footer는 범위에 포함하지 않았다.

## 저장소와 실행 화면에서 확인한 사실

`ApplicationFrame`은 메모 과업에서 `h-dvh`와 `grid-rows-[auto_minmax(0,1fr)]`를 사용한다. 좁은 메모 화면에서는 첫 번째 자식인 전역 탐색이 `display: none`이고 두 번째 자식인 콘텐츠 wrapper에는 명시적인 Grid 행이 없다. CSS Grid 자동 배치에 따라 남은 콘텐츠가 첫 번째 행에 배치되고, 두 번째 남은 높이 행은 비어 있게 된다.

배포된 화면을 360 × 720 CSS px 표시 영역에서 확인했을 때 frame 높이는 720px로 `window.innerHeight`와 같았다. 그러나 메모 상세 콘텐츠 wrapper는 386px, 일괄 복사 수집 화면의 wrapper는 274px에 그쳤다. 상세 저장 영역과 수집 화면 하단 동작은 각 wrapper의 아래쪽에 정확히 배치됐다. 따라서 `dvh` 계산이나 하단 동작 자체가 아니라 콘텐츠 wrapper가 첫 번째 자동 높이 행에 들어간 것이 직접 원인이다.

현재 `ArrowBackIcon`은 메모 상세, 일괄 복사 상태 및 확인 화면의 뒤로가기뿐 아니라 보드 시점을 네 방향으로 움직이는 제어에도 회전해 사용한다. 메모 상세의 링크만 별도 테두리, 채운 배경과 테두리 hover를 사용하고 있어 같은 화면의 다른 아이콘 전용 동작과 표현도 일치하지 않는다.

## 표준과 공식 지침

[CSS Grid Layout Module Level 2](https://www.w3.org/TR/css-grid-2/)의 자동 배치 절차는 행이나 열 위치가 정해지지 않은 Grid item을 사용 가능한 첫 위치부터 배치한다. `display: none`인 탐색은 Grid item을 만들지 않으므로 콘텐츠의 행을 명시하지 않으면 첫 번째 자동 높이 행에 들어갈 수 있다. 콘텐츠에 두 번째 행을 지정하면 탐색의 표시 여부와 무관하게 남은 높이 행을 사용한다.

[CSS Values and Units Module Level 4](https://www.w3.org/TR/css-values-4/)는 `dvh`를 브라우저 UI 변화에 따라 달라지는 동적 표시 영역 크기로 정의한다. 실행 화면에서도 frame 높이가 `innerHeight`와 일치했으므로 현재 단위를 유지하는 것이 타당하다.

[Android 웹 콘텐츠의 window inset 안내](https://developer.android.com/develop/ui/views/layout/webapps/understand-window-insets)는 웹 콘텐츠가 시스템 UI와 겹치지 않도록 inset과 `safe-area-inset-*` 값을 고려하도록 안내한다. 현재 하단 여백 처리는 제거하지 않고 남은 높이 행 안에서 계속 적용해야 한다.

[Android의 자동 반전 Material 아이콘 안내](https://developer.android.com/reference/kotlin/androidx/compose/material/icons/Icons.AutoMirrored)는 뒤로가기처럼 진행 방향을 나타내는 아이콘을 별도 의미로 제공하고, RTL 환경에서는 자동으로 방향을 바꾸도록 한다. 현재 애플리케이션에서 화면 이동은 이전 화면을 열고 보드 시점 이동은 캔버스의 보이는 위치를 바꾸므로, 각각의 의미를 가진 아이콘으로 나누는 편이 공용 아이콘 변경의 뜻하지 않은 영향을 줄인다.

## 계획에 미치는 영향

- `ApplicationFrame`의 콘텐츠 wrapper만 두 번째 Grid 행에 명시적으로 놓는다. route별 높이 계산, 화면별 `fixed` footer와 JavaScript 높이 측정은 추가하지 않는다.
- 메모 목록, 상세, 일괄 복사 수집 및 확인과 보조 route를 좁고 넓은 화면에서 다시 확인한다. 공통 frame 수정이므로 메모 상세 한 화면만 확인해서는 완료할 수 없다.
- 화면 이동용 `NavigateBackIcon`을 추가하고 메모 상세, 일괄 복사 상태와 모바일 확인 화면에 사용한다. 기존 `ArrowBackIcon`은 보드 방향 제어가 계속 사용하므로 삭제하거나 모양을 바꾸지 않는다.
- 메모 상세 링크의 테두리, 채운 배경과 테두리 hover를 제거한다. 접근 가능한 이름, 저장 전 이탈 확인과 목적 route는 유지한다.
- CSS class나 Grid 행 문자열을 검사하는 테스트는 작성하지 않는다. 실제 표시 영역 안에서 하단 동작을 계속 실행할 수 있는지와 뒤로가기가 기존 상태 및 목적 화면 이동을 보존하는지를 브라우저 과업으로 확인한다. 외곽 테두리와 아이콘의 시각적 적합성은 실제 모바일 화면 검토로 판정한다.

## 한계와 다시 확인할 조건

데스크톱 Playwright의 표시 영역 크기 변경은 모바일 브라우저 도구 모음의 모든 동작을 재현하지 못한다. 자동 검사는 서로 다른 화면 높이와 스크롤 뒤의 사용자 동작을 확인하고, 실제 Android 브라우저에서 도구 모음이 보이거나 접힌 상태와 화면 아래쪽 inset을 별도로 확인해야 한다.

명시적인 두 번째 행 배치가 좁은 보조 route의 현재 탐색 또는 넓은 화면 application bar를 가리거나 document scroll을 새로 만들면 구현을 멈추고 frame의 route 조립을 다시 조사한다. 하단 동작이 화면 키보드와 겹치면 footer를 별도로 고정하기 전에 편집 영역의 내부 스크롤과 visual viewport 변화를 먼저 확인한다.
