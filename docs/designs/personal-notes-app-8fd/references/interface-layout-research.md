# 화면 구성과 공간형 메모 상호작용 조사

## 결론

메모 화면은 크기가 정해진 페이지보다 내용이 추가될수록 확장되는 공간형 보드가 요구사항에 가장 가깝다. 사용자는 보드를 이동하고 확대해 탐색하며, 메모를 선택해 위치와 크기를 바꾸고, 화면 맞춤으로 메모가 있는 범위를 다시 찾을 수 있어야 한다. 메모 작업 영역의 너비가 작으면 같은 메모를 공간형 보드 대신 일반적인 목록 형태로 제공한다. 인쇄나 내보내기 범위가 필요해질 때 프레임을 추가하는 편이 전체 보드 크기를 먼저 정하게 하는 것보다 유사 서비스의 동작과 잘 맞는다.

일반 클릭을 복사에 사용하는 이번 애플리케이션은 유사 서비스의 클릭 편집을 그대로 적용할 수 없다. [메모 복사와 편집 동작 결정](../decisions/note-copy-and-edit.md)에 따라 읽기 본문 클릭은 복사로 유지하고, 복사, 누적과 편집 버튼을 본문과 분리해 항상 사용할 수 있게 한다. 텍스트 범위를 선택한 드래그는 전체 복사를 실행하지 않는다. 편집 중에는 본문 클릭이 커서 이동과 텍스트 선택에 쓰이고, `Escape`나 완료 버튼으로 읽기 상태로 돌아간다. 메모 본문의 URL이나 링크처럼 보이는 문자열도 링크로 바꾸지 않고 일반 텍스트로 표시하며, 일반 클릭하면 전체 원문에 포함해 복사한다.

현재 개발하는 로컬 애플리케이션은 보드, 누적 텍스트, 사용 빈도, 텍스트 겹침, 템플릿과 설정만 제공한다. 계정과 동기화 탐색 항목 및 페이지는 제공하지 않고, 겹침 화면에는 사용자가 누르는 분석 버튼을 둔다. 계정 기능을 추가하는 최우선 백로그를 시작하면 공통 화면 구조와 조작을 유지하는 방안을 다시 검증해야 한다.

라이브러리 패키지와 포트폴리오 라우트 연결은 현재 구현에서 다루지 않고 백로그로 둔다. 이 백로그를 시작하면 독립 실행 애플리케이션과 포트폴리오 라우트에 연결된 모듈이 개인 메모 내부의 정보 구조와 조작 방식을 공유하되, 바깥쪽 탐색과 개인 메모 내부 탐색이 중복되지 않도록 제공 영역을 먼저 나눠야 한다.

이 문서는 [개인 메모 애플리케이션 요구사항](../requirements.md)의 메모 편집, 자유 배치와 크기 변경, 작은 화면의 목록, 누적 설정, 클립보드 알림 및 페이지 배치를 조사한 참고 자료다. UX 설계 담당자가 흐름 초안을 만들고 결정 책임자가 상호작용을 승인할 때 사용한다.

구성요소별 시각 특징, 2026년 디자인 흐름과 AI 생성 UI의 반복 패턴은 [2026년 웹 애플리케이션 시각 디자인과 AI 생성 UI 조사](web-visual-design-research-2026.md)에서 별도로 다룬다.

작은 화면의 목록과 링크 형식 문자열을 일반 텍스트로 다루는 것은 승인된 요구사항이다. [공간형 보드와 작은 화면 목록 결정](../decisions/responsive-note-presentation.md)은 메모 컨테이너 `48rem`을 초기 전환값으로 정하고 기기 종류 판별을 제외한다. 시각적 성격과 세부 디자인 값은 아직 승인되지 않았다. 공식 도움말, 접근성 표준과 공식 화면 예시는 2026년 8월 30일에 검토했다.

## 유사 서비스에서 확인한 메모 편집 방식

### macOS Stickies

[Apple Stickies 사용 설명서](https://support.apple.com/en-euro/guide/stickies/welcome/mac)는 메모의 제목 막대를 드래그해 이동하고 가장자리를 드래그해 크기를 바꾸며, 제목 막대를 이중 클릭해 메모를 접는 동작을 안내한다. 메모 창 자체가 입력 대상이므로 별도 보기 화면을 열지 않고 바로 편집한다. 이동을 본문과 분리된 제목 영역에 맡기는 방식은 본문 클릭을 복사에 써야 하는 이번 애플리케이션에도 적용할 수 있다.

### Apple Freeform

[Freeform에서 보드 만들기](https://support.apple.com/guide/freeform/create-a-board-frfm9474646a9/mac)는 보드가 내용 추가에 따라 확장되며 페이지 형식이나 크기에 제한되지 않는다고 설명한다. [도형에 텍스트 추가하기](https://support.apple.com/guide/freeform/add-a-shape-or-line-frfm8479c716/mac)는 도형을 이중 클릭해 텍스트를 입력하는 동작을 안내하고, [항목 크기 변경하기](https://support.apple.com/en-gb/guide/freeform/frfmaec1128f/mac)는 선택한 항목의 핸들을 드래그해 크기를 바꾸는 방식을 설명한다.

[Freeform 보드 보기 변경하기](https://support.apple.com/en-gb/guide/freeform/frfm000074a4e/mac)는 확대, 축소, 선택 항목으로 이동, 콘텐츠 전체 맞춤, Space 키를 누른 채 드래그하는 pan과 점 격자를 제공한다. 공식 화면 예시에서도 도구는 상단에, 보드 탐색과 zoom은 보드 가장자리의 작은 제어 영역에 배치되어 콘텐츠 공간을 우선한다.

### FigJam

[FigJam 파일 둘러보기](https://help.figma.com/hc/en-us/articles/15300412458647-Explore-FigJam-files)는 하나의 무한 보드, pan과 zoom, 파일 패널과 주 도구 막대로 화면을 나눈다. [FigJam 스티커 메모 도움말](https://help.figma.com/hc/en-us/articles/1500004414322-Sticky-notes-in-FigJam)은 스티커를 선택한 뒤 입력하고, 내용에 따라 세로로 커지며, 옆면이나 모서리를 드래그해 폭 또는 전체 크기를 바꾸는 동작을 설명한다. [화면 읽기 프로그램으로 FigJam 사용하기](https://help.figma.com/hc/en-us/articles/14477051168791-Use-FigJam-with-a-screen-reader)는 항목을 선택하고 `Enter`로 편집하는 키보드 흐름을 안내한다.

이 사례는 선택 상태와 편집 상태를 나눌 수 있고, 선택 뒤 `Enter`가 편집 진입으로 이해될 수 있음을 보여준다.

### Miro

[Miro 보드 콘텐츠 구조화 도움말](https://help.miro.com/hc/en-us/articles/360017730973-Structuring-board-content)은 보드가 끝없이 확장되며 프레임으로 콘텐츠를 묶고 발표나 내보내기 순서를 정하는 방식을 설명한다. [Miro 스티커 메모 도움말](https://help.miro.com/hc/en-us/articles/360017572054-Sticky-notes)은 스티커를 선택해 입력하고 선택 상태의 제어 UI로 크기와 모양을 바꾸는 동작을 안내한다. [Miro 프레임 도움말](https://help.miro.com/hc/en-us/articles/360018261813-Frames)은 무한 보드 안에 정해진 영역을 만들고 콘텐츠를 구성하는 별도 수단을 제공한다.

이 사례는 보드 전체의 페이지 크기를 사용자가 먼저 지정하지 않아도, 나중에 프레임으로 작업 영역이나 출력 범위를 만들 수 있음을 보여준다.

### Google Keep과 Microsoft Sticky Notes

[Google Keep의 메모 수정 도움말](https://support.google.com/keep/answer/2888246?co=GENIE.Platform%3DDesktop&hl=en-GB)은 목록이나 그리드에서 메모를 클릭해 편집 화면을 열고 실행 취소와 다시 실행을 제공한다. [Google Keep의 화면 읽기 프로그램 도움말](https://support.google.com/keep/answer/16914649?hl=en)은 `Enter`로 메모를 편집하고 `Escape`로 나오는 흐름을 설명한다. Keep은 클릭을 복사에 쓰지 않으므로 클릭 편집을 그대로 가져올 수 없지만, 편집 진입과 종료 상태를 구분하는 참고가 된다.

[Microsoft Sticky Notes 시작 안내](https://support.microsoft.com/en-us/windows/apps/stickynotes/get-started-with-sticky-notes)는 메모 상단을 드래그해 이동하고 가장자리를 드래그해 크기를 바꾸며 위치를 기억한다고 설명한다. Apple Stickies와 마찬가지로 이동 영역과 크기 조절 가장자리가 구분된다.

## 편집, 복사와 이동을 충돌 없이 나누는 결정

### 기본 상태

- 메모 본문을 일반 click하면 메모를 선택하고 전체 원문을 복사한다. 텍스트 범위를 선택한 drag는 복사를 실행하지 않는다.
- 메모 안의 URL이나 링크처럼 보이는 문자열도 일반 텍스트로 표시하며, 본문을 일반 클릭하면 전체 원문에 포함해 복사한다.
- URL 형식 문자열을 자동으로 링크 요소로 바꾸거나 미리보기를 붙이지 않는다.
- 메모의 제목 또는 전용 이동 손잡이를 드래그하면 위치를 바꾼다.
- 메모에는 hover 없이 접근할 수 있는 복사, 누적과 편집 버튼을 두고, 선택되면 테두리와 크기 조절 핸들을 보여준다.
- 복사 성공은 짧은 상태 알림으로 알리고 키보드 focus는 옮기지 않는다.

### 편집 상태

- 편집 버튼을 실행해 편집을 시작한다. 버튼은 `Enter`와 `Space`로도 실행할 수 있다.
- 편집 중 본문 클릭은 커서 이동과 범위 선택에 사용하며 복사를 실행하지 않는다.
- `Escape` 또는 완료 버튼으로 편집을 마치고 기본 상태로 돌아간다.
- 편집 중 이동은 제목 또는 전용 손잡이에서만 시작해 텍스트 선택과 구분한다.

브라우저의 이중 클릭은 앞선 클릭 이벤트를 포함하므로 일반 클릭 복사를 즉시 실행하면 편집 전에 한 번 이상 복사될 수 있다. 복사를 늦춰 이중 클릭 여부를 기다리면 단일 클릭의 즉시성이 떨어진다. 따라서 명시적 편집 버튼을 기본으로 삼고 이중 클릭 편집은 제공하지 않는다. `Enter`와 `Space`는 현재 포커스를 받은 버튼의 이름대로 동작한다.

### 크기 변경

- 선택 상태의 가장자리와 모서리 핸들을 드래그해 메모 크기를 바꾼다.
- 키보드와 정밀 조작을 위해 선택한 메모의 위치와 크기를 숫자 및 단계 조절 UI로 바꿀 수 있게 한다.
- 최소 폭과 높이는 편집 버튼, 이동 손잡이와 알림 상태가 겹치지 않는 값으로 시각 검증 뒤 정한다.
- 내용이 사용자가 정한 메모 크기를 넘으면 메모 안에서 스크롤한다.

## 보드 크기와 탐색 결정

Freeform, FigJam과 Miro는 고정 페이지 크기보다 내용에 따라 확장되는 보드를 사용한다. [공간형 보드와 작은 화면 목록 결정](../decisions/responsive-note-presentation.md)은 다음 동작을 현재 범위에 적용한다.

- 메모 위치와 크기는 zoom과 독립적인 작업 공간 좌표로 저장한다.
- 빈 공간 드래그나 `Space+드래그`로 pan하고, 트랙패드와 제어 UI로 zoom한다.
- `모든 메모 맞춤`은 메모들의 외곽 범위를 계산해 viewport에 맞춘다.
- 메모를 추가하면 현재 보이는 영역 안의 예측 가능한 위치에 놓는다.
- 메모가 멀리 떨어져 보이지 않을 때 보드 전체 맞춤이나 메모 검색으로 돌아올 수 있게 한다.
- 출력 범위가 필요해지면 Miro의 frame처럼 이름 붙인 영역을 후속 기능으로 검토한다.

사용자는 보드의 폭과 높이를 직접 입력하지 않는다. 고정 페이지가 필요한 인쇄, PDF 내보내기나 프레젠테이션 요구가 승인되면 frame 크기 또는 콘텐츠 외곽 범위를 출력 단위로 삼을 수 있다. 확장형 보드는 실제 무한 숫자 범위를 뜻하지 않으므로 좌표 한계, 부동소수점 정밀도와 멀리 떨어진 메모를 렌더링하지 않는 범위는 구현에서 측정한 뒤 정해야 한다.

## 페이지 공통 구성 제안

각 페이지는 접을 수 있는 왼쪽 탐색, 현재 페이지의 제목과 주요 동작을 담은 상단 영역, 주 콘텐츠 영역과 전체 상태 알림 영역으로 구성한다. 현재 로컬 애플리케이션의 탐색에는 보드, 누적 텍스트, 사용 빈도, 텍스트 겹침, 템플릿과 설정만 둔다. 계정 및 동기화 항목을 감추는 데 그치지 않고 해당 route도 만들지 않아야 한다.

### 백로그: 포트폴리오 라우트 연결

[로컬 실행 구조와 계정 및 라이브러리 백로그 조사](runtime-modes-and-architecture.md)는 백로그를 시작할 때 검토할 연결 방식을 제안한다. 다음 항목은 현재 화면 구현의 선행 조건이나 완료 기준이 아니다. 포트폴리오 연결 작업을 시작하면 개인 메모 UI는 자신의 주 콘텐츠와 내부 과업 구조를 유지하되, 포트폴리오 전체 탐색과 같은 바깥쪽 영역을 중복해서 그리지 않는 구성이 필요하다.

- 독립 실행 애플리케이션은 개인 메모의 최상위 탐색, 페이지 제목과 전체 상태 알림을 직접 제공할 수 있다.
- 포트폴리오 웹 애플리케이션은 포트폴리오 탐색과 라우트 위치를 제공하고, 개인 메모 모듈은 내부 페이지 탐색과 주 콘텐츠를 제공하는 방안을 검토한다.
- 호스트가 개인 메모의 각 내부 페이지를 하위 라우트로 연결하면 모듈의 탐색은 호스트 라우트 접두어를 기준으로 이동해야 한다.
- 호스트가 단일 라우트만 제공하면 누적 텍스트, 사용 빈도, 겹침 분석, 템플릿과 설정 사이의 전환을 URL에 반영할지 별도로 정해야 한다.
- theme, error boundary, loading UI와 전체 상태 알림을 호스트와 모듈이 각각 중복해서 만들지 않도록 한쪽의 책임을 승인해야 한다.

위 항목은 백로그에서 제공 영역을 비교하기 위한 제안이며, 포트폴리오 라우트에 연결된 최종 화면 구조로 승인되지 않았다.

### 넓은 화면의 메모 보드

목적은 메모 작성, 복사, 누적과 공간 배치다.

- 왼쪽 탐색에는 보드, 누적 텍스트, 사용 빈도, 텍스트 겹침, 템플릿과 설정으로 가는 항목을 둔다.
- 상단 도구 영역에는 새 메모와 모든 메모 맞춤처럼 현재 보드에 필요한 동작만 둔다.
- 중앙은 메모를 자유롭게 놓는 보드다.
- 선택한 메모의 편집, 크기와 위치 제어는 화면 오른쪽의 접을 수 있는 속성 패널 또는 메모 가까이의 상황별 조작부 가운데 하나로 제공한다.
- 확대와 보드 이동 상태는 콘텐츠를 가리지 않는 보드 모서리에 둔다.
- 누적된 항목 수는 탐색 항목의 badge나 작은 상태 표시로 보여주고, 메모 위에 지속적으로 큰 패널을 띄우지 않는다.

### 작은 화면의 메모 목록

메모 작업 container의 inline size가 `48rem` 미만이면 메모 보드 대신 생성 순서 목록을 제공한다. [WCAG 2.2 Reflow 이해 문서](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)는 정보나 기능 손실 없이 320 CSS 픽셀 너비에 해당하는 화면에서도 내용을 한 방향으로 읽을 수 있어야 한다고 설명하고, 작은 화면에서는 구획을 한 열로 재배치하는 방식을 예로 든다. 공간형 보드 자체는 이차원 배치가 필요한 영역일 수 있지만, 메모 읽기와 기본 조작까지 이차원 스크롤에 의존하게 만들 필요는 없다.

- 목록에서도 메모 작성, 편집, 일반 클릭 복사와 누적 조작을 제공한다.
- 위치 및 크기 조절 핸들, 보드 이동, 확대와 화면 맞춤처럼 공간 배치에만 필요한 제어 UI는 목록에서 표시하지 않는다.
- 목록은 같은 메모를 생성 순서로 보여주며, 목록 전환은 저장된 위치와 크기를 바꾸지 않는다. 작업 영역이 넓어지면 기존 공간 배치를 복원한다.
- 목록의 각 항목에는 메모 원문과 편집 동작을 함께 제공하고, 복사 성공과 실패 알림은 넓은 화면과 같은 방식으로 표시한다.

[CSS Containment Level 3](https://www.w3.org/TR/css-contain-3/)은 구성요소가 실제로 받은 크기에 따라 표현을 바꾸는 container query를 정의한다. 전체 뷰포트나 User-Agent가 아니라 실제 메모 영역을 기준으로 목록을 전환한다.

### 누적 텍스트

목적은 순서 편집, 제거 복구와 결합 결과 확인이다.

- 상단에는 실행 취소, 다시 실행과 결합된 전체 텍스트 복사 동작을 둔다.
- 넓은 화면에서는 왼쪽에 순서가 있는 항목 목록, 오른쪽에 구분자가 반영된 전체 미리보기를 둔다.
- 항목은 drag로 순서를 바꾸고 목록 밖에 놓으면 제거한다. 목록 밖에 있는 동안 제거 예정 상태를 표시하고 `Escape`와 `pointercancel`은 작업을 취소한다.
- 각 항목에는 드래그 없이 위로 이동, 아래로 이동과 제거를 수행할 버튼도 둔다.
- 제거 직후 상태 알림에서 실행 취소를 제공하되, 화면 상단의 이력 제어도 유지한다.

### 사용 빈도

목적은 일반 복사, 누적과 합계를 혼동 없이 비교하는 것이다.

- 각 텍스트 항목에 원문 식별 정보, 일반 복사 횟수, 누적 횟수와 계산된 합계를 같은 순서로 보여준다.
- 메모 ID, content revision과 실행 당시 원문별로 항목을 구분한다. 같은 원문을 가진 서로 다른 메모는 합치지 않는다.
- 일반 복사, 누적과 두 값에서 계산한 합계를 함께 보여준다. 기간 그래프, 순위와 마지막 갱신 시각은 현재 범위에 추가하지 않는다.

### 텍스트 겹침

목적은 줄 단위 비교를 명시적으로 실행하고 결과의 근거를 확인하는 것이다.

- 상단에는 분석 실행 버튼, 분석 대상과 마지막 완료 시점을 둔다.
- 실행 중에는 진행 상태를 제공한다.
- 결과는 정확한 반복, 포함 관계와 생김새가 일부 겹치는 후보로 나누고, 각 결과에서 두 원문 줄, 원본 메모로 이동할 동작과 `이 두 줄로 템플릿 제안` 버튼을 제공한다.
- 점수만 보여주지 않고 어떤 줄의 어느 관계인지 함께 보여준다.
- 현재 로컬 애플리케이션은 명시적 분석 버튼과 브라우저 분석기를 사용한다. 최우선 계정 및 동기화 백로그에서 서버 분석을 도입하더라도 이 화면과 조작을 유지하고 실행 위치만 교체할 수 있는지 다시 검증한다.

### 템플릿

목적은 분석 제안 검토, 직접 플레이스홀더 지정과 일회성 텍스트 생성이다.

- 템플릿 목록과 선택한 템플릿 편집 영역을 분리한다.
- 제안은 저장된 템플릿과 시각적으로 구분하고 사용자가 승인해야 템플릿 목록에 들어간다.
- 겹침 결과에서 들어오면 선택한 두 원문 줄과 원본 메모 이동 동작을 먼저 보여준다. 선택 없이 직접 들어오거나 새로고침으로 선택이 사라지면 수동 작성과 겹침 결과로 돌아가기 동작을 제공한다.
- 수동 작성은 원문에서 범위를 선택하고 `플레이스홀더로 지정` 버튼을 실행하게 한다. 편집 영역에서는 일반 텍스트와 플레이스홀더의 구분을 확인하고 플레이스홀더 이름, 순서와 일반 텍스트로 되돌리기를 제공한다.
- 일회성 생성 영역은 필요한 입력값, 완성된 미리보기와 복사 동작을 함께 보여준다.

### 설정

목적은 누적 조작이 브라우저나 운영체제 동작과 충돌할 때 다른 조작을 선택하게 하고 클립보드 문제를 진단하는 것이다.

- `Command+클릭` 추가 동작을 켜거나 끄는 UI를 둔다.
- 각 메모의 누적 버튼은 항상 유지한다. 설정은 `Command+클릭` 가속 동작의 사용 여부만 바꾸며, 다른 보조 키 조합과 누적 모드는 제공하지 않는다.
- 현재 브라우저에서 secure context인지와 마지막 클립보드 실패를 설명하되, 권한 상태 사전 조회만으로 복사 가능 여부를 단정하지 않는다.
- 설정을 바꾸기 전에 새 조작을 시험할 수 있는 예제 메모 영역을 검토한다.
- 현재 로컬 설정에는 계정 및 동기화 항목을 표시하지 않는다. 해당 항목은 최우선 계정 및 동기화 백로그에서 검토한다.

### 최우선 백로그: 계정 및 동기화

계정 및 동기화 페이지는 현재 로컬 애플리케이션에 포함하지 않는다. 모든 백로그 가운데 가장 먼저 진행할 계정 기능 개발에서 로그인 상태, 마지막 동기화, 충돌, 로그아웃과 계정 데이터 관리 동작을 다룬다. 인증 방식, 충돌 UI와 삭제 범위가 정해지지 않았으므로 세부 레이아웃은 아직 만들 수 없다.

## 클립보드 알림 제안

[WAI-ARIA의 `status` role](https://www.w3.org/TR/wai-aria-1.2/#status)은 중요도가 낮은 상태 메시지를 polite live region으로 알리는 역할을 정의한다. 복사와 누적 성공은 focus를 옮기지 않는 status 알림으로 전달할 수 있다.

[WAI-ARIA Authoring Practices의 Alert 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/alert/)은 alert가 포커스를 옮기지 않으면서 즉시 알려야 할 메시지에 쓰이며, 너무 빨리 사라지면 안 된다고 설명한다. 클립보드 실패 알림에는 실패 사실, 다시 시도와 설정 열기를 제공하고 사용자가 내용을 읽거나 닫을 때까지 유지하는 방안을 제안한다. 반복 실패를 매번 겹쳐 띄우지 않고 같은 알림을 갱신해야 한다.

브라우저는 권한과 사용자 활성화를 다르게 처리하므로 실제 클립보드 쓰기 실패를 알림의 기준으로 삼는다. 사용자가 설정에서 조작 방법을 바꾸더라도 복사는 사용자 동작 안에서 실행되어야 한다.

## 드래그 외의 조작도 제공해야 한다

[WCAG 2.2의 Dragging Movements 이해 문서](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)는 드래그가 필요한 기능에 드래그 없이 단일 포인터로 수행할 수 있는 대안을 제공하도록 설명한다. 누적 목록의 위로, 아래로와 제거 버튼은 순서 변경과 목록 밖 제거의 대안이 된다.

공간형 보드에서는 선택한 메모의 위치와 크기를 숫자 및 단계 조절 UI에서도 바꿀 수 있게 한다. 키보드 조작은 dragging criterion과 별개의 접근성 요구이므로 포커스 순서, 선택 상태, 편집 상태와 단축키 충돌을 실제 브라우저와 화면 읽기 프로그램에서 확인해야 한다.

### 포트폴리오 연결 백로그에서 결정할 사항

- 독립 실행 애플리케이션과 포트폴리오 호스트가 최상위 탐색, 내부 페이지 탐색, 제목, theme, error boundary와 상태 알림을 나누는 방식
- 포트폴리오 호스트가 개인 메모의 단일 라우트만 제공할지 내부 페이지별 하위 라우트도 제공할지와 모듈 탐색이 사용할 라우트 접두어
