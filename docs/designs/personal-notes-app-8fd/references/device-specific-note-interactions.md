# 메모 서비스의 기기별 UI와 저장 경험 조사

데스크탑은 메모의 공간 배치와 복사할 텍스트의 순서 조합에, 모바일은 목록에서 복사하고 별도 화면에서 편집하는 순서에 맞춰 설계하는 안을 권고한다. 같은 자료를 다루더라도 이동을 시작하는 영역과 화면 구성을 기기별로 구분해야 한다. 일괄 복사의 완성도는 장식보다 잡은 항목, 삽입 위치와 제거 예정 상태를 구별하는 데서 높일 수 있다. 모바일 자동 저장과 본문 실행 취소는 함께 제공하되 저장 완료와 편집 기록을 서로 독립적으로 관리해야 한다. 메모는 서버에만 저장하며 화면에서는 저장과 연결 상태를 확인할 수 있게 한다. 아래 내용은 실제 서비스와 표준 및 현재 코드에서 도출한 제안이며, [요구사항](../requirements.md#기기별-사용-경험과-서버-저장)의 미정 사항을 확정하지 않는다.

## 조사 범위와 근거의 한계

2026년 11월 4일 기준으로 PC에서 메모를 배치하고 모바일에서 같은 메모를 확인하거나 편집하려는 사용 경험을 조사했다. 화면 구성, 터치와 키보드 접근성, 자동 저장의 신뢰성, 기기 연결 및 기존 기능 보존을 비교한다. 사용량이나 수익성에 관한 시장 조사는 포함하지 않는다.

공식 자료는 서비스가 설명하는 동작의 근거다. 누구나 열람할 수 있는 사용자 신고는 어떤 조건에서 불편이 생겼는지를 보여주지만 발생 빈도를 입증하지 않는다. 현재 메모 서비스의 사용자 인터뷰나 사용 기록은 근거에 포함하지 않았다. 따라서 아래 우선순위는 실패했을 때의 영향과 요구사항에 미치는 영향을 기준으로 정했다. 실제 이탈률을 측정한 순위는 아니다.

Codex 내장 브라우저에서 현재 메모의 데스크탑 화면, Atlassian 삽입선 예시와 Apple Notes의 편집 화면 이미지를 확인했다. Apple 자료에는 본문 위 실행 취소 버튼과 아래 편집 도구가 구분돼 있다. 경쟁 서비스의 로그인 후 조작이나 실제 휴대전화에서 터치 동작을 재현한 결과는 아니다. 현재 메모 서비스가 모바일 구성으로 전환된 화면 증거도 확보하지 못했으므로 터치 사용성과 키보드가 열렸을 때의 사용성을 판정할 수는 없다.

## 우선 해결할 사용 문제

### 1. 저장됐다고 생각한 본문과 실제 저장된 본문이 달라지는 문제

메모 수정 화면에서 사용자는 입력을 마친 뒤 안심하고 다른 화면으로 이동하려 한다. 앞선 저장의 완료를 최신 입력의 완료로 표시하거나 화면 종료 때만 저장하면 이 기대를 충족하지 못한다. 심각도는 높다. 이 서비스에서의 발생 빈도는 미확인이지만 종료 이벤트에 의존할 수 없다는 기술적 근거의 신뢰도는 높다. 저장 상태를 최신 본문과 연결하고 실패 시 입력과 재시도 조작을 남기는 것을 우선 권고한다.

[Chrome의 페이지 수명 주기 문서](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)는 모바일에서 hidden 상태 전환이 마지막으로 관찰 가능한 시점일 수 있으며, 페이지 폐기 시 이벤트가 발생하지 않을 수 있다고 설명한다. 이를 다른 모든 브라우저의 동일한 실행 순서로 일반화할 수는 없지만 종료 직전 저장만으로 입력을 모두 보존한다고 설명해서는 안 된다는 근거다.

### 2. 모바일의 한 번의 터치가 서로 다른 동작을 실행하는 문제

목록에서 복사하려는 터치, 추가하려는 길게 누르기와 스크롤을 구분해야 한다. [Joplin의 Android 웹 긴 누르기 신고](https://github.com/laurent22/joplin/issues/15604)는 선택 상태가 잠깐 켜졌다가 해제되는 현상을 기록한다. 2026년 6월에 버전 3.6.20으로 신고됐고 8월에 종료 처리된 이슈다. 현재 Joplin에도 남아 있는 결함이라는 뜻은 아니다.

심각도는 중간 이상이며 이 신고는 한 사례이므로 빈도는 알 수 없다. 입력 방식에 따라 결과가 달라졌다는 신고 근거는 명확하지만 우리 서비스에서 같은 결함을 재현한 것은 아니다. 본문과 이동 핸들을 구분하고 길게 누르기 뒤 손을 떼는 동작에서 복사가 다시 실행되지 않도록 하는 설계의 우선도가 높다.

### 3. 실행 취소 버튼이 실제 편집 기록과 맞지 않는 문제

모바일 편집자는 잘못 지운 문장을 복원하려 한다. [Joplin의 편집 모드 전환 신고](https://github.com/laurent22/joplin/issues/13151)에는 기록이 사라졌는데도 Undo 버튼이 사용 가능한 것처럼 남은 현상이 있다. Android 3.4.6에서 2025년 9월 신고됐고 10월에 종료 처리됐다. 이 사례는 기록 유지 기간과 버튼 상태를 함께 정의해야 하는 근거다.

심각도는 높지만 빈도는 미확인이다. 신고 조건과 상태 불일치에 대한 근거 신뢰도는 높고, 우리 서비스에도 발생할 것이라는 예측은 검증 전이다. 편집 화면의 수명과 기록의 수명을 정하고 실행할 기록이 없을 때 버튼을 비활성화하는 방향을 권고한다.

### 4. 순서 변경과 항목 제거를 혼동하는 문제

일괄 복사에서 사용자는 원문을 잃지 않고 원하는 순서를 만들려 한다. 현재 패널 밖 드롭은 항목 제거이므로 마지막 행 뒤로 이동하려다 패널을 벗어나면 예상과 다른 결과가 생길 수 있다. 심각도는 중간 이상이고 실제 오조작 빈도는 미확인이다. 동작 자체는 요구사항으로 확인되지만 사용자가 얼마나 혼동하는지는 추정이다. 놓기 전에 삽입과 제거를 구별하는 표시가 필요하다.

[Atlassian 드래그 지침](https://atlassian.design/components/pragmatic-drag-and-drop/design-guidelines/)은 상대 위치를 나타내는 선과 영역을 나타내는 배경을 구분한다. 이 구분을 적용하되 패널 밖 제거를 유지할지 별도 제거 조작으로 바꿀지는 별도 결정으로 남긴다.

### 5. 입력 도중 화면이 움직이거나 도구가 가려지는 문제

모바일 편집자는 커서와 수정 중인 문장을 계속 확인할 수 있어야 한다. [2026년 Notion 모바일 사용자 글](https://www.reddit.com/r/Notion/comments/1r9t7qg/the_mobile_experience_is_terrible/)은 입력하려고 터치할 때 화면이 움직이는 현상을 “jumping around when you tap the screen to type”라고 표현한다. 직접 사용한 사람의 진술이지만 원인과 기기 조건을 충분히 확인할 수 없는 사례다.

심각도는 중간이고 빈도는 미확인이다. 불편 진술의 존재는 확인되지만 특정 구현 원인에 대한 신뢰도는 낮다. 우리 서비스에서는 키보드 표시, Undo/Redo와 저장 문구 변경이 본문의 위치를 불필요하게 바꾸지 않도록 하는 검증 과제로 연결한다.

### 6. 다른 기기에 메모가 없는 이유를 알 수 없는 문제

사용자는 PC에서 저장한 메모가 모바일에도 나타날 것으로 기대한다. 다른 계정과 연결 실패를 구분하지 않으면 빈 목록을 메모 손실로 오해할 수 있다. [Apple의 메모가 나타나지 않을 때 안내](https://support.apple.com/en-mide/121669)는 계정의 동기화 설정 확인을 안내한다. 이는 계정과 동기화 상태를 구별할 필요의 근거이며 발생률 자료는 아니다.

심각도는 높고 빈도는 미확인이다. 공식 안내된 해결 절차의 근거 신뢰도는 높다. 서버 메모 화면에서 계정 또는 연결된 보관 공간을 식별하고 빈 목록, 연결 중과 연결 실패를 구분하는 안을 권고한다.

## 데스크탑 메모와 캔버스

메모의 실선 빨간 테두리는 선택된 메모를 뜻하고, 헤더는 이동을 시작하는 영역으로 구성한다. 본문을 클릭해 편집해도 같은 선택 표시를 유지한다. 왼쪽 핸들은 제거하며 오른쪽 버튼과 본문에서는 이동을 시작하지 않는다. 이 부분은 최신 요구사항이며 다음 세부 표현은 제안이다.

- 평상시 헤더는 본문보다 낮은 시각적 비중을 갖게 한다. 버튼 이외 영역에 포인터를 올렸을 때만 은은한 배경과 잡기 커서를 표시한다.
- 이동이 시작되면 잡는 중 커서로 바꾸고 메모 자체를 포인터에 맞춰 움직인다. 본문 텍스트 선택과 메모 이동의 시작 영역을 겹치지 않는다.
- 선택선과 키보드 포커스를 구별한다. 메모 외곽에 점선을 다시 추가하는 대신 입력 또는 버튼의 포커스 위치가 식별되게 한다.
- 헤더의 단순 클릭은 선택만 하고 실제 이동이 성립한 경우에만 좌표를 바꾼다. 오른쪽 버튼에서 누른 채 이동해도 메모 드래그로 전환하지 않는다.
- 크기 조절은 기존 모서리와 가장자리 조작을 유지한다. 좌표와 크기는 속성 패널에서도 조정할 수 있게 하며 화면 이동과 메모 이동을 구분한다.

[Todoist의 작업 안내](https://www.todoist.com/help/todoist/features/introduction-to-tasks-080OAXric)는 목록 왼쪽 핸들로 작업을 이동하는 방식을 설명한다. 목록의 핸들을 공간 캔버스에 그대로 복제할 필요는 없다. 메모는 헤더가 있고 본문 편집을 보호해야 하므로 버튼을 제외한 헤더가 이동 영역이라는 규칙이 더 직접적이다.

[Miro의 입력 장치별 이동 안내](https://help.miro.com/hc/en-us/articles/360017731053-Using-Miro-with-a-mouse-trackpad-or-touchscreen)는 캔버스 이동과 확대를 별도로 설명한다. 우리 서비스는 기존 왼쪽 아래 확대 비율과 전체 보기 조작을 유지하고 빈 캔버스에서만 화면을 이동하는 안이 적합하다. 현재의 보조 키 복사 조작과 선택 표시의 관계는 일반 클릭과 별도로 결정해야 한다.

## 데스크탑 일괄 복사 패널

메모를 모아 원하는 순서로 복사하는 세로 목록을 중심에 둔다. 왼쪽 이동 핸들, 원문 미리보기와 오른쪽 더보기의 배치를 행마다 통일한다. 기존 조건인 순서 번호와 합친 본문 미리보기 제외를 유지한다. 중복 추가한 항목도 각각 별도 행으로 남긴다.

[Atlassian 지침](https://atlassian.design/components/pragmatic-drag-and-drop/design-guidelines/)의 미리보기와 삽입선 구분을 바탕으로 다음 상태를 제안한다. 내장 브라우저의 예시에서도 흐린 원래 행, 떠 있는 미리보기와 가로 삽입선을 구분할 수 있었다.

1. 시작 전에는 항목을 옮길 수 있는 핸들을 식별할 수 있게 한다. 행 전체를 이동 영역으로 만들지 않아 텍스트 선택과 더보기 조작을 보호한다.
2. 이동 중에는 원래 행의 자리를 유지하며 약하게 표시한다. 미리보기는 첫 부분의 텍스트로 항목을 식별하게 하고 과한 회전이나 확대를 넣지 않는다.
3. 유효한 위치에는 하나의 삽입선을 표시한다. 첫 항목 앞과 마지막 항목 뒤도 같은 규칙을 사용한다. 패널 안의 여백을 제거 영역으로 취급하지 않는다.
4. 놓으면 새 위치를 잠깐 강조하고 조작하던 항목의 포커스를 유지한다. 스크린리더에는 이동 결과를 한 번 알린다.
5. Escape 또는 포인터 취소 때는 원래 순서를 유지한다. 저장 실패 시 실패한 이동만 되돌리고 이후 성공한 다른 편집까지 복원하지 않는다.

패널 밖 제거를 유지하는 안에서는 밖으로 나가는 순간 미리보기에 `놓으면 목록에서 제거`를 표시하는 방법을 제안한다. 이때는 삽입선을 숨긴다. 대안은 명시적인 제거 영역이나 더보기의 제거만 사용하는 방식이다. 대안은 실수 가능성을 줄일 수 있지만 기존 드롭 동작을 바꾸므로 승인 전에는 적용하지 않는다.

넓은 데스크탑의 오른쪽 패널과 중간 너비의 모달에서도 같은 행 구조와 상태를 사용한다. 속성과 일괄 복사는 기존과 같이 오른쪽에서 동시에 겹쳐 열지 않는다. 모달에서는 닫은 뒤 열기 버튼으로 포커스를 돌려준다. 데스크탑 패널에 새 Undo/Redo 버튼을 추가하는 안은 포함하지 않으며 기존 키보드 복원 조작을 보존한다.

## 모바일 목록과 개별 메모 조작

모바일의 첫 화면은 한 열 목록으로 구성하고 복사할 본문을 찾는 데 시선을 집중시킨다. [Notion 모바일 안내](https://www.notion.com/help/notion-for-mobile)는 hover가 없는 환경에서는 아이콘을 표시하고 여러 열의 내용을 한 열로 제공한다고 설명한다. 이는 모바일을 데스크탑 축소판으로 만들지 않을 근거이며 해당 서비스의 모든 메뉴를 도입할 근거는 아니다.

기존 모바일 조작을 유지하는 제안은 왼쪽 중앙 핸들, 본문과 오른쪽 위 더보기로 구성한다. 핸들 옆 구분선이나 별도 배경을 추가하지 않고 터치 영역으로 구분한다. 짧은 메모와 긴 메모에 다른 종류의 카드를 만들지 않는다. 본문을 임의로 잘라 복사하거나 원문 공백을 정리하지 않는다.

- 짧게 터치하면 원문 전체를 한 번 복사하고 실제 성공한 뒤 알림을 표시한다. 실패하면 성공 알림을 내지 않는다.
- 길게 누르기가 성립하면 손을 떼기 전에 일괄 복사에 한 번 추가한다. 계속 누르거나 손을 떼어도 추가나 복사를 반복하지 않는다. 본문의 누름 테두리는 손을 떼거나 취소하면 해제한다.
- 스크롤이 시작되면 본문의 누름 상태와 추가 대기를 취소하는 안을 권고한다. 스크롤을 멈춘 뒤 손을 뗐다는 이유로 복사하지 않는다.
- 더보기 시트에는 복사, 일괄 복사에 추가, 수정과 삭제를 둔다. 길게 누르기를 몰라도 복사와 추가를 실행할 수 있다.
- 헤더의 일괄 복사 아이콘은 현재 작업의 항목 수를 표시하고 확인 화면으로 바로 이동한다. 중복 항목을 포함한 실제 개수를 세며 0개일 때는 배지를 숨기고 이동을 비활성화한다.
- 새 메모는 오른쪽 아래 플러스 버튼으로 만든다. 기존 조건처럼 목록에 남기며 자동으로 편집 화면을 여는 변경은 제안에 포함하지 않는다. 버튼은 마지막 메모와 더보기를 가리지 않게 한다.

목록에서 편집으로 이동한 뒤 돌아올 때 기존 스크롤 위치와 편집했던 메모를 찾을 수 있게 하는 안을 권고한다. 페이지 전체에 지속적으로 스크롤을 막는 방식은 피한다. 목록과 보조 페이지의 탐색 메뉴는 유지하되 편집 및 일괄 복사 확인 화면에는 작업을 마치고 돌아갈 조작을 우선한다.

## 모바일 드래그와 일괄 복사 확인

모바일 원본 목록과 일괄 복사 목록은 같은 이동 표현을 사용하되 서로 다른 순서를 바꾼다. 본문 길게 누르기는 추가에 쓰므로 드래그는 핸들에서만 시작하는 안을 우선 권고한다. 별도 순서 편집 모드는 오조작을 줄일 후보지만 진입 단계가 늘어나고 초기 화면에서 바로 이동하는 기존 조작 순서가 바뀐다.

핸들을 잡으면 원래 자리를 남기고 미리보기와 삽입선을 표시한다. 손가락 아래에 가려지는 중앙보다 항목 사이의 선으로 도착 위치를 읽을 수 있게 한다. 화면 가장자리에서는 목록만 자동 스크롤하며 의도하지 않은 가로 이동을 시작하지 않는다. 중단 또는 포인터 취소 때는 순서를 바꾸지 않는다. 모바일 원본의 순서 변경은 데스크탑 좌표와 탐색 순서 및 일괄 복사 순서를 변경하지 않는다.

확인 화면의 본문은 모은 항목과 순서에 집중시키고 아래에 `취소`와 `일괄 복사`를 둔다. 기존의 뒤로 가기는 작업을 유지하고 취소는 작업을 버리므로 두 조작을 같은 의미로 표시하지 않는다. 별도 초기화 버튼은 추가하지 않는다. 현재 수집 작업은 새로고침하면 사라지는 조건이므로, 저장된 목록과 동일한 보관 표시를 사용하지 않는다. 이 차이가 불편하다면 지속 보관 여부를 별도로 결정해야 한다.

[WCAG 2.2 드래그 설명](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)은 “provide a simple pointer alternative”라고 설명한다. 키보드 조작만으로는 터치 또는 클릭 대안을 대신할 수 없다. 원본 목록의 더보기에 위로와 아래로 이동을 제공하는 안을 권고한다. 현재는 원본 목록의 대체 조작이 백로그이고 일괄 복사의 대체 버튼도 설정에서 켜는 구조이므로, 이 상태를 접근성이 해결됐다고 평가하지 않는다. 백로그 범위를 바꾸는 결정이 필요하다.

## 모바일 자동 저장과 저장 상태

편집 화면에서는 저장 버튼 대신 본문 가까이의 일정한 위치에 현재 저장 상태를 표시하는 안을 권고한다. 화면 상단의 제목 아래 한 줄을 확보하면 키보드가 열려도 상태를 확인할 수 있고 문구 길이가 바뀌어도 본문이 밀리지 않는다. [Google Docs의 오프라인 안내](https://support.google.com/docs/answer/6388102?hl=en)는 제목 옆 문서 상태로 오프라인 사용 가능 여부를 확인하도록 안내한다. 상태의 위치를 일관되게 제공하는 참고 사례이며 우리 서비스의 오프라인 기능이 이미 있다는 근거는 아니다.

저장 완료 문구는 서버 저장이 성공한 경우에만 표시한다. 다음은 문구 후보이며 최종 카피는 아니다.

- 진행 중: `저장 중`.
- 서버 저장 완료: `저장됨`.
- 실패: `저장하지 못했습니다`와 `다시 시도`. 원인이 확인되지 않았다면 네트워크 문제로 단정하지 않는다.

입력이 시작되면 이전의 저장 완료 표시를 해제한다. 짧은 대기 후 저장하는 경우도 대기 중인 변경을 완료로 표시해서는 안 된다. 저장 A 이후에 입력 B가 생기면 A의 응답만으로 완료를 표시하지 않고 B까지 저장됐을 때 완료로 바꾼다. 버튼을 없애는 것과 모든 키 입력마다 서버 요청을 보내는 것은 같은 결정이 아니다.

저장 실패는 사라지는 알림만으로 전달하지 않고 편집 화면에 남긴다. 실패 중에도 입력과 Undo/Redo를 유지하며 재시도는 최신 본문을 대상으로 한다. 화면을 나가려는 경우에는 현재 입력을 보관할 수 있는지에 따라 동작을 정해야 한다. 보관할 수 없다면 화면에 머물러 재시도하거나 미저장 입력을 버리고 나가는 선택을 명확히 구분하는 안을 제안한다. 이 정책은 아직 미정이다.

[WCAG 상태 메시지 설명](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)을 근거로 저장 결과는 포커스를 빼앗지 않고 알리는 방식을 권고한다. 모든 키 입력마다 같은 저장 문구를 읽어 주지 않으며 실패는 별도로 식별할 수 있게 한다.

## 모바일 편집의 Undo와 Redo

실행 취소와 다시 실행은 모바일 본문 편집 화면에만 나란히 배치하는 안을 권고한다. 상단에 뒤로 가기, 화면 제목과 두 버튼을 두고 바로 아래에 저장 상태를 둔다. [Apple Notes 안내](https://support.apple.com/en-ie/118442)는 화면 위의 Undo 버튼과 현재 메모가 열린 동안의 변경 취소를 설명한다. 저장과 구분된 편집 도구의 참고 사례다.

상단 배치는 키보드가 열린 뒤에도 위치가 유지되는 장점이 있지만 한 손으로 누르기 어려울 수 있다. 대안인 키보드 위 도구 모음은 누르기 쉽지만 모바일 브라우저의 화면 높이가 바뀌어도 도구가 본문을 가리지 않게 조정해야 한다. 우선 상단 배치를 시안으로 비교하고 좁은 화면과 큰 글자에서도 버튼과 저장 상태가 겹치지 않는지 확인하는 안을 제안한다.

동작 가능한 기록이 없으면 해당 버튼을 비활성화하고 보조 기술에서 이름과 상태를 알 수 있게 한다. 버튼 조작 후에는 본문의 적절한 커서 또는 선택 위치로 편집을 이어갈 수 있어야 한다. 자동 저장 완료는 기록을 지우지 않으며 실행 취소와 다시 실행의 결과도 자동 저장한다. 실행 취소 후 새 편집은 이전 다시 실행 기록을 버린다.

기록 유지 기간의 후보는 다음과 같다.

- 편집 화면을 연 동안 유지: 구조가 단순하고 다른 메모의 기록이 섞이기 어렵다. 화면을 나갔다 돌아오면 되돌릴 수 없다는 제약이 있다. 우선 비교할 제안이다.
- 같은 탭에서 메모를 다시 열어도 유지: 돌아온 뒤 수정 실수를 복구하기 쉽지만 메모별 기록과 메모리 제한을 관리해야 한다.
- 새로고침 후에도 유지: 복구 범위가 넓지만 기록 보관과 정리 및 저장된 본문과의 일치를 추가로 설계해야 한다. 현재 요구만으로 이 복잡성을 도입할 근거는 부족하다.

연속 입력을 한 번에 되돌리는 기준은 아직 정하지 않았다. 한글 조합 도중의 낱자 상태를 각각 복원하지 않고 조합이 끝난 입력을 기준으로 묶는 안을 권고한다. 붙여넣기와 선택 영역 교체는 독립된 편집 단위로 비교한다. 기록 개수와 메모리 제한은 긴 본문에서 확인한 뒤 정해야 하며 임의의 숫자를 확정하지 않는다.

[Input Events Level 2](https://www.w3.org/TR/input-events-2/)는 `historyUndo`, `historyRedo`와 조합 입력을 구분한다. 표준 초안의 존재가 모든 브라우저에서 동일하게 동작한다는 뜻은 아니다. 운영체제의 실행 취소와 화면 버튼이 한 조작에 두 번 적용되지 않도록 하는 실제 모바일 확인이 필요하다. Undo 기능을 추가한다는 이유만으로 `revision`, `contentRevision`이나 `noteDrafts`의 제거 또는 유지가 결정되지는 않는다.

## 삭제, 복원과 바텀 시트

메모 삭제 복원과 본문 편집의 실행 취소는 같은 기록으로 묶지 않는다. 원본 메모의 더보기는 메뉴, 삭제 확인, 처리 중, 완료와 실패를 같은 높이의 시트 안에서 표시하는 기존 조건을 유지한다. 완료 화면의 `실행 취소`는 시트를 닫을 때까지 가능하고 자동으로 시트를 닫지 않는다.

삭제 확인에는 대상 본문의 일부와 명확한 삭제 버튼을 표시한다. 처리 중 중복 실행을 막고 실패 시 대상을 잃지 않은 상태에서 재시도하게 한다. 짧은 화면이나 큰 글자에서는 시트 안의 내용만 스크롤하고 취소와 닫기 및 복원 조작에 접근할 수 있게 하는 안을 권고한다. 고정 높이를 지키느라 마지막 버튼을 가리는 것은 적합하지 않다.

일괄 복사 항목 제거는 원본 메모 삭제와 다른 행동이다. 해당 시트는 기존처럼 처리 후 닫을 수 있으며 원본 메모까지 삭제했다는 표현을 사용하지 않는다. 삭제 완료 화면, 편집 화면과 일괄 복사 화면에서 같은 `실행 취소`라는 말이 서로 다른 대상을 가리키더라도 화면 문맥과 접근성 이름으로 그 대상을 알 수 있게 한다.

## 서버 전용 메모 화면

저장 대상 선택 없이 `메모` 화면으로 진입하는 안을 권고한다. 데스크탑은 캔버스, 모바일은 목록과 상세 편집으로 구성한다. 서버 전용 저장은 확정 요구이며 페이지 구성은 제안이다. 브라우저 메모 페이지와 저장 대상 사이의 이동 조작은 제공하지 않는다.

계정 로그인을 선택한다면 처음 진입에서 로그인하고 다른 기기에서도 같은 계정으로 접속하는 방식을 제안한다. 계정 표시와 로그아웃은 계정 메뉴에 둔다. 로그인 전, 로그인 취소, 세션 만료와 메모가 없는 상태를 구분한다. 인증 제공자와 복구 방법은 아직 정하지 않았다.

로그인 없는 기기 연결을 선택한다면 기존 기기에서 연결을 시작하고 새 기기에서 코드 또는 QR로 연결을 요청한 뒤 기존 기기에서 승인하는 순서를 후보로 둔다. 대기, 만료, 거절과 완료를 각 기기에서 표시하고 연결된 기기를 해제하는 조작도 필요하다. 단순한 짧은 코드를 영구 접근 수단으로 쓰는 안은 제안하지 않는다. 기존 기기를 모두 잃었을 때 복구할 수단을 별도로 정하지 않으면 계정 방식과 같은 복구 경험을 제공한다고 설명할 수 없다. 이 연결 방식은 우리 서비스의 설계 후보이며 특정 경쟁 서비스에서 검증한 구현은 아니다.

서버 화면은 자료를 불러오는 중, 메모 없음, 연결 실패와 접근 만료를 서로 다른 상태로 제공한다. 불러오기 실패를 빈 목록으로 표시하지 않는다. 저장 성공은 다른 기기에도 즉시 표시됐다는 뜻이 아니므로 저장 상태와 다른 기기의 수신 완료를 혼동하지 않는다. 연결이 끊겼을 때 화면 메모리에서 편집을 허용할지와 여러 기기 동시 편집 정책은 미정이다. 서버 전용 저장 조건에서 브라우저 영구 저장을 복구 수단으로 전제하지 않는다. 단일 탭 사용 조건은 PC와 모바일의 동시 접근까지 자동으로 제외하지 않는다.

## 화면별 구성과 텍스트 카피

서버 전용 저장에 맞춘 각 화면의 배치와 상태별 문구 후보는 [화면 구성과 텍스트 카피](screen-layout-and-copy.md)에 정리한다. 사용 빈도, 텍스트 분석, 템플릿 작성 및 사용과 설정의 데스크탑 및 모바일 구성도 같은 문서에서 비교한다.

## 시각 구성과 접근성

기존 Pretendard와 강조색 `#EE5165`, 밝은 중성 캔버스와 흰 메모를 유지하면서 상태 표현을 정돈하는 안을 권고한다. 차별점은 공간에서 텍스트를 배치하고 순서대로 모아 복사하는 경험에 둔다. 다른 서비스의 장식이나 일반적인 대시보드 구성을 추가할 근거는 없다.

선택은 실선 외곽, 누름은 누르는 동안의 두께 변화, 드래그 도착은 항목 사이 선, 실패는 설명과 재시도로 구분한다. 빨간색 하나로 선택과 삭제 및 오류의 뜻을 모두 전달하지 않는다. 강조색을 쓰는 가는 글자와 흰 숫자 배지는 실제 배경 및 크기에서 대비를 확인해야 한다. 기존 색이라는 이유만으로 접근성 기준을 충족한다고 판단하지 않는다.

[WCAG 터치 대상 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)의 최소 대상 기준은 예외 조건을 포함한 24 CSS px다. 이를 모바일 버튼을 모두 24px로 줄일 근거로 사용하지 않는다. 현재 토큰의 모바일 터치 크기 2.75rem을 출발점으로 삼고 아이콘의 그림과 실제 터치 영역을 구분한다. 확대 글자, 좁은 화면과 가로 화면에서도 인접 버튼을 잘못 누르지 않는지 확인해야 한다.

키보드 포커스, 스크린리더 이름과 상태, 이동 뒤 포커스, 모달을 닫은 뒤 복귀를 화면별로 확인할 필요가 있다. 드래그 대체 조작을 백로그로 남기는 결정과 접근성이 충족됐다는 평가는 함께 성립하지 않는다.

## 현재 코드와 설계의 연결

[`note-card.tsx`](../../../../apps/notes/src/_pages/notes/ui/note-card.tsx)는 본문의 `focus-visible`에 점선을 표시하고 선택에는 실선을 사용한다. 이동은 왼쪽 버튼에 연결돼 있어 일반 본문 클릭의 선택, 포커스 표시와 헤더 이동을 함께 조정할 대상이다.

[`batch-copy-list.tsx`](../../../../apps/notes/src/features/edit-batch-copy/ui/batch-copy-list.tsx)에는 선택, 이동 중 상태와 앞뒤 삽입선이 이미 있다. 따라서 삽입선을 새 기능으로 추가하는 제안이 아니라 기존 상태의 시각적 구분과 미리보기를 개선하는 제안이다.

[`mobile-notes-workspace.tsx`](../../../../apps/notes/src/_pages/notes/ui/mobile-notes-workspace.tsx)와 [`mobile-note-card.tsx`](../../../../apps/notes/src/_pages/notes/ui/mobile-note-card.tsx)는 모바일 목록과 개별 조작을 담당한다. 데스크탑과 모바일의 화면을 하나로 합치기보다 본문 저장, 복사와 순서 변경처럼 결과가 같은 처리를 재사용하는 방향을 권고한다. 원본 목록 순서와 일괄 복사 순서는 자료가 다르므로 같은 저장 작업으로 취급하지 않는다.

현재 브라우저 저장 구조에는 메모, 순서, 복사 목록과 복구 초안이 있으며 revision만을 위한 전용 저장소는 확인되지 않았다. `revision`, `contentRevision`과 `noteDrafts`의 제거 여부는 편집 기록 UI만으로 결정할 수 없다. 특히 단일 탭에서도 이전 저장 응답과 새 입력의 순서 문제는 남는다. 화면에는 내부 필드명이나 저장소 이름을 표시하지 않고 저장 결과와 사용 가능한 다음 조작을 보여준다.

## 적용 우선순위 제안

단기 개선 후보는 데스크탑 선택선과 헤더 이동, 드래그 상태 표현, 모바일 터치 중복 방지, 자동 저장 상태 및 Undo/Redo의 활성 상태다. 이번 주에 검토할 묶음으로 제안하지만 구현 일정이나 완료 약속은 아니다. 사용자가 수행하려는 조작과 실패 시의 영향을 바로 확인할 수 있는 항목들이다.

분기 단위의 확장 후보는 서버 전용 메모 화면, 기기 연결과 재접속, 실패 복구, 모바일 보조 페이지 및 드래그 대체 조작이다. 로그인 또는 기기 연결 방식이 정해져야 서버 화면의 시작과 복구 절차를 확정할 수 있다. 드래그 대체 조작을 앞당길지는 기존 백로그 변경을 포함한다.

추가 사용자 확인이 필요한 주제는 긴 누르기 발견 가능성, 패널 밖 제거의 오조작, Undo/Redo 상단 배치의 한 손 접근성 및 목록으로 돌아온 뒤 편집 기록의 기대다. 짧고 긴 메모, 긴 목록, 키보드가 열린 화면과 저장 실패를 포함한 시안으로 비교해야 한다. 인터뷰나 관찰 없이 성공률과 이탈률 개선 수치를 제시할 근거는 없다.

## 아직 결정해야 할 동작

- 모바일 편집 기록을 화면을 나간 뒤 또는 새로고침 뒤에도 유지할지, 연속 입력을 어떻게 묶고 얼마나 보관할지.
- 자동 저장 실패 중 화면을 나갈 때 입력을 어디에 보관하고 어떤 선택을 제공할지.
- 서버 접근을 계정과 기기 연결 중 무엇으로 시작할지, 연결 수단을 모두 잃은 경우 어떻게 복구할지.
- 서버 메모의 오프라인 편집과 여러 기기 동시 편집을 어느 범위까지 제공할지.
- 패널 밖 제거를 유지할지, 드래그 대체 조작을 백로그에서 현재 범위로 옮길지.
- 보조 키 복사와 선택 표시의 관계 및 서버 메모 이외 자료의 동기화 범위.

이 선택들은 새로운 UI 시안을 확정하는 데 필요한 판단이다. 현재 조사만으로 기존 메모 보존을 중단하거나 저장 구조를 변경할 수는 없다.

## 출처별 기여와 확인 범위

공식 서비스 문서에서는 Atlassian의 이동 상태, Todoist의 핸들, Notion의 모바일 구성, Apple의 편집 도구, Miro의 캔버스 조작 및 Google Docs의 저장 상태를 비교했다. 문서가 뒷받침하는 설명 옆에 출처를 연결했다. W3C는 드래그 대체 조작과 터치 대상 및 상태 안내의 기준을, Chrome 문서는 종료 시점 저장의 한계를 제공한다.

GitHub는 공식 Joplin 저장소의 신고 본문과 종료 상태를 확인했다. Reddit은 모바일 입력 중 화면 이동에 대한 직접 진술을 제공하지만 빈도를 추정하지 않았다. Stack Overflow 검색에는 프로그램이 텍스트를 바꿀 때 Undo 기록과 연결되지 않는 오래된 질문이 있었으나 현재 브라우저 구현을 선택하는 근거로 사용하지 않았다. Hacker News와 X 검색에서는 이 서비스의 요구사항에 직접 적용할 만큼 구체적이고 확인 가능한 자료를 확보하지 못했다.

서비스 이름 검색만으로 notes.nwlee.com의 독립적인 사용성 평가나 빈도를 추정할 자료는 확보하지 못했다. 내부 고객 문의 기록과 사용 분석 자료도 포함하지 않았다. 따라서 경쟁 서비스에서 신고된 문제와 이 서비스의 코드로 확인한 동작을 구분하며, 제안의 효과는 시안과 실제 기기의 조작 결과로 확인해야 한다.
