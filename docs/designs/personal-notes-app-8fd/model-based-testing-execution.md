## 본문 편집과 원문 revision 실행 결과

2026년 9월 24일 새 절차의 로컬 판정은 `pass`다. `note.test.ts`에서 원문 교체, 공백을 포함한 입력, 줄바꿈, URL 모양 문자열, 원래 값 복귀, 같은 값 재적용과 X 위치 변경을 생성했다. 기대 모델은 앞선 기대 원문 및 revision과 이번 입력만 보관하며, 실제 결과는 `reviseNote`에서 읽었다. 정상 후보 100개가 통과했다. 공백을 제거하는 통제 결함과 위치만 바꿀 때 원문 revision을 증가시키는 통제 결함은 같은 관찰식에서 실패했다.

전체 단위 검사 실행에서 공백 손실은 seed `-934025517`, path `3:1:0`, replayPath `BEB:F`로 재실행했다. 처음 실패한 여러 행동은 공백만 있는 원문 교체 하나로 줄었고, 예상 원문은 공백 두 개였지만 통제 결함에서는 빈 문자열이었다. 위치 결함은 seed `-1589639760`, path `0:1:0`, replayPath `BFB:F`로 재실행했다. 축소된 행동은 X 변경 하나이며, 예상 원문 revision `2` 대신 통제 결함은 `3`을 관찰했다. 두 축소 행동을 난수 없이 다시 실행하면 각 결함에서만 실패하고 정상 함수에서는 통과한다. 숫자 revision은 해당 실행의 초기 자료에서 나온 값이며 일반 상수로 쓰지 않았다.

동일 책임의 이전 본문 탐색은 `note-lifecycle.model.test.ts`에서 제거했다. 배치, 삭제 및 복원 검사는 남겼다. 전체 단위 검사 36개 파일의 199개 검사, 타입 검사와 lint가 통과했다. 기존 실제 편집기 과업에는 축소에서 드러난 공백만 있는 원문을 추가해 저장소 재조회, 원문 revision과 새로고침 뒤의 값을 Chromium, Firefox 및 WebKit에서 확인했고 세 검사 모두 통과했다. 실제 IME 조합과 외부 앱 붙여넣기는 이 결과에 포함하지 않는다.

### 이전 실행 기록

당시 본문 편집과 원문 revision은 `pass`였다. `reviseNote`를 실행하는 독립 모델은 빈 원문, 공백, 여러 줄, Unicode, URL 모양 원문, 원래 값 복귀, 같은 값 반복과 위치 변경을 조합한다. 로컬 빠른 프로필의 정상 후보 100개에서 행동 471개를 실행했고 거절되거나 시간 상한으로 중단된 행동은 없다.

- 행동 생성: `edit-blank`, `edit-lines`, `edit-unicode`, `paste-url`, `restore-original`, `move-x`와 `inspect`를 `fc.commands`로 생성했다. 본문 행동은 적용할 전체 원문을 모델에 보관하고 위치 행동은 X 값만 바꿔 두 revision의 예상값을 독립적으로 계산한다.
- 오류 탐지: 본문 앞뒤 공백을 제거하는 결함은 예상 원문 `" "`과 관찰 원문 `""`의 차이를 탐지했다. 위치만 바꿀 때 content revision도 높이는 결함은 예상 revision 2와 관찰 revision 3의 차이를 같은 불변 조건 `content-revision-changes-only-for-content`에서 탐지했다.
- 실패 순서 축소: 공백 결함의 첫 실패 `move-x(30), paste-url, paste-url, edit-blank`는 `edit-blank` 하나로 줄었다. 위치 결함의 `inspect, move-x(30)`은 `move-x(30)` 하나로 줄었다. 두 실행 모두 한 번 축소됐고 문자열 축소와 행동 순서 축소를 구분했다.
- 로그 기록: 공백 결함은 seed `2`, path `2:1`, replayPath `E:B`, 위치 결함은 seed `2`, path `0:1`, replayPath `BEA:F`를 기록했다. 초기 및 예상 및 관찰 원문, content revision, 전체 revision, X 값, 앱과 모델 revision, 도구 버전, 프로필, 명령 집계, 소요 시간과 종료 이유도 JSON에 포함했다.
- 재현: 두 결함 모두 seed, path와 replayPath로 다시 실패했고 축소된 행동을 난수 없이 실행해 같은 불변 조건을 확인했다. 같은 두 행동은 정상 `reviseNote`에서 통과했다.

실제 애플리케이션에서는 textarea 전체를 선택해 앞뒤 공백, 줄바꿈과 URL 모양 문자열을 키보드로 입력했다. 저장된 IndexedDB 원문과 content revision을 읽어 본문 편집에서 두 revision이 한 번씩 증가하고, 이어 X만 바꾸면 전체 revision만 증가하는 것을 확인했다. URL은 링크가 되지 않았다. 이 검사는 Chromium, Firefox와 WebKit에서 통과했다. 외부 애플리케이션에서 가져온 Clipboard 붙여넣기는 이번 자동 검사로 입증했다고 기록하지 않는다.

공통 명령 계측은 생성과 편집 검사에서 실제 반복 책임이 확인된 뒤 재사용 함수로 옮겼다. Git revision 읽기도 Node와 브라우저 Vitest 설정이 같은 함수를 사용한다. 운영 화면, 메모 자료 형식과 오류 처리는 바꾸지 않았다. CI 재현은 원격 저장소와 CI 서비스가 정해진 뒤 별도로 확인한다.

## 데스크톱 자동 저장 실행 결과

2026년 9월 24일 데스크톱 자동 저장의 로컬 판정은 `pass`다. 실제 메모 화면에서 원문 입력, 799ms, 1ms 및 800ms 경과, 재입력, blur와 저장 조회를 생성했다. 정상과 편집 후 IndexedDB 쓰기 누락 조건을 Chromium, Firefox 및 WebKit에서 실행한 여섯 검사가 통과했다. 누락 조건의 실패 행동은 입력과 저장 기한 도달로 축소됐고 seed, path, replayPath 재생 및 난수 없는 실행에서 같은 예상 원문과 저장 원문의 차이를 보였다. 정상 저장에서는 축소된 행동이 통과했다. 대표적인 축소는 WebKit의 `enter(" "),advance(799),advance(799)`이며, 특정 입력값이나 행동 수를 일반 규칙으로 가정하지 않는다.

실제 설정 링크를 누른 내부 이동은 저장 기한이 끝나기 전의 최신 원문을 저장했다. 숨김 및 pagehide 명령은 실제 메모 화면에 합성된 문서 이벤트를 전달해 처리 연결만 확인했다. 이 검사의 세 브라우저 실행 여섯 건이 통과했다. 브라우저 탭 전환 또는 OS 종료 자체를 확인한 결과는 아니다.

이전 Browser Mode의 테스트용 편집기 기반 타이머 명령과 중복 보고 코드는 제거했다. 지연된 첫 저장 검사는 운영 `NoteCard`의 편집기를 Provider와 지연 저장 대역에 연결하도록 바꾸고, hook 등록을 복제하던 `AutosaveEditor`를 삭제했다. 서로 다른 두 입력 원문을 생성해 첫 쓰기가 끝나기 전에 두 번째 원문을 카드에 입력했다. 첫 쓰기 해제 뒤에도 카드 입력이 두 번째 원문을 유지했고, 후속 쓰기가 완료되자 저장 대역에서 다시 읽은 원문도 같았다. 저장 요청에 담긴 값으로 기대 원문을 만들지 않았다. 이 카드 및 저장소 검사를 포함한 Browser Mode 51건, 타입 검사와 lint가 통과했다. 운영 코드와 저장 자료 형식은 변경하지 않았다.

Chromium의 한 실행에서는 seed `2139788344`, path `0:0:0:0:0:0:0`으로 반복 개별 복사를 각각 한 번, 초기 revision을 0, 두 원문을 공백 한 글자와 두 글자로 줄였다. 축소된 입력을 직접 실행하고 seed 및 path로 다시 실행했을 때 격리 조건에서만 실패했으며 정상 입력에서는 통과했다. 이 축소는 필수 편집과 복사 순서를 고정하고 반복 횟수 및 원문을 줄인 것이며 모든 가능한 행동 순서의 최소성 증명은 아니다. 최초 및 축소 입력, 기대 및 관찰 횟수, seed, path와 브라우저별 실행은 Browser Mode의 표준 출력에 남겼다.

생성 자료의 기록 schema와 집계 검사 네 건, 전체 단위 검사 188건, IndexedDB Browser Mode 27건, Chromium Clipboard E2E 10건, 타입 검사, lint와 운영 빌드가 통과했다. 전체 E2E와 실제 기기 Clipboard 입력은 이 변경 뒤 실행하지 않았다. 기록 저장소, 집계 함수, UI와 저장 자료 형식은 바꾸지 않았다.

단위 검사 시작 전에는 기존 원문 모델의 `numShrinks > 0` 가정이 임의 seed에서 실패했다. 최초 실패가 이미 한 행동일 수 있으므로 축소 후 행동 수가 늘지 않는 조건으로 바꿨고 전체 단위 검사가 통과했다. Clipboard E2E 전체 병렬 실행에서는 자동 저장이 끝나기 전 화면을 다시 열어 이전 원문이 보였다. 수정한 원문이 새 저장소 연결에서 읽힌 뒤 화면을 다시 열도록 관찰 시점을 바꾸자 10건 모두 통과했다.

## 기능별 입증 계획과 기존 작업 유지 판단

2026년 9월 13일에 [기능별 조사](references/note-feature-exploration-research.md)와 [계획](plan.md#u12-모델-기반-탐색과-실패-재현)을 정리했다. 생성, 본문 편집, 자동 저장, 모바일 저장, 초안 복구, 위치 및 크기, 겹침 순서, 삭제 취소, 선택 및 포커스, 캔버스 보기, 개별 복사와 사용 기록으로 나눴다. 각 기능에 행동 생성, 오류 탐지, 실패 순서 축소, 로그 기록과 재현 상태를 표시하고 필요한 실제 저장 및 화면 증거를 함께 완료하도록 바꿨다.

공통 실행 방안에는 후보별 초기화, 실제 요청과 기대값의 분리, 명령별 실행량, 일반 실패 로그, seed 및 직접 행동 재현을 포함했다. 시간 제한이 진행 중 Promise를 취소하지 않는 점, 예산 중단과 정상 완료의 구분, 직접 만든 BrowserContext의 trace와 불변 조건 로그도 정리했다. 기능마다 필요한 결함 후보와 축소에서 보존할 선행 행동을 기록했으며 새 결함을 실행해 확인한 결과는 아니다.

당일 변경분의 제거 필요성은 읽기 조사로 확인했다. 초안 제거 재시도 운영 수정, fast-check와 실행 설정, 원문 및 revision 비교, 부분 실패 검사와 실제 IndexedDB 재조회는 유지할 근거가 있다. 기존 코드를 통째로 되돌릴 이유는 확인하지 못했다. 모델 연결, 일반 실패 보고와 화면 관찰은 목적을 보존해 보완할 대상이며 중복 검사의 제거 여부는 대체 증거 확보 뒤 판단한다. 상세 근거는 [제거 필요성 조사](references/note-feature-exploration-research.md#기존-작업의-제거-필요성)에 있다.

이번 변경은 요구사항의 기능별 완료 조건, 조사, 계획 및 문서 간 참조의 갱신이다. 기존 단계 1부터 4의 실행 기록은 아래에 남기되 현재 기능 완료 판정으로 사용하지 않는다. 운영 코드, 테스트, 의존성과 Git 이력을 제거하거나 수정하지 않았고 테스트도 재실행하지 않았다. CI 서비스와 원격 저장소 선택은 여전히 미정이다.

## 후속 조사에 따른 판정 정정

2026년 9월 13일의 [후속 조사](references/model-testing-validity-research.md#보완-후에도-남은-문제와-근본-원인)는 실패 보고, 계측, 모델 독립성, 축소, 비동기 저장, 화면 조작과 문서 상태를 비교했다. 근본 원인은 요구사항마다 구별해야 할 오류와 관찰 시점을 실행 증거에 연결하지 않은 채 일부 통과를 단계 전체 완료로 해석한 것이다. 아래 단계별 `pass`는 당시의 제한된 검사 판정이며 현재 단계 완료를 뜻하지 않는다.

기존 기록의 생략 0개는 fast-check의 속성 검사 `numSkips=0`이다. 명령의 `check`가 거절한 횟수를 측정한 값이 아니므로 명령 생략 수는 미확인이다. 결함의 seed 재실행은 고정된 행동 순서의 입력 축소이며 `fc.commands`의 행동 순서 축소와 replayPath 재현은 아직 증명하지 않았다.

직전 읽기 검토에서 `pnpm --filter notes-app test:model`은 3개 파일, 13개 검사와 각 모델 100개 사례를 통과했다. 명령 실행 총합은 복사 519회, 저장 362회와 생명 주기 381회였다. 저장 및 복사의 결함 입력은 공백 한 글자, 복원 결함 입력은 `[0,0]`으로 축소됐다. 이 통과 결과는 새 서비스 버그 발견이나 전체 브라우저 재실행의 증거가 아니다.

이 후속 조사에서는 운영 코드, 테스트, 의존성과 CI를 변경하거나 새 결함을 주입하지 않았다. 실패 보고 및 계측, 저장 입력 분리, 실제 저장과 조작의 보완점은 현재 [기능별 재보완 절차](plan.md#로컬-검증력-재보완-절차)에 연결되어 있다. 아래 단계 1부터 4의 `pass`와 실행 수치는 당시 기록이며 현재의 기능별 입증 상태는 앞부분과 계획을 따른다.

## 단계 1: 편집, 저장과 복구

독립 모델로 보완했다. `note-content.model.test.ts`의 모델은 현재 입력, 저장된 원문 및 원문 revision, 보관된 초안의 기준 revision과 다음 저장소 실패만 계산한다. `beginNoteContentSave`의 요청과 `saveNoteContent`의 반환값은 모델을 갱신하는 근거가 아니라 비교할 관찰값이다. 모델은 같은 저장이 진행 중일 때 새 요청을 만들지 않는 비정상 시도도 별도 명령으로 실행한다.

명시적 순서는 A 저장 요청 뒤 B 입력과 중복 요청, A 완료, B의 메모 쓰기 실패와 재시도, C 저장 뒤 초안 제거 실패, 같은 원문의 다음 저장에서 초안 제거 재시도까지 연결한다. 저장된 원문과 revision, 초안 내용과 기준 revision, 복구 가능 여부를 같은 관찰식으로 비교한다. 이 검사는 실제 IndexedDB 또는 화면 복구의 증거가 아니며, 실제 저장소와 화면 복구 검사는 단계 4에 남아 있다.

통제된 저장소 결함도 같은 관찰식으로 확인했다. 저장한 메모를 이전 값으로 돌려주는 결함, 메모 저장 실패 뒤 초안을 없애는 결함, 첫 저장 뒤 다음 저장을 이전 값으로 되돌리는 결함은 정상 Adapter가 아닌 경우에만 실패한다. 첫 결함은 fast-check가 입력 `" "`로 축소했고, seed `20260913`, path `0:0:0`으로 재실행한 뒤 같은 입력을 난수 생성 없이 다시 실행해 같은 위반을 확인했다.

`pnpm --filter notes-app test:model`의 `local-fast` 실행은 생성 사례 100개, 실제 명령 350개, 생략 0개를 기록했고 3개 파일의 8개 검사가 통과했다. 같은 변경에서 타입 검사와 lint도 통과했다. 전체 `pnpm notes:test`는 34개 파일, 178개 검사가 통과했다.

단계 1은 `pass`다. [초안 제거 재시도 결정](decisions/note-draft-cleanup-retry.md)에 따라 변경된 메모 저장 뒤 초안 제거만 실패하면 저장 성공을 유지한다. 저장 상태는 초안 정리가 남았음을 보관하고, 다음 저장은 원문이 같아도 제거를 다시 시도한다. 재시도 성공은 메모 원문과 revision을 바꾸지 않으며 초안을 없앤다.

## 단계 2: 생성, 배치, 삭제와 복원

독립 모델로 보완했다. `note-lifecycle.model.test.ts`의 모델은 메모 전체 자료와 제거 시각을 별도로 보관한다. 운영 함수는 모델의 기대값을 만드는 데 사용하지 않는다. 각 명령 뒤에는 원문, 원문 revision, ID, geometry와 Tab 순서를 실제 도메인 결과와 직접 비교한다. 위치와 크기 변경, 맨 앞으로 및 맨 뒤로 이동, 삭제, 최근 삭제 복원, 5초 만료와 빈 이력 복원 시도를 생성한다.

고정 순서는 `A=1, B=2, C=3`에서 B 삭제, A 맨 앞으로, B 복원으로 실행했다. 복원 직후에는 `C=1, A=2, B=2`가 남고, B를 다시 맨 앞으로 보내면 `C=1, A=2, B=3`으로 정리된다. 복원한 메모의 `zIndex`를 1 올리는 통제된 결함은 같은 관찰식에서 실패했다. fast-check는 입력 `[0,0]`으로 축소했고 seed `20260913`, path `0:0:0` 재실행과 난수 없이 같은 입력을 실행한 경우에도 같은 위반을 확인했다.

`pnpm --filter notes-app test:model`은 생성 사례 100개, 실제 생명 주기 명령 369개, 생략 0개를 기록했다. 3개 파일의 10개 검사가 통과했다. 같은 변경에서 `pnpm notes:typecheck`, `pnpm notes:lint`, `pnpm notes:test`가 통과했고 전체 검사는 34개 파일, 180개 검사였다. 단계 2는 `pass`다. 실제 IndexedDB 새 연결과 화면에서 중복 `zIndex`를 보존하는 검사는 단계 4에 남아 있다.

## 단계 3: 개별 복사와 사용 기록

독립 모델로 보완했다. `copy-note.model.test.ts`의 모델은 현재 원문, 원문 revision, 복사한 원문과 사용 기록을 각각 보관한다. 위치 변경은 content revision을 바꾸지 않는 실제 `reviseNote` 결과와 비교한다. 복사 명령은 복사 시점의 원문, revision과 ID를 Clipboard와 사용 기록에 정확히 전달했는지 비교한다. 이후 메모를 편집해도 이전 사용 기록이 새 revision으로 바뀌지 않는지 확인한다.

Clipboard 쓰기 실패는 복사 원문과 사용 기록을 모두 추가하지 않는다. Clipboard가 성공한 뒤 사용 기록만 실패하면 복사 원문은 남고 사용 기록만 빠진다. 복사 당시 revision을 하나 높여 기록하는 통제된 결함은 같은 관찰식에서 실패했다. fast-check는 입력 공백 한 글자로 축소했고 seed `20260913`, path `0:0:0` 재실행과 난수 없이 같은 입력을 실행한 경우에도 같은 위반을 확인했다. 빈 원문을 Clipboard에 쓰는 결함도 직접 실행에서 검출했다.

`pnpm --filter notes-app test:model`은 생성 사례 100개, 실제 개별 복사 명령 495개, 생략 0개를 기록했다. 3개 파일의 13개 검사가 통과했다. 같은 변경에서 `pnpm notes:typecheck`, `pnpm notes:lint`, `pnpm notes:test`가 통과했고 전체 검사는 34개 파일, 183개 검사였다. 단계 3은 `pass`다. 일괄 복사 목록은 포함하지 않았으며, 실제 Clipboard 권한과 사용 빈도 화면은 단계 4에 남아 있다.

## 단계 4: 실제 저장소와 메모 화면 연결

실제 IndexedDB 검사를 보완했다. 세 메모를 저장한 뒤 B를 삭제하고 즉시 조회해 B가 없고 A와 C만 남았음을 확인한다. 이어 A를 명시적으로 맨 앞으로 보낸 뒤 B를 저장하면 새 연결에서 `C=1, A=2, B=2`를 읽는다. 복원으로 생긴 같은 `zIndex`는 그대로 보존한다. B를 다시 명시적으로 맨 앞으로 보낸 뒤 또 다른 새 연결에서 `C=1, A=2, B=3`을 읽는다. ID별로 비교해 IndexedDB의 object store 읽기 순서를 겹침 순서의 기준으로 사용하지 않는다. 연결과 저장 자료는 사례마다 초기화하고 모든 연결을 해제한다. 이 검사는 실제 운영 repository의 고정 순서 검사이며 생성한 행동 순서 검사는 아니다.

`notes-model.spec.ts`에는 데스크톱의 세 메모를 생성하고, B 삭제, A의 명시적 순서 변경, B 취소 복원, 새로고침 순으로 실행하는 사례를 추가했다. 새로고침 뒤 메모 세 개와 각각의 입력 원문을 확인한다. 이 검사는 CSS 숫자나 DOM 순서를 읽지 않고 사용자가 실행하는 버튼, 알림, 입력값과 새로고침 뒤 상태를 관찰한다. 기존 사례는 생성, 편집, 800ms 자동 저장, 삭제와 취소, fast-check 원문 후보의 새 BrowserContext, 320px의 명시적 저장과 새로고침을 계속 확인한다.

`pnpm --filter notes-app test:browser`는 12개 파일, 48개 검사가 통과했다. 변경 직후 E2E 파일은 Chromium, Firefox와 WebKit에서 12개 검사가 통과했고, 전체 `pnpm notes:test:e2e`는 빌드 완료 뒤 99개 검사가 통과했다. `pnpm --filter notes-app test:model`은 3개 파일, 13개 검사와 생성 사례 각 100개를 통과했다. 실제 명령 수는 복사 464개, 원문 저장 368개, 생명 주기 398개였고 생략은 모두 0개였다. `pnpm notes:test`는 34개 파일, 183개 검사, `pnpm notes:typecheck`와 `pnpm notes:lint`도 통과했다.

단계 4는 `pass`다. 이 검사는 실제 브라우저가 강제로 종료되는 상황, 운영체제 수준의 앱 이탈 또는 IndexedDB 자체 장애에서의 자료 보존을 증명하지 않는다. 그런 조건은 현재 제어할 수 없으므로 완료 근거에 포함하지 않는다.

## 검증력 조사와 보완 계획

2026년 9월 13일에 기대값, 결과 관찰, 행동 실행량, 비동기 및 저장, 완료 증거를 조사했다. [원인과 공식 자료](references/model-testing-validity-research.md)를 정리하고 [U12 보완 순서](plan.md#보완-순서와-단계별-완료-증거)를 추가했다. 테스트와 운영 코드, 의존성 및 CI는 변경하지 않았다. 결함 주입과 테스트 재실행도 이번 문서 작업의 결과로 보고하지 않는다.

현재 U12 전체 상태는 `needs revision`이다. 단계 1부터 단계 4까지 일부 증거를 보완했으나 후속 조사에서 확인한 로컬 미완료 조건과 CI 재현이 남아 있다. 완료 판정은 문서 앞부분의 정정과 플랜의 재보완 절차를 따른다.

## 남은 판정과 실행 환경

다음 작업은 로컬 재보완이다. 로컬 완료 증거를 확보한 뒤 CI 서비스와 실행할 원격 저장소가 정해지면 같은 잠금 파일과 도구 버전으로 재현한다.

삭제 전 숫자 보존에 관한 추가 조사에서는 현재 복원과 일반 저장이 이미 숫자를 보존하며, 화면 동률 처리와 명시적 이동의 동률 처리 기준은 다를 수 있음을 확인했다. [적용 조사](references/note-restoration-z-index-research.md)에 코드 근거와 표준을 기록하고 요구사항, 삭제 복원 결정과 플랜을 업데이트했다. 실제 브라우저 실행이나 서비스 코드 수정의 완료 기록은 아니다.

CI 재현은 Git remote와 CI 서비스가 정해지지 않아 시작하지 않았다. 로컬 실행 기록을 특정 서비스의 workflow나 원격 저장소 설정으로 바꾸지 않았다.
