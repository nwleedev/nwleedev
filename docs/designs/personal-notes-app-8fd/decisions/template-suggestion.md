# 템플릿 제안 생성 결정

사용자가 고른 두 원문 줄을 grapheme 단위로 비교해 공통 구간은 일반 텍스트로, 다른 연속 구간은 순서가 있는 플레이스홀더로 제안한다. 제안은 사용자가 저장하기 전까지 템플릿이 아니다.

## 결정 질문과 요구 결과

[요구사항의 템플릿 결과](../requirements.md#의도한-결과)는 겹치는 텍스트에서 제안을 받고, 직접 여러 플레이스홀더를 지정하며, 입력값으로 일회성 텍스트를 만들도록 요구한다. LLM 없이 설명 가능한 제안 조건과 실패 상태뿐 아니라 겹침 결과에서 두 줄을 전달하는 단위와 수동 지정 흐름도 정해야 했다.

## 검토한 선택지

- 공통 prefix와 suffix만 사용하면 중간에 여러 차이 구간이 있는 텍스트를 처리하지 못한다.
- 단어 단위 diff는 한국어와 기호가 섞인 줄에 별도 token 규칙을 요구한다.
- grapheme 단위의 결정적 diff는 사용자에게 보이는 문자 차이를 유지하면서 여러 구간을 찾을 수 있다.
- LLM 기반 변수 이름과 의미 추론은 현재 범위와 맞지 않는다.
- 겹침 결과의 줄을 여러 행에서 따로 고르게 하면 선택 쌍의 출처와 확정 시점을 설명하기 어렵다. 한 결과 행이 이미 가진 두 줄을 함께 전달하면 분석 근거를 유지할 수 있다.
- 텍스트 안에서 플레이스홀더 문법을 직접 입력하게 하면 원문과 제어 문자를 구분하기 어렵다. 비어 있지 않은 범위를 선택한 뒤 명시적인 지정 동작으로 바꾸면 포인터와 키보드에 같은 결과를 제공할 수 있다.

## 결정 이력

- 초기 권장안은 사용자가 선택한 겹치는 두 줄의 공통 구간을 일반 텍스트로, 다른 구간을 플레이스홀더로 바꾸고 자동 저장하지 않는 방식이었다.
- 재검토에서는 세 줄 이상을 한 번에 맞추는 방식보다 두 줄의 근거를 직접 확인하는 방식이 초기 범위에서 설명 가능하고 안정적이라는 결론을 유지했다.
- 상호작용 검토에서는 겹침 결과 한 행의 두 줄을 선택 쌍으로 전달하고, 수동 작성에서 범위 선택, 겹침 방지, 이름 오류와 해제 동작을 명시해야 한다는 점을 보완했다.
- 현재 결정은 결과 행의 두 원문 줄을 하나의 선택 쌍으로 전달하고, 결정적 차이 분석, 순서형 플레이스홀더 이름과 범위 선택 기반 수동 작성을 제공하는 것이다.

## 승인된 결정과 이유

- 분석용 정규화 문자열이 아니라 선택 당시 원문 스냅샷 두 개를 비교한다.
- 각 겹침 결과 행에 `이 두 줄로 템플릿 제안` 동작을 둔다. 실행하면 그 행의 두 원문 스냅샷과 원본 메모 참조를 실행 중 상태에 보관하고 템플릿 화면으로 이동한다.
- 템플릿 화면은 전달받은 두 줄과 원본 메모 이동 동작을 먼저 보여준다. 선택 없이 직접 열었거나 새로고침으로 선택이 사라졌으면 수동 작성 시작과 겹침 결과로 돌아가기 동작을 제공한다.
- 사용자 인식 문자 단위 shortest edit script 또는 동등한 결정적 LCS diff로 공통 구간과 차이 구간을 찾는다.
- 서로 붙은 차이 구간은 하나의 placeholder로 합치고 여러 차이 구간은 여러 placeholder로 만든다.
- 의미를 추론한 이름을 만들지 않고 `입력값 1`, `입력값 2`처럼 순서만 나타낸다. 사용자가 저장 전에 이름과 구간을 바꿀 수 있다.
- 공통 일반 텍스트가 없거나 공백과 문장부호만 공통이면 제안하지 않는다. 두 줄이 같아 차이 구간이 없어도 자동 placeholder를 만들지 않는다.
- 제안하지 못한 이유와 수동 플레이스홀더 작성 동작을 보여준다.
- 수동 작성은 사용자가 입력하거나 붙여넣은 원문에서 비어 있지 않은 범위를 선택한 뒤 `플레이스홀더로 지정` 버튼을 실행하는 흐름을 사용한다. 이미 지정된 플레이스홀더와 겹치거나 중첩된 범위는 바꾸지 않고 이유를 표시한다.
- 새 플레이스홀더를 만들면 이름 입력으로 포커스를 옮긴다. 각 플레이스홀더에는 이름 변경과 `일반 텍스트로 되돌리기` 동작을 제공하며, 되돌릴 일반 텍스트를 확인한 뒤 segment를 바꾼다.
- 빈 이름과 중복 이름은 저장을 막고 각 이름 입력 가까이에 오류를 표시한다. 포인터로 범위를 선택하지 않아도 키보드로 같은 지정 흐름을 완료할 수 있어야 한다.
- 사용자가 명시적으로 저장한 뒤에만 템플릿 저장소에 추가한다. 일회성 출력은 별도 저장 요청이 없으면 보관하지 않는다.

[Myers의 diff 알고리즘 논문](https://doi.org/10.1007/BF01840446)은 두 sequence의 shortest edit script를 구하는 결정적 방법을 제시한다. 이 근거는 특정 구현을 강제하지 않으며 같은 사용자 결과를 내는 동등한 알고리즘을 허용한다.

## 예상 결과와 계획 영향

제안기, 겹치지 않는 segment 전이, 이름 규칙과 템플릿 결과 생성기는 TDD 대상으로 삼는다. 저장 전 제안이 템플릿 목록을 바꾸지 않는지는 저장소 통합으로 확인한다. 범위 선택, 지정 뒤 포커스, 오류의 읽기 순서, 선택 쌍 전달과 새로고침 뒤 수동 작성 전환은 실제 브라우저에서 확인한다.

## 다시 검토할 조건

- 세 줄 이상에서 하나의 공통 구조를 추출해야 하는 경우
- 사용자가 제안을 반복해서 거절하고 수동으로 다시 만드는 경우
- placeholder의 형식, 선택값 또는 조건부 구간이 요구되는 경우
