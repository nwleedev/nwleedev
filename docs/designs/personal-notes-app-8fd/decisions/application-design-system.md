# 개인 메모 디자인 시스템과 UI 기반 결정

개인 메모 애플리케이션은 Tailwind CSS, 네이티브 폼 요소와 자체 `shared/ui`를 바탕으로 고유 디자인 시스템을 만든다. 네이티브 요소는 브라우저 기본 외형을 그대로 쓰겠다는 뜻이 아니라 의미, 키보드 동작과 폼 참여 방식을 유지한다는 뜻이다. 외부 접근성 부품은 폼 값을 다루지 않는 복합 상호작용에 실제 필요가 확인된 경우에만 자체 구성요소 안에서 사용한다.

## 결정 질문과 요구 결과

[고유 디자인 시스템 요구사항](../requirements.md#반드시-지킬-조건)은 여러 화면이 같은 시각 언어와 상태 표현을 사용하면서도 완성형 UI 라이브러리의 기본 외형이나 흔한 AI 생성 화면을 답습하지 않도록 요구한다. 동시에 React Hook Form의 단순 입력을 불필요하게 제어 상태로 바꾸지 않고, 복합 상호작용의 접근성을 직접 재구현하는 위험도 피해야 한다.

## 검토한 선택지

- 네이티브 요소를 브라우저 기본 스타일로만 사용하면 의미와 기본 동작은 얻지만 애플리케이션 고유의 위계, 밀도와 상태 표현을 만들 수 없다.
- daisyUI처럼 완성된 테마를 제공하는 도구나 다른 스타일 포함 UI 라이브러리를 화면 기반으로 삼으면 초기 속도는 빠르지만 외부 테마의 조형과 구성요소 문법이 애플리케이션의 시각 기준이 된다.
- shadcn/ui처럼 소스 코드를 프로젝트가 가져가는 방식을 전체 기반으로 삼아도 초기 구성요소의 구조와 외형에서 출발하게 된다. 필요한 코드를 참고할 수 있다는 점과 고유 디자인 시스템을 정의했다는 것은 같지 않다.
- Base UI 같은 스타일 없는 접근성 부품을 폼 전체에 적용하면 복합 제어의 접근성 구현 부담을 줄일 수 있다. 다만 [Base UI 폼 안내](https://base-ui.com/react/handbook/forms)의 React Hook Form 예시는 `Controller`로 상태와 이벤트를 연결한다. Base UI가 모든 입력에 제어 상태를 강제하는 것은 아니고 네이티브 제출도 지원하지만, 단순 입력까지 일괄 적용하면 React Hook Form의 직접 등록 방식과 별도의 필드 상태 모델이 겹친다.
- Tailwind CSS, 네이티브 폼 요소와 자체 `shared/ui`를 조합하고, 외부 접근성 부품은 폼과 무관한 실제 필요에만 사용하면 네이티브 동작을 유지하면서 시각 규칙과 구성요소 API를 이 애플리케이션이 정할 수 있다.

## 결정 이력

- 초기 검토에서는 Tailwind CSS 위에 daisyUI 또는 shadcn/ui를 적용하는 방안을 비교했다.
- 추가로 스타일 포함 UI 라이브러리와 스타일 없는 접근성 부품을 검토했으나, 애플리케이션 고유의 디자인을 외부 기본 테마에서 출발시키지 않기로 했다.
- Base UI를 주요 후보로 검토한 뒤 React Hook Form 연결이 단순 입력까지 `Controller` 중심이 될 수 있다는 우려를 다시 확인했다. 라이브러리가 기술적으로 한 방식만 강제한다고 단정하지 않고, 현재 폼 요구에 가장 단순한 연결 방식을 기준으로 판단했다.
- 네이티브 요소 사용은 스타일을 포기하는 선택이 아니라 의미와 기본 동작을 보존한 채 고유 외형을 적용하는 선택으로 정리했다.
- 현재 결정은 Tailwind CSS와 자체 `shared/ui`를 디자인 시스템의 기반으로 승인하고, 외부 접근성 부품은 폼과 무관한 실제 복합 상호작용에만 제한하는 것이다.

## 승인된 결정과 이유

### Tailwind CSS와 의미 기반 디자인 토큰

- Tailwind CSS를 구성요소 스타일 작성과 반응형 상태 표현에 사용한다. [Next.js CSS 안내](https://nextjs.org/docs/app/getting-started/css)는 Tailwind CSS를 맞춤 디자인을 만드는 저수준 utility framework로 설명하고, 공통 스타일은 공통 구성요소로 분리하라고 권한다.
- 색, 글자, 간격, 모서리, 테두리, 깊이, motion, 포커스와 제어 요소 크기는 용도를 나타내는 디자인 토큰으로 관리한다. 화면 파일에 같은 임의 값을 반복해 사실상의 두 번째 디자인 규칙을 만들지 않는다.
- Tailwind의 정확한 버전과 PostCSS 연결 방식은 U1에서 Next.js 및 지원 브라우저와 함께 고정한다. [Tailwind CSS Preflight 안내](https://tailwindcss.com/docs/preflight)는 Tailwind를 가져오면 브라우저 기본 스타일 일부가 재설정된다고 설명하므로 운영용 CSS 파일과 네이티브 제어 요소에 적용 가능한 상태를 실제 브라우저에서 확인한다.

### 네이티브 폼 요소와 자체 `shared/ui`

- 단순 폼 제어는 실제 `button`, `input`, `textarea`와 `select`를 렌더링하고, checkbox는 `input[type="checkbox"]`로 렌더링한다. 현재 [W3C ARIA in HTML 권고안](https://www.w3.org/TR/html-aria/)은 HTML 요소의 기본 의미와 충돌하거나 같은 역할을 중복하는 ARIA 사용을 제한하며, [ARIA APG의 사전 안내](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/)는 ARIA 역할만으로 브라우저의 키보드 동작이 생기지 않는다고 설명한다.
- `shared/ui`에는 `Button`, `IconButton`, `TextField`, `Textarea`, `NativeSelect`, `Checkbox`와 `FieldMessage`처럼 업무 자료를 모르는 구성요소를 둔다. 각 구성요소는 자체 public API를 두고 하나의 전체 barrel로 다시 내보내지 않는다.
- 폼 구성요소는 네이티브 속성, `name`, 이벤트와 ref를 실제 요소까지 전달한다. 단순 입력은 [React Hook Form의 `register` API](https://react-hook-form.com/docs/useform/register)로 연결할 수 있어야 하며, 자체 구성요소가 `Controller`나 `useController` 사용을 강제하지 않아야 한다.
- 네이티브 요소에는 디자인 토큰과 Tailwind CSS로 고유 외형을 적용한다. 각 구성요소에 적용 가능한 기본, hover, `focus-visible`, pressed, disabled, 오류, 진행 중, 고대비와 reduced motion 상태를 정의하고 색 하나만으로 상태를 구분하지 않는다.

### 폼과 무관한 접근성 부품의 제한적 사용

- Dialog, Menu와 Tooltip처럼 폼 입력값을 만들지 않는 복합 상호작용은 네이티브 `<dialog>`, Popover API와 직접 구현을 먼저 비교한다. 지원 브라우저에서 포커스 이동, 키보드 상호작용과 화면 읽기 프로그램의 안내를 자체 구현으로 신뢰하기 어려울 때에만 스타일 없는 접근성 부품을 선택한다.
- 외부 부품을 추가하기 전에는 실제 사용할 구성요소, 정확한 버전, 직접 및 전이 의존성, 라이선스, 번들 영향과 Server 및 Client Component 조건을 검토한다. 패키지 전체를 디자인 시스템으로 채택하지 않는다.
- 외부 import와 API 변환은 외부 부품을 감싸는 `shared/ui` 구성요소 안에 둔다. 화면과 업무 동작을 구현하는 모듈은 외부 패키지를 직접 가져오지 않으며, 외부 기본 테마나 구성요소 이름을 사용자에게 보이는 디자인 기준으로 쓰지 않는다.
- 현재 요구사항에 없는 Combobox, 날짜 선택기나 맞춤 Select처럼 폼 입력값을 만드는 복합 제어가 필요해지면 이 결정을 먼저 다시 검토한다. 폼 접근성 부품을 예외로 추가한다고 추정하지 않는다.

### 디자인 확장 순서

- 먼저 실제 한국어 메모와 사용자가 메모 화면에서 반드시 거치는 상태를 사용해 글자, 색, 밀도, 제어 요소와 상태 조합을 대표 화면에 적용한다.
- 시각 및 접근성 담당자가 개인 메모의 공간 작업 특성, 정보 위계, 키보드 포커스와 상태 식별을 확인한 뒤 승인된 토큰과 `shared/ui`만 다른 화면으로 확장한다.
- 구성요소 수를 목표로 삼지 않는다. 두 화면 이상에서 같은 책임과 상태 규칙을 실제로 공유하거나, 한 화면에서 접근성 및 상태 일관성을 책임져야 할 때만 `shared/ui` 구성요소를 추가한다.

## 예상 결과와 계획 영향

U1은 Tailwind CSS와 필요한 빌드 연결의 정확한 버전 및 의존성을 확정하고 운영용 정적 CSS를 검증한다. U4는 디자인 토큰, 네이티브 폼 기반 `shared/ui`, 공통 탐색과 상태 표현을 대표 화면에서 완성한 뒤 담당자 승인을 받는다. U5부터 U10까지는 승인된 구성요소를 사용하고, U11은 여섯 화면의 시각 일관성, 네이티브 의미, 접근성 상태와 외부 테마 누출 여부를 함께 판정한다.

## 다시 검토할 조건

- 네이티브 요소로 현재 폼 요구와 접근성 기준을 충족할 수 없는 구체적인 복합 제어가 추가되는 경우
- 같은 역할의 `shared/ui` 구성요소가 화면마다 예외 스타일과 API를 요구해 공통 책임을 잃는 경우
- Tailwind CSS로 생성한 운영용 CSS 파일이 지원 브라우저나 Next.js 정적 내보내기에서 적용되지 않는 경우
- 폼과 무관한 접근성 부품이 폼 상태, 외부 테마 또는 애플리케이션 전역 Provider를 함께 요구하는 경우
- 디자인 시스템을 다른 애플리케이션이나 라이브러리 패키지에서도 사용해야 하는 백로그를 시작하는 경우
