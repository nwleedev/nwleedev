# 로컬 저장과 실행 중 상태 결정

사용자가 만든 현재 자료, 저장 전 메모 복구 초안과 모바일 일괄 복사 작업 초안은 IndexedDB에 보관한다. 일괄 복사 항목 제거 이력, 메모 삭제 복구 이력, 메모 선택, 활성 오른쪽 패널, 속성 초안, 분석 결과, 저장 전 제안과 일회성 출력은 현재 애플리케이션 실행의 메모리에만 둔다. IndexedDB를 백업으로 표현하지 않는다.

## 결정 질문과 요구 결과

[요구사항의 로컬 애플리케이션 결과](../requirements.md#의도한-결과)를 새로고침과 브라우저 종료 뒤에도 이어서 사용하려면 보관 대상과 일시 상태를 구분해야 했다. 백엔드 없는 저장이 제공할 수 없는 복구 범위도 숨기지 않아야 했다. 정적 사전 렌더링 중 브라우저 전역을 읽지 않으면서 라우트 이동에는 실행 중 상태를 유지하는 조립 위치와, 여러 object store를 함께 바꾸는 transaction 책임도 정해야 했다.

## 검토한 선택지

- 모든 상태를 메모리에만 두면 사용자가 만든 메모와 템플릿이 새로고침으로 사라진다.
- 모든 상태를 IndexedDB에 두면 분석 파생물, 모바일 일괄 복사 작업, 메모 선택과 실행 취소 이력의 무효화 및 migration 부담이 커진다.
- 사용자가 만든 현재 자료와 실행 중 파생 상태를 나누면 각 수명에 맞는 저장 방식을 사용할 수 있다.
- 브라우저 구현을 라우트마다 조립하면 이동할 때 실행 중 상태가 초기화되고, 서버 또는 정적 사전 렌더링 중 바로 조립하면 브라우저 전역 접근으로 빌드가 실패할 수 있다.
- 일괄 복사 항목과 사용 횟수를 서로 다른 저장 동작이 갱신하면 별도 transaction이 열려 일부만 반영될 수 있다. 하나의 목적별 저장 동작이 두 object store 변경을 책임지면 원자성을 한곳에서 판정할 수 있다.

## 결정 이력

- 초기 권장안은 메모, geometry, 누적 목록, 횟수, 템플릿과 설정을 IndexedDB에 저장하고 분석과 undo를 메모리에 두는 방식이었다.
- 재검토에서는 실행 취소 이력을 라우트 구성요소가 아니라 애플리케이션 범위 메모리에 두고, 메모 위치 변경과 내용 변경의 revision을 구분해야 한다는 점을 보완했다.
- 구현 가능성 검토에서는 공통 Client Provider의 수명과 정적 사전 렌더링에 안전한 조립 조건, 여러 object store를 바꾸는 transaction의 단일 책임이 추가로 필요하다는 점을 확인했다.
- 상호작용 검토에서는 첫 자료 읽기 전 화면을 실제 빈 상태로 오인하지 않도록 불러오기, 자료 표시, 읽기 실패와 다른 탭 대기를 구분해야 한다는 점을 보완했다.
- U2 자료 규칙 검토에서는 로컬 revision을 0부터 단조 증가하는 JavaScript 안전 정수로 확정했다. 계정 동기화에서 사용할 ETag나 분산 revision 표현은 이 로컬 값과 같은 타입으로 간주하지 않는다.
- 첫 모바일 일괄 복사 요구에서는 길게 눌러 추가한 항목과 메모의 선택 표시를 실행 중 항목 ID로 연결하기로 했다.
- 후속 모바일 요구는 길게 누르기를 개별 복사로 바꾸고, 목록 헤더 아이콘으로 시작한 일괄 복사 상태에서 짧게 누른 순서를 기록하도록 변경했다. 최신 요구는 반복 클릭을 별도 항목으로 기록하고 `초기화`로 현재 작업을 비우도록 확정했다. 후속 요구에서 `다음`은 별도 확인 페이지로 이동하고 작업 사본을 재정렬, 복제 및 삭제하도록 확정했으며, 당시에는 기존 저장 목록과의 추가 또는 교체 관계가 남아 있었다. 이전 선택 연결은 폐기하고 새 작업을 영구 저장 목록에 바로 연결하지 않는다.
- 넓은 화면의 선택한 메모 ID, 활성 오른쪽 패널과 속성 입력 초안은 실행 중 상태로 추가됐다. 적용이 승인된 geometry만 IndexedDB에 저장하며, 포커스 이동이나 패널 열림 상태를 메모 record에 저장하지 않는다.
- 메모 제거는 IndexedDB의 활성 목록에서 즉시 사라지는 결과와 실행 중 취소 동작을 함께 제공하도록 정해졌다. 당시에는 복원 자료의 보관 방식, 알림 수명과 새로고침 뒤 취소 범위가 후속 결정으로 남아 있었다.
- 현재 결정은 사용자 자료와 실행 중 상태의 수명을 나누고, 공통 Provider에서 브라우저 구현을 한 번 조립하며, 목적별 저장 동작이 여러 object store의 transaction을 책임지게 하는 것이다. 내보내기와 가져오기는 현재 범위에 포함하지 않는다.
- 구현 필수 결정 재검토에서 메모 자동 저장 또는 모바일 명시적 저장 직전의 입력과 모바일 일괄 복사 확인 작업이 새로고침으로 사라지는 위험을 확인했다. `noteDrafts`와 `mobileBatchCopyDrafts`를 복구용 IndexedDB 자료로 추가하되 기준 메모와 저장된 일괄 복사 목록에서는 분리하기로 했다.
- 같은 재검토에서 메모 삭제 취소는 자동 만료 없이 현재 실행의 LIFO 이력으로 관리하고, 새로고침 뒤 복원은 휴지통 기능이 없는 현재 범위에서 제공하지 않기로 했다.

## 승인된 결정과 이유

- IndexedDB에는 메모 원문, 전체 revision, content revision, geometry, 현재 일괄 복사 항목과 순서, 사용 횟수, 저장된 템플릿, 조작 설정, 저장 전 메모 복구 초안과 하나의 활성 모바일 일괄 복사 작업 초안을 보관한다.
- 메모 원문이 바뀌면 content revision을 증가시킨다. 위치, 크기나 z-order만 바뀌면 전체 revision만 증가시키고 content revision은 유지한다.
- 로컬의 전체 revision과 content revision은 0 이상의 JavaScript 안전 정수다. 실제 값이 달라진 저장 변경마다 해당 revision을 한 번 증가시키며, 같은 값을 다시 적용한 경우에는 증가시키지 않는다.
- 일괄 복사 항목 제거 undo 및 redo, 메모 삭제 LIFO 복구 이력, 분석 요청과 결과, 템플릿 제안에 사용할 두 원문 줄의 선택 쌍, 저장 전 템플릿 제안과 일회성 출력은 메모리에 둔다.
- 선택한 메모 ID, `note-properties` 또는 `batch-copy`인 최근 활성 오른쪽 패널과 저장 전 X, Y, 너비 및 높이 입력 초안은 메모리에 둔다. 유효한 geometry 적용만 메모 record를 갱신한다. 패널 전환만으로 선택, 입력 초안과 일괄 복사 자료를 지우지 않는다.
- 모바일 일괄 복사 상태와 확인 페이지의 이번 작업은 저장 목록과 분리한 `mobileBatchCopyDrafts`의 한 활성 초안으로 둔다. 확인 단계의 재정렬, 복제와 삭제는 이 초안만 바꾸고 메모 repository, 저장 목록과 사용 횟수를 바꾸지 않는다. route 이동과 새로고침에서는 복원하고 헤더 뒤로가기 또는 확인 페이지 `취소`에서 지운다.
- 넓은 화면 자동 저장과 모바일 상세 편집의 최신 원문은 `noteDrafts`에 기준 메모 ID, 기준 content revision과 수정 시각을 함께 둔다. 메모 저장 transaction이 완료되면 대응 초안을 지우며, 시작할 때 메모보다 새로운 초안만 복구 후보로 사용한다.
- 메모 제거 transaction이 완료된 뒤 복원 스냅샷을 현재 실행의 LIFO 메모리 이력에 넣는다. route 이동에서는 유지하고 새로고침에서는 지운다.
- `PersonalNotesProvider`는 명시적인 Client Component 진입점으로 두고 공통 루트 layout의 자식에서 한 번 유지한다. `createLocalApplication`과 브라우저 구현의 생성 과정에서는 브라우저 전역을 읽지 않으며, IndexedDB, Clipboard와 Worker는 브라우저에서 실제 동작을 시작할 때 접근한다.
- 일괄 복사 항목 추가와 해당 횟수 증가는 하나의 목적별 저장 동작으로 제공한다. 현재 `IndexedDbAccumulationWriter` 이름을 바꾸려면 기존 schema 및 호출자 migration을 함께 설계하며, 구현은 두 object store의 request를 같은 readwrite transaction에 등록하고 `complete` 또는 중단을 최종 결과로 돌려준다.
- IndexedDB transaction의 완료를 확인한 뒤에만 저장 성공으로 표시한다.
- HTTP와 HTTPS를 포함해 origin이 다르면 자료가 공유되지 않는다는 사실을 검증과 사용 안내에서 고려한다.
- 현재 범위에는 내보내기, 가져오기와 브라우저가 지운 자료의 복구를 포함하지 않는다. 저장소 영구 보관 요청이 승인되어도 백업이라고 표시하지 않는다.
- 첫 자료 읽기는 `불러오는 중`, `사용 가능한 빈 상태`, `자료 표시`, `읽기 실패`와 `다른 탭으로 인한 대기`를 구분한다. 첫 읽기가 끝나기 전과 읽기 실패 중에는 자료 변경 동작을 제공하지 않으며 실패 안내에는 다시 시도, 다른 탭 확인과 기존 자료를 덮어쓰지 않았다는 설명을 포함한다.
- `noteDrafts`와 `mobileBatchCopyDrafts`의 쓰기도 transaction `complete` 뒤에만 복구 가능한 것으로 처리한다. 최신 초안조차 기록되지 않은 변경이 있을 때만 제한적으로 `beforeunload` 경고를 사용한다.

[IndexedDB 3.0](https://w3c.github.io/IndexedDB/#transaction-lifetime)은 transaction의 완료와 중단 수명을 정의한다. [Storage Standard](https://storage.spec.whatwg.org/#storage-keys)는 자료가 storage key에 묶인다는 점을, [persistence 절](https://storage.spec.whatwg.org/#persistence)은 영구 보관 요청이 자료 복구를 보장하지 않는다는 점을 뒷받침한다.

## 예상 결과와 계획 영향

저장 interface는 object store 구조를 호출자에게 드러내지 않고 필요한 동작을 제공하며 실제 브라우저 IndexedDB 구현으로 검증한다. 가짜 IndexedDB만으로 완료를 판정하지 않는다. 운영용 빌드, 라우트 왕복과 새로고침을 통해 조립 시점, 사용자 자료 및 실행 중 상태의 수명과 다중 저장 변경의 원자성을 확인한다.

## 다시 검토할 조건

- 내보내기, 가져오기 또는 브라우저 자료 복구가 요구되는 경우
- 계정 동기화 백로그를 시작하는 경우
- 분석 결과 비교나 새로고침 뒤 undo 복원이 요구되는 경우
- 여러 모바일 일괄 복사 작업을 동시에 유지하거나 다른 기기와 초안을 동기화해야 하는 경우
- Next.js의 정적 사전 렌더링 또는 layout 수명 규칙이 바뀌는 경우
