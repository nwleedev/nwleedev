# 메모 제거와 취소 알림 결정

메모 제거는 확인 대화상자 없이 대상 메모를 활성 목록에서 바로 없앤다. 메모 작업 주 영역의 중앙 하단에는 5초 동안 `메모를 제거했습니다.`와 오른쪽 `취소` 버튼을 함께 표시하고, 그 안에 취소하면 제거 전 원문, 위치, 크기와 겹침 순서를 복원한다. 연속 삭제는 현재 실행의 LIFO 이력으로 관리하고 새로고침 뒤에는 복원하지 않는다.

## 결정 질문과 요구 결과

[메모 제거 요구사항](../requirements.md#반드시-지킬-조건)은 헤더의 삭제 아이콘 실행 결과를 바로 확인하면서 실수한 제거를 같은 화면에서 되돌릴 수 있게 한다. 알림 위치, 복원 범위와 키보드 포커스가 메모 편집, 캔버스 이동 및 오른쪽 패널과 충돌하지 않아야 한다.

## 검토한 선택지

- 제거 전에 확인 대화상자를 열면 실수를 막을 수 있지만 반복 작업을 매번 중단하고 새 요구의 취소 알림과 역할이 겹친다.
- 즉시 영구 삭제하면 단순하지만 취소 버튼으로 복원할 자료가 남지 않는다.
- 활성 목록에서는 즉시 제거하고 원래 메모 자료를 복원할 수 있게 보관하면 사용자가 결과를 바로 확인하고 실수를 되돌릴 수 있다.

## 결정 이력

- 이전 요구사항은 헤더에 삭제 아이콘을 두었지만 확인, 실행 취소, 휴지통과 영구 삭제 시점은 정하지 않았다.
- 후속 요구에서 제거 직후 주 작업 영역 중앙 하단에 안내와 `취소`를 제공하도록 승인됐다.
- 이 결정으로 제거 전 확인 여부는 해소됐지만 알림 수명, 연속 제거와 새로고침 뒤 취소 범위가 남았다.
- 구현 필수 결정 재검토에서 자동 만료, 마지막 삭제 한 건만 유지, 여러 알림을 동시에 쌓는 방식을 비교했다. 취소 동작이 시간 때문에 사라지지 않도록 자동 만료를 없애고, 한 알림 위치에서 가장 최근 삭제부터 처리하는 LIFO 이력을 채택했다.
- 같은 재검토에서 삭제 뒤 포커스는 알림으로 옮기지 않고 다음 메모, 이전 메모와 새 메모 제어 순으로 옮기기로 했다. 취소로 복원하면 복원된 메모의 선택 지점으로 옮긴다.
- 2026년 9월 3일 후속 요구는 모든 toast를 3초 뒤 닫도록 정했다. 이전의 자동 만료 없는 제거 알림은 이 요구로 대체하며, `취소`는 현재 알림이 보이는 3초 동안만 제공한다. 복원 자료의 LIFO 수명과 새로고침 시 초기화 규칙은 바꾸지 않는다.
- 같은 날 추가 요구에서 모든 toast의 수명을 5초로 늘렸다. 3초 결정은 이 값으로 대체하며 복원 자료의 LIFO 수명과 새로고침 시 초기화 규칙은 그대로 유지한다.
- 2026년 9월 4일 코드 검토에서 route를 오간 뒤 알림 component가 다시 mount되면 같은 삭제의 5초가 새로 시작되고, 비동기 복원 중 다른 메모를 삭제하면 완료 시점의 최근 이력을 잘못 제거할 수 있음을 확인했다. 표시 component의 수명 대신 삭제 완료 시각에서 만료 시각을 한 번 정하고, 복원 성공 뒤에는 시작할 때 잡은 스냅샷만 이력에서 제거하기로 했다.

## 승인된 결정과 이유

- 헤더의 삭제 아이콘을 실행하면 확인 대화상자를 먼저 열지 않고 대상 메모만 활성 목록에서 제거한다.
- 다른 메모의 원문, geometry와 상대 겹침 순서는 바꾸지 않는다.
- 메모 작업 주 영역의 중앙 하단에 `메모를 제거했습니다.`를 표시하고 같은 알림 오른쪽에 `취소` 버튼을 둔다.
- 알림과 `취소` 실행 기한은 제거가 완료된 시각부터 5초다. route 이동, component 재생성, 창 비활성화와 timer 지연은 이 기한을 새로 시작하지 않는다. 새 제거 결과가 오면 새 삭제에 대해서만 별도의 5초를 시작한다.
- 알림은 전역 상단 탐색, 오른쪽 패널과 변환되는 캔버스의 자식이 아니다. 캔버스 시점을 이동하거나 오른쪽 패널을 열어도 주 작업 영역 중앙 하단의 화면 위치를 유지한다.
- 알림이 나타날 때 현재 키보드 포커스를 `취소`로 강제로 옮기지 않는다. 상태 문구는 보조 기술에 전달하고 `취소`는 일반 Tab 순서에서 실행할 수 있어야 한다.
- 취소하면 같은 메모 ID, 원문, revision 관계, 위치, 크기와 겹침 순서를 제거 전 상태로 복원한다. 복원 때문에 다른 메모의 content revision을 바꾸지 않는다.
- 메모 제거 transaction이 완료되면 활성 저장 자료에서 삭제된 것으로 처리하고, 복원 스냅샷은 현재 애플리케이션 실행의 LIFO 이력에 넣는다. 가장 최근 삭제 한 건만 5초 알림에 표시한다. 기한이 지난 스냅샷은 실행 가능한 이력에서 제거하며 이전 이력을 자동으로 다시 표시하지 않는다.
- 복원은 실행 직전에 대상 스냅샷의 제거 시각과 만료 여부를 확인한다. 비동기 복원이 끝나기 전에 다른 삭제가 추가돼도 복원 시작 때의 메모 ID와 제거 시각이 같은 스냅샷만 이력에서 제거한다.
- 삭제 이력은 애플리케이션 안의 route 이동에서 유지하고 새로고침에서는 지운다. 새로고침 뒤 취소를 제공하려면 별도 휴지통 자료 결정이 필요하다.
- 삭제된 메모 또는 그 자식이 포커스를 갖고 있었다면 다음 `tabIndex` 메모, 이전 메모, 새 메모 제어 순으로 포커스를 옮긴다. 취소로 복원하면 복원된 메모 선택 지점으로 포커스를 옮긴다.

[메모 선택, 속성 편집과 제거 복구 조사](../references/note-selection-properties-and-removal-research.md)는 실행 취소 결과, 동작이 있는 알림과 제거 뒤 키보드 포커스에 관한 공식 근거를 기록한다. [데스크톱 입력과 피드백 복원력 조사](../references/desktop-input-and-feedback-resilience-research.md)는 5초 제한과 hover, focus 및 reduced motion을 고려한 전환 사례를 비교하고 현재 요구와 공식 지침 사이의 차이를 기록한다.

## 예상 결과와 계획 영향

U2와 U3는 제거 복원 자료, 절대 만료 시각과 실행 중 이력을 정의하고, U4는 중앙 하단의 5초 알림과 동작 버튼을 디자인 시스템에 추가한다. U5는 대상 메모 ID와 제거 시각이 분명한 제거 및 취소 명령을 연결하고, U11은 선택된 메모와 포커스된 메모를 각각 제거한 뒤 자료와 포커스가 유지되는지 확인한다. 제거, 만료와 복원의 순수 자료 전이는 TDD로 개발하고 알림 위치, route 재진입을 포함한 수명, live region, 전환과 포커스 이동은 실제 브라우저에서 확인한다.

## 다시 검토할 조건

- 여러 메모를 빠르게 제거했을 때 가장 최근 삭제부터 복원되는 결과를 예측하기 어려운 경우
- 5초가 지나기 전에 `취소`를 발견하고 실행하기 어렵거나 알림 전환이 주 작업을 가리는 경우
- 토스트가 사라진 뒤 같은 복원 동작을 실행할 지속적인 위치가 필요하다고 판단되는 경우
- 새로고침 뒤에도 삭제를 취소해야 하거나 휴지통이 추가되는 경우
- 삭제와 복원 뒤 포커스 이동이 메모의 `tabIndex` 순서와 맞지 않는 경우
