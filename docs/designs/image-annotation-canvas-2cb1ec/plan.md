# 이미지와 메모를 배치하는 캔버스 구현 계획

로컬 프로젝트 목록에서 작업을 열어 이미지와 메모를 배치하고, 결과 이미지를 내보내거나 편집용 ZIP으로 보관하는 흐름을 구현한다. 목록 헤더, ZIP 불러오기 창과 전체 내보내기 여백은 최신 시안과 요구사항을 기준으로 검토한다.

기준은 [캔버스 요구사항](requirements.md), [라우팅 결정](decisions/browser-routing.md), [라이브러리 결정](decisions/canvas-and-zip-libraries.md)이다. 개발 전 [저장소 개발 지침](../../dev/README.md)에서 새 앱에 적용할 검사와 명령을 확인한다. 앱 소스, 테스트와 설정은 새 앱 패키지에 두고 기존 포트폴리오의 앱 진입 링크는 통합 단계에서 변경한다.

## 구현 전 ESLint 설정

상태: 완료. 캔버스 패키지의 lint와 TypeScript 검사 및 빌드가 통과했다. 조립부 외부의 `idb` 직접 import는 거부되고 조립부의 import는 허용된다.

[코드 구조](requirements.md#코드-구조)에 따라 기능 코드를 작성하기 전에 새 앱의 `eslint.config.mjs`를 구성한다. 지원 버전을 확인한 뒤 React Hooks의 `rules-of-hooks`, `static-components`와 해당 버전에서 지원하는 컴포넌트 및 Hook 팩토리 검사를 설정한다. FSD 참조 방향, 슬라이스 내부 접근, 구체 어댑터 직접 import는 파일 범위를 제한한 `no-restricted-imports`와 필요한 경우 경로를 해석하는 경계 규칙으로 검사한다. 별칭과 상대 경로를 모두 고려하며 조립부의 허용 범위를 지정한다. [React 정적 컴포넌트 검사](https://react.dev/reference/eslint-plugin-react-hooks/lints/static-components), [ESLint import 제한](https://eslint.org/docs/latest/rules/no-restricted-imports)

TDD는 적용하지 않는다. 기존 ESLint CLI로 적용 설정을 확인하고 필요한 경우 표준 입력으로 허용 및 금지 사례의 판정을 확인한다. 별도 스크립트나 픽스처는 추가하지 않는다. 직접 컴포넌트 호출이나 동적 import처럼 설정한 규칙이 잡지 못하는 형태와 모듈 책임, Props 전달, 상태의 기준 위치는 검토에서 확인한다. 폼과 서버 데이터 전용 규칙은 해당 도구를 채택한 절차에서 다시 검토한다.

설정이 완료되려면 ESLint의 `--print-config`에서 UI, 모델과 조립부에 의도한 규칙이 적용돼야 한다. 표준 입력을 사용한다면 화면의 구체 어댑터 import와 렌더링 중 컴포넌트 정의는 거부되고, 하위 슬라이스의 공개 API와 조립부의 구체 어댑터 import는 허용되는지 확인한다. 별칭과 상대 경로가 같은 대상에 닿는 경우도 확인한다. 설정으로 판정하지 못하는 항목은 해당 기능 절차의 검토에 포함한다. [ESLint CLI](https://eslint.org/docs/latest/use/command-line-interface)

## 각 절차의 착수와 완료 기준

절차마다 공식 문서에서 적용할 패턴과 동작을 확인하고, 추가하거나 수정할 코드와 제거, 통합 또는 분리할 코드를 정한다. 컴포넌트에 의존성 주입과 제어 역전이 필요한지 절차당 한 번 판단한다. 브라우저 저장소와 같은 외부 동작을 조립부에서 연결하고, 화면 컴포넌트 테스트에서는 실제 사용자 조작과 관찰 가능한 상태를 검증한다. 저장 동작 자체는 실제 IndexedDB 통합 테스트로 확인한다. 대단원 코드 리뷰에서 중복된 `useState`, `useEffect`, `useMemo`, `useCallback`, `useRef`를 찾고 각 ref의 용도를 확인한다. [React useRef](https://react.dev/reference/react/useRef)

컴포넌트를 추가하거나 변경할 때 각 Props를 받는 곳에서 화면 표시, 판단 또는 조작에 직접 사용하는지 확인한다. 하위 컴포넌트에 그대로 넘기거나 전달용 콜백 안에서만 호출한다면, 실제로 쓰는 컴포넌트에 직접 연결하고 중간 컴포넌트는 `children`으로 배치하는 방식을 먼저 검토한다. 코드 리뷰에서 컴포넌트마다 변경 이유와 책임을 설명할 수 있는지 확인한다.

작업 전 대상 슬라이스와 추가, 수정, 제거할 파일을 확인한다. 기존 파일을 확장할 때는 기존 코드와 변경할 코드가 같은 책임을 맡고 같은 이유로 변경되는지 확인한다. 외부 동작을 연결하는 절차는 필요한 기능, 주입하는 곳, 실제로 호출하는 곳을 정한다. 상태를 추가하는 절차는 원본 상태를 변경하는 곳과 그 값에서 표시값을 구하는 곳을 정한다. 사용처가 하나인 코드는 해당 페이지에서 시작하고, 이름은 상위 경로의 역할을 되풀이하지 않는다.

각 절차의 마지막에 변경한 import, Props, Context와 상태 위치를 한 번 검토한다. Props는 받는 곳에서 소비하는 값과 호출하는 함수로 제한한다. 화면 합성은 `children`과 명시적 하위 컴포넌트로 표현한다. 깊은 하위 트리에서 값을 공유해야 Context를 추가하며, 주입 접근 훅은 현재 기능을 반환하는 일만 맡는다. 렌더링 중 컴포넌트 타입을 만들거나 컴포넌트 함수를 직접 호출하는 곳이 없는지 확인한다. 발견한 문제를 해결하고 기존 검사와 해당 절차의 동작 검증을 통과하면 절차를 마친다. [React 상태 공유](https://react.dev/learn/sharing-state-between-components), [FSD 공개 API](https://feature-sliced.design/docs/reference/public-api)

React Hook Form, TanStack Query, Zustand와 서버·클라이언트 분리 규칙은 해당 도구나 실행 환경을 채택한 절차에서 적용한다. React Hook Form을 채택하면 폼 수명과 필드별 구독을 확인하고 편집 모델과 같은 값을 계속 복제하지 않는지 검토한다. 서버 조회를 추가하면 쿼리 키와 취소 신호, 캐시 갱신, 성공 데이터의 표시용 파생과 입력 검증을 각각 확인한다. 현재 로컬 조회에는 라우터 로더와 주입된 저장소를 사용한다.

## FSD 파일 구성과 의존성 조립

상태: 파일 배치와 주입 위치를 확정했다. 라우터와 목록 슬라이스의 초기 진입점을 사용하며, 저장소와 Worker의 연결은 해당 기능을 구현할 때 추가하고 검증한다.

[코드 구조](requirements.md#코드-구조)에 따라 다음 파일 위치를 새 앱의 `src/` 기준으로 사용한다. `app`은 라우터와 의존성 조립을 맡는다. `pages`는 화면별 UI와 조작 흐름을 맡고, `entities`는 여러 화면이 사용하는 문서 모델과 규칙을 맡는다. `shared`에는 도메인과 무관한 UI와 스타일을 둔다. 공통 사용처가 생겼을 때 `features` 또는 `widgets`로 분리한다. 서로 다른 페이지가 직접 참조하거나 하위 레이어가 상위 레이어를 가져오지 않는다. 각 슬라이스에서 다른 레이어에 제공할 항목만 `index.ts`에 명시한다. [FSD 레이어](https://feature-sliced.design/docs/reference/layers), [FSD Public API](https://feature-sliced.design/docs/reference/public-api)

의존성 조립은 `app/composition/`에서 수행한다. 프로젝트 저장과 조회의 타입은 `entities/project/model/`에서 정의하고, 편집용 파일과 이미지 출력에 필요한 타입은 해당 동작을 맡는 페이지의 `model/`에서 정의한다. 조립부에서 IndexedDB, zip.js와 Worker 연결을 구성하고 각 페이지 및 로더에 필요한 함수만 전달한다. React 트리 여러 곳에서 같은 의존성을 쓰면 역할별 Context를 사용할 수 있다. 조립에 필요한 항목은 일반 화면 진입점과 분리해 명시적으로 노출한다. 저장소와 Worker는 브라우저에서 사용 시 초기화하고 앱이 관리하는 수명이 끝나면 정리한다. [의존성 주입과 구성 분리](https://martinfowler.com/articles/injection.html)

이 절차에는 별도 TDD를 적용하지 않는다. 기능 절차의 테스트에서 조립된 실제 동작을 확인한다. 통합 단계에서 레이어 방향, 슬라이스 내부 파일 우회, 순환 참조, 다른 앱의 소스 참조가 없는지 확인한다.

조립부 검토에서는 목록 조회, 프로젝트 읽기 및 저장, ZIP 읽기 및 쓰기, 이미지 출력의 소비자가 각각 사용하는 기능만 받는지 확인한다. 조립부가 구성한 저장소와 Worker의 수명은 컴포넌트 렌더링과 분리한다. 구현체를 바꿀 때 UI와 문서 모델의 import 또는 구현이 바뀌어야 한다면 의존성 연결을 다시 검토한다.

## 목록 헤더와 조작 시안 확정

상태: 헤더와 카드 그리드의 표시 구조를 구현했다. Chromium의 360px와 1053px 화면에서 헤더 하나, 문구 없는 직사각형과 가로 넘침이 없는 것을 확인했다. 새 프로젝트와 불러오기는 각 절차에서 동작을 연결한다. 실제 데이터가 담긴 카드와 입력의 포커스 표시는 해당 화면을 연결한 뒤 검증한다.

목록 헤더와 로고 자리 표시는 `pages/projects/ui/`에 둔다. 캔버스 헤더는 `pages/editor/ui/`에 둔다. 공통 아이콘 버튼은 `shared/ui/`, 테마 토큰은 `shared/styles/`에서 관리한다.

[로컬 프로젝트 관리와 UI 검토 기준](requirements.md#로컬-프로젝트-관리)을 적용한다. 목록 전용 헤더 왼쪽에는 문구 없는 직사각형을 두고, 오른쪽에는 새 프로젝트와 불러오기 아이콘 버튼을 배치한다. 본문은 캔버스 미리보기, 프로젝트 이름과 마지막 편집 시각을 담은 카드 그리드로 구성한다. 도움말과 설정은 [백로그](requirements.md#백로그)에서 관리한다. [Carbon 버튼 지침](https://carbondesignsystem.com/components/button/usage/), [W3C 버튼 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/button/)

TDD는 적용하지 않는다. 데스크톱과 모바일에서 카드의 미리보기와 제목이 읽히고 가로 넘침이 없는지 확인한다. 직사각형 안에 문구가 없는지, 버튼에 접근 가능한 이름이 있는지 확인한다. 클릭과 터치에서 기본 테두리가 나타나지 않고 키보드에서는 포커스 표시가 한 겹으로 보이는지 확인한다. 붉은 배경과 흰색 계열 아이콘의 대비를 실제 적용 색으로 확인한다. [W3C 포커스 표시](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html), [W3C 비텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

편집기와 내보내기 입력을 연결할 때 클릭, 터치와 Tab 이동을 확인한다. 기존 입력 테두리의 색이나 굵기로 포커스를 표시하며 두 겹 테두리나 레이아웃 이동이 없는지 확인한다. 버튼과 입력의 상태 색은 `shared/styles/`의 테마 토큰으로 관리하고 JSX의 색상 리터럴을 점검한다.

헤더 버튼은 이름, 상태와 실행 콜백만 사용한다. 목록 페이지가 새 프로젝트 및 불러오기 동작을 연결하고, 공통 아이콘 버튼은 라우터나 저장소를 가져오지 않는지 확인한다. 목록과 편집기 헤더를 비교해 실제 동작과 변경 이유를 공유하는 요소만 공통화한다.

## 프로젝트 목록과 로컬 저장

상태: 빈 프로젝트 생성과 조회를 연결했다. 프로젝트, 원본, 배치와 메모 배치 정보는 하나의 트랜잭션으로 추가하고 삭제한다. Chromium에서 v1 프로젝트 보존, 다시 열었을 때 원본 바이트와 메모 연결 복원, 잘못된 참조 거부와 중복 메모 저장의 롤백을 확인했다. 배치 삭제 후 공유 원본 보존, 마지막 참조 삭제 후 원본 정리와 프로젝트 간 삭제 격리도 확인했다. 편집 화면에서 호출하는 연결은 편집기 절차에서 추가한다.

이미지 이동과 크기 조절 중에는 미리보기를 갱신하고, 조작을 완료하면 최종 값을 저장한다. 취소한 조작은 저장하지 않는다. 메모는 마지막 입력 이후 짧은 대기 시간을 두고 변경분을 저장한다. 입력이 이어지면 대기 시간을 다시 시작하고, 한글 조합이 끝난 뒤 저장을 예약한다. 구체적인 대기 시간은 연속 입력과 저장 요청 횟수를 확인해 정한다.

편집기 연결 뒤에는 드래그 중 저장 순서가 바뀌지 않고 완료 후 최종 위치 또는 크기가 한 번 저장되는지 확인한다. 메모는 연속 입력 중 저장을 미루고 입력을 멈추면 마지막 내용이 저장되는지 확인한다. 두 경우 모두 새로고침 후 커밋한 값을 복원한다.

목록 UI와 상태는 `pages/projects/ui/`와 `pages/projects/model/`에 둔다. 프로젝트 식별자와 문서 데이터는 `entities/project/model/`, 저장소 구현은 `app/composition/storage/`, 목록과 편집기 로더 연결은 `app/router/`에서 관리한다.

[로컬 프로젝트 관리](requirements.md#로컬-프로젝트-관리)와 라우팅 결정에 따라 목록과 편집 화면을 연결한다. 조회와 화면 이동은 React Router의 로더 및 오류 처리를 사용한다. 목록의 빈 상태, 조회 중, 조회 실패와 존재하지 않는 프로젝트를 구분한다. [React Router 경로 객체](https://reactrouter.com/start/data/route-object)

IndexedDB의 필드, 키와 인덱스는 [로컬 프로젝트 저장 스키마](references/local-storage-schema.md)를 기준으로 정의한다. 각 레코드는 하나의 대상을 나타내며 목록과 편집 화면에서 필요한 값을 조회해 조합한다.

`app/composition/storage/`에서 `idb`로 데이터베이스를 열고 조회, 저장과 버전별 업그레이드를 처리한다. `DBSchema`로 store별 키와 레코드 타입을 정의한다. 읽은 레코드는 저장된 버전에 맞게 검증하고, 쓰기는 `tx.done`이 완료된 뒤 성공으로 처리한다. [idb 문서](https://github.com/jakearchibald/idb)

- `projects`는 프로젝트 식별자, 제목, 수정 시각과 마지막으로 저장한 변경 순서를 관리한다.
- `assets`는 프로젝트에 속한 원본의 식별자, 파일 유형, 원본 크기와 `Blob`을 관리한다. 같은 원본을 다시 배치해도 같은 프로젝트 안에서는 기존 원본 레코드를 참조할 수 있다.
- `placements`는 프로젝트와 원본을 참조하며 좌표, 배치 크기, 겹침 순서와 개별 품질 설정을 관리한다.
- `memos`는 배치한 이미지를 참조하며 부착 위치, 너비와 높이를 관리한다. 텍스트 동시 편집에 필요한 변경 기록은 메모 식별자로 연결한 별도 store에서 관리한다.

목록 조회는 원본 이미지까지 읽지 않는다. 프로젝트별 배치와 배치별 메모를 식별자와 인덱스로 조회한다. IndexedDB는 참조 무결성을 자동으로 검사하지 않으므로 저장 구현에서 참조 대상의 존재와 같은 프로젝트에 속하는지를 확인한다.

프로젝트 생성 및 ZIP 불러오기는 프로젝트, 원본, 배치와 메모를 한 쓰기 트랜잭션에서 저장한다. 배치나 프로젝트를 삭제할 때는 관련 레코드도 같은 트랜잭션에서 정리한다. 남은 배치가 참조하는 원본은 보존한다. 트랜잭션이 완료된 뒤에만 목록이나 성공 상태에 반영한다. [IndexedDB object store와 트랜잭션](https://www.w3.org/TR/IndexedDB-3/#transaction-construct)

TDD를 적용한다. 실제 브라우저의 IndexedDB를 사용하는 저장소 통합 테스트에서 프로젝트, 원본, 배치와 메모를 저장한다. 연결을 닫고 다시 열어 프로젝트 목록과 문서를 조회하고 원본 바이트, 배치와 메모 연결을 확인한다. 저장과 조회가 구현되기 전에는 복원 검사가 실패해야 한다. 라우터를 연결한 뒤에는 존재하지 않는 프로젝트 주소에서 목록으로 돌아갈 수 있는지 확인한다.

첫 스키마에서는 빈 DB에 필요한 store와 인덱스가 생기고 프로젝트를 저장할 수 있는지 확인한다. 실제 스키마 변경이 생기면 이전 지원 버전에서 현재 버전으로 바로 열기, 변환 중단 후 기존 버전과 레코드 보존, 이전 탭의 연결 때문에 업그레이드가 대기했다가 연결 종료 후 재개되는 상황을 검증한다. [IndexedDB 업그레이드 트랜잭션](https://www.w3.org/TR/IndexedDB-3/#upgrade-transaction-construct)

로더의 목록 결과를 별도 Context나 스토어에 복제하지 않는다. 목록 항목은 표시할 프로젝트 요약과 실행할 조작만 받는다. 저장소 구현에서 저장을 완료한 뒤 목록 조회 결과가 갱신되는지, 오류 안내와 목록 항목이 직접 IndexedDB를 호출하지 않는지 확인한다.

실제 IndexedDB에서 다른 프로젝트의 원본을 참조하는 배치와 존재하지 않는 배치에 붙인 메모의 저장을 각각 시도한다. 저장이 거부되고 다시 열었을 때 기존 레코드와 저장 순서가 유지되는지 확인한다.

브라우저 통합 테스트에서 관련 레코드 중 일부를 쓴 뒤 트랜잭션이 중단되는 상황을 재현한다. 다시 조회했을 때 새 프로젝트가 목록에 없어야 하며, 기존 프로젝트의 배치와 원본을 계속 읽을 수 있어야 한다. 같은 원본을 참조하는 배치 두 개 중 하나를 삭제한 뒤 남은 배치의 원본과 메모가 복원되는지도 확인한다.

## 여러 탭에서 수정 반영

상태: IndexedDB v4에 메모 변경분을 저장하고 메모를 삭제하면 함께 정리한다. Chromium 두 탭에서 알림 직후 조회, 저장한 Yjs 변경분으로 본문 복원과 동일 변경 ID의 재시도를 확인했다.

이미지 위치와 크기 및 메모 크기 수정 명령을 추가했다. 각 수정은 트랜잭션에서 최신 값을 읽어 요청한 항목만 바꾼다. 편집 명령은 저장 순서 갱신과 커밋 알림을 공유한다. Chromium 두 탭에서 동시에 바꾼 이미지 위치와 크기가 모두 남고 같은 위치나 메모 크기의 수정은 마지막 커밋 값이 남는 것을 확인했다. 잘못된 크기와 삭제된 배치의 저장도 거부했다.

편집 화면의 라우터 로더가 프로젝트와 하위 레코드를 같은 읽기 트랜잭션에서 가져온다. 새 저장 알림이나 화면 복귀를 감지하면 로더를 다시 실행한다. Chromium 두 탭에서 제목 갱신과 이전 알림 무시를 확인했다. 알림 없이 커밋한 제목은 `visibilitychange`를 발생시켜 재조회하는 것을 확인했다. [React Router 재검증](https://reactrouter.com/api/hooks/useRevalidator)

기존 메모의 입력을 `Y.Text`에 연결했다. Chromium 두 탭에서 한 탭의 삭제와 다른 탭의 삽입이 합쳐지고 포커스와 다시 연 탭의 본문이 유지되는 것을 확인했다. 조합 이벤트를 발생시켜 다른 탭의 변경이 한글 조합이 끝난 뒤 반영되는 것도 확인했다. 저장 명령을 한 번 실패시키는 모델 검사에서 동일 변경 ID로 재시도한 뒤 새 입력도 저장했다.

다른 탭이 배치를 삭제하면 저장하지 못한 메모는 열린 편집 화면에서 읽기 전용으로 표시한다. Chromium에서 자동 저장 대기 중인 입력과 조합 중인 입력을 각각 삭제해, 입력을 복사할 수 있고 배치는 되살아나지 않음을 확인했다. 조합 검사는 합성 이벤트를 사용했다. 실제 한글 IME와 편집기 조작을 연결한 검증은 남아 있다.

대단원 코드 리뷰에서 조합 시작 전에 예약된 자동 저장을 취소하고 조합이 끝나면 다시 예약하도록 수정했다. 탭을 다시 조회할 때는 메모마다 이미 적용한 변경 ID를 건너뛴다. Chromium 두 탭에서 조합 중 저장 순서가 유지되고 조합 종료 뒤 한 번 증가하는 것을 확인했다. 메모의 두 ref는 각각 입력 요소와 연결 객체를 가리킨다. 입력 상태와 로더 데이터의 중복 저장은 발견하지 않았다.

편집 동작과 병합 규칙은 `entities/project/model/`에 두고, 트랜잭션과 탭 간 알림은 `app/composition/storage/`에서 연결한다. 편집 화면의 입력, 드래그와 선택 상태는 `pages/editor/model/`에서 관리한다.

두 탭에서 같은 대상의 위치나 크기를 바꾸면 IndexedDB에서 마지막으로 커밋된 값을 표시한다. 위치의 X와 Y는 한 묶음으로, 크기의 너비와 높이는 한 묶음으로 저장한다. 한 탭이 위치를 바꾸고 다른 탭이 크기를 바꾸면 두 수정이 모두 남는다.

각 저장은 `projects`와 수정할 object store를 포함하는 하나의 `readwrite` 트랜잭션에서 처리한다. IndexedDB는 같은 object store를 쓰는 트랜잭션을 순서대로 실행한다. 트랜잭션 안에서 프로젝트와 대상의 최신 레코드를 읽고, 요청에 포함된 값만 적용한다. 대상이 삭제됐으면 저장을 거부한다. 변경된 레코드와 1을 더한 프로젝트 저장 순서를 같은 트랜잭션으로 커밋한다. 이 순서가 어느 값이 마지막으로 저장됐는지를 결정한다. 탭의 시각이나 알림 도착 순서는 판정에 사용하지 않는다. [IndexedDB 트랜잭션 실행 순서](https://www.w3.org/TR/IndexedDB-3/#transaction-scheduling)

메모마다 Yjs 문서의 `Y.Text`에 삽입과 삭제를 적용한다. 자동 저장 시 메모 ID와 변경 ID로 바이너리 변경분을 기록하고 프로젝트 저장 순서를 같은 트랜잭션에서 갱신한다. 재시도에는 같은 변경 ID를 사용한다. 이미 저장한 변경의 재시도는 성공으로 처리하며 저장 순서를 올리지 않는다. 탭을 다시 열면 저장된 변경분을 적용해 본문을 복원한다. [Yjs 변경분 문서](https://docs.yjs.dev/api/document-updates)

트랜잭션의 `complete` 이벤트 이후에만 `BroadcastChannel`로 프로젝트 ID와 저장 순서를 알린다. 트랜잭션이 중단되면 변경과 저장 순서가 함께 취소된다. 알림을 보내지 못해도 성공한 저장은 유지한다. [트랜잭션 완료 이벤트](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event)

같은 프로젝트를 편집하는 탭은 현재 반영한 저장 순서보다 높은 알림을 받으면 프로젝트의 저장 순서와 변경된 값을 같은 읽기 트랜잭션에서 가져온다. 조회가 완료될 때 이미 더 최신 저장본을 반영했다면 이전 조회 응답을 무시한다. 새로 탭을 열거나 숨겨진 탭이 다시 표시되면 알림과 무관하게 저장 순서를 확인한다. 다른 탭의 변경을 화면에 반영하는 과정에서는 다시 저장하거나 알림을 보내지 않는다.

드래그 미리보기, 한글 조합 중인 입력과 아직 저장하지 못한 변경은 화면 갱신과 별도로 유지한다. 현재 편집 화면에서는 저장에 실패한 변경을 다시 저장할 수 있게 유지한다. 다른 탭이 대상을 삭제한 경우에도 열린 편집 화면에서 미저장 입력을 회수할 수 있어야 한다. [HTML BroadcastChannel 표준](https://html.spec.whatwg.org/multipage/web-messaging.html#broadcasting-to-other-browsing-contexts), [Yjs 변경 데이터 문서](https://docs.yjs.dev/api/document-updates)

TDD를 적용한다. 편집 화면을 연결하기 전에는 같은 브라우저 컨텍스트의 두 페이지에서 실제 저장 모듈을 호출해 병합, 커밋 순서와 롤백을 검증한다. 아래 시나리오 중 화면과 입력 상태를 확인하는 검사는 편집 화면과 저장 동작을 연결한 뒤 실행한다. 이미지별 품질을 변경하는 검사는 품질 동작을 확정하고 구현한 뒤 실행한다. [Playwright의 여러 페이지 사용](https://playwright.dev/docs/pages#multiple-pages)

- 한 탭은 이미지를 옮기고 다른 탭은 같은 이미지의 품질을 바꾼다. 두 탭과 다시 연 프로젝트에서 위치와 품질이 모두 유지되는지 확인한다. 다른 이미지에 동시에 적용한 수정도 각각 확인한다.
- 두 탭이 같은 저장본을 연 상태에서 같은 이미지를 서로 다른 위치로 옮긴다. 한 탭의 저장이 완료된 뒤 다른 탭의 저장을 진행하도록 제어한다. 두 탭과 다시 연 프로젝트에 두 번째로 커밋된 X와 Y가 함께 표시되는지 확인한다. 같은 이미지의 크기와 메모 크기도 이 순서로 검사한다. 두 번째 트랜잭션이 중단된 경우에는 첫 번째 값이 남아야 한다.
- 새 저장본을 표시한 탭에 같은 알림과 이전 저장 순서의 알림을 전달한다. 위치나 크기가 이전 값으로 돌아가지 않고 받는 탭에서 재저장과 알림이 발생하지 않는지 확인한다. 저장과 조회는 실제 IndexedDB에서 실행하고 테스트는 알림 전달 순서만 바꾼다.
- 같은 본문을 연 두 탭에서 각각 문자열을 삽입하거나 삭제한다. 두 탭과 다시 연 프로젝트에서 같은 본문을 확인한다. 같은 변경을 재시도하거나 알림을 중복 전달해도 본문이 중복되지 않고 저장 순서가 한 번만 증가하는지 확인한다. 실패한 트랜잭션의 알림이 다른 탭에 도착하지 않는지도 검증한다. 실제 입력에서는 원격 변경이 도착해도 포커스와 한글 조합이 유지되는지 확인한다.
- 변경 알림을 받지 못한 탭을 다시 표시한다. 빠진 저장 내용을 따라잡고 그 탭의 미저장 수정도 반영하는지 확인한다. 알림 누락은 전달만 차단해 재현하고 IndexedDB 읽기와 쓰기는 실제 구현을 사용한다.
- 한 탭에서 배치를 삭제한 뒤 다른 탭이 이전 상태로 저장한다. 배치가 되살아나지 않고, 삭제 전에 그 탭에서 입력한 미저장 메모를 회수할 수 있는지 확인한다.

## 캔버스 편집과 메모 부착

상태: 이미지 배치 너비를 원본 비율과 크기 상한에 맞춰 계산한다. 메모는 선택한 이미지 변의 중앙에 맞춰 배치한다. 두 이미지 비율과 네 부착 방향에서 이동과 크기 변경 뒤 메모가 이미지에 닿는지 검사했다.

Konva에서 저장된 원본 이미지와 메모를 표시하고 같은 그룹으로 이동한다. 이미지 선택은 속성 패널의 메모 입력과 연결한다. 드래그가 끝나면 위치만 저장한다. Chromium에서 이미지 픽셀 표시, 드래그한 위치의 저장과 새로고침 후 복원, 360px 화면에서 가로 넘침이 없는 것을 확인했다. [Konva 드래그](https://konvajs.org/docs/react/Drag_And_Drop.html)

편집 화면에서 이미지를 추가하면 브라우저가 해석한 이미지 크기로 배치한다. 원본과 배치를 함께 커밋하고 다른 탭에 알린다. Chromium에서 PNG 원본 바이트 보존, 다른 탭 반영, 새로고침 후 표시와 손상된 이미지의 저장 거부를 확인했다.

선택한 이미지 모서리의 조절점과 속성 패널의 너비 입력을 연결했다. 드래그하는 동안 이미지와 메모 위치를 함께 계산하고 조작을 마치면 크기를 저장한다. Chromium에서 축소, 새로고침 후 복원, 원본 크기 상한 및 숫자 입력 저장을 확인했다.

선택한 이미지에 메모를 추가하고 속성 패널에서 부착 방향을 고를 수 있다. Chromium 두 탭에서 같은 배치에 메모 추가를 다시 요청해도 한 개만 남고, 변경한 방향이 다른 탭과 새로고침 후에도 유지됨을 확인했다. 이미지와 메모는 같은 모서리 조절점 컴포넌트를 사용한다. 메모의 너비와 높이는 부착 방향을 유지하며 변경한다. 네 방향의 좌표 계산과 Chromium에서 아래에 붙인 메모의 드래그 저장 및 새로고침 후 재조절을 확인했다.

대단원 리뷰에서 편집 명령의 저장 후 재조회를 통합하고, 같은 탭의 메모 자동 저장 후에도 문서를 다시 읽도록 연결했다. Chromium에서 이미지 선택을 바꿔도 각 메모의 입력이 유지되고, 메모 자동 저장 후 캔버스의 본문이 갱신되며 포커스가 유지됨을 확인했다. 두 탭의 메모 병합도 다시 확인했다. 상태 훅과 ref는 선택, 조작 미리보기, DOM과 입력 연결 객체의 수명에 따라 검토했다. 실제 모바일 조작과 한글 IME, 시안 비교는 화면 통합에서 확인한다.

Konva 화면과 속성 패널은 `pages/editor/ui/`에 둔다. 현재 선택과 편집 조작은 `pages/editor/model/`에서 관리한다. 저장과 불러오기에서도 유지해야 하는 이미지 크기와 메모 부착 규칙은 `entities/project/model/`에서 관리한다.

[이미지 배치](requirements.md#이미지-배치), [메모 부착](requirements.md#이미지에-붙이는-메모), [속성 조작](requirements.md#속성-조작-방식)을 구현한다. 편집 문서를 상태의 기준으로 두고 Konva 화면과 우측 속성 패널이 같은 선택 및 배치 정보를 사용한다. 메모 입력은 브라우저의 텍스트 입력을 사용한다. 드래그로 바뀌는 값과 숫자로 정확히 지정할 값을 나눠 데스크톱과 모바일에서 확인한다. [Konva 저장 지침](https://konvajs.org/docs/data_and_serialization/Best_Practices.html), [속성별 조작 조사](references/property-controls.md)

TDD를 적용한다. 배치 규칙은 서로 다른 비율의 이미지와 네 부착 방향으로 검증한다. 이미지 이동과 크기 조절, 메모 너비와 높이 변경 뒤 같은 이미지와 접한 변이 유지되고 두 영역이 겹치지 않아야 한다. 축소 후 원본 크기로 복원할 때 원본 비율과 상한이 유지되는지도 확인한다. 실제 브라우저에서는 한 이미지를 이동한 뒤 다른 이미지를 선택해 메모와 속성이 해당 이미지로 바뀌는지 확인한다. 규칙이 연결되기 전에는 경계값이나 선택 대상이 기대와 달라 실패해야 한다.

확정된 좌표, 크기와 메모는 문서 모델에서 읽는다. 드래그 중 값이 필요하면 일시적인 미리보기로 관리하고 완료 시 문서 변경으로 확정한다. Konva 노드나 속성 패널이 확정된 값을 따로 관리하지 않는지 확인한다. 이미지 선택을 바꾼 뒤 이전 이미지의 메모나 품질 설정이 새 선택에 반영되지 않아야 한다.

## 편집용 ZIP 저장과 불러오기

[편집용 파일로 저장](requirements.md#편집용-파일로-저장)에 명시된 네 한도를 저장과 불러오기 양쪽에 적용한다. ZIP 파일 크기와 압축 해제 후 항목 합계, 원본 수와 총 원본 픽셀을 각각 검사한다. 불러오기에서 한도 초과가 확인되면 새 프로젝트를 만들기 전에 중단한다.

[1080p PNG 10장 측정](references/editable-file-format.md#1080p-png-10장-측정)에서는 공개 PNG를 두 집합에서 10장씩 무작위로 골라 CPU 제한 조건에서 각각 두 번 측정했다. 더 큰 ZIP은 30.39 MB였으며 불러오기 확인 뒤 첫 이미지 표시는 최대 2.88초였다.

Chromium에서 총 픽셀 한도에 도달하고 ZIP 용량 한도에 가까운 PNG 10장 프로젝트를 저장한다. 다운로드한 ZIP을 목록에서 미리 보고 새 프로젝트로 연다. 원본 바이트, 이미지 배치와 메모 원문을 확인한다. 저장과 불러오기에서 각 한도를 넘는 입력을 거부하는지도 확인한다. [저장과 복원 검증 결과](references/editable-file-format.md#한도에-가까운-zip의-저장과-복원)

구현분 코드 리뷰에서 불러오기 파일명, 검증 결과와 진행 상태를 한 상태로 통합했다. 취소 신호, 파일 입력과 모달 조작의 ref는 수명이 달라 분리했다. Chromium에서 취소, 미지원 버전과 누락된 원본 거부, 정상 파일 재선택과 새 프로젝트 복원을 다시 확인했다.

데스크톱에서 Pixel 7을 에뮬레이션한 Chromium과 iPhone 15를 에뮬레이션한 WebKit으로 터치 저장, 확인 창 취소, 파일 오류 안내와 새 프로젝트 복원을 확인했다. 이 검사는 모바일 화면과 조작을 확인한다. 모바일 실기기에서의 성능 측정은 [백로그](requirements.md#백로그)에 둔다.

상태: ZIP 쓰기 모듈과 편집기 다운로드를 연결했다. 저장 버튼을 누르면 열려 있는 메모의 변경을 먼저 저장한 뒤 최신 문서로 파일을 만든다. Chromium에서 다운로드 파일명, 자동 저장 대기 중이던 메모 원문, 스키마 버전, 배치와 무압축 원본 바이트를 확인했다.

편집 파일의 첫 스키마는 버전 `1`이다. ZIP에 형식 식별자와 편집 상태를 담은 JSON 및 별도의 원본 이미지 항목을 둔다. 기존 지원 버전을 읽을 수 있는지는 실제 파일을 불러와 확인한다. [편집 파일 형식 조사](references/editable-file-format.md#형식-식별-버전과-불러오기)

읽기 모듈은 형식과 버전, 항목 이름, 원본 이미지와 문서의 참조를 확인한다. 검증한 문서는 새 식별자를 사용하며 저장은 호출부가 실행한다. Chromium에서 쓰기 모듈로 만든 ZIP을 읽어 기존 프로젝트와 같은 이름의 새 프로젝트를 저장했다. 원본 바이트, 배치와 메모 연결 및 원문을 복원했다. 목록의 확인 창은 파일명과 대표 이미지를 보여준다. Chromium에서 실제 다운로드 파일의 미리보기, 취소 후 포커스 복귀, 손상된 ZIP의 거부, 확인 후 새 프로젝트와 메모 복원을 검증했다. 확인 창을 닫으면 ZIP 읽기에 취소 신호를 전달한다. Chromium에서 진행 중인 읽기가 취소 오류로 종료되는 것을 확인했다. 미지원 정수 버전은 별도로 안내하고 불러오기를 비활성화한다. Chromium에서 v2 ZIP과 원본 이미지 항목이 빠진 ZIP을 각각 거부하고 기존 프로젝트를 보존하는 것을 확인했다. 같은 화면에서 정상 파일을 다시 선택하면 새 프로젝트로 복원된다. Chromium에서 원본을 기록하는 중 IndexedDB 트랜잭션을 강제로 중단했다. 기존 프로젝트만 남고 같은 확인 창에서 다시 시도하면 새 프로젝트가 복원되는 것을 확인했다.

Chrome DevTools의 Performance 패널에서 CPU 제한을 보정한다. 동일한 빌드와 기존 세 작업량을 사용해 CPU 제한 없음, 중급 모바일, 저사양 모바일 조건에서 반복 측정한다. 네트워크 제한은 끄고 조건별 CPU 배율과 반복 횟수를 기록한다. [Chrome DevTools CPU 제한 보정](https://developer.chrome.com/docs/devtools/settings/throttling/)

저장 버튼을 누른 뒤 다운로드 완료까지, 파일을 선택한 뒤 미리보기까지, 불러오기 확인 뒤 첫 이미지 표시까지의 시간을 각각 잰다. ZIP 크기, 압축 해제 후 총량, 항목 수와 원본 픽셀 수를 함께 기록한다. 프레임 간격과 입력 지연을 구분하고, JS 힙과 브라우저 메모리 사용량을 따로 기록한다. [Chrome DevTools 메모리 측정](https://developer.chrome.com/docs/devtools/memory-problems)

데스크톱에서는 ZIP 쓰기와 읽기, 다운로드, 미리보기와 편집 재개를 세 작업량으로 측정했다. 프레임 간격, Chromium 프로세스 RSS 및 포인터 이벤트 전달 시간을 표본으로 기록했다. 이 기록을 CPU 제한 없음 조건의 비교 자료로 사용한다. CPU 제한 예비 측정도 기록했다. CPU 조건별 두 번의 순차 측정에서 59.40 MB와 237.50 MB 파일의 긴 화면 공백을 다시 확인했다. 저사양 조건에서 더 가벼운 작업량의 입력 지연과 JS 힙을 추가 측정했다. 5.14 MB 작업의 추가 측정에서는 약 600 ms의 프레임 공백이 클릭 이벤트 전달 전에 발생했다. 편집 화면이 안정된 상태에서는 59.40 MB 저장이 259~260 ms였고 불러오기 확인 뒤 첫 이미지 표시는 7.47~7.59초였다. 같은 해상도의 이미지 6장과 9장을 추가로 비교했다. [중간 작업량 비교](references/editable-file-format.md#이미지-6장과-9장의-작업량-비교) [편집 화면 표시 후 저장 측정](references/editable-file-format.md#편집-화면-표시-후-저장-시작) [클릭 시점 비교](references/editable-file-format.md#저장-클릭과-프레임-공백의-시점-비교) [소용량 ZIP 측정](references/editable-file-format.md#저사양-cpu-조건의-소용량-zip-측정) [CPU 제한 순차 재측정](references/editable-file-format.md#cpu-제한-순차-재측정) [CPU 제한 예비 측정](references/editable-file-format.md#cpu-제한-예비-측정) [데스크톱 ZIP 처리 시간](references/editable-file-format.md#데스크톱-zip-처리-시간)

ZIP 생성은 저장소에서 읽은 문서를 전달받은 Worker가 처리한다. Chromium에서 다운로드 및 불러오기를 다시 검증했다. 237.50 MB 파일을 저장 버튼으로 다운로드할 때 화면 공백을 관측했으나 단계별 실행에서는 재현하지 못했다. [단계별 프레임 간격](references/editable-file-format.md#zip-저장-단계별-프레임-간격)

불러오기 창과 확인 상태는 `pages/projects/ui/` 및 `pages/projects/model/`에 둔다. 저장 동작은 편집기에서 시작한다. ZIP을 읽고 쓰는 구현은 `app/composition/archive/`에 두고, 각 화면에는 필요한 읽기 또는 쓰기 동작만 주입한다. 페이지 사이에 불러오기 UI를 공유하게 되면 그 동작을 `features/import-project/`로 옮긴다.

[편집용 파일](requirements.md#편집용-파일로-저장)과 [불러오기 창](requirements.md#로컬-프로젝트-관리)을 연결한다. 파일 검증과 새 프로젝트 생성을 분리한다. 파일 이름과 미리보기를 `프로젝트 불러오기` 창에 표시하고 `불러오기`로 확정한다. 별도의 새 프로젝트 안내 문구는 생략한다. 모달을 닫으면 호출 지점으로 포커스를 돌린다. [편집 파일 형식 조사](references/editable-file-format.md), [W3C 모달 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

TDD를 적용한다. 실제 편집 파일을 저장해 같은 이름의 기존 프로젝트가 있는 목록에서 불러온다. 확인 전 목록이 바뀌지 않고, 확인 후 별도 프로젝트가 생성되며 기존 프로젝트와 원본 바이트, 메모 연결이 보존되는지 확인한다. 취소하거나 필수 원본이 빠졌거나 지원하지 않는 스키마 버전의 ZIP을 열었을 때는 새 항목이 생기지 않아야 한다. ZIP 처리와 목록 반영을 연결하기 전에는 복원 시나리오가 실패해야 한다.

불러오기 동작을 연결하는 곳은 주입받은 ZIP 읽기와 프로젝트 생성 기능을 호출한다. 미리보기와 확인 버튼은 검증 결과와 실행 콜백을 받는다. 창에서 zip.js, 프로젝트 저장소 또는 범용 DI 조회에 직접 접근하지 않는지, 검증이 끝나기 전에 쓰기 동작에 도달할 수 없는지 확인한다.

## 캔버스 화면 이동과 확대

Chromium에서 선택 전 이미지 위 드래그로 화면이 이동하고, 손가락을 뗀 뒤 선택된 이미지만 별도 드래그로 이동해 새로고침 후에도 좌표가 유지되는지 확인했다. 두 손가락 핀치, 마우스 휠 확대, 터치패드 입력 방식에서의 스크롤과 전체 보기 복귀도 확인했다. 포인터 아래 좌표와 터치 이동 대상은 모델 테스트에서 검사한다. 화면 상태와 활성 입력은 수명에 따라 상태와 ref로 관리하며 드래그 취소 처리를 공유한다. 실제 터치패드와 모바일 실기기, 내보내기 결과에 화면 변환이 반영되지 않는지는 후속 검증에서 확인한다.

[캔버스 화면 이동과 확대](requirements.md#캔버스-화면-이동과-확대)를 편집 화면에 연결한다. 화면의 이동량과 확대율은 문서 좌표 및 저장 상태와 분리해 `pages/editor/model/`에서 관리한다. 캔버스와 확대 조작은 같은 화면 상태를 사용한다. 마우스 휠과 터치패드 스크롤을 확실히 구분하기 어려운 브라우저에서는 마우스와 터치패드 입력 방식의 명시적인 전환을 제공한다. [입력 방식 조사](references/canvas-navigation.md) [Konva 포인터 기준 확대](https://konvajs.org/docs/sandbox/Zooming_Relative_To_Pointer.html) [Konva 멀티터치 확대](https://konvajs.org/docs/sandbox/Multi-touch_Scale_Stage.html)

좌표 변환과 입력 전환에 TDD를 적용한다. 이동한 화면에서 포인터를 기준으로 확대해도 포인터 아래 문서 좌표가 유지돼야 한다. 확대율이 다른 화면에서 이미지를 끌면 화면 이동량을 문서 좌표로 변환한 값이 저장돼야 한다. 두 번째 손가락이 닿거나 터치가 취소되면 진행 중인 이미지 조작이 의도치 않게 저장되지 않아야 한다. 내보내기 절차에서는 같은 문서를 서로 다른 화면 위치와 확대율에서 저장해 결과의 치수와 내용이 같은지 확인한다.

모바일에서는 이미지 선택 여부와 드래그 시작 지점에 따라 이동 대상을 정한다. 아무 이미지도 선택하지 않은 상태에서 이미지 위를 끌면 화면 위치만 바뀌는지 확인한다. 이미지를 터치한 채 움직이지 않으면 손가락을 떼기 전까지 선택이 확정되지 않아야 한다. 손가락을 뗀 뒤 선택한 이미지를 다시 끌면 화면 위치는 그대로이고 이미지와 메모가 함께 이동해야 한다. [W3C 포인터를 뗄 때 동작 확정](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html#up-event-activation-or-completion)

브라우저에서 마우스, 터치패드와 모바일 터치로 각각 확인한다. 캔버스 밖의 스크롤, 메모 입력 중 Space, 손가락 하나에서 두 개로 전환했다가 떼는 경우, 화면 밖으로 이동한 작업을 전체 보기로 다시 찾는 경우를 포함한다. 자동화한 입력과 실제 기기에서 확인한 입력을 구분해 기록한다.

## 이미지 내보내기와 여백

PNG, SVG, JPG 내보내기와 영역 선택을 연결했다. Chromium에서 PNG 여백 0px와 24px의 치수와 픽셀, PNG 다운로드 이름, SVG의 원본 내장, JPG 미리보기와 투명 영역의 저장 제한, 사각형과 원형 및 자유형 선택을 확인했다. 출력 한도의 경계값은 모델 테스트에서 검사한다. WebKit 27.2의 비영구 프로필에서 앱 코드 없이도 IndexedDB에 Blob을 기록할 때 오류가 재현됐다. 영구 프로필에서는 이미지 추가와 새로고침, 세 형식의 미리보기와 투명 영역의 JPG 제한을 확인했다. [브라우저의 기준 배치 확인](references/image-export-quality.md#브라우저의-기준-배치-확인)에서 1080p 10장 PNG와 SVG 합성이 현재 한도를 충족했다. 원본 품질의 추가 표본, 다른 배치와 렌더링 성능은 검증이 남아 있다. 큰 SVG는 축소한 PNG로 미리 보고 다운로드에는 SVG를 사용한다. Chromium의 같은 CPU 제한 조건에서 Worker 응답 후 디코딩 시간이 8.8~9.3초에서 0.43~0.49초로 줄었으며 다운로드 치수와 바이트 수는 같았다.

내보내기 검토에서 선택 사각형과 겹치지 않는 원본도 디코딩하거나 SVG에 내장하는 동작을 수정했다. 이미지와 메모는 각각 겹치는지 검사한다. Chromium에서 이미지 두 장을 전체 SVG로 저장하면 원본 두 장이 들어가고 한 장만 포함한 선택 SVG를 다운로드하면 원본 한 장만 들어감을 확인했다.

패널 UI와 내보내기 설정은 `pages/editor/ui/`와 `pages/editor/model/`에 둔다. 합성 영역과 여백은 편집 문서 및 출력 설정을 입력으로 계산한다. Worker 실행과 메시지 연결은 `app/composition/export/`에서 관리한다.

[이미지 파일로 저장](requirements.md#이미지-파일로-저장)을 적용한다. 편집기 안에서 미리보기와 설정을 함께 확인한다. 형식과 범위에는 선택의 의미가 드러나는 라벨을 두고, 여백은 정확한 값을 지정하는 숫자 입력을 우선 검토한다. 전체에서만 0~24px 입력 하나를 제공한다. 라벨과 입력 사이, 설정 묶음 사이의 간격으로 구조를 드러낸다. 현재 문서와 내보내기 설정을 한 단위로 사용해 미리보기, 예상 용량과 실제 출력이 같은 설정을 반영하게 한다. 합성과 인코딩은 Worker에 맡긴다. [속성별 조작 조사](references/property-controls.md), [이미지 내보내기 품질 조사](references/image-export-quality.md), [WHATWG Canvas 표준](https://html.spec.whatwg.org/multipage/canvas.html)

TDD를 적용한다. 여러 이미지와 메모가 든 작업을 전체 PNG로 내보내 여백 0px와 24px의 파일을 디코딩해 비교한다. 너비와 높이는 각각 48px 늘고 모든 요소는 좌우와 상하에서 각각 24px 이동해야 한다. 선택 영역으로 전환하면 여백 입력이 사라지고 전체 여백이 결과에 적용되지 않아야 한다. 여백 계산 또는 범위 분기를 연결하기 전에는 출력 크기나 좌표가 달라 실패해야 한다.

실제 브라우저에서 사각형, 원형, 자유형의 출력 범위와 바깥 투명도, 투명 영역에서 JPG 제한, SVG의 이미지 내장, 원본 크기 PNG와 파일명을 확인한다. [요구사항의 초기 출력 한도](requirements.md#이미지-파일로-저장)와 정확히 같은 값 및 초과 값을 각각 확인한다. 각 변의 길이와 총 픽셀 수는 합성 전에 검사한다. 바이트 수는 현재 설정으로 인코딩한 결과에서 확인하고 미리보기와 다운로드는 동일한 합성 설정을 사용한다. 큰 SVG의 미리보기는 축소한 PNG를 쓰고, 용량과 다운로드는 SVG 결과를 사용한다. 설정 변경으로 다시 한도 이내가 되면 저장이 활성화되어야 한다. 빠르게 설정을 바꿨을 때 이전 계산 결과가 현재 상태를 덮지 않는지도 검증한다. 일반 크기 라벨 대비, 라벨과 입력의 연결 및 패널 간격은 실제 화면에서 확인한다.

JPG에서 이미지별 품질과 합성 이미지 전체의 저장 품질을 각각 조절할 수 있도록 한다. PNG와 SVG로 전환하면 품질 조절이 숨겨지고 JPG 품질 설정이 미리보기와 저장 결과에 적용되지 않는지 확인한다. 기본 PNG는 원본 크기의 불투명 8비트 sRGB 표본에서 치수와 RGB 값 일치를 확인한다. EXIF 회전 표본은 출력 방향과 회전 후 치수를 비교한다. 투명 영역은 알파가 0인지 확인하고 반투명 가장자리는 흰색과 검은색 배경에 합성한 RGB 값의 채널별 차이를 비교한다. 초기 검증 기준은 채널별 8비트 값 차이 최대 2다. 결정된 기준으로 품질을 바꾼 이미지와 그대로 둔 이미지가 각각 미리보기와 저장 파일에 반영되는지 확인한다. 용량 기준을 넘었다가 설정을 조정해 기준 이내로 돌아오면 저장이 다시 활성화되는지도 확인한다. [이미지 내보내기 품질 조사](references/image-export-quality.md)

1080p 이미지 10장으로 메모와 최대 여백을 포함한 5열 2행, 세로 배치, 이미지 사이가 넓은 배치를 비교한다. 사진과 세부 무늬가 많은 표본을 섞고 PNG, SVG, JPG에서 치수, 결과 용량, 미리보기 준비 시간, 입력 지연, 최대 메모리와 인코딩 실패를 기록한다. Chromium의 보정된 저사양 CPU 조건과 WebKit에서 확인한다. 기준 배치가 실패하거나 반복 내보내기 중 입력이 밀리면 실패한 단계와 수치를 근거로 초기 한도를 조정한다. 실기기 조건은 별도로 구분해 기록한다. [초기 한도 산정 근거](references/image-export-quality.md#통합-이미지의-초기-한도)

형식, 범위와 여백의 현재 값을 내보내기 설정 한 곳에서 관리한다. 패널의 필드는 필요한 값과 변경 동작만 받는다. 출력 요청을 만드는 코드와 Worker를 생성하는 코드의 책임을 분리한다. 미리보기와 예상 용량이 같은 설정에서 계산되고, Worker 응답이나 폼 상태 전체를 범용 Context로 전달하지 않는지 확인한다.

## 화면 통합과 배포 확인

목록에서 작업 열기, 메모 편집, 이미지 내보내기, ZIP으로 다시 열기를 이어서 확인한다. 정적 배포에서 편집 주소로 직접 진입하거나 새로고침할 때 앱이 열리고 Worker 파일을 로드하는지 확인한다. TDD는 적용하지 않는다. 앞 절차의 동작 검사를 통과한 운영 빌드를 대상으로 화면과 배포 환경을 확인한다. [Vite Worker 지원](https://vite.dev/guide/features#web-workers), [React Router SPA 배포](https://reactrouter.com/how-to/spa)

화면에서 원본과 메모를 추가해 저장한 뒤 새로고침한다. 목록에서 같은 프로젝트를 열어 원본과 메모를 확인하고, 두 탭에서 저장한 변경을 새로고침 없이 확인한다. 데스크톱과 모바일에서 실제 파일을 저장한다. 앱을 연 뒤 네트워크를 끊고 편집과 이미지 내보내기를 확인한다. 오프라인 새로고침과 재실행을 제공하기로 정하면 배포 검증에 그 시나리오도 포함한다.

[사용 환경](requirements.md#사용-환경)에 따라 편집 화면 렌더링을 내보내기와 별도로 측정한다. 1080p 이미지 10장에 메모를 붙인 같은 문서와 운영 빌드를 사용한다. 최초 진입부터 첫 이미지와 전체 이미지가 표시될 때까지를 각각 잰다. 화면 이동, 휠과 핀치 확대, 이미지 드래그와 크기 조절, 메모 입력을 같은 순서로 반복한다. 모든 요소가 보이는 화면과 일부가 화면 밖으로 나간 화면을 비교하고, 내보내기 Worker가 실행 중일 때도 같은 조작을 반복한다.

Chromium에서 CPU 제한 없음과 보정한 저사양 조건을 비교한다. 프레임 간격의 중앙값과 95백분위, 누락 프레임 비율, 입력부터 화면 반영까지의 지연, 긴 메인 스레드 작업과 메모리를 기록한다. 연속 이동과 휠 조작은 클릭과 동일한 지표로 대체하지 않고 프레임 기록을 함께 확인한다. WebKit에서는 지원하는 지표와 제스처를 확인한다. 브라우저 버전, 화면 크기와 픽셀 비율, CPU 배율, 반복 횟수와 실기기 여부를 남긴다. 반복 조작이 끊기거나 화면 반영이 늦어지면 이미지 디코딩, Konva 다시 그리기와 React 갱신 중 지연이 발생한 단계를 확인해 수정한 뒤 같은 조건에서 비교한다. [Chrome DevTools 프레임 검사](https://developer.chrome.com/docs/devtools/rendering/performance) [Chromium 그래픽 지표](https://chromium.googlesource.com/chromium/src/+/a2b622c333dcb50f75aded93771bac39f82a56f6/docs/speed/graphics_metrics_definitions.md)

Chromium 156에서 1,440×900, 픽셀 비율 1의 화면으로 1080p 이미지 10장과 메모 상자 기준 배치를 전체 보기에 맞춘 뒤 화면 이동을 측정했다. CPU 제한 없음과 12.1배 제한에서 SVG 생성이 없는 경우와 겹치는 경우를 각각 세 번씩 비교했다. 매 실행에 마우스 이동 30건을 요청했다. SVG 생성 중에 전달된 이벤트는 실행당 23~28건이었다.

프레임 콜백 간격의 중앙값은 모든 실행에서 16.7ms였고 95백분위는 16.7~16.8ms였다. CPU 12.1배 제한에서 포인터 이벤트 시각부터 다음 프레임 콜백까지의 95백분위는 생성 전 14.5~14.7ms, 생성과 겹칠 때 12.4~15.6ms였다. 측정 구간에 50ms 이상의 메인 스레드 작업은 관측되지 않았다. 프레임 콜백 시각은 화면에 픽셀이 표시된 시각과 다르다. 누락 프레임과 실제 표시 지연, 메모리, 화면 이동 외 조작의 성능은 추가 측정한다.

같은 Chromium 화면에서 메모 타이핑, 휠 확대와 축소, 이미지 너비 입력과 드래그 저장을 각각 확인했다. 수정 전 CPU 12.1배 제한의 너비 저장 구간과 드래그 구간에서 최대 프레임 콜백 간격은 각각 약 1,200ms와 1,417ms였다. 편집 후 다시 읽은 원본 Blob이 기존 참조와 달라 캔버스가 이미지를 다시 불러오는 구조였다. 원본 바이트가 바뀌면 새 원본 식별자를 쓰는 저장 구조에 맞춰, 캔버스에서 원본 식별자가 같은 동안 디코딩 결과를 재사용한다.

수정 뒤 같은 CPU 제한과 10장 배치에서 너비와 위치가 IndexedDB에 저장됐으며 원본에 대한 객체 URL은 처음 생성한 10개 그대로였다. 프레임 콜백 최대 간격은 너비 저장 16.7ms, 드래그 33.4ms였다. 전후 각 한 번의 표본이며 실제 화면 표시 지연을 직접 측정한 값은 아니다. [React Effect Event](https://react.dev/reference/react/useEffectEvent) [IndexedDB 값 복제](https://w3c.github.io/IndexedDB/#clone-a-value)

Chromium 운영 빌드에서 편집 주소를 직접 열고 네트워크를 끊은 뒤 메모를 편집하고 첫 PNG 내보내기를 실행했다. 변경 전에는 Worker 스크립트 요청이 실패해 미리보기가 열리지 않았다. 이미지 내보내기 Worker를 초기 앱 번들에 포함한 뒤 미리보기와 PNG 다운로드를 확인했다. 이후 ZIP Worker와 읽기 모듈도 앱을 열 때 로드하도록 바꿨다. Chromium에서 ZIP을 처음 사용하기 전에 네트워크를 끊고 편집 파일을 다운로드했다. 같은 오프라인 세션에서 미리보기, 새 프로젝트로 불러오기와 메모 원문 복원을 확인했다. 초기 JS 번들은 gzip 기준 약 226kB에서 380kB로 늘었다. 브라우저를 다시 시작한 뒤 오프라인에서 앱을 여는 동작은 검증하지 않았다. [Vite 인라인 Worker](https://vite.dev/guide/features#web-workers)

자동화 검사는 계획의 시나리오와 대응하되 계획 파일을 참조하지 않는다. 실제 브라우저 저장소, ZIP 입출력과 인코딩 결과를 관찰한다. 예상 결과를 대신 반환하는 모의 객체나 사용하지 않는 픽스처와 스크립트는 작성하지 않는다. [Playwright 검증 지침](https://playwright.dev/docs/best-practices)

## 진행 조건

화면 시안과 배치 규칙은 독립적으로 구체화할 수 있다. 모바일 실기기 측정은 [백로그](requirements.md#백로그)에 둔다. 합성본의 문자 및 번호는 모델 비교 결과가 필요하다. 미저장 편집 복구, SSR과 실사용 성능 대응은 [백로그](requirements.md#백로그)에서 관리한다.
