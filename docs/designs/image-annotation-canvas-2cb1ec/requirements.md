# 이미지와 메모를 배치하는 캔버스 요구사항

사용자는 AI 이미지 생성에 참고할 이미지와 이미지별 지침을 미리 준비한다. 생성 요청마다 참고 이미지를 하나씩 올리고 각 이미지의 지침을 다시 입력하는 수고를 줄이기 위해, 이미지와 메모를 한 장으로 내보내 AI 이미지 생성 도구에 참고 이미지로 전달할 수 있다.

사용자는 넓은 캔버스에 여러 이미지를 자유롭게 배치하고, 각 이미지에서 참고할 아트 스타일, 포즈, 특정 요소 등을 메모로 붙일 수 있다. 캔버스 전체 또는 선택 영역을 이미지 파일로 저장할 수 있다. 캔버스 전체를 편집용 파일로 저장하면 다른 기기에서 열어 작업을 이어갈 수 있다.

## 이미지 배치

- 이미지를 감싸는 별도의 프레임을 두지 않는다. 사용자는 원본의 가로세로 비율을 유지하면서 이미지의 배치 크기를 줄이거나 원본 크기까지 다시 키울 수 있다.
- 크기를 줄여도 업로드한 원본을 보존한다. 사용자가 원본 크기로 되돌리면 보존한 원본으로 표시한다.
- 사용자는 캔버스에서 이미지를 드래그해 위치를 바꿀 수 있다. 붙어 있는 메모는 이미지와 함께 이동한다.
- 사용자는 이미지의 크기 조절점을 드래그해 배치 크기를 바꿀 수 있다. 가로세로 비율을 유지하며 원본 크기까지만 키울 수 있다.

## 이미지에 붙이는 메모

- 사용자는 각 이미지에 붙일 메모를 작성할 수 있다. 메모는 이미지의 위, 아래, 왼쪽 또는 오른쪽 가장자리에 빈틈없이 닿으며 이미지를 가리지 않는다.
- 사용자는 붙인 방향에 관계없이 메모의 너비와 높이를 드래그해 조절할 수 있다. 조절하는 동안 메모는 같은 이미지 가장자리에 계속 닿고 이미지와 겹치지 않는다.
- 캔버스와 내보낸 이미지의 메모에는 화살표나 방향 표시 띠를 넣지 않는다. 사용자는 속성 패널에서 메모를 붙일 이미지 가장자리를 바꿀 수 있다.
- 이미지를 이동하거나 크기를 바꾸고 편집용 ZIP을 새 캔버스로 불러온 뒤에도 메모는 같은 이미지에 붙어 있어야 한다.
- 내보낸 이미지에 문자나 번호를 붙일지는 AI의 이미지와 메모 짝짓기, 생성 결과에 글자가 나타나는지를 비교한 뒤 정한다.

## 속성 조작 방식

- 속성마다 숫자 입력, 드래그, 슬라이더, 버튼과 선택 목록 중 어떤 조작이 적합한지 조사한다. 정확한 값을 지정하는 경우와 화면에서 변화를 보며 조절하는 경우를 모두 고려한다.

## UI 디자인과 시안 검토

- 데스크톱 편집 화면은 상단에 낮은 헤더를 둔다. 캔버스에는 여러 이미지를 자유롭게 배치할 공간을 확보한다. 오른쪽 패널에서는 캔버스를 보면서 선택한 이미지의 메모와 속성을 편집할 수 있다. 다른 이미지를 선택하면 패널도 해당 이미지의 내용으로 바뀐다.
- 이미지 편집 서비스의 주 테마 색상은 `#EE5165`다.
- UI 색상은 CSS 테마 토큰으로 관리하고 JSX에서는 토큰을 사용하는 스타일을 적용한다. 붉은 배경의 아이콘 버튼에는 배경과 대비되는 흰색 계열 아이콘을 기본으로 사용한다.
- 버튼을 클릭하거나 터치할 때 브라우저 기본 포커스 테두리를 표시하지 않는다. 키보드로 버튼에 포커스하면 테마에 맞춘 표시가 한 겹으로 보인다.
- 입력에 포커스하면 기존 테두리의 색이나 굵기를 바꾼다. 마우스, 터치와 키보드 모두에서 포커스를 확인할 수 있어야 하며 기본 테두리나 별도 링이 겹치지 않는다.
- 헤더 오른쪽의 `이미지 내보내기`는 배경을 채우지 않은 텍스트 버튼으로 표시한다. 테마 계열에서 실제 배경과 4.5:1 이상의 대비를 확보하는 글자색을 사용한다. 확대율 숫자와 글자의 기준선을 맞춘다. 클릭 영역은 투명한 여백을 포함해 최소 24×24 CSS px로 확보하고, 키보드 포커스를 눈으로 확인할 수 있게 한다.

- 각 UI 요소의 역할과 비슷한 실제 사용 사례를 조사한다. 데스크톱과 모바일 시안에서 배치, 크기, 간격, 대비와 조작 상태가 실제 표시 크기에서 어떻게 보이는지 비교한 뒤 표현 방식을 정한다.
- 정보와 상태는 그 내용을 알아보기 쉬운 방식으로 표시한다. 예를 들어 선택한 이미지는 썸네일로 알아볼 수 있게 하고, 현재 배치는 캔버스에서 확인할 수 있게 한다. 조작 요소는 사용자가 수행할 일에 맞춰 선택한다. 즉시 실행에는 버튼을, 범위 안에서 값을 조절할 때는 슬라이더를, 정확한 값을 지정할 때는 숫자 입력을 검토한다.
- 아이콘만으로 의미나 동작을 이해할 수 있는 요소에는 같은 뜻의 텍스트를 붙이지 않는다. 아이콘만으로 구분하기 어렵거나 사용자가 선택 결과를 알아야 하면 텍스트를 표시한다. 아이콘만 표시하는 조작 요소에도 동작을 설명하는 접근 가능한 이름을 제공한다.
- 아이콘 버튼은 클릭 영역의 정렬과 아이콘 자체의 시각적 정렬을 각각 확인한다. 버튼의 위치가 맞더라도 아이콘 내부 여백이나 모양 때문에 어긋나 보이면, 클릭 영역을 유지하면서 실제로 보이는 아이콘의 위치를 보정한다. 아이콘끼리는 시각적 중심을 맞추고, 제목이나 텍스트와 나란히 놓일 때는 글자와 함께 보이는 위치를 확인한다.

## 사용 환경

- 모바일 기기에서도 이미지 배치, 메모 작성과 이미지 저장을 쾌적하게 할 수 있어야 한다.
- 캔버스 편집과 이미지 내보내기는 브라우저에서 처리한다. 사용자는 서버에 접속하지 않아도 이미지를 편집하고 저장할 수 있다.
- 이미지 합성, 인코딩, 품질 미리보기와 예상 파일 용량 계산에서 오래 걸리는 처리는 Worker를 활용해 메인 스레드의 부담을 줄인다. 처리 중에도 페이지는 사용자 입력에 응답해야 한다.

## 이미지 파일로 저장

- 내보내기 패널에는 출력 미리보기, 형식, 범위, 예상 용량과 파일명을 표시한다. 설정마다 라벨을 붙이고, 라벨과 입력 사이 및 설정 묶음 사이에 이전 시안보다 여백을 넉넉히 둔다. 설정 묶음은 여백으로 구분하고, 구분선은 영역을 식별하는 데 필요한 곳에만 둔다.
- 범위가 `전체`일 때 패널에서 `여백`을 조절할 수 있다. 입력 하나로 상하좌우에 같은 값을 적용하며 기본값은 0px, 범위는 0~24px, 조절 단위는 1px이다. 값이 바뀌면 현재 내보내기의 미리보기와 예상 용량을 갱신한다. 선택 영역 내보내기에는 이 입력을 표시하지 않는다.

- 캔버스 전체나 선택 영역을 이미지로 내보낼 때는 사용자가 크기와 품질을 조정하지 않은 업로드 이미지의 원본 품질을 유지한다. 합성 및 저장 과정에서 품질이 달라지는 조건을 조사하고 그 근거를 내보내기 방식에 반영한다.
- 이미지 내보내기 파일명은 `<filename>.nwlee.<실제 확장자>` 형식을 사용한다.
- PNG(`.png`), SVG(`.svg`), JPG(`.jpg`)로 내보낼 수 있다. PNG는 합성한 픽셀을 무손실로 저장하며 기본 형식으로 제공한다.
- 기본 PNG에서 원본 크기로 배치한 이미지는 방향 정보를 반영한 원본의 가로와 세로 픽셀 수를 유지한다. 사용자가 줄인 이미지는 설정한 배치 크기로 합성한다. 화면 확대율은 합성본에 들어가는 이미지의 픽셀 크기에 영향을 주지 않는다.
- SVG에는 내보낼 영역에 포함된 이미지 내용을 담는다. 사용자는 원본 이미지 파일을 따로 전달하지 않아도 SVG에서 이미지와 메모를 볼 수 있다.
- JPG는 투명한 부분이 없는 이미지에서 선택할 수 있다. 손실 압축으로 이미지 품질이 달라질 수 있음을 저장 전에 알리고, 사용자가 JPG 저장을 선택한 경우에만 손실 압축을 적용한다.
- 사용자는 내보내기에 포함되는 각 이미지의 품질을 개별적으로 조정할 수 있다. 이미지별 품질은 합성 이미지 전체의 저장 품질과 별도로 조정한다.
- 이미지별 품질을 변경할 때마다 미리보기에 즉시 반영한다. 사용자는 변경된 모습을 확인한 뒤 이미지 파일을 저장할지 결정할 수 있다.
- 캔버스는 저장 전에 현재 내보내기 영역, 형식과 품질 설정을 기준으로 예상 이미지 파일 용량을 계산한다. 설정을 바꾸면 예상 용량을 다시 계산한다.
- 예상 용량이 저장 기준치를 초과하면 이미지 저장을 비활성화한다. 다시 계산한 예상 용량이 기준치 이내면 용량 초과로 인한 제한을 해제한다.
- 메모 내용이 표시 영역을 넘으면 캔버스를 이미지로 변환하기 전에 경고를 표시한다.
- 전체 캔버스를 이미지로 저장할 때는 각 이미지의 캔버스 좌표를 기준으로 이미지와 메모를 모두 담는다.
- 전체 이미지를 저장할 때 모든 배치 요소를 감싸는 사각형에 내보내기 패널에서 지정한 여백을 적용한다.
- 사용자는 사각형, 원형, 자유형으로 영역을 선택해 그 영역만 이미지로 저장할 수 있다.
- 원형이나 자유형을 선택해도 저장되는 이미지 파일은 사각형이다. 사각형 안에서 선택 영역에 포함되지 않는 부분은 투명하게 저장한다.

## 로컬 프로젝트 관리

- 이미지 이동과 크기 조절은 조작을 끝냈을 때 자동 저장한다. 메모 본문은 입력이 잠시 멈추면 자동 저장한다.

- 사용자는 현재 브라우저에 저장한 프로젝트를 목록에서 확인하고 열어 편집을 이어갈 수 있다. 목록을 다시 열면 저장한 프로젝트를 찾을 수 있어야 한다.
- 로컬 프로젝트는 IndexedDB에 저장한다. 프로젝트, 원본 이미지, 캔버스에 배치한 이미지와 메모는 관계에 따라 별도의 object store에 정규화하고 식별자로 연결한다. 전체 프로젝트나 하위 레코드 목록을 한 레코드에 중첩 객체나 JSON 문자열로 저장하지 않는다.
- 앱에서 IndexedDB 연결, 조회, 저장과 스키마 업그레이드에 `idb`를 사용한다.
- 새 프로젝트를 만들거나 ZIP을 불러올 때 프로젝트와 필요한 원본 및 편집 정보가 모두 저장된 뒤 목록에 표시한다. 저장에 실패하면 일부만 저장된 프로젝트를 열 수 없어야 하며 이미 저장한 작업은 보존한다.
- 같은 브라우저의 여러 탭에서 같은 프로젝트를 동시에 편집할 수 있다. 다른 이미지나 같은 이미지의 서로 다른 속성에 대한 수정은 모두 남아야 한다. 같은 메모에 동시에 입력해도 각 탭의 텍스트 변경을 병합한다.
- 메모 본문은 메모별 Yjs `Y.Text`로 병합한다. 입력이 잠시 멈추면 Yjs가 생성한 바이너리 변경분(`Uint8Array`)을 IndexedDB에 저장한다. 같은 변경을 다시 받아도 본문에 한 번만 반영한다.
- 같은 이미지의 위치나 크기를 두 탭이 동시에 바꾸면, 같은 항목에 대해 IndexedDB에 마지막으로 저장된 값을 표시한다.
- IndexedDB 커밋이 성공하면 `BroadcastChannel`로 같은 출처에서 앱을 연 다른 탭에 프로젝트 ID와 저장 순서만 알린다. 저장에 실패하면 알림을 보내지 않는다.
- 같은 프로젝트를 편집하는 탭은 새 저장 알림을 받으면 IndexedDB에서 최신 저장본을 읽고 메모 변경분을 병합한다. 알림이 중복되거나 늦게 도착해도 수정이 중복되거나 화면이 이전 저장본으로 돌아가지 않아야 한다. 알림을 놓친 탭은 화면에 다시 표시될 때 IndexedDB에서 최신 저장본을 확인한다.
- 다른 탭에서 저장한 수정은 새로고침 없이 반영한다. 다른 탭의 수정이 현재 입력 포커스, 선택한 이미지나 드래그를 끊지 않아야 한다. 백그라운드에 있던 탭을 다시 열면 놓친 저장 내용을 반영하고 현재 탭의 저장 대기 중인 수정도 보존한다.
- 목록에는 헤더를 한 번만 표시한다. 목록 헤더는 캔버스 편집기 헤더와 별도로 구성한다. 로고가 확정될 때까지 왼쪽에 문구 없는 직사각형을 표시한다. 오른쪽에는 새 프로젝트와 불러오기를 배치한다.
- 프로젝트는 캔버스 미리보기가 중심인 카드 그리드로 표시한다. 카드 아래에는 프로젝트 이름과 마지막 편집 시각을 표시한다.
- 새 프로젝트와 불러오기는 아이콘 버튼으로 표시하고 각 버튼에 동작을 설명하는 접근 가능한 이름을 제공한다.
- 편집용 ZIP을 선택하면 `프로젝트 불러오기` 창에 파일명과 미리보기를 표시한다. 확인 버튼은 `불러오기`로 표시하고, 사용자가 누르면 새 프로젝트로 연다. 창에는 `새 프로젝트로 열립니다` 문구를 표시하지 않는다.

## 편집용 파일로 저장

- 편집용 ZIP에는 원본 이미지 바이트와 현재 편집 상태를 담는다. 다른 기기에서 불러오면 새 프로젝트에 프로젝트 이름, 이미지 위치, 배치 크기, 겹침 순서, 이미지별 품질 설정, 메모 원문과 크기 및 부착 방향을 복원한다. 이미지와 메모의 연결도 유지한다.
- 편집용 파일은 ZIP으로 저장하며 파일명은 `<filename>.nwlee.zip` 형식을 사용한다. 전용 확장자 정의는 보류한다.
- 파일 내부의 형식 식별자와 정수 스키마 버전으로 불러올 수 있는 파일인지 판별한다. 첫 버전은 `1`이며 앱 배포 버전과 별도로 관리한다. 새 스키마를 도입할 때는 기존 지원 버전의 편집 상태를 복원할 수 있는지 검증한다. 지원하지 않는 버전이면 새 프로젝트를 만들기 전에 안내한다.
- 편집용 ZIP의 저장과 불러오기 한도는 대상 데스크톱과 모바일 환경에서 대표 프로젝트를 직접 측정한 뒤 정한다. 같은 지원 조건에서 앱이 저장한 파일을 다시 불러올 수 있어야 한다.

## 코드 구조

- 캔버스 앱은 Feature-Sliced Design(FSD)을 따른다. 화면 전용 코드는 해당 페이지에 두고, 여러 화면이 같은 의미로 사용하는 프로젝트 데이터와 편집 규칙은 공통 모델로 관리한다. 슬라이스 사이의 참조는 하위 레이어가 외부에 제공하는 API를 사용한다.
- 브라우저 저장소, 편집용 ZIP, 이미지 처리 Worker는 의존성 주입으로 연결한다. 각 동작은 필요한 기능을 타입으로 선언하고, 앱 시작부에서 구체 구현을 선택해 전달한다. 화면과 편집 규칙에서 구체 구현을 직접 생성하거나 전역 객체에서 찾아 쓰지 않는다.
- 캔버스 앱의 화면, 편집 규칙과 브라우저 연결부는 해당 앱에서 관리한다. 다른 애플리케이션의 소스나 실행 환경 없이 빌드하고 구현할 수 있어야 한다.

### 모듈과 의존성

- 폴더와 파일 이름은 kebab-case로 작성한다. 규칙을 적용하기 어려운 이름이 있으면 이유를 설명하고 결정을 기다린다. 함수나 메서드와 클래스 본문에서 의미 있는 숫자나 정규표현식은 이름을 붙인 상수로 사용한다. 날짜는 밀리초 단위 Unix 타임스탬프로 저장한다.

- 모듈마다 책임을 하나로 정한다. 같은 책임을 완성하며 함께 변경되는 타입, 상수와 구현은 함께 둘 수 있다. 작성 전에 추가, 수정, 제거할 코드를 확인한다. 기존 모듈에 추가할 코드의 책임이나 변경 이유가 다르면 분리한다. 중복은 같은 책임과 변경 이유를 공유할 때 공통화할지 검토하며, 모양이 비슷하다는 이유로 서로 다른 역할의 코드를 복제하거나 합치지 않는다.
- 폴더, 파일, 타입과 심볼에는 역할이 드러나는 이름을 붙인다. 상위 경로의 문맥이나 `Feature`, `Entities`, `View`, `Controller` 같은 일반 분류명을 이름에 반복하지 않는다.
- HTTP, 스토리지, 로그, 분석, 설정 및 외부 SDK는 실행 환경과 테스트에 따라 사용하는 쪽의 코드를 바꾸지 않고 교체할 수 있게 한다. UI, 폼, 쿼리와 애플리케이션 동작은 구체 구현을 직접 가져오지 않는다. 필요한 작업만 인터페이스로 정의하고 독립적으로 바뀌는 조회, 수정과 삭제는 필요한 경우에만 묶는다.
- 범용 의존성 조회를 UI에 노출하지 않는다. 필요한 기능만 반환하는 전용 접근 훅은 현재 주입된 구현을 반환하며 조회, 캐시와 데이터 변환을 수행하지 않는다. 이 훅은 쿼리, 변경 처리 또는 외부 연동 코드에서 우선 사용한다. 말단 UI는 인프라 의존성을 조회하지 않는다.

### React 합성과 상태

- React Router의 loader와 action, TanStack Query의 조회와 변경, React Hook Form이 관리하는 값을 `useState`에 복사하지 않는다. `useRef`는 DOM 참조나 렌더링과 별개로 유지할 값을 다룰 때 사용한다.

- 컴포넌트는 자신의 역할에 필요한 값과 직접 호출하는 함수만 Props로 선언한다. 하위 컴포넌트로 넘기기만 하는 값이나 함수는 Props로 받지 않는다. 받은 함수를 호출하는 일만 하는 콜백을 새로 만들어 하위 컴포넌트에 전달하는 경우에도 같은 기준을 적용한다.
- 컴포넌트마다 화면 표시, 사용자 조작 처리, 화면 조립 등 맡는 일을 구분한다. 화면을 배치하는 컴포넌트는 실제로 값이나 함수를 쓰는 컴포넌트를 `children`으로 배치할 수 있다. 깊은 하위 트리가 같은 값을 공유해야 할 때 Context를 사용한다.
- UI 합성은 `children` 또는 명시적인 Compound Components를 우선한다. 임의의 JSX Props로 슬롯을 늘리거나 자체 API의 기본 방식으로 Render Props를 도입하지 않는다. 외부 라이브러리의 공식 연동 API가 요구하는 Render Props는 허용한다.
- 컴포넌트나 Hook을 렌더링 중에 정의하지 않는다. `useState`, `useMemo`, `useCallback`으로 컴포넌트 타입을 생성하지 않는다. 컴포넌트는 JSX로 렌더링하며 일반 함수처럼 호출하지 않는다.
- 기능 진입점은 조회, 폼, 변경 처리와 화면 흐름을 연결할 수 있다. 상태와 Hook은 실제로 사용하는 곳에 둔다. 말단 UI는 표현과 자체 조작에 필요한 UI 및 폼 Context를 사용할 수 있다. 재사용 UI에는 데이터 조회, 화면 이동, 캐시 갱신과 의존성 조회를 내장하지 않는다.
- 같은 의미의 상태는 한 곳에서 관리한다. 브라우저에서 한 번만 생성해야 하는 클라이언트는 컴포넌트 밖의 브라우저 초기화 코드에서 생성한다. 서버와 클라이언트를 나누는 환경에서는 클라이언트 동작이 필요한 하위 트리의 진입점에만 `"use client"`를 선언한다.

### 폼과 서버 데이터 도구의 적용 조건

- React Hook Form을 사용하면 각 폼의 `useForm`이 수명을 관리한다. 하위 필드에서 같은 폼을 공유할 때는 `FormProvider`와 공식 Context API를 사용한다. 네이티브 입력은 `register`를 우선하고, 외부 제어 입력 또는 필드 단위 제어가 필요할 때 `Controller`나 `useController`를 사용한다. `useWatch`, `useFormContext`, `watch`, `setValue` 등은 구독, 연동 또는 명령형 갱신에 필요한 범위에서 사용한다. 필요한 필드만 구독하고 폼 상태와 제어 객체를 DI Context나 별도 스토어에 복제하지 않는다. Compound Component의 하위 필드도 폼과 UI에 필요한 작업만 맡는다.
- TanStack Query를 사용하면 서버 데이터와 캐시 수명은 Query에 맡긴다. 변경 모듈은 서버 변경과 관련 캐시 갱신 또는 무효화를 맡는다. 쿼리 함수에서 주입된 I/O를 호출할 수 있지만 Query 자체를 DI로 감싸지 않는다. 여러 곳에서 재사용하거나 키와 정책의 일관성이 필요할 때 `queryOptions`를 사용하고, 취소 신호는 이를 지원하는 I/O에 전달한다.
- 성공한 쿼리 데이터에서 표시값을 구할 때 순수 selector나 `select`를 사용한다. 검증 실패를 쿼리 오류로 처리해야 하면 쿼리 함수에서 검증한다. 재사용할 selector는 모듈 범위에 두고 단순 계산에는 불필요한 메모화를 추가하지 않는다. 쿼리나 변경 훅의 반환 객체 전체를 Context나 범용 Props로 전달하지 않는다. Zustand 같은 스토어는 독립적인 클라이언트 상태가 있을 때만 사용하며 Query 캐시를 복제하지 않는다.

### 구현 전 정적 검사

- 구현 전에 ESLint로 방지할 수 있는 규칙을 해당 앱의 설정에 적용한다. 설정 파일 구성으로 진행하며 별도 검사 스크립트나 검사용 모듈을 만들지 않는다. 모듈의 책임, 상태의 중복과 합성 방식처럼 코드의 의미를 판단해야 하는 기준은 변경 검토에서 확인한다.

## 백로그

- 저장되지 않은 편집을 새로고침하거나 탭을 닫은 뒤 다시 열었을 때 복구하는 기능은 보류한다.

- 전용 로고를 확정하면 목록 헤더의 직사각형을 전용 SVG 로고로 교체한다.

- 목록 헤더의 도움말과 설정은 보류한다. 제공할 내용과 동작을 정한 뒤 아이콘으로 배치한다.

- 서버 렌더링(SSR)이 필요한 화면이 생기거나 SSR 환경에서 호환 문제가 확인되면 영향받는 화면과 기능을 파악하고 대응 방식을 조사한다. Konva, 브라우저 저장소와 Worker가 브라우저에서 초기화되고 기존 프로젝트를 계속 열 수 있는지 확인한다.

- 실제 서비스 사용 중 이미지 편집, 내보내기 또는 편집용 파일 저장과 불러오기에서 성능 문제가 발생하면 재현 조건과 병목을 확인하고, 문제가 생긴 처리 단계에 적용할 수 있는 대안을 조사한다.
