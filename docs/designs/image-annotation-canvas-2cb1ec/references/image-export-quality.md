# 캔버스에서 내보낸 이미지의 원본 품질

기본 PNG는 업로드한 원본을 캔버스에 설정된 이미지 크기로 합성한다. 원본 크기로 배치하면 방향 정보를 반영한 원본의 가로와 세로 픽셀 수를 유지한다. 줄인 이미지를 원본 크기로 되돌릴 때는 보존한 원본을 사용한다. [이미지 저장 요구사항](../requirements.md#이미지-파일로-저장)

- Canvas의 `drawImage()`는 원본 영역을 대상 영역에 그린다. 두 영역의 치수를 같게 하고 저장할 이미지에서 원본을 그리기 시작할 위치를 정수 픽셀에 맞추면 크기 조절과 소수 픽셀 위치에서 생기는 보간을 피할 수 있다. 선택 영역 저장에서 일부가 가려지거나 잘리면 선택 안에 있고 가려지지 않은 픽셀만 비교한다. [WHATWG 이미지 그리기](https://html.spec.whatwg.org/multipage/canvas.html#drawing-images), [ImageBitmap 방향 처리](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#imagebitmap) (2026-11-12 확인)
- PNG는 합성한 픽셀을 무손실로 저장하고 투명도를 담을 수 있다. 색 공간 변환이나 반투명 픽셀 합성에서 바뀐 값은 PNG에도 반영된다. 저장 파일의 색 프로필은 합성 비트맵의 색 공간을 나타낸다. [W3C PNG 3판, 2025-06-24](https://www.w3.org/TR/png-3/), [WHATWG Canvas 색 공간과 파일 저장](https://html.spec.whatwg.org/multipage/canvas.html#serialising-bitmaps-to-a-file) (2026-11-12 확인)
- 불투명 8비트 sRGB 표본은 픽셀 값을 직접 비교한다. Canvas는 투명 색을 알파가 곱해진 형태로 저장하므로 반투명 색을 원래 표현으로 바꾸는 과정에서 반올림 차이가 생길 수 있다. 반투명 가장자리는 밝고 어두운 배경에 합성한 색으로 확인한다. Display P3와 HDR은 [백로그](../requirements.md#백로그)에서 다룬다. [WHATWG Canvas의 투명도 표현](https://html.spec.whatwg.org/dev/canvas.html) (2026-11-13 확인)

## 통합 이미지의 초기 한도

초기 한도는 [이미지 저장 요구사항](../requirements.md#이미지-파일로-저장)에 둔다. 아래 계산과 상용 도구 사례를 초기값을 정하는 근거로 사용했다.

- Figma REST API의 이미지 렌더링은 3,200만 픽셀보다 큰 결과를 자동으로 줄인다. 플러그인 API에서는 배율, 지정 너비와 높이, 색 프로필을 각각 지정한다. API에서 적용하는 출력 정책을 브라우저 로컬 처리 성능으로 해석할 수는 없다. [Figma 렌더링 API](https://developers.figma.com/docs/rest-api/file-endpoints/#get-image) [Figma 플러그인 ExportSettings](https://developers.figma.com/docs/plugins/api/ExportSettings/) (2026-11-13 확인)
- Canva Connect의 PNG 내보내기 작업은 너비와 높이 입력에 각각 25,000px 상한을 둔다. Photopea 유지보수자는 특정 환경에서 8,192px를 넘는 GPU 텍스처 문제를 보고받아 WebGL을 끄고 비교하도록 안내했다. Adobe Photoshop UXP Imaging API도 픽셀 요청 크기를 줄이고 사용이 끝난 이미지 데이터를 해제하도록 안내한다. [Canva Connect 내보내기 API](https://www.canva.dev/docs/apps/rest-apis/reference/exports/create-design-export-job/) [Photopea 유지보수자 답변](https://github.com/photopea/photopea/issues/5888) [Photoshop UXP Imaging API](https://developer.adobe.com/photoshop/uxp/2022/ps-reference/media/imaging) (2026-11-13 확인)

1080p 이미지 10장을 5열 2행에 놓고 이미지 아래에 200px 높이의 메모를 붙인다고 가정한다. 열과 행 사이에 64px를 띄우고 외곽에 24px 여백을 적용하면 결과는 9,904 × 2,672px, 약 2,646만 픽셀이다. 각 변 12,288px, 총 2,800만 픽셀의 초기값은 이 배치를 수용한다. 총 픽셀 한도에서 8비트 RGBA 버퍼 하나는 약 106.8 MiB를 사용한다. 원본 디코딩, 미리보기와 인코더 메모리는 별도로 필요하다. [WHATWG ImageData 저장 형식](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#imagedata)

파일 한도 64 MiB는 초기 추정값이다. 예를 들어 편집용 ZIP의 32 MiB 원본을 SVG에 Base64로 모두 넣으면 인코딩 데이터는 약 42.7 MiB가 되고 여기에 SVG 구조와 메모가 추가된다. PNG는 합성 픽셀의 내용에 따라 파일 크기가 달라지므로 치수 검사를 통과하더라도 별도로 파일 바이트를 확인한다. [RFC 4648 Base64](https://www.rfc-editor.org/rfc/rfc4648.html#section-4) [W3C PNG 명세](https://www.w3.org/TR/png-3/)


## 브라우저의 기준 배치 확인

Chromium 156은 CPU를 12.1배 느리게 설정했고, WebKit 27.2는 CPU 제한 없이 영구 프로필로 실행했다. 브라우저에서 만든 불투명 단색 PNG 5장과 무작위 색을 담은 PNG 5장을 각각 1,920×1,080으로 준비했다. 이미지에 높이 200px의 빈 메모 상자를 붙여 5열 2행에 배치하고 외곽에 24px 여백을 적용했다. 브라우저별 한 번씩 실행했다.

- Chromium에서 PNG는 15,329,812바이트였고 미리보기 확인에 약 0.93초가 걸렸다. SVG는 47,862,128바이트였고 약 9.69초가 걸렸다.
- WebKit에서 PNG는 15,056,304바이트였고 약 1.00초가 걸렸다. SVG는 48,636,468바이트였고 약 0.39초가 걸렸다.
- 네 파일 모두 9,904×2,672px였고 현재 치수와 용량 한도를 충족했다. 측정 시간에는 형식 선택, 미리보기 디코딩과 Blob 크기 조회가 포함된다. CPU 조건이 달라 엔진 간 처리 속도를 직접 비교할 수 없다.

같은 Chromium과 CPU 제한 조건에서 SVG를 두 번씩 비교했다. 기존 Worker 응답은 270~271ms였고 응답부터 미리보기 디코딩까지 8,783~9,294ms가 걸렸다. 긴 변 768px의 PNG 미리보기를 Worker에서 별도로 합성한 뒤 응답은 384~395ms, 응답 후 디코딩은 428~494ms였다. 미리보기를 768×208px로 표시해도 다운로드한 SVG는 9,904×2,672px와 47,862,128바이트를 유지했다. 편집 입력과 겹칠 때의 프레임 지연은 별도 검증 대상이다.

## 회전과 투명도가 있는 PNG 출력 확인

Chromium 156과 WebKit 27.2의 영구 프로필에서 각 표본을 원본 크기로 배치하고 PNG를 다운로드했다. EXIF 방향 값이 6인 80×40 JPEG는 두 브라우저에서 모두 40×80 PNG로 저장됐고 빨간색이 위, 파란색이 아래에 놓였다. 회전을 반영해 디코딩한 원본과 출력 PNG의 픽셀 값이 일치했다.

완전 투명 영역과 알파 25%, 75% 영역을 담은 80×40 PNG도 두 브라우저에서 치수와 투명 영역을 유지했다. 원본과 출력 파일을 각각 흰색과 검은색 배경에 합성해 전체 픽셀을 비교했을 때 두 배경 모두 채널별 최대 차이는 0이었다. 두 표본에서 확인한 결과다.

## 1080p 이미지 10장의 배치 비교

두 브라우저에서 5열 2행 배치의 PNG와 SVG 미리보기가 초기 한도에 들어왔다. 세로 한 줄은 높이 한도, 간격을 넓힌 5열 2행은 총 픽셀 한도를 초과했다.

사진을 잘라 만든 1,920×1,080 PNG 10장을 사용했다. 그중 5장에는 왼쪽 절반에 무작위 색상 무늬를 더했다. 모든 이미지 아래에 높이 200px의 빈 메모 상자를 붙이고 외곽 여백을 24px로 설정했다. 각 브라우저에서 원본을 인코딩한 뒤 같은 원본의 배치만 바꿨다. Chromium 156은 CPU 12.1배 제한, WebKit 27.2는 CPU 제한 없이 영구 프로필을 사용했다. 두 브라우저 모두 1,440×1,000 화면에서 조합별 한 번 측정했다.

| 배치 | 내보내기 치수 | 두 브라우저에서 확인한 동작 |
| --- | ---: | --- |
| 5열 2행, 간격 64px | 9,904×2,672px | PNG와 SVG 미리보기 표시. JPG는 투명 영역 경고로 차단 |
| 세로 한 줄, 간격 64px | 1,968×13,424px | 세 형식 모두 높이 한도에서 차단 |
| 5열 2행, 가로 간격 580px, 세로 간격 320px | 11,968×2,928px | 세 형식 모두 총 픽셀 한도에서 차단 |

5열 2행에서 형식 선택 직전부터 미리보기 디코딩 또는 경고 표시까지 걸린 시간과 패널의 예상 용량을 확인했다.

| 브라우저 | PNG | SVG | JPG 경고 |
| --- | --- | --- | --- |
| Chromium | 1.28초, 41.57 MiB | 0.85초, 55.09 MiB | 1.23초 |
| WebKit | 2.12초, 38.48 MiB | 0.79초, 51.05 MiB | 1.09초 |

같은 구간에서 프레임 콜백의 최대 간격은 Chromium에서 PNG 183.3ms, SVG 16.8ms, JPG 경고 750ms였다. WebKit에서는 각각 325ms, 19ms, 309ms였다. 실제 입력부터 화면 표시까지의 지연과 최대 메모리는 측정하지 않았다. CPU 설정과 원본 PNG 인코더가 달라 두 엔진의 속도와 용량을 직접 비교할 수 없다.

### 프레임 공백이 발생한 구간

Chromium 156의 CPU 12.1배 제한에서 같은 5열 2행과 여백을 사용해 SVG, PNG, JPG 순으로 세 번 반복했다. 사진의 절반에 더한 무작위 색상은 이전 측정과 다른 시드로 생성했다. Worker 요청과 응답 시각, 미리보기 디코딩 또는 경고 확인 시각, 프레임 콜백과 Long Tasks 항목을 기록했다.

- **PNG.** 세 번 모두 Worker가 원본 크기의 PNG를 반환한 뒤 가장 긴 프레임 공백이 발생했다. 실행별 최대 간격은 150ms, 783ms, 183ms였다. 같은 응답 이후 구간에 메인 스레드의 72~184ms 작업이 실행당 두 건씩 기록됐다. 디코딩과 이미지 표시 과정 중 어느 작업이 각 공백을 일으켰는지는 아직 구분하지 못했다.
- **SVG.** 축소한 PNG 미리보기를 반환했을 때 최대 간격은 17~50ms였다. PNG도 축소 미리보기를 별도로 만들고 다운로드에는 원본 크기의 PNG를 사용하는 방안을 같은 표본으로 비교할 수 있다. 이 경우 추가 합성과 인코딩 비용도 함께 측정한다.
- **JPG.** 세 번 모두 Worker가 투명 영역 경고만 반환했고 이미지 미리보기를 디코딩하지 않았다. 응답 전 83~367ms 공백이 있었고, 응답 이후에도 83~100ms 공백이 관측됐다. Long Tasks 항목은 관측되지 않았다. Worker 내부 투명도 검사, 이전 미리보기 제거와 브라우저 렌더링에 걸린 시간을 추적해야 원인을 구분할 수 있다.

### PNG 축소 미리보기 적용

큰 PNG는 Worker에서 합성한 캔버스를 한 번 더 그려 긴 변 768px의 미리보기를 만든다. 다운로드에는 원래 크기로 인코딩한 PNG를 사용한다. Worker 응답에 전체 크기 PNG만 포함했을 때는 패널도 전체 크기 PNG를 디코딩했고, 앞선 추적에서 응답 이후 프레임 공백이 반복됐다.

CSS로 표시 크기만 제한하는 방식은 원래 크기 PNG를 패널에 전달한다. SVG처럼 축소 크기로 다시 합성하는 방식은 원본 이미지 디코딩과 메모 그리기를 반복한다. 합성한 캔버스를 축소하는 방식은 그려 둔 픽셀을 재사용하고 미리보기만 다시 인코딩한다. PNG 다운로드의 크기와 내용도 유지할 수 있어 이 방식을 적용했다.

Chromium 156에서 CPU 12.1배 제한과 1,440×1,000 화면을 사용했다. 같은 1080p 이미지 10장을 5열 2행에 배치하고 메모 높이 200px, 외곽 여백 24px로 설정했다. 두 빌드에서 SVG 미리보기를 표시한 뒤 PNG로 전환하는 동작을 각각 세 번 측정했다.

| 지표 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 최대 프레임 콜백 간격 | 200~800ms | 약 17ms |
| Worker 요청부터 응답까지 | 746~765ms | 744~757ms |
| 응답부터 미리보기 디코딩 확인까지 | 413~1,063ms | 66~71ms |

미리보기는 9,904×2,672px에서 768×208px로 줄었다. 두 빌드의 다운로드는 모두 9,904×2,672px, 43,585,603바이트였고 SHA-256이 일치했다. Worker 응답 시간은 관측 범위가 겹쳤다. 축소 인코딩만의 비용, 최대 메모리와 실제 입력 지연은 이 비교에서 측정하지 않았다.

### JPG 투명도 검사 비용 분리

Chromium 156에서 9,904×2,672px의 단색 캔버스를 Worker에 만들고, 앱과 같은 64행 단위로 알파 값을 읽었다. 페이지에 CPU 12.1배 제한을 적용하고 외곽 여백 24px와 0px 조건을 각각 세 번 실행했다. 투명 여백이 있으면 첫 읽기에서 검사가 끝났고 6.0~6.6ms가 걸렸다. 전체가 불투명하면 42회 읽기에 47.8~51.4ms가 걸렸다. 이미지 디코딩과 합성은 이 비교에서 제외했다. 이 측정만으로 앱에서 관측한 프레임 공백의 원인을 알 수 없다.

전체 내보내기에서 외곽 여백이 양수이면 합성 전에도 투명 영역이 생긴다는 것을 알 수 있다. 여백이 0px이거나 사각형을 선택한 경우에는 원본의 알파 값과 배치에 따라 달라진다. 외곽 여백이 있는 JPG 요청의 조기 판정은 메모 잘림 경고를 보존하는 조건에서 비교한다. 여백만으로 판단할 수 없는 요청은 합성 픽셀 검사를 유지한다.

### 흰색 배경 JPG의 10장 저장

흰색 배경을 적용한 운영 빌드에서 1080p 이미지 10장을 5열 2행으로 배치했다. 간격은 64px, 메모 높이는 200px, 외곽 여백은 24px였다. Chromium 156에서 화면 1,440×1,000과 CPU 12.1배 제한을 사용했다. 이미지별 품질과 전체 품질은 모두 100%로 두고, SVG 미리보기에서 JPG로 전환하는 동작을 세 번 반복했다.

| 지표 | 1회 | 2회 | 3회 |
| --- | ---: | ---: | ---: |
| Worker 요청부터 응답까지 | 940ms | 662ms | 691ms |
| 응답부터 미리보기 디코딩 확인까지 | 457ms | 796ms | 442ms |
| 최대 프레임 콜백 간격 | 350ms | 383ms | 100ms |

마지막 미리보기에서 저장한 JPG는 27,288,917바이트였다. 미리보기 치수는 9,904×2,672px였다. 저장 클릭부터 자동화에서 다운로드 스트림을 모두 읽을 때까지 105ms가 걸렸다. 실제 입력 지연과 최대 메모리는 이 측정에 포함하지 않았다. 기존 투명도 경고 측정과는 결과 파일 생성 여부가 달라 전후 성능 비교로 사용하지 않는다.

같은 조건에서 큰 JPG를 Worker에서 디코딩해 768×208px PNG 미리보기로 만드는 방식을 기존 방식과 각각 세 번 비교했다. Worker 요청부터 디코딩 확인까지는 기존 1,107~1,514ms, 축소 방식 1,422~1,696ms였다. 최대 프레임 콜백 간격은 기존 333ms, 333ms, 100ms와 축소 방식 350ms, 83ms, 83ms로 관측됐다.

전체 품질 100%와 20%에서 두 방식의 다운로드 SHA-256이 각각 일치했다. 축소 미리보기도 품질 변경에 따라 달라졌다. 추가 디코딩과 PNG 인코딩이 미리보기 준비 시간을 늘렸고 최대 프레임 공백도 일관되게 줄지 않아 기존 방식을 유지했다.

### JPG 생성 중 클릭 지연과 메모리

Chromium 156에서 같은 5열 2행 배치, 24px 여백과 CPU 12.1배 제한을 사용했다. SVG 미리보기가 표시된 상태에서 화면 이동 버튼을 10회 클릭한 경우와 JPG로 전환하면서 같은 버튼을 10회씩 클릭한 세 경우를 비교했다. Event Timing의 클릭 시작부터 처리 시작까지와 클릭 시작부터 다음 표시까지를 기록했다. [W3C Event Timing](https://www.w3.org/TR/event-timing/)

| 조건 | 클릭 처리 시작까지 최대 | 클릭 시작부터 다음 표시까지 최대 | 브라우저 프로세스 RSS 합계 시작 → 표본 최고값 |
| --- | ---: | ---: | ---: |
| SVG 표시 중, JPG 요청 없음 | 16ms | 56ms | 609 → 616 MiB |
| JPG 1회 | 307ms | 352ms | 616 → 914 MiB |
| JPG 2회 | 40ms | 136ms | 779 → 1,067 MiB |
| JPG 3회 | 40ms | 656ms | 990 → 1,284 MiB |

브라우저와 자식 프로세스의 RSS를 100ms 간격으로 합산했다. 공유 메모리를 중복 집계할 수 있고 GPU 메모리와 표본 사이의 최고값은 확인하지 못했다. 같은 탭에서 반복할수록 시작값도 늘었다. 이 수치만으로 메모리 누수를 판정할 수 없다. 첫 실행에서 처리 시작까지 307ms가 걸린 클릭은 Worker 응답 전이었고, 세 번째 실행에서 표시까지 656ms가 걸린 클릭은 응답 이후였다. 후속 비교에서는 내보내기 반복을 멈춘 뒤 메모리가 줄어드는지와 두 구간의 브라우저 작업을 추적한다.
