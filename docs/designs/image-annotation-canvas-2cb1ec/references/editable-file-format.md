# 캔버스 편집용 파일 형식과 호환성

원본 이미지 여러 장과 편집 상태를 다른 기기로 옮기려면 JSON 문서와 원본 이미지 파일을 한 ZIP에 담는 방식을 우선 검토할 만하다. 작업당 원본 이미지의 총용량이 낮다면 이미지를 Base64로 담는 단일 JSON도 후보다. 비교 기준은 [편집용 파일로 저장](../requirements.md#편집용-파일로-저장)이다. 편집용 파일은 ZIP으로 저장하며, 내부 구성과 버전 호환 정책은 아직 결정되지 않았다.

## 파일 구성 후보

### JSON과 원본 이미지를 묶는 ZIP

ZIP은 이름이 있는 여러 파일을 하나로 묶는다. EPUB의 OCF는 ZIP 내부에 형식을 식별하는 파일과 문서 및 리소스를 함께 두는 사례다. [PKWARE ZIP APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT), [W3C EPUB 3.3 권고안, 2026-01-13](https://www.w3.org/TR/2026/REC-epub-33-20260113/#sec-zip-container)

이 캔버스에서는 JSON에 객체의 식별자, 캔버스 좌표, 이미지 배치 크기, 메모 크기와 내용과 부착 정보, 이미지 파일의 참조를 둘 수 있다. 원본 이미지는 별도 항목으로 넣어 이미지 바이트를 그대로 가져갈 수 있다. 이 방식에는 ZIP 처리와 내부 파일 참조 검사가 필요하다. PNG나 JPEG를 다시 압축해 얻는 이득과 기기에서 쓰는 메모리는 대표 작업 파일로 확인해야 한다.

### 이미지를 포함하는 단일 JSON

Excalidraw의 로컬 저장 코드는 형식과 버전, 편집 요소와 참조된 파일을 하나의 JSON으로 직렬화한다. 바이너리를 JSON에 넣는 한 방법인 Base64는 입력 3바이트를 문자 4개로 바꾼다. UTF-8로 저장하면 이미지 부분만 보아도 큰 입력에서 약 3분의 1이 늘어난다. [Excalidraw 저장 소스, dd8296a](https://github.com/excalidraw/excalidraw/blob/dd8296af1802d4920a645591e0de88b9272745fa/packages/excalidraw/data/json.ts), [RFC 4648 §4, 2006-10](https://www.rfc-editor.org/rfc/rfc4648.html#section-4)

JSON 하나는 내용을 직접 확인하기 쉽고 압축 파일을 푸는 단계가 없다. 다만 파일 전체를 문자열로 읽고 이미지까지 디코딩하면 원본 바이트와 별도로 문자열과 디코딩 자료가 메모리를 차지할 수 있다. 이미지 URL이나 기기 내부의 파일 위치만 저장하면 새 기기에서 원본을 열 수 없는 경우가 생긴다. 두 후보 모두 편집에 필요한 원본을 파일 안에 포함하는 구성이 적합하다.

## 전용 확장자와 일반 ZIP 비교

전용 확장자는 편집할 수 있는 캔버스 파일임을 이름으로 드러낸다. ZIP에 JSON과 원본 이미지를 담는 내부 구성에도 전용 확장자를 붙일 수 있다. EPUB 3.3은 ZIP 기반 컨테이너에 `.epub`을 쓰는 사례다. [W3C EPUB 3.3 권고안, 2026-01-13](https://www.w3.org/TR/2026/REC-epub-33-20260113/)

Figma Design은 로컬 복사본을 `.fig`로 저장하며, 사용자는 Figma의 파일 브라우저에서 다시 가져올 수 있다. Figma는 이 형식을 자체 형식으로 설명하며 변경될 수 있다고 명시한다. 이 사례는 전용 확장자로 편집 문서를 구분하는 근거다. Figma 도움말에는 내부 컨테이너 구성이 명시되어 있지 않다. [Figma 로컬 복사본 저장](https://help.figma.com/hc/en-us/articles/8403626871063-Save-a-local-copy-of-files), [Figma 파일 가져오기](https://help.figma.com/hc/en-us/articles/360041003114-Import-files-to-the-file-browser) (2026-11-12 확인)

- 전용 확장자의 장점은 다운로드 폴더에서 일반 압축 파일과 캔버스 문서를 구별하기 쉽고, 앱의 파일 선택창에서 편집용 파일을 찾도록 도울 수 있다는 점이다.
- 전용 확장자의 단점은 운영체제나 파일 앱이 파일 종류를 모를 때 연결 앱, 미리보기 또는 압축 풀기가 바로 제공되지 않을 수 있다는 점이다. 브라우저의 파일 선택 필터는 확장자를 힌트로 사용한다. 운영체제에서 파일을 바로 열 수 있는지, 웹 앱에서 파일을 골라 불러올 수 있는지 각각 확인한다. [WHATWG 파일 선택 규칙](https://html.spec.whatwg.org/multipage/input.html#attr-input-accept), [Apple 파일 형식 정의](https://developer.apple.com/documentation/UniformTypeIdentifiers/defining-file-and-data-types-for-your-app) (2026-11-12 확인)
- 일반 `.zip`은 iPhone과 iPad의 파일 앱이나 Windows 파일 탐색기에서 원본 이미지를 직접 꺼낼 수 있다. 일반 압축 파일과 섞이기 쉬우며 파일을 탭했을 때 편집을 재개하는 대신 압축이 풀릴 수 있다. [Apple ZIP 안내](https://support.apple.com/en-ae/102532), [Microsoft ZIP 안내](https://support.microsoft.com/en-us/windows/experience/storage-filemanagement/zip-and-unzip-files) (2026-11-12 확인)

편집용 파일은 이름에 `.nwlee`를 붙이고 표준 `.zip` 확장자를 사용한다. 전용 확장자 정의는 보류한다. 파일명이 바뀌어도 내부 식별자와 버전이 일치하면 다시 열 수 있는 방식은 불러오기 정책의 후보다.

## 형식 식별, 버전과 불러오기

- 확장자는 파일 선택에 쓰고, 파일 내부 식별자와 문서 형식 버전으로 읽을 수 있는 파일인지 판단하는 방안을 제안한다. 앱 배포 버전과 파일 형식 버전은 별도로 관리한다. 이전 형식을 계속 읽기로 했다면 버전별 변환을 거쳐 현재 객체를 복원한다. 읽을 수 없는 새 버전은 변경을 적용하기 전에 알린다. [Excalidraw 저장 소스, dd8296a](https://github.com/excalidraw/excalidraw/blob/dd8296af1802d4920a645591e0de88b9272745fa/packages/excalidraw/data/json.ts)
- JSON Schema 2020-12는 필수 필드, 자료형과 숫자의 상한 및 하한을 검사할 수 있다. 이미지 참조가 ZIP 안에 실제로 존재하는지, 메모가 존재하는 이미지에 붙는지, 메모가 이미지 가장자리에 닿고 이미지를 가리지 않는지는 별도로 확인해야 한다. [JSON Schema Validation 2020-12, 2022-06 문서](https://json-schema.org/draft/2020-12/json-schema-validation)
- 불러오기 전에 파일 구조, 이미지 참조와 디코딩 가능 여부를 확인하고 검사가 끝난 뒤 작업을 연다는 방안을 제안한다. ZIP을 택하면 중복 항목, 허용된 디렉터리 밖을 가리키는 이름, 항목 개수와 압축을 푼 뒤의 총량도 확인한다. 압축 파일 크기만으로 풀린 크기를 판단할 수 없으므로 실제로 읽는 양도 제한해야 한다. [PKWARE ZIP APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)

## 선택에 필요한 확인

### 데스크톱 ZIP 처리 시간

2026-11-13에 메모리 32 GiB인 Apple Silicon Mac의 Chromium 156에서 브라우저용 ZIP 쓰기와 읽기 모듈을 각 조건에서 3회 실행했다. 조건마다 무작위 픽셀로 만든 JPEG 하나를 여러 원본 항목에 사용했다. 아래 시간은 중앙값이다. 압축 해제 후 총량은 원본 합계에 매니페스트 크기를 더한 값이다.

- 1,920×1,080 이미지 3장, ZIP 항목 4개, 원본 합계 5.14 MB, ZIP 5.14 MB. 쓰기 16 ms, 읽기 70 ms.
- 3,000×2,000 이미지 12장, ZIP 항목 13개, 원본 합계 59.39 MB, ZIP 59.39 MB. 쓰기 113 ms, 읽기 666 ms.
- 4,000×3,000 이미지 24장, ZIP 항목 25개, 원본 합계 237.49 MB, ZIP 237.50 MB. 쓰기 369 ms, 읽기 2,673 ms.

읽기 시간에는 원본 추출과 이미지 디코딩 검증이 포함된다. 측정 구간에서 50 ms 이상의 Long Task는 관측되지 않았다. 실제 조작 지연, 메모리 최고 사용량, 미리보기, IndexedDB 저장과 편집 화면 표시까지 걸린 시간은 측정 대상에서 제외했다. 이 수치는 데스크톱 모듈의 비교 자료로 사용한다.

### 데스크톱 화면에서 저장과 불러오기

같은 Mac의 Chromium 156에서 각 작업량을 한 번 실행했다. 테스트용 JPEG를 사용하고 저장된 이미지의 배치 너비는 원본의 8분의 1로 지정했다. 다운로드 버튼 클릭부터 파일 기록 완료까지, 파일 입력부터 대표 이미지 디코딩 완료까지, 확인 버튼 클릭부터 새 캔버스에 이미지 픽셀이 표시될 때까지의 시간을 각각 측정했다.

- 1,920×1,080 이미지 3장, ZIP 5.14 MB. 다운로드 147 ms, 미리보기 209 ms, 편집 재개 138 ms.
- 3,000×2,000 이미지 12장, ZIP 59.40 MB. 다운로드 840 ms, 미리보기 807 ms, 편집 재개 662 ms.
- 4,000×3,000 이미지 24장, ZIP 237.50 MB. 다운로드 4,976 ms, 미리보기 2,817 ms, 편집 재개 2,295 ms.

이번 시간에는 브라우저 자동화의 클릭과 파일 입력 및 대기 시간도 포함된다. 편집 재개는 캔버스의 첫 이미지 픽셀을 기준으로 삼았다.

### 데스크톱 프레임 간격과 메모리 표본

동일한 작업량으로 한 번 더 실행했다. 다운로드와 미리보기 각각에서 연속한 `requestAnimationFrame` 콜백의 최대 간격을 기록했다. 다운로드 시작 직전과 전체 실행 중 약 100 ms 간격으로 Chromium 프로세스들의 RSS 합계를 읽었다.

- 이미지 3장, ZIP 5.14 MB. 다운로드와 미리보기 최대 프레임 간격은 각각 17 ms와 17 ms였다. RSS 합계는 시작 457 MiB, 최대 표본 619 MiB였다.
- 이미지 12장, ZIP 59.40 MB. 최대 프레임 간격은 17 ms와 17 ms였다. RSS 합계는 시작 797 MiB, 최대 표본 1,701 MiB였다.
- 이미지 24장, ZIP 237.50 MB. 최대 프레임 간격은 2,167 ms와 17 ms였다. RSS 합계는 시작 1,942 MiB, 최대 표본 2,616 MiB였다.

프레임 간격은 화면 갱신의 공백을 보여준다. 포인터 입력부터 화면 반영까지 걸린 시간은 측정하지 않았다. RSS는 프로세스들의 공유 메모리를 중복 합산할 수 있고, 표본 사이의 최고값은 놓칠 수 있다. 같은 브라우저에서 작업량을 순서대로 늘렸으므로 조건별 시작값에는 이전 작업의 영향이 남을 수 있다. 모바일 실기기에서 이 값을 재현하는지는 아직 확인하지 않았다.

### 데스크톱 포인터 이벤트 전달 시간

다운로드 및 미리보기 중 브라우저 자동화로 포인터 이동을 보내고, 이벤트 생성 시각부터 페이지가 이벤트를 받은 시각까지 기록했다. 조건별 한 번을 실행했으며 자동화가 포인터 이동을 보낼 수 있는 시점에만 표본을 얻었다.

- 5.14 MB. 다운로드 중 표본 0건, 미리보기 중 2건의 최대값 18 ms.
- 59.40 MB. 다운로드 중 4건의 최대값 431 ms, 미리보기 중 12건의 최대값 17 ms.
- 237.50 MB. 다운로드 중 12건의 최대값 2,106 ms, 미리보기 중 49건의 최대값 27 ms.

가장 큰 파일의 다운로드 중 이전에 관측한 프레임 공백과 비슷한 길이의 이벤트 전달 지연이 나타났다. 이 값은 이벤트 처리와 다음 화면 표시까지의 지연을 포함하지 않는다. CPU 제한을 적용한 반복 측정 방법은 [실행 계획](../plan.md#편집용-zip-저장과-불러오기)에 있다. [DOM 이벤트 시각 정의](https://dom.spec.whatwg.org/#dom-event-timestamp), [Event Timing 명세](https://w3c.github.io/event-timing/)

### ZIP 생성 Worker 적용 후

같은 데스크톱에서 4,000×3,000 이미지 24장을 한 번 더 저장했다. ZIP 크기는 237.50 MB였다. 다운로드 완료까지 2,852 ms가 걸렸고 다운로드 중 최대 프레임 간격은 2,133 ms였다. ZIP 생성은 Worker에서 실행되지만, 다운로드를 포함한 화면 공백은 여전히 관측됐다. 이 실행에서는 저장소 조회, Worker 메시지와 브라우저 다운로드에 걸린 시간을 따로 측정하지 않았다.

### ZIP 저장 단계별 프레임 간격

같은 데스크톱과 237.50 MB 조건에서 편집 화면을 연 뒤 IndexedDB 조회, ZIP 생성 Worker 호출, 브라우저 다운로드를 각각 실행했다. 조회는 두 번 모두 13~14 ms에 끝났으며 최대 프레임 간격은 17 ms였다. Worker 응답은 442~443 ms였으며 최대 간격은 18~19 ms였다. 두 번째 실행에서 별도로 시작한 다운로드의 최대 간격은 17 ms였다.

이 측정에서는 저장 버튼을 통한 전체 실행에서 관측한 약 2.13초의 공백을 재현하지 못했다. 각 단계의 시작점을 나눠 관측한 결과이므로 공백의 원인을 특정할 수 없다. 모바일 실기기 측정에서도 모듈 호출과 사용자 조작 전체를 구분한다.

### CPU 제한 예비 측정

데스크톱 Chromium 156에서 DevTools 소스의 벤치마크와 목표 점수를 사용해 중급 조건 3.29배, 저사양 조건 12.1배를 산출했다. 배율은 Chrome DevTools Protocol로 적용했다. DevTools 화면에서 실행하는 보정 절차와 구분한다. [Chromium CPU 보정 소스](https://chromium.googlesource.com/devtools/devtools-frontend/+/HEAD/front_end/panels/mobile_throttling/CalibrationController.ts)

세 작업량을 CPU 제한 없음, 3.29배, 12.1배로 두 번씩 실행했다. 다음은 저사양 조건의 다운로드, 미리보기, 편집 재개 시간이다.

- 5.14 MB는 다운로드 0.89~1.60초, 미리보기 0.55~0.56초, 편집 재개 0.86~0.89초였다.
- 59.40 MB는 다운로드 14.94~15.00초, 미리보기 2.65~2.73초, 편집 재개 7.66~7.69초였다.
- 237.50 MB는 다운로드 31.84~59.96초, 미리보기 7.85~8.22초, 편집 재개 2.77~29.58초였다.

프레임을 기록한 실행에서 저사양 조건의 다운로드 중 최대 간격은 작업량 순서대로 617 ms, 7,150 ms, 28,316 ms였다. 두 브라우저 실행이 일부 겹쳤고 가장 큰 작업은 편집 재개 시간 편차도 컸다. 예비 결과는 병목 후보를 확인하는 데 사용한다. 한도 산정에는 순차 재측정과 입력 지연 및 메모리 표본이 필요하다.

### CPU 제한 순차 재측정

Chromium 156 한 세션에서 동일한 세 작업량을 CPU 제한 없음, 3.29배, 12.1배 조건으로 각각 두 번씩 실행했다. 저사양 조건의 관측 범위는 다음과 같다.

- ZIP 5.14 MB는 다운로드 0.77~0.89초, 미리보기 0.57~0.58초, 편집 재개 0.84초였다. 다운로드 중 최대 프레임 간격은 567~583 ms였다.
- ZIP 59.40 MB는 다운로드 7.47~7.79초, 미리보기 2.24~2.34초, 편집 재개 7.50초였다. 다운로드 중 최대 프레임 간격은 6.88~6.93초였다.
- ZIP 237.50 MB는 다운로드 29.80~30.40초, 미리보기 7.58~7.73초, 편집 재개 2.44~28.62초였다. 다운로드 중 최대 프레임 간격은 27.27~27.28초였다.

약 150 ms 간격으로 Chromium 프로세스의 RSS 합계를 표본으로 기록했다. 저사양 조건의 최대 표본은 작업량 순서대로 1,208 MiB, 2,392 MiB, 5,315 MiB였다. 한 세션에서 작업을 반복해 시작 메모리가 달랐고 공유 메모리가 중복 집계될 수 있다. 이 값으로 파일별 메모리 상한을 판단할 수 없다. 이번 실행에서는 JS 힙과 포인터 입력 지연을 따로 측정하지 않았다.

### 저사양 CPU 조건의 소용량 ZIP 측정

Chromium 156에서 CPU 제한 12.1배를 적용하고 각 작업량을 두 번 실행했다. 매 실행에 새 브라우저 컨텍스트를 사용했다. 포인터 이동의 생성 시각부터 페이지 수신까지의 지연을 다운로드 중 실행당 세 건 기록했다. 다운로드부터 편집 재개까지 페이지 대상의 JS 힙을 표본으로 읽었다.

- 1,280×720 이미지 1장, ZIP 약 0.76 MB. 다운로드 420~537 ms, 미리보기 546~549 ms, 편집 재개 276~301 ms. 최대 입력 전달 지연 37~40 ms, 최대 JS 힙 표본 27.66~27.80 MB.
- 1,600×900 이미지 2장, ZIP 약 2.39 MB. 다운로드 863~1,017 ms, 미리보기 629~633 ms, 편집 재개 501~507 ms. 최대 입력 전달 지연 197~214 ms, 최대 JS 힙 표본 25.07~25.40 MB.
- 1,920×1,080 이미지 3장, ZIP 약 5.14 MB. 다운로드 1,533~1,541 ms, 미리보기 675~678 ms, 편집 재개 834~847 ms. 최대 입력 전달 지연 531~571 ms, 최대 JS 힙 표본 21.38~22.25 MB.

이미지 수, 해상도와 파일 용량이 함께 달라졌으므로 어느 변수 하나의 영향으로 해석할 수 없다. 입력 표본에는 다음 화면 표시까지의 시간이 빠져 있다. JS 힙은 이미지 디코딩 버퍼와 Worker를 포함한 전체 메모리를 나타내지 않는다.

### 저장 클릭과 프레임 공백의 시점 비교

저사양 CPU 조건 12.1배에서 5.14 MB 작업을 두 번 실행했다. 클릭 이벤트가 페이지에 전달된 시각, Worker에 문서를 보내는 호출, Worker 응답과 다운로드 요청에 각각 시각을 기록했다.

두 실행 모두 약 600 ms의 프레임 공백이 클릭 이벤트가 페이지에 전달되기 전에 끝났다. 클릭 이벤트 전달 후 다운로드 요청까지는 각각 135 ms와 91 ms였다. Worker에 문서를 보내는 호출, Worker 종료와 다운로드 요청 호출의 시작과 끝은 각 실행에서 같은 밀리초로 기록됐다.

이 두 실행에서 가장 긴 공백은 클릭 처리나 ZIP 생성 중에 발생하지 않았다. 앞서 자동화 클릭 명령부터 계산한 시간에는 앱이 클릭을 받기 전 대기도 들어 있다. 초기 한도를 정할 때는 편집 화면이 안정된 뒤 클릭하고, 이벤트 전달 시각부터 다운로드 완료까지의 구간을 확인한다. 클릭 전 공백의 원인은 아직 확인하지 않았다.

### 남은 확인

- 예상하는 이미지 수와 용량을 기준으로 대상 기기에서 두 후보의 파일 크기, 저장과 불러오기 시간, 최대 메모리 사용량을 비교한다. 수치는 아직 측정하지 않았다.
- 다른 기기에서 파일을 열었을 때 원본 이미지의 바이트, 이미지와 메모의 위치 및 부착 관계가 유지되는지 확인한다. 손상된 파일이나 이미지가 빠진 파일을 열 때 현재 작업이 보존되는지도 확인한다.
- 형식을 확정하기 전에 읽을 이전 버전과 허용할 이미지 종류 및 작업량을 정한다. 이미지와 객체의 편집 상태를 복원하는 데 필요한 정보는 저장 대상이다. 확대율, 화면 위치와 실행 취소 이력까지 옮길지는 별도 선택이다.
