# 이미지 편집 후 프레임 공백

원본 식별자가 같을 때 디코딩한 이미지를 재사용하자, 이미지 너비와 위치를 저장한 뒤 발생하던 프레임 공백이 줄었다. 변경 커밋은 `030051f`다.

## 문제와 원인

Chromium에서 1080p 이미지 10장을 배치한 뒤 너비를 입력해 저장하거나 이미지를 끌어 위치를 저장하면 프레임 콜백 사이에 1초가 넘는 공백이 생겼다. 두 동작 모두 배치 정보만 수정하지만 저장 뒤 문서를 다시 조회한다. IndexedDB는 원본 Blob을 새 자바스크립트 객체로 반환할 수 있다. 기존 화면은 Blob 참조가 달라질 때마다 기존 이미지를 표시 목록에서 제외하고 객체 URL과 이미지 요소를 다시 만들었다. 원본 바이트가 그대로인 편집에도 이 과정이 반복됐다. [IndexedDB 값 복제](https://w3c.github.io/IndexedDB/#clone-a-value)

## 선택한 방법과 대안

원본 식별자를 이미지 로딩의 기준으로 삼았다. 같은 식별자로 다시 조회하면 이미 디코딩한 이미지를 사용하고, 다른 원본으로 바뀌면 새로 로드한다. 저장 코드에서는 원본을 추가할 때 새 식별자를 부여하므로 배치 저장과 이미지 로딩을 분리할 수 있다. `useEffectEvent`는 로딩을 시작할 때 최신 Blob을 읽는 데 사용한다. [이미지 표시 코드](../../../../apps/canvas/src/pages/editor/ui/canvas-asset.tsx) [React Effect Event](https://react.dev/reference/react/useEffectEvent)

아래 대안은 변경 내용을 설명하기 위해 사후에 비교했다. 각각의 성능은 측정하지 않았다.

- **메모와 배치만 다시 읽기.** 원본 레코드를 조회하는 비용까지 줄일 수 있다. 원본 추가와 삭제, 다른 탭에서 발생한 변경을 감지하고 필요한 데이터만 다시 읽는 절차가 추가된다. 원본 디코딩을 없앤 뒤에도 IndexedDB 조회가 병목으로 남으면 검토할 수 있다.
- **공용 디코딩 캐시 사용.** 여러 화면에서 같은 원본을 쓸 때도 디코딩을 공유할 수 있다. 프로젝트를 닫거나 원본을 삭제했을 때 해제하는 규칙과 메모리 상한이 필요하다. 이번 문제는 편집 화면이 열린 동안 발생했으므로 해당 화면에서 이미지를 재사용하는 것으로 해결했다.
- **Blob의 바이트나 해시 비교.** 식별자를 유지한 채 원본을 바꾸는 구조에서도 내용 변경을 감지할 수 있다. 현재 저장 구조에서는 원본 식별자가 내용을 구분한다. 매번 바이트를 읽거나 해시를 계산하면 대형 이미지에서 별도의 비용이 생긴다.

## 전후 측정

Chromium 156, 1,440×900 화면, 픽셀 비율 1, CPU 12.1배 제한에서 1080p 이미지 10장으로 측정했다. 변경 전과 후에 각각 한 번씩 실행했다.

- 너비 입력 후 저장 구간의 최대 프레임 콜백 간격은 **약 1,200ms에서 16.7ms**로 줄었다.
- 이미지 드래그와 위치 저장 구간의 최대 프레임 콜백 간격은 **약 1,417ms에서 33.4ms**로 줄었다.
- 변경 후 너비와 위치가 IndexedDB에 저장됐고, 편집 중 원본용 객체 URL은 처음 생성한 10개에서 늘지 않았다.

프레임 콜백 사이의 간격을 비교한 결과다. 실제 화면에 픽셀이 표시된 시각은 측정하지 않았다. [Chrome DevTools 프레임 검사](https://developer.chrome.com/docs/devtools/performance/reference)
