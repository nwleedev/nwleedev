# 개인 메모 앱의 Independent Work 소개 가치

`apps/notes`는 Independent Work의 소개 후보로 유지한다. 텍스트 선택, 순서 편집과 복사를 연결한 작업 흐름, 저장 자료 보존과 실제 입력 오류의 해결은 프론트엔드 역량을 보여줄 근거다. 다만 프로젝트를 만든 실제 불편과 개인이 직접 판단한 부분을 확인한 뒤 추가할 것을 권고한다. 저장 버그 수정만으로 추가를 확정하지 않는다.

이 문서는 [선정 요구사항](../requirements.md)에 따라 개발자 소개 사이트에 실을 내용을 판단하는 근거다. 2026년 10월 2일 확인한 저장소 근거는 `a06bfc94c64232581742792a9834b82f5963f225`의 앱 상태와 그 이전의 Git 기록이다. [커밋별 평가](commit-assessment.md)는 현재 이력의 18개 커밋을, [합친 이력](squashed-history.md)은 중복을 제외한 관련 변경 175개를 각각 판단한다. 실행 근거는 같은 날 기존 평가에서 확인한 로컬 운영 빌드와 선택한 브라우저 검사이며 개별 커밋마다 재실행한 결과는 아니다. 항목 추가와 소개 문구는 제안이다.

## apps/entry의 역할과 개발 의도

`apps/entry`는 회사 경력을 중심으로 개발자의 판단과 성과를 전달하는 한국어 및 영어 한 페이지 소개 사이트다. 저장소 전체가 여러 미니 애플리케이션으로 프론트엔드 역량을 보여주려는 목적을 갖지만, entry의 첫 화면은 모든 앱을 나열하거나 실행하는 역할을 맡지 않는다. [사이트 요구사항의 역할과 정보 순서](../../developer-portfolio-f4b7/requirements.md)와 [현재 홈페이지](../../../../apps/entry/src/_pages/home/ui/HomePage.astro)에서 이 구분을 확인할 수 있다.

현재 소개는 서비스 문제의 원인을 찾고 사용자가 정확한 정보와 작업 상태를 확인하도록 개선하는 개발자를 보여준다. Experience 다음에 Open Source와 Independent Work를 배치해 회사 밖에서의 작업을 보충한다. Independent Work는 제목, 기간, 설명, 선택적인 링크와 기술 정보를 표시한다. 별도 프로젝트 격자를 만드는 구조는 아니다. 근거는 [한국어 소개 내용](../../../../apps/entry/src/shared/terms/ko.json)과 [Independent Work 구성](../../../../apps/entry/src/_pages/home/ui/IndependentWorkSection.astro)이다.

현재 두 항목은 AI Agent Workflow와 Offline Translation Web App이다. 전자는 저장소 규칙과 문구 검사, 후자는 네트워크 연결 없이 번역하는 브라우저 앱 경험을 설명한다. [첫 버전의 독립 작업 선정](../../developer-portfolio-f4b7/decisions/project-availability.md)은 새로운 항목이 기존 두 작업과 다른 판단 또는 확인 가능한 결과를 보태야 한다고 정한다.

같은 선정 기록에서 메모 앱은 개발 중인 목적과 기능만 확인돼 경력 중심 구성에서 우선순위가 낮았다. 이는 메모 앱을 계속 제외해야 한다는 결정은 아니다. 현재 확인되는 저장 문제의 발견과 수정 결과는 당시의 기능 설명보다 구체적인 선정 근거가 된다.

## 메모 앱의 확인 가능한 목적

메모 앱은 텍스트를 작성하고 보관한 뒤, 필요한 메모를 순서대로 모아 복사하고 템플릿으로 재사용하는 로컬 도구다. 데스크톱에서는 메모를 공간에 배치하고 바로 편집하며, 모바일에서는 목록에서 메모를 고르고 상세 화면에서 저장한다. [메모 앱 요구사항의 의도한 결과](../../personal-notes-app-8fd/requirements.md#의도한-결과)를 종합한 설명이다.

`apps/notes`는 이 저장소 안의 독립 실행 앱이며 별도의 Git 저장소는 아니다. 현재 범위는 계정과 서버 동기화를 포함하지 않는다. 로컬 저장과 LLM 없이 실행하는 텍스트 분석은 확인되지만, 웹앱 전체를 네트워크 없이 처음부터 열 수 있다는 의미의 오프라인 앱으로 소개할 근거는 없다. [현재 범위와 실행 조건](../../personal-notes-app-8fd/requirements.md#반드시-지킬-조건)은 브라우저의 로컬 처리와 웹앱을 제공하는 서버를 구분한다.

## 앞에 둘 성과와 기여

### 텍스트 재사용 과업을 화면과 저장 규칙으로 연결

개인 앱의 목적을 설명할 첫 후보는 여러 메모에서 고른 텍스트를 조합해 다시 사용하는 흐름이다. 넓은 화면에서는 원문 메모와 작업 사본을 나란히 확인하고, 모바일에서는 선택 및 순서 편집과 복사를 이어간다. 작업 사본의 편집은 원본 메모를 바꾸지 않는다. 반복 텍스트는 달라지는 부분을 입력하는 템플릿으로 사용할 수 있다.

근거는 [커밋별 평가의 텍스트 재사용](commit-assessment.md#텍스트를-보관한-뒤-조합하고-다시-사용하는-흐름)이다. 기존 도구에서 어떤 조작이 불편했고 이 흐름을 선택해 무엇이 달라졌는지 확인하면 프로덕트 판단을 설명할 수 있다. 현재는 기능과 설계 이유가 확인되며 실제 이용의 목적과 효과는 미확인이다.

### 모바일 저장 누락과 저장 전 원문 변경 해결

이 항목은 가장 구체적인 기술적 결과다. 첫 번째 저장 후 다른 원문을 입력해 다시 저장하면 화면의 내용과 저장소의 내용이 달라지는 결함이 발견됐고 수정됐다. 또 복구 초안을 가진 모바일 목록에서 상세 화면으로 이동하면 저장 버튼을 누르기 전에 원문이 바뀌던 결함도 수정됐다. 두 사례는 사용자의 저장 의도가 실제 자료에도 반영되는지 확인한 결과다.

발견 당시의 행동과 수정 결과는 [메모 앱 플랜의 모바일 명시적 저장과 이탈](../../personal-notes-app-8fd/plan.md#모바일-명시적-저장과-이탈)에 기록되어 있다. 현재의 [상세 편집 처리](../../../../apps/notes/src/_pages/notes/model/use-note-detail-editing.ts)와 [화면 선택](../../../../apps/notes/src/_pages/notes/ui/notes-collection.tsx), [실제 화면의 저장 검사](../../../../apps/notes/e2e/notes.spec.ts)가 그 결과를 뒷받침한다. 최초 수정은 `7291f47`이며 [bb14d8d](https://github.com/nwleedev/nwleedev/commit/bb14d8d)에 합쳐져 있다. [41c3dd0](https://github.com/nwleedev/nwleedev/commit/41c3dd0)은 이후 복구와 저장 자료 확인을 보강한 기록이다.

회사의 인증 및 주요 절차 E2E 경험과 검사 도구 사용은 겹친다. 메모 앱이 보태는 내용은 브라우저에 저장한 원문, 복구 초안과 화면 전환이 함께 동작할 때 생긴 실제 결함을 해결한 사례다. 입력한 원문이 의도대로 저장되는지 확인한 사례로 설명하면 기존 소개를 보충한다.

### 복구 초안과 정리 실패 후 재시도

저장 실패와 초안 정리 실패를 구분한 동작은 두 번째 근거로 쓸 수 있다. 메모 저장에 실패하면 초안을 남기고, 메모 저장은 성공했지만 초안 제거만 실패하면 저장된 원문을 유지하면서 다음 저장에서 정리를 다시 시도한다. 사용자가 다시 편집하거나 저장할 수 있는 상태를 남기는 판단이 중요하다.

근거는 [초안 제거 재시도 결정](../../personal-notes-app-8fd/decisions/note-draft-cleanup-retry.md), [초안 복구와 제거 재시도의 확인 범위](../../personal-notes-app-8fd/plan.md#초안-복구와-제거-재시도), [현재 저장 처리](../../../../apps/notes/src/_pages/notes/model/save-note-content.ts)다. 저장 실패 후 화면을 다시 열어 복구한 기록은 저장 동작의 실패를 주입한 Browser Mode 검사다. 아래의 이번 E2E 실행 결과와는 구분한다.

### 화면과 입력 방식에 맞는 메모 작업

화면별 배치만이 아니라 실제 입력 충돌의 해결을 설명할 수 있다. 포인터를 놓아도 캔버스가 움직이던 문제, 먼 좌표의 메모가 화면에서 겹치던 문제와 생성 버튼이 크기 조절 지점을 가리던 문제는 각각 전후 차이가 있다. 포인터, 키보드와 메뉴로 순서를 바꾸면서 원문, 항목 ID와 포커스를 유지한 결과도 확인된다. 근거는 [커밋별 평가의 입력 방식](commit-assessment.md#여러-입력-방식이-같은-작업-결과를-내도록-조정)이다. 모바일 대응 자체나 접근성 표준 전체 준수를 대표 성과로 삼지는 않는다.

### 분석과 구조 개선의 위치

텍스트 분석은 같은 줄, 포함 관계와 문자열 조각의 겹침을 브라우저에서 비교하는 기능이다. 의미를 이해하는 AI 분석으로 설명하면 실제 기능과 달라진다. [분석 처리](../../../../apps/notes/src/_pages/analysis/model/analyze-text.ts)와 [분석 Worker 연결](../../../../apps/notes/src/_pages/analysis/api/worker-text-analyzer.ts)은 외부 LLM 없이 분석하고, 분석 도중 다른 화면으로 이동하는 조건을 설명할 근거다.

Worker와 IndexedDB 사용 자체는 번역 앱과 회사의 브라우저 처리 경험에 이미 등장한다. 이 앱의 분석에서 설명할 내용은 잘못된 원문이나 오래된 요청의 결과를 보여주지 않는 조건이다. 기능별 외부 동작을 분리한 구조 정리는 유지보수 판단을 설명하는 면접 자료로 남기는 편이 적합하다. [구조 개선의 비교 기록](../../notes-architecture-refactor-4d8c/plan.md)은 같은 자료의 표시 시간, DOM 수와 메모리를 세 번 비교했지만 성능 개선을 입증하지 않는다. 렌더 횟수와 실제 변경 비용의 감소도 확인되지 않았다.

## 현재 실행으로 확인한 결과

운영 빌드 후 기존 사용자 시나리오 다섯 개를 Chromium, Firefox와 WebKit에서 실행해 15개 실행이 모두 통과했다.

- 모바일 상세 화면에서 연속 입력 및 저장과 이탈 선택을 조합하는 동작.
- 복구 초안이 있는 목록에서 상세 화면을 열어도 저장 전 원문을 유지하는 동작.
- 복구 초안을 저장하고 초안 제거 실패를 다음 저장에서 정리하는 동작.
- 명시적으로 분석을 요청한 뒤 실제 Worker 자산을 실행해 분석 후보를 표시하는 동작.
- 분석 요청 직후 메모 화면으로 이동하는 동작.

근거 파일은 [메모 화면 E2E](../../../../apps/notes/e2e/notes.spec.ts), [분석 화면 E2E](../../../../apps/notes/e2e/analysis.spec.ts)와 [브라우저 실행 설정](../../../../apps/notes/playwright.config.ts)이다. 저장 및 복구 과업은 화면 입력과 실제 IndexedDB의 원문을 비교한다. 초안 제거 실패는 검사에서 의도적으로 만든 조건이다. 이전 기록에서 저장 버튼 연결을 일부러 제거해 탐지 능력을 확인한 사례도 실제 앱에서 발견한 두 결함과 구분한다.

이는 로컬 운영 빌드에서 해당 동작을 확인한 결과다. 전체 E2E, 실제 모바일 기기, 운영 중 장애와 CI의 결과를 뜻하지 않는다. 과거 플랜의 전체 검사 건수는 당시 결과이므로 현재 통과 건수나 대표 성과 수치로 옮기지 않는다.

## Independent Work에 실을 문구 제안

짧은 소개에는 텍스트 재사용 과업과 저장 의도를 지킨 결과를 연결한다. 앱 기능과 수정 결과에 근거한 아래 초안은 개인이 맡은 부분을 확인한 뒤 선택할 제안이다. 실제 불편과 이용 결과가 확인되면 그 내용을 먼저 쓴다. [채용과 경험 서술 기준](hiring-and-writing.md#이-프로젝트에-적용할-서술-기준)에 따라 내부 처리 순서는 소개 문구에서 설명하지 않는다.

- 제목: `Personal Notes Workspace`
- 기간: `2026`
- 기술 정보: `TypeScript`, `React`, `Next.js`, `IndexedDB`
- 링크: [메모 앱 소스](https://github.com/nwleedev/nwleedev/tree/a06bfc94c64232581742792a9834b82f5963f225/apps/notes). 실행 서비스 주소가 아니라 검토한 소스 버전이다.

한국어 설명 제안:

> 여러 메모의 텍스트를 골라 순서를 편집하고 한 번에 복사하는 작업을 연결했습니다. 모바일 연속 저장 누락과 저장 전 원문 변경을 해결하고, 원문과 편집 초안을 구분해 복구할 수 있도록 했습니다.

영어 설명 제안:

> Built a workflow for selecting text from multiple notes, arranging it, and copying it together. Fixed mobile editing issues that skipped consecutive saves or changed stored content before an explicit save, while keeping stored content separate from recoverable drafts.

이력서에서는 직접 맡은 내용과 확인할 수 있는 결과를 선택한다. 아래 후보를 모두 나열하기보다 목적과 가장 잘 이어지는 내용을 남긴다.

- 여러 메모의 텍스트 선택, 순서 편집과 복사를 연결하고 작업 사본 편집이 원본 메모를 바꾸지 않도록 구성. 넓은 화면에서 원문과 작업 사본을 함께 확인하고 모바일에서 선택과 확인 단계를 이어가는 흐름 제공.
- 모바일에서 서로 다른 원문을 연속 저장할 때 두 번째 입력이 저장되지 않던 문제와, 상세 화면 이동만으로 복구 초안이 원문에 반영되던 문제를 수정. 실제 화면과 저장소의 원문을 비교하는 시나리오를 브라우저 3종에서 확인.
- 메모 저장 성공 후 초안 제거만 실패하는 상황에서 원문을 유지하고 다음 저장으로 정리를 재시도하는 동작 제공. 저장 실패 후 복구는 실패를 주입한 브라우저 검사에서 확인.
- 저장 형식 변경에서 기존 텍스트 순서, 사용 기록과 설정을 이전. 실제 저장소 연결을 다시 열어 이전 자료의 내용을 확인하는 검사 제공. 운영 중 이용자 자료를 이전한 성과와는 구분.

검토한 코드와 Git 기록은 변경 내용을 뒷받침하지만 개인의 기여율, 단독 작성 여부나 팀을 이끈 역할까지 입증하지는 않는다. 소개 문구에 그런 역할을 추가하려면 별도 사실이 필요하다.

## 추가 여부를 결정하는 기준

현재 근거로는 기술적 결과가 있는 소개 후보이며, 실제 사용 목적과 개인의 판단을 확인한 뒤 추가하는 편이 적합하다. 기존 두 항목은 작업 규칙과 오프라인 번역을 설명한다. 메모 앱은 텍스트 재사용 과업을 구체화하고 저장, 복구와 입력 충돌을 해결한 내용을 보탠다.

경력 프론트엔드 사례로는 연속 입력, 비동기 완료와 저장 자료의 일관성을 판단한 근거가 있다. 프로덕트 엔지니어 사례로 더 설득력을 갖추려면 왜 이 과업이 필요했는지, 어떤 대안을 직접 선택했고 실제로 무엇이 달라졌는지가 필요하다. 코드의 양, 검사 건수와 사용하는 기술 이름만으로 두 역량을 대신 설명하지 않는다.

다만 사용자 증가, 작업 시간 절감, 처리 속도 개선과 장애 감소율은 확인되지 않았다. 데이터 유실을 완전히 방지했다거나 앱 전체를 오프라인으로 쓸 수 있다는 주장도 제외한다. 이런 수치나 기능을 만들어내야만 항목이 성립하는 것은 아니다.

직접 판단한 부분을 확인하지 못하거나 기능 목록만 남길 경우에는 추가를 보류한다. 실제 이용자 수가 없어도 확인 가능한 문제, 판단과 전후 결과를 설명할 수 있으면 추가할 가치가 있다. 확인할 사실은 [커밋 평가의 선정 판단](commit-assessment.md#선정-판단과-확인할-사실), 반영 제안은 [후속 적용 플랜](../plan.md#항목-추가를-선택할-때의-후속-적용안)에 있다.
