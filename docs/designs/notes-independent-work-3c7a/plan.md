# 개인 메모 앱의 소개 가치 평가 플랜

반복 지침과 명령어 관리의 불편을 직접 정의하고 일괄 복사와 템플릿을 선택한 기여를 근거로 Independent Work 추가를 권고한다. 개별 커밋의 입력 및 저장 문제 해결을 그 목적에 연결한다. 항목 등록과 애플리케이션 변경은 포함하지 않는다.

기준은 [요구사항의 필요한 결과와 완료 자료](requirements.md)다. 이후 화면을 변경하게 되면 [개발 지침](../../dev/README.md)과 [Astro 구현 지침](../../dev/frontend/astro-fsd-tailwind.md)을 적용한다.

## 평가 절차

1. 사이트의 역할과 선정 기준을 확인한다. `apps/entry`의 현재 소개와 설계 기록, `apps/notes`의 요구사항, 코드와 Git 기록을 대조해 `references/assessment.md`에 근거를 정리한다. 기능의 존재, 실행 결과와 이용자 성과를 구분할 수 있으면 완료다.
2. 경력 채용과 경험 서술 기준을 조사한다. 국내 기업의 프론트엔드 채용공고와 이력서 작성 자료를 비교해 `references/hiring-and-writing.md`에 적용할 기준을 정리한다. 각 기준에 직접 연결되는 출처와 자료의 적용 범위를 확인한다.
3. 성과 후보를 평가하고 문구를 제안한다. 목적, 해결한 문제, 확인된 결과와 기존 소개에 보태는 역량을 기준으로 `references/assessment.md`를 완성한다. 근거 없는 수치와 역할을 제외한 문구, 추가 권고 또는 보류 이유와 후속 조건이 있으면 완료다.

평가 절차는 문서 작성 단위이며 테스트 코드나 TDD를 적용하지 않는다. 기존 문서와 코드는 평가 자료로만 사용한다.

## 개별 커밋 평가

1. 앱을 바꾼 커밋과 합쳐진 개별 변경을 확인한다. 반복된 기록을 제외하고 현재 이력의 전후 차이와 근거를 `references/commit-assessment.md`에, 합치기 전의 개별 변경 판단을 `references/squashed-history.md`에 기록한다. 단순한 작업 목록 대신 이력서에서 사용할 가치와 이유를 각각 판단하면 완료다.
2. 성과 후보를 비교한다. 실제 사용 목적과 개인이 판단한 부분을 확인하고, 채용 조사와 기존 Independent Work에 보태는 역량을 기준으로 `references/assessment.md`를 수정한다. 이용 성과와 개인 기여는 확인된 사실만 사용한다.
3. 평가 문서와 소개 제안을 맞춘다. 기능의 존재, 실제 결함 수정, 검사에서 의도적으로 만든 실패와 이용 결과를 구분한다. 새로운 평가가 기존 소개안 및 `references/hiring-and-writing.md`와 모순되지 않으면 완료다.

이 단계는 기존 워크트리에서 문서만 변경한다. 요구사항과 플랜을 갱신하고 커밋별 참고 문서 두 개를 추가하며, 결론에 영향을 받는 두 참고 문서를 수정한다. 앱 코드와 테스트 코드는 변경하지 않는다. 커밋과 자료의 평가는 계속하되, 개인의 주도 역할이나 이용 성과가 필요한 서술은 사실을 확인한 뒤 정한다.

### 개별 평가의 상태

- 커밋과 전후 결과: 완료. 현재 이력의 18개와 합친 기록에서 중복을 제외한 175개에 개별 판단이 있다. 모바일 최초 수정의 근거는 `bb14d8d`에 포함된 `7291f47`로 바로잡고, 이후 바뀐 모바일 선택 복구와 위치 교환은 현재 기능에서 제외했다.
- 성과 후보 비교: 완료. 반복 지침 및 명령어 관리의 목적과 일괄 선택, 템플릿, 모바일 대안 및 저장소 선택의 직접 판단을 확인했다. 기술적 결과와 개별 코드 작성 또는 오류 분석 역할은 구분한다.
- 종합 평가와 소개 제안: 추가 권고. 확인된 목적과 직접 정한 기여를 앞에 둔 초안을 제안한다. 사이트에 반영할 문구와 항목 추가는 별도 선택이다.

## 사용 목적과 드래그 사례의 연결

1. 사용 경험과 직접 선택한 사항을 정리한다. `references/workflow-and-input.md`에 반복 지침 및 명령어 메모의 불편, 일괄 복사와 템플릿의 목적을 기록한다. 회고로 확인한 판단과 코드로 확인한 동작이 구분되면 완료다.
2. 드래그 문제를 현재 동작과 연결한다. 같은 문서에 시점 되돌림, 정상 WebKit 입력의 중단과 종료 뒤 계속 이동한 문제의 원인 및 전후 결과를 정리한다. 각각의 변경과 현재 앱의 근거가 있으며 구현 순서를 자세히 설명하지 않으면 완료다.
3. 선정 판단과 소개안을 맞춘다. `references/assessment.md`, `references/commit-assessment.md`와 `references/hiring-and-writing.md`를 수정해 목적 및 직접 정한 기여를 먼저 쓴다. 개별 수정의 미확인 역할과 측정하지 않은 성과가 소개안에 없으면 완료다.

세 단위는 완료됐다. 사용 목적과 직접 정한 기여, 드래그 변경 및 현재 동작의 근거, 그 내용을 앞에 둔 소개 제안이 각 문서에 있다. 문서 작성이므로 TDD를 적용하지 않는다. 생성할 파일은 사용 목적과 입력 문제의 참고 문서 하나이며, 나머지 네 문서는 수정한다. 앱과 테스트 파일을 바꾸거나 문서를 삭제하지 않는다. 실제 모바일 현상과 개별 수정의 연결은 확인된 만큼만 설명한다.

## 평가 결과와 완료 근거

- 사이트의 역할과 선정 기준: [소개 가치 평가의 entry 역할](references/assessment.md#appsentry의-역할과-개발-의도)에 현재 화면과 기존 선정 기록의 근거가 있다.
- 채용과 경험 서술 기준: [경력 프론트엔드 채용 조사](references/hiring-and-writing.md)에 여섯 기업의 요구와 자료의 확인일 및 모집 상태, 프로젝트 서술에 적용할 기준이 있다.
- 성과와 소개 문구: [소개 가치 평가](references/assessment.md)에 실제 목적, 직접 정한 기능과 입력 및 저장 문제 해결의 근거, 한국어 및 영어 초안과 추가 권고 이유가 있다. [사용 목적과 입력 문제](references/workflow-and-input.md)는 사용 경험과 드래그 문제의 전후 결과를 연결한다. [커밋별 평가](references/commit-assessment.md)와 [합친 이력](references/squashed-history.md)에 각 변경의 소개 가치가 있다.
- 실행 결과: 2026년 10월 2일 운영 빌드 후 저장, 복구와 분석의 기존 시나리오 다섯 개가 Chromium, Firefox와 WebKit에서 모두 통과했다. [실행 확인 범위](references/assessment.md#2026년-10월-2일-확인한-실행-결과)는 15개 실행과 과거 기록을 구분한다.

## 항목 추가를 선택할 때의 후속 적용안

이 절차는 항목 추가와 소개 문구를 선택한 뒤 적용할 제안이다. 현재 평가만으로 기존 소개 내용이나 선정 결정을 변경하지 않는다.

1. 소개 문구를 선택한다. [성과 후보와 소개안](references/assessment.md#independent-work에-실을-문구-제안)은 확인된 목적과 직접 정한 기여를 사용한다. 추가로 이용 성과나 개별 수정의 주도 역할을 쓰려면 [더 확인할 사실](references/commit-assessment.md#선정-판단과-확인할-사실)의 근거를 갖춘다. 문구와 항목 추가를 선택하면 다음 단계로 진행한다. 실행 주소 없이 소스 링크만 사용할 경우에도 링크가 무엇을 보여주는지 명확해야 한다.
2. 사이트 선정 기록을 반영한다. `docs/designs/developer-portfolio-f4b7/requirements.md`의 Independent Work에 필요한 변경을 제안하고, 문구가 확정되면 `decisions/project-availability.md`에 새 선정 이유를 반영한다. 메모 앱의 필수 제외 기록과 새 소개가 모순되지 않으면 완료다.
3. 소개 내용을 반영한다. `apps/entry/src/shared/terms/ko.json`과 `en.json`의 Independent Work 항목에 같은 목적, 결과, 기간과 소스 링크를 담는다. 기존 한 페이지 구성과 다른 항목의 기능을 유지한다. 텍스트 재사용의 목적과 확인된 결과가 기능 목록이나 기술 정보보다 앞서는지, 두 언어가 같은 내용을 전달하는지 확인한다.
4. 소개 화면을 확인한다. [개발 지침](../../dev/README.md)과 [Astro 구현 지침](../../dev/frontend/astro-fsd-tailwind.md)의 검사 및 빌드 기준을 적용하고, 한국어와 영어 화면에서 항목과 링크를 확인한다. 새 테스트 코드 작성이나 별도 상세 화면 제작은 이 제안에 포함하지 않는다.

## 평가를 멈추는 조건

성과 설명에 필요한 수치, 개인 기여 또는 이용 결과를 확인할 수 없으면 해당 주장을 보류한다. 확인 가능한 기능과 판단의 평가는 계속한다. 실제 항목 등록은 평가 이후의 별도 선택이다.
